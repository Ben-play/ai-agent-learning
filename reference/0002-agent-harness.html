Agent Harness 架构参考

Prompt Engineering 定义模型收到什么指令；Harness Engineering 定义围绕模型的运行、验证与恢复。两者互补，不是新旧替代关系。

什么是 Agent Harness？

Agent Harness 是围绕 LLM 的脚手架系统，决定 Agent 如何运行、何时停止、如何处理错误。它不是单个 Prompt，而是整个运行环境的设计。

例如，Anthropic 的长任务案例同时使用面向不同阶段的提示、外置进度记录和端到端验证。该案例是一种设计参考，不是统一架构标准。

四层教学视图

Layer 1: Agent Reasoning（推理层）

LLM 的核心推理能力。包括：

  • Chain-of-Thought 推理
  • Extended Thinking（深度推理）
  • 规划和决策能力
  • 自我反思和纠错

Layer 2: Context Engineering（上下文工程）

决定 Agent 能"看到"什么信息。包括：

  • 按模型和任务管理上下文窗口，保留工具交互和输出预算
  • 动态上下文加载和卸载
  • 记忆系统（短期/长期）
  • RAG 检索结果整合
  • 工具调用结果缓存

Layer 3: Tooling（工具层）

Agent 能"做"什么。包括：

  • 工具注册和发现（MCP 协议）
  • 工具调用调度和并发控制
  • 权限管理和安全沙箱
  • 工具执行结果处理

Layer 4: Persistence（持久化层）

Agent 的状态如何保存。包括：

  • 会话状态持久化
  • 检查点和恢复
  • 日志和可观测性
  • 审计追踪

Prompt Engineering vs Harness Engineering

Prompt Engineering：模型如何理解任务

  • 写清目标、约束和答案应该包含什么
  • 用任务集比较提示版本、示例和反例
  • 适用于单次调用，也适用于多轮循环中的每一步

Harness Engineering：应用如何执行和验证任务

  • 决定上下文来源、预算和终态
  • 在应用侧做工具权限校验、审批和受控执行
  • 记录结果并验证中断恢复，检查点不等于外部操作只生效一次

关键设计原则

  1. 可观测性优先：每个决策都要可追踪、可调试
  2. 优雅降级：工具失败时有备用方案
  3. 上下文效率：只加载必要的上下文，避免窗口溢出
  4. 安全边界：关键操作需要人工确认
  5. 状态管理：支持中断恢复和长时运行
