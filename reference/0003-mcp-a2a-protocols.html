MCP / A2A 协议参考

先明确要连接的是工具与数据，还是远程 Agent；再固定协议与 SDK 版本，不把“接上协议”当作授权或生产就绪。

核验日期：2026-11-06。MCP 规范基线：2026-07-28。 本页依据官方发布说明、变更记录、传输与授权规范；这是版本化参考，不是可运行 SDK 工程。Phase 6/10 正文仍在规划，所列实验是后续验收目标；SDK 是否支持本基线须单独验证。

先选集成边界

方式主要用途何时考虑
普通函数 / API应用内确定性操作不需要协议互操作时，保持最简单可行方案
MCP · Model Context ProtocolHost 经 Client 连接 Server，使用工具、资源和提示等标准接口多个宿主需要复用外部工具或数据接入
A2A · Agent-to-Agent Protocol远程 Agent 的发现、任务委托、状态与结果交互确有跨系统 Agent 互操作需求；本地并行或多 Agent 不自动需要 A2A
Agent Skills打包可复用的流程知识、参考资料与脚本复用“怎么做”的业务步骤；可调用工具/MCP，但本身不是传输或授权协议

MCP 与 A2A 可以互补，但不要求同时采用。协议标准化了交互方式，不自动保证对端可信、任务成功或细粒度业务权限。

MCP 核心概念与本版边界

  • Host / Client / Server：Host 是集成 MCP 的应用，Client 负责协议交互，Server 提供能力；不等于模型可绕过应用直接执行任意操作。
  • Tools / Resources / Prompts：分别用于工具操作、上下文资源与提示模板；工具定义、资源内容和返回结果均需校验，外部内容按不可信输入处理。
  • stdio：本地进程通过标准输入/输出通信；日志不要混入协议输出。凭证从环境获取，遵守最小权限并避免写入示例、日志或代码库。
  • Streamable HTTP：每条客户端 JSON-RPC 消息使用独立 POST；请求可返回 JSON 对象或请求范围内的 SSE 响应流，客户端须支持两者。
不要混用旧教程：2026-07-28 已移除 initialize / notifications/initialized 握手、协议级 session 和 MCP 端点的 GET 通知流；不等于移除了 SSE 响应。旧版 HTTP+SSE 传输与新版 Streamable HTTP 的 SSE 响应不是同一个概念。
  • 逐请求版本与能力：请求 _meta 携带 io.modelcontextprotocol/protocolVersion 和 io.modelcontextprotocol/clientCapabilities；Server 必须实现 server/discover，Client 可预先调用以了解版本和能力。
  • 无协议 session：不再依赖 Mcp-Session-Id；业务确需跨调用状态时用显式句柄等应用机制。Agent 的持久任务、审批状态与数据库检查点仍由应用负责。
  • 变更通知：使用 subscriptions/listen 的长时 POST 响应流接收已选择的变更通知；进度等请求范围通知留在对应请求的响应流。
  • Tasks：已从核心移到官方可选扩展 io.modelcontextprotocol/tasks，不是“非官方提案”，也不是所有客户端/服务端必有的能力。采用前核实扩展版本、双方支持和失败行为。

授权是独立的工程边界

MCP 授权能力在协议层面是可选的；采用 HTTP 授权时，官方要求实现应遵循该版授权规范（SHOULD），其中具体 MUST/SHOULD 按原文执行。不能把“可选”理解为企业受限资源可以不做鉴权。

场景应落实的边界验收目标
远程 HTTP 授权保护资源元数据与授权服务器发现、客户端注册、PKCE、目标 resource / audience、issuer 校验、最小 scope；OAuth 2.1 引用仍是 IETF 草案缺失/过期令牌被拒；错误 audience 或 issuer 失败；scope 不足不执行工具；审批不隐式扩大 scope
stdio 凭证不套用此 HTTP OAuth 流程，从环境取得所需凭证；宿主控制进程与环境可见范围缺凭证明确失败；无敏感值泄露；子进程只获得必要权限
业务执行授权应用与 Server 在执行前校验用户/租户、对象、动作、参数与审批状态；工具展示/发现不是授权已发现但无权执行的工具零执行；同名资源不能跨租户读取；高风险动作需要有效审批
下游系统令牌验证令牌确实面向当前 MCP Server，不接收/透传任意其他资源令牌；安全保存凭证并审计错误受众与越权调用失败，日志脱敏；不把 MCP 令牌当作所有下游 API 的通行证

“MCP 自动提供细粒度授权”是错误表述。协议授权流程不替代文档 ACL、行级权限、每次工具 dispatch 的允许集合或人工审批；即使模型/Skill 选择了工具，仍必须过执行侧检查。

跨版本迁移检查表

先记录旧规范、目标规范、客户端/服务端 SDK 锁定版本与运行环境。不要只升级依赖后假定兼容；规范发布日期也不是 SDK 已支持的证明。

检查项迁移到 2026-07-28应保留的测试证据
初始化与版本移除新版链路的 initialize 握手；逐请求传版本/能力，验证 server/discover 与不支持版本错误发现、兼容版本成功、不兼容版本可解释失败；旧版适配分支与新版不混用
HTTP 元数据按规范传 MCP-Protocol-Version、Mcp-Method 及适用的 Mcp-Name；头与 body 一致；工具指定 x-mcp-header 时遵循映射规则缺字段、头/body 不一致、编码边界被正确拒绝，不把所有 400 都当作旧版服务
协议 session移除 Mcp-Session-Id、依赖 session 的路由/清理；业务状态用显式机制管理跨连接调用不依赖隐式 session，应用检查点仍可恢复且租户隔离
通知流移除 MCP GET 流；变更通知改为 subscriptions/listen 的 POST 响应流订阅与请求进度分别走正确通道；新版端点不依赖 GET/DELETE session 流程
响应与断线同时处理 JSON / SSE；本版无 Last-Event-ID 恢复或消息重投，断流后以新请求 ID 重发完整响应、断流、取消、重发都有测试；可能已发生的业务副作用由幂等机制处理，不能仅换请求 ID
结果与补充输入适配 resultType 和 MRTR 补充输入；兼容早期结果缺 resultType 时按 complete 处理普通结果、input_required 与旧版结果分开覆盖，不等待旧式服务端主动请求
Tasks 与其他扩展核心和扩展分开；不沿用旧实验 Tasks API，按扩展规范及 SDK 实际支持选用不支持扩展时有明确降级；不以协议任务句柄冒充应用的持久恢复保证
HTTP 授权采用时按本版发现、注册、PKCE、resource/audience、issuer 与 scope 流程实现；stdio 单独处理401/403、错误受众/签发者、权限不足、用户取消与最小权限测试

若仍需支持 2025-11-25 等旧端点，应隔离并标注其版本流程。现代请求返回可识别的版本/头校验错误时，先按错误修正请求，不盲目降级到旧握手。完整兼容规则见官方传输文档。

SDK 与最小实验

原页将未定义的 server / agent 与假定导入混在一起，不能直接执行，现已移除。这里不虚构替代 API；从官方 SDK 的对应版本示例开始，锁定依赖，再逐步增加能力。

  1. 查官方 SDK 的发行说明与所支持规范：MCP Python SDK、MCP TypeScript SDK。若尚未支持目标版，保留明确标注的旧版实验，不谎称已完成迁移。
  2. 本地只用无敏感数据、无外部副作用的测试工具，验证发现 → 列表 → 调用 → 结构化结果/错误；无密钥的协议 fixture 与真实互操作测试分别记录。
  3. 按上表测试 JSON/SSE、版本不兼容、断线重发、权限拒绝与幂等；记录规范、SDK、测试配置和未测项。

A2A：按需了解

A2A 面向远程 Agent 互操作，关注能力发现、任务委托、状态与产出。先证明单 Agent 不足，再决定是否需要远程委托；认证、信任边界与业务授权仍要设计。本页未逐版本审查 A2A，不提供假定可运行的 SDK 样例；实现时另固定其规范与 SDK 版本，参见A2A 官方文档与官方仓库。
