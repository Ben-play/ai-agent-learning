Streaming 流式输出

让回复像 ChatGPT 一样逐字往外蹦，而不是干等一大段

💡 为什么这课重要？

上一课（L25）你学会了发一串 messages、收一条回复。但你有没有发现一个体验问题：如果模型要写 500 字，你得干等到整段生成完才看到第一个字——短则两三秒，长则十几秒，界面一直转圈，用户以为卡死了。

流式输出（Streaming）把回复分块发送，不必等整段写完才给用户看。这样可以降低首字延迟（TTFT），但先看到字不代表已经得到可交付结果。本课会对照三种接口的增量、用量和成功终态。

学习目标

完成本课后，你将能够：

  • 说清流式 vs 非流式的差别，以及为什么流式能降低首字延迟（TTFT）
  • 理解流式底层是 SSE（Server-Sent Events）：服务端把回复切成一串 chunk 推过来
  • 用 Chat Completions 开启 stream=True，区分有候选的增量块和只带用量的尾块
  • 区分 Responses、Chat Completions 与 Messages 的增量和终态，知道何时才能交付正文
  • 避开三个工程坑：usage 统计、流式 Function Calling、中途断流

1. 为什么要流式：把"干等"变成"边看边等"

一次 LLM 调用其实要花不少时间生成 token。非流式模式下，服务端攒齐整段回复才一次性返回——你的用户面对的是一个转圈的加载框，回复越长等得越久，中途还完全看不到任何进展。

流式则相反：模型逐 token 边生成边返回，每生成一小块就立刻推给客户端，客户端收到就立刻显示。于是用户几乎立刻看到字往外蹦——就像 ChatGPT 那样。

非流式：  [用户提问] ──等 8 秒（黑屏转圈）──> [唰！一次性出现 500 字]
流式：    [用户提问] ─等 0.3 秒─> 字 字 字 字 字 …… 边生成边显示，一路到底
                                  ↑ 首字延迟(TTFT)极低，体验天差地别

关键指标叫 TTFT（Time To First Token，首字延迟）：从发请求到看到第一个 token的时间。流式把用户的"感知等待"从"整段总时长"压到了"首字时间"。总生成时间没变，但体验完全不同——这就是流式的核心价值。

💡 一个直觉：流式不会让模型"算得更快"，它改变的是你什么时候开始看到结果。对话类、长文生成、Agent 的思考展示——凡是"人在盯着屏幕等"的场景，流式几乎是标配。

2. 原理：流式跑在 SSE 上

流式不是什么黑魔法，它基于一个成熟的 Web 协议：SSE（Server-Sent Events，服务器推送事件）。机制很简单：客户端发一次请求，服务端不立刻关闭连接，而是把回复切成一串 chunk 事件，一个接一个地"推"过来；客户端逐个接收、增量拼接，直到收到结束标志。

客户端 ──一次请求──> 服务端
       <── data: {chunk 1}      "写"
       <── data: {chunk 2}      "一首"
       <── data: {chunk 3}      "短诗"
       <── data: [DONE]         Chat Completions 的 SSE 结束标记；不是 Responses 的完成事件。
       （同一条连接，事件一个一个流过来）

这正好呼应你前面学过的两块基础：

  • L15 · httpx SSE——SSE 就是流式的传输层。当你不用高层 SDK、直接打 HTTP 时，收到的就是一行行 data: {...} 的事件流，需要自己逐行解析。SDK 只是帮你把这层封装好了。
  • L12 · 生成器——用 for chunk in stream: 逐块消费。是否累积整段回复取决于消费代码和 SDK：只预览可以逐块处理，要求验收后一次交付则可以先缓冲。

一句话：SSE 负责"怎么把 chunk 推过来"，生成器负责"怎么在 Python 里一块块拿出来"。

Q LLM 流式输出底层依赖的是哪种机制？
流式跑在 SSE（Server-Sent Events）上：客户端发一次请求，服务端保持连接、把回复切成一串 chunk 事件单向推过来，客户端逐个收、增量拼接（呼应 L15 httpx SSE）。它不是轮询（那要发很多次请求），也不是一次性返回（那就不叫流式了）；虽然 WebSocket 也能做，但 LLM 流式的行业标准是 SSE——单向推送足矣，更简单。

3. Chat Completions：读取增量、用量和终止原因

把 L25 的单候选纯文本 Chat 调用改为 stream=True。下面的消费函数可以离线测试；可选联网片段接在它后面运行，需要凭证和预算。只有预览分支会逐块显示；正式正文在验收后一次返回。

def collect_chat(chunks, *, preview=None):
    parts, finish_reason, usage = [], None, None
    refused = False
    for chunk in chunks:
        if chunk.usage is not None:
            usage = chunk.usage
        if not chunk.choices:                  # 仅带 usage 的尾块没有候选
            continue
        choice = chunk.choices[0]              # 本例只有一个候选
        if choice.delta.refusal:
            refused = True
        delta = choice.delta.content
        if delta and not refused:
            parts.append(delta)
            if preview is not None:           # 仅用于标成临时的界面预览
                preview(delta)
        if choice.finish_reason is not None:
            finish_reason = choice.finish_reason
    if refused:
        raise ValueError("Chat 拒答")
    if finish_reason != "stop" or not parts:
        raise ValueError(f"Chat 无完整文本: {finish_reason}")
    return "".join(parts), usage
import os
from openai import OpenAI

client = OpenAI()
with client.chat.completions.create(
    model=os.environ["OPENAI_MODEL"],
    messages=[{"role": "user", "content": "写一首短诗"}],
    stream=True, stream_options={"include_usage": True},
) as stream:
    text, usage = collect_chat(stream)
print(text)
print(usage)
  • 先读用量，再检查 choices 是否为空；单独的用量块不是成功终态。
  • 正文是 delta.content，不是 message.content；角色块和结束块的正文可能是 None。
  • 只有 finish_reason == "stop" 且未拒答才交付正文。纯展示可用 preview 降低感知等待，见第 6 节；它不能写入正式历史或触发动作。
📖 上面是 Chat Completions 的兼容接口示例，不要把它的 choices[0].delta 套到 Responses。官方流式指南按事件类型分别定义文本增量、完成与失败；只有收到正常终态，才能把临时显示的文本当成完整结果。

3.1 Responses 实践：按类型消费，按终态验收

延续 L25 的 OpenAI 主线。增量只在本地缓冲，不预览；只有收到 response.completed、状态为 completed，且没有拒答，才返回正文和用量。即使已经收到正文增量，也要检查结束对象里所有消息 Item 的内容块。

def collect_responses(events):
    parts = []
    for event in events:
        if event.type == "response.output_text.delta" and event.delta:
            parts.append(event.delta)
        elif event.type in {"response.failed", "response.incomplete", "error"}:
            raise ValueError(f"Responses 流未完成: {event.type}")
        elif event.type in {"response.refusal.delta", "response.refusal.done"}:
            raise ValueError("Responses 拒答")
        elif event.type == "response.completed":
            response = event.response
            if response.status != "completed":
                raise ValueError(f"Responses 流未完成: {response.status}")
            if any(part.type == "refusal" for item in response.output
                   if item.type == "message" for part in item.content):
                raise ValueError("Responses 拒答")
            if not parts:
                raise ValueError("Responses 无正文增量")
            return "".join(parts), response.usage
    raise ValueError("Responses 缺少完成事件")

4. Anthropic 流式：形状不同，概念一致

Claude 的 text_stream 只提供文本增量，适合临时预览，不能据此确认成功。这里迭代完整事件流，用 message_stop 确认消息到达末尾，再通过 SDK 的 get_final_message() 检查停止原因，得到可交付的正文和用量。

def collect_messages(stream):
    saw_stop = False
    for event in stream:
        if event.type == "message_stop":
            saw_stop = True
    if not saw_stop:
        raise ValueError("Messages 缺少 message_stop")
    message = stream.get_final_message()
    if message.stop_reason != "end_turn":
        raise ValueError(f"Messages 未正常结束: {message.stop_reason}")
    text = "".join(block.text for block in message.content if block.type == "text")
    if not text:
        raise ValueError("Messages 无正文")
    return text, message.usage

Q Chat Completions 流式里，应怎样读取正文增量？
先确认 choices 非空，再取 choices[0].delta.content。角色块和结束块的增量可能为 None；只带用量的尾块则连候选也没有。

5. 工程注意：流式带来的三个坑

流式体验好，但工程上有三件事和非流式不一样，提前知道能少踩坑：

  • ① Token 用量（usage）。Chat Completions 的 stream_options={"include_usage": True} 请求末尾的用量块；它的 choices 为空，不是正文，也不是成功终态。Responses 和 Messages 分别从完成事件、最终消息读用量；断流时可能拿不到完整统计。这直接影响你按 L23 算成本。
  • ② 流式里做 Function Calling 更麻烦。工具调用的参数（一段 JSON）也是切成 delta 一块块推的，你得把这些 tool_calls 的增量片段按 index 拼起来，拼完整才能解析成参数。这个细节在 L27 Function Calling 起步、到 L36 工具健壮性里会真正用到——这里先埋个点，知道"流式 + 工具调用要增量拼参数"即可。
  • ③ 出错处理：流到一半断了怎么办？ 非流式也可能返回截断结果，但流式还有一个问题：连接断开时，界面可能早已展示了半句。标记预览失败、避免写入半成品，并考虑超时和重试去重，见 L31 重试/超时/退避。

一句话总结这三坑：usage 挪到了末尾、工具参数要拼、断流要有兜底。它们不难，但不知道就会在生产里被咬一口。

决策卡：可以预览，不等于可以入库

适用：同一条工单摘要既供人预览，又要写入正式记录。不适用：无人等待的批处理不必做逐字预览，直接用非流式终态验收更简单。

误判：收到字就逐块保存

工单摘要已收到半句，连接却断了。保存增量会留下不完整记录，重试还可能写重复。

对照：预览和正式记录分两条路

同一断流可让临时预览标为中断；不写正式记录。只有正常终态且未拒答，才交付一次完整摘要。

取舍：临时预览换首字体验；缓冲增加内存和交付等待，换来可检验的完整性。若连预览也不应出现，像本课 Responses 示例一样等终态再显示。

  1. 运行下方验收，先给增量配正常终态。
  2. 保留相同增量，改成断流、截断或后置拒答，比较返回值和预览。

结果诊断：正常流只交付一次正文；失败流无正文返回。有字仍入库，先查是否把预览或 EOF 当成了完成信号。

from types import SimpleNamespace as Record


def reject(run, expected):
    try:
        run()
    except ValueError as exc:
        assert str(exc) == expected, exc
    else:
        raise AssertionError(f"不应交付正文: {expected}")


usage = Record(input_tokens=9, output_tokens=2)
delta = Record(type="response.output_text.delta", delta="摘")
more = Record(type="response.output_text.delta", delta="要")
text_item = Record(type="message", content=[Record(type="output_text", text="摘要")])
refusal_item = Record(type="message", content=[Record(type="refusal", refusal="未提供答案")])


def terminal(kind, status, output):
    return Record(type=kind, response=Record(status=status, output=output, usage=usage))

assert collect_responses(iter([delta, more, finished])) == ("摘要", usage)
reject(lambda: collect_responses(iter([delta])), "Responses 缺少完成事件")
for kind in ("response.failed", "response.incomplete", "error"):
    reject(lambda: collect_responses(iter([delta, Record(type=kind)])), f"Responses 流未完成: {kind}")
not_done = terminal("response.completed", "incomplete", [text_item])
reject(lambda: collect_responses(iter([delta, not_done])), "Responses 流未完成: incomplete")

    reject(lambda: collect_responses(iter([delta, Record(type=kind), finished])), "Responses 拒答")
reject(lambda: collect_responses(iter([finished])), "Responses 无正文增量")


def chunk(text=None, *, finish=None, refusal=None):
    choice = Record(delta=Record(content=text, refusal=refusal), finish_reason=finish)
    return Record(choices=[choice], usage=None)

Q 关于流式模式下的 Token 用量（usage），下面哪种说法对？
Chat Completions 用 stream_options={"include_usage": True} 请求仅带用量的尾块，choices 为空。Responses 和 Messages 在各自的终态附近提供用量；断流可能没有完整统计，不能用尾块来推断文本成功。

6. 和 Agent 的关系：流式是"能被看见"和"能被边解析"的前提

你可能觉得流式只是"好看"，但对 Agent 它有两层实打实的价值：

  • 临时预览（给人看）：长回复可以边收边显示，降低感知等待。中断时标明预览不完整，不把它写进正式历史。
  • 增量准备（给程序用）：可以先缓存文本或按索引拼工具参数；即使片段看起来已是合法 JSON，也要等正常终态，再验结构和权限后才执行工具或写入。

有进展和交付成功是两件事。预览能否提前显示由任务规则决定；正式记录始终单独验收。

🎤 面试高频：「Streaming 的好处是什么？」 标准答法：① 降低首字延迟（TTFT），用户更早看到第一个字；② 改善长回复体验，把等待变成可见进展；③ 支持边收边准备，如拼接工具参数。SSE 逐块推送，但不保证更短的总生成时间。
变式追问：如果要求模型拒答或断流时一个字也不能显示，还能用打字机预览吗？不能；可以继续流式接收并缓冲，正常完成后才显示，代价是用户看不到生成中的字。

同一公告第一次遇到 length，虽有用量尾块，也只能留下临时预览；第二次正常完成才允许写一次公告。用第 3 节 collect_chat 作为消费函数，接上可复制的起点，实现 deliver(chunks, preview, posted)：两份列表分别记录预览增量与已发布全文，返回是否发布。全程离线，没有 SDK 或真实公告系统。

from types import SimpleNamespace as Record


def chunk(text=None, *, finish=None):
    choice = Record(delta=Record(content=text, refusal=None), finish_reason=finish)
    return Record(choices=[choice], usage=None)


usage_only = Record(choices=[], usage=Record(total_tokens=15))
cut_off = [chunk("东门柜台"), chunk(finish="length"), usage_only]
complete = [chunk("东门柜台"), chunk("恢复服务。"), chunk(finish="stop"), usage_only]
# TODO: deliver(chunks, preview, posted)；只在 collect_chat 返回全文后发布。
展开独立参考与断言（接在起点后运行）
def deliver(chunks, preview, posted):
    try:
        text, _ = collect_chat(iter(chunks), preview=preview.append)
    except ValueError:
        return False
    posted.append(text)
    return True


preview, posted = [], []
assert not deliver(cut_off, preview, posted)
assert preview == ["东门柜台"] and posted == [], (preview, posted)
preview = []  # 显式重试时，新预览不拼接上一次的片段。
assert deliver(complete, preview, posted)
assert preview == ["东门柜台", "恢复服务。"], preview
assert posted == ["东门柜台恢复服务。"], posted

🎯 速查卡：流式输出

【SSE】一次请求，逐块推送；临时预览可降低首字延迟（TTFT）。

【Chat Completions】先取 usage；choices 为空就跳过候选读取。
  非空 delta.content 才拼接；纯文本验 finish_reason == "stop" 且无拒答。

【Responses】缓冲 response.output_text.delta；等 response.completed。
  验状态 completed、遍历消息排除 refusal；失败、截断或缺终态不交付。

【Messages】text_stream 可供预览；验收看 message_stop 和最终 stop_reason。
  纯文本只接受 end_turn；max_tokens 或 refusal 不交付。

【三个工程坑】用量不等于完成；工具参数按索引拼；断流重试避免重复副作用。

总结

  • 流式 = 逐 token 边生成边返回，用户立刻看到字往外蹦，首字延迟（TTFT）大幅降低
  • 底层是 SSE：服务端把回复切成一串 chunk 推过来，客户端逐块收、增量拼接（呼应 L15/L12）
  • Chat 的仅用量块没有候选；先判候选和增量非空，再确认 stop 且未拒答。
  • Responses 检查完成事件、响应状态和拒答；Messages 检查 message_stop 和最终 end_turn。
  • 先拼增量，正常终态后才交付；临时预览、用量统计和实际副作用分别处理。
