Streaming 流式输出

让回复像 ChatGPT 一样逐字往外蹦，而不是干等一大段

💡 为什么这课重要？

上一课（L25）你学会了发一串 messages、收一条回复。但你有没有发现一个体验问题：如果模型要写 500 字，你得干等到整段生成完才看到第一个字——短则两三秒，长则十几秒，界面一直转圈，用户以为卡死了。

ChatGPT 为什么感觉"快"？因为它不等全部写完——字是一个一个往外蹦的。这就是流式输出（Streaming）：模型每生成一小块就立刻推给你，用户几乎立刻看到第一个字（首字延迟 TTFT 大幅降低）。这一课我们讲清它的原理（SSE）、两家 SDK 的正确写法（已核对 openai 2.x），以及工程上真正会踩的坑。对 Agent 来说，"打字机效果"和"边生成边解析"都靠它。

学习目标

完成本课后，你将能够：

  • 说清流式 vs 非流式的差别，以及为什么流式能降低首字延迟（TTFT）
  • 理解流式底层是 SSE（Server-Sent Events）：服务端把回复切成一串 chunk 推过来
  • 用 openai SDK 开启 stream=True，正确从 chunk.choices[0].delta.content 取增量并判空
  • 知道 Anthropic 的流式写法（messages.stream + text_stream），理解两家形状不同、概念一致
  • 避开三个工程坑：usage 统计、流式 Function Calling、中途断流

1. 为什么要流式：把"干等"变成"边看边等"

一次 LLM 调用其实要花不少时间生成 token。非流式模式下，服务端攒齐整段回复才一次性返回——你的用户面对的是一个转圈的加载框，回复越长等得越久，中途还完全看不到任何进展。

流式则相反：模型逐 token 边生成边返回，每生成一小块就立刻推给客户端，客户端收到就立刻显示。于是用户几乎立刻看到字往外蹦——就像 ChatGPT 那样。

非流式：  [用户提问] ──等 8 秒（黑屏转圈）──> [唰！一次性出现 500 字]
流式：    [用户提问] ─等 0.3 秒─> 字 字 字 字 字 …… 边生成边显示，一路到底
                                  ↑ 首字延迟(TTFT)极低，体验天差地别

关键指标叫 TTFT（Time To First Token，首字延迟）：从发请求到看到第一个 token的时间。流式把用户的"感知等待"从"整段总时长"压到了"首字时间"。总生成时间没变，但体验完全不同——这就是流式的核心价值。

💡 一个直觉：流式不会让模型"算得更快"，它改变的是你什么时候开始看到结果。对话类、长文生成、Agent 的思考展示——凡是"人在盯着屏幕等"的场景，流式几乎是标配。

2. 原理：流式跑在 SSE 上

流式不是什么黑魔法，它基于一个成熟的 Web 协议：SSE（Server-Sent Events，服务器推送事件）。机制很简单：客户端发一次请求，服务端不立刻关闭连接，而是把回复切成一串 chunk 事件，一个接一个地"推"过来；客户端逐个接收、增量拼接，直到收到结束标志。

客户端 ──一次请求──> 服务端
       <── data: {chunk 1}      "写"
       <── data: {chunk 2}      "一首"
       <── data: {chunk 3}      "短诗"
       <── data: [DONE]         结束（OpenAI 用 [DONE]；Anthropic 用 message_stop 事件）
       （同一条连接，事件一个一个流过来）

这正好呼应你前面学过的两块基础：

  • L15 · httpx SSE——SSE 就是流式的传输层。当你不用高层 SDK、直接打 HTTP 时，收到的就是一行行 data: {...} 的事件流，需要自己逐行解析。SDK 只是帮你把这层封装好了。
  • L12 · 生成器——生成器天然适合逐块 yield。所以各家 SDK 的流式返回值都是一个可迭代对象：你用 for chunk in stream: 一块一块地取，取一块处理一块，内存里从不驻留整段回复。语言基础和 API 设计在这里完美对上了。

一句话：SSE 负责"怎么把 chunk 推过来"，生成器负责"怎么在 Python 里一块块拿出来"。

Q LLM 流式输出底层依赖的是哪种机制？
流式跑在 SSE（Server-Sent Events）上：客户端发一次请求，服务端保持连接、把回复切成一串 chunk 事件单向推过来，客户端逐个收、增量拼接（呼应 L15 httpx SSE）。它不是轮询（那要发很多次请求），也不是一次性返回（那就不叫流式了）；虽然 WebSocket 也能做，但 LLM 流式的行业标准是 SSE——单向推送足矣，更简单。

3. OpenAI 流式：一个 stream=True 搞定

把 L25 的非流式调用改成流式，只加一个参数、把取值方式换一下（已核对 openai 2.x 写法）：

from openai import OpenAI

client = OpenAI()   # 仍然读 OPENAI_API_KEY，别硬编码（L25 铁律）

stream = client.chat.completions.create(
    model="gpt-5.5",                          # 型号以官网为准，别写死
    messages=[{"role": "user", "content": "写一首短诗"}],
    stream=True,                              # ← 开启流式，返回值变成可迭代
)

for chunk in stream:                          # 逐块取（生成器，L12）
    delta = chunk.choices[0].delta.content    # ← 增量片段，可能是 None
    if delta:                                 # ← 必须判空，否则会拼进 "None"
        print(delta, end="", flush=True)      # 逐块打印，别换行、立刻刷新

三个必须记住的点：

  • 正文在 chunk.choices[0].delta.content——注意是 delta（增量），不是非流式的 message。每个 chunk 只带这一小块新增的文字，你要自己把它们首尾相接。
  • delta.content 可能是 None——比如第一个 chunk 常常只带角色信息、末尾 chunk 带结束原因，正文是空的。所以一定要 if delta: 判空，否则 print 会把字符串 "None" 也拼进去。这是新手最常见的 bug。
  • print(delta, end="", flush=True)——end="" 保证不换行（否则每块一行就乱了）；flush=True 强制立刻输出到终端，才有"逐字蹦"的效果，不然会被缓冲攒着。

要拿到完整文本？边打印边 full += delta 累积即可。流式的本质就是：把一次"大返回"拆成 for 循环里的一串"小增量"，你负责拼。

📖 官方权威写法见 OpenAI · Streaming responses。里面还讲了 Responses API 的流式事件模型（response.output_text.delta 等），概念一致、字段名不同——记住"取 delta、判空、拼接"这个心法就能举一反三。

4. Anthropic 流式：形状不同，概念一致

Claude 的流式写法长得不太一样，但你会发现内核完全相同：还是"逐块取增量、自己拼"。它用一个上下文管理器，并贴心地提供了一个只吐文本的迭代器 text_stream：

from anthropic import Anthropic

client = Anthropic()   # 读 ANTHROPIC_API_KEY

with client.messages.stream(                  # ← 用 stream()，配 with 上下文
    model="claude-sonnet-4-6",                # 型号以官网为准
    max_tokens=1024,                          # Anthropic 必填（L25 差异①）
    messages=[{"role": "user", "content": "写一首短诗"}],
) as stream:
    for text in stream.text_stream:           # ← 直接拿到文本增量，无需判空
        print(text, end="", flush=True)

对比一下两家，你就抓住了流式的"不变量"与"可变量"：

  • 不变（概念）：都是 SSE 推 chunk、都用 for 循环逐块取增量、增量拼接、都能立刻显示。
  • 可变（形状）：OpenAI 是 stream=True + 直接迭代 + 手动取 delta.content 并判空；Anthropic 是 messages.stream(...) + with 上下文 + text_stream 直接给文本。

所以别去死记两套 API——记住「逐块取增量 → 拼接 → 立刻显示」这一条心法，换任何厂商都只是查一下"增量字段叫什么、要不要判空"而已。

Q OpenAI 流式里，每个 chunk 的正文增量该从哪取、要注意什么？
流式下正文在 chunk.choices[0].delta.content——是 delta（增量），不是非流式的 message.content，每块只带新增的一小段。而且它可能是 None（首块带角色、末块带结束原因，正文为空），所以必须 if delta: 判空后再拼接/打印，否则会把字符串 "None" 混进结果。这是流式最经典的坑。

5. 工程注意：流式带来的三个坑

流式体验好，但工程上有三件事和非流式不一样，提前知道能少踩坑：

  • ① Token 用量（usage）统计变了。非流式一返回就有 usage；流式下正文一路是 delta，用量通常出现在最后一个 chunk，或需要单独开启（OpenAI 要传 stream_options={"include_usage": True} 才会在末尾多推一个带 usage 的 chunk）。别在循环中途读 usage——那时它还没来。这直接影响你按 L23 算成本。
  • ② 流式里做 Function Calling 更麻烦。工具调用的参数（一段 JSON）也是切成 delta 一块块推的，你得把这些 tool_calls 的增量片段按 index 拼起来，拼完整才能解析成参数。这个细节在 L27 Function Calling 起步、到 L36 工具健壮性里会真正用到——这里先埋个点，知道"流式 + 工具调用要增量拼参数"即可。
  • ③ 出错处理：流到一半断了怎么办？ 非流式是"要么全拿到、要么整个失败"；流式则可能已经收了半段、连接突然断了。你手里是部分结果——要考虑：是把已收到的展示出来，还是重试？重试又可能重复。健壮的流式要包 try/except、设超时、想清楚部分结果 + 重试的策略。这属于容错话题，L31 重试/超时/退避会系统讲。

一句话总结这三坑：usage 挪到了末尾、工具参数要拼、断流要有兜底。它们不难，但不知道就会在生产里被咬一口。

Q 关于流式模式下的 Token 用量（usage），下面哪种说法对？
流式下正文是一路 delta，用量通常出现在最后一个 chunk，或需要单独开启（OpenAI 需传 stream_options={"include_usage": True}，才会在流末尾多推一个带 usage 的 chunk）。所以它能拿到，只是不像非流式那样一返回就有；也不是每块都带、更不在首块。算成本（L23）时要注意等到流结束再读。

6. 和 Agent 的关系：流式是"能被看见"和"能被边解析"的前提

你可能觉得流式只是"好看"，但对 Agent 它有两层实打实的价值：

  • 打字机效果（给人看）：Agent 常要输出长回复、展示"正在思考"的过程。流式让用户立刻看到进展，而不是盯着转圈——交互式 Agent、聊天助手几乎都开流式。
  • 边生成边解析（给程序用）：更进阶的玩法是不等模型说完就开始处理——比如流式解析模型正在吐的结构化输出（JSON），或在工具调用参数刚拼够时就提前准备执行。这让 Agent 的响应链路更短、更灵敏。它依赖的正是"增量到达、增量处理"这个流式本质。

所以流式不只是 UI 糖：它是 Agent "能被人看见"（打字机）和 "能被程序边收边用"（流式解析）的共同前提。学完这一课，你已经具备把 L25 的普通调用升级成"活的、会蹦字的"调用的能力。

✅ 参考答案（先自己写，再对照） 
from openai import OpenAI
client = OpenAI()

stream = client.chat.completions.create(
    model="gpt-5.5",
    messages=[{"role": "user", "content": "用三句话介绍一下向量数据库"}],
    stream=True,                                   # ① 开启流式
)

full = ""
for chunk in stream:
    delta = chunk.choices[0].delta.content         # ② 取增量
    if delta:                                      #    判空（可能是 None）
        print(delta, end="", flush=True)           # ③ 逐字打印，不换行、立刻刷新
        full += delta                              # ④ 累积完整回复

print()                                            # 收尾换个行
print(f"共 {len(full)} 字")

核心就三步：stream=True 开启、delta.content 判空后取、end="" flush=True 逐字打印。想在 Anthropic 上做？把中间换成 with client.messages.stream(...) as stream: for text in stream.text_stream: 即可——心法不变。

🎤 面试高频：「Streaming 的好处是什么？」 标准答法：① 降低首字延迟（TTFT），用户几乎立刻看到第一个字；② 改善长回复体验，把"干等整段"变成"边看边等"；③ 支持边生成边处理（如流式解析结构化输出 / 工具调用参数）。本质上它是把回复经 SSE 逐块推送、客户端增量拼接——总生成时间没变，但感知等待大幅下降。

  • 流式 = 逐 token 边生成边返回，用户立刻看到字往外蹦，首字延迟（TTFT）大幅降低
