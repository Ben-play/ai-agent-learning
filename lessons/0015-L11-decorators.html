装饰器 — Agent 框架的基石

@tool、@chain、@agent 都是装饰器 — 看懂它，你就看懂了半个框架源码

💡 为什么这课重要？

翻开任何 Agent 框架，满眼都是 @tool、@chain、@agent、@retry——它们全是装饰器。装饰器让你"给函数加一层包装"而不改函数本身：加日志、加重试、加计时、把普通函数注册成工具。

本课是 Part B 的收官，也是闭包（L06）的实战出口：装饰器 = 返回闭包的高阶函数。学完你会亲手写一个 @tool，从函数签名自动生成工具 Schema——这正是框架在幕后做的事。

学习目标

完成本课后，你将能够：

  • 解释装饰器的本质（闭包 + 高阶函数）
  • 写基础装饰器，并用 functools.wraps 保留元信息
  • 写带参数的装饰器（三层结构）
  • 理解多层装饰器的叠放顺序
  • 手写一个 @tool，从类型注解提取参数 Schema

1. 装饰器的本质

装饰器就是一个"接收函数、返回新函数"的函数。@deco 只是 fn = deco(fn) 的语法糖：

import functools

def timed(fn):
    @functools.wraps(fn)              # 保留原函数的名字/文档（关键！）
    def wrapper(*args, **kwargs):     # 用 *args/**kwargs 接住任意签名（呼应 L05）
        import time
        start = time.perf_counter()
        result = fn(*args, **kwargs)  # 调用原函数
        dur = time.perf_counter() - start
        print(f"{fn.__name__} 耗时 {dur:.4f}s")
        return result
    return wrapper                    # 返回的 wrapper 是个闭包（记住了 fn）

@timed
def search(query):
    return f"结果: {query}"

# 等价于 search = timed(search)
search("ai")                # search 耗时 0.0000s
print(search.__name__)      # search  ← 因为用了 wraps，否则会变成 'wrapper'

三个要点：① wrapper 是闭包（记住了外层的 fn）；② 用 *args/**kwargs 才能包装任意函数；③ 一定加 @functools.wraps(fn)，否则被装饰函数的 __name__、__doc__ 会被 wrapper 覆盖。

Q @deco 写在 def f 上方，等价于什么？
@deco 是语法糖，等价于把 f 传给 deco、再把返回值赋回 f——即 f = deco(f)。之后你调用的 f 其实是装饰器返回的新函数（通常是个闭包 wrapper）。

2. 带参数的装饰器（三层）

想写 @retry(times=3) 这种"能传参"的装饰器，需要多一层：最外层收参数，返回一个真正的装饰器：

import functools

def retry(times):                     # ① 收装饰器参数
    def deco(fn):                     # ② 真正的装饰器（收函数）
        @functools.wraps(fn)
        def wrapper(*args, **kwargs): # ③ 包装逻辑
            err = None
            for _ in range(times):
                try:
                    return fn(*args, **kwargs)
                except Exception as e:
                    err = e
            raise err
        return wrapper
    return deco

@retry(times=3)                       # 先调用 retry(3) 得到 deco，再用 deco 装饰
def flaky():
    ...

记忆：不带参数的装饰器两层，带参数的三层。多出来的最外层就是用来"接收装饰器自己的参数"。

3. 多层装饰器的顺序

@timed        # 后执行（外层）
@retry(times=3)   # 先执行（内层，离函数近）
def call():
    ...

# 等价于：call = timed(retry(times=3)(call))
# 装饰：自下而上包裹；调用：自上而下进入

规则：离函数最近的装饰器最先"套"上去（内层），最上面的最后套（最外层）。运行时，请求从最外层往里穿过每一层。

💡 面试常见问题：

"为什么装饰器里几乎总要写 @functools.wraps(fn)？"

答：不写的话，被装饰函数的 __name__、__doc__、签名等会被内层 wrapper 覆盖，导致调试、文档、以及"靠反射读函数信息"的框架（比如从函数生成工具 Schema）全部失灵。wraps 把这些元信息复制回来。

4. @tool：从函数生成工具 Schema

这是装饰器在 Agent 里最经典的用法——把普通函数注册成工具，并读取它的类型注解自动生成参数 Schema（喂给 LLM）：

import functools, inspect

REGISTRY = {}

def tool(fn):
    sig = inspect.signature(fn)                  # 读函数签名（L05 的签名在这里被"消费"）
    params = {}
    for pname, p in sig.parameters.items():
        params[pname] = {
            "type": getattr(p.annotation, "__name__", "any"),
            "required": p.default is inspect.Parameter.empty,
        }
    REGISTRY[fn.__name__] = {
        "name": fn.__name__,
        "doc": (fn.__doc__ or "").strip(),
        "params": params,
    }
    @functools.wraps(fn)
    def wrapper(*args, **kwargs):
        return fn(*args, **kwargs)
    return wrapper

@tool
def web_search(query: str, max_results: int = 5) -> dict:
    "搜索网页并返回结果"
    return {"query": query, "n": max_results}

print(REGISTRY["web_search"])
# {'name': 'web_search', 'doc': '搜索网页并返回结果',
#  'params': {'query': {'type': 'str', 'required': True},
#             'max_results': {'type': 'int', 'required': False}}}
🔑 Agent 开发关联：

这就是 LangChain 的 @tool、Pydantic AI 的工具注册在幕后做的事：装饰器读取你的函数签名（L05）+ 类型注解（L13）+ docstring，自动生成 LLM 能理解的工具描述。到 L14 用 Pydantic 后，这个 Schema 会更严谨（带校验、可导出标准 JSON Schema）。Part B 到这里闭环了。

Q @tool 装饰器靠什么读出函数的参数信息？
用 inspect.signature(fn) 读取函数的参数名、类型注解、默认值——这是"反射"。装饰器据此自动生成工具 Schema，无需你手写。这也是为什么 L05 强调"函数签名就是工具契约"、以及为什么装饰器必须用 functools.wraps 保住元信息。

知识图谱

装饰器本质
├── @deco 等价 f = deco(f)（语法糖）
├── 返回闭包 wrapper（记住 fn，← L06）
├── wrapper(*args, **kwargs) 接任意签名（← L05）
└── @functools.wraps(fn) 保留 __name__/__doc__/签名（必写）

带参数装饰器 → 三层（外层收参数）
多层装饰器 → 离函数近的先套；调用自外向内

@tool（Agent 经典用法）
├── inspect.signature 读签名（反射）
├── 类型注解 → 参数 type（← L13）
├── docstring → 工具描述
└── 生成 Schema 喂 LLM（→ L14 Pydantic 更严谨）

实战练习

练习：手写 @tool 装饰器

实现一个工具注册装饰器，自动收集函数名、参数 Schema（从 type hints 提取）、描述，构建工具注册表。先自己写，再看答案。

任务清单

  1. tool 装饰器：用 inspect.signature 读参数
  2. 每个参数记录：类型名（从注解）、是否必填（有无默认值）、默认值
  3. 从 docstring 取工具描述
  4. 存进全局 REGISTRY（工具名 → 描述+schema）
  5. 用 functools.wraps，保证被装饰函数仍可正常调用
  6. 加一个 get_schemas() 返回所有工具的 schema 列表（模拟"喂给 LLM 的工具清单"）
💡 点击查看参考答案 
import functools, inspect

REGISTRY = {}

def tool(fn):
    sig = inspect.signature(fn)
    params = {}
    for name, p in sig.parameters.items():
        ann = p.annotation
        has_default = p.default is not inspect.Parameter.empty
        params[name] = {
            "type": getattr(ann, "__name__", "any"),
            "required": not has_default,
            "default": None if not has_default else p.default,
        }
    REGISTRY[fn.__name__] = {
        "name": fn.__name__,
        "description": (fn.__doc__ or "").strip(),
        "parameters": params,
    }

    @functools.wraps(fn)
    def wrapper(*args, **kwargs):
        return fn(*args, **kwargs)
    return wrapper

def get_schemas():
    return list(REGISTRY.values())


@tool
def web_search(query: str, max_results: int = 5) -> dict:
    "搜索网页，返回若干条结果"
    return {"query": query, "n": max_results}

@tool
def calculator(expression: str) -> float:
    "计算一个数学表达式"
    return eval(expression)     # 教学用；生产别用 eval

# 被装饰后照常调用
print(web_search("ai agents"))          # {'query': 'ai agents', 'n': 5}
print(web_search.__name__)              # web_search（wraps 生效）

# 模拟"喂给 LLM 的工具清单"
import json
print(json.dumps(get_schemas(), ensure_ascii=False, indent=2))

思考题

先自己想，再点开对答案。

Q1为什么去掉 @functools.wraps 后，很多框架会读不到工具的真实名字？

因为装饰器默认是用内层的 wrapper 函数替换掉原函数，没有 @functools.wraps 把元信息复制回来，func.__name__ 就变成了 "wrapper"，而不是工具的真实名字。

@deco 等价于 fn = deco(fn)，装饰之后外界拿到的其实是 wrapper 这个新函数对象。wrapper 自己的 __name__ 就是字符串 "wrapper"、__doc__ 是 None，于是原函数的名字、docstring、签名全被盖掉了。

而很多 Agent 框架（LangChain、Pydantic AI 等）注册工具时，正是靠反射读 func.__name__ 当工具名、读 func.__doc__ 当工具描述、读签名生成参数 Schema。少了 @functools.wraps(fn)，框架读到的就是一堆叫 "wrapper"、没有描述的工具——名字冲突、LLM 也不知道每个工具是干嘛的。functools.wraps 的作用就是把原函数的 __name__/__doc__/__wrapped__ 等元信息拷回 wrapper，让包装对外"透明"。

Q2到 L14，如果用 Pydantic 的模型来描述参数，这个 Schema 会多出什么能力？（提示：校验 + 标准 JSON Schema 导出）

比手写的 dict Schema 多出三样：运行时自动校验、一键导出标准 JSON Schema、以及字段级的描述/默认值/嵌套建模。

① 运行时校验：Pydantic 模型在实例化时会按类型和约束（如 int、gt=0、max_length）自动校验入参，不符合就抛 ValidationError。而我们手写的 {"type": "str", "required": True} 只是一份"描述"，本身并不会真正拦截非法参数——LLM 传错类型也照样进来。

② 标准 JSON Schema 导出：调 Model.model_json_schema() 就能得到符合 JSON Schema 规范的结构，可以直接塞进 OpenAI / Anthropic tools 定义里的 parameters 字段，不用自己拼 type/required/properties，也不怕拼错格式。

③ 更丰富的表达力：每个字段能带 Field(description=...) 描述（LLM 看得懂）、默认值、可选/必填、以及嵌套模型和复杂类型（list[Item]、枚举等）。这就是为什么 L14 之后工具 Schema 会比本课手写版严谨得多——校验和导出都交给 Pydantic，人只负责声明。

面试常见问题

Q1：装饰器的本质是什么？

答：一个"接收函数、返回新函数"的高阶函数，返回值通常是记住了原函数的闭包。@deco 等价于 f = deco(f)，用来在不改原函数的前提下增强它。

Q2：为什么装饰器要用 functools.wraps？

答：否则内层 wrapper 会覆盖原函数的 __name__/__doc__/签名，破坏调试、文档和依赖反射的框架（如从函数生成工具 Schema）。wraps 把元信息复制回来。

Q3：带参数的装饰器和不带参数的结构差别？

答：不带参数两层（装饰器 → wrapper）；带参数三层（收参数 → 装饰器 → wrapper），最外层负责接收装饰器自己的参数。

Q4：@a @b def f 的执行顺序？

答：等价 f = a(b(f))。装饰时离函数近的 b 先套上（内层），a 后套（外层）；调用时从外层 a 往里穿过。

Q5：装饰器 wrapper 为什么常写成 (*args, **kwargs)？

答：为了能包装任意签名的函数——原样接收所有位置/关键字参数再转发给原函数，不限制被装饰函数长什么样。
