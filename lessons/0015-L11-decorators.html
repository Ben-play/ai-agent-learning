装饰器 — Agent 框架的基石

@tool、@chain、@agent 都是装饰器 — 看懂它，你就看懂了半个框架源码

💡 为什么这课重要？

翻开任何 Agent 框架，满眼都是 @tool、@chain、@agent、@retry——它们全是装饰器。装饰器让你"给函数加一层包装"而不改函数本身：加日志、加重试、加计时、把普通函数注册成工具。

本课是 Part B 的收官，也是闭包（L06）的实战出口：本课聚焦函数装饰器——接收一个 callable、返回一个替代对象，最常见的实现是返回记住了原函数的闭包 wrapper。但这不是绝对定义：装饰器也能作用在类上（如 @dataclass），返回值也不一定是"新函数"或闭包。学完你会亲手写一个 @tool，从函数签名自动生成工具 Schema——这正是框架在幕后做的事。

学习目标

完成本课后，你将能够：

  • 解释装饰器的本质（闭包 + 高阶函数）
  • 写基础装饰器，并用 functools.wraps 保留元信息
  • 写带参数的装饰器（三层结构）
  • 理解多层装饰器的叠放顺序
  • 手写一个 @tool，从类型注解提取参数 Schema

1. 装饰器的本质（本课聚焦函数装饰器）

本课聚焦函数装饰器：接收一个 callable、返回一个替代对象；最常见的实现是返回一个记住了原函数的 wrapper 闭包。@deco 只是 fn = deco(fn) 的语法糖：

import functools

def timed(fn):
    @functools.wraps(fn)              # 保留原函数的名字/文档（关键！）
    def wrapper(*args, **kwargs):     # 用 *args/**kwargs 接住任意签名（呼应 L05）
        import time
        start = time.perf_counter()
        result = fn(*args, **kwargs)  # 调用原函数
        dur = time.perf_counter() - start
        print(f"{fn.__name__} 耗时 {dur:.4f}s")
        return result
    return wrapper                    # 返回的 wrapper 是个闭包（记住了 fn）

@timed
def search(query):
    return f"结果: {query}"

# 等价于 search = timed(search)
search("ai")                # search 耗时 0.0000s
print(search.__name__)      # search  ← 因为用了 wraps，否则会变成 'wrapper'

三个要点：① wrapper 是闭包（记住了外层的 fn）；② 用 *args/**kwargs 才能包装任意函数；③ 一定加 @functools.wraps(fn)，否则被装饰函数的 __name__、__doc__ 会被 wrapper 覆盖。

装饰器不止能装饰函数：装饰器语法（@X）本质上只是"把下面这个对象传给 X、再把返回值绑回同一个名字"，X 可以作用于函数，也可以作用于类。例如 @dataclass 装饰的是一个类，返回的也是（改造过的）类本身，而不是函数或闭包。本课后续例子都聚焦"函数装饰器"这一种最常见的形态，但请记住这不是装饰器的全部定义。

Q @deco 写在 def f 上方，等价于什么？
@deco 是语法糖，等价于把 f 传给 deco、再把返回值赋回 f——即 f = deco(f)。之后你调用的 f 其实是装饰器返回的新函数（通常是个闭包 wrapper）。

2. 带参数的装饰器（三层）

想写 @retry(times=3) 这种"能传参"的装饰器，需要多一层：最外层收参数，返回一个真正的装饰器：

import functools

def retry(times):                     # ① 收装饰器参数
    def deco(fn):                     # ② 真正的装饰器（收函数）
        @functools.wraps(fn)
        def wrapper(*args, **kwargs): # ③ 包装逻辑
            err = None
            for _ in range(times):
                try:
                    return fn(*args, **kwargs)
                except Exception as e:
                    err = e
            raise err
        return wrapper
    return deco

@retry(times=3)                       # 先调用 retry(3) 得到 deco，再用 deco 装饰
def flaky():
    ...

记忆：不带参数的装饰器两层，带参数的三层。多出来的最外层就是用来"接收装饰器自己的参数"。

3. 多层装饰器的顺序

@timed        # 后执行（外层）
@retry(times=3)   # 先执行（内层，离函数近）
def call():
    ...

# 等价于：call = timed(retry(times=3)(call))
# 装饰：自下而上包裹；调用：自上而下进入

规则：离函数最近的装饰器最先"套"上去（内层），最上面的最后套（最外层）。运行时，请求从最外层往里穿过每一层。

💡 面试常见问题：

"为什么装饰器里几乎总要写 @functools.wraps(fn)？"

答：不写的话，被装饰函数的 __name__、__doc__、签名等会被内层 wrapper 覆盖，导致调试、文档、以及"靠反射读函数信息"的框架（比如从函数生成工具 Schema）全部失灵。wraps 把这些元信息复制回来。

4. @tool：从函数生成工具 Schema

这是装饰器在 Agent 里最经典的用法——把普通函数注册成工具，并读取它的类型注解自动生成参数 Schema（喂给 LLM）。

📌 先说清楚类型注解：

类型注解（query: str 这种写法）是什么、能写多复杂，是 L13 才系统学的内容。本课直接给你写好的函数签名，重点是装饰器怎么在导入阶段读签名、把函数注册进表里，不考察复杂 typing（Optional、Literal、泛型等）。下面的简易 Schema 也刻意只覆盖最基础的四种类型。

import functools, inspect

REGISTRY = {}

TYPE_MAP = {str: "string", int: "integer", float: "number", bool: "boolean"}  # 简易 Schema 只认这 4 种

def _param_schema(name, annotation):
    if annotation is inspect.Parameter.empty:
        raise TypeError(f"参数 `{name}` 缺少类型注解，本课简易 Schema 不支持无注解参数（L13 会系统讲类型注解）")
    if annotation not in TYPE_MAP:
        raise TypeError(
            f"参数 `{name}` 的类型 {annotation!r} 超出本课支持范围（仅 str/int/float/bool）。"
            f"list/Optional/Literal/嵌套模型等复杂类型需要 L13 类型提示 + L14 Pydantic 才能正确处理。"
        )
    return TYPE_MAP[annotation]

def tool(fn):
    sig = inspect.signature(fn)
    properties, required = {}, []
    for name, p in sig.parameters.items():
        properties[name] = {"type": _param_schema(name, p.annotation)}
        if p.default is inspect.Parameter.empty:
            required.append(name)
    input_schema = {"type": "object", "properties": properties, "required": required}

    REGISTRY[fn.__name__] = {                    # registry 保存"中立"信息，不绑定任何厂商格式
        "fn": fn,
        "name": fn.__name__,
        "description": (fn.__doc__ or "").strip(),
        "input_schema": input_schema,
    }

    @functools.wraps(fn)
    def wrapper(*args, **kwargs):
        return fn(*args, **kwargs)
    return wrapper

@tool
def web_search(query: str, max_results: int = 5) -> dict:
    "搜索网页并返回结果"
    return {"query": query, "n": max_results}

print(REGISTRY["web_search"])
# {'fn': <function web_search ...>, 'name': 'web_search',
#  'description': '搜索网页并返回结果',
#  'input_schema': {'type': 'object',
#                    'properties': {'query': {'type': 'string'},
#                                   'max_results': {'type': 'integer'}},
#                    'required': ['query']}}

# 无注解 / 复杂类型：明确拒绝，不静默瞎猜
@tool
def bad(x):            # TypeError：缺少类型注解
    ...
@tool
def bad2(items: list): # TypeError：list 超出 str/int/float/bool 范围
    ...

无注解不会退化成 "any" 或 "_empty"，而是直接 TypeError；不在 str/int/float/bool 内的类型（list[str]、Optional[int]、Literal、嵌套 Pydantic 模型等）同样拒绝并指向 L13/L14——宁可拒绝，也不能给 LLM 一份错的 Schema。

🔑 厂商边界：registry 是中立的，请求格式要适配

上面 REGISTRY 里存的 name/description/input_schema 是厂商无关的中立信息。真正发给 LLM 时，OpenAI 和 Anthropic 的字段结构并不一样，需要各自的 adapter 转换：

def to_openai_schema(entry):
    return {"type": "function", "function": {
        "name": entry["name"],
        "description": entry["description"],
        "parameters": entry["input_schema"],       # OpenAI 叫 parameters
    }}

def to_anthropic_schema(entry):
    return {
        "name": entry["name"],
        "description": entry["description"],
        "input_schema": entry["input_schema"],     # Anthropic 直接叫 input_schema
    }

不是"两家都塞进 parameters"——字段名、嵌套层级都不同，adapter 要分开写。

⚠️ Schema ≠ 运行时校验：

本课的 @tool 只做了两件事——注册（存进 REGISTRY）和描述（生成喂给 LLM 看的 Schema）。它不会在调用 web_search(...) 时校验实参类型对不对——LLM 传个字符串当 max_results，这段代码照样会往下执行，出错与否取决于函数体自己怎么处理。L14 会用 Pydantic BaseModel 在构造实例时自动校验；届时注册表应保存模型类 / validator，执行前先构造模型得到已验证参数。

🔑 Agent 开发关联：

这就是 LangChain 的 @tool、Pydantic AI 的工具注册在幕后做的事：装饰器读取你的函数签名（L05）+ 类型注解（L13 会系统学）+ docstring，自动生成中立的工具描述，再由各家 SDK 转成自己的请求格式。到 L14 用 Pydantic 后，Schema 会更严谨（自动导出标准 JSON Schema，且真的带运行时校验）。Part B 到这里闭环了。

Q @tool 装饰器靠什么读出函数的参数信息？
用 inspect.signature(fn) 读取函数的参数名、类型注解、默认值——这是"反射"。装饰器据此生成中立的工具描述（registry），发送前再由 OpenAI/Anthropic 各自的 adapter 转成对应请求格式；这份 Schema 本身不做运行时校验。这也是为什么 L05 强调"函数签名就是工具契约"、以及为什么装饰器必须用 functools.wraps 保住元信息。

import functools, inspect, json

REGISTRY = {}
TYPE_MAP = {str: "string", int: "integer", float: "number", bool: "boolean"}

def _param_schema(name, annotation):
    if annotation is inspect.Parameter.empty:
        raise TypeError(f"参数 `{name}` 缺少类型注解（本课简易 Schema 不支持，见 L13）")
    if annotation not in TYPE_MAP:
        raise TypeError(f"参数 `{name}` 类型 {annotation!r} 不在 str/int/float/bool 内（见 L13/L14）")
    return TYPE_MAP[annotation]

def tool(fn):
    sig = inspect.signature(fn)
    properties, required = {}, []
    for name, p in sig.parameters.items():
        properties[name] = {"type": _param_schema(name, p.annotation)}
        if p.default is inspect.Parameter.empty:
            required.append(name)
    REGISTRY[fn.__name__] = {
        "fn": fn,
        "name": fn.__name__,
        "description": (fn.__doc__ or "").strip(),
        "input_schema": {"type": "object", "properties": properties, "required": required},
    }

    @functools.wraps(fn)
    def wrapper(*args, **kwargs):
        return fn(*args, **kwargs)
    return wrapper

def to_openai_schema(entry):
    return {"type": "function", "function": {
        "name": entry["name"], "description": entry["description"],
        "parameters": entry["input_schema"],
    }}

def to_anthropic_schema(entry):
    return {"name": entry["name"], "description": entry["description"],
            "input_schema": entry["input_schema"]}


@tool
def web_search(query: str, max_results: int = 5) -> dict:
    "搜索网页，返回若干条结果"
    return {"query": query, "n": max_results}

@tool
def calculator(expression: str, precise: bool = True) -> float:
    "计算一个数学表达式"
    return 0.0

# 被装饰后照常调用
print(web_search("ai agents"))          # {'query': 'ai agents', 'n': 5}
print(web_search.__name__)              # web_search（wraps 生效）

# 分别导出两家请求格式
entry = REGISTRY["web_search"]
print(json.dumps(to_openai_schema(entry), ensure_ascii=False, indent=2))
print(json.dumps(to_anthropic_schema(entry), ensure_ascii=False, indent=2))

思考题

先自己想，再点开对答案。

Q1为什么去掉 @functools.wraps 后，很多框架会读不到工具的真实名字？

因为装饰器默认是用内层的 wrapper 函数替换掉原函数，没有 @functools.wraps 把元信息复制回来，func.__name__ 就变成了 "wrapper"，而不是工具的真实名字。

@deco 等价于 fn = deco(fn)，装饰之后外界拿到的其实是 wrapper 这个新函数对象。wrapper 自己的 __name__ 就是字符串 "wrapper"、__doc__ 是 None，于是原函数的名字、docstring、签名全被盖掉了。

而很多 Agent 框架（LangChain、Pydantic AI 等）注册工具时，正是靠反射读 func.__name__ 当工具名、读 func.__doc__ 当工具描述、读签名生成参数 Schema。少了 @functools.wraps(fn)，框架读到的就是一堆叫 "wrapper"、没有描述的工具——名字冲突、LLM 也不知道每个工具是干嘛的。functools.wraps 的作用就是把原函数的 __name__/__doc__/__wrapped__ 等元信息拷回 wrapper，让包装对外"透明"。

Q2到 L14，如果用 Pydantic 的模型来描述参数，这个 Schema 会多出什么能力？（提示：校验 + 标准 JSON Schema 导出）

比手写的 dict Schema 多出三样：运行时自动校验、一键导出标准 JSON Schema、以及字段级的描述/默认值/嵌套建模。

① 运行时校验：Pydantic BaseModel 在构造实例时会按类型和约束（如 int、gt=0、max_length）自动校验入参，不符合就抛 ValidationError。而本课手写的 {"type": "string"} 只是一份"描述"，本身并不会真正拦截非法参数——LLM 传错类型也照样调用到函数体。L14 会用 Pydantic BaseModel 在构造实例时自动校验；届时注册表应保存模型类 / validator，执行前先构造模型得到已验证参数。

② 标准 JSON Schema 导出：调 Model.model_json_schema() 就能得到符合 JSON Schema 规范的结构，直接作为 input_schema 塞进 OpenAI/Anthropic 各自的 adapter，不用自己拼 type/required/properties，也不怕拼错格式，还能覆盖 list/Optional/嵌套模型等本课拒绝的复杂类型。

③ 更丰富的表达力：每个字段能带 Field(description=...) 描述（LLM 看得懂）、默认值、可选/必填、以及嵌套模型和复杂类型（list[Item]、枚举等）。这就是为什么 L14 之后工具注册表会比本课手写版严谨得多——校验和导出都交给 Pydantic，registry 也该保存"模型类"而不只是 dict Schema。

面试常见问题

Q1：装饰器的本质是什么？

答：本课聚焦函数装饰器——接收一个 callable、返回一个替代对象；常见实现是返回记住了原函数的闭包 wrapper。@deco 等价于 f = deco(f)，用来在不改原函数的前提下增强它。但装饰器不止能用于函数：作用于类（如 @dataclass）时返回值也是类本身，不是函数或闭包。

Q2：为什么装饰器要用 functools.wraps？

答：否则内层 wrapper 会覆盖原函数的 __name__/__doc__/签名，破坏调试、文档和依赖反射的框架（如从函数生成工具 Schema）。wraps 把元信息复制回来。

Q3：带参数的装饰器和不带参数的结构差别？

答：不带参数两层（装饰器 → wrapper）；带参数三层（收参数 → 装饰器 → wrapper），最外层负责接收装饰器自己的参数。

Q4：@a @b def f 的执行顺序？

答：等价 f = a(b(f))。装饰时离函数近的 b 先套上（内层），a 后套（外层）；调用时从外层 a 往里穿过。

Q5：装饰器 wrapper 为什么常写成 (*args, **kwargs)？

答：为了能包装任意签名的函数——原样接收所有位置/关键字参数再转发给原函数，不限制被装饰函数长什么样。

Q6：工具 Schema 存进 registry 后，能直接发给 OpenAI 和 Anthropic 吗？

答：不能直接混用。registry 里存的是厂商中立信息（name/description/input_schema）；OpenAI 要包成 {"type":"function","function":{...,"parameters":schema}}，Anthropic 要用 {"name":...,"input_schema":schema}，字段名和嵌套层级不同，需要各自的 adapter 转换。而且这份 Schema 只是描述，不会在调用时自动做运行时校验。
