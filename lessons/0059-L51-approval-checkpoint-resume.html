审批暂停、进程退出与恢复

换一个进程，继续等待同一份工单草稿的审批

为什么这课重要？

Agent 拟好工单草稿后，审批人可能明天才回来。部署重启不能丢掉草稿或换一个任务重新跑，更不能因为恢复成功就跳过审批。L44 的交接已把这条恢复路径列为待验证项；本课用真正退出的 Python 子进程补上它。

学习目标

  • 区分会话记录、检查点和业务写入。
  • 从同一 SQLite 路径用新进程恢复相同的任务、草稿版本和待审批状态。
  • 验证审批缺失或不匹配时零草稿写入，只有匹配的批准才执行原动作。

1. 三种记录回答三个不同的问题

对任务 task-demo-51，会话记录（transcript）回答「当时说了什么」。即使聊天里有「已经批准」，那也是一句话，不是可信审批。重播会话还可能重新生成不同的草稿，不能用它猜下一步。

检查点（checkpoint）回答「下次从哪一步继续」。本例记录的是 tenant-demo 的 requester-demo 发起的原任务，下一步是等待批准 save_draft，正文固定为第 2 版 Training draft。把正文写入检查点是保存续跑状态，不是完成保存草稿的动作。

业务效果（business effect）回答「实际改变了什么」：本例看 drafts 表有没有原任务的第 2 版。若系统另存执行回执（execution receipt），可以用操作 ID 查到某一步实际提交的草稿编号，却不能从回执推断整个任务的下一步。原例直接查业务表，没有独立回执；后面的调拨练习才把回执、转运标签和下一步分别查询。

2. 沿时间线走一遍：先提交检查点，恢复后再验批

  1. 暂停并提交：旧进程把原任务、身份、动作、内容及版本写入 SQLite，提交 pending_approval 后退出。此时库里有检查点、没有业务草稿；不持锁等审批人。
  2. 换进程找回原任务：新进程只接收同一库路径、命令、任务 ID 和调用方身份，按任务与身份查找。换成其他发起人时查不到，不建新任务，也不返回原草稿。查到原任务时，从检查点取正文，不靠内存或对话重建。
  3. 核对决定才写入：没有审批、第 1 版获批或第 2 版被拒时，不满足匹配批准，仍返回原待审状态，草稿表为空。测试驱动写入第 2 版的匹配批准后，新进程核对任务、身份、动作和版本，在一个短事务内写入原正文并标记 done；提交后才返回完成状态。

恢复命令没有「已批准」参数；决定来自测试驱动模拟的可信来源。版本须对应不可变的正文，改稿就换版重审。真实系统还要认证调用人和审批人、核对审批权限、处理撤回与过期；恢复成功不能代替这些检查，也不能扩大允许的动作。

3. 分开验证跨进程续跑、审批闸门和业务效果

只关闭并重开数据库连接，可以检验新连接能否读到已提交状态，但不能排除程序靠原进程内存补齐遗漏字段。这里等旧子进程正常退出，再启动新解释器，不传正文和状态；比较恢复结果的完整快照，查的是任务有没有原样续上。另用独立连接查业务表：仍待审却有草稿，要排查写入是否绕开审批；返回 done 却没有原版草稿，要排查提交及完成状态是否同步。只断言返回状态，会漏掉这两类问题。

再次恢复 done 时仍只有一条草稿，说明这个本地流程不会重做已标记完成的任务。它没模拟强杀进程或断电，也没制造「业务效果已经提交、调用方却没收到结果，检查点仍待办」的窗口。L52 专门制造这个窗口，用稳定操作 ID 和持久回执判断是否已生效；能续跑并不等于在未知结果下可以安全重做。

Q 新进程读到原任务仍待审批，应当怎样决定是否执行？
等待时长、消息文本和恢复成功都不能授予权限。只有可信审批里的决策及绑定字段都匹配，才执行约定的草稿动作。

跟做：只改审批版本，追踪两次恢复

  1. 记录第 1 版批准后恢复：___ / ___。
  2. 只把批准改为第 2 版，再恢复：___ / ___。

自检：旧版批准不能写入；匹配批准才返回 done，表中只能有原任务的第 2 版正文。

import sqlite3
import subprocess
import sys
from contextlib import closing

# 固定的本地 worker，不依赖外层代码来自文件还是 python -c。
WORKER = '''
import json
import sqlite3
import sys
from contextlib import closing

path, command, task_id, tenant, requester = sys.argv[1:]
with closing(sqlite3.connect(path, isolation_level=None)) as db:
    db.row_factory = sqlite3.Row
    if command == "pause":
        db.executescript("""
            CREATE TABLE checkpoints (
                task_id TEXT PRIMARY KEY NOT NULL, tenant TEXT NOT NULL,
                requester TEXT NOT NULL, action TEXT NOT NULL,
                revision INTEGER NOT NULL, body TEXT NOT NULL, state TEXT NOT NULL
            );
            CREATE TABLE approvals (
                task_id TEXT PRIMARY KEY NOT NULL, tenant TEXT NOT NULL,
                requester TEXT NOT NULL, action TEXT NOT NULL,
                revision INTEGER NOT NULL, decision TEXT NOT NULL
            );
            CREATE TABLE drafts (
                task_id TEXT NOT NULL, revision INTEGER NOT NULL, body TEXT NOT NULL
            );
        """)
    with db:
        db.execute("BEGIN IMMEDIATE")
        if command == "pause":
            db.execute("INSERT INTO checkpoints VALUES (?, ?, ?, ?, ?, ?, ?)",
                       (task_id, tenant, requester, "save_draft", 2,
                        "Training draft", "pending_approval"))
        row = db.execute(
            "SELECT * FROM checkpoints WHERE task_id=? AND tenant=? AND requester=?",
            (task_id, tenant, requester),
        ).fetchone()
        result = dict(row) if row is not None else None
        if (command == "resume" and result is not None
                and result["state"] == "pending_approval" and result["action"] == "save_draft"):
            approved = db.execute("""
                SELECT 1 FROM approvals
                WHERE task_id=? AND tenant=? AND requester=? AND action=?
                  AND revision=? AND decision='approved'
            """, (task_id, tenant, requester, result["action"], result["revision"])).fetchone()
            if approved is not None:
                db.execute("INSERT INTO drafts VALUES (?, ?, ?)",
                           (task_id, result["revision"], result["body"]))
                db.execute("UPDATE checkpoints SET state='done' WHERE task_id=?", (task_id,))
                result["state"] = "done"
print(json.dumps(result))  # 已退出事务，提交后才报告状态。
'''


def step(path, command, task_id, tenant, requester):
    child = subprocess.run(
        [sys.executable, "-I", "-c", WORKER, str(path), command, task_id, tenant, requester],
        cwd=path.parent, capture_output=True, encoding="utf-8", check=True, timeout=10,
    )  # 返回时子进程已经退出；下次调用会启动全新进程。
    return json.loads(child.stdout)


def record_fixture(path, identity, revision, decision):
    # 仅测试驱动可写，模拟可信审批端交付当前决策；不是对话或模型输入。
    with closing(sqlite3.connect(path)) as db, db:
        db.execute("INSERT OR REPLACE INTO approvals VALUES (?, ?, ?, ?, ?, ?)",
                   (*identity, "save_draft", revision, decision))


def drafts(path):
    with closing(sqlite3.connect(path)) as db:
        return db.execute("SELECT task_id, revision, body FROM drafts").fetchall()


if not __debug__:

with TemporaryDirectory() as directory:

    identity = ("task-demo-51", "tenant-demo", "requester-demo")

    assert drafts(path) == []
    done = {**pending, "state": "done"}

    assert step(path, "resume", *identity) == done

最佳实践：用检查点续跑，用回执核对效果，用对话回看

适用：工单草稿等待人工审批时，部署可能更换工作进程。边界：这里验证正常退出后换进程读同一个 SQLite 文件，不测试断电或外部效果；只重开连接不能排除旧进程内存补齐状态。

错误：换进程后从对话重建并推断进度

待审批时原进程退出。新进程重播对话来生成草稿，又把聊到的「批准」当决定，可能生成另一版或在尚无可信批准时就写入。即使页面仍说「等待」，也无法证明业务表没写。

正确：以持久检查点找回相同的待办

同样退出再恢复，按原身份找回原版本和下一步；没有匹配批准时保持等待，草稿表仍是零行。匹配后验证表中只有原草稿；若系统另有执行回执，则按操作键核对本次业务结果，不用回执或对话推断整个任务的下一步。

原因与代价：对话可供解释但不授予权限；检查点保存控制流而不是效果证明；回执绑定已提交的操作。分开后需维护版本、持久化边界和对账规则。数据库里若已有按稳定操作键唯一且可核对的业务行，它可充当回执，不必复制数据。把审批核对和本地写入放在短事务中，不持锁等人（参见 SQLite 事务说明）。

  1. 运行原跨进程验收前，记录「首次暂停、旧版批准、正确批准」各自的完整快照与业务行数。核实每次 step 都启动子进程并等待它退出。
  2. 在临时副本中去掉审批查询里的版本条件和对应参数，其余不变。观察旧版批准在哪条路径首先改变状态；恢复条件后重新运行。

结果诊断：原样只输出 L51 ACCEPTED。删掉条件后，旧版批准用例应首先失败。状态仍「等待」但业务表有行时，查写入是否越过闸门；状态为 done 但原版本不在表中时，查事务和效果核验，而不是重播对话。

import json
import sqlite3
import sys
from contextlib import closing

path, command, job, owner = sys.argv[1:]
with closing(sqlite3.connect(path, isolation_level=None)) as db, db:
    db.execute("BEGIN IMMEDIATE")
    if command == "pause":
        db.execute("INSERT INTO checkpoints VALUES (?, ?, ?, ?, ?, ?)",
                   (job, owner, "book-42", 2, "label-req-42", "awaiting_review"))
    row = db.execute("SELECT * FROM checkpoints WHERE job=? AND owner=?",
                     (job, owner)).fetchone()
    if command == "resume" and row and row[-1] == "awaiting_review":
        approved = db.execute("""
            SELECT 1 FROM reviews WHERE job=? AND owner=? AND item=? AND revision=?
              AND decision='approved'
        """, row[:4]).fetchone()
        if approved:
            label_id = db.execute("INSERT INTO labels(item) VALUES (?)", (row[2],)).lastrowid
            db.execute("INSERT INTO receipts VALUES (?, ?)", (row[4], label_id))
            db.execute("UPDATE checkpoints SET next_step='pack' WHERE job=?", (job,))
            row = (*row[:-1], "pack")
print(json.dumps(row))

运行与诊断：保存整段，用 python -I 文件名.py 运行，只应输出 L51 TRANSFER PASSED。聊天声称「批准」后若有标签，查是否读错决定来源；没有聊天就恢复失败，查是否把恢复绑在对话上。回执已有标签但下一步仍待审，查状态推进；再次恢复多出标签，查是否重做已完成的子动作，而不是继续等待打包。

文字知识图

  • 待审批检查点已提交 → 原进程退出 → 新进程按原 ID 和身份找回原状态。
  • 身份不匹配 → 不恢复；没有匹配的批准 → 保持等待，零草稿。
  • 可信批准匹配固定版本和动作 → 本地写入原草稿并标记完成。

面试自查

先合上答案，按「结论 → 理由 → 如何验证」作答，再展开追问。

Q1调拨备注写「已打包」，库里有标签回执，检查点的下一步是 pack。续跑该交接打包、跳过打包，还是重打标签？

参考回答：交接打包，不跳过也不重打。检查点给出下一步，原操作键匹配的回执仅证明登记过标签，备注不能证明打包完成。分别查询三处记录，并确认回执指向本任务实际登记的标签。

追问：标签查到了，但检查点仍写「待审」，该重打一张吗？

答题要点：不要重打。先核对回执与原操作键，排查状态推进是否漏做；旧检查点不能证明标签未登记。

Q2第 2 版工单待审时进程要退出，哪些数据必须提交到检查点？

参考回答：提交任务 ID、租户与发起人、下一动作 save_draft、不可变的第 2 版正文及 pending_approval 状态。这样能找回同一待办，不必重生成正文。独立连接应查到完整快照，但业务草稿表仍为零行。

追问：同租户另一发起人传入相同任务 ID，如何验收？

答题要点：恢复应找不到任务，不返回原草稿，不创建新任务。检查响应无快照、检查点未变、草稿表仍为空。

Q3同进程重开 SQLite 连接已通过，怎样证明续跑没借用原进程内存？

参考回答：等保存检查点的子进程成功退出，再启动新解释器，只给同一库路径、恢复命令、任务 ID 和调用方身份，不传正文或状态。新进程返回的完整快照应与暂停时相同；只换连接不能排除原内存补齐遗漏字段。

追问：这能作为强制终止后也能恢复的证据吗？

答题要点：不能，只证明正常退出后能换进程读取已提交的快照。强制终止需要另设故障点并单独取证。

Q4新进程找回第 2 版待审任务，怎样证明「能续跑」不等于「能保存」？

参考回答：恢复先找回原快照，再从可信来源核对与任务、身份、动作和版本匹配的批准。分别注入无审批、第 1 版获批和第 2 版被拒，断言都仍待审且零草稿；换成第 2 版匹配批准后，才应返回 done 并在独立连接查到唯一一条原版草稿。

追问：若返回 done，独立连接却查不到原稿，先查什么？

答题要点：先确认查的是同一库和原任务版本，再看草稿插入与 done 是否同事务提交、是否在提交前就报告完成；不能只信返回值。
