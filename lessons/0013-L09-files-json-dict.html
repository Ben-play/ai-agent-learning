文件、JSON 与 Dict 深度操作

LLM 说的是 JSON — 读写文件、解析流式响应，是 Agent 的日常 I/O

💡 为什么这课重要？

LLM 的输入输出、工具调用参数、配置文件、缓存——全是 JSON。Agent 每一步都在做 JSON 的序列化（对象→字符串）和反序列化（字符串→对象）。

本课以 JSON Lines（一行一个完整 JSON）这种常见的本地/自定义流格式练手，要能逐行解析、拼接、还要分清"完整但语法坏的记录"和"网络传来的半行"。这是处理真实 LLM 输出的基础技能，真实 SSE/SDK 层留到 L15。

学习目标

完成本课后，你将能够：

  • 用 with open() 安全读写文件
  • 用 pathlib 优雅地处理路径
  • 熟练 json.dumps / json.loads 及常用参数
  • 逐行解析 JSON Lines 流，区分坏记录与半行并正确容错
  • 知道 orjson 何时能提速

1. 文件读写：永远用 with

from pathlib import Path

# 写
with open("config.json", "w", encoding="utf-8") as f:
    f.write('{"model": "claude"}')
# with 块结束自动关闭文件，即使中途出错也保证关闭

# 读
with open("config.json", "r", encoding="utf-8") as f:
    text = f.read()

# pathlib：更现代的路径处理
p = Path("data") / "logs" / "run.json"   # 用 / 拼路径，跨平台
p.parent.mkdir(parents=True, exist_ok=True)   # 确保目录存在
p.write_text('{"ok": true}', encoding="utf-8")   # 一行读写
print(p.read_text(encoding="utf-8"))

要点：永远用 with（自动关闭）、永远指定 encoding="utf-8"（避免中文乱码），路径用 pathlib 而非字符串拼接。

⚠️ 三种打开模式的破坏性边界：
"w"写模式——打开瞬间就清空原文件内容（哪怕你还没写一个字）。原文件不存在则新建。
"a"追加模式——保留原内容，新写入的内容接在文件末尾。原文件不存在则新建。
"r"只读模式（默认）——文件不存在会抛 FileNotFoundError；不会修改文件。

实测证明 "w" 覆盖、"a" 追加：

with open("t.txt", "w", encoding="utf-8") as f:
    f.write("line1\n")
with open("t.txt", "a", encoding="utf-8") as f:
    f.write("line2\n")
print(open("t.txt", encoding="utf-8").read())
# line1
# line2

with open("t.txt", "w", encoding="utf-8") as f:
    f.write("only-this\n")
print(open("t.txt", encoding="utf-8").read())
# only-this   ← 上面的 line1/line2 已被清空
Q 用 with open(...) 读文件，最大的好处是？
with（上下文管理器，L10 详讲）保证代码块结束时自动关闭文件——即使中途抛异常也会关。不关文件会泄露句柄。速度和编码不是它解决的问题。

2. JSON 序列化与反序列化

会读写文件了，但文件里存什么格式？Agent 世界的答案几乎总是 JSON——配置、LLM 响应、工具参数都是它。问题是：Python 内存里是 dict/list 对象，文件里是纯文本字符串，两者要互相转换。对象→字符串叫序列化，字符串→对象叫反序列化，靠的就是 json 模块：

import json

obj = {"name": "search", "args": {"q": "python"}, "ok": True}

# 序列化：对象 → 字符串
s = json.dumps(obj, ensure_ascii=False, indent=2)
# ensure_ascii=False → 中文正常显示（不转成 \uXXXX）
# indent=2 → 美化缩进（存文件时好读）

# 反序列化：字符串 → 对象
back = json.loads(s)
print(back == obj)    # True

# 直接读写文件
with open("c.json", "w", encoding="utf-8") as f:
    json.dump(obj, f, ensure_ascii=False)   # dump 写文件（没有 s）
with open("c.json", "r", encoding="utf-8") as f:
    data = json.load(f)                       # load 读文件

记忆法：带 s 的（dumps/loads）操作字符串；不带 s 的（dump/load）直接操作文件。

🔗 Python 字面量 ↔ JSON 字面量（承接 L03）： 
Python: True / False / None
JSON:   true / false / null

两者大小写不同、不能互换：Python 源码里写 true（小写）会直接报 NameError；JSON 文本里写 True（大写）会让 json.loads 抛 JSONDecodeError。json.dumps/json.loads 在两套字面量之间自动转换，这正是它存在的意义之一（与 L03 中 Python/JSON 边界的说明一致）。

💡 面试常见问题：

"json.dumps 的中文变成 \uXXXX 怎么办？"

答：加 ensure_ascii=False。它默认为 True 会把非 ASCII 转义；关掉后中文原样输出（记得文件用 utf-8 编码）。

3. 解析 JSON Lines（本地日志/自定义流）

很多本地日志、自定义事件流会选择一行一个完整 JSON 对象的格式（即 JSON Lines，简称 JSONL）。这只是众多流格式里的一种——本节示例演示如何逐行解析 JSONL，还得扛住空行和「确认完整但语法坏」的行。注意：这不是真实 LLM SSE 的通用骨架，SSE 有自己的分行/分事件规则，见下面的三层对照卡。

在写 try/except 之前先说一句：try 包住可能失败的代码，except 只接住你指定的异常类型（这里是 json.JSONDecodeError，即"这行文本不是合法 JSON"）；其他异常不会被它吃掉。try/except 的完整语法和多分支用法 L10 系统学习，这里先知道"try 里放可能炸的代码，except 只接指定类型"即可。

import json

# 模拟 JSONL 流：每行一个事件，中间可能有空行或坏行
stream = '{"tok":"Hel"}\n{"tok":"lo"}\n\n{oops bad line}\n{"done":true}\n'

tokens = []
done = False
for line in stream.splitlines():
    line = line.strip()
    if not line:
        continue                       # 跳过空行
    try:
        event = json.loads(line)
    except json.JSONDecodeError:
        continue                       # 这一整行已收全，但语法坏——记录/跳过
    if "tok" in event:
        tokens.append(event["tok"])
    if event.get("done"):
        done = True

print("".join(tokens), done)   # Hello True
🔑 坏记录 vs 网络半行——不是一回事：

上面例子里的 {oops bad line} 是一整行都已经收到了，只是内容本身不符合 JSON 语法——这种情况下用 try/except JSONDecodeError 记录/跳过是安全的，不会丢数据（这条记录本身就是坏的）。

但如果数据来自网络（比如 TCP/HTTP 的 chunk），情况不同：网络传输不保证按行或按事件边界到达，一次 recv 可能只拿到半行，比如 {"tok":"He。这种"半行"不能直接当坏行丢弃——它不是语法错误，而是数据还没收全。正确做法是先缓冲，等拼上后续数据、凑齐完整一行后再 json.loads。直接丢弃会丢失这部分内容。

📊 三层对照：不要混为一谈 
JSON Lines: 每行一个完整 JSON 对象，行与行之间用 \n 分隔
原始 SSE:   event:/data: 字段 + 空行分隔事件（协议自带分帧规则）
SDK:        客户端库已经解析好的结构化事件/chunk 对象（不用你自己切行）

三者结构不同，处理方式也不同。真实 LLM API 的原始传输大多是 SSE，本课不手写完整 SSE parser——SSE 的分行/分事件规则见 L15 · httpx。

Q 下面哪种处理方式是正确的？
关键在于先区分"这一行是否已经完整收到"：如果一整行都收全了、只是语法本身坏了（如 {oops bad line}），可以安全地记录/跳过。但如果数据来自网络，chunk 可能在行中间被截断，这种"半行"不是语法错误而是不完整——必须先缓冲、拼上后续数据凑成完整一行，再尝试解析，绝不能直接丢弃，否则会丢内容。

4. json vs orjson（性能）

标准库 json 足够日常使用。当你要序列化大量或超大 JSON（如批处理、日志管线）时，第三方 orjson 快得多（常见快 3–10 倍），且原生支持 datetime、dataclass 等。

# 安装（二选一）
uv add orjson
pip install orjson
# 用法几乎一样，但 orjson 返回 bytes
import orjson
data = orjson.loads(b'{"ok": true}')
raw = orjson.dumps({"ok": True})   # b'{"ok":true}'

原则：先用标准库 json；确认序列化是性能瓶颈后再装 orjson，这是可选依赖，别过早优化。

知识图谱

文件 I/O
├── with open(..., encoding="utf-8") → 自动关闭 + 防乱码
└── pathlib：Path("a")/"b"、mkdir、read_text/write_text

JSON
├── dumps/loads → 操作字符串（带 s）
├── dump/load → 操作文件（不带 s）
├── ensure_ascii=False → 中文原样
└── indent=2 → 美化

流式解析（JSON Lines）
├── splitlines() 逐行 + strip()
├── 空行跳过；完整坏行 try/except 跳过；网络半行先缓冲不丢弃
└── 拼接 tok、检测 done

JSON Lines / 原始 SSE / SDK → 三层结构不同，处理方式不同（详见 L15）

json vs orjson → 大量序列化时 orjson 快 3–10x

实战练习

练习：解析 JSON Lines 事件日志

模拟本地日志或自定义流中已经组装好的完整 JSON Lines 文本，逐行解析、拼接内容、统计用量，并对完整坏记录容错。先自己写，再看答案。

任务清单

  1. 输入是多行字符串，每行可能是：{"type":"token","text":"..."}、{"type":"usage","tokens":N}、{"type":"done"}，也可能有空行/坏行
  2. 逐行解析，拼接所有 token 的 text 成完整回答
  3. 累加 usage 的 tokens
  4. 空行跳过；确认完整但语法错误的记录在记录后跳过，不崩溃
  5. 返回 {"text": 完整回答, "total_tokens": N, "done": bool}
💡 点击查看参考答案 
import json

def parse_stream(stream: str) -> dict:
    parts = []
    total_tokens = 0
    done = False

    for line in stream.splitlines():
        line = line.strip()
        if not line:
            continue
        try:
            ev = json.loads(line)
        except json.JSONDecodeError:
            continue                       # 完整但语法坏的记录：记录后跳过

        kind = ev.get("type")
        if kind == "token":
            parts.append(ev.get("text", ""))
        elif kind == "usage":
            total_tokens += ev.get("tokens", 0)
        elif kind == "done":
            done = True

    return {"text": "".join(parts), "total_tokens": total_tokens, "done": done}


stream = (
    '{"type":"token","text":"你好"}\n'
    '{"type":"token","text":"，世界"}\n'
    '\n'                                   # 空行
    '{oops bad line}\n'                    # 坏行
    '{"type":"usage","tokens":42}\n'
    '{"type":"done"}\n'
)
print(parse_stream(stream))
# {'text': '你好，世界', 'total_tokens': 42, 'done': True}

思考题

先自己想，再点开对答案。

Q1如果最后一行被网络截断成半个 JSON（如 {"type":"tok），你的代码会崩吗？

当前简单示例不会崩，但它会把半行跳过并丢失数据；这不能直接用于真实网络流。

代码里的 json.loads(line) 会对 {"type":"tok 抛出 JSONDecodeError，随后被 except 捕获，所以程序不会崩溃。这只证明了异常被接住，不代表处理策略正确：如果这段文本只是网络暂时送到的半行，执行 continue 会永久丢掉已经收到的内容。

真实网络 chunk 不保证落在行或事件边界。半行必须先放入缓冲区，与后续 chunk 拼接；确认得到完整一行后，才能尝试解析。只有已经确认完整、但 JSON 语法仍然错误的记录，才可以在记录错误后跳过。本练习的 parse_stream 只处理已经组装好的完整 JSON Lines 字符串，不负责网络分块。

Q2真实 SSE 流每行前面还有 data: 前缀，你会怎么先剥掉它？（提示：L04 的 removeprefix）

在 json.loads 之前，先用 line = line.removeprefix("data: ")（Python 3.9+）把 SSE 前缀剥掉。

SSE（Server-Sent Events）规范里每条数据行长成 data: {"type":"token",...}，前面固定带 data: 。str.removeprefix 的好处是：前缀存在就精确切掉，不存在就原样返回，比 line[6:] 这种硬编码切片安全得多。

顺序上，在 strip() 之后、json.loads() 之前插入这一步即可。另外 SSE 常用 data: [DONE] 作为结束哨兵——剥掉前缀后要单独判断 if line == "[DONE]": break（或 continue），因为 [DONE] 不是 JSON，直接丢给 json.loads 会当坏行跳过，虽然不崩，但显式处理更清晰。

面试常见问题

Q1：json.dump 和 json.dumps 区别？

答：带 s 的 dumps/loads 在字符串和对象之间转换；不带 s 的 dump/load 直接读写文件对象。

Q2：为什么读写文件推荐用 with？

答：with 是上下文管理器，块结束时自动关闭文件（即使异常也关），避免句柄泄露。比手动 f.close() 更安全。

Q3：解析 JSON Lines 流时要注意什么？

答：逐行解析、容错——空行跳过；一整行已收全但语法坏的记录用 try/except JSONDecodeError 记录/跳过；而网络传来的半行不是语法错误，需先缓冲拼接成完整行再解析，不能直接丢弃。同时要拼接内容、检测结束标志。真实 LLM SSE 传输和 SDK 已解析事件是另外两层，规则不同，见 L15。

Q4：什么时候用 orjson 而不是标准库 json？

答：当 JSON 序列化成为性能瓶颈（大量或超大数据、高频调用）时。orjson 通常快数倍，并原生支持 datetime/dataclass。日常仍可用标准库。
