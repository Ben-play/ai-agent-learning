文件、JSON 与 JSON Lines

许多接口使用 JSON 兼容结构 — 文件往返与逐行事件解析是常见 I/O

💡 为什么这课重要？

许多 LLM 接口的请求/响应、工具参数、配置文件和缓存会使用 JSON 或 JSON 兼容结构。Agent 因而经常要做 JSON 的序列化（对象→字符串）和反序列化（字符串→对象），但具体 SDK 也可能直接提供结构化对象。

本课以 JSON Lines（一行一个完整 JSON 值）这种常见的本地/自定义流格式练手：先确认完整行，再解析 JSON 值，最后按应用自己的对象事件契约校验。还要分清“完整但语法坏的记录”和“网络传来的半行”；真实 SSE/SDK 层留到 L15。

本课关键决策：单份文档用 JSON；逐条独立记录用 JSONL；网络事件优先交给 SDK 或合规的 SSE parser。

学习目标

完成本课后，你将能够：

  • 用 with open() 安全读写文件
  • 用 pathlib 优雅地处理路径

1. 文件读写：文件对象用 with，便捷读写用 Path

from pathlib import Path

# 写
with open("config.json", "w", encoding="utf-8") as f:
    f.write('{"model": "claude"}')
# with 块结束自动关闭文件，即使中途出错也保证关闭

# 读
with open("config.json", "r", encoding="utf-8") as f:
    text = f.read()

# pathlib：更现代的路径处理
p = Path("data") / "logs" / "run.json"   # 用 / 拼路径，跨平台
p.parent.mkdir(parents=True, exist_ok=True)   # 确保目录存在
p.write_text('{"ok": true}', encoding="utf-8")   # 一行读写
print(p.read_text(encoding="utf-8"))

要点：需要直接操作文件对象时用 with open(...) 保证关闭；一次性读写可用会自行管理文件句柄的 Path.read_text()/write_text()。两种方式都显式指定 encoding="utf-8"，路径用 pathlib 而非字符串拼接。

最佳实践：重要 JSON 先完整写入同目录临时文件，再替换目标

适用场景：配置更新失败时，希望旧目标文件继续保持完整，而不是留下半段 JSON。

可丢失或可再生成输出：可直接写
path.write_text(json.dumps(data), encoding="utf-8")

实现最简单，但写入失败时目标可能被截断。

重要配置：唯一临时文件写完后替换
write_json_atomic(path, data)  # 调用下方定义并自检的原子写入 helper

helper 为每个写者使用不同临时名，并在写入或替换失败时清理；替换发生前旧目标仍保持原样。

为什么更优：同目录唯一临时文件先承接完整内容，再由 os.replace 一次切换目标名称，避免目标在写入中途暴露半成品，从而提升数据完整性与故障原子性。代价是额外一次完整写入和名称切换 I/O，且不自动保留元数据、保证断电持久性或协调多写者；当需要并发一致性或崩溃后持久承诺时，加入文件锁与文件/目录同步，或改用支持事务的数据库。

自检：替换失败时保留旧目标并清理唯一临时文件
import json
import os
from contextlib import suppress
from pathlib import Path
from tempfile import NamedTemporaryFile, TemporaryDirectory


def write_json_atomic(path, data, replace=os.replace):
    text = json.dumps(data, ensure_ascii=False, allow_nan=False)
    tmp = None
    try:
        with NamedTemporaryFile(
            "w", encoding="utf-8", dir=path.parent,
            prefix=f".{path.name}.", suffix=".tmp", delete=False,
        ) as file:
            tmp = Path(file.name)
            file.write(text)
        replace(tmp, path)
        tmp = None
    except BaseException:
        if tmp is not None:
            with suppress(OSError):
                tmp.unlink()
        raise

with TemporaryDirectory() as directory:
    path = Path(directory) / "config.json"
    write_json_atomic(path, {"version": 1})

    def fail_before_replace(source, target):
        raise OSError("simulated replace failure")

    try:
        write_json_atomic(path, {"version": 2}, replace=fail_before_replace)
    except OSError as exc:
        assert str(exc) == "simulated replace failure"
    else:
        raise AssertionError("替换失败必须向上传播")
    assert json.loads(path.read_text(encoding="utf-8")) == {"version": 1}
    assert list(path.parent.glob(".config.json.*.tmp")) == []

    write_json_atomic(path, {"version": 2})
    assert json.loads(path.read_text(encoding="utf-8")) == {"version": 2}

结果解释：注入替换失败后，旧目标仍是可解析的 version 1，临时文件已清理，且原始 OSError 没被覆盖；正常替换后才切换到 version 2。

边界：唯一临时文件必须位于目标目录。同文件系统内 os.replace 成功时提供名称切换的原子可见性，但仍可能因权限或文件占用失败；它不保证断电持久性，也不保留旧目标的权限等元数据。多个写者仍需锁或单写者设计。

⚠️ 三种打开模式的破坏性边界：
"w"写模式——打开瞬间就清空原文件内容（哪怕你还没写一个字）。原文件不存在则新建。
"a"追加模式——保留原内容，新写入的内容接在文件末尾。原文件不存在则新建。
"r"只读模式（默认）——文件不存在会抛 FileNotFoundError；不会修改文件。

实测证明 "w" 覆盖、"a" 追加：

with open("t.txt", "w", encoding="utf-8") as f:
    f.write("line1\n")
with open("t.txt", "a", encoding="utf-8") as f:
    f.write("line2\n")
print(Path("t.txt").read_text(encoding="utf-8"))
# line1
# line2

with open("t.txt", "w", encoding="utf-8") as f:
    f.write("only-this\n")
print(Path("t.txt").read_text(encoding="utf-8"))
# only-this   ← 上面的 line1/line2 已被清空
Q 用 with open(...) 读文件，最大的好处是？
with（上下文管理器，L10 详讲）保证代码块结束时自动关闭文件——即使中途抛异常也会关。不关文件会泄露句柄。速度和编码不是它解决的问题。

2. JSON 序列化与反序列化

会读写文件了，但文件里存什么格式？Agent 开发中的许多配置、接口响应和工具参数使用 JSON 或 JSON 兼容结构。Python 内存里常见的是 dict/list 对象，JSON 文件里是文本，两者需要互相转换：对象→字符串叫序列化，字符串→对象叫反序列化，靠的就是 json 模块：

import json

obj = {"name": "search", "args": {"q": "python"}, "ok": True}

# 序列化：对象 → 字符串
s = json.dumps(obj, ensure_ascii=False, indent=2, allow_nan=False)
# ensure_ascii=False → 中文正常显示（不转成 \uXXXX）
# indent=2 → 美化缩进（存文件时好读）

# 反序列化：字符串 → 对象
back = json.loads(s)
print(back == obj)    # True

# 直接读写文件
with open("c.json", "w", encoding="utf-8") as f:
    json.dump(obj, f, ensure_ascii=False)   # dump 写文件（没有 s）
with open("c.json", "r", encoding="utf-8") as f:
    data = json.load(f)                       # load 读文件

记忆法：带 s 的（dumps/loads）操作字符串；不带 s 的（dump/load）直接操作文件。

🔗 Python 字面量 ↔ JSON 字面量（承接 L03）： 
Python: True / False / None
JSON:   true / false / null

两者大小写不同、不能互换：Python 源码里写 true（小写）会直接报 NameError；JSON 文本里写 True（大写）会让 json.loads 抛 JSONDecodeError。json.dumps/json.loads 在两套字面量之间自动转换，这正是它存在的意义之一（与 L03 中 Python/JSON 边界的说明一致）。

💡 面试常见问题：

"json.dumps 的中文变成 \uXXXX 怎么办？"

答：加 ensure_ascii=False。它默认为 True 会把非 ASCII 转义；关掉后中文原样输出（记得文件用 utf-8 编码）。

3. 解析 JSON Lines（本地日志/自定义流）

JSON Lines（JSONL）的格式层只规定：每一行是一个完整、合法的 JSON 值。这个值可以是对象、数组、字符串、数字、布尔值或 null；“必须是对象”不是 JSONL 规则，而是本例事件日志的应用契约。本课只处理已经按完整行分帧的本地/自定义 JSONL，不编写通用 SSE parser。

处理时依次过三层，诊断也不要混写：①完整行分帧——网络 chunk 中尚无换行的尾部必须继续缓冲；②JSON 值——仅在完整行上调用 json.loads，语法失败记为 syntax；③应用事件契约——本应用要求对象，否则记为 non-object，再校验已知事件种类及必需字段/类型，失败记为 contract。

import json


def contract_error(event):
    kind = event.get("type")
    if kind == "text_delta":
        if "text" not in event or not isinstance(event["text"], str):
            return "text_delta requires string field 'text'"
    elif kind == "usage":
        tokens = event.get("tokens")
        if not isinstance(tokens, int) or isinstance(tokens, bool):
            return "usage requires integer field 'tokens'"
    elif kind == "done":
        pass
    else:
        return f"unknown event type: {kind!r}"
    return None


def reject_non_json_constant(token):
    raise json.JSONDecodeError(
        f"non-standard JSON constant: {token}", token, 0,
    )


def parse_jsonl(text):
    events, diagnostics = [], []
    lines = text.split("\n")
    if lines and lines[-1] == "":
        lines.pop()  # 末尾 LF 后的切分哨兵不是额外记录
    for line_no, line in enumerate(lines, start=1):
        try:
            value = json.loads(
                line, parse_constant=reject_non_json_constant,
            )
        except json.JSONDecodeError as exc:
            diagnostics.append({
                "line": line_no, "category": "syntax", "message": exc.msg,
            })
            continue
        if not isinstance(value, dict):
            diagnostics.append({
                "line": line_no, "category": "non-object",
                "message": f"application event must be object, got {type(value).__name__}",
            })
            continue
        message = contract_error(value)
        if message is not None:
            diagnostics.append({
                "line": line_no, "category": "contract", "message": message,
            })
            continue
        events.append(value)
    return events, diagnostics


stream = (
    '{"type":"text_delta","text":"Hel"}\n'
    '{"type":"text_delta","text":"lo"}\n'
    '42\n'
    '{"type":"usage","tokens":"many"}\n'
    '{oops}\n'
    '{"type":"done"}\n'
)
events, diagnostics = parse_jsonl(stream)
text = "".join(e["text"] for e in events if e["type"] == "text_delta")
print(text)                                      # Hello
print([d["category"] for d in diagnostics])   # non-object, contract, syntax

except 这里只捕获真正抛出的 JSONDecodeError。非对象值和契约不匹配是校验结果，不是假装“捕获了 TypeError”；因此诊断保存稳定的类别、行号和具体消息，而不是把异常类本身塞进记录。标准库为 JavaScript 互操作默认接受 NaN/Infinity；严格 JSONL 在解析入口用 parse_constant 拒绝它们。

🔑 完整行 vs 网络半行：

JSONL 记录分隔符是换行符 \n，因此按 "\n" 切分，而不使用还会识别 NEL 等更多 Unicode 行边界的 splitlines()。JSON 空白 SP/TAB/CR 只能包围一个值，空白本身不是值，所以严格模式会把空行和空白行都诊断为 syntax；仅忽略文本末尾 LF 切分出来的非记录哨兵。也不要用 strip() 让 NBSP 等字符绕过语法校验。若数据按网络 chunk 到达，最后一段可能只是半行；在看到换行前要保留并与下个 chunk 拼接，不能提前归类为 syntax。分帧完成后，才进入 JSON 语法和应用契约两层。

📊 传输层不要混为一谈 
JSONL: 每个完整行承载任意一种合法 JSON 值
应用事件: 本例额外要求 object + 已知 type + 对应必需字段/类型
SDK: 已解析好的结构化 event/chunk；按 SDK 契约消费
SSE: 另有事件与 data 行规则；本课不实现通用 parser

JSONL 的“任意 JSON 值”与本应用的“对象事件”必须分开表述。真实接口优先使用 SDK；需要处理原始 SSE 时使用合规 parser，相关边界见 L15 · httpx。

Q 下面哪种处理方式是正确的？
关键在于先区分“这一行是否已经完整收到”：完整但语法错误的记录应先记录，再按业务契约决定隔离、终止或跳过；本课示例采用隔离后继续。网络 chunk 则可能停在行中间，这种“半行”不是坏记录——必须先缓冲、拼上后续数据凑成完整一行，再尝试解析。

4. json vs orjson（性能）

标准库 json 足够日常使用。当你要序列化大量或超大 JSON（如批处理、日志管线）时，第三方 orjson 快得多（常见快 3–10 倍），且原生支持 datetime、dataclass 等。

知识图谱

文件 I/O
├── with open(..., encoding="utf-8") → 自动关闭 + 防乱码
└── pathlib：Path("a")/"b"、mkdir、read_text/write_text

JSON
├── dumps/loads → 操作字符串（带 s）
├── dump/load → 操作文件（不带 s）
├── ensure_ascii=False → 中文原样
└── indent=2 → 美化

流式解析（JSON Lines）
├── framing：只把完整行送去解析；网络半行先缓冲
├── JSON value：语法错误 → syntax
├── 应用事件：非对象 → non-object；未知种类/字段类型错 → contract
└── text_delta 拼接 text；usage 累加 tokens；done 结束

JSONL / 应用事件契约 / SSE / SDK → 层次不同，处理方式不同（详见 L15）

json vs orjson → 大量序列化时 orjson 快 3–10x

练习：按三层边界解析 JSON Lines 事件日志

import json


def validate_event(event):
    kind = event.get("type")
    if kind == "text_delta":
        if "text" not in event or not isinstance(event["text"], str):
            return "text_delta requires string field 'text'"
    elif kind == "usage":
        tokens = event.get("tokens")
        if not isinstance(tokens, int) or isinstance(tokens, bool):
            return "usage requires integer field 'tokens'"
    elif kind != "done":
        return f"unknown event type: {kind!r}"
    return None


def reject_non_json_constant(token):
    raise json.JSONDecodeError(
        f"non-standard JSON constant: {token}", token, 0,
    )


def parse_complete_jsonl(text: str) -> dict:
    parts, diagnostics = [], []
    total_tokens = 0
    done = False

    lines = text.split("\n")
    if lines and lines[-1] == "":
        lines.pop()  # 末尾 LF 后的切分哨兵不是额外记录
    for line_no, line in enumerate(lines, start=1):
        try:
            value = json.loads(
                line, parse_constant=reject_non_json_constant,
            )
        except json.JSONDecodeError as exc:
            diagnostics.append({
                "line": line_no, "category": "syntax", "message": exc.msg,
            })
            continue
        if not isinstance(value, dict):
            diagnostics.append({
                "line": line_no, "category": "non-object",
                "message": f"application event must be object, got {type(value).__name__}",
            })
            continue
        message = validate_event(value)
        if message is not None:
            diagnostics.append({
                "line": line_no, "category": "contract", "message": message,
            })
            continue

        if value["type"] == "text_delta":
            parts.append(value["text"])
        elif value["type"] == "usage":
            total_tokens += value["tokens"]
        else:
            done = True

    return {
        "text": "".join(parts), "total_tokens": total_tokens,
        "done": done, "diagnostics": diagnostics,
    }


stream = (
    '{"type":"text_delta","text":"你好"}\n'
    '{"type":"text_delta","text":"，世界"}\n'
    '[]\n'                                  # 合法 JSON，违反对象事件契约
    '{"type":"usage","tokens":"42"}\n'  # 对象，但字段类型错误
    '{oops bad line}\n'                    # 完整行，JSON 语法错误
    '{"type":"usage","tokens":42}\n'
    '{"type":"done"}\n'
)
print(parse_complete_jsonl(stream))

思考题

先自己想，再点开对答案。

Q1如果最后一个 chunk 只带来半行 JSON（如 {"type":"text_del），你的代码会崩吗？

不会崩，但会误把半行当坏记录并丢失数据，因此不能直接用于网络流。

边界见本节“坏记录 vs 网络半行”：本练习只接收已分帧的完整 JSONL；网络事件应先由 SDK 或 SSE parser 完成分帧与缓冲。

Q2为什么合法 JSON 数字 42 仍会被本练习拒绝？

因为 JSONL 层允许任意 JSON 值，但本应用的事件契约只接受对象。

42 已通过完整行和 JSON 语法两层，因此诊断类别应是 non-object，而不是 syntax。不要由此误写成“JSONL 只允许对象”。

本课最佳实践验收：故障原子更新与三层 JSONL 校验

任务目标

实现故障原子的 JSON 更新与分层 JSONL 校验，证明写入失败不会破坏旧状态，流式输入错误能在 framing、语法和应用契约层被准确分类。

操作清单

  1. 先完成一次成功原子更新。
  2. 注入 replace 失败并核对旧目标。
  3. 证明失败路径无临时文件且异常对象未被替换。
  4. 仅解析完整 JSONL 行。
  5. 校验已知事件种类、必需字段与类型。

通过标准

  • 成功路径读回新 settings
  • 失败路径保留可解析旧目标
  • 两条路径均无临时文件残留
  • 原始注入异常对象继续向上传播
  • 三类诊断均含准确行号和非空消息
  • 最终打印本课唯一验收标记

        try:
            value = json.loads(
                line, parse_constant=reject_non_json_constant,
            )
        except json.JSONDecodeError as exc:
            diagnostics.append({
                "line": line_no, "category": "syntax", "message": exc.msg,
            })
            continue
        if not isinstance(value, dict):
            diagnostics.append({
                "line": line_no, "category": "non-object",
                "message": f"application event must be object, got {type(value).__name__}",
            })
            continue
        message = validate_event(value)
        if message is not None:
            diagnostics.append({
                "line": line_no, "category": "contract", "message": message,
            })
            continue
        events.append(value)
    return events, diagnostics

面试常见问题

Q1：json.dump 和 json.dumps 区别？

答：带 s 的 dumps/loads 在字符串和对象之间转换；不带 s 的 dump/load 直接读写文件对象。

Q2：为什么读写文件推荐用 with？

答：with 是上下文管理器，块结束时自动关闭文件（即使异常也关），避免句柄泄露。比手动 f.close() 更安全。

Q3：解析 JSON Lines 流时要注意什么？

答：先确保拿到完整行，再解析其中任意合法 JSON 值；若应用只接受对象事件，还要继续校验已知种类、必需字段和类型。诊断应区分语法错误、非对象值和契约错误。网络半行必须先缓冲；真实 SSE 与 SDK 事件是其他层，规则不同，见 L15。

Q4：什么时候用 orjson 而不是标准库 json？

答：当 JSON 序列化成为性能瓶颈（大量或超大数据、高频调用）时。orjson 通常快数倍，并原生支持 datetime/dataclass。日常仍可用标准库。

总结

  • 文件对象用 with open(...) 管理；一次性文本读写可用 Path 方法；两者都显式指定 UTF-8
  • dumps/loads 操作字符串；dump/load 操作文件
  • ensure_ascii=False 让中文原样输出；Python True/False/None ↔ JSON true/false/null
  • JSONL 每个完整行可承载任意合法 JSON 值；对象事件是本应用额外契约
  • 按三层处理：完整行 framing → JSON 语法 → 已知事件种类、必需字段与类型
  • 诊断区分 syntax、non-object、contract；网络半行先缓冲，不能误报语法错
  • JSONL、原始 SSE、SDK 结构不同；真实接口优先 SDK，本课不手写通用 SSE parser
  • 大量序列化才考虑 orjson，别过早优化
