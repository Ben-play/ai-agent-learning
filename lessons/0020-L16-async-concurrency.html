async/await 与并发

同时发 10 个 LLM 请求而不是一个个等 — Agent 提速的关键

💡 为什么这课重要？

Agent 常常要同时做很多件"等网络"的事：并发调多个工具、批量向 LLM 发请求、多路检索。如果一个个串行等，10 个各 1 秒的请求要 10 秒；并发起来只要 1 秒多。

1. GIL 与"为什么 async 有用"

GIL（全局解释器锁）：CPython 同一时刻只允许一个线程执行 Python 字节码。所以多线程不能让纯计算（CPU 密集）真正并行。

但 Agent 的瓶颈几乎都是等网络（I/O 密集）——等 LLM 回、等 API 回。等待时并不占用 CPU。async 正是利用这一点：一个请求在等网络时，切去处理别的请求，单线程内把等待时间重叠起来，实现高并发。

一句话：I/O 密集（调 API）→ async；CPU 密集（大量计算）→ 多进程。

Q asyncio 最适合加速哪类任务？
asyncio 擅长 I/O 密集任务——大量"等网络/等磁盘"的操作（如并发调 LLM）。等待时切去干别的，把等待重叠。纯计算（CPU 密集）受 GIL 限制，async 帮不上，得用多进程。

2. async / await 基础：协程函数、协程对象、Task

知道了"async 适合等 I/O"，来看它的两个关键字怎么写，以及三个容易混的概念：

import asyncio

async def call_llm(prompt):          # ① async def 定义的是"协程函数"
    await asyncio.sleep(1)            # await：在此"可能让出"，等 I/O(这里模拟耗时)
    return f"回答: {prompt}"

async def main():
    coro = call_llm("你好")           # ② 调用协程函数 → 得到"协程对象"，函数体还没执行一行
    result = await coro               # await 协程对象：驱动它执行，拿到返回值
    print(result)

asyncio.run(main())                  # 用 asyncio.run 启动整个异步程序
  • 协程函数（coroutine function）：async def 定义的函数本身，比如 call_llm
  • 协程对象（coroutine object）：调用协程函数得到的对象，比如 coro = call_llm("你好")——这一步函数体一行都没执行，只是造出一个"待执行的计划"
  • await：驱动协程对象真正执行、直到它返回或抛出。await 只能用在 async def 里
  • Task：事件循环用来调度协程的包装（由 asyncio.create_task() 或 gather 内部生成）。协程对象本身不会被调度，必须包成 Task（或直接 await）才会真正运行；这里先建立印象，细节不展开
  • asyncio.run(main()) 是同步世界进入异步世界的入口
⚠️ await 不等于"一定切换任务"

await 等待的对象尚未完成时，当前协程才会挂起，事件循环去运行别的可运行任务；如果被 await 的对象已经完成（比如结果已经就绪），并不保证真的发生一次任务切换——具体行为取决于事件循环实现细节。记住结论就够了：出现 await 不等于自动获得并发。并发需要把多个协程交给事件循环调度；下一节本例使用 gather，也可用 TaskGroup 或 create_task 组织并发。

3. 用 gather 并发调度多个协程

逐个 await 通常是串行。本例用 asyncio.gather 将多个协程交给事件循环并发调度、一起等待；TaskGroup 或 create_task 也可以组织并发：

import asyncio, time

async def call_llm(prompt):
    await asyncio.sleep(1)
    return f"回答: {prompt}"

async def main():
    t0 = time.perf_counter()
    # 同时发起三个，一起等 —— 总耗时≈1 秒，而不是 3 秒
    results = await asyncio.gather(
        call_llm("问题1"),
        call_llm("问题2"),
        call_llm("问题3"),
    )
    print(results)                                   # ['回答: 问题1', ...]
    print(f"耗时 {time.perf_counter()-t0:.2f}s")     # ≈1.00s

asyncio.run(main())

批量场景用解包：await asyncio.gather(*(call_llm(p) for p in prompts))。

🔑 Agent 开发关联：

多工具并行、多路 RAG 检索、批量向 LLM 打分——只要这些子任务互不依赖，就可用 gather（或 TaskGroup / create_task）组织并发，让等待时间尽量重叠。这是 Agent 常见的性能优化手段。

4. 并发限制、超时与异步上下文

上一节的 gather 能一口气并发，但"一口气"太猛也会出事——把本地连接池打满、某个请求卡死拖住全局。所以生产里 gather 之外还要三道护栏：并发限制（Semaphore 控制同时在飞的数量）、超时（wait_for 给单个任务设上限）、异步上下文（async with 确保连接等资源用完即放）。

Semaphore：限制并发数量（不是限流器）

sem = asyncio.Semaphore(5)           # 最多同时 5 个在飞

async def guarded_call(prompt):
    async with sem:                  # 拿到名额才进，超出的排队
        return await call_llm(prompt)

# 就算 100 个任务，也最多 5 个同时在飞
await asyncio.gather(*(guarded_call(p) for p in prompts))
⚠️ Semaphore 只管"同时有几个在飞"，不等于遵守厂商的 RPM/TPM

Semaphore(n) 保护的是并发资源：本地连接池、socket、文件描述符——同一时刻最多 n 个请求在处理中。但 LLM 厂商的限流通常是速率限制：RPM（每分钟请求数）、TPM（每分钟 token 数）。这是两回事：Semaphore(5) 只要 5 个请求都很快返回，短时间内仍可能打出远超 RPM 的请求量，照样触发 429。

要真正遵守 RPM/TPM，需要额外的速率器（令牌桶/时间窗口限速，按时间而非"同时几个"节流），并且在收到 429 时优先读取响应里的 Retry-After 头决定等多久，而不是自己瞎猜退避时间。Semaphore 和"限流"是两个不同维度的护栏，都需要、但不能互相替代。

wait_for：给单个任务加超时

try:
    result = await asyncio.wait_for(call_llm("你好"), timeout=5)
except asyncio.TimeoutError:
    result = None                    # 5 秒没回就放弃

异步上下文管理器（呼应 L10 / L15）

async with httpx.AsyncClient() as client:      # async with
    r = await client.post(url, json=payload)
Q asyncio.gather 相比逐个 await，好处是？
本例用 gather 将多个协程交给事件循环并发调度、一起等待；在各任务耗时相近且可重叠时，总耗时接近最慢的一批，而逐个 await 通常是串行、耗时近似相加。gather 会保持结果顺序，但那不是它相对逐个等待的核心优势；TaskGroup / create_task 也能组织并发。

5. 协程 vs 线程 vs 进程

方式适合Agent 里的用途
协程 asyncioI/O 密集、高并发并发调 LLM/API/检索（首选）
线程 threadingI/O 密集、但库不支持 async包装只有同步版的 SDK
进程 multiprocessingCPU 密集（绕开 GIL）大批量本地计算/向量运算

Agent 绝大多数场景是"等 API"，所以 asyncio 是默认答案；遇到只有同步接口的库可用线程兜底；重计算才上多进程。

知识图谱

GIL → 同一刻只一个线程跑字节码
├── CPU 密集：多线程无用 → 多进程
└── I/O 密集(等网络)：async 把等待重叠 → 高并发

async/await/Task
├── 协程函数(async def) → 调用得到"协程对象"(函数体未执行)
├── await 协程对象 → 驱动执行；等待未完成对象才挂起，非绝对切换
├── Task = 事件循环调度协程的包装(create_task/gather 内部生成)
├── asyncio.run(main()) 入口
└── 单个 await ≠ 并发；出现 await 不代表自动获得并发

并发工具
├── gather / TaskGroup / create_task → 可组织多个协程并发调度
│   └── 本例 gather(*coros) 同时等待并按输入顺序收集结果★
├── Semaphore(n) + async with → 只限制"同时在飞"的并发数，不是限流器
├── RPM/TPM 限流 → 需额外令牌桶/时间窗口速率器 + 遵循 Retry-After
├── wait_for(coro, timeout) → 超时控制
└── async with(异步上下文，如共享的 AsyncClient)

选型：I/O→协程 / 同步库→线程 / CPU→进程

import asyncio, time

async def fake_llm(prompt: str) -> dict:
    await asyncio.sleep(0.2)                       # 模拟网络耗时
    return {"answer": f"回答:{prompt}", "tokens": len(prompt) + 10}

async def call_one(prompt, sem):
    async with sem:                               # 限制同时在飞数量
        try:
            r = await asyncio.wait_for(fake_llm(prompt), timeout=1.0)
            return {"ok": True, **r}
        except Exception as e:                       # TimeoutError 也是 Exception 的子类
            return {"ok": False, "error": repr(e)}   # 单个失败不拖垮整体

async def batch(prompts):
    sem = asyncio.Semaphore(3)                     # 最多同时 3 个在飞
    t0 = time.perf_counter()
    results = await asyncio.gather(*(call_one(p, sem) for p in prompts))
    ok = [r for r in results if r["ok"]]
    return {
        "answers": [r["answer"] for r in ok],
        "success": len(ok),
        "failed": len(results) - len(ok),
        "total_tokens": sum(r["tokens"] for r in ok),
        "elapsed": round(time.perf_counter() - t0, 2),
    }

prompts = [f"问题{i}" for i in range(7)]
print(asyncio.run(batch(prompts)))
# 7 个请求、Semaphore(3)、每个 0.2s → 约 3 批 ≈ 0.6s，而非串行的 1.4s
# {'answers': [...7 条...], 'success': 7, 'failed': 0,
#  'total_tokens': ..., 'elapsed': 0.6}

真实版：共享 AsyncClient + tenacity 正确分层

真实调用要接入 httpx 和重试，结构要点：@retry 装饰"只发一次 HTTP 请求"的 request_once，让可重试异常原样往外抛；call_one 在外层用 try/except 包住"整个重试过程"，重试全部耗尽后才把异常转成 {"ok": False, ...}。共享 client 的 httpx.Timeout(3.0) 限制的是 connect/read/write/pool 等各网络操作的等待，不是一次 attempt 的墙钟上限；不能据此推导整个重试周期最多多久。wait_for(..., timeout=15.0) 包住整个 tenacity 重试周期，是硬总预算：到期会取消调用，可能发生在全部 attempt 完成之前。生产中应按业务 SLA、客户端各阶段 timeout 和退避策略共同调参。若必须给每个 attempt 设置墙钟上限，可在 request_once 内用 wait_for 单独包住 client.post，并把 asyncio.TimeoutError 纳入 tenacity 的重试异常类型；本例不再增加这层代码。批次内所有请求共享同一个 AsyncClient（依赖注入进来，不在 call_one/request_once 内新建）。

import asyncio
import httpx
from tenacity import retry, stop_after_attempt, wait_exponential, retry_if_exception_type

class LLMError(Exception):
    """此异常类型代表允许重试的临时 HTTP 状态错误。"""

@retry(
    retry=retry_if_exception_type((LLMError, httpx.RequestError)),
    stop=stop_after_attempt(3),
    wait=wait_exponential(min=1, max=8),
    reraise=True,                          # 重试耗尽后抛"最后一次"的原始异常
)
async def request_once(client: httpx.AsyncClient, prompt: str) -> dict:
    # 只负责发一次请求；可重试的错误(429/5xx/网络)直接向外抛，交给 @retry 处理
    r = await client.post("/v1/chat", json={"prompt": prompt})
    if r.status_code == 429 or 500 <= r.status_code < 600:
        raise LLMError(f"HTTP {r.status_code}")
    r.raise_for_status()
    return r.json()

async def call_one(client: httpx.AsyncClient, prompt: str, sem: asyncio.Semaphore) -> dict:
    async with sem:                        # 包住整个重试周期；退避时仍占用并发名额
        try:
            # 15s 是整个 tenacity 重试周期的硬总预算；到期可能提前取消剩余 attempt
            result = await asyncio.wait_for(request_once(client, prompt), timeout=15.0)
            return {"ok": True, **result}
        except Exception as e:             # 重试耗尽(或不可重试)之后才在这里捕获
            return {"ok": False, "error": repr(e)}

async def batch(prompts, client: httpx.AsyncClient):
    sem = asyncio.Semaphore(3)
    return await asyncio.gather(*(call_one(client, p, sem) for p in prompts))

# 调用方负责创建"一个"client 并在整个批次生命周期内共享；3.0 限制各网络操作等待:
# async with httpx.AsyncClient(base_url=BASE, timeout=httpx.Timeout(3.0)) as client:
#     results = await batch(prompts, client)
⚠️ 关于 Semaphore 的位置

上面把 async with sem 放在 call_one 里、包住"整次调用（含所有重试尝试）"——这样一个请求从第一次尝试到重试耗尽，全程占用一个并发名额，简单但退避等待期间也占着名额。如果希望退避等待时释放名额、让其它请求先用，采用下面的替代版本：把 semaphore 参数传给被 @retry 装饰的 request_once，并在函数体内只包住每一次实际 HTTP 调用；同时删除 call_one 外层的 async with sem。两种范围不能同时套用，否则同一个请求会重复获取同一 semaphore，可能造成不必要的阻塞甚至死锁。

@retry(
    retry=retry_if_exception_type((LLMError, httpx.RequestError)),
    stop=stop_after_attempt(3),
    wait=wait_exponential(min=1, max=8),
    reraise=True,
)
async def request_once(
    client: httpx.AsyncClient,
    prompt: str,
    sem: asyncio.Semaphore,
) -> dict:
    async with sem:                    # 每次 attempt 只在实际 HTTP 调用期间占名额
        r = await client.post("/v1/chat", json={"prompt": prompt})
    if r.status_code == 429 or 500 <= r.status_code < 600:
        raise LLMError(f"HTTP {r.status_code}")
    r.raise_for_status()
    return r.json()

async def call_one(client, prompt, sem) -> dict:
    try:                               # 这里不再使用 async with sem
        result = await asyncio.wait_for(
            request_once(client, prompt, sem), timeout=15.0
        )
        return {"ok": True, **result}
    except Exception as e:
        return {"ok": False, "error": repr(e)}

这两个版本都合法，取舍点在于：退避等待期间是否把并发名额让给其它请求。

本机演示环境未安装 tenacity，以上代码结构已按其官方 API（retry_if_exception_type / stop_after_attempt / wait_exponential / reraise，用法同 L10）静态核对，不在此冒充实跑；下方"离线异步验证"用 httpx.MockTransport 实际跑通了协程对象、gather、Semaphore 最大并发、批次耗时、共享 client 这几项，tenacity 部分留给你在本地装好库后自行验证。

思考题

先自己想，再点开对答案。

Q1为什么要用 Semaphore 限制并发，而不是一口气 gather 100 个？

【结论】一口气 gather 100 个会同时把 100 个请求全发出去，本地可能耗尽 socket / 连接池，对方也可能因请求太密而返回 429。Semaphore(n) 把"同时在飞"的请求数限制在 n 个，缓解这两个问题——但注意它只管并发数量，不是速率限流器（见正文护栏说明）。

并发不是越多越好。客户端的文件描述符、连接池有上限，开太多连接会报错或急剧变慢；服务端也有各种保护机制。

async with sem: 让每个协程先抢名额、拿到才发请求、发完释放，超出的自动排队。这样即使有 100 个任务，任一时刻也最多 n 个在跑，既快又稳。

但如果厂商限制的是 RPM/TPM（例如每分钟 60 次），Semaphore(n) 只要 n 个请求都很快返回，短时间内仍可能打出远超 RPM 的请求量——这种情况需要额外的速率器（按时间窗口节流），Semaphore 单独并不足够。

Q2把 gather 换成逐个 await，7 个请求耗时会变成多少？

【结论】会从并发的≈0.6s 变成串行的≈1.4s（7 × 0.2s，逐个相加）。

逐个 await 是串行：发第 1 个、等它 0.2s 回来，再发第 2 个……7 个就是 7 段 0.2s 首尾相接，总计≈1.4s。这时 async 的并发优势完全没用上。

await asyncio.gather(*(call_one(p, sem) for p in prompts)) 则同时发起所有协程、一起等——若不限制并发，总耗时≈最慢的那个≈0.2s；但本例 Semaphore(3)、请求数 7，要分约 3 批跑，实际 ≈0.6s。无论哪种，都远快于串行的 1.4s。

要点：逐个 await 本身不带来并发；本例由 gather 把多个协程交给事件循环并发调度，也可用 TaskGroup 或 create_task 组织并发。

Q3真实版里，tenacity 的 @retry 应该装饰哪个函数？异常应该在哪一层被捕获？

【结论】@retry 装饰"只发一次 HTTP 请求"的内层函数（如 request_once），让可重试的异常原样往外抛；外层 call_one 的 try/except 包住"整个重试过程"，在重试全部耗尽（或遇到不可重试的错误）之后才捕获异常、转成 {"ok": False, ...}。若再用 wait_for 包住它，这个 timeout 是整个重试周期的硬总预算，到期可能在全部 attempt 完成前取消调用。注意 httpx.Timeout 限制各网络操作等待，并非每个 attempt 的墙钟上限；如需后者，应在 request_once 内单独用 wait_for 包住 client.post，并将 asyncio.TimeoutError 纳入重试类型。

常见的错误写法是反过来：在 call_one 里先 try/except 吞掉异常返回 {"ok": False}，再在外面套一层 @retry。这样 tenacity 永远看不到异常——它只能看到 call_one 正常返回了一个字典，判断"这次调用成功了"，于是一次都不会重试。重试装饰器必须放在"会真正抛出异常"的那一层，而不是已经把异常吞成返回值的那一层。

另外重试的粒度也要和失败的粒度一致：每个请求独立重试自己的错误（放在单请求级的 call_one/request_once），不要把整个 gather 包起来重跑——否则一个请求失败就会把所有请求（包括已成功的）统统重发一遍。

面试常见问题

Q1：什么是 GIL？它对并发有什么影响？

答：全局解释器锁，让 CPython 同一刻只有一个线程执行字节码。导致多线程无法加速 CPU 密集任务；但 I/O 密集任务（等网络）不受影响，可用 async 或多线程并发。CPU 密集要用多进程。

Q2：async 和多线程都能做并发，区别在哪？

答：async 是单线程内协作式切换（等待未完成的 I/O 时挂起、换别的任务跑），开销小、适合高并发 I/O；多线程由 OS 调度、有切换开销、受 GIL 限制。调大量 API 首选 async；只有同步库时用线程兜底。

Q3：asyncio.gather 是做什么的？它是唯一的并发方式吗？

答：gather 可把多个协程交给事件循环并发调度，并按输入顺序收集结果；在各子任务耗时相近且可重叠的本例中，总耗时约等于最慢的一批，而非逐个相加。它不是唯一方式，TaskGroup 或 create_task 也能组织并发。

Q4：并发调 API 时 Semaphore 能替代限流吗？

答：不能。asyncio.Semaphore(n) + async with 只限制"同时在飞"的并发数量，保护本地连接池/socket；厂商的 RPM/TPM 是速率限制，即使 Semaphore 很小，短时间内密集发送仍可能超过速率上限触发 429。真正遵守速率限制需要额外的令牌桶/时间窗口速率器，并在收到 429 时优先按响应的 Retry-After 头退避。Semaphore 和速率器是两个维度的护栏，需要同时具备。

Q5：真实场景里 tenacity 的 @retry 该放在哪一层？

答：放在"只发一次请求"的内层函数上，让可重试异常原样往外抛；外层函数用 try/except 包住整个重试过程，在重试耗尽之后才捕获转成失败结果。如果先在内层吞异常返回失败字典、再在外面套 @retry，tenacity 看到的永远是"正常返回"，永远不会触发重试。

Q6：await 能用在普通函数里吗？

答：不能。await 只能出现在 async def 协程里。要从同步代码进入异步，用 asyncio.run(coro)。

总结

  • GIL 让多线程无法加速计算；但 async 能重叠 I/O 等待
  • I/O 密集用协程，同步库用线程，CPU 密集用进程
  • 协程函数（async def）调用后得到协程对象（函数体未执行），await 驱动执行；Task 是事件循环调度协程的包装
  • await 只在等待未完成对象时才挂起当前任务，并不等于自动获得并发
  • 本例用 asyncio.gather 并发调度并收集多个协程的结果；TaskGroup / create_task 也能组织并发
  • Semaphore 只限制"同时在飞"的并发数量，不等于遵守 RPM/TPM；速率限制需要额外的令牌桶/时间窗口速率器 + Retry-After
  • wait_for 超时、async with 共享的异步资源（如批次内共享一个 AsyncClient）
  • tenacity 的 @retry 要装饰"只发一次请求"的内层函数、让异常原样往外抛；外层在重试耗尽后才捕获，不能先吞异常再套重试
