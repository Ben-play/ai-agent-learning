async/await 与并发

同时发 10 个 LLM 请求而不是一个个等 — Agent 提速的关键

💡 为什么这课重要？

Agent 常常要同时做很多件"等网络"的事：并发调多个工具、批量向 LLM 发请求、多路检索。如果一个个串行等，10 个各 1 秒的请求要 10 秒；并发起来只要 1 秒多。

1. GIL 与"为什么 async 有用"

GIL（全局解释器锁）：在常见的、启用 GIL 的 CPython 构建中，同一时刻通常只有一个线程执行 Python 字节码，因此纯 Python 的 CPU 密集计算一般不能靠多线程获得真正并行。原生扩展可在执行期间释放 GIL，现代 CPython 也提供可选的 free-threaded 构建，所以这是一条默认选型规则，不是所有运行时的绝对定律。

Agent 的常见瓶颈是等异步网络库（I/O 密集）——等 LLM 回、等 API 回。await 的网络操作挂起时，事件循环可调度别的任务，从而在单线程内重叠等待。普通同步文件读写仍会阻塞事件循环；要并发处理磁盘 I/O，需使用异步实现或通过 asyncio.to_thread() 等方式卸载。

默认选型：大量异步网络 I/O → asyncio；阻塞型 I/O → 异步实现或线程卸载；纯 Python CPU 密集计算 → 优先评估多进程，再按运行时和扩展是否释放 GIL 调整。

Q asyncio 最适合加速哪类任务？
asyncio 擅长使用异步接口的 I/O 密集任务，典型例子是并发等待 LLM/API 网络响应；等待未完成的异步操作时，事件循环可调度别的任务。普通同步磁盘读写不会自动协作让出，需要异步文件实现或 asyncio.to_thread()。纯 Python CPU 密集计算通常应优先评估多进程，而不是用 async 加速。

2. async / await 基础：协程函数、协程对象、Task

知道了"async 适合等 I/O"，来看它的两个关键字怎么写，以及三个容易混的概念：

import asyncio

async def call_llm(prompt):          # ① async def 定义的是"协程函数"
    await asyncio.sleep(1)            # await：在此"可能让出"，等 I/O(这里模拟耗时)
    return f"回答: {prompt}"

async def main():
    coro = call_llm("你好")           # ② 调用协程函数 → 得到"协程对象"，函数体还没执行一行
    result = await coro               # await 协程对象：驱动它执行，拿到返回值
    print(result)

asyncio.run(main())                  # 用 asyncio.run 启动整个异步程序
  • 协程函数（coroutine function）：async def 定义的函数本身，比如 call_llm
  • 协程对象（coroutine object）：调用协程函数得到的对象，比如 coro = call_llm("你好")——这一步函数体一行都没执行，只是造出一个"待执行的计划"
  • await：驱动协程对象真正执行、直到它返回或抛出。await 只能用在 async def 里
  • Task：事件循环用来调度协程的包装（由 asyncio.create_task() 或 gather 内部生成）。协程对象本身不会被调度，必须包成 Task（或直接 await）才会真正运行；这里先建立印象，细节不展开
  • asyncio.run(main()) 是同步世界进入异步世界的入口
⚠️ await 不等于"一定切换任务"

await 等待的对象尚未完成时，当前协程才会挂起，事件循环去运行别的可运行任务；如果被 await 的对象已经完成（比如结果已经就绪），并不保证真的发生一次任务切换——具体行为取决于事件循环实现细节。记住结论就够了：出现 await 不等于自动获得并发。并发需要把多个协程交给事件循环调度；下一节本例使用 gather，也可用 TaskGroup 或 create_task 组织并发。

3. 用 gather 并发调度多个协程

逐个 await 通常是串行。本例用 asyncio.gather 将多个协程交给事件循环并发调度、一起等待；TaskGroup 或 create_task 也可以组织并发：

import asyncio, time

async def call_llm(prompt):
    await asyncio.sleep(1)
    return f"回答: {prompt}"

async def main():
    t0 = time.perf_counter()
    # 同时发起三个，一起等 —— 总耗时≈1 秒，而不是 3 秒
    results = await asyncio.gather(
        call_llm("问题1"),
        call_llm("问题2"),
        call_llm("问题3"),
    )
    print(results)                                   # ['回答: 问题1', ...]
    print(f"耗时 {time.perf_counter()-t0:.2f}s")     # ≈1.00s

asyncio.run(main())

批量场景用解包：await asyncio.gather(*(call_llm(p) for p in prompts))。

🔑 Agent 开发关联：

多工具并行、多路 RAG 检索、批量向 LLM 打分——只要这些子任务互不依赖，就可用 gather（或 TaskGroup / create_task）组织并发，让等待时间尽量重叠。这是 Agent 常见的性能优化手段。

4. 并发限制、取消截止时间与异步上下文

上一节的 gather 能一口气并发，但"一口气"太猛也会出事——把本地连接池打满、某个请求卡死拖住全局。所以生产里 gather 之外还要三道护栏：并发限制（Semaphore 控制活动调用数量）、取消截止时间（wait_for 到期发起取消并等待清理）、异步上下文（async with 确保资源用完即放）。本课的截止时间统一覆盖 semaphore 排队与 operation 执行。

Semaphore：限制并发数量（不是限流器）

sem = asyncio.Semaphore(5)           # 最多同时 5 个在飞

async def guarded_call(prompt):
    async with sem:                  # 拿到名额才进，超出的排队
        return await call_llm(prompt)

# 就算 100 个任务，也最多 5 个同时在飞
await asyncio.gather(*(guarded_call(p) for p in prompts))
⚠️ Semaphore 只管"同时有几个在飞"，不等于遵守厂商的 RPM/TPM

Semaphore(n) 保护的是并发资源：本地连接池、socket、文件描述符——同一时刻最多 n 个请求在处理中。但 LLM 厂商的限流通常是速率限制：RPM（每分钟请求数）、TPM（每分钟 token 数）。这是两回事：Semaphore(5) 只要 5 个请求都很快返回，短时间内仍可能打出远超 RPM 的请求量，照样触发 429。

要真正遵守 RPM/TPM，需要额外的速率器（令牌桶/时间窗口限速，按时间而非"同时几个"节流），并且在收到 429 时优先读取响应里的 Retry-After 头决定等多久，而不是自己瞎猜退避时间。Semaphore 和"限流"是两个不同维度的护栏，都需要、但不能互相替代。

最佳实践：调度层只负责逐项调度与批次隔离

适用：一批彼此独立的 item 需要并发执行，并希望每项都得到最终结果。L16 的输入契约是 Callable[[Item], Awaitable[Result]]：调用 operation(item) 必须得到可等待对象。L15 提供的是“唯一重试 owner 与最终成功/异常”的所有权原则，不是可直接复用的同步实现；L15 的同步 HTTP 示例不能直接 await。真实异步 HTTP 必须用 httpx.AsyncClient 写 adapter，并由 adapter 落实 L15 的最终语义后，再注入 L16。本卡只做一个决策：批次采用逐项失败隔离，不因一项最终失败重跑或取消其它独立项。

from collections.abc import Awaitable, Callable
from typing import Any

Operation = Callable[[str], Awaitable[Any]]

async with httpx.AsyncClient() as client:
    # adapter 内使用 await client...，并落实 L15 的唯一重试 owner / 最终异常原则
    operation: Operation = make_async_operation(client)
    results = await schedule_items(items, operation)
❌ 某项失败就重跑整个 batch
try:
    return await asyncio.gather(
        *(operation(item) for item in items)
    )
except Exception:
    return await run_batch_again(items)

已经成功的 item 会再次调用，产生重复成本或副作用；调度层还侵入了单项策略。

✅ 每项只运行一个 worker
results = await asyncio.gather(
    *(settle_item(item, operation, slots, deadline)
      for item in items)
)

每个 worker 只负责自己的最终结果。一个 item 的最终异常或超时不会取消其它 item，成功项也不会被重跑。

为什么更优：边界清晰：异步 adapter 按 L15 原则拥有单项调用策略并产出最终成功或最终异常；L16 的批次调度只决定“何时运行以及怎样隔离结果”。Semaphore 只包住活动的 operation 调用；本课选择让 wait_for 的截止时间包住“等待 semaphore + 执行 operation”全过程，因此排队时间计入该 item 的截止时间。协调器显式创建 invoke Task；捕获 TimeoutError 时，只有该 Task 因 wait_for 的截止时间取消而处于 cancelled() 状态，才分类为调度超时。若 operation 自己以 TimeoutError 结束，Task 已完成而未取消，必须保留其最终错误类型与消息。截止时间到达时，wait_for 会发起取消并等待取消清理完成；所以墙钟耗时可能超过 timeout。worker 和 operation 的清理代码都必须让 CancelledError 继续传播，async with/finally 才能可靠释放许可与活动资源。

材料成本：并发不是免费加速。通常每个 item 至少对应一个协程/Task 及其栈、异常、结果与追踪状态；gather 会保留整批状态和结果直到批次收齐，批量越大内存越高。并发还会占用连接池并放大上游压力；尾部慢项决定整批可见延迟。取消路径也必须专门测试，包括 operation 是否收到取消、许可是否归还、活动状态是否归零、批次结束是否还有 pending task。海量输入不应一次创建无限 Task，应改用有界队列或分块。

备选结构：数据很少或需要严格顺序时，用串行 for 最简单、状态与内存最低；任一失败都应立即终止同组工作时，用 TaskGroup 的 fail-fast 结构；结果应一完成就下游消费、而不等待尾部慢项时，用 asyncio.as_completed() 做完成顺序流式处理。本卡不混用这些语义，继续坚持“独立项逐项隔离”这一项决策。

自检：可独立运行；逐项隔离、单次成功调用、超时取消清理与许可归还
import asyncio
from collections import Counter


async def settle_item(item, operation, slots, deadline):
    async def admitted_call():
        async with slots:
            return await operation(item)

    invoke_task = asyncio.create_task(admitted_call())
    try:
        value = await asyncio.wait_for(invoke_task, timeout=deadline)
        return {"item": item, "ok": True, "value": value}
    except TimeoutError as error:
        if invoke_task.cancelled():
            return {"item": item, "ok": False, "error": "timeout"}
        return {
            "item": item,
            "ok": False,
            "error": type(error).__name__,
            "message": str(error),
        }
    except asyncio.CancelledError:
        raise
    except Exception as error:
        return {"item": item, "ok": False, "error": type(error).__name__}


async def check():
    calls = Counter()
    active = 0
    cancelled = set()
    cleanup_finished = set()
    slots = asyncio.Semaphore(2)

    async def operation(item):
        nonlocal active
        calls[item] += 1
        active += 1
        try:
            if item == "slow":
                await asyncio.sleep(10)
            else:
                await asyncio.sleep(0.005)
            if item == "bad":
                raise ValueError("final failure")
            if item == "inner-timeout":
                raise TimeoutError("operation-owned timeout")
            return f"ok:{item}"
        except asyncio.CancelledError:
            cancelled.add(item)
            await asyncio.sleep(0.005)
            cleanup_finished.add(item)
            raise
        finally:
            active -= 1

    outcomes = await asyncio.gather(
        *(settle_item(item, operation, slots, 0.10)
          for item in ["ok", "bad", "inner-timeout", "slow"])
    )
    by_item = {outcome["item"]: outcome for outcome in outcomes}

    assert by_item["ok"]["value"] == "ok:ok"
    assert by_item["bad"]["error"] == "ValueError"
    assert by_item["inner-timeout"] == {
        "item": "inner-timeout",
        "ok": False,
        "error": "TimeoutError",
        "message": "operation-owned timeout",
    }
    assert by_item["slow"] == {
        "item": "slow", "ok": False, "error": "timeout"
    }
    assert calls["ok"] == 1
    assert cancelled == {"slow"}
    assert cleanup_finished == {"slow"}
    assert active == 0

    await asyncio.wait_for(slots.acquire(), 0.05)
    await asyncio.wait_for(slots.acquire(), 0.05)
    slots.release()
    slots.release()
    current = asyncio.current_task()
    assert not [
        task for task in asyncio.all_tasks()
        if task is not current and not task.done()
    ]


asyncio.run(check())

结果诊断：自检成功时保持静默。它实际调用完整调度路径：坏项的最终异常被隔离，operation 自己抛出的 TimeoutError("operation-owned timeout") 保留精确错误类型与消息且不会伪装成调度超时，成功项调用次数恰为 1；只有慢项被截止时间取消并完成异步清理；结束后活动计数归零、两个 semaphore 许可均可立即重新取得，并且没有遗留 pending task。

wait_for：给单个 item 设置取消截止时间

async def invoke():
    async with sem:                  # 本课选择：排队也在截止时间内
        return await operation(item)

invoke_task = asyncio.create_task(invoke())
try:
    result = await asyncio.wait_for(invoke_task, timeout=5)
except TimeoutError as error:
    if invoke_task.cancelled():              # wait_for 截止时间取消了 invoke
        result = None
    else:
        raise error                          # operation 自己的最终 TimeoutError

wait_for 的 timeout 是取消截止时间，不是“函数一定在该秒数内返回”的墙钟保证。本例把等待 semaphore 与执行 operation 一起包在截止时间内，并显式保留 invoke Task 以区分两种同名异常：到期后，wait_for 会取消该 Task 并等待取消清理，捕获时 invoke_task.cancelled() 为真；operation 自己以 TimeoutError 结束时，Task 已完成而未取消，不能误报为调度超时。如果 operation 的 finally 清理需要时间，实际墙钟耗时可以超过 5 秒。worker 或 operation 捕获 CancelledError 时必须重新抛出，不能把取消吞成普通失败。

异步上下文管理器：取消时也释放资源

async with slots:                  # 正常返回、异常、取消都会退出上下文
    return await operation(item)

L16 只依赖注入的 operation，不需要知道它是否使用 httpx。如果 operation 内部拥有连接、流或其它临时资源，应在自己的 async with/finally 中清理，并在捕获 CancelledError 后重新抛出。

Q asyncio.gather 相比逐个 await，好处是？
本例用 gather 将多个协程交给事件循环并发调度、一起等待；在各任务耗时相近且可重叠时，总耗时接近最慢的一批，而逐个 await 通常是串行、耗时近似相加。gather 会保持结果顺序，但那不是它相对逐个等待的核心优势；TaskGroup / create_task 也能组织并发。

5. 协程 vs 线程 vs 进程

方式适合Agent 里的用途
协程 asyncioI/O 密集、高并发并发调 LLM/API/检索（首选）
线程 threadingI/O 密集、但库不支持 async包装只有同步版的 SDK
进程 multiprocessing纯 Python CPU 密集（绕开常见 GIL 构建的限制）大批量本地计算；原生库释放 GIL 时需实测后选型

Agent 绝大多数场景是"等 API"，所以 asyncio 是默认答案；遇到只有同步接口的库可用线程兜底；重计算才上多进程。

知识图谱

常见启用 GIL 的 CPython → 同一刻通常只有一个线程执行 Python 字节码
├── 纯 Python CPU 密集：默认优先评估多进程（free-threaded 构建/原生扩展需实测）
├── 异步网络 I/O：await 挂起时重叠等待 → 高并发
└── 普通同步磁盘 I/O：会阻塞事件循环 → 异步实现或 asyncio.to_thread()

async/await/Task
├── 协程函数(async def) → 调用得到"协程对象"(函数体未执行)
├── await 协程对象 → 驱动执行；等待未完成对象才挂起，非绝对切换
├── Task = 事件循环调度协程的包装(create_task/gather 内部生成)
├── asyncio.run(main()) 入口
└── 单个 await ≠ 并发；出现 await 不代表自动获得并发

并发工具
├── gather / TaskGroup / create_task → 可组织多个协程并发调度
│   └── 本例 gather(*coros) 同时等待并按输入顺序收集结果★
├── Semaphore(n) + async with → 只限制"同时在飞"的并发数，不是限流器
├── RPM/TPM 限流 → 需额外令牌桶/时间窗口速率器 + 遵循 Retry-After
├── wait_for(coro, timeout) → 取消截止时间；发起取消并等待清理，墙钟可超时
└── 注入异步 operation(item) → adapter 按 L15 所有权原则产出最终语义；L16 只调度与隔离

选型：I/O→协程 / 同步库→线程 / CPU→进程

实战练习

练习：并发执行注入的单项最终操作

实现一个批次调度器。调用方注入 Callable[[Item], Awaitable[Result]] 形状的异步 operation(item)；异步 adapter 已按 L15 的唯一重试 owner 原则完成单项策略，并以返回值或最终异常结束。L15 的同步示例不能直接被 await；真实异步 HTTP adapter 应使用 httpx.AsyncClient。L16 不读取 HTTP 状态、不添加重试。先自己写，再看答案。

任务清单

  1. 用 asyncio.gather 为每个 item 调度一个 worker，并为每项保留一个最终结果。
  2. 用 Semaphore 限制最多 3 个活动 operation 调用；等待许可的队列不算活动调用。
  3. 显式创建 invoke Task，再用 wait_for 让截止时间覆盖“等待许可 + 执行 operation”全过程；捕获 TimeoutError 后用 Task 的取消状态区分调度截止时间与 operation 自己的最终同名异常。
  4. worker 遇到外部 CancelledError 必须重新抛出；operation 的取消清理也必须重新抛出。
  5. 把注入操作的最终异常转换为该 item 的失败结果，不影响其它项，也不重跑已成功项。

import asyncio
from collections.abc import Awaitable, Callable
from typing import Any

Operation = Callable[[str], Awaitable[Any]]


async def run_one(
    item: str,
    operation: Operation,
    slots: asyncio.Semaphore,
    deadline: float,
) -> dict[str, Any]:
    async def invoke() -> Any:
        async with slots:                  # 只覆盖活动 operation 调用
            return await operation(item)

    invoke_task = asyncio.create_task(invoke())
    try:
        # 明确选择：等待 semaphore 的队列时间也计入截止时间
        value = await asyncio.wait_for(invoke_task, timeout=deadline)
        return {"item": item, "ok": True, "value": value}
    except TimeoutError as error:
        if invoke_task.cancelled():
            return {"item": item, "ok": False, "error": "timeout"}
        # operation 自己的最终 TimeoutError：保留类型和消息
        return {
            "item": item,
            "ok": False,
            "error": type(error).__name__,
            "message": str(error),
        }
    except asyncio.CancelledError:
        raise                               # 保留结构化取消语义
    except Exception as error:
        # operation 已决定这是最终失败；L16 只做逐项隔离
        return {
            "item": item,
            "ok": False,
            "error": type(error).__name__,
            "message": str(error),
        }


async def run_batch(
    items: list[str],
    operation: Operation,
    *,
    max_concurrency: int = 3,
    deadline: float = 1.0,
) -> list[dict[str, Any]]:
    slots = asyncio.Semaphore(max_concurrency)
    return await asyncio.gather(
        *(run_one(item, operation, slots, deadline) for item in items)
    )


async def demo_operation(item: str) -> str:
    try:
        if item == "slow":
            await asyncio.sleep(10)
        else:
            await asyncio.sleep(0.005)
        if item == "final-failure":
            raise RuntimeError("injected final operation failure")
        if item == "inner-timeout":
            raise TimeoutError("operation-owned timeout")
        return f"done:{item}"
    except asyncio.CancelledError:
        raise                               # operation 清理后继续传播取消
    finally:
        pass                                # 在这里关闭单项临时资源


async def main() -> None:
    items = ["a", "final-failure", "inner-timeout", "slow", "b"]
    results = await run_batch(items, demo_operation, deadline=0.10)
    by_item = {result["item"]: result for result in results}

    assert [result["item"] for result in results] == items
    assert by_item["inner-timeout"] == {
        "item": "inner-timeout",
        "ok": False,
        "error": "TimeoutError",
        "message": "operation-owned timeout",
    }
    assert by_item["slow"] == {
        "item": "slow", "ok": False, "error": "timeout"
    }
    assert sum(result["ok"] for result in results) == 2


asyncio.run(main())

调度语义：gather 返回值按输入顺序排列，而不是按完成先后排列。每项 worker 都把普通最终异常转成自己的失败结果，因此其它项继续完成。若整个批次被上层取消，CancelledError 会继续传播，而不是被误报为某项普通失败。

截止时间语义：这里先显式创建 invoke Task，再由 wait_for 包住它，所以 semaphore 排队与 operation 执行共用一个截止时间。捕获 TimeoutError 后只在 Task 已取消时落为调度 timeout；Task 已完成则表示 operation 自己抛出了最终 TimeoutError，其类型和消息必须保留。到期会发起取消并等待清理；墙钟耗时可能超过配置值。async with slots 会在取消路径释放许可，operation 则应在 finally 清理活动资源并重新抛出 CancelledError。

思考题

先自己想，再点开对答案。

Q1为什么 Semaphore 只包住 operation，而不是包住整个 batch？

【结论】semaphore 表示可同时占用的活动调用槽位。每个 worker 排队拿到许可后才进入 operation，结束、失败或取消时释放；这样排队任务不占活动名额，任一时刻实际 operation 调用不超过上限。

Q2为什么必须单独处理 TimeoutError 与 CancelledError？

【结论】TimeoutError 可能来自调度截止时间，也可能是 operation 自己的最终异常，不能仅凭异常类型判断。显式保存传给 wait_for 的 Task：捕获时 Task 已取消才是调度 timeout；Task 已完成则保留 operation 的错误类型与消息。CancelledError 往往表示上层正在取消整个批次，必须继续传播。混在宽泛异常处理中会破坏取消语义，并可能留下未清理资源。

Q3L16 为什么不判断 429/5xx，也不调用 Tenacity？

【结论】这些属于遵循 L15 所有权原则的单项异步 adapter。adapter 使用异步客户端并决定怎样重试以及何时形成最终异常；L16 只消费最终成功或最终失败。L15 的同步示例不能直接 await。分层后不会出现两层重试、重复退避，批次调度也不依赖 HTTP。

本课最佳实践验收：档案馆文档预览协调器

这是近迁移验收：不再复刻 item worker 的命名和 fixture 结构，而是在陌生的“数字档案馆并行文档预览”领域实现域级 PreviewCoordinator。注入的 renderer 仍满足 Callable[[Document], Awaitable[Preview]]，并已通过异步 adapter 落实 L15 的唯一重试 owner / 最终异常原则；协调器只负责并发、截止时间、取消传播与逐文档隔离。验收还必须机械地区分 renderer 自己的最终 TimeoutError 与协调器截止时间：前者保留错误身份与消息，后者才落为 timeout。

操作清单

  1. 由 PreviewCoordinator 并发渲染五份档案文档，最多两个 renderer 同时活动。
  2. 让一份损坏文档抛出最终渲染异常，只把该文档落为失败。
  3. 让另一份文档由 renderer 自己抛出带精确消息的最终 TimeoutError，确认不会误分为协调器 timeout。
  4. 让一份超慢手稿越过截止时间，确认 renderer 收到取消并完成清理。
  5. 另起一次渲染批次，由上层取消整个协调器调用，确认取消继续传播。
  6. 两次场景后都确认许可全部恢复、活动数归零且没有 pending task。
通过标准
  • 五份文档各有一个最终结果；两个成功预览的 renderer 调用次数均为 1。
  • 损坏文档的最终失败不影响其它文档，实测峰值活动并发恰为 2。
  • renderer 自己的 TimeoutError 精确保留错误类名与消息；超慢手稿才落为 timeout，且取消清理完成。
  • 外部取消传播 CancelledError，没有被伪装成文档失败。
  • 许可全部可重新获取、无活动 renderer、无 pending task；标准输出恰为 L16 ACCEPTED。
课末近迁移验收（纯标准库；离线、无网络/密钥/文件、无 httpx/Tenacity）：
import asyncio
import time
from collections import Counter
from collections.abc import Awaitable, Callable
from typing import Any

Document = str
Preview = str
Renderer = Callable[[Document], Awaitable[Preview]]


class FinalRenderFailure(Exception):
    pass


class PreviewCoordinator:
    def __init__(self, renderer: Renderer, *, parallelism: int, deadline: float):
        self.renderer = renderer
        self.slots = asyncio.Semaphore(parallelism)
        self.deadline = deadline

    async def render_documents(self, documents: list[Document]) -> list[dict[str, Any]]:
        return await asyncio.gather(
            *(self._capture_preview(document) for document in documents)
        )

    async def _capture_preview(self, document: Document) -> dict[str, Any]:
        async def render_when_admitted() -> Preview:
            async with self.slots:
                return await self.renderer(document)

        render_task = asyncio.create_task(render_when_admitted())
        try:
            preview = await asyncio.wait_for(
                render_task, timeout=self.deadline
            )
            return {"document": document, "status": "ready", "preview": preview}
        except TimeoutError as error:
            if render_task.cancelled():
                return {"document": document, "status": "timeout"}
            return {
                "document": document,
                "status": "failed",
                "error": type(error).__name__,
                "message": str(error),
            }
        except asyncio.CancelledError:
            raise
        except Exception as error:
            return {
                "document": document,
                "status": "failed",
                "error": type(error).__name__,
                "message": str(error),
            }


async def reclaim_all_permits(coordinator: PreviewCoordinator, count: int) -> None:
    for _ in range(count):
        await asyncio.wait_for(coordinator.slots.acquire(), timeout=0.05)
    for _ in range(count):
        coordinator.slots.release()


def assert_no_background_tasks() -> None:
    current = asyncio.current_task()
    leftovers = [
        task for task in asyncio.all_tasks()
        if task is not current and not task.done()
    ]
    assert leftovers == []


def instrumented_renderer(state: dict[str, Any]) -> Renderer:
    async def render(document: Document) -> Preview:
        state["calls"][document] += 1
        state["active"] += 1
        state["peak"] = max(state["peak"], state["active"])
        try:
            if document in {"slow-manuscript", "cancelled-volume"}:
                await asyncio.sleep(10)
            else:
                await asyncio.sleep(0.01)
            if document == "damaged-map":
                raise FinalRenderFailure("unreadable archive scan")
            if document == "renderer-timeout":
                raise TimeoutError("renderer exhausted its own budget")
            return f"preview:{document}"
        except asyncio.CancelledError:
            state["cancelled"].add(document)
            await asyncio.sleep(0.01)
            state["cleaned"].add(document)
            raise
        finally:
            state["active"] -= 1

    return render


def fresh_state() -> dict[str, Any]:
    return {
        "calls": Counter(),
        "active": 0,
        "peak": 0,
        "cancelled": set(),
        "cleaned": set(),
    }


async def main() -> None:
    state = fresh_state()
    coordinator = PreviewCoordinator(
        instrumented_renderer(state), parallelism=2, deadline=0.08
    )
    documents = [
        "slow-manuscript",
        "policy-volume",
        "damaged-map",
        "renderer-timeout",
        "table-ledger",
    ]

    started = time.perf_counter()
    outcomes = await coordinator.render_documents(documents)
    elapsed = time.perf_counter() - started
    by_document = {outcome["document"]: outcome for outcome in outcomes}

    assert [outcome["document"] for outcome in outcomes] == documents
    assert by_document["policy-volume"] == {
        "document": "policy-volume",
        "status": "ready",
        "preview": "preview:policy-volume",
    }
    assert by_document["table-ledger"] == {
        "document": "table-ledger",
        "status": "ready",
        "preview": "preview:table-ledger",
    }
    assert by_document["damaged-map"]["status"] == "failed"
    assert by_document["damaged-map"]["error"] == "FinalRenderFailure"
    assert by_document["renderer-timeout"] == {
        "document": "renderer-timeout",
        "status": "failed",
        "error": "TimeoutError",
        "message": "renderer exhausted its own budget",
    }
    assert by_document["slow-manuscript"] == {
        "document": "slow-manuscript", "status": "timeout"
    }
    assert state["calls"] == Counter({document: 1 for document in documents})
    assert state["calls"]["policy-volume"] == 1
    assert state["calls"]["table-ledger"] == 1
    assert state["peak"] == 2
    assert state["cancelled"] == {"slow-manuscript"}
    assert state["cleaned"] == {"slow-manuscript"}
    assert elapsed >= 0.09
    assert state["active"] == 0
    await reclaim_all_permits(coordinator, 2)
    assert_no_background_tasks()

    cancel_state = fresh_state()
    cancel_coordinator = PreviewCoordinator(
        instrumented_renderer(cancel_state), parallelism=1, deadline=10.0
    )
    render_job = asyncio.create_task(
        cancel_coordinator.render_documents(["cancelled-volume"])
    )
    while cancel_state["active"] == 0:
        await asyncio.sleep(0)
    render_job.cancel()
    try:
        await render_job
    except asyncio.CancelledError:
        pass
    else:
        raise AssertionError("external batch cancellation must propagate")

    assert cancel_state["calls"] == Counter({"cancelled-volume": 1})
    assert cancel_state["cancelled"] == {"cancelled-volume"}
    assert cancel_state["cleaned"] == {"cancelled-volume"}
    assert cancel_state["active"] == 0
    await reclaim_all_permits(cancel_coordinator, 1)
    assert_no_background_tasks()

    print("L16 ACCEPTED")


asyncio.run(main())

结果诊断：脚本必须无断言失败，并只打印唯一标记 L16 ACCEPTED。成功预览调用次数超过 1 表示协调器错误地重跑；损坏地图影响其它文档表示最终失败未隔离；renderer 自己的 TimeoutError 没有保留精确类名与消息、或被落为 timeout，表示协调器把 operation 最终错误误判为调度截止时间；峰值不是 2 表示并发许可范围错误；慢手稿没有完成取消清理表示截止时间语义错误；外部取消没有穿过协调器表示批次级取消被吞掉；许可无法全部重新取得、活动数非 0 或存在 pending task，则说明取消/异常路径仍泄漏状态。

阶段实践检查点：失败责任归属

用纯标准库把 L10 根因链、L15 单一重试 owner 与 L16 独立项隔离接起来：adapter 独自完成单项重试和异常翻译，scheduler 只并发收齐结果，绝不重试整个 batch。

操作清单

  1. 让 adapter 对临时失败项独自重试 1 次并成功。
  2. 把永久传输失败翻译为领域异常，并保留 __cause__。
  3. 并发调度临时项、永久失败项与两个稳定项。
  4. 把每项最终成功或异常隔离为独立结果，并核对每项调用次数。
通过标准
  • 临时项只由 adapter 调用 2 次，第二次成功。
  • 永久项返回失败结果，领域异常的 __cause__ 是原始永久错误。
  • 两个稳定项各调用 1 次，所有四项都有独立结果。
  • scheduler 的 batch 调度次数为 1，没有批次重试。
  • 标准输出只有检查点标记。

参考验收程序（独立完成后展开，纯标准库）
import asyncio
from collections import Counter
from collections.abc import Awaitable, Callable
from dataclasses import dataclass


class TransientTransportError(Exception):
    pass


class PermanentTransportError(Exception):
    pass


class ItemUnavailable(Exception):
    pass


@dataclass(frozen=True)
class ItemResult:
    item: str
    value: str | None = None
    error: Exception | None = None


class Adapter:
    def __init__(self) -> None:
        self.calls: Counter[str] = Counter()

    async def fetch(self, item: str) -> str:
        for attempt in range(2):
            try:
                return await self._transport(item)
            except TransientTransportError:
                if attempt == 1:
                    raise
                await asyncio.sleep(0)
            except PermanentTransportError as error:
                raise ItemUnavailable(f"unavailable:{item}") from error
        raise AssertionError("retry loop exhausted without a final outcome")

    async def _transport(self, item: str) -> str:
        self.calls[item] += 1
        await asyncio.sleep(0)
        if item == "transient" and self.calls[item] == 1:
            raise TransientTransportError("try once more")
        if item == "permanent":
            raise PermanentTransportError("gone")
        return f"ok:{item}"


Operation = Callable[[str], Awaitable[str]]
batch_runs = 0


async def settle(item: str, operation: Operation) -> ItemResult:
    try:
        return ItemResult(item=item, value=await operation(item))
    except asyncio.CancelledError:
        raise
    except Exception as error:
        return ItemResult(item=item, error=error)


async def schedule(items: list[str], operation: Operation) -> list[ItemResult]:
    global batch_runs
    batch_runs += 1
    return await asyncio.gather(*(settle(item, operation) for item in items))


async def main() -> None:
    adapter = Adapter()
    items = ["steady-a", "transient", "permanent", "steady-b"]
    results = await schedule(items, adapter.fetch)
    by_item = {result.item: result for result in results}

    assert [result.item for result in results] == items
    assert by_item["steady-a"].value == "ok:steady-a"
    assert by_item["transient"].value == "ok:transient"
    assert by_item["steady-b"].value == "ok:steady-b"

    permanent = by_item["permanent"].error
    assert isinstance(permanent, ItemUnavailable)
    assert isinstance(permanent.__cause__, PermanentTransportError)
    assert str(permanent.__cause__) == "gone"

    assert adapter.calls == Counter(
        {"transient": 2, "steady-a": 1, "permanent": 1, "steady-b": 1}
    )
    assert batch_runs == 1
    assert len(results) == len(items)

    print("P1 CHECKPOINT FAILURE-OWNERSHIP PASSED")


asyncio.run(main())

结果诊断：临时项不是 2 次说明 adapter 没有独占一次重试；稳定项超过 1 次或 batch_runs 超过 1 说明 scheduler 错误地重跑 batch；永久失败没有 PermanentTransportError 作为 __cause__，说明异常翻译丢失根因；结果少于输入项表示单项失败扩散到了其它独立任务。

面试常见问题

Q1：什么是 GIL？它对并发有什么影响？

答：在常见的、启用 GIL 的 CPython 构建中，同一刻通常只有一个线程执行 Python 字节码，因此纯 Python CPU 密集任务一般不能靠多线程并行加速；默认优先评估多进程。原生扩展可释放 GIL，CPython 也有可选 free-threaded 构建，所以最终仍要按运行时和负载实测。异步网络等待则可用 async 或线程并发。

Q2：async 和多线程都能做并发，区别在哪？

答：async 是事件循环中的协作式切换：等待未完成的异步 I/O 时挂起当前任务，开销小、适合高并发网络 I/O；普通同步文件调用仍会阻塞，需要异步实现或 asyncio.to_thread()。线程由 OS 调度，适合包装阻塞型库；是否受 GIL 限制取决于 CPython 构建和原生代码是否释放 GIL。

Q3：asyncio.gather 是做什么的？它是唯一的并发方式吗？

答：gather 可把多个协程交给事件循环并发调度，并按输入顺序收集结果；在各子任务耗时相近且可重叠的本例中，总耗时约等于最慢的一批，而非逐个相加。它不是唯一方式，TaskGroup 或 create_task 也能组织并发。

Q4：并发调 API 时 Semaphore 能替代限流吗？

答：不能。asyncio.Semaphore(n) + async with 只限制"同时在飞"的并发数量，保护本地连接池/socket；厂商的 RPM/TPM 是速率限制，即使 Semaphore 很小，短时间内密集发送仍可能超过速率上限触发 429。真正遵守速率限制需要额外的令牌桶/时间窗口速率器，并在收到 429 时优先按响应的 Retry-After 头退避。Semaphore 和速率器是两个维度的护栏，需要同时具备。

Q5：L16 批次调度器与 L15 单项操作怎样分工？

答：L15 提供“唯一重试 owner 与最终异常”的所有权原则，不提供可直接等待的同步示例。调用方用异步 adapter（HTTP 场景使用 httpx.AsyncClient）实现 Callable[[Item], Awaitable[Result]] 的最终语义；L16 不重复这些策略，只为每项调度一次异步操作，用 Semaphore 限制活动调用，用取消截止时间约束排队加执行，并把最终成功、失败或超时隔离成逐项结果。成功项不会因别项失败而重跑。

Q6：wait_for 的 timeout 是严格墙钟上限吗？

答：不是。它是取消截止时间：到期后发起取消，并等待内部协程完成取消清理后才抛出 TimeoutError，所以墙钟可能更久。本课让截止时间覆盖 semaphore 排队和 operation，并显式保存 invoke Task：捕获同名异常时，Task 已取消才是调度截止时间；Task 已完成则是 operation 自己的最终 TimeoutError，必须保留身份与消息。worker 与 operation 都必须重新抛出 CancelledError。

Q7：await 能用在普通函数里吗？

答：不能。await 只能出现在 async def 协程里。要从同步代码进入异步，用 asyncio.run(coro)。

总结

  • 常见启用 GIL 的 CPython 构建会限制纯 Python 多线程并行；free-threaded 构建和释放 GIL 的原生扩展需另行实测
  • 异步网络 I/O 用协程；阻塞型 I/O 用异步实现或线程卸载；纯 Python CPU 密集默认优先评估多进程
  • 协程函数（async def）调用后得到协程对象（函数体未执行），await 驱动执行；Task 是事件循环调度协程的包装
  • await 只在等待未完成对象时才挂起当前任务，并不等于自动获得并发
  • 本例用 asyncio.gather 并发调度并收集多个协程的结果；TaskGroup / create_task 也能组织并发
  • Semaphore 只限制"同时在飞"的并发数量，不等于遵守 RPM/TPM；速率限制需要额外的令牌桶/时间窗口速率器 + Retry-After
  • wait_for 设置取消截止时间：本课把 semaphore 排队与 operation 都纳入；显式保留 invoke Task，只有 Task 因截止时间被取消时才分类为调度 timeout，operation 自己的最终 TimeoutError 保留类型与消息；到期发起取消并等待清理，因此墙钟可能超过 timeout
  • L16 消费 Callable[[Item], Awaitable[Result]] 形状的异步 operation；adapter 按 L15 所有权原则提供最终语义（同步示例不可直接 await，异步 HTTP 使用 AsyncClient），L16 不分类 HTTP 状态、不实现重试，只隔离逐项结果且不重跑成功项
  • worker 与 operation 的取消清理必须重新抛出 CancelledError；async with/finally 负责释放许可与活动资源
