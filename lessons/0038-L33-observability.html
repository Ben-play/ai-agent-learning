LLM 可观测性

用 OpenTelemetry GenAI 语义约定，看清 Agent 慢在哪、错在哪、哪些费用算得出来

💡 为什么这课重要？

一个 Agent 上线后，本质是个黑盒：它调了哪些模型、走了哪些工具、烧了多少 Token 和钱、哪一步慢、哪一步失败——如果你"看不见"，就既没法调优、也没法排障。用户说"它变慢了、变贵了、答错了"，你连从哪查起都不知道。

这一课教你给 Agent 装上“仪表盘”：用 OpenTelemetry GenAI 语义约定给数据统一命名，用 trace 查单次请求，用 metrics 看趋势，用有用量和价格依据的账本算成本。课内固定采用独立发布的 v0.1.0（2026-11-21 发布，截至 2026-11-23 仍为 Development）。统一命名能减少迁移工作，不等于后端会自动映射；默认不采集原始输入输出或工具参数、结果。

学习目标

完成本课后，你将能够：

  • 说清可观测性三大支柱：Traces / Metrics / Logs，以及为什么 Agent 最看重 trace
  • 选出默认记录的最小信号：模型、Token 数、耗时、工具名和错误类型；区分首输出块与首 Token
  • 按 OTel GenAI v0.1.0 区分 span 属性与 metric，核对升级时的名称和单位
  • 说明自动埋点和 OTLP 后端各管什么，列出接入前要验收的映射和隐私设置
  • 用有价格依据的用量做成本告警，并显式保留未知费用，接回 L23 的成本工程

1. 为什么 Agent 必须"能被看见"

普通函数错了，你看堆栈就行。但 Agent 不是普通函数——它是一串自主的、多步的、带随机性的决策：想一步、调个工具、再想一步、再调个模型……问题恰恰藏在"哪一步"里：

  • 为什么慢？是某次 LLM 生成太长，还是某个工具（如搜索、DB）卡住了？
  • 为什么贵？是上下文越滚越大（L23），还是某条链路反复重试？
  • 为什么错？是模型幻觉，还是工具返回了脏数据、参数拼错了？

不可观测，这些问题全靠猜。生产 Agent 必须能"看见"自己的每一步——可观测性不是锦上添花，是 Agent 从 demo 走向线上的准入门槛。

2. 三大支柱：Traces / Metrics / Logs

可观测性（Observability）是一套通用工程概念，由三根支柱组成：

  • Traces（链路追踪）：一次请求完整的调用链。链里的每个操作是一个 span（跨度），span 之间有父子关系，串成一棵树。
  • Metrics（指标）：可聚合的数字，例如 Token 用量、延迟和错误率；业务侧也可以发布由账本算出的成本指标。
  • Logs（日志）：离散的事件记录，用来翻查“某刻发生了什么”。可用 Trace ID 关联，但也不默认写正文。

对 LLM / Agent 来说，trace 特别适合定位某一步：给观测到的 LLM 和工具调用分别建 span，串起实际执行顺序。它记录的是执行轨迹，不是模型的内部思考。

Trace: flight_assistant                （root span，任务类型，不是用户原话）
├─ span  LLM 调用①                     模型、已知 Token 数、耗时
├─ span  工具调用 search_flights        工具名、状态、耗时
├─ span  LLM 调用②                     模型、已知 Token 数、耗时
└─ span  工具调用 book                  工具名、状态、耗时、失败类型（若有）
Q 三大支柱里，为什么 Agent 最看重 trace？
Agent 是多步、自主的，问题藏在“哪一步”。trace 用父子 span 串起观测到的 LLM / 工具调用，不用看原始输入或工具参数也能定位先后顺序、耗时和失败。Metrics 用于聚合看趋势，Logs 可关联事件；两者都不能替代这条单次调用链。

3. 该追踪什么（LLM 特有的信号）

要查清“慢 / 贵 / 错”，优先记录以下元数据，不需要把请求正文塞进遥测：

  • 模型和 Token 数：区分请求模型和响应报告的模型；有用量才记输入 / 输出 Token 数。路由后实际模型可能不同（L32）。
  • 延迟：总耗时衡量整次调用；流式调用还可记首输出块时间。只含元数据的事件不算首块；首块可能是工具调用信息，也可能有多个 Token，不能直接当作 TTFT（首 Token 时间，见 L26）。
  • 工具与错误：记工具名、耗时、状态和可用的关联 ID；失败时记可聚合的错误类型，例如超时、限流（L31），不要把原始错误正文当类型。
  • 成本：按计费用量和对应价格在业务账本估算（L23），缺数据就保留未知。

默认不采集提示词、原始输入输出（含系统指令）或工具参数、结果，日志也一样。确需诊断时才授权启用，先脱敏并限制采样、访问和保留期；采样本身不能去除敏感信息。

4. OpenTelemetry GenAI 语义约定（本课重点）

统一命名能少写一层 model / model_name / llm.model 转换，但先分清信号。下面是 GenAI v0.1.0（Development）中本课用到的部分约定，不是完整字段表。

Span 属性：描述单次调用

gen_ai.operation.name                # 如 chat（推理）、execute_tool（工具）
gen_ai.provider.name                 # 埋点所识别的提供方，可能不同于实际上游
gen_ai.request.model                 # 请求发出的模型名
gen_ai.response.model                # 响应报告的模型名，可能不同
gen_ai.usage.input_tokens            # 已知输入 Token 数（整数）
gen_ai.usage.output_tokens           # 已知输出 Token 数（整数）
gen_ai.response.time_to_first_chunk  # 流式首输出块时间（秒，无首块就不记）
gen_ai.tool.name                     # 工具执行 span 的工具名
error.type                           # 失败时记录错误类型

结构化不等于可以默认上传。这个版本要求带 JSON Schema 的属性（如 gen_ai.input.messages、gen_ai.output.messages、gen_ai.system_instructions、gen_ai.tool.definitions）在 span / event 上用符合 schema 的结构化值，不再用 JSON 字符串兜底。输入输出消息很可能含个人信息；系统指令和工具定义也可能含敏感信息。推理消息的部件可以带工具调用数据；工具执行 span另有需要显式启用的 gen_ai.tool.call.arguments / gen_ai.tool.call.result，同样按各自 schema 记录，也可能含敏感信息。本课默认不采集这些内容。

Metrics：记录可聚合的样本，不是把 span 属性改名

  • 推理耗时：旧的 gen_ai.client.operation.duration 对推理改用 gen_ai.client.inference.duration（Histogram，s）；不要把其他操作的旧序列也改成推理。
  • 每次推理用量：旧的 gen_ai.client.token.usage 对推理拆为 gen_ai.client.inference.operation.input_tokens 与 gen_ai.client.inference.operation.output_tokens（Histogram，{token}），不再用 gen_ai.token.type 区分方向。这两条用于看每次调用的分布，不用于算账。
  • 流式首输出块：旧的 gen_ai.client.operation.time_to_first_chunk 改为 gen_ai.client.inference.time_to_first_chunk（Histogram，s）。在认证和首次尝试前开始计时，包含失败尝试和重试等待；到客户端完整收到第一个含非空新输出的已解码提供方事件为止。没收到就不记该样本。

按标签版本核对名称、类型和单位。共享语义能降低迁移成本，但 OTLP 能传输数据，不代表后端会自动将它们映射到查询、看板或告警。

面试高频：「LLM 应用怎么做可观测性？」 可以这样答：用 Trace 串起模型和工具调用，用 Metrics 看聚合趋势，用 Logs 补充事件。固定 OTel GenAI 版本，分清 span 属性和指标，接入时验收后端映射与单位；默认不传正文或工具参数。成本按有效用量和价格估算，告警同时关注已知成本和缺数，不能把未知当零。
Q 用 GenAI v0.1.0 做推理延迟看板，哪种做法正确？
gen_ai.request.model 是描述单次调用的 span 属性；gen_ai.client.inference.duration 才是推理耗时直方图（秒）。统一命名能减少映射工作，但仍要固定约定和埋点库版本，验收后端是否按预期入库和聚合，迁移时更新旧查询。

5. 工具生态：怎么落地

约定解决“叫什么”，埋点库解决“能采到什么”，后端解决“能查到什么”。例如，OpenLLMetry（Traceloop）是自动埋点选项，Langfuse提供 OTLP trace 接入；不能据此推断它们支持本课版本的所有属性、结构化值或指标。

  1. 采集前：固定埋点库和采用的约定版本；确认覆盖的模型和工具调用，关闭正文采集，先检查本地生成的 span 和指标。
  2. 接入时：在自己的测试环境按信号验收。对照 trace 父子关系、指标名称 / 类型 / 单位和后端映射；用已知样本验算查询与告警，不只看 OTLP 是否返回成功。
  3. 升级时：逐项迁移旧查询、看板和告警；不要把旧指标与新指标直接混算。

第 7 节只做离线映射验收，不启动埋点库、exporter 或后端，不能据此宣布集成已通过。

6. 成本告警：把可观测性变成行动

光看看板还不够。要让告警真有用，先把“观测到多少用量”和“能算出多少费用”分清楚：

  • 看用量：每次调用的 Token 直方图用于看分布。启用该埋点时，按约定记录失败调用（带 error.type）；没有响应或响应没有用量时，直方图记录 0。这个值不是实际零用量。若本来就无法高效取得计数、也未显式启用离线计数，则不发用量指标。
  • 看总量：用 gen_ai.client.inference.usage.input_tokens / gen_ai.client.inference.usage.output_tokens（Counter，{token}）累计已知用量，不拿单次用量直方图当账单。缓存输入和模型推理（reasoning）输出的细分值已含在相应总量里，不能再相加。
  • 算成本：按可计费用量和对应模型、计费类别、币种及有效价格计算估算费用（见 L23）。缺用量、缺必要的明细或缺价就记未知，不要把指标的 0 填进账本。GenAI 约定不提供价格，也不会自动生成成本指标。
  • 设告警：分别监控“已知日成本超过预算”和“未知费用的笔数或比例升高”。延迟可看推理耗时或首块耗时的 P95；错误率要有明确的分母（如失败次数 / 总调用数），参见 L31。
Q 调用失败且未返回用量，直方图按约定记了 0，这次应怎么记账？
直方图里的 0 是用量缺失时的记法，不是账单证据。已知用量和对应价格才能算出已知费用。按已知成本设预算告警，同时单独监控未知费用；用 trace 和日志定位缺数或失败。

离线验收：只输出一行通过标记

把下面整段复制到 Python 文件，用 python -I 文件名.py 运行。不需密钥、网络或第三方包；样本、价格都是虚构的，假设只有按输入 / 输出 Token 计费。验收仅验证本地字段映射、毫秒转秒、正文不出现在结果里，以及占位零、未知费用与真实零的区别。不验证 OTel SDK、exporter 或后端。全部断言通过后输出 L33 ACCEPTED。

import json


def normalize(call, rates):
    dimensions = {
        "gen_ai.operation.name": "chat",
        "gen_ai.provider.name": call["provider"],
        "gen_ai.request.model": call["requested_model"],
        "gen_ai.response.model": call["response_model"],
    }
    span = dimensions.copy()
    if error := call.get("error_type"):
        span["error.type"] = error
    metric_attrs = span.copy()
    metrics = {"gen_ai.client.inference.duration": ("s", call["duration_ms"] / 1000, metric_attrs)}
    if (first := call.get("first_chunk_ms")) is not None:
        span["gen_ai.response.time_to_first_chunk"] = first / 1000
        metrics["gen_ai.client.inference.time_to_first_chunk"] = ("s", first / 1000, dimensions)

    usage = call.get("usage")  # 样本只模拟完整用量或完全没有用量
    for direction, count in zip(("input", "output"), usage if usage is not None else (0, 0)):
        if usage is not None:
            span[f"gen_ai.usage.{direction}_tokens"] = count
        metrics[f"gen_ai.client.inference.operation.{direction}_tokens"] = ("{token}", count, metric_attrs)

    rate = rates.get((call["provider"], call["response_model"]))
    cost = None if usage is None or rate is None else sum(n * p for n, p in zip(usage, rate))
    return {"span": span, "metrics": metrics, "ledger": {"usage": usage, "cost": cost}}

决策卡：首输出块计时既不从重试重置，也不停在元数据上

适用：流式展馆助手用首输出块指标定位用户等待。只关心整次调用耗时时，查推理耗时指标；首块也不是首 Token。

见首个事件就记值

这条流先收元数据，失败重试后才收工具参数块。见元数据就报 20 ms，会把等待算短；最终没收到输出也不能记 0。

在收到非空新输出时停表

同一条流从首次认证前计时，包含失败和等待；首个非空工具块也是新输出。若始终没有新输出，就没有首块样本。

取舍：适配器必须区分事件内容并保留同一次推理的起点；多做这层归一化，才能比较等待时长。发出耗时样本不需要上传片段正文。

【成本】计费用量 × 对应单价；未知不是零，已知成本和缺数分别监控。

总结

  • Traces / Metrics / Logs各有分工：把观测到的 LLM / 工具 span 串成树定位单次问题，用指标看趋势，用日志补事件。
  • 固定 OTel GenAI v0.1.0（Development）：span 属性描述调用，metric 独立记录可聚合样本；接入和升级都要验收字段、单位及后端映射。
  • 默认记模型、已知用量、耗时、工具名和错误类型；首输出块不一定是首 Token，原始输入输出及工具参数、结果默认不采集。
  • 账本按计费用量和对应单价算估算费用；缺量或缺价仍是未知。已知成本和数据缺口分别告警。
