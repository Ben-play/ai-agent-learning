LLM 可观测性

用 OpenTelemetry GenAI 标准，看清 Agent 每一步花了多少、慢在哪、错在哪

💡 为什么这课重要？

一个 Agent 上线后，本质是个黑盒：它调了哪些模型、走了哪些工具、烧了多少 Token 和钱、哪一步慢、哪一步失败——如果你"看不见"，就既没法调优、也没法排障。用户说"它变慢了、变贵了、答错了"，你连从哪查起都不知道。

这一课教你给 Agent 装上"仪表盘"。关键不是随便挑个工具，而是用 OpenTelemetry 的 GenAI 语义约定这套厂商无关的标准字段来记录——这样换监控工具、换模型厂商，你的可观测代码都不用重写。这是 2026 年生产级 Agent 的事实标准。

学习目标

完成本课后，你将能够：

  • 说清可观测性三大支柱：Traces / Metrics / Logs，以及为什么 Agent 最看重 trace
  • 列出 LLM 调用该追踪什么：模型、Token、延迟（TTFT）、成本、工具调用、错误
  • 说出 OpenTelemetry GenAI 语义约定的标准字段（gen_ai.*）并解释它为什么是厂商无关的答案
  • 知道 Langfuse / OpenLLMetry 等工具怎么"一行接入自动追踪"
  • 基于 metrics 设成本告警，把可观测性接回 L23 的成本工程

1. 为什么 Agent 必须"能被看见"

普通函数错了，你看堆栈就行。但 Agent 不是普通函数——它是一串自主的、多步的、带随机性的决策：想一步、调个工具、再想一步、再调个模型……问题恰恰藏在"哪一步"里：

  • 为什么慢？是某次 LLM 生成太长，还是某个工具（如搜索、DB）卡住了？
  • 为什么贵？是上下文越滚越大（L23），还是某条链路反复重试？
  • 为什么错？是模型幻觉，还是工具返回了脏数据、参数拼错了？

不可观测，这些问题全靠猜。生产 Agent 必须能"看见"自己的每一步——可观测性不是锦上添花，是 Agent 从 demo 走向线上的准入门槛。

2. 三大支柱：Traces / Metrics / Logs

可观测性（Observability）是一套通用工程概念，由三根支柱组成：

  • Traces（链路追踪）：一次请求完整的调用链。链里的每个操作是一个 span（跨度），span 之间有父子关系，串成一棵树。
  • Metrics（指标）：可聚合的数字——Token 用量、延迟、错误率、成本，用来画趋势图、设告警。
  • Logs（日志）：离散的文本事件，记录"某刻发生了什么"，用于事后翻查细节。

对 LLM / Agent 来说，最关键的是 trace。因为一次 Agent 任务里，每一次 LLM 调用、每一次工具调用都是一个 span，它们串成的树，正好还原了 Agent"想了什么、做了什么、顺序如何"。看懂这棵树，等于看懂了 Agent 的这次思考。

Trace: "帮我订下周去上海的机票"        （root span，整个任务）
├─ span  LLM 调用①  规划要做几步        model=..., 输入/输出 Token, 延迟
├─ span  工具调用   search_flights(...)  参数, 返回, 耗时
├─ span  LLM 调用②  从结果里选航班       Token, 延迟, 成本
└─ span  工具调用   book(...)            参数, 返回 / 报错
Q 三大支柱里，为什么 Agent 最看重 trace？
Agent 是多步、自主的，问题藏在"哪一步"。trace 把一次任务里每次 LLM 调用、每次工具调用都记成一个 span，串成父子树，正好还原了 Agent 的执行顺序与每步耗时/成本——这才是排障的关键视图。Metrics（Token/延迟/成本/错误率）和 Logs 同样有用、缺一不可，只是 trace 最贴合 Agent 这种链式结构。

3. 该追踪什么（LLM 特有的信号）

通用 trace 只会记"调了个函数、耗时多少"。但 LLM 调用有一堆专属信号，不记下来就等于没记。一次 LLM span 至少要有：

  • 模型名：这次到底用了哪个型号（路由后可能每次不同，见 L32）。
  • 输入 / 输出 Token 数：直接决定成本，对应 L23 的账单公式。
  • 延迟：尤其是 TTFT（首 Token 时间，见 L26）——流式体验的核心指标。
  • 成本：由 Token × 单价算出，是告警与预算的基础。
  • prompt / completion 内容：出问题时要能回看"到底喂了什么、模型答了什么"。
  • 工具调用：调了哪个工具、参数是什么、返回了什么。
  • 错误：超时、限流、解析失败……（L31 说过：错误也要可观测）。

记住一句话：凡是会影响"慢 / 贵 / 错"的信号，都要进 span。下一节的问题是——这些字段该叫什么名字。

4. OpenTelemetry GenAI 语义约定（本课重点）

上一节列了该记的信号。但如果每个团队、每个工具都各造一套字段名——A 家叫 model、B 家叫 model_name、C 家叫 llm.model——那你换一次工具，仪表盘、告警、查询全得重写。这正是标准要解决的问题。

答案是 OpenTelemetry 的 GenAI 语义约定（Semantic Conventions for GenAI）。OpenTelemetry（OTel）本身是 CNCF 的可观测性开放标准；它的 GenAI semantic conventions 专门为 LLM/Agent 定义了一套厂商无关的标准 span 属性名：

gen_ai.operation.name          # 操作类型，如 chat / embeddings
gen_ai.provider.name           # 厂商，如 openai / anthropic
gen_ai.request.model           # 请求的模型名
gen_ai.usage.input_tokens      # 输入 Token 数  ← 成本
gen_ai.usage.output_tokens     # 输出 Token 数  ← 成本
gen_ai.response.time_to_first_chunk   # 首 Token 时间（TTFT）
gen_ai.tool.name               # 工具调用：工具名（在"执行工具"这类 span 上）
# 注：工具调用的参数/结果不是顶层 span 属性，而是放在 gen_ai.input/output.messages 的消息部件里
error.type                     # 出错类型（复用通用约定）

它正在成为厂商无关的通用标准：OTel 的 GenAI 语义约定持续演进中（仍标记为 Experimental，属性名以官方最新版为准），Langfuse、OpenLLMetry 等已按它接入。方向明确——别自造字段，向标准靠。

为什么这是"厂商无关的答案"？因为字段名由中立标准定义，不属于任何一家监控厂商。你按 gen_ai.* 记录，换 Langfuse、换 Datadog、换自建后端，甚至换模型厂商，可观测代码都不用重写——这就是不被单一厂商绑定（vendor lock-in）的关键。

面试高频：「LLM 应用怎么做可观测性？」 标准答法：用 Trace（把每次 LLM/工具调用记成 span，串成调用树）+ Metrics（Token / 延迟 / 成本 / 错误率）+ Logs；字段用 OpenTelemetry GenAI 语义约定（gen_ai.*）这套厂商无关标准，配 Langfuse 等工具落地；再基于成本 metrics 设告警。一句话点出 OTel GenAI 是厂商无关的标准，基本就答到点子上了。
Q 为什么用 OpenTelemetry GenAI 的 gen_ai.* 标准字段，而不是自定义字段名？
OTel GenAI 语义约定由中立的 CNCF 标准定义了厂商无关的字段名（gen_ai.request.model、gen_ai.usage.input_tokens 等）。按它记录，换监控工具、换模型厂商，仪表盘/告警/查询都不用重写，避免被单一厂商绑定。它不会让模型更快、也不省 Token——它省的是你的迁移与维护成本。自定义字段并非"不被支持"，只是各家不互通、迁移即返工。

5. 工具生态：怎么落地

标准解决"记成什么"，工具解决"怎么记、在哪看"。主流选择：

  • Langfuse：开源的 LLM 可观测平台，原生支持 OpenTelemetry——可作为 OTLP 后端接收 gen_ai.* span，直接给你调用树、Token、成本、延迟看板。
  • OpenLLMetry（Traceloop）：一组基于 OTel 的自动埋点库，一行 init 就能自动追踪 LangChain / OpenAI 等框架，把调用变成标准 span。
  • 各类 APM（Datadog / Grafana 等）：只要它们吃 OTLP，你的 gen_ai.* 数据就能直接进去。

典型体验是"一行接入、自动追踪"——你几乎不改业务代码，埋点库就把每次 LLM/工具调用自动记成标准 span：

# 概念示意：自动埋点 + 送到支持 OTel 的后端（如 Langfuse）
from traceloop.sdk import Traceloop
Traceloop.init()                     # 一行初始化，之后自动追踪

# 你原来的 LangChain / OpenAI 代码照常写，
# 每次调用会被自动记成 gen_ai.* span，送到 OTLP 后端

因为大家都遵循 OTel，埋点库和后端可以自由组合：用 OpenLLMetry 埋点、送进 Langfuse 看，或换成任何吃 OTLP 的 APM——这正是标准带来的自由。（具体价格/额度以官网为准，不同方案差异大。）

6. 成本告警：把可观测性变成行动

光看板还不够——你不会一直盯着屏幕。可观测性真正闭环的一步是告警：基于 metrics 设阈值，越线就自动通知你。

  • 成本：日成本超过 X 元报警——防止一个失控循环把预算烧穿（呼应 L23 的成本工程）。
  • 错误率：5xx / 解析失败比例突增就报警（呼应 L31）。
  • 延迟：P95 延迟或 TTFT 恶化就报警，用户抱怨之前先发现。

因为 Token、成本、延迟这些都已按 gen_ai.* 标准记成了 metrics，设告警只是在后端加个规则，不用再改埋点。标准记录 → 聚合成指标 → 阈值告警，这条链一旦通了，Agent 的"贵 / 慢 / 错"就能在出事前或第一时间被你抓住。

Q "日成本超过阈值就自动报警"主要靠哪根支柱？
成本、Token、延迟这类可聚合数字属于 Metrics，天然适合设阈值告警（超 X 就通知）。因为已按 gen_ai.usage.* 等标准记录，加告警只是在后端配规则、不用改埋点。Trace 用于事后定位是哪一步贵/慢，Logs 用于翻查细节，都不是"自动越线报警"的主力；模型本身也不会主动上报你的账单。

7. 动手练习：为一次 Agent 任务设计 span 属性

假设你的 Agent 要完成"查一下明天北京的天气，然后写一句出行建议"。它会：调用一次 LLM 规划 → 调用 get_weather 工具 → 再调用一次 LLM 生成建议。

请你写出：这次任务的 trace 里应该有哪些 span？每个 span 该记录哪些属性？并说明——为什么用 OTel 的标准字段（gen_ai.*）而不是自己起名（如 my_model、tokens_in）？ 想清楚再展开看参考。

点开看参考答案

span 结构（一棵树）：

root span: "明天北京天气 + 出行建议"     整个任务

├─ LLM 调用①（规划）
│    gen_ai.operation.name      = "chat"
│    gen_ai.provider.name       = "openai"
│    gen_ai.request.model       = "gpt-...(具体型号)"
│    gen_ai.usage.input_tokens  = 输入 Token 数
│    gen_ai.usage.output_tokens = 输出 Token 数
│    gen_ai.response.time_to_first_chunk = TTFT
│
├─ 工具调用 get_weather
│    gen_ai.tool.name = "get_weather"   # 参数/结果在消息部件里，非顶层属性
│    （工具返回、耗时、error.type 若失败）
│
└─ LLM 调用②（生成建议）
     gen_ai.request.model / usage.* / TTFT ...（同上）

为什么用标准字段而不是自定义？

  • 不被绑定：字段名由中立的 OTel 标准定义，不属于任何监控厂商。换 Langfuse / Datadog / 自建后端，或换模型厂商，看板、告警、查询都不用重写。
  • 工具即插即用：OpenLLMetry 等埋点库本来就发 gen_ai.*，Langfuse 等后端本来就认它——自定义名字反而要写胶水去映射。
  • 可跨系统聚合：多个服务、多个团队都用同一套名，指标才能拼在一起统一看；各起各的名，数据永远对不齐。
  • 一句话：自定义字段"现在能用、以后返工"；标准字段"一次记好、随处能读"。

总结

  • Agent 是黑盒——不可观测就没法调优和排障，可观测是生产准入门槛
  • 三大支柱 Traces / Metrics / Logs；Agent 最看重 trace：每次 LLM/工具调用是一个 span，串成树
  • LLM 要追踪：模型 · Token · 延迟(TTFT) · 成本 · 内容 · 工具调用 · 错误
  • 字段用 OpenTelemetry GenAI 语义约定（gen_ai.request.model / gen_ai.usage.input_tokens …）——厂商无关，换工具换厂商不用重写（约定仍在演进，以官方最新版为准）
  • 落地用 Langfuse（开源, 原生 OTel）/ OpenLLMetry，一行接入自动追踪
  • 基于 metrics 设成本告警，让可观测性形成闭环
没有可观测性，Agent 上线即失控——你不知道它为什么慢、为什么贵、为什么错。而 OTel GenAI 语义约定，正是让"看见 Agent"这件事标准化、且不被单一厂商绑定的关键一步。下一课 L34：设计好 Tool Schema——工具调用既是 Agent 的手，也是 trace 里最该看清的一环。有疑问随时问我。
