第六阶段 · LangGraph 与 MCP30分钟

LangGraph 中断、持久恢复与重放

恢复的是下一步，不是执行权限

为什么这课重要？

L55 的图从起点一路跑到终点。真实草稿会等人批准，等待期间进程可能退出；获准写入后也可能在返回前失败。两种情况下都要恢复原来的任务，却不能把「恢复」理解成重新生成草稿或照旧再写一条。

学习目标

用状态快照找到待办节点，区分中断恢复与故障重放，并为两者写出相反的业务写入断言。

1. 先弄清三份记录各证明什么

给图编译时传一个 SqliteSaver，用宿主选定的 thread_id 查同一条执行历史。线程标识是定位键，不是身份令牌。get_state 返回的 values 是已持久化的图状态，next 是待执行节点名，不说明为何停住；中断或异常的信息看 tasks。本课由测试驱动显式选择 resume 或 recover，宿主只用 next 检查命令是否匹配当前阶段。新进程用同一库文件和线程标识读取进度；内存 saver 不跨进程保留这些记录。

本课的三个 SQLite 文件用来回答什么不能代替什么
graph.sqlite图还待执行什么？状态保留修订版、内容摘要、编排状态和业务操作 ID；中断值只有任务名和修订版。不证明这个人批准了，也不证明一次业务提交。
reviews.sqlite可信测试驱动记录的决定是否对应当前身份、任务、动作与快照？不能替业务库证明草稿已保存；不是生产认证。
business.sqlite业务检查点保留原始标题、正文和来源 ID。保存后，草稿行也保留这些字段及原操作 ID。不能推断图已把哪个节点标为完成。

宿主展示的原始预览和返回的完整草稿都不写入图检查点。不要把 Command(resume="approve")、用户话术或客户端自报的身份直接传给保存入口充当批准；本课只从可信的合成决定库取决定。

2. 带着第 2 版工单走一次暂停和恢复

review 先核对业务检查点的绑定，再用任务名和修订版调用 interrupt。默认调用形式把中断对象放在 __interrupt__；宿主另查匹配的业务检查点来展示预览，不保持数据库事务等待人。旧进程退出后，新进程用同一线程读到 next=("review",)，并独立读回原标题、正文、来源 ID 和修订版。绑定不符时不拿新版冒充原预览。

无匹配决定不恢复；有匹配决定时，宿主用 Command(resume="review_recorded") 发送唤醒信号，不传批准。节点从头再跑，这次 interrupt 返回该信号。中断前只核对检查点，不插入草稿。进入 apply_review 才重新读取决定并调用 Phase 5 的保存口。

若业务事务已提交但节点尚未返回，业务库已有草稿，图却仍待 apply_review。这里不用审批 Command。在单写者演练中先读该线程的当前快照，再用 invoke(None, snapshot.config, durability="sync") 固定这份快照并重跑待执行节点；业务保存口应取原回执和原稿，不再插入。

snapshot.config 可带 checkpoint_id，指定的是一个停点，不是「执行时的最新线程」。本例没有在读取与推进之间另起写者，因此重放的是刚读到的停止点；不能把较早快照用于生产续跑。L85 对照只传 thread_id 的最新续跑：旧 ID 用来读历史，不用来推进。两者都不以线程 ID 代替审批或业务去重。

3. 区分安全重跑与已经提交的效果

从第 2 版的内容摘要和作用域得到同一业务操作身份。Phase 5 在一个业务事务里写草稿与可核对结果，后来者读原记录，不再发起插入。图的 durability="sync" 约束图先持久化步骤再推进，不会把两个数据库自动变成一个事务。如果确认不了业务回执，停下来核对，不因为图还 pending 就生成新的操作标识。外部服务超时和真正的进程强杀是若干不同故障，不由本地异常替身替代。

最佳实践：中断前只读，写入边界仍要可重放

适用：任务经人工决定后会保存一份可恢复草稿。不适用：无副作用的短任务不必为每一步增加持久化；远端操作不能沿用同库事务的结论。

误判：从上次行号继续

在 interrupt 前先写一条业务行，以为恢复不会再次经过它。

对照：暂停和提交分开

同样暂停后重进，节点只重读预览。获准再进入保存，丢响应也用原操作读回结果。

取舍：业务去重与图持久化要维护两种记录，但可以解释「任务没结束，效果已发生」。并发撤权若是产品要求，还需专门设计一致性边界，不由本课的顺序夹具保证。

  1. 分别观察图快照、决策、插入入口与独立查询。
  2. 先加无有效批准的负例，再注入提交后故障，最后查原 ID、正文和行数。

零行不等于零次尝试；相同返回也不等于同一个操作。若重放反而新增写入，查保存口是否沿用了旧绑定，而不是调整图进度来遮掉问题。

Q 图仍待保存，独立查询发现绑定相同的操作已提交。该怎么做？
图状态只说明该节点尚未报告完成；业务库的原回执才说明是否已写入。

新解释器读取同一线程，第 2 版待审；唯一审批属于第 1 版。

本课最佳实践验收：图的运行次数不是出库次数

迁移到良品托盘标签。同一托盘同一次打标签可在保存后丢响应，节点会被重新调用。先写独立的判定：最多允许一次实际插入；两次执行后仍是同一个标签编号。再做错版，只修改一次条件：重放时改用新的业务操作键。

独立起点：先填恢复调用的键

初次：托盘 A，业务键 pallet-A/v1，已提交标签 1，响应丢失。
重放的业务键 ___ → 预期标签 ___，累计插入次数 ___。
反例键 pallet-A/v1/attempt-2 → 预期标签 ___，累计插入次数 ___。

通过标准：相同业务键返回原标签，入口不再增加；反例必须在存储或入口观察上失败，不能只比较两次调用是否都有回复。

展开变式参考（持久效果，用标准库对照）
from contextlib import closing
from pathlib import Path
import sqlite3
from tempfile import TemporaryDirectory


def label(path, operation, attempted):
    with closing(sqlite3.connect(path)) as db, db:
        db.execute("CREATE TABLE IF NOT EXISTS labels(id INTEGER PRIMARY KEY, op TEXT UNIQUE)")
        old = db.execute("SELECT id FROM labels WHERE op=?", (operation,)).fetchone()
        if old:
            return old[0]
        attempted.append(operation)
        return db.execute("INSERT INTO labels(op) VALUES (?)", (operation,)).lastrowid


with TemporaryDirectory() as tmp:
    for suffix in ("stable", "changed"):
        path = Path(tmp) / suffix
        attempted = []
        first = label(path, "pallet-A/v1", attempted)
        key = "pallet-A/v1" if suffix == "stable" else "pallet-A/v1/attempt-2"
        recovered = label(path, key, attempted)
        with closing(sqlite3.connect(path)) as db:
            rows = db.execute("SELECT id, op FROM labels ORDER BY id").fetchall()
        accepted = first == recovered and rows == [(1, "pallet-A/v1")] and attempted == ["pallet-A/v1"]
        assert accepted == (suffix == "stable"), (recovered, rows, attempted)
        if suffix == "changed":
            assert rows == [(1, "pallet-A/v1"), (2, key)] and len(attempted) == 2
print("L56 TRANSFER PASSED")

面试自查

先按「结论 → 理由 → 如何验证」作答，再展开追问。

Q1新进程用原 thread_id 查到第 2 版待审，能否当作批准开始写？

参考回答：不能。标识定位状态，不赋予身份或权限；用可信决定按身份、动作、任务和修订快照核对。无匹配决定时，精确检查草稿不变，插入计数为零。

追问：同一个人在旧版本批准过，能换一个唤醒字符串跳过吗？

答题要点：不能；字符串不传递批准。应以第 2 版的正确绑定做单变量对照。

Q2把保存草稿放在 interrupt 上方会有什么后果？怎么证实？

参考回答：暂停前就触及写入，恢复从节点开头再运行。用空业务库在首次暂停就断言零尝试，再检测恢复。不要把去重当审批的替代。

追问：若同一段只读了不变的预览呢？

答题要点：可重读但要核对原修订版，不能恢复成新预览；如内容变了，应拒绝旧绑定。

Q3异常后图还在 apply_review，要不要再发 Command(resume=...)？

参考回答：不是人工中断，按待执行快照重跑失败步骤。先确认异常在提交前还是提交后；若已提交，通过业务回执取回原结果。测试让响应在提交后丢失，再比 ID 和插入计数。

追问：增加同步图持久化就能保证外部写入一次吗？

答题要点：不能。图提交点不控制外部事务；外部效果未知要查权威结果。

Q4从同一进程关连接再开已经通过，如何避免把它误报成换进程恢复？

参考回答：先让旧解释器结束，再启动新解释器；只给同一临时库和任务定位条件，不传原正文或决定。用两边的持久状态和业务查询作证。

追问：这能替代强杀和多工作者测试吗？

答题要点：不能。正常退出重启、特定故障点、任意时刻强杀、并发抢占是不同验收条件，应分开记录。
