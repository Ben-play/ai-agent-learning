异常处理、日志与上下文管理器

Agent 会失败 — 优雅地处理错误、记录日志、管理资源，是生产级的分水岭

💡 为什么这课重要？

Agent 天生脆弱：LLM API 会超时、返回会格式错误、工具会抛异常、网络会抖动。怎么处理失败，是"能跑的 demo"和"能上线的系统"的分水岭。

三件生产级基本功：异常处理（分类捕获、别吞错）、logging（结构化日志，而非 print 调试）、上下文管理器（保证进入/退出和清理机会）。超时该交给客户端超时参数/asyncio.wait_for，重试该交给 tenacity/SDK 自带的重试机制——上下文管理器本身不自动做超时或重试。从第一天就养成，后面每一课都受益。

学习目标

完成本课后，你将能够：

  • 用 try/except/else/finally 精准处理错误
  • 定义自定义异常，用 raise ... from 保留异常链
  • 用 logging 记录结构化日志
  • 写上下文管理器（with）保证进入/退出与清理执行
  • 知道超时、重试不是上下文管理器的职责，而是客户端/wait_for/tenacity 的职责
  • 用 tenacity 只对临时性异常重试，理解 stop_after_attempt 与 reraise 的语义

1. try / except / else / finally

try:
    result = call_llm(prompt)
except TimeoutError:
    result = None            # 针对性处理某类错误
except (ConnectionError, OSError) as e:
    result = None            # 一次处理多种错误
else:
    log_success(result)      # 没抛错才执行
finally:
    cleanup()                # 无论如何都执行（关连接、释放资源）
  • 按类型分开 except：超时、限流、格式错误各自处理，别用一个 except Exception 全吞
  • else：try 没抛错时才走
  • finally：一定执行，用于清理
💡 面试常见问题：

"为什么不推荐裸 except: 或 except Exception: pass？"

答：会"吞掉"所有错误（包括你没预料的 bug），让问题被掩盖、极难排查。应捕获具体异常类型并至少记录日志。

2. 自定义异常与异常链

给 Agent 定义清晰的异常类型，出错时能精准分类；用 raise ... from 保留"原始原因"：

class AgentError(Exception):
    """所有 Agent 异常的基类"""

class ToolError(AgentError):
    """工具执行失败"""

def run_tool(args):
    try:
        return int(args["value"])
    except ValueError as e:
        raise ToolError("参数解析失败") from e   # 保留底层原因

# 捕获时能拿到原始异常
try:
    run_tool({"value": "abc"})
except ToolError as e:
    print(e)              # 参数解析失败
    print(e.__cause__)    # invalid literal for int()...  ← 原始 ValueError

from e 让 traceback 同时显示"表层错误"和"根本原因"，排查时一目了然。

Q raise ToolError("x") from e 里的 from e 作用是？
from e 建立异常链：新异常的 __cause__ 指向原始异常，traceback 会显示"由……引起"。这样既能对外抛出语义清晰的自定义异常，又不丢失底层根因，排查快得多。

3. logging：别再用 print 调试

import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(name)s: %(message)s",
)
logger = logging.getLogger("agent")

logger.debug("详细调试信息")        # 开发时看
logger.info("工具 search 调用成功")  # 正常事件
logger.warning("重试第 2 次")        # 需要注意

try:
    result = call_llm(prompt)
except TimeoutError:
    logger.exception("LLM 调用失败")  # 只在 except 块里用，自动带 traceback

为什么不用 print：logging 能分级（生产只输出 INFO 以上）、能带时间/模块名、能输出到文件/收集系统、能关掉。print 全靠手删，且没有结构。

⚠️ logger.exception 只能在真实 except 块里用：

logger.exception(msg) 等价于 logger.error(msg, exc_info=True)——它靠 sys.exc_info() 拿"当前正在处理的异常"来打印 traceback。如果在没有活动异常的地方调用（比如 except 块外，或异常已经处理完），exc_info=True 拿不到异常对象，只会打出 NoneType: None，看起来像日志失败了。牢记：exception 属于 except，不属于别处。

🔑 Agent 开发关联：

这是 Agent 可观测性的第一层（Phase 8 会上 LangSmith/Langfuse 做全链路追踪，但根基是结构化日志）。调试一个"异步 + 多工具"的 Agent，靠 print 根本理不清；分级日志 + 时间戳才能还原发生了什么。

4. 上下文管理器：保证清理

with 背后是 __enter__ / __exit__。你也能自己写，用来保证成对操作（开→关、进→出、计时开始→结束）：

from contextlib import contextmanager
import time

@contextmanager
def timed(label):
    start = time.perf_counter()
    print(f"[{label}] 开始")
    try:
        yield                        # yield 之前 = __enter__，之后 = __exit__
    finally:
        dur = time.perf_counter() - start
        print(f"[{label}] 结束，耗时 {dur:.3f}s")   # 保证执行

with timed("llm-call"):
    do_work()
# [llm-call] 开始
# [llm-call] 结束，耗时 0.052s

用 @contextmanager + yield 是写上下文管理器最简单的方式：yield 前是进入逻辑，finally 里是退出清理（无论是否异常都执行）。

📎 关于 @name 这一行：

本课的 @contextmanager、下一节的 @retry 都是装饰器：写在函数定义上方的 @xxx，会在函数定义完成后把这个函数交给 xxx 处理、返回一个新对象。这里先直接把它们当"标准组件"使用即可，不需要弄懂内部机制——装饰器是怎么写、怎么工作的，L11 会系统讲。

Q @contextmanager 函数里，yield 之后的代码相当于？
用 @contextmanager 时，yield 之前的代码是进入（__enter__），之后的是退出清理（__exit__）。放在 finally 里能保证即使 with 块内抛异常也执行清理。

5. 重试：用 tenacity，只重试临时性异常

LLM API 会因限流/网络临时失败，需要指数退避重试；但参数错误（400）、鉴权失败（401）这类确定性错误重试也没用，只会浪费时间和配额。原理你要懂，工程上别手写——用 tenacity：

# 安装：uv add tenacity  或  pip install tenacity

from tenacity import retry, stop_after_attempt, wait_exponential, retry_if_exception_type

class TemporaryAPIError(Exception):
    """网络抖动/限流等临时性错误，值得重试"""

class InvalidRequestError(Exception):
    """参数错误、鉴权失败等确定性错误，重试没用"""

@retry(
    retry=retry_if_exception_type(TemporaryAPIError),  # 只对临时异常重试
    stop=stop_after_attempt(3),                          # 总共最多尝试 3 次
    wait=wait_exponential(multiplier=1, min=1, max=10),  # 等 1s、2s...
    reraise=True,                                        # 耗尽重试后抛出最后一次的原始异常
)
def call_llm(prompt):
    return api.chat(prompt)

retry_if_exception_type(TemporaryAPIError)：只有抛出 TemporaryAPIError 才会重试；抛 InvalidRequestError 会立刻向上传播，只调用一次，不重试——避免对"注定失败"的请求做无意义重试。

stop_after_attempt(3)：语义是总共尝试 3 次（第 1 次 + 最多 2 次重试），不是"重试 3 次"；两次重试之间按 wait_exponential 退避等待。

reraise=True：3 次都失败后，直接抛出最后一次调用的原始异常（这里是 TemporaryAPIError）；不设为 True 的话，tenacity 默认会包一层 RetryError，掩盖原始异常类型，排查更麻烦。

知识图谱

异常处理
├── try/except(按类型)/else/finally
├── 别裸 except、别 except: pass（吞错）
└── 自定义异常 + raise ... from e（保留异常链 __cause__）

logging（可观测性第一层）
├── 分级 debug/info/warning/error
├── 带时间/模块名/堆栈(exc_info=True)
└── 优于 print：可分级/可关/可收集

上下文管理器 with
├── __enter__ / __exit__
├── @contextmanager + yield（前=进，后=清理）
├── 只负责进入/退出与清理机会，不自动做超时/重试
└── 保证清理/计时/关闭

logger.exception 只能用在真实 except 块里（靠当前异常上下文）

重试 → tenacity（超时用客户端/wait_for，重试用 tenacity，职责分开）
├── retry_if_exception_type：只对临时异常重试
├── stop_after_attempt(n)：总尝试 n 次
└── reraise=True：耗尽后抛最后一次原始异常

实战练习

练习：实现一个 API 调用上下文管理器

写一个上下文管理器，自动为 LLM API 调用计时、记日志、保证清理。先自己写，再看答案。

任务清单

  1. 用 @contextmanager 写 api_call(name)
  2. 进入时 logger.info 记录"开始调用 {name}"
  3. 退出时（finally）记录耗时；出错时 logger.error 记录并重新抛出
  4. 自定义异常 APIError，把底层异常用 from 链起来
  5. （选做）叠加 tenacity 的 @retry 做 3 次指数退避
💡 点击查看参考答案 
import time, logging
from contextlib import contextmanager

logging.basicConfig(level=logging.INFO,
                    format="%(levelname)s %(name)s: %(message)s")
logger = logging.getLogger("agent")

class APIError(Exception):
    """LLM API 调用失败"""

@contextmanager
def api_call(name):
    start = time.perf_counter()
    logger.info(f"开始调用 {name}")
    try:
        yield
    except Exception as e:
        logger.error(f"{name} 调用失败: {e!r}")
        raise APIError(f"{name} 失败") from e    # 保留原因
    finally:
        dur = time.perf_counter() - start
        logger.info(f"{name} 结束，耗时 {dur:.3f}s")   # 一定执行

# 正常
with api_call("chat"):
    time.sleep(0.01)

# 出错
try:
    with api_call("embed"):
        raise ConnectionError("timeout")
except APIError as e:
    print("捕获:", e, "| 根因:", e.__cause__)

思考题

先自己想，再点开对答案。

Q1为什么在 except 里 logger.error 后还要 raise？

因为"记录 ≠ 处理"。logger.error 只是把错误留了个痕，并没有真正解决它；不 raise 重抛，异常就被这个 except 吞掉了。

异常一旦被 except 捕获又不重抛，控制流就会正常离开 try 块继续往下走，函数最终可能返回 None 或半成品结果。调用方收不到任何异常信号，会误以为调用成功了——这就是最危险的"静默错误"：日志里明明记了错，程序却装作没事，问题被掩盖到很后面才爆发。

正确的原则是：要么在这一层彻底处理（有兜底方案、能恢复），要么记录后重抛，把决定权交给更了解业务的上层。这里的上下文管理器选择记录 + raise APIError(...) from e，既留了痕、又保留了根因异常链，还让调用方能明确知道"这次失败了"。

Q2耗时统计放在 finally 而不是 else，为什么？

因为耗时无论成功还是失败都要统计，而 finally 一定执行、else 只在没抛异常时才执行。

else 分支只有当 try 块没有抛出任何异常时才会走；一旦调用出错（超时、连接失败），控制流转到 except，else 直接被跳过——那次失败调用的耗时就统计不到了。可失败调用往往正是我们最想知道耗时的场景（比如超时到底卡了多久）。

finally 则保证"无论 try 正常结束、抛异常、还是在 except 里被重抛"，收尾代码都会执行。把 time.perf_counter() 的差值计算放这里，成功和失败两条路径都能覆盖，耗时日志永远完整。这也是上下文管理器"保证成对操作收尾一定执行"的核心用法。

面试常见问题

Q1：try/except/else/finally 各自什么时候执行？

答：try 放可能出错的代码；except 按类型捕获；else 在 try 没抛错时执行；finally 无论如何都执行（用于清理）。

Q2：为什么不要用 except Exception: pass？

答：它会吞掉所有异常（包括意料外的 bug），让问题被掩盖、无法排查。应捕获具体异常类型并至少记录日志。

Q3：logging 相比 print 有什么优势？

答：可分级（生产只输出 INFO+）、带时间/模块名、可输出到文件或日志系统、可统一开关。print 无结构、需手删，不适合生产。

Q4：上下文管理器（with）解决什么？怎么自己实现？

答：保证"成对操作"的收尾一定执行（关文件/连接、释放锁、计时）。实现方式：类里写 __enter__/__exit__，或用 @contextmanager + yield（前进后清理）。

Q5：LLM API 调用的重试该怎么做？

答：对临时性错误（限流 429、超时）做指数退避重试，且只应重试临时异常（如自定义 TemporaryAPIError），400/401 类确定性错误重试没有意义。工程上用 tenacity（retry_if_exception_type + stop_after_attempt + wait_exponential + reraise=True），别手写。超时用客户端参数/wait_for处理，和重试是两个职责。

总结

  • 按类型 except，别裸 except、别 except Exception: pass 吞错
  • 自定义异常 + raise ... from e 保留根因（__cause__）
  • 用 logging 分级记录，替代 print —— 可观测性的第一层
  • logger.exception 只能写在真实 except 块内，否则拿不到异常上下文
  • 上下文管理器（with / @contextmanager+yield）保证清理一定执行，但不负责超时/重试
  • 记录错误后要重抛，别让调用方误以为成功
  • 重试用 tenacity 只对临时异常做，stop_after_attempt 是总尝试次数，reraise=True 抛原始异常
