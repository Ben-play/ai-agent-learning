异常处理、日志与上下文管理器

Agent 会失败 — 优雅地处理错误、记录日志、管理资源，是生产级的分水岭

💡 为什么这课重要？

Agent 天生脆弱：LLM API 会超时、返回会格式错误、工具会抛异常、网络会抖动。怎么处理失败，是"能跑的 demo"和"能上线的系统"的分水岭。

三件生产级基本功：异常处理（分类捕获、别吞错）、logging（分级、可配置日志，而非 print 调试）、上下文管理器（保证进入/退出和清理机会）。超时该交给客户端超时参数/asyncio.wait_for，重试该交给 tenacity/SDK 自带的重试机制——上下文管理器本身不自动做超时或重试。从第一天就养成，后面每一课都受益。

本课关键决策：能恢复才捕获；能补充业务语义才翻译；只有临时失败才重试。

学习目标

完成本课后，你将能够：

  • 用 try/except/else/finally 精准处理错误
  • 定义自定义异常，用 raise ... from 保留异常链
  • 用 logging 记录分级、可配置日志
  • 写上下文管理器（with）保证进入/退出与清理执行
  • 知道超时、重试不是上下文管理器的职责，而是客户端/wait_for/SDK 重试配置的职责
  • 先配置 SDK max_retries；需要补充策略时再用 tenacity，并理解 stop_after_attempt 与 reraise

1. try / except / else / finally

# 这里的 call_llm 是应用自己的 provider adapter：
# 它已把具体 SDK 异常翻译为这一层约定的内置异常。
try:
    result = call_llm(prompt)
except TimeoutError:
    result = None            # 针对性处理某类错误
except (ConnectionError, OSError) as e:
    result = None            # 一次处理多种错误
else:
    log_success(result)      # 没抛错才执行
finally:
    cleanup()                # 正常离开或异常传播时执行清理
  • 按类型分开 except：超时、限流、格式错误各自处理；except Exception 会捕获大多数应用级异常，只有确实要在边界统一记录并重抛时才使用
  • else：try 没抛错且正常到达末尾时才走
  • finally：离开 try 语句时通常都会执行，包括正常结束、异常、return、break、continue；它不能保证进程被强制终止、解释器崩溃或机器断电时仍运行
💡 面试常见问题：

"为什么不推荐裸 except: 或 except Exception: pass？"

答：裸 except: 连 KeyboardInterrupt、SystemExit 等不继承 Exception 的控制流异常也会捕获；except Exception: pass 范围稍窄，但仍会静默吞掉大多数应用错误和意外 bug。应优先捕获具体异常类型；若在系统边界宽捕获用于记录，也要重新抛出或明确转换。

2. 自定义异常与异常链

给 Agent 定义清晰的异常类型，出错时能精准分类；用 raise ... from 保留"原始原因"：

class AgentError(Exception):
    """所有 Agent 异常的基类"""

class ToolError(AgentError):
    """工具执行失败"""

def run_tool(args):
    try:
        return int(args["value"])
    except ValueError as e:
        raise ToolError("参数解析失败") from e   # 保留底层原因

# 捕获时能拿到原始异常
try:
    run_tool({"value": "abc"})
except ToolError as e:
    print(e)              # 参数解析失败
    print(e.__cause__)    # invalid literal for int()...  ← 原始 ValueError

from e 让 traceback 同时显示"表层错误"和"根本原因"，排查时一目了然。

最佳实践：只翻译能补充业务语义的具体异常

适用：内部契约已保证 value 为 str，而 int(value) 的 ValueError 需要转换成调用方稳定处理的 ToolError。不适用：没有新增业务语义，或 TypeError/KeyError 表示调用方破坏了契约时，应原样传播；公共输入边界则应先显式验证。

❌ 捕获所有 Exception
try:
    return int(value)
except Exception:
    raise ToolError("工具失败")

意料外的编程错误也会被错误包装。

✅ 精准捕获并链接根因
try:
    return int(value)
except ValueError as exc:
    raise ToolError("value 必须是整数") from exc

调用方得到业务语义，排错时仍有 __cause__。

为什么更优：只把已知底层失败映射为稳定的业务异常，并用 raise ... from 链接原始原因，使调用方获得可依赖的错误契约，同时保持可诊断性。代价是必须持续维护异常映射；若底层异常没有新增业务语义就原样传播，而公共输入边界应先显式校验，再把已验证数据交给内部逻辑。

自检：只翻译 ValueError，TypeError 不被包装
class ToolError(Exception):
    pass


def parse_value(value: str):
    """解析内部已保证为 str 的值。"""
    try:
        return int(value)
    except ValueError as exc:
        raise ToolError("value 必须是整数") from exc

assert parse_value("42") == 42
try:
    parse_value("bad")
except ToolError as exc:
    assert str(exc) == "value 必须是整数"
    assert isinstance(exc.__cause__, ValueError)
else:
    raise AssertionError("非法值应抛 ToolError")

# 未声明处理的编程错误不能被包装
try:
    parse_value(None)
except TypeError:
    pass
else:
    raise AssertionError("TypeError 应原样传播")

结果解释：退出码为 0 且断言无失败即通过。若 __cause__ 断言失败，异常翻译丢失了根因；若 None 没触发 TypeError，捕获范围过宽；若合法输入失败，正常路径已被异常策略破坏。

Q raise ToolError("x") from e 里的 from e 作用是？
from e 建立异常链：新异常的 __cause__ 指向原始异常，traceback 会显示"由……引起"。这样既能对外抛出语义清晰的自定义异常，又不丢失底层根因，排查快得多。

3. logging：别再用 print 调试

import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(name)s: %(message)s",
)
logger = logging.getLogger("agent")

logger.debug("详细调试信息")        # 开发时看
logger.info("工具 search 调用成功")  # 正常事件
logger.warning("重试第 2 次")        # 需要注意

# call_llm 是 provider adapter，已把 SDK 的类型化异常翻译为内置超时异常。
try:
    result = call_llm(prompt)
except TimeoutError:
    logger.exception("LLM 调用失败")  # 当前有活动异常，自动带 traceback

为什么不用 print：logging 能分级（生产只输出 INFO 以上）、能带时间/模块名、能输出到文件/收集系统、能关掉。print 全靠手删，且没有结构。

🔒 敏感数据边界：日志不是数据仓库

不要记录 API key/访问令牌等密钥，也不要默认记录完整 prompt、tool arguments 或 model output；它们可能含用户数据、凭据或业务机密。优先记录安全的元数据：请求 ID、模型名、工具名、状态码、耗时、重试次数，以及经过允许列表筛选并脱敏/截断后的字段。结构化日志也要遵守相同边界，并按环境设置访问控制与保留期。

# 不要：logger.info("request", extra={"api_key": key, "prompt": prompt,
#                                      "tool_args": args, "model_output": output})
logger.info(
    "LLM 调用完成",
    extra={"request_id": request_id, "model": model,
           "tool_name": tool_name, "status_code": status_code,
           "duration_ms": duration_ms},
)
⚠️ logger.exception 只在存在当前异常上下文时使用：

logger.exception(msg) 等价于 logger.error(msg, exc_info=True)——它靠 sys.exc_info() 取得当前正在处理的异常。最常见位置是 except 块；由异常处理器同步调用的辅助函数也能读取同一异常上下文。若当前没有活动异常，只会输出 NoneType: None，因此不要把它当普通错误日志使用。

🔑 Agent 开发关联：

这是 Agent 可观测性的第一层（Phase 8 会上 LangSmith/Langfuse 做全链路追踪，但根基是分级、可配置日志）。调试一个"异步 + 多工具"的 Agent，靠 print 根本理不清；分级日志 + 时间戳才能还原发生了什么。

4. 上下文管理器：保证清理

with 背后是 __enter__ / __exit__。你也能自己写，用来保证成对操作（开→关、进→出、计时开始→结束）：

from contextlib import contextmanager
import time

@contextmanager
def timed(label):
    start = time.perf_counter()
    print(f"[{label}] 开始")
    try:
        yield                        # yield 之前 = __enter__，之后 = __exit__
    finally:
        dur = time.perf_counter() - start
        print(f"[{label}] 结束，耗时 {dur:.3f}s")   # 保证执行

with timed("llm-call"):
    do_work()
# [llm-call] 开始
# [llm-call] 结束，耗时 0.052s

前置桥梁：@contextmanager 把一个只 yield 一次的生成器函数适配成上下文管理器；yield 前是进入逻辑，恢复执行后是退出逻辑。把清理放进 finally，即可在 Python 正常控制流离开 with 时执行（包括异常传播）；强制终止、解释器崩溃或断电不在保证范围内。

⚠️ 异常是否继续传播，取决于退出逻辑：

类式上下文管理器的 __exit__(exc_type, exc, tb) 返回真值会表示“异常已处理”，从而吞掉 with 块的异常；返回 False/None 则继续传播。用 @contextmanager 时，yield 处收到块内异常：如果生成器捕获后正常结束而不重新抛出，同样会吞掉异常；若不捕获或显式 raise，异常才继续向上传播。

class SuppressValueError:
    def __enter__(self):
        return self
    def __exit__(self, exc_type, exc, tb):
        return exc_type is ValueError  # 真值只吞 ValueError

with SuppressValueError():
    raise ValueError("handled")
print("continued")
📎 关于 @name 这一行：

本课的 @contextmanager、下一节的 @retry 都是装饰器：写在函数定义上方的 @xxx，会在函数定义完成后把这个函数交给 xxx 处理、返回一个新对象。这里先直接把它们当"标准组件"使用即可，不需要弄懂内部机制——装饰器是怎么写、怎么工作的，L11 会系统讲。

Q @contextmanager 函数里，yield 之后的代码相当于？
用 @contextmanager 时，yield 之前的代码是进入（__enter__），之后的是退出清理（__exit__）。放在 finally 里能保证即使 with 块内抛异常也执行清理。

5. 重试：SDK 优先，Tenacity 补缺口

先看 SDK：官方 Claude SDK 和许多其他服务 SDK 通常已经内置重试。Anthropic Python SDK 当前自动重试连接错误、408、409、429 和 5xx；先配置 SDK 的 max_retries。Tenacity 只用于 SDK 未覆盖的错误或跨步骤工作流，避免在同一层叠加两套重试导致尝试次数与等待时间相乘。

LLM API 会因限流/网络临时失败，需要指数退避重试；但参数错误（400）、鉴权失败（401）这类确定性错误重试也没用，只会浪费时间和配额。官方 Anthropic Python SDK 默认会自动重试连接错误、408、409、429 和 5xx，并可用 max_retries 配置；直接使用 SDK 时应捕获其类型化异常，例如 anthropic.APITimeoutError、anthropic.APIConnectionError、anthropic.RateLimitError 和 anthropic.APIStatusError，而不是假定 SDK 直接抛内置 TimeoutError/ConnectionError。只有需要补充 SDK 未覆盖策略或编排跨步骤重试时，再用 Tenacity 文档：

# 安装：uv add tenacity  或  pip install tenacity

from tenacity import retry, stop_after_attempt, wait_exponential, retry_if_exception_type

class TemporaryAPIError(Exception):
    """网络抖动/限流等临时性错误，值得重试"""

class PermanentAPIError(Exception):
    """参数错误、鉴权失败等确定性错误，重试没用"""

@retry(
    retry=retry_if_exception_type(TemporaryAPIError),  # 只对临时异常重试
    stop=stop_after_attempt(3),                          # 总共最多尝试 3 次
    wait=wait_exponential(multiplier=1, min=1, max=10),  # 等 1s、2s...
    reraise=True,                                        # 耗尽重试后抛出最后一次的原始异常
)
def call_llm(prompt):
    return api.chat(prompt)

retry_if_exception_type(TemporaryAPIError)：只有抛出 TemporaryAPIError 才会重试；抛 PermanentAPIError 会立刻向上传播，只调用一次，不重试——避免对"注定失败"的请求做无意义重试。这里的两个类型属于示例 provider adapter 的稳定应用契约，不是 Anthropic SDK 的异常类。

stop_after_attempt(3)：语义是总共尝试 3 次（第 1 次 + 最多 2 次重试），不是"重试 3 次"；两次重试之间按 wait_exponential 退避等待。

reraise=True：3 次都失败后，直接抛出最后一次调用的原始异常（这里是 TemporaryAPIError）；不设为 True 的话，tenacity 默认会包一层 RetryError，掩盖原始异常类型，排查更麻烦。

知识图谱

异常处理
├── try/except(按类型)/else/finally
├── 裸 except 还会捕获 KeyboardInterrupt/SystemExit；Exception 较窄但也不能静默 pass
└── 自定义异常 + raise ... from e（保留异常链 __cause__）

logging（可观测性第一层）
├── 分级 debug/info/warning/error
├── 带时间/模块名/堆栈(exc_info=True)
└── 优于 print：可分级/可关/可收集

上下文管理器 with
├── __enter__ / __exit__
├── @contextmanager + yield（前=进，后=退出逻辑）
├── __exit__ 返回真值或 contextmanager 不重抛可吞异常
├── 只负责进入/退出与清理机会，不自动做超时/重试
└── 正常控制流离开时保证清理机会，不覆盖强制终止/崩溃/断电

logger.exception 只在存在当前异常上下文时使用（通常位于 except 处理链）

重试 → 先用 SDK max_retries；Tenacity 补 SDK 未覆盖错误或跨步骤工作流
├── 同一层不要叠加两套重试
├── retry_if_exception_type：只对临时异常重试
├── stop_after_attempt(n)：总尝试 n 次
└── reraise=True：耗尽后抛最后一次原始异常

import time, logging
from contextlib import contextmanager

logging.basicConfig(level=logging.INFO,
                    format="%(levelname)s %(name)s: %(message)s")
logger = logging.getLogger("agent")

# 教学前提：api_call 位于 provider adapter 之后；adapter 已把
# anthropic.APITimeoutError/APIConnectionError 映射为下面的内置异常。

class APIError(Exception):
    """LLM API 调用失败"""

@contextmanager
def api_call(name):
    start = time.perf_counter()
    logger.info("开始调用 %s", name)
    try:
        yield
    except (ConnectionError, TimeoutError) as e:
        logger.exception("%s 调用失败", name)
        raise APIError(f"{name} 失败") from e    # 只翻译预期的临时错误
    finally:
        dur = time.perf_counter() - start
        logger.info("%s 结束，耗时 %.3fs", name, dur)   # 正常控制流离开时执行

# 正常
with api_call("chat"):
    time.sleep(0.01)

# 出错
try:
    with api_call("embed"):
        raise ConnectionError("timeout")
except APIError as e:
    print("捕获:", e, "| 根因:", e.__cause__)

思考题

先自己想，再点开对答案。

Q1为什么在 except 里 logger.error 后还要 raise？

因为"记录 ≠ 处理"。logger.error 只是把错误留了个痕，并没有真正解决它；不 raise 重抛，异常就被这个 except 吞掉了。

异常一旦被 except 捕获又不重抛，控制流就会正常离开 try 块继续往下走，函数最终可能返回 None 或半成品结果。调用方收不到任何异常信号，会误以为调用成功了——这就是最危险的"静默错误"：日志里明明记了错，程序却装作没事，问题被掩盖到很后面才爆发。

正确的原则是：要么在这一层彻底处理（有兜底方案、能恢复），要么记录后重抛，把决定权交给更了解业务的上层。这里的上下文管理器选择记录 + raise APIError(...) from e，既留了痕、又保留了根因异常链，还让调用方能明确知道"这次失败了"。

Q2耗时统计放在 finally 而不是 else，为什么？

因为成功和失败两条 Python 控制流都要统计耗时；finally 会在正常离开、异常传播或重抛时执行，而 else 只在没抛异常时执行。

else 分支只有当 try 块没有抛出任何异常时才会走；一旦调用出错（超时、连接失败），控制流转到 except，else 直接被跳过——那次失败调用的耗时就统计不到了。可失败调用往往正是我们最想知道耗时的场景（比如超时到底卡了多久）。

finally 会覆盖 try 正常结束、异常传播以及 except 中重抛等 Python 控制流，因此适合计算成功和失败路径的耗时；强制杀进程、解释器崩溃或断电仍可能让清理来不及执行。这也是上下文管理器管理成对操作时必须说明的边界。

def _load_trusted_config(text: str, *, decoder=json.loads):
    """内部契约：text 已由公共边界验证为 str；decoder seam 仅用于自检。"""
    try:
        return decoder(text)
    except json.JSONDecodeError as exc:
        raise ConfigError("配置不是合法 JSON") from exc

@contextmanager
def tracked(events):
    events.append("enter")
    try:
        yield
    finally:
        events.append("cleanup")

success = []
with tracked(success):
    assert load_config('{"enabled": true}') == {"enabled": True}
assert success == ["enter", "cleanup"]

failure = []
try:
    with tracked(failure):
        load_config('{"enabled": }')
except ConfigError as exc:
    logger.exception("config load failed")
    assert str(exc) == "配置不是合法 JSON"
    assert isinstance(exc.__cause__, json.JSONDecodeError)
else:
    raise AssertionError("非法 JSON 应抛 ConfigError")
assert failure == ["enter", "cleanup"]
logged = log_output.getvalue()
assert "config load failed" in logged
assert "Traceback" in logged
assert "ConfigError" in logged
assert "JSONDecodeError" in logged

# 负向控制：已通过 str 边界后，解析器内部的无关 TypeError 仍须原样传播。
def unrelated_type_error(_text):
    raise TypeError("decoder bug")


type_failure = []
try:
    with tracked(type_failure):
        _load_trusted_config("{}", decoder=unrelated_type_error)
except TypeError as exc:
    assert type(exc) is TypeError
    assert str(exc) == "decoder bug"
    assert exc.__cause__ is None
else:
    raise AssertionError("无关 TypeError 应原样传播")
assert type_failure == ["enter", "cleanup"]

# 公共输入边界也有明确类型契约。
try:
    load_config(None)
except TypeError as exc:
    assert str(exc) == "text 必须是 str"
else:
    raise AssertionError("非 str 公共输入应抛 TypeError")

此块只补充证明：仅 TemporaryAPIError 会重试，reraise=True 保留最后一个原始异常，而永久错误只调用一次。不要把它与上面的标准库主验收或 SDK 自带重试叠在同一层。

from tenacity import retry, retry_if_exception_type, stop_after_attempt

class TemporaryAPIError(Exception):
    pass

class PermanentAPIError(Exception):
    pass

attempts = 0
@retry(
    retry=retry_if_exception_type(TemporaryAPIError),
    stop=stop_after_attempt(3),
    reraise=True,
)
def flaky():
    global attempts
    attempts += 1
    raise TemporaryAPIError("temporary")

try:
    flaky()
except TemporaryAPIError as exc:
    assert str(exc) == "temporary"
else:
    raise AssertionError("耗尽重试后应抛最后一次原始异常")
assert attempts == 3

invalid_attempts = 0
@retry(
    retry=retry_if_exception_type(TemporaryAPIError),
    stop=stop_after_attempt(3),
    reraise=True,
)
def invalid_request():
    global invalid_attempts
    invalid_attempts += 1
    raise PermanentAPIError("invalid")

try:
    invalid_request()
except PermanentAPIError:
    pass
else:
    raise AssertionError("确定性错误应立即传播")
assert invalid_attempts == 1
print("L10 RETRY ACCEPTED")

面试常见问题

Q1：try/except/else/finally 各自什么时候执行？

答：try 放可能出错的代码；except 按类型捕获；else 在 try 没抛错且正常结束时执行；finally 在 Python 控制流离开 try 语句时通常执行，用于清理，但不覆盖强制终止、崩溃或断电。

Q2：为什么不要用 except Exception: pass？

答：except Exception: pass 会静默吞掉大多数应用异常和意外 bug；裸 except: 更宽，连 KeyboardInterrupt/SystemExit 也会接住。应优先捕获具体类型；边界层若宽捕获用于记录，也应重抛或明确转换。

Q3：logging 相比 print 有什么优势？

答：可分级（生产只输出 INFO+）、带时间/模块名、可输出到文件或日志系统、可统一开关。print 无结构、需手删，不适合生产。

Q4：上下文管理器（with）解决什么？怎么自己实现？

答：在 Python 正常控制流离开 with 时保证成对操作有退出/清理机会（正常结束、异常、return 等；不覆盖强制终止、崩溃或断电）。类式实现写 __enter__/__exit__，其中 __exit__ 返回真值可吞异常；@contextmanager 若捕获 yield 处异常后不重抛，也会吞异常。

Q5：LLM API 调用的重试该怎么做？

答：先使用官方 SDK 的重试配置（Claude Python SDK 用 max_retries）；Anthropic Python SDK 当前自动重试连接错误、408、409、429 和 5xx。其他 4xx（如 400/401）通常是确定性错误，不应重试。Tenacity 用于 SDK 未覆盖的错误或跨步骤工作流，不要与 SDK 在同一层重复包裹。超时仍由客户端参数/wait_for负责。

总结

  • 按类型 except；裸 except 会捕获控制流异常，except Exception 较窄但也不能静默 pass
  • 自定义异常 + raise ... from e 保留根因（__cause__）
  • 用 logging 分级记录，替代 print；密钥、完整 prompt、工具参数与模型输出默认不入日志，优先记录脱敏的安全元数据
  • logger.exception 只在存在当前异常上下文时使用；最常见于 except 处理链
  • 上下文管理器在正常控制流离开时保证退出/清理机会，但不覆盖强制终止等边界，也不负责超时/重试
  • __exit__ 返回真值，或 @contextmanager 捕获后不重抛，都会吞掉块内异常
  • 记录错误后要重抛，别让调用方误以为成功
  • 重试先配置 SDK max_retries；Anthropic Python SDK 当前覆盖连接错误、408、409、429 和 5xx；Tenacity 只补未覆盖错误或跨步骤工作流，避免同层叠加
