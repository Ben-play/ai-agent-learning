工具搜索与受限的结果聚合

少展开定义，不少检查权限；找到候选，不冒充交付

为什么这课重要？

同一位客服既可能只查导出留存，也可能查同步或交班值守。把所有目录端上来浪费上下文；只给一个工具能省字节，却完不成后两类任务。工具搜索适合「目录大、每题只用少数」的负载，不替代 L75 的分发权限边界。本节只用固定合成只读业务记录：不写入、不联网，不加载外部工具或执行用户输入。

学习目标

  • 在同一批任务上比较刻意收窄的小工具集、展开全部授权工具和按需加载。
  • 区分候选命中、真实本地读次数、有来源的完整结果，以及目录是否完整发出。
  • 先过滤可发现元数据，在分发边界重验当前主体、scope、严格类型和累计预算。

1. 目录只给线索，宿主决定能不能读

实验可信主体固定为 (support, mei)，有 policy:read 和 desk:read。同一合成目录中，客服可读六个工具：留存、留存术语说明、同步、值守、队列及草稿标签；运维的留存工具虽然同样是只读、同为 mei，也不会进入这位客服的候选或输出。目录中没有写工具，也没有文件路径、命令、脚本、URL 或凭据参数。

课堂形状与独立的检查点
阶段可见示例验收点
元数据名称、说明、limit 输入模式按需查留存时，read_retention 与术语工具同分，稳定排序后只展开前者。不得泄漏同主题的运维名称。

每题上限为两次实际读、两条累计记录；分发前用 limit 预留最坏的返回条数，不靠事后截断来谎称预算合格。比如先取留存两条，再取同步一条，即使还有一次调用额度，也必须拒绝第二次读。若只设每次最多两条，跨工具聚合仍可能超量。本实验预算管本地读次数与结果条数；模型回合、发现次数、时长、输出字节的线上硬上限应另设，不能从这两个值推出。

Q 已发现留存工具，调度前宿主撤销 policy:read。应该怎样处理？
旧目录不是新授权；缩小返回量也不会获得授权。用当前可信状态拦在业务读取之前。

2. 三种目录用一张账本：测整个实际输出

固定 phase9-tools/v1：只查留存、合查留存与同步、只查值守，共需四个正确候选。刻意收窄组只给常用留存工具；全授权组给客服的六个工具，而不是跨租户全库；按需组先给发现入口，用题目主题查找并逐次加载定义。三组共用分发逻辑、读取实现和业务结果金标，目录金标则按策略和题目确定。

宿主明确传入 compare(rows, strategy=...)，评分器不从报告推断策略，也不调用运行时目录或搜索来生成答案。它用独立金标逐题校验目录条目的类型与顺序、完整定义（名称、说明、schema）以及发现说明、主题与候选；候选命中、实际读次数、业务原文和来源另行核对。

上下文大小按实际序列化的 {manifest, results} 计 UTF-8 字节：发现说明、发现结果、展开的定义、来源、返回记录、拒绝终态和 JSON 结构都算。每题一次序列化，整批求和；这不是 Token、线上带宽、缓存或真实模型延迟。本实验用精确主题和排序，不测模型选工具准确率。

同一批三题：小工具集只有窄题足够；字节数越少不代表越合格

合查题的按需目录依次发出空定义列表、发现说明、留存候选与定义、同步候选与定义，另有两份业务结果。即使正文和来源全对，漏发目录条目、截短 schema 或调换目录顺序仍会记入 manifest_errors；实际字节和命中分母照计，但不能入围。

若累计预算压到一条，同步候选仍命中，分发却返回 budget_exhausted；此时按需方案是 4/4 命中、3 次实际读，目录正确但交付不完整。反过来，若业务只做留存，小工具集完整读一次，只用 456 B，低于按需的 677 B。

厂商接口与课堂模拟不是同一件事。以 Claude 的工具搜索为例，defer_loading: true 延后的是进入模型上下文，不是免于在 API 请求中提交已授权工具定义；发现返回引用，服务将其展开。无论在哪一层搜索，发现和参数模式都不赋予业务权限。MCP 的列工具与调用也是分开的操作；本实验不启动 MCP 服务、不验证厂商实现。

决策卡：先缩小业务面，再判断是否值得搜索

适用：同一可信目录支持多类任务，大片定义很少会用，但主动删掉会造成实际任务缺项。

误判：正文对，字节少，就更好

少发目录也会省字节，即使合查结果带着正确的来源。

选择：目录完整、结果有据才入围

选择前过滤、分发时复验；把所有实际输出和本地读计入观察。

  1. 先用够用的小目录做正控，锁定任务族和授权规则。
  2. 需要覆盖长尾时比较全授权与按需；逐题核对实际发出的目录、命中、读取、来源和结果。
  3. 预先定聚合预算；用目录漏发、撤权、非法参数和预算耗尽做负控。

取舍：按需少展开定义，却多一次发现决策与维护成本。若目录很小或大部分工具每题都用，直接展开可能更划算；若业务确实只有留存，单工具方案最简单。

Q 合查题命中两个工具，但累计预算只允许实际读取一条。如果业务需要两条完整来源，该方案算什么？
命中是找到工具，不是读到了结果；把未完成的任务留在分母里。

from dataclasses import replace
import json
import runpy

if not __debug__:
    raise RuntimeError("run without -O")
lab = runpy.run_path("code/phase9-advanced-agent/advanced-lab/tools/main.py")
assert lab["COHORT_VERSION"] == "phase9-tools/v1"
for strategy, hits, reads, size, failures in (
    ("small", 2, 2, 1248, ("policy-and-sync", "duty")),
    ("all-authorized", 4, 4, 4838, ()),
    ("lazy", 4, 4, 2483, ()),
):
    rows = lab["replay"](strategy)
    report = lab["compare"](rows, strategy=strategy)
    assert (report.candidate_hits, report.expected_candidates, report.read_calls) == (hits, 4, reads)
    assert (report.context_bytes, report.ineligible_tasks, report.eligible) == (size, failures, not failures)
    assert not report.manifest_errors
    for row in rows:
        whole = json.loads(row.context)
        assert set(whole) == {"manifest", "results"}
        text = json.dumps(whole, ensure_ascii=False, sort_keys=True, separators=(",", ":"))
        assert row.context == text.encode("utf-8")
        assert b"read_ops_retention" not in row.context
routine, dual, duty = lab["replay"]("lazy")
assert dual.selected == dual.reads == ("read_retention", "read_sync")
assert dual.records[-1] == lab["Record"]("support", "SYNC-POLICY", 1, "§1", "同步任务每天 02:00 运行。")
assert [item["type"] for item in json.loads(dual.context)["manifest"]] == [
    "definitions", "discovery", "discovery_result", "definitions", "discovery_result", "definitions"
]
for change in ("omitted", "truncated", "reordered"):
    payload = json.loads(dual.context)
    manifest = payload["manifest"]
    if change == "omitted":
        del manifest[1]  # 只改目录，不改结果。
    elif change == "truncated":
        del manifest[3]["tools"][0]["input_schema"]["required"]
    else:
        manifest[2], manifest[3] = manifest[3], manifest[2]
    damaged = replace(dual, context=lab["serialize"](payload))
    rows = (routine, damaged, duty)
    report = lab["compare"](rows, strategy="lazy")
    assert (report.candidate_hits, report.expected_candidates, report.read_calls) == (4, 4, 4)
    assert report.context_bytes == sum(len(row.context) for row in rows)
    assert (report.context_bytes < 2483) == (change != "reordered")
    assert report.manifest_errors == report.ineligible_tasks == ("policy-and-sync",)
    assert not report.eligible
print("L81 ACCEPTED")

面试自查

先描述边界和观测点，再说换条件会怎样。

Q1 目录找到了一个正确的工具，却在执行前撤权。能不能读一次再更新列表？

参考回答：不能。当前授权要在业务分发前检查，证明零读。旧目录未即时消失不是许可。

追问（改条件）：若 scope 不变，但登录主体从客服换成同名运维呢？

答题要点：原会话绑定的主体已变化；重建授权上下文和目录，不能复用旧候选执行。

Q2 工具名和参数格式都正确，合查只拿到第一条。先查什么？

参考回答：分别查候选、分发终态和有来源的实际结果；看是否耗尽累计行数或调用额度。

追问（改条件）：单次限制仍为两条，新需求却要合计三条，能把初始限制不变继续多读一次吗？

答题要点：不能绕开总预算。要么从批准的任务参数调整预算并验证，要么报告明确缺项。

Q3 按需组的启动目录很短，但报告没少多少字节，为什么？

参考回答：查完整序列：发现能力说明、搜索返回、延后定义、结果及包裹都占空间。

追问（改条件）：若用厂商的 defer_loading，能直接承诺 HTTP 请求也更小吗？

答题要点：不能；请求传输与模型上下文不同，先按实际接口分别计量。

Q4 小目录组省了一半以上字节，为什么仍不建议在整批上线？

参考回答：它少了同步与值守，省量不是同质交付；先过独立完整性门再省。

追问（改条件）：若新产品只承诺查留存呢？

答题要点：重定任务版本，在同一窄负载比较；同样成功时可以选择小目录。

小结与一手参考

授权决定可发现范围，宿主决定可分发范围；完整性决定能否入围。评分器按宿主选定的策略，用独立金标核对实际目录和业务结果。字节照实计，漏发不算节省；命中不替代真实读和交付。

  • Claude API · Tool search tool：核对 defer_loading、引用展开和模型支持。
  • MCP Tools（课程固定修订）：区分列工具、调用工具、输入验证和访问控制。
