第三阶段 · LLM API 工程实践 45分钟

成本工程：负载驱动的成本决策

先守住质量与延迟，再比较每个成功任务的总成本；不背固定排序，不承诺账单砍半

为什么这课重要？

一个 Agent 的账单不仅由模型单价决定，还受工具往返、无效循环、检索结果量、输出长度、重试和 fallback 影响。一次请求便宜，不等于完成一个任务便宜。如果降低单价却引入更多失败或补救调用，成功任务成本反而可能上升。

L23 提供缓存与路由的基础，本课把它们放回真实负载中判断：先约定成功标准、质量门槛和延迟约束，再测量瓶颈、选择实验、回归验证。缓存、Batch、effort、路由、压缩、蒸馏都只是候选，没有跨业务通用的六层优先级，也没有保证省一半的配方。

学习目标

完成本课后，你将能够：

  • 为同一任务集定义质量门槛、总成本 / 成功任务数、端到端 p95 延迟，计入失败、重试与 fallback
  • 区分前缀缓存的输入复用与语义缓存的答案复用，解释不同问题为何仍可能共享前缀命中
  • 按 provider、model、API、TTL、最小长度、断点及写读价格核对缓存，验证真实 usage 而非猜测命中
  • 按租户、权限、知识版本和时效约束语义缓存，排除动作执行结果的复用
  • 离线运行精确断言，根据负载选择优化实验，并说明哪些结论仍需真实评估

1. 先定义能交付的任务，再谈成本

比较单位是完整任务，不是单次模型响应。例如“查到符合权限的退货政策并给出有效引用”才算成功；返回了 JSON、少调一次工具或没有抛异常，都不自动等于业务成功。先固定任务与难度分布、检查规则、重试上限和资源边界，再比较候选策略。

指标记录方法避免的误判
质量门槛按最终结果验收任务成功率，并单独检查引用、权限、关键字段等硬性要求低质量方案不能仅凭低价入选；总体平均值也不能掩盖关键任务退化
成功任务成本在同一评估窗口中，用全部任务总成本除以成功任务数失败任务花的钱也进分子；零成功时成本未定义，不能报成零
端到端 p95从任务进入到最终成功或失败结束，含排队、工具、重试与 fallback；按约定分位算法统计不能只报模型首 token 延迟，也不能只统计成功的快请求

总成本的边界要写清：所有模型尝试的输入、输出与计费推理 token，缓存写入与读取，embedding、检索、工具和网关等；涉及压缩或蒸馏时，还要计入相应推理、数据、训练、部署和维护的摊销。不要遗漏失败或把同一批 usage 重复计价。

保留每个任务的调用 trace、usage、耗时和最终 outcome；在代表性任务集上做重复试验，区分偶然成功与稳定交付。开发集选方案，独立验收集查退化。先筛掉不达质量 / 延迟门槛的方案，再在合格者中比较成本。若没有合格者，应调整方案或需求，而不是把最低价者上线。

本课离线 fixture 只有四个任务，p95 使用 nearest-rank，此时就是最大耗时。它能验证计算逻辑，不能提供可信的线上尾延迟或真实模型质量估计。

2. 从负载证据选择实验，不按工具名排序

先从 trace 找主要开销，再问哪一种改动能改善它。下表是条件匹配表，不是落地顺序；不同业务可能从完全不同的一行开始。

观察到的瓶颈可测试的改动必须一起验证
重复工具调用、无效规划循环，结果或输出过量终止条件与预算守卫、工具结果分页 / 字段裁剪、检索 top-k、简洁输出契约是否漏掉必需证据或提前终止；减少输出上限也可能造成截断与重试
长静态前缀在有效期内反复出现原生前缀缓存；稳定可复用内容与动态后缀分离最低长度、断点、TTL、实际命中率，以及写入溢价能否被后续读取抵消
同一权限范围内重复的只读知识问答受隔离与时效约束的语义缓存答案等价性、权限与知识版本、误命中率、查询和失效维护成本
任务可异步交付，截止时间宽松Batch API，与实时通道分开目标模型 / 接口的资格、折扣、完成窗口、失败重投与业务截止时间；不能把实时请求全部搬过去
推理开销高，但部分任务不需要同样深度测试目标模型 / API 支持的 effort 档位质量、总 token、尾延迟与重试；降低 effort 不保证成功任务成本降低
难度或任务类型差异大模型路由，配合有预算上限的升级 / fallback路由判断成本、误分流、补救调用与困难子集质量；参见 L32
上下文冗余多，或窄任务长期高频检索去重 / 压缩；有数据与稳定需求时再评估蒸馏 / 微调压缩的信息损失和额外调用；蒸馏的数据、训练、维护摊销与分布变化；必要时参考 LLMLingua

例如，反复执行同一检索却得不到新证据，应先实验终止 / 去重，而不是仅把这些无效调用缓存得便宜一些；夜间离线任务则可能直接从 Batch 实验开始。选哪个实验，由当前瓶颈、预期净收益、改造成本和风险决定。

组合优化要重新测量，不能把各项“省额”直接相加：语义缓存减少模型请求，前缀缓存可读次数也会变化；压缩或改工具定义可能破坏原有前缀；路由会改变模型和缓存分布。收益、质量和延迟都要在组合后的完整任务上复算。

Q 两个候选都达到质量与延迟门槛。判断哪个更省，应该重点比较什么？
成功任务成本的分子包含全部任务的实际花费，包括失败、重试、fallback 和相关工具 / 缓存费用。请求单价与调用次数是诊断信号，不是最终成本目标。质量、关键子集和延迟门槛必须先达标。

3. 前缀缓存：不同问题仍可复用共同输入

原生 Prompt Caching 复用精确匹配的共同前缀，不复用旧答案。实际匹配按厂商对输入内容、token / 内容块、参数及可用边界的规则进行，不能简化为自己对两个问题做字符串比较。命中后仍要处理动态部分并生成本轮输出。

两次请求都以相同的工具定义、system 指令和政策文档开头，末尾分别问“退货政策是什么”和“怎么申请退货”。用户问题不同，不妨碍前面那段共同输入在满足条件时命中。变化只会阻止越过该变化点的复用；不是任何位置改一个字，之前所有可用前缀都会失效。两种问法是否能复用整份答案，则是另一层问题。

请求 A：相同工具 + 相同指令 + 同版本政策 | 问题 A → 生成新答案 A
请求 B：相同工具 + 相同指令 + 同版本政策 | 问题 B → 生成新答案 B
        └── 满足长度、边界、TTL 等条件时可复用 ──┘
缓存折扣针对可复用的输入部分；动态输入、输出和其他费用仍需计入。

通常把稳定、可复用内容放在动态内容之前，但不能为了命中率移除必要的用户权限、业务上下文或安全校验。工具排序、文档版本、历史重写和压缩都可能改变前缀。静态内容不足最低长度、缓存过期或路由条件不满足时，即使看起来相同也不保证命中。

每次接入都核对一份缓存契约

核对项要回答的问题
provider / model / API具体供应商、部署平台、模型版本、区域和接口是什么？所用能力是否受支持？记录核验日期
TTL 与失效默认和可选有效期是什么？读取是否续期？升级有效期或变更内容是否重新收费？
最小长度与断点可缓存前缀是否够长？自动还是显式边界？可用断点、匹配粒度和查找范围有什么限制？
写价 / 读价 / 普通输入价首次或重新写入怎么计费？不同 TTL 是否有不同写价？读取价格是否因模型而异？
usage 与命中边界如何区分普通输入、cache write、cache read？哪些字段包含哪些子集？租户 / 组织、路由或内容变化是否影响命中？

依照审查报告中的官方来源：OpenAI Prompt Caching 按模型代际、接口和 TTL 区分策略，不能从部分早期模型的无额外写费推导出“OpenAI 一律免费写”；Anthropic Prompt Caching 的最低长度、写入 / 读取计费也要按模型、平台与 TTL 核对，不能统一套用某个读取倍数。本课不硬编码新模型价格。

测量而非想象命中：从对应 API 的 usage 读取缓存写入、缓存读取与未缓存输入量，并按该接口字段定义去重计价；没有对应字段时先确认可观测性，不能把“请求成功”当成“缓存命中”。再比较整批任务的实际账单、质量与延迟。

同一段等长前缀的简化测算：按实际写入次数乘写价、读取次数乘读价、未缓存处理次数乘普通输入价，三部分相加；真实账单应换成各类 token 数及对应计价单位。只写一次却没有后续读取，可能比不用缓存更贵。这还只是前缀成本，不能冒充整次请求或整项任务的节省比例。

Q 两个用户问题措辞不同，但前面有相同的长政策文档。哪种判断正确？
原生缓存不根据问题语义选旧答案。不同的动态后缀仍可共享之前的精确前缀，但实际命中还取决于模型 / API、长度、断点、TTL 和路由等。命中后仍生成新输出，也不代表整次调用免费。

4. 语义缓存：答案复用先过隔离与时效关

维度原生前缀缓存应用层语义缓存
复用对象符合厂商规则的精确共同输入前缀已经验收、允许复用的问答结果
命中依据精确输入匹配、可用缓存边界与生命周期隔离与有效性检查，再做相似检索及答案等价性判断
命中后生成仍调用模型生成本轮新答案可直接返回答案，省去本轮生成；查询等开销仍在
主要限制写读价、TTL、最小长度、断点、路由等越权、误命中、过期答案及不可缓存的动作结果

语义缓存通常用 embedding 检索相近问题，但相似度不是答案可复用的充分条件。“退货政策是什么”与“退货要几天”相关，却未必需要同一份答案；同一问题在不同地区、商品或政策版本下也可能答案不同。

  • 租户与权限：在检索前限定 tenant、用户或可证明等价的权限范围；缓存键 / 命名空间包含相应隔离信息。命中后仍核验当前权限与资料访问权，不能先跨租户取答案、最后才过滤。
  • 版本与时效：记录知识版本、答案 / 提示策略版本、必要的地区与业务条件，以及 TTL。政策更新、文档删除或授权撤销应触发失效或读时校验，不能只等待 TTL 到期。
  • 误命中：在独立样本上校准阈值与等价性规则，保留近义但不等价的反例；抽查实际命中答案，单独记录误命中率和业务影响。
  • 排除动作执行结果：不能复用“订单已提交”“退款已执行”“审批已通过”来替代本次执行。动作需要本次授权、状态检查与独立的幂等 / 执行记录；那不是语义答案缓存。敏感账户状态也不应默认复用。

只有在上述条件都成立时，命中才可跳过本轮生成；否则正常执行只读问答流程，经过验收再决定是否写回。embedding、向量查询、复核、存储和失效维护都有成本，高命中率不等于低成功任务成本，更不等于高正确率。

可参考 GPTCache 的实现思路，但接入一个库不会自动提供业务权限与时效保证。前缀缓存和语义缓存可以共存，是否值得组合仍需完整测量。

Q 两个租户问了同样的问题，向量相似度为 1。语义缓存应该怎么处理？
相似度不能越过权限边界。语义缓存需要租户 / 用户或等价权限范围隔离、当前授权检查、知识版本和 TTL，并排除动作执行结果。只读知识答案可以受控复用，业务动作仍须独立执行或按其幂等协议处理。

5. 离线测算：单次低价为什么可能更贵

这是虚构 fixture，不是真实模型、价格或性能基准。下面用整数“成本单位”表示每次尝试的总花费，手工指定最终结果和端到端耗时；每个候选覆盖相同的四个任务。retry 策略的每个任务都先失败一次，再尝试一次，最后按整项任务验收。候选代表完整策略（含重试），不是模型能力排名。为缩小示例，这里假定其他费用为零；真实评估必须补齐第 1 节的成本边界。

本次仅为演示，质量门槛设为成功率至少 3/4、p95 不超过 1200 ms；生产门槛应由业务风险和 SLO 决定。使用标准库 Fraction 避免金额比较的浮点误差，分位数采用 nearest-rank。

运行任务

将下方完整代码复制到独立的 l37_cost_check.py，用 Python 3.10+ 执行 py -I l37_cost_check.py。不需要 Key、网络或额外依赖，不要使用 -O，以免禁用断言。

通过标准

  • 精确验证总成本、成功率、成功任务成本、p95 和调用数，失败尝试也被累计
  • 每次尝试更便宜的 retry 策略，成功任务成本反而更高
  • 质量不达标或尾延迟超标的低价方案被淘汰；零成功不报零成本
  • 验证前缀缓存首次写入、后续命中、反复失效的不同成本
  • 所有断言通过后，标准输出只有一行 L37 ACCEPTED
from dataclasses import dataclass
from fractions import Fraction
from math import ceil


@dataclass(frozen=True)
class TaskTrial:
    attempt_costs: tuple[int, ...]  # 失败、重试、fallback 都要记账
    success: bool                 # 整个任务的最终验收结果
    latency_ms: int               # 端到端时间，包含所有尝试和等待


@dataclass(frozen=True)
class Metrics:
    total_cost: int
    success_rate: Fraction
    cost_per_success: Fraction | None
    p95_ms: int
    calls: int


def measure(trials):
    if not trials:
        raise ValueError("need at least one task")
    total = sum(sum(t.attempt_costs) for t in trials)
    successes = sum(t.success for t in trials)
    times = sorted(t.latency_ms for t in trials)
    rank = ceil(Fraction(95, 100) * len(times))
    return Metrics(
        total_cost=total,
        success_rate=Fraction(successes, len(trials)),
        cost_per_success=Fraction(total, successes) if successes else None,
        p95_ms=times[rank - 1],
        calls=sum(len(t.attempt_costs) for t in trials),
    )


# 完全虚构的四个任务及四种策略；单位不对应任何厂商货币或单价。
fixtures = {
    "baseline": [
        TaskTrial((6,), True, 400),
        TaskTrial((6,), True, 600),
        TaskTrial((6,), True, 800),
        TaskTrial((6,), False, 900),
    ],
    "retry": [
        TaskTrial((4, 4), True, 900),
        TaskTrial((4, 4), True, 1000),
        TaskTrial((4, 4), True, 1100),
        TaskTrial((4, 4), False, 1200),
    ],
    "low_quality": [
        TaskTrial((1,), True, 200),
        TaskTrial((1,), False, 250),
        TaskTrial((1,), False, 300),
        TaskTrial((1,), False, 350),
    ],
    "slow": [
        TaskTrial((2,), True, 1300),
        TaskTrial((2,), True, 1400),
        TaskTrial((2,), True, 1500),
        TaskTrial((2,), True, 1600),
    ],
}
stats = {name: measure(rows) for name, rows in fixtures.items()}
assert stats["baseline"] == Metrics(24, Fraction(3, 4), Fraction(8), 900, 4)
assert stats["retry"] == Metrics(32, Fraction(3, 4), Fraction(32, 3), 1200, 8)
assert stats["low_quality"] == Metrics(4, Fraction(1, 4), Fraction(4), 350, 4)
assert stats["slow"] == Metrics(8, Fraction(1), Fraction(2), 1600, 4)
assert all(c < 6 for t in fixtures["retry"] for c in t.attempt_costs)
assert stats["retry"].cost_per_success > stats["baseline"].cost_per_success

quality_floor = Fraction(3, 4)
p95_limit = 1200
eligible = {
    name: m for name, m in stats.items()
    if m.success_rate >= quality_floor and m.p95_ms <= p95_limit
}
assert set(eligible) == {"baseline", "retry"}
# 实际评估若无合格方案，应停止选择，而不是绕过门槛。
winner = min(eligible, key=lambda name: eligible[name].cost_per_success) if eligible else None
assert winner == "baseline"
assert measure([TaskTrial((4,), False, 50)]) == Metrics(4, Fraction(0), None, 50, 1)


# 独立的前缀成本算例：每次恰好处理一个等长前缀单位。
# 虚构普通价 10、写价 16、读价 2；不代表任何 provider 或 TTL。
def prefix_cost(writes, reads, *, write_price, read_price):
    return writes * write_price + reads * read_price


prices = {"write_price": 16, "read_price": 2}
first_write = prefix_cost(1, 0, **prices)
warm = prefix_cost(1, 3, **prices)   # 有效期内，一次写入、三次读取
churn = prefix_cost(4, 0, **prices)  # 反复过期 / 变更，四次全是写入
assert first_write == 16
assert first_write > 10
assert warm == 22
assert churn == 64
assert warm < 4 * 10 < churn

print("L37 ACCEPTED")

结果诊断：只能输出 L37 ACCEPTED。baseline 总成本 24，成功任务成本 8；retry 单次 4 虽低于 6，但八次尝试共花 32，成功任务成本为 32/3。low_quality 成本更低却未达质量门槛；slow 全部成功却超过延迟门槛。缓存写入算例为 16，四次复用场景为 22，反复失效则为 64，不能只看读取价 2。

证据边界：通过标记仅证明此 fixture 下的计算与筛选规则，不证明真实模型成功率、缓存命中率、延迟或任何降本比例。代码没有实现模型调用、缓存服务、租户权限或动作幂等。

6. 把测算变成可验证的优化实验

练习 A：换一种负载，结论会怎样变化？
  1. 先不运行，预测 retry 没有重试、四个任务仍是三个成功一个失败时，成功任务成本会怎样变化。
  2. 复制 fixture 的 retry 数据，在新副本中把每个 (4, 4) 改成 (4,)，只对新副本测算；保留原始验收不变。断言总成本为 16、成功率为 Fraction(3, 4)、成功任务成本为 Fraction(16, 3)。
  3. 把缓存读取次数从 3 改成 0，预测只有首次写入时会不会省钱。再用不同的虚构 TTL 失效次数比较，但不要据此推导真实 provider 的阈值。

解释要求：成本变化来自尝试次数与命中分布，不是模型名字。现实里取消重试可能降低成功率，必须重新评估，不能沿用 fixture 手工指定的 success。

练习 B：给客服知识问答写一张实验决策卡

已知请求有共同的长政策前缀，也有近义问题；不同租户的政策权限不同，政策随时更新，还有“帮我提交退款”的动作请求。不能预先断言哪种缓存更省。

  • 列出基线：任务分布、质量与关键子集门槛、总成本 / 成功任务数、端到端 p95，以及循环、结果量、输出、重试与 fallback 的占比。
  • 为前缀缓存列出模型 / API、TTL、最小长度、断点、写读价和 usage 验证方法；不同问题的共同前缀仍可命中。
  • 为语义缓存写出租户 / 权限范围、知识版本、TTL 与失效规则；用近义但不等价的反例检验误命中，并明确动作执行结果不缓存。
  • 只选一个有证据支持的首轮实验，写清验收集、净收益预期、回滚条件与未知项。组合其他改动后重新测，不能简单相加省额。
Q 面对月账单 10k、目标 5k 的 Agent，合理的第一步是什么？
预算目标不是效果保证。先定义可接受质量与延迟，测全链路成本和失败，再按负载提出实验。Batch、effort、缓存、路由等均需验证，组合收益也不能直接相加；达不到目标时应如实说明预算与需求的冲突。
面试回答：一个 Agent 每月 10k，如何尝试降到 5k？ 先确认流量、任务难度、质量门槛和延迟 SLO；按完整任务追踪全部尝试及工具费用，算成功任务成本并看 p95。根据 trace 选择实验：若无效循环或结果 / 输出量主导，就测试减少这些浪费；若共同前缀复用高，就核对目标模型 / API 的缓存契约与写读账；若可延后交付，就评估 Batch；再按证据测试 effort、路由、压缩或蒸馏。语义缓存只复用同租户 / 权限范围、有效版本下的可复用知识答案，不复用动作结果。各方案须通过同一验收集与灰度回归，组合后重新算净收益；无法满足预算时说明差距，不保证砍半。前缀缓存省重复输入且仍生成新答案，语义缓存满足约束后才可跳过生成，两者不能混为一谈。

速查卡：决策证据，不是优先级口诀

  • 基线：同一任务分布与验收规则，记录最终成功、所有尝试总花费、端到端 p95；零成功不报零成本。
  • 筛选：先过质量、权限等硬要求与延迟门槛，再比较总成本 / 成功任务数。
  • 前缀缓存：精确共同输入复用；不同问题仍可能命中共同前缀；逐项核对 provider / model / API / TTL / 最小长度 / 断点 / 写读价。
  • 语义缓存：受控答案复用；租户、权限、知识版本、TTL 与等价性缺一不可，动作执行结果不缓存。
  • 选实验：减少无效循环与过量结果 / 输出、缓存、Batch、effort、路由、压缩 / 蒸馏，均按瓶颈选，不设通用排序。
  • 验收：保留独立任务集，组合后重新测量，计算摊销和回滚条件；fixture 通过不等于真实降本。

总结

  • 负载驱动：先定质量门槛、计入全部尝试的成功任务成本和端到端 p95，再选择优化实验，不背固定六层顺序。
  • 单次低价可能更贵：失败、重试和 fallback 会放大花费；不合格质量或延迟不能靠低价抵消。
  • 两种缓存不是替代关系：共同前缀可在问题不同的情况下命中；语义缓存复用的是经隔离、版本与时效校验的答案，不是业务动作结果。
  • 缓存看全账：按 provider / model / API / TTL / 最小长度 / 断点 / 写读价与 usage 核对，既看首次写入，也看命中和失效。
  • 结论有边界：标准库 fixture 验证核算逻辑；真实负载仍需独立验收、重复试验、摊销核算与回滚，不保证省一半。
