成本工程：2026 降本优先级

把所有降本手段排成一张优先级清单——照着从上往下拧，$10k 砍到 $5k

💡 为什么这课重要？

L23 教了两根主杠杆——Prompt Caching 和 Model Routing。这一课把它们放进一张完整的、按性价比排序的降本清单里，并补上 L23 没细讲的几层：语义缓存、提示压缩、小模型蒸馏、Batch API。

为什么 Agent 尤其需要这个：Agent 是调用密集型系统——一次任务反复往返 LLM，每次都拖着长上下文（L23 的四个放大器）。所以成本工程不是锦上添花，而是生产必修。这套优先级清单还是一道面试高频题的标准答法："一个 Agent 每月 $10k，怎么砍到 $5k？"——面试官想听的不是某一招，而是你按什么顺序拧、每一层省的是什么。学完你能把降本从"零散技巧"升级成"有优先级的工程决策"。

学习目标

完成本课后，你将能够：

  • 背出 2026 降本优先级清单（6 层 + 组合心法），并说清每层省的是什么
  • 讲清 前缀缓存 vs 语义缓存的本质区别（逐字节命中 vs 语义相似命中）——本课的灵魂
  • 知道语义缓存跳过的是整次 LLM 调用，以及它的误命中（阈值）风险
  • 认识 提示压缩（LLMLingua）、小模型蒸馏、Batch API 各自的适用场景
  • 用这套优先级回答"$10k → $5k"这类成本面试题

1. 一张表：2026 降本优先级清单

先给全景。降本不是"招越多越好"，而是"按性价比从上往下拧"——上面的收益大、改动小、几乎无副作用；下面的更专、更费工。L23 讲了 ①③（缓存与路由），这里把清单补全：

优先级手段降的是什么成本改动量 / 代价
①Prompt Caching（前缀缓存）重复静态前缀的输入成本近乎零改动；命中即降价
②语义缓存（semantic cache）相似问题的整次调用成本需接向量库；要调阈值
③Model Routing（模型路由）简单请求用贵模型的浪费需难度判断 / 网关
④提示压缩（Prompt Compression）冗长 prompt 里的冗余 token引入压缩工具；有信息损失风险
⑤小模型蒸馏 / 微调特定任务改用便宜小模型要训练 / 数据；工程最重
⑥Batch API非实时任务约省 50%牺牲延迟（结果稍后返回）

本课其余章节逐层拆开讲。重点在 ①②——两种缓存的区别（第 2~3 节）是这一课的灵魂，也是面试最爱直接问的点。

读表顺序 = 落地顺序。先把 ①② 缓存吃干净（零/低成本、大收益），再上 ③ 路由，剩下 ④⑤⑥ 按场景补。别一上来就搞最重的 ⑤ 蒸馏——那是"最后一公里"，不是第一步。

2. ① 原生 Prompt Caching（第一杠杆，回顾）

这层 L23 已详讲，这里快速捡回作为清单第一档。原理：把静态的、重复的前缀（长 system prompt、固定工具定义、反复出现的文档）缓存起来。后续请求只要前缀逐字节命中，这部分就大幅降价——不再为"每次都一样的内容"付全价。

数量级（以官方文档为准，一律用"约"）：

厂商缓存读（命中）缓存写（首次）
Anthropic约 0.1× 输入价（省约 90%）约 1.25×（首次略贵）
OpenAI命中约省 50%~90%（视模型代次，以官方为准）自动，无额外写入费

出处：Anthropic: Prompt Caching、OpenAI: Prompt Caching。核心设计原则一句话：把 prompt 拆成「静态前缀（可缓存）+ 动态后缀（每次变）」，静态放最前面——因为是前缀匹配，开头混进时间戳 / 用户 ID / 随机数，缓存就永远不命中。

【缓存键设计：静态前缀 + 动态后缀】
┌─ 静态前缀（放前面，打缓存标记）─────────┐
│  角色设定 / 工具定义(排序) / 固定示例    │ ← 命中约 0.1×
└──────────────────────────────────────────┘
┌─ 动态后缀（放后面，不缓存）───────────────┐
│  本轮用户问题 / 时间戳 / 新检索片段        │ ← 全价但很短
└──────────────────────────────────────────┘

对 Agent 来说，长 system prompt + 固定工具集天然就是巨大的静态前缀，缓存几乎是"免费的午餐"。它降的是"重复前缀的输入成本"——记住这句，下一节的语义缓存降的是另一样东西。

Q 前缀缓存（Prompt Caching）命中的条件是什么？
前缀缓存是逐字节的前缀匹配：开头哪怕差一个字符（时间戳、随机 ID、没排序的 JSON），整段前缀就失效、不命中。它不看语义——"意思相近"命中的是下一节的语义缓存，两者是不同的东西。命中也不是全免，而是降到约 0.1×（Anthropic）/ 约省 50%~90%（OpenAI，视模型代次）。具体倍数以官方为准。

2 与 3 的分水岭：两种缓存到底差在哪

这是全课最容易混、也最值钱的一张对照表。务必记牢：

维度① 前缀缓存（Prompt Caching）② 语义缓存（Semantic Cache）
命中条件前缀逐字节相同问题语义相似（超过阈值）
怎么判断命中字符串前缀比对embedding 算相似度
降的是重复前缀的输入成本相似问题的整次调用成本
还调 LLM 吗要（仍生成本轮输出）不调！直接返回缓存答案
典型例子同一 system prompt 反复复用"退货政策是什么" ≈ "怎么退货"

一句话把两者钉死：前缀缓存省"输入的重复部分"，但每次照样调模型出新答案；语义缓存直接把"这个问题以前答过了"整次跳过，连 LLM 都不碰。

3. ② 语义缓存：与前缀缓存的本质区别（重点）

问题所在：前缀缓存要求前缀逐字节相同才命中。但真实用户不会一字不差地重复提问——"退货政策是什么" 和 "怎么退货" 意思一样，可字节完全不同，前缀缓存一个都命不中，两次都得完整调一遍 LLM。这正是语义缓存要补的洞。

原理：把每个问题先转成 embedding 向量，进来的新问题也转成向量，去缓存里找语义最相似的历史问题。相似度超过阈值，就直接返回那条缓存答案，完全跳过 LLM 调用——省的不是"输入的一部分"，而是整整一次调用（输入 + 输出 + 往返延迟全省）。

【语义缓存工作流】
新问题 → 转 embedding → 在向量缓存里找最相似的历史问题
   ├─ 相似度 ≥ 阈值 → 命中！直接返回缓存答案（✗ 不调 LLM）
   └─ 相似度 < 阈值 → 未命中 → 正常调 LLM → 把「问题→答案」写回缓存

例：缓存里已有「退货政策是什么 → {政策原文}」
   来一句「怎么退货」→ 语义高度相似 → 直接返回，省下整次调用

工具： GPTCache（专门的 LLM 语义缓存库）、Redis 向量缓存（用向量检索做语义缓存层）。二者都是 2026 生产里常见的语义缓存方案。

关键区分（再强调一次，面试直接问）：

  • 前缀缓存降的是 "重复前缀的输入成本"——本轮 LLM 还是照调，只是输入那段前缀便宜了。
  • 语义缓存降的是 "相似问题的整次调用成本"——命中就不调 LLM 了，输入输出一起省，还顺带省了延迟。

对 Agent 的意义：客服、FAQ、内部知识问答类 Agent，大量问题高度重复或近义——语义缓存能把一大票"换个说法的同一个问题"直接挡在 LLM 之外，是前缀缓存够不着的一大块钱。

⚠️ 语义缓存的头号风险：误命中（相似但不该等价）。阈值调太松，"我要退货" 可能错命中 "我要退款" 的答案——答非所问还一脸自信。所以阈值要调好：宁可偏严（多放几次真调用），也别让语义相近但语义不等价的问题串答案。上线后要抽查命中样本，盯住误命中率。
Q 语义缓存相比前缀缓存，最本质的省钱点在哪？
语义缓存按 embedding 相似度命中：意思相近但措辞不同的问题（"退货政策是什么" vs "怎么退货"）也能命中同一答案，命中后直接返回、完全不调 LLM——省的是整整一次调用（输入+输出+延迟）。前缀缓存则相反：它只降重复前缀的输入成本，本轮 LLM 照样要调。压前缀、改 TTL、打折单价都不是语义缓存的机制。

4. ③ Model Routing（模型路由，回顾）

清单第三档，L23 和 L32 已讲透，这里定位它在优先级里的位置。原理：不是所有请求都值得用最贵的模型。便宜快的小模型兜底简单请求，贵而强的大模型只接难请求。

请求进来 → 判断难度
   ├─ 简单（分类 / 提取 / 闲聊 / 格式化）→ 便宜快模型 兜底
   ├─ 中等（一般问答 / 总结）           → 中档模型
   └─ 困难（多步推理 / 复杂 Agent 规划） → 顶级模型 只接这类

为什么放在缓存之后：路由要做难度判断、接网关、可能调策略，改动比"打个缓存标记"大一些；但收益依然很高（L23 引用的真实报道降幅 40%~85%）。工程落地用一个 gateway（LiteLLM）统一路由，业务代码不用管背后是哪个模型。它和"选型"一脉相承——只是把选择从一次性决策变成每请求的动态决策（见 L23 对 L20/L22 的呼应）。

5. ④ 提示压缩（Prompt Compression）

缓存和路由拧完，还想再抠，就轮到压 prompt 本身。很多长 prompt（尤其塞了大段检索文档、冗长示例）里有大量对结果无关紧要的冗余 token。提示压缩就是用工具把这些冗余删繁就简，在尽量保留关键信息的前提下缩短输入。

代表工具：微软 LLMLingua——它用一个小模型识别并删除 prompt 里"信息密度低"的 token，把长上下文压短再喂给大模型，能显著压缩（具体压缩比以你的实测为准，不同任务差别很大，别记死某个倍数）。

注意事项：

  • 压缩有信息损失风险——压太狠可能把关键细节也删掉，影响回答质量。压缩率和质量之间要权衡、要实测。
  • 它和缓存是互补：缓存降的是"重复内容的价"，压缩降的是"内容本身的量"。二者可以叠加。
  • 对 Agent：RAG 检索片段、超长历史是压缩的主要靶子——先压再进上下文，既省钱又缓解上下文膨胀。

6. ⑤ 小模型蒸馏 / 微调，与 ⑥ Batch API

清单最后两档，更专、更重，按需上。

⑤ 小模型蒸馏 / 微调小模型：把大模型在某个特定任务上的能力"蒸馏"或微调到一个便宜的小模型上——用大模型生成/标注数据，训练小模型学会这一类活。之后这类任务全交给小模型，单价断崖式下降。代价是要数据、要训练、要维护，工程最重，所以排在缓存/路由/压缩之后，适合"某类高频任务量特别大、值得为它专门养一个小模型"的场景。

⑥ Batch API：非实时任务（离线分类、批量总结、夜间跑的数据处理）走批处理接口，通常约省 50%，代价是延迟——结果不是立刻返回，而是稍后交付。凡是"不急着要答案"的活，都该考虑走 Batch。对 Agent：实时对话走普通接口，后台的批量离线任务走 Batch，两条通道分开。

Q 按 2026 降本优先级，应该最先动手的是哪一档？
优先级的第一原则是"缓存优先"：①前缀缓存 + ②语义缓存收益大、改动小、几乎无副作用，是最高性价比的第一步。蒸馏（⑤）工程最重、Batch（⑥）牺牲延迟只适合非实时、压缩（④）有信息损失风险且收益在缓存之后——它们都排在缓存和路由后面。顺序是：①②缓存 → ③路由 → ④⑤⑥按需。

7. 组合心法：从上往下拧

把六档串成一条落地路径，照顺序拧，每拧一层再看还差多少：

① 前缀缓存   ← 先上，零/低改动、静态前缀省约 90%（呼应"原生缓存优先"）
② 语义缓存   ← 紧接着，相似问题整次跳过、连 LLM 都不调
─────────── 以上两层：缓存吃干净，通常已砍掉一大半 ───────────
③ 模型路由   ← 便宜模型兜底、贵模型只接难题
④ 提示压缩   ← 还想抠，用 LLMLingua 压掉冗余 token（实测权衡质量）
⑤ 小模型蒸馏 ← 某类高频任务量大，值得养专用小模型
⑥ Batch API  ← 非实时任务走批处理，约省 50%（换延迟）

心法就一句：先缓存（①②），再路由（③），其余（④⑤⑥）按需。越靠上性价比越高——先把上面的收益吃满，再决定要不要动下面更重的手段。

为什么这套优先级是 Agent 的生产必修：Agent 调用密集（一次任务多次往返、每次拖长上下文），成本被 L23 的四个放大器反复放大。单次 chat 省不省无所谓，Agent 规模下这条清单直接决定账单是 $10k 还是 $5k。把它当成 Agent 上线前的成本"体检 + 优化"标准流程。

🛠 练习：客服 Agent，为什么语义缓存比前缀缓存更省？

场景：一个客服 Agent，每天收到大量意思重复但措辞不同的问题——"退货政策是什么" / "怎么退货" / "退货要几天" / "我想退货怎么办"……含义高度重叠，但字节各不相同。请说明：为什么语义缓存比前缀缓存更省？以及阈值有什么风险？

① 为什么语义缓存更省

  • 前缀缓存命不中这些问题：它要求前缀逐字节相同。这些问题措辞全不一样，前缀比对失败，每一句都得完整调一次 LLM——前缀缓存只能省掉它们共享的那段 system prompt 输入，本轮问答照样全算。
  • 语义缓存直接整次跳过：把问题转成 embedding 按语义相似度命中——"怎么退货"和已缓存的"退货政策是什么"语义高度相似，超过阈值就直接返回缓存答案，完全不调 LLM。省的不是"输入的一部分"，而是整整一次调用（输入 + 输出 + 往返延迟全省）。
  • 一句话：前缀缓存降"重复前缀的输入成本"，语义缓存降"相似问题的整次调用成本"——客服场景大量近义问题，正好是语义缓存的甜点、前缀缓存够不着的一大块钱。

② 阈值风险

  • 阈值太松 → 误命中：语义相近但不该等价的问题会错串答案（"我要退货" 误命中 "我要退款" 的答案），答非所问还很自信。
  • 阈值太严 → 命中率低，很多本可复用的相似问题又都去调了 LLM，省得不够。
  • 做法：宁可偏严，并上线后抽查命中样本、盯误命中率，再微调阈值。缓存答案是"折叠"起来的，一旦折错就是错答案直接返给用户，所以阈值必须谨慎。

最佳组合：两层缓存一起上——前缀缓存负责所有请求共享的 system prompt / 工具定义（逐字节复用），语义缓存负责挡下近义的重复问题（整次跳过）。各降一块，互不替代。

💼 面试高频："一个 Agent 每月 $10k，怎么砍到 $5k？" 满分答法按优先级顺序，并说清每层省什么：① Prompt Caching——缓存逐字节相同的静态前缀，静态部分省约 90%；② 语义缓存——按语义相似命中，相似问题跳过整次调用（连 LLM 都不调）；③ 模型路由——便宜模型兜底、贵模型只接难题；④ 提示压缩（LLMLingua，压冗余 token）；⑤ 蒸馏（高频任务养专用小模型）；⑥ Batch（非实时约省 50%）。务必点破 ①② 的区别——前缀缓存 = 逐字节前缀命中、降输入；语义缓存 = 语义相似命中、跳过整次调用。能把这个区别讲清，这道题就满分。

总结

  • 2026 降本是一张按性价比排序的清单：①前缀缓存 → ②语义缓存 → ③路由 → ④压缩 → ⑤蒸馏 → ⑥Batch
  • 灵魂是①②的区别：前缀缓存要前缀逐字节相同、降"重复前缀的输入成本"、本轮仍调 LLM；语义缓存按语义相似命中、降"相似问题的整次调用成本"、命中就不调 LLM
  • 语义缓存用 embedding 相似度 + 阈值命中（工具：GPTCache / Redis 向量缓存），注意误命中风险——宁严勿松
  • ④压缩（LLMLingua 压冗余 token，有损）/ ⑤蒸馏（高频任务养小模型，最重）/ ⑥Batch（非实时约省 50%，换延迟）按需补
  • 组合心法：先缓存、再路由、其余按需；这套优先级是 Agent 生产必修，也是"$10k→$5k"的标准答法
拿你自己的一个 Agent 场景走一遍这张清单：先估未优化月成本（L23 第 6 节的四步），然后从 ① 往下逐层问"这层能省多少"——① 静态前缀多大？② 有多少近义重复问题？③ 有多少简单请求可以下放？把每层的预估省额加起来，你会立刻看到从哪砍最划算。拿不准某个倍数（一律以官方为准）或语义缓存阈值怎么定，随时问我或你的老师。下一课我们把 Phase 3 学的工程能力一起用到 综合实战里。
