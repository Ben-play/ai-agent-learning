1. Python 是怎么运行的

很多人说"Python 是解释型语言"，但这不完全准确。Python 的执行分两步：

第一步：编译为字节码（Bytecode）
Python 解释器先把 .py 源代码编译为字节码。字节码是一种中间表示，不是机器码，但比源代码更接近执行层面。

第二步：Python 虚拟机执行字节码
Python 虚拟机（PVM）逐条执行字节码指令。这才是真正的"解释执行"。

字节码会不会缓存成 .pyc 文件？
看这个模块是被 import 的还是直接运行的。被 import 的模块，字节码通常会缓存到所在目录的 __pycache__ 里，下次 import 时如果源文件没改就直接加载缓存；而你直接 python xxx.py 运行的那个"主模块"，它的字节码只在内存里编译执行一次，不会为自己生成 .pyc 文件。 
# 实测验证：主模块 vs 被 import 的模块
$ printf 'print("main")\n' > mainmod.py
$ printf 'x = 42\n' > imported.py
$ python mainmod.py
main
$ python -c 'import imported'
$ find .
./__pycache__/imported.cpython-314.pyc   # 只有 imported 生成了 .pyc
./imported.py
./mainmod.py                              # mainmod 没有对应的 .pyc
# 你可以看到 Python 生成的字节码
import dis

def greet(name):
    return f"Hello, {name}"

dis.dis(greet)
# 输出类似：
#   0 LOAD_CONST     1 ('Hello, ')
#   2 LOAD_FAST      0 (name)
#   4 FORMAT_VALUE   0
#   6 BUILD_STRING   2
#   8 RETURN_VALUE
🔑 Agent 开发关联：

理解字节码不常直接用到，但当你调试 Agent 框架的奇怪行为时，知道 Python 先编译再执行这个事实，能帮你理解为什么某些语法错误在"运行前"就会被捕获（编译阶段），而另一些要到运行时才报错。

Python 的执行入口

当你运行 python my_script.py 时，Python 做了这些事：

  1. 启动 Python 解释器
  2. 把 my_script.py 编译为字节码
  3. 设置特殊变量 __name__ 为 "__main__"
  4. 从上到下逐行执行代码
  5. 执行完毕，退出解释器

2. __name__ == "__main__"

这是 Python 中最常见也最容易困惑的模式。理解它只需要一个关键认知：

核心规则：
· 当一个文件被直接运行时，__name__ 的值是 "__main__"
· 当一个文件被import时，__name__ 的值是模块名（文件名去掉 .py） 
# calculator.py
def add(a, b):
    return a + b

# 这段代码只在直接运行时执行，被 import 时不会执行
if __name__ == "__main__":
    print(f"2 + 3 = {add(2, 3)}")
# 直接运行
$ python calculator.py
# 输出: 2 + 3 = 5
# 因为 __name__ == "__main__"，所以 if 块内的代码执行了

# 被 import
$ python -c "from calculator import add; print(add(10, 20))"
# 输出: 30
# __name__ == "calculator"，if 块内的代码没有执行
🔑 Agent 开发中的实际用法：

Agent 项目的 main.py 通常这样写：

# main.py
from agent import create_response

def run():
    message = create_response("Hello Agent!")
    print(message)

if __name__ == "__main__":
    run()

这样做的好处：

  • 直接运行 python main.py 启动 Agent
  • 其他模块可以 import main 中的函数而不会意外启动 Agent
  • 测试时可以单独测试 run() 函数
Q 如果一个文件 agent.py 被 import agent，那么在这个文件中 __name__ 的值是什么？
被 import 时，__name__ 的值是模块名（文件名去掉 .py）。只有直接运行时才是 "__main__"。

3. 模块与包

模块（Module）

一个 .py 文件就是一个模块。模块名就是文件名（去掉 .py）。

# tools.py          → 模块名是 "tools"
# schemas.py        → 模块名是 "schemas"
# agent/core.py     → 模块名是 "agent.core"

包（Package）

一个包含 __init__.py 文件的目录就是一个包。包是用来组织模块的。

my-agent/        # 项目目录，可以含连字符（不是 Python 标识符，不能被 import）
└── agent/       # Python 包名，必须是合法标识符
    ├── __init__.py      # 标记 agent 是一个包
    ├── core.py          # 模块: agent.core
    ├── tools.py         # 模块: agent.tools
    └── schemas.py       # 模块: agent.schemas
└── main.py
⚠️ 常见混淆：项目目录 ≠ Python 包名

my-agent/ 这一层只是操作系统里的一个文件夹，用来装你的项目，它的名字随便起（甚至可以带连字符），不能被 import，因为 - 不是合法的 Python 标识符。真正能被 import 的是里面那个没有连字符、且含 __init__.py 的目录，比如这里的 agent/。

💡 Python 3.3+ 的变化：

Python 3.3 引入了"命名空间包"，__init__.py 不再是必须的。但强烈建议始终创建它，因为：

  • 明确标识这是一个包
  • 某些工具（如 pytest、mypy）依赖它
  • 可以在其中控制包的公开接口

__init__.py 的作用

__init__.py 可以把少量稳定名称再导出为包的公开入口，并用 __all__ 声明星号导入的范围：

# agent/__init__.py
from .schemas import Message
from .core import create_response

__all__ = ["Message", "create_response"]

相邻原则：import 应无可见副作用。导入包时会执行模块顶层代码，因此不要在 __init__.py 或被它导入的模块中启动 Agent、发网络请求、改文件或打印日志；启动行为放到 main.py 的 if __name__ == "__main__": 下。

最佳实践：只为稳定入口做 re-export

一个决策：这个名称是否是承诺给应用入口或外部调用方的稳定接口？若答案是“是”，才从 __init__.py 再导出；包内实现与针对内部模块的测试仍可显式导入子模块。

什么时候会遇到：希望将来调整 core.py，又不想修改 main.py 等公开接口调用方。

❌ 公开调用方绑定内部路径
# main.py
from agent.core import create_response

入口知道了实现文件的位置，移动实现会波及调用方。

✅ 再导出稳定入口
# agent/__init__.py
from .core import create_response
from .schemas import Message
__all__ = ["Message", "create_response"]

# main.py 等公开接口调用方
from agent import create_response

公开路径保持稳定；包内代码仍可写 from .schemas import Message，测试内部行为时也可显式导入 agent.core。

为什么更优：只 re-export 稳定名称，会用包入口隔离公开调用方与内部文件布局，从而提升接口稳定性和重构可维护性。代价是维护精确的公开清单，并承担首次导入这些模块的启动成本；实验性实现或重模块的低频能力应保留显式子模块导入，避免过早承诺兼容性和拖慢包导入。

  1. 把 Message 与 create_response 定为本练习的两个稳定公开名称。
  2. 在 agent/__init__.py 精确再导出并列入 __all__。
  3. 让 main.py 从 agent 导入，内部模块按需显式导入子模块。

__all__ 控制公开接口

# agent/__init__.py
from .core import create_response
from .schemas import Message
from .internal import _debug  # 内部工具，不希望用户直接使用

__all__ = ["create_response", "Message"]  # 只有这两个会被 from agent import * 导出
# 用户代码
from agent import *       # 只导入 create_response 和 Message，不导入 _debug
from agent import _debug  # 显式导入仍然可以

4. import 机制

import 的查找模型（初学者简化版）

完整导入机制由 sys.meta_path 上的 finder/loader 协作完成，还包含 built-in 与 frozen 模块等来源。本课先用下面的排错模型理解常见项目导入：

  1. sys.modules 缓存 — 名称已经加载时通常直接复用模块对象，不重新执行模块顶层代码
  2. finder 处理特殊来源 — 例如编译进解释器的 built-in 模块和 frozen 模块
  3. 文件系统 finder 按 sys.path 查找 — 在路径条目中寻找标准库、第三方包和项目模块，常见来源包括：
    • 当前脚本所在目录或启动时加入的项目根
    • PYTHONPATH 环境变量指定的目录
    • 标准库目录（os、json 等许多模块来自这里）
    • site-packages（第三方包安装位置）

这不是 Python 导入协议的完整执行顺序，而是定位“为什么找不到项目包”的简化排错模型。实测 json.__file__ 通常能打印出标准库路径；有些 built-in/frozen 模块可能没有普通源码文件路径，不能只靠 __file__ 判断所有模块来源。

# 查看 Python 的模块搜索路径
import sys
print(sys.path)

# 查看模块从哪里加载的
import json
print(json.__file__)  # /usr/lib/python3.12/json/__init__.py

虚拟环境对 sys.path 的影响

激活虚拟环境后，sys.path 会改变，优先使用虚拟环境中的包：

# 未激活虚拟环境
$ python -c "import sys; print(sys.path)"
['', '/usr/lib/python3.12', ..., '/usr/lib/python3.12/site-packages']

# 激活虚拟环境后
$ source .venv/bin/activate
$ python -c "import sys; print(sys.path)"
['', '/home/user/.venv/lib/python3.12/site-packages', ...]
🔑 Agent 开发关联：

Agent 项目通常有多个依赖（openai、langchain、pydantic 等）。如果不理解虚拟环境对 sys.path 的影响，你会遇到"明明安装了包但 import 报错"的问题。这在 Agent 开发中极其常见。

两种 import 方式

# 方式 1：导入整个模块
import agent.core
agent.core.run()

# 方式 2：从模块中导入特定内容
from agent.core import run
run()

最佳实践：普通 import 放在模块顶部

一个决策：这个 import 是否确实需要延迟到函数调用时？当前练习没有例外许可，因此所有运行时 import 都应位于模块顶层。

什么时候会遇到：函数内混入普通 import，依赖被隐藏，且项目没有声明可直接使用的 lint 工具。

❌ 无理由地局部导入
def test_create_response():
    from agent.schemas import Message
    ...

依赖直到函数执行时才可见，AST 检查会报告文件与行号。

✅ 普通依赖置顶
from agent.core import create_response
from agent.schemas import Message


def test_create_response():
    ...

这与当前 tests/test_core.py 的结构一致；本练习的 allowlist 为空。

为什么更优：把普通 import 置顶，会让依赖在模块加载时集中解析并对读者和静态工具可见，从而提升可读性、可分析性和故障定位速度。代价是导入成本在启动阶段支付，且可选依赖缺失会更早报错；其他项目若确有可选依赖、明显昂贵的导入或局部打断循环等边界，应为具体位置建立有说明的 allowlist，而不是放宽整条规则。

uv run --offline python - <<'PY'
import ast
from pathlib import Path

files = sorted([Path("main.py"), *Path("agent").glob("*.py"), *Path("tests").glob("*.py")])
allowed = set()  # 当前练习没有函数内 import 例外
found = []
for path in files:
    tree = ast.parse(path.read_text(encoding="utf-8"), filename=str(path))
    parents = {}
    for parent in ast.walk(tree):
        for child in ast.iter_child_nodes(parent):
            parents[child] = parent
    for node in ast.walk(tree):
        if not isinstance(node, (ast.Import, ast.ImportFrom)):
            continue
        parent = parents.get(node)
        while parent is not None and not isinstance(
            parent, (ast.FunctionDef, ast.AsyncFunctionDef, ast.Lambda)
        ):
            parent = parents.get(parent)
        if parent is not None:
            location = (path.as_posix(), node.lineno)
            if location not in allowed:
                found.append(f"{path.as_posix()}:{node.lineno}:{node.col_offset + 1}")

assert not found, "function imports not allowed:\n  " + "\n  ".join(found)
print("function imports: []")

怎么看结果：当前 fixture 的 import 已在模块顶层，应输出 function imports: []。若出现 function imports not allowed，后续每行都会精确给出违规位置；不要再期待过时的 [5]。

相对导入 vs 绝对导入

# 绝对导入（推荐，尤其是入口文件）
from agent.core import run
from agent.schemas import Message

# 相对导入（只在包内部使用）
# 在 agent/tools.py 中（agent 是当前唯一一层包）：
from .schemas import Message      # 当前包的 schemas 模块
from .config import load_config   # 当前包的 config 模块
💡 什么时候才需要 ..？

.. 表示"上一级包"，只有当你的模块确实有父包时才用得上。比如结构是 project/agent/tools.py，且 project/ 也是一个包（含 __init__.py）：这时 project.agent.tools 里如果要访问 project.config，才写 from ..config import load_config。在本课 agent-hello/agent/ 这种只有一层包的结构里，agent 已经是顶层包，没有"上一级包"可言，所以不会用到 ..。

⚠️ 常见陷阱：

相对导入只能在包内部使用，不能在直接运行的脚本中使用。如果你在 main.py 中写 from .agent import run，会报 ImportError。这就是为什么 main.py 通常用绝对导入。

Q 以下哪个是正确的相对导入？假设当前文件在 agent/tools.py 中。
.schemas 表示当前包内的 schemas 模块。from agent.schemas 是绝对导入（虽然也能工作），import .schemas 是语法错误，..schemas 是上级包。

5. 循环导入：Agent 项目的大敌

循环导入是 Agent 开发中最常见的模块问题之一。当模块 A 导入模块 B，而模块 B 又导入模块 A 时，就会发生循环导入。

# ❌ 可能失败的循环导入示例
# agent/core.py
from agent.tools import search  # core 导入 tools

# agent/tools.py
from agent.core import create_response  # 若名字此时尚未绑定，会失败

为什么有时会报错？

Python 导入一个模块时，会在真正执行模块代码之前，先把这个模块对象放进 sys.modules（此时对象存在，但名字可能尚未绑定——"部分初始化"状态）。如果执行过程中又导入同一模块，Python 会返回这个部分初始化对象，不会因为检测到环就自动报错；有些循环只要不提前读取尚不可用的名称，也能完成。失败发生在代码过早取用名称或属性时：from a import x 常见 ImportError，而先 import a 再访问尚未绑定的 a.x 可能是 AttributeError。

# 实测：a.py 和 b.py 互相导入
# a.py:  from b import y \n x = 1
# b.py:  from a import x \n y = 2
$ python -c 'import a'
Traceback (most recent call last):
  ...
  File "b.py", line 1, in <module>
    from a import x
ImportError: cannot import name 'x' from partially initialized module 'a'
# 说明：不是"检测到循环就报错"，而是 b 想要 a.x 时，a 还没执行到定义 x 的那一行

解决方案

# 方案 1：提取公共模块（首选，根治架构耦合）
# agent/types.py（新建）
class SearchResult:
    pass

# agent/core.py
from agent.types import SearchResult  # 从公共模块导入

# agent/tools.py
from agent.types import SearchResult  # 从公共模块导入

# 方案 2：延迟导入（局部解法，常用但治标不治本）
# agent/tools.py
def search(query: str):
    from agent.core import create_response  # 在函数内部导入，而不是顶层
    return create_response(query)

# 方案 3：使用 TYPE_CHECKING（仅用于类型注解，不解决运行时循环导入）
from __future__ import annotations
from typing import TYPE_CHECKING

if TYPE_CHECKING:
    from agent.core import Agent  # 只在类型检查时导入，运行时不导入

def bind(agent: Agent) -> None:
    ...
💡 from __future__ import annotations 是什么？

加了这一行后，函数签名里的类型注解（如 agent: Agent）在定义函数时不会立即求值，而以延迟形式保存；静态类型检查器仍能读取 if TYPE_CHECKING: 中的导入，因此普通运行路径不会触发该导入。但这不等于运行时永远不需要名称：若代码调用 typing.get_type_hints() 等去解析注解，Agent 仍必须能在提供的 globalns/localns 或模块命名空间中解析，否则会报错。

最佳实践：让当前运行时依赖保持单向

一个决策：现有文件之间是否出现反向运行时依赖？当前项目的实际方向应为 agent.__init__ → agent.core → agent.schemas，同时 agent.__init__ → agent.schemas；agent.schemas 不应反向导入上层模块。

什么时候会遇到：给现有包增加功能或 re-export 时，需要确认没有把底层数据模型连回入口或业务逻辑。

❌ 为读取 Message 让底层反向依赖
# agent/schemas.py
from agent.core import create_response

# 业务仍调用同一个公开入口
from agent import create_response

同样要创建响应，却让数据模型反向依赖已经使用它的业务模块，形成运行时闭环。

✅ 下沉数据模型，公开入口只向下依赖
# agent/core.py
from .schemas import Message

# agent/__init__.py
from .schemas import Message
from .core import create_response

# 业务调用保持不变
from agent import create_response

对调用方仍是同一个 create_response，但数据模型位于依赖图底部；当前项目没有 tools.py，检查也不假设它存在。

💡 面试常见问题：

"如何诊断和解决 Python 循环导入？"

答：先看 ImportError 或 AttributeError 的堆栈，找到部分初始化期间过早访问的名称或属性；循环本身也可能完成，并非检测到环就报错。解决方法：优先提取公共模块根治耦合；延迟导入是常见的局部解法；TYPE_CHECKING 条件导入只适用于纯类型依赖，运行时解析注解时仍要保证名称可解析。

6. import 的性能考量

__init__.py 只在包首次被 import 时执行一次；之后同一进程里再 import agent，会直接命中 sys.modules 缓存，不会重复执行（显式 importlib.reload() 等特殊情况除外）。但"只执行一次"不代表没有代价——如果 __init__.py 里 re-export 了很多重模块，那么第一次 import agent 时就会把这些模块全部加载一遍，拖慢启动速度。

# ❌ 不好的做法：在 __init__.py 中导入太多东西
# agent/__init__.py
from .core import create_response
from .tools import search, calculator, weather, file_reader, ...
from .schemas import Message, ToolCall, Response, ...
from .utils import helper1, helper2, helper3, ...
# 首次 import agent 会把这些 re-export 的模块全部加载一遍

# ✅ 好的做法：只导出核心接口
# agent/__init__.py
from .core import create_response
from .schemas import Message
__all__ = ["create_response", "Message"]
# 用户按需导入：from agent.tools import search

"Python import 的性能优化有哪些方法？"

答：1）保持 __init__.py 轻量；2）使用延迟导入；3）避免循环导入；4）按需导入而不是一次性导入所有模块。

思考题

先自己想，再点开对答案。答案均在真实 agent-hello 项目里跑过验证。

Q1如果把 from agent.schemas import Message 改成 from .schemas import Message，在 core.py 中能工作吗？为什么？

看你怎么运行它——「作为包导入」能，「当脚本直接跑」不能。

from .schemas import 是相对导入，那个 . 表示"当前包"。它要工作，Python 必须知道 core.py 属于哪个包（即 __package__ 有值）。

· ✅ 作为包被导入时（import agent.core / 从 main.py 里 from agent.core import …）：Python 知道它在 agent 包内，. 解析成 agent，正常工作。

· ❌ 直接把文件当脚本跑（python agent/core.py）：此时 __package__ 为空、__name__ 变成 "__main__"，没有"当前包"可参照，报错 ImportError: attempted relative import with no known parent package。

结论：包内模块之间用相对导入（from .schemas import）是推荐写法，但前提是这个包始终「被导入」而非「被直接运行」。要能直接跑的入口文件（如 main.py）才用绝对导入。

Q2如果在 tests/test_core.py 中导入 agent.core，Python 怎么找到它？

Python 按 sys.path 从前到后逐个目录找名叫 agent 的包，找到就停。

导入 agent.core 时，Python 遍历 sys.path（一个目录列表），在每个目录下找 agent/ 这个带 __init__.py 的包；命中后再进去找 core.py。实测命中的是项目根 agent-hello/ 下的 agent/core.py——前提是项目根必须在 sys.path 里。

关键就在这个前提：sys.path[0] 取决于你怎么启动。python tests/test_core.py 会把 sys.path[0] 设成脚本目录 tests/（那里没有 agent/）→ 报 ModuleNotFoundError: No module named 'agent'。让项目根进 sys.path 的正确做法：在项目根用 python -m tests.test_core，或 pytest 配 pythonpath=["."]。

一句话：能不能找到，不看文件在哪，看项目根在不在 sys.path 里。（这正是你刚踩的 ModuleNotFoundError 那个坑，详见 L02 答疑。）

Q3如果 core.py 和 tools.py 互相导入，会发生什么？怎么解决？

不一定报错；关键看初始化期间是否过早读取尚未绑定的名称或属性。

当 core.py 顶部 from tools import …、而 tools.py 顶部又 from core import …：导入 core 时它先去导 tools，tools 会拿到尚未执行完的 core。若此时执行 from core import make 且 make 还未绑定，常见 ImportError；若先 import core 再访问尚未绑定的 core.make，可能是 AttributeError。若双方都没有提前取用缺失名称，循环也可能完成。

三种解法：

① 提取公共模块（首选，最治本）——把两边都依赖的东西（如 schemas.py 里的 Message）抽到第三个模块，core 和 tools 都只依赖它，环就断了。这是最治本的设计。
② 延迟导入（常见但不是架构根治）——把 import 从模块顶部挪进真正用到它的函数体内，等函数被调用时模块早已初始化完。实测可解，但只是绕开了问题，没有解决模块间耦合过紧的根本原因。
③ TYPE_CHECKING 条件导入——若互相导入只是为了类型注解，用 if TYPE_CHECKING: 包住 import，配合延迟注解；但若运行时调用 get_type_hints() 解析注解，仍须提供可解析的名称。

根治思路：循环导入往往是架构信号——两个模块耦合太紧。优先想①的"抽公共模块"，而不是硬用延迟导入打补丁；延迟导入常见，但只是局部应急手段。

    completed = subprocess.run(
        [sys.executable, "-c", source], cwd=root, env=env,
        capture_output=True, text=True, encoding="utf-8", check=False,
    )
    assert completed.returncode == 0, completed.stderr
    return completed.stdout, completed.stderr


def module_name(path):
    name = ".".join(path.with_suffix("").parts)
    return name.removesuffix(".__init__") or "miniagent"


def package_edges(root):
    paths = sorted((root / "miniagent").glob("*.py"))
    known = {module_name(path.relative_to(root)) for path in paths}
    edges = set()
    for path in paths:
        source = module_name(path.relative_to(root))
        tree = ast.parse(path.read_text(encoding="utf-8"), filename=str(path))
        for node in ast.walk(tree):
            if isinstance(node, ast.Import):
                targets = [alias.name for alias in node.names]
            elif isinstance(node, ast.ImportFrom):
                package = source if path.name == "__init__.py" else source.rsplit(".", 1)[0]
                if node.level != 1:
                    targets = [node.module or ""]
                else:
                    base = ".".join(filter(None, (package, node.module or "")))
                    targets = [
                        f"{base}.{alias.name}" if f"{base}.{alias.name}" in known else base
                        for alias in node.names
                    ]
            else:
                continue
            edges.update((source, target) for target in targets if target in known and target != source)
    return edges


def assert_acyclic(edges):
    graph = {}
    for source, target in edges:
        graph.setdefault(source, set()).add(target)
    visiting, visited = set(), set()
    def visit(node):
        assert node not in visiting, f"FAIL: 检测到反向边形成的环: {node}"
        if node in visited:
            return
        visiting.add(node)
        for target in graph.get(node, ()):
            visit(target)
        visiting.remove(node)
        visited.add(node)
    for node in graph:
        visit(node)

知识图谱

Python 执行流程
├── .py 源代码
│   └── 编译为字节码
│       ├── 主模块（直接运行）：只在内存中编译，不生成自己的 .pyc
│       └── 被 import 的模块：通常缓存到 __pycache__
└── PVM 逐条执行字节码

__name__ 机制
├── 直接运行 → __name__ == "__main__"
└── 被 import → __name__ == "模块名"
    └── 用途：保护直接运行的代码

模块与包
├── 模块 = 一个 .py 文件
├── 包 = 包含 __init__.py 的目录（须是合法标识符，项目目录名不是包名）
│   ├── __init__.py：首次 import 时执行一次，可定义公开接口
│   └── __all__：控制 from package import *
└── 命名空间包（3.3+）：__init__.py 可选但推荐

import 机制
├── 查找顺序：sys.modules 缓存 → 内置模块（极少）→ sys.path（标准库/第三方/项目）
├── 绝对导入：from agent.core import run（推荐）
├── 相对导入：from .core import run（包内使用）
├── import / from-import 都可放顶层，延迟导入取决于循环依赖/启动成本/可选依赖
└── 虚拟环境改变 sys.path 优先级

循环导入
├── 机制：A 与 B 可形成循环并完成；过早访问部分初始化模块中未绑定的名称/属性才失败
├── 方案 1（首选）：提取公共模块
├── 方案 2（常见局部解法）：延迟导入（函数内部 import）
└── 方案 3（仅类型注解）：TYPE_CHECKING 条件导入

面试常见问题

Q1：Python 的执行流程是什么？

答：Python 先将源代码编译为字节码，再由 Python 虚拟机（PVM）逐条执行。直接运行的主模块通常只在内存里编译一次，不会为自己生成 .pyc；而被 import 的模块，字节码通常会缓存到所在目录的 __pycache__ 里，下次 import 若源文件未改则直接加载缓存。

Q2：__name__ == "__main__" 的作用是什么？

答：用于判断文件是被直接运行还是被 import。直接运行时 __name__ 是 "__main__"，被 import 时是模块名。常用于保护测试代码或启动代码，防止被 import 时意外执行。

Q3：模块和包的区别？

答：模块是一个 .py 文件，包是包含 __init__.py 的目录，且目录名必须是合法的 Python 标识符（比如不能带连字符）。项目根目录只是普通文件夹，不等于 Python 包名。Python 3.3+ 引入了命名空间包，__init__.py 不再是必须的，但仍然推荐使用。

Q4：什么是循环导入？怎么解决？

答：两个模块互相导入就形成循环，但循环不一定失败；若初始化期间过早访问对方尚未绑定的名称或属性，依导入形式可能报 ImportError 或 AttributeError。解决方法：1）提取公共模块（首选，根治耦合）；2）延迟导入（函数内部 import，常见但只是局部解法）；3）使用 TYPE_CHECKING 条件导入（仅用于类型注解；运行时解析注解仍需名称可解析）。

Q5：import 的查找顺序是什么？

答：1）sys.modules 缓存（已导入的模块）；2）真正的内置模块（数量很少，如 sys）；3）sys.path 上的模块（当前目录/项目根、PYTHONPATH、标准库如 json、site-packages 第三方包）。虚拟环境会改变 sys.path 的优先级。

Q6：__all__ 的作用是什么？

答：定义包的公开接口，控制 from package import * 的行为。只有在 __all__ 列表中的名字才会被导出。显式导入（from package import name）不受影响。

总结

  • Python 先编译为字节码，再由 PVM 执行；主模块不缓存 .pyc，被 import 的模块通常会
  • __name__ == "__main__" 保护直接运行的代码

  • 相对导入只能在包内部使用，main.py 用绝对导入
  • 循环导入优先提取公共模块根治，延迟导入是常见但局部的解法
  • __all__ 控制包的公开接口
  • __init__.py 只在首次 import 时执行，保持轻量避免拖慢启动速度
