第六阶段 · LangGraph 与 MCP45分钟

先走本地 MCP stdio

让证据跨过进程边界，不让权限跟着扩大

为什么这课重要？

沿用 L54 的问题「导出文件有效期？」。答案仍要靠 KB-01 支持，但这次证据不再由宿主直接查表，而是从本地子进程取回。换了取证方式，不能把「接口返回了」当成「证据可以使用」。

学习目标

能读懂指定版本的 stdio 轨迹；能分别验证读取入口、结果结构和任务作用域；能定位失败发生在传输、协议、工具还是宿主验收。

1. 先划边界：谁取证，谁决定交给模型什么？

用户问导出文件保留多久，并没有授权读取本机任何目录，也没有要求写草稿。宿主（host）管理任务、用户许可和模型上下文；本课由固定代码把这个问题映射为 export 作用域和 KB-01 来源。客户端（client）在宿主内，一对一连接一个服务端：启动课程子进程、编码请求、按 ID 对齐响应、超时后收尾。服务端（server）在子进程内，公布能力、认工具名、校验参数，再从内存夹具取证。宿主可以拥有多个客户端，但某个服务端不会因此获得别的服务端结果或完整对话。这里父子真跨进程，选工具与组织证据由代码演示，没有模型参与。

接口通常由谁选、拿来做什么同一知识库怎么选
工具（tool）模型可建议调用；宿主控制是否暴露和执行。用 tools/list 发现，用 tools/call 传入参数并得到结果。问题需要在回答前按来源 ID 查一次，选只读 read_evidence，便于观察是哪个参数触发读取。
资源（resource）应用决定取哪些上下文。用 resources/list 发现，以 URI 通过 resources/read 读取。如果页面只是让用户勾选一条已知政策作为附件，可以把政策建成资源，不必把每段文字都包装成工具。
提示模板（prompt）通常由用户选择何时使用。用 prompts/list 发现，用 prompts/get 取服务端定义的模板内容。「按来源写保留期答复」可以是模板；它约束答复形式，并不等于已读 KB-01，也不会授予读取权限。

本实验只公布工具能力，没有资源读取接口或模板。发现工具只是看见目录，capabilities.tools 也只是协议能力，不是授权。这里的 scope 是业务夹具的分区，不是 OAuth scope 或真实身份；来源 ID 只有和分区配对才有意义。宿主从任务决定分区，不从工具结果、模型建议、进程 ID 或自报的客户端名称推导权限。

2. 跟一次真实轨迹：从启动到 KB-01

客户端使用当前 sys.executable 和固定的课程源码绝对路径启动子进程，不经过 shell，也不把用户文字当命令、路径或环境变量。父进程写子进程的 stdin，从子进程的 stdout 读响应；每条消息是一行 UTF-8 的 JSON-RPC，实际换行符只作分隔，字符串里的换行应由 JSON 转义，不能把排版后的多行 JSON 发到线上。日志另走 stderr，客户端单独排空；诊断有内容不等于调用失败。版本信息在消息体，不设 HTTP 头。

本课固定 MCP 2026-07-28。每条请求的 params._meta 都带 io.modelcontextprotocol/protocolVersion 和 io.modelcontextprotocol/clientCapabilities，也带上建议提供的 io.modelcontextprotocol/clientInfo。先发 server/discover（ID 1），确认响应中的 supportedVersions 和 capabilities.tools；服务端必须实现这个方法，对客户端则是可选的发现，不是建立会话的握手。接着 tools/list（ID 2）确认唯一允许的工具和本地预期的输入、输出契约。这两条成功响应都带 ttlMs: 0 与 cacheScope: "public"：目录不因用户而变，且实验不复用缓存。即使走 stdio，也须按 MCP 缓存规范填写这两个提示；它们不替代权限检查。发现结束后也不能省略下一条的版本或能力。

这是实测 ID 3 的两条线帧（上下为请求、响应；每行仍是一个完整 JSON 值）：

{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"read_evidence","arguments":{"scope":"export","source_id":"KB-01"},"_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28","io.modelcontextprotocol/clientInfo":{"name":"l57-host","version":"1.0"},"io.modelcontextprotocol/clientCapabilities":{}}}}
{"jsonrpc":"2.0","id":3,"result":{"resultType":"complete","isError":false,"content":[{"type":"text","text":"{\"scope\":\"export\",\"source_id\":\"KB-01\",\"excerpt\":\"导出文件生成后保留 7 天。\"}"}],"structuredContent":{"scope":"export","source_id":"KB-01","excerpt":"导出文件生成后保留 7 天。"},"_meta":{"io.modelcontextprotocol/serverInfo":{"name":"l57-evidence","version":"1.0"}}}}

客户端对上响应 ID 才交回宿主。宿主检查结果类型、错误标记，以及 structuredContent 的字段、类型、长度和预期的分区／来源；只投影 source_id 与 excerpt，不把请求元数据、原始结果、文本副本或诊断日志塞进模型上下文。若将来接模型，摘录仍是待引用的数据，不是指令；结构正确也不保证内容真实。content 中的 JSON 文本是兼容用的副本，本课不在结构缺失时降级信任它。

怎样读旧教程：2025-11-25 先发 initialize，在它的 params 中协商版本，再发 notifications/initialized。本课没有这两帧，也不自动降级。若现代形状中版本不受支持，按 -32022 的 supported 列表看是否有共同版本；看到这个错误不代表对方是旧服务端。官方 Python SDK 稳定版 2.3.0 已支持现代版本，1.x 是旧握手系列；本环境未获准安装外部 SDK 验证 Windows 运行，因此用已实测的标准库教学子集，不是通用 SDK，也不声称完整合规。

3. 失败时先看哪一层？

ID 4 把 export 配上 PICKUP-01：两个值分别出现在枚举里，却不是合法的一对。调用外壳可解析，工具返回 resultType: "complete" 加 isError: true，没有结构化证据。ID 5 的工具名不存在，返回 JSON-RPC error.code: -32602；把 arguments 直接传成数组也是协议错误，但原因是外壳不合法。不能把这三种情况都记成「证据为空」，否则会把参数错误误诊成缺政策。三次调用中，真实读取入口的审计只有 evidence-read export KB-01 一条；验证的是拒绝发生在读取前，不只是报错文案。

如果完全收不到一行，在父端区分超时和提前 EOF，检查是否刷出了完整一行；如果首行是日志或 ID 不对，先排查输出通道或对应关系，不重试业务。实验为每次写入和等响应合计留 3 秒；失败就结束这次运行。收尾先关闭输入给子进程 EOF，再限时等它退出，必要时终止、强杀并等待回收。真实系统还需设计每请求取消、重启和重试策略；此处不把关闭整个子进程说成已实现 notifications/cancelled。

最佳实践：要不要把本地取证拆成 stdio？

适用：证据服务需要独立运行或被多个支持 MCP 的宿主复用，且可把入口缩成可审查的参数和结果。边界：若同一 Python 应用内部已能直接查固定表，拆进程不自动提高正确率或隔离权限；需要远端接入、多人授权或多路请求时，本实验也不是现成方案。

误判：列得到就开放，答得像就使用

把清单中的所有工具都交给模型，见到带 KB-01 的文本就采纳。同名证据可能属于另一个分区；缺少结构或调用其实失败时，漂亮的文字仍会混进答案。

对照：先绑定调用，再绑定结果

固定可信程序和允许的工具，服务端在读之前验参数配对；宿主在投影前用独立的任务预期验作用域和来源，再拿同 ID、错分区的结果测试验收门。

取舍：拆开后能独立看协议轨迹和读取日志，也引入启动、编码、超时和版本匹配的成本。课程严格比对单工具契约，变化即停；正式集成通常只筛选允许的工具，再用版本化契约接受兼容变化，不必因无关工具加入就断开整个服务。stdio 是传输，不是 OS 沙箱。

  1. 记录固定路径、协议版本、允许的工具和每个任务所需来源。
  2. 同时查响应与读取审计：有效调用读一次，不合法的调用不读。
  3. 在迁移自检中保留正确结构，只替换分区，确认宿主不输出错证。

结果诊断：拒绝响应伴随读取日志，说明门放在动作后；无额外读取但已接纳同 ID 的异区结果，说明宿主只验了形状或 ID。

Q 调用返回匹配的 JSON-RPC ID，结构有效且来源都是 PICKUP-01，但当前任务是北校区、返回的却是南校区。最能防止误用的做法是什么？
ID 对齐只能识别哪次请求收到该响应，枚举也只描述哪些值可能有效；都不能证明内容属于本次任务的分区。

展开参考：轨迹答案与可复跑验收

ID 3 为 complete、isError: false，给模型侧留下来源与摘录，读 1 次。ID 4 是 complete、isError: true；ID 5 是 -32602；均读 0 次。审计来自子进程 stderr，只有 ID 3 的业务读取。

import asyncio
import runpy
from pathlib import Path

# 在仓库根运行；路径固定，不来自调用参数。
lab = runpy.run_path(str(Path("code/phase6-langgraph-mcp/stdio-lab/lab.py")))
report = asyncio.run(lab["worked_report"]())
assert report["model_view"] == {"source_id": "KB-01", "excerpt": "导出文件生成后保留 7 天。"}
assert report["bad"]["isError"] is True and "structuredContent" not in report["bad"]
assert report["unknown"]["code"] == -32602
for (request, reply), method in zip(report["trace"][:2], ("server/discover", "tools/list"), strict=True):
    assert request["method"] == method
    assert (reply["result"]["ttlMs"], reply["result"]["cacheScope"]) == (0, "public")
assert report["audit"] == ["evidence-read export KB-01"]
assert report["returncode"] == 0

本课最佳实践验收：同编号的校区领取政策

新场景是器材领取，不再使用 KB-01。北校区和南校区在各自目录都用 PICKUP-01，地点不同。用同一个子进程按各自分区读取两条，确认都可用于自己的任务。模拟宿主缓存只按来源编号取快照，把真实的南校区结果当作北校区候选。不改字段、不造坏 JSON，也不发第三次读取；比较只验形状与再验任务绑定的结果。

面试自查

先合上答案，按「结论 → 理由 → 如何验证」作答，再展开追问。

Q1宿主、客户端与服务端中，谁决定给模型什么，谁真正取证？

参考回答：宿主选允许的工具和任务分区，校验并投影结果；客户端维护与单个服务端的协议连接；服务端校验工具名与参数后取证。用请求参数、读取入口审计和宿主投影三处对账，不看一条成功响应就下结论。

追问：用户在界面选了「保留期答复」模板，可以跳过读取 KB-01 吗？

答题要点：不能。模板是怎么组织消息，不是答案证据。如果政策以资源暴露，宿主仍要读取并验来源。

Q2发现成功后，去掉第二条请求的 _meta，应该发生什么？

参考回答：现代版本每条请求自带版本与客户端能力。缺必填项应回 -32602，不能从发现响应补齐；用同个子进程先发现，再发无元数据和有元数据的两次列表对照。

追问：发现返回 -32022，是否该直接发 initialize？

答题要点：不该。这是现代错误，有可支持的版本列表就找交集。本课只实现一个版本，无交集就停止；旧握手不是现代请求的补丁。

Q3坏参数已报错，但子进程还多出一条读取日志，能过验收吗？

参考回答：不能，拒绝必须发生在证据读取之前。把日志记在实际读取入口，同一次运行同时做有效对照与坏参数、未知工具两种拒绝，核对只有有效对照真的到达入口。

追问：把日志从 stderr 重定向到 stdout，客户端解析为什么可能失败？

答题要点：stdout 每行必须是有效的协议消息。普通日志会让 JSON 解析或响应信封检查失败，不能通过略过任意非 JSON 行来假装协议正常。

Q4北校区拿到来源编号相同的南校区证据，为什么请求 ID 和输出 schema 都不能证明它属于本次任务？

参考回答：请求 ID 只关联帧，schema 只证明字段形状。宿主用任务自己的分区和来源约束绑定结果；拿真实南区响应做负例，保留其结构和编号，证明只验形状时会误收。

追问：若分区吻合但摘录内容可疑，可以当系统指令执行吗？

答题要点：不可以。宿主只把合适的字段当数据使用；分区与结构检查不是内容真实性或指令授权。真实使用还要审查来源和披露范围。
