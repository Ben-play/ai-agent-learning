Pydantic 数据验证

Pydantic 把类型变成运行时校验 — 也是生成 Tool Schema 的标准工具

💡 为什么这课重要？

L13 说过：类型提示运行时不校验。Pydantic 补上这一环——外部数据（LLM 输出、用户输入、API 响应）进来时按 v2 规则和模型配置校验、可能转换，失败则报错。数据脏了立刻拦住，而不是在下游炸出诡异 bug。

更重要的是：Pydantic 能一键导出 JSON Schema。这正是喂给 LLM 的"工具说明书"。L11 你手写的 @tool，真实框架（LangChain、OpenAI SDK、Pydantic AI）就是用 Pydantic 来做的。这一课把 Part B 那条 @tool → Schema 线彻底闭环。

※ 本课代码基于 Pydantic v2，先安装：uv add pydantic（或 pip install pydantic）。v2 的方法名和 v1 不同（如 .model_dump() 取代 .dict()）。

学习目标

完成本课后，你将能够：

  • 用 BaseModel 定义带校验的数据模型
  • 用 Field 加默认值、描述、约束（范围/长度）
  • 用 @field_validator 写自定义校验
  • 序列化：model_dump() / model_dump_json()
  • 导出 JSON Schema 作为 Tool Schema，并说清 dataclass vs Pydantic

1. BaseModel：按规则校验，并按配置决定是否转换

from pydantic import BaseModel

class Message(BaseModel):
    role: str
    content: str
    tokens: int = 0

# 传进来自动按类型校验
m = Message(role="user", content="你好", tokens="42")
print(m.tokens)          # 42  ← 字符串 "42" 被自动转成 int 42

# 类型不对且无法转换 → 抛 ValidationError
Message(role="user", content="hi", tokens="abc")
# ❌ ValidationError: tokens 不是有效整数

和 dataclass 最大的区别：Pydantic 会在创建实例时校验。脏数据在门口就被拦下，这对"消化 LLM 不可控输出"至关重要。

Q Pydantic 的 BaseModel 相比 @dataclass，核心多了什么？
两者都能定义数据模型、都有 __repr__/__eq__。Pydantic 的关键增值是创建实例时自动校验类型、尝试转换、失败抛 ValidationError——dataclass 完全不校验。所以外部/不可信数据用 Pydantic。

2. Field：默认值、描述与约束

from pydantic import BaseModel, Field

class SearchInput(BaseModel):
    query: str = Field(..., description="搜索关键词", min_length=1)
    max_results: int = Field(5, ge=1, le=50, description="返回条数，1~50")
    #                        ↑默认值  ↑约束：>=1 且 <=50

SearchInput(query="ai", max_results=100)
# ❌ ValidationError: max_results 必须 <= 50
  • Field(...) 里的 ...（Ellipsis）表示必填；给具体值就是默认值
  • ge/le（>=/<=）、gt/lt、min_length/max_length 等是内置约束
  • description 会进入 JSON Schema —— LLM 就靠它理解每个参数是干嘛的
🔑 Agent 开发关联：

description 和约束不只是校验，它们会写进工具的 JSON Schema。LLM 决定"要不要调这个工具、参数填什么"时，读的就是这些描述。写清楚 Field 描述 = 提升工具调用准确率，这是工具工程（Phase 3.4）的关键技巧。

3. 自定义校验与嵌套模型

上一节 Field 能表达"类型、范围、必填"这类通用约束。但有些规则 Field 写不出来——比如"工具名必须在已知列表里"、"表达式不能含危险字符"。这时用 @field_validator 写自己的校验函数；再看模型如何嵌套（一个模型的字段是另一个模型），对应 LLM 那种层层嵌套的响应。

@field_validator：写自己的校验规则

from pydantic import BaseModel, field_validator

class ToolCall(BaseModel):
    name: str

    @field_validator("name")
    @classmethod
    def must_be_known(cls, v: str) -> str:
        allowed = {"search", "calc", "weather"}
        if v not in allowed:
            raise ValueError(f"未知工具: {v}")
        return v

ToolCall(name="hack")   # ❌ ValidationError: 未知工具: hack

嵌套模型：模型套模型

class Function(BaseModel):
    name: str
    arguments: dict

class ToolCallEnvelope(BaseModel):
    id: str
    function: Function            # 字段本身是另一个模型

# 传嵌套 dict，Pydantic 会递归校验
tc = ToolCallEnvelope(id="c1", function={"name": "search", "arguments": {"q": "x"}})
print(tc.function.name)          # search

4. 序列化 & 导出 JSON Schema

from pydantic import BaseModel, Field

class SearchInput(BaseModel):
    query: str = Field(..., description="搜索关键词")
    max_results: int = Field(5, ge=1, le=50)

obj = SearchInput(query="ai agents")

# 序列化（v2 方法名）
obj.model_dump()          # {'query': 'ai agents', 'max_results': 5}   → dict
obj.model_dump_json()     # '{"query":"ai agents","max_results":5}'    → JSON 字符串

# 导出 JSON Schema —— 这就是喂给 LLM 的"工具参数说明书"
SearchInput.model_json_schema()
# 输出节选（为便于阅读，省略模型/字段 title 等键）：
# {
#   'type': 'object',
#   'properties': {
#     'query': {'type': 'string', 'description': '搜索关键词', ...},
#     'max_results': {'type': 'integer', 'default': 5,
#                     'minimum': 1, 'maximum': 50, ...}
#   },
#   'required': ['query'],
#   ...
# }
🔑 Agent 开发关联：

model_json_schema() 输出的是模型参数的标准 JSON Schema，但 OpenAI 和 Anthropic 外层字段不同（L11 提过）：OpenAI 把它塞进 function.parameters；Anthropic 直接塞进顶层 input_schema。同一份 Schema，两家各自的 adapter 负责套外壳，字段名不能混用。回想 L11 你用 inspect 手写的简易 Schema —— 真实框架就是用 Pydantic 生成这份标准、带校验、带描述的 JSON Schema，再交给各厂商 adapter。

最佳实践：Schema 负责描述，模型实例负责校验；跨信任边界的原始参数必须先经 Pydantic v2 再执行工具

适用：参数来自 LLM 工具调用、HTTP 请求、消息队列、CLI 或其他进程，执行器会读文件、写数据库、发请求或产生其他副作用。把收到的原始 mapping 视为不可信数据，先用 Model.model_validate(raw_args) 得到已校验模型，再调用工具。不适用：调用方已经持有同一模型类创建并校验过的实例，且对象没有被转回原始 dict、没有再次跨越信任边界；这时可直接传递该实例，不必重复校验。

❌ 只导出 Schema，原始参数直接执行
entry = {
    "input_schema": TransferInput.model_json_schema(),
    "executor": execute_transfer,
}

# 参数虽按 Schema 提供给 LLM，返回时仍只是原始 dict
result = entry["executor"](raw_args)

这在请求端已经启用结构化约束时看似省事，但仅导出 Schema 不会执行 Python validator；validator 会在模型验证/构造期间运行，启用 validate_assignment=True 时也可能在字段赋值时运行。其他调用方、旧客户端或手工重放的原始参数仍可能绕过模型校验。

✅ 边界先 model_validate，再执行
entry = {
    "model": TransferInput,
    "executor": execute_transfer,
}

validated = entry["model"].model_validate(raw_args)
result = entry["executor"](validated)

registry 保存模型类。只有 model_validate 成功返回的模型实例能进入执行器；ValidationError 在副作用之前中断链路。

为什么更优：model_json_schema() 读取类定义并生成描述，不执行 @field_validator；validator 在模型验证/构造期间运行，启用 validate_assignment=True 时也可能在字段赋值时运行。这里的 model_validate() 解析原始 mapping、运行约束和 validator。把这一步放在执行器前，因果上阻止无效参数触达副作用，保护正确性、数据完整性、可靠性与错误可诊断性。实际代价是每次边界调用多一次模型解析与对象分配，还要维护 Pydantic 依赖、模型和错误映射；高吞吐路径应基准测试，而不是跳过校验。当数据已是可信的同类模型实例时直接复用；只需校验列表、联合类型等非模型形状时可改用 Pydantic TypeAdapter；依赖受限且契约极简单时可用一段集中、经过测试的显式 parser，但不能用“已经导出 Schema”替代运行时验证。

动手自检（Pydantic v2，离线且整块复制即可运行）：
from pydantic import BaseModel, ValidationError, field_validator

validator_calls = 0
executor_calls = 0


class TransferInput(BaseModel):
    destination: str

    @field_validator("destination")
    @classmethod
    def require_account_prefix(cls, value: str) -> str:
        global validator_calls
        validator_calls += 1
        if not value.startswith("acct-"):
            raise ValueError("destination 必须以 acct- 开头")
        return value


def execute_transfer(validated: TransferInput) -> str:
    global executor_calls
    executor_calls += 1
    return f"sent:{validated.destination}"


def run_tool(raw_args: dict[str, object]) -> str:
    validated = TransferInput.model_validate(raw_args)
    return execute_transfer(validated)


schema = TransferInput.model_json_schema()
assert schema["properties"]["destination"]["type"] == "string"
assert validator_calls == 0       # Schema 导出没有执行 validator
assert executor_calls == 0

try:
    run_tool({"destination": "external"})
except ValidationError:
    pass
else:
    raise AssertionError("无效原始参数应被 Pydantic 拒绝")

assert validator_calls == 1       # model_validate 确实执行了 validator
assert executor_calls == 0        # 无效输入没有触达执行器
assert run_tool({"destination": "acct-42"}) == "sent:acct-42"
assert validator_calls == 2
assert executor_calls == 1        # 有效输入只执行一次

结果诊断：无输出且退出码为 0 即通过。Schema 导出后 validator_calls 非 0，说明导出路径意外构造了实例；无效输入后 executor_calls 非 0，说明校验门没有位于副作用之前；最终计数不是 validator 两次、executor 一次，则验证或执行发生了遗漏/重复。

Q Pydantic v2 里把模型转成 dict，用哪个方法？
Pydantic v2 用 model_dump()（转 dict）和 model_dump_json()（转 JSON 字符串），并用 model_json_schema() 导出 Schema。这些取代了 v1 的 .dict()/.json()/.schema()——面试和实战都要认准 v2 名字。

5. dataclass vs Pydantic：怎么选

场景选择
内部纯数据容器、不接触外部输入@dataclass（轻、快、零依赖）
校验 LLM 输出 / 用户输入 / API 响应Pydantic（按模型配置与 v2 规则校验，并可能转换）
定义工具参数、要导出 JSON Schema 喂 LLMPydantic（model_json_schema）
配置模型（带默认值、约束）Pydantic（Field 约束）

一句话：数据一旦跨越"信任边界"（来自外部或要给外部），就用 Pydantic；纯内部传递用 dataclass。

知识图谱

Pydantic v2（pip install pydantic）
├── BaseModel → 按 v2 规则/模型配置校验，可能转换（失败抛 ValidationError）
├── Field(默认/描述/约束 ge le min_length...) → 描述进 Schema
├── @field_validator + @classmethod → 模型验证/构造时执行；validate_assignment=True 时也可能在赋值时执行
├── 嵌套模型 → 递归校验
├── 序列化：model_dump() / model_dump_json()
├── ConfigDict(strict=True) / Field(strict=True) → 需要时关闭相应宽松转换
└── model_json_schema() → 导出参数 Schema（只是描述，不执行 validator）★

Tool Schema 落地到厂商请求
├── model_json_schema() 结果是"中立"参数 Schema
├── OpenAI → 塞进 function.parameters
├── Anthropic → 塞进顶层 input_schema
└── 执行前必须 Model(**raw_args) 重新构造实例做校验，registry 需保存模型类

dataclass vs Pydantic
├── 内部数据 → dataclass（轻、零依赖）
└── 跨信任边界(LLM/用户/API)、要 Schema → Pydantic

实战练习

练习：为 3 个工具设计 Pydantic Schema，并适配两家厂商

为三个真实工具定义 Pydantic 输入模型，导出 JSON Schema，再分别包装成 OpenAI / Anthropic 的工具定义格式。先自己写，再看答案。

任务清单

  1. SearchInput：query（必填、非空）、max_results（默认 5、1~50）、lang（可选，Literal["zh","en"]，默认 "zh"）
  2. ReadFileInput：path（必填）、encoding（默认 "utf-8"）
  3. CalcInput：不要用自由表达式字符串（不安全也难校验）；改用明确字段 a: float、b: float、operation: Literal["add","subtract","multiply","divide"]
  4. 写一个 calculate(validated: CalcInput) 执行器：用 if/elif 按 operation 分支计算，不使用 eval；除数为 0 时抛业务级 ValueError（这是运行时业务错误，不是 Pydantic 校验错误）
  5. 对每个模型调用 model_json_schema() 生成中立条目 {"name", "description", "input_schema", "model"}；description 必须显式传入非空工具说明，model 存模型类本身供执行前重新构造校验
  6. 写 to_openai_schema(entry) / to_anthropic_schema(entry) 两个 adapter，分别对照 L11 的写法

from typing import Literal
from pydantic import BaseModel, Field

class SearchInput(BaseModel):
    query: str = Field(..., min_length=1, description="搜索关键词")
    max_results: int = Field(5, ge=1, le=50, description="返回条数 1~50")
    lang: Literal["zh", "en"] = Field("zh", description="结果语言")

class ReadFileInput(BaseModel):
    path: str = Field(..., description="文件路径")
    encoding: str = Field("utf-8", description="文本编码")

class CalcInput(BaseModel):
    a: float = Field(..., description="第一个操作数")
    b: float = Field(..., description="第二个操作数")
    operation: Literal["add", "subtract", "multiply", "divide"] = Field(..., description="运算类型")

def calculate(validated: CalcInput) -> float:
    a, b, op = validated.a, validated.b, validated.operation
    if op == "add":
        return a + b
    if op == "subtract":
        return a - b
    if op == "multiply":
        return a * b
    if op == "divide":
        if b == 0:
            raise ValueError("除数不能为 0")   # 业务错误，不是 ValidationError
        return a / b
    raise ValueError(f"未知运算: {op}")

# 每个工具显式提供清晰描述；model 类在执行前用于重新校验
TOOLS = {
    "search": (SearchInput, "按关键词搜索网页并返回限定条数的结果"),
    "read_file": (ReadFileInput, "按指定编码读取文本文件"),
    "calc": (CalcInput, "对两个数执行加、减、乘或除运算"),
}

def make_entry(name, model, description):
    description = description.strip()
    if not description:
        raise ValueError(f"工具 {name} 缺少 description")
    return {"name": name, "description": description,
            "input_schema": model.model_json_schema(), "model": model}

entries = {
    name: make_entry(name, model, description)
    for name, (model, description) in TOOLS.items()
}

def to_openai_schema(entry):
    return {"type": "function", "function": {
        "name": entry["name"], "description": entry["description"],
        "parameters": entry["input_schema"],       # OpenAI 叫 parameters
    }}

def to_anthropic_schema(entry):
    return {
        "name": entry["name"], "description": entry["description"],
        "input_schema": entry["input_schema"],     # Anthropic 直接叫 input_schema
    }

# --- 执行链路：Schema 导出 → LLM 回填参数 → 构造模型校验 → 执行 ---
entry = entries["calc"]
print(entry["description"])  # 对两个数执行加、减、乘或除运算
print(to_openai_schema(entry)["function"]["parameters"]["properties"].keys())
print(to_anthropic_schema(entry)["input_schema"]["properties"].keys())

raw_args = {"a": 3, "b": 4, "operation": "add"}   # 模拟 LLM 回填
validated = entry["model"](**raw_args)             # ← validator/类型校验在这里执行
print(calculate(validated))                        # 7.0

# Literal 非法值 → ValidationError（构造模型时拦下）
# CalcInput(a=1, b=2, operation="power")
# 除零 → 业务 ValueError（构造校验通过后，执行阶段拦下）
# calculate(CalcInput(a=1, b=0, operation="divide"))

思考题

先自己想，再点开对答案。

Q1为什么 CalcInput 改成 a/b/operation 字段，而不是接收一个自由表达式字符串？

【结论】因为"接收任意表达式字符串再想办法安全求值"这条路本身就很难做对；把参数收窄成明确的、类型受限的字段（a: float、b: float、operation: Literal[...]），执行器用 if/elif 分支计算，完全不需要对任意字符串求值，安全性和可预测性天然更高。

此前有一种常见但站不住脚的做法：字段是 expression: str，靠一个 @field_validator 检查"不包含 import 子串"就宣称"防住了注入/RCE"。这是虚假的安全承诺——字符串黑名单挡不住 eval 能触达的全部攻击面（例如不含 "import" 字样的属性链逃逸、内置函数滥用等），本课不采用、也不做这种承诺。

字符白名单（只允许数字和 + - * / . ( )）能在一定程度上收紧输入，但这仍然只是普通业务校验，不是通用 Python 沙箱；真正稳妥的做法是课程推荐方案：不接收自由表达式，改用 Literal 枚举 + 分支执行，从根上避免"对不可信字符串求值"这件事——本课示例全程不调用 eval。

Q2这三个模型导出的 Schema，和 OpenAI / Anthropic 工具定义分别是什么关系？

【结论】model.model_json_schema() 导出的是厂商中立的参数 JSON Schema，两家都直接复用这份 Schema 内容，但外层包装字段不同：OpenAI 把它放进 {"type":"function","function":{...,"parameters": schema}} 的 parameters；Anthropic 把它放进 {"name":...,"description":...,"input_schema": schema} 的 input_schema。不是两家都叫 parameters，也不是随便哪个字段名都能通用。

练习里 make_entry(name, model, description) 产出的中立条目 {"name","description","input_schema","model"} 就是这个对应关系的雏形。工具说明由注册者显式传入，去掉首尾空白后若为空就抛 ValueError，避免把缺少用途说明的工具交给 LLM；同一份 input_schema 再交给 to_openai_schema 和 to_anthropic_schema 分别套外壳。这正是 L11 你手写 registry 时讲过的 adapter 模式，这里用 Pydantic 生成的标准 Schema 替换掉手写的简易 Schema。

关键好处仍是单一真源：同一个 Pydantic 模型既负责运行时校验入参，又负责导出给 LLM 的 Schema。但要注意：model_json_schema() 本身不会执行任何 @field_validator；validator 在模型验证/构造期间运行，启用 validate_assignment=True 时也可能在字段赋值时运行。本例只有在执行工具前用 entry["model"](**raw_args) 重新构造实例，入参校验才真正发生。这也是为什么中立条目要额外存一份 model（模型类），而不能只存 input_schema 这份静态 dict。

本课最佳实践验收：在路由分发前验证原始数据

换到不同的 Dispatch/Route 场景：不复用上面的转账模型，独立验收“描述与验证分离”以及“无效原始数据零执行、有效数据恰好执行一次”。

操作清单

  1. 用 Pydantic v2 API 离线运行整段自检。
  2. 导出 Route Schema 后检查 validator 调用数。
  3. 提交非法原始 mapping 后检查 handler 执行记录。
  4. 提交合法原始 mapping，检查类型转换后的 handler 结果。
  5. 全部提交完成后检查 handler 的精确执行次数。
  6. 所有断言通过后打印验收标记。
通过标准
  • 离线执行成功，且调用的是 model_json_schema()/model_validate()。
  • Schema 导出对应 validator 调用数严格为 0。
  • 非法原始数据对应 handler 执行数严格为 0。
  • 合法数据把 priority="2" 转为整数；handler 用 type(priority) is int 证明后返回 queued:support。
  • handler 最终精确执行 1 次，唯一记录为 support:2。
  • 标准输出严格为一行 L14 ACCEPTED，且标记只出现 1 次。

from typing import Any

from pydantic import BaseModel, ValidationError, field_validator

validation_events: list[str] = []
execution_events: list[str] = []


class Route(BaseModel):
    topic: str
    priority: int

    @field_validator("topic")
    @classmethod
    def require_known_topic(cls, value: str) -> str:
        validation_events.append(value)
        if value not in {"billing", "support"}:
            raise ValueError("未知路由 topic")
        return value


class Dispatch:
    def __init__(self, handler: Callable[[Route], str]) -> None:
        self._handler = handler

    def submit(self, raw_route: dict[str, Any]) -> str:
        route = Route.model_validate(raw_route)
        return self._handler(route)


def handle(route: Route) -> str:
    assert type(route.priority) is int  # 不能用格式化字符串代理类型证据
    execution_events.append(f"{route.topic}:{route.priority}")
    return f"queued:{route.topic}"


schema = Route.model_json_schema()
assert set(schema["properties"]) == {"topic", "priority"}
assert validation_events == []
assert execution_events == []

dispatch = Dispatch(handle)
try:
    dispatch.submit({"topic": "unknown", "priority": 9})
except ValidationError as exc:
    assert "未知路由 topic" in str(exc)
else:
    raise AssertionError("非法 route 应在 handler 前失败")

assert validation_events == ["unknown"]
assert execution_events == []

result = dispatch.submit({"topic": "support", "priority": "2"})
assert result == "queued:support"
assert validation_events == ["unknown", "support"]
assert execution_events == ["support:2"]

print("L14 ACCEPTED")

结果诊断：标准输出严格为一行 L14 ACCEPTED 即通过。若 Schema 导出后已有验证事件，说明错误地在导出阶段实例化了模型；若非法 topic 留下执行事件，说明 handler 绕过了 model_validate；若 handler 的 type(route.priority) is int 失败，说明宽松转换没有产生契约要求的精确类型；若合法路径的执行事件不是唯一的 support:2，说明执行次数或记录结果不符合契约。需要拒绝字符串 "2" 而不是转换时，应为模型或字段启用 strict 模式。

阶段实践检查点：数据边界契约

把 L03 字段契约、L05 关键字绑定、L13 Literal 与 L14 Pydantic v2 串成一道执行前边界：原始 mapping 只有完整、无多余字段且值合法时，才进入关键字专用 handler。

操作清单

  1. 定义 Pydantic v2 输入模型，并在 dispatch 边界用显式字段集合拒绝缺失或额外字段。
  2. 分别提交缺字段、额外字段和非法 Literal 的 mapping。
  3. 用 model_validate() 验证后，以 **model_dump() 绑定关键字专用 handler。
  4. 最后提交合法 mapping，并核对 handler 的调用记录与整数精确类型。
通过标准
  • 缺字段/额外字段由显式字段契约拒绝，非法 Literal 由 Pydantic 拒绝；三组输入后 handler 调用数保持 0。
  • 合法 mapping 才进入 handler，且只进入 1 次。
  • handler 收到 type(retries) is int 的值，关键字绑定结果准确。
  • 标准输出只有检查点标记。

先独立完成：先自行定义 mapping 字段集合、Pydantic 模型和关键字专用 handler，并写出三组无效输入零副作用断言；完成后再展开参考验收程序。

参考验收程序（独立完成后展开，需 Pydantic v2）
from collections.abc import Mapping
from typing import Literal

from pydantic import BaseModel, Field, ValidationError

handler_calls: list[tuple[str, str, int]] = []
EXPECTED_FIELDS = {"query", "mode", "retries"}


class ToolRequest(BaseModel):
    query: str = Field(min_length=1)
    mode: Literal["fast", "safe"]
    retries: int = Field(strict=True, ge=0)


def handle_search(
    *, query: str, mode: Literal["fast", "safe"], retries: int
) -> str:
    assert type(retries) is int
    handler_calls.append((query, mode, retries))
    return f"search:{query}:{mode}:{retries}"


def dispatch(raw: Mapping[str, object]) -> str:
    actual_fields = set(raw)
    if actual_fields != EXPECTED_FIELDS:
        missing = EXPECTED_FIELDS - actual_fields
        extra = actual_fields - EXPECTED_FIELDS
        raise ValueError(f"field mismatch: missing={missing}, extra={extra}")
    validated = ToolRequest.model_validate(raw)
    return handle_search(**validated.model_dump())


invalid_requests = [
    {"query": "agents", "mode": "safe"},
    {"query": "agents", "mode": "safe", "retries": 1, "debug": True},
    {"query": "agents", "mode": "turbo", "retries": 1},
]

for raw in invalid_requests:
    try:
        dispatch(raw)
    except (ValueError, ValidationError):
        pass
    else:
        raise AssertionError(f"invalid mapping reached handler: {raw}")

assert handler_calls == []
assert dispatch({"query": "agents", "mode": "safe", "retries": 1}) == (
    "search:agents:safe:1"
)
assert handler_calls == [("agents", "safe", 1)]

print("P1 CHECKPOINT BOUNDARY-CONTRACTS PASSED")

结果诊断：若缺字段、额外字段或非法 Literal 后出现调用记录，说明边界验证位于 handler 之后或被绕过；若合法路径不能通过 **mapping 调用关键字专用签名，说明字段契约与函数签名不同步；若调用次数不是 1 或 retries 不是精确 int，说明执行链发生重复或类型契约被放宽。

面试常见问题

Q1：Pydantic 和 dataclass 的核心区别？

答：Pydantic 在创建实例时自动校验并转换类型、失败抛 ValidationError，还能导出 JSON Schema；dataclass 不校验。外部数据、工具 Schema 用 Pydantic，内部纯数据用 dataclass。

Q2：Pydantic v2 相比 v1 的方法名有什么变化？

答：主要是 .dict()→.model_dump()、.json()→.model_dump_json()、.schema()→.model_json_schema()、@validator→@field_validator。v2 性能也大幅提升（核心用 Rust 重写）。

Q3：Pydantic 在 Agent 里最重要的用途是什么？

答：两点：① 校验 LLM 的不可控输出（尤其 structured output）；② 用 model_json_schema() 生成工具参数的中立 Schema，再由 OpenAI（parameters）/ Anthropic（input_schema）各自 adapter 转成请求格式，是 Function Calling 的基础。

Q4：Field 的 description 有什么实际作用？

答：它会进入导出的 JSON Schema，成为 LLM 理解"这个参数是什么、该怎么填"的依据。描述写得好，工具调用准确率更高。

Q5：model_json_schema() 导出的 Schema 会执行 @field_validator 吗？

答：不会。model_json_schema() 只是读类定义生成描述性 JSON，不执行 validator。validator 在模型验证/构造期间（如 CalcInput(**raw_args) 或 CalcInput.model_validate(raw_args)）运行；启用 validate_assignment=True 时，也可能在字段赋值时运行。因此工具执行前必须显式用收到的参数验证/构造模型，registry 要保存模型类或验证函数，而不能只存一份 Schema dict。

Q6：用字符串黑名单（比如禁止出现 "import"）能防住工具参数被用来做 RCE 吗？

答：不能，这是虚假的安全承诺。黑名单只能挡住"包含特定子串"的输入，挡不住其他攻击路径；它本质上不是通用的 Python 沙箱。更稳妥的做法是从设计上避免"对不可信字符串求值"——比如把自由表达式参数换成 Literal 枚举字段，执行器用 if/elif 分支处理，全程不使用 eval。

总结

  • BaseModel 按 Pydantic v2 规则和模型配置校验、可能转换；失败抛 ValidationError，需要时启用 strict
  • Field 加默认值/描述/约束（ge/le/min_length…），描述会进 Schema
  • @field_validator（配 @classmethod）写自定义校验；模型可嵌套；validator 在模型验证/构造期间运行，启用 validate_assignment=True 时也可能在赋值时运行；仅导出 Schema 不会跑
  • v2 序列化：model_dump() / model_dump_json()
  • model_json_schema() 导出中立参数 Schema；OpenAI 塞进 parameters、Anthropic 塞进 input_schema，字段名不同，需各自 adapter
  • 工具参数应避免自由表达式 + 字符串黑名单（不是通用沙箱、也不是真实的 RCE 防护）；推荐用 Literal 枚举字段 + 分支执行，不使用 eval
  • 执行工具前必须用收到的参数重新构造模型实例做校验；registry 需保存模型类，而非只存 Schema dict
  • 跨信任边界的数据用 Pydantic，内部纯数据用 dataclass
