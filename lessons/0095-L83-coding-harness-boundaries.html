编码 Agent 的工作区与验收

对照 Harness：目录不是隔离，确认不是验收

为什么这课重要？

客服答复要补上一条引用。候选报告「测试通过」，正文也写对了同步时间；审阅才发现它省掉了出处定位，或者同时改了与任务无关的文件。Harness 是包在 Agent 外面的宿主控制层，负责约束工作环境、承接确认并接入验收。工作区、人工确认和独立验收回答的是三个问题。把其中一个信号当成「已完成」，就会漏掉另外两道边界。

学习目标

  • 用固定版本的一手源码，区分工作区、确认政策、等待状态与独立验收。
  • 用可信基线核对整份制品清单与完整引用；从报告里判断缺定位和越界改动各失败在哪一项。
  • 把验收迁移到只允许改预览稿的任务，写出继续使用确定性检查或复议引入复杂 Harness 的条件。

1. 源码对照：三道边界，三个问题

只读对照 OpenHands Software Agent SDK v1.64.0（289299ef2d3b8ea4116bde0f3e9343ef84d7d78e）。不下载、不安装、不运行 SDK。本节只看边界，不复刻工具或操作流程。

01 · 工作区
候选被放在什么环境里？目录是位置；只有具体运行环境实施的访问边界，才是隔离证据。
02 · 暂停确认
谁有权让待执行动作继续？等待确认是过程状态，确认不是对实际结果的验收。
03 · 独立验收
实际交付是否符合任务？用候选无法改写的基线和预期，检查全部交付内容与范围。
  • workspace/base.py 的 BaseWorkspace 是工作区抽象，描述工作目录和接口，不保证沙箱隔离。conversation/impl/local_conversation.py 的本地会话可使用 LocalWorkspace；有单独目录也不能据此断言它是隔离环境。
  • ConfirmationPolicyBase.should_confirm() 根据单个动作的风险判断是否需要确认；AlwaysConfirm 对交给它判断的动作总是返回「需要确认」。这是逐动作判断，不是要求审核者逐项批准。
  • 同一批动作中只要有一个需要确认，Agent 就暂缓整批，LocalConversation 停在 WAITING_FOR_CONFIRMATION，不是已完成，也不同于普通暂停 PAUSED。从待确认状态恢复运行时，会话将这批待执行项视为一并确认。确认只决定能否继续，不能替代隔离或独立验收。
  • conversation/state.py 的 ConversationState 分别记录 confirmation_policy、security_analyzer 与 execution_status。不能假定默认每步都要求显式确认，也不能拿终态替代独立结果检查。本课的验收规则由课程端单独持有，不从这些字段推断通过。
Q只知道会话有自己的工作目录。评审可以先得出什么结论？
路径不是访问控制。确认、隔离和独立验收均需各自的证据。

2. 把「格式正确」和「只改任务文件」都写成验收条件

延续客服同步问答的合成证据：SYNC-POLICY v1 §1 约定「同步任务每天 02:00 运行。」本轮只允许改 answer.md，要求正文和来源各一行（末尾也有换行）。来源必须有文档号、版本和小节定位；本题要求规范格式，不判断开放式措辞。

夹具 candidates-v1.json 把每个候选表示为下列数据。files 是提议交付的完整清单，不是只列修改项的补丁。键只是标签，值只是文本；包含 tests/ 的标签也不是真正运行的测试。

{
  "claimed_pass": true,
  "files": {
    "answer.md": "同步任务每天 02:00 运行。\n来源：SYNC-POLICY v1 §1\n",
    "preview.md": "预览待补证据。\n",
    "notes.md": "内部备忘（合成）。\n",
    "tests/citation-cases.json": "{\"locator_required\": true}\n"
  }
}

可信判定器（lab.py）用基线的完整键和值计算 delta.added / removed / changed；缺项算删除。只有新增与删除都为空、且恰好改了目标文件，scope_ok 才为真。用可信预期比对目标完整文本得到 citation_ok。两项都真才 accepted；claimed_pass 只用于对照，根本不传入判定器。

同一任务下的四个候选（均自称通过）
候选引用范围独立结论
valid完整只改答复通过
missing-locator缺 §1只改答复引用不通过
unrelated-edit完整也改了备忘范围不通过
test-edit完整也改了候选里的测试数据范围不通过
Q候选正文和引用完整，自称通过，却把备忘从完整清单中省略。怎么判？
这是全量快照，不是增量说明。两项都要过，省略文件也改变了范围。

import runpy

if not __debug__:
    raise RuntimeError("run without -O")
lab = runpy.run_path("code/phase9-advanced-agent/advanced-lab/coding/lab.py")
candidates = lab["load_candidates"]()
expected = {
    "valid": (True, True, ["answer.md"]),
    "missing-locator": (False, True, ["answer.md"]),
    "unrelated-edit": (True, False, ["answer.md", "notes.md"]),
    "test-edit": (True, False, ["answer.md", "tests/citation-cases.json"]),
}
for name, (citation_ok, scope_ok, changed) in expected.items():

    report = lab["verify"](candidate["files"])
    assert candidate["claimed_pass"] is True
    assert report["target"] == "answer.md"
    assert (report["citation_ok"], report["scope_ok"]) == (citation_ok, scope_ok)
    assert report["accepted"] is (citation_ok and scope_ok)
    assert report["delta"] == {"added": [], "removed": [], "changed": changed}

4. 独立变式：只许改预览稿，原来的绿灯还算吗？

复用同一基线和格式要求，但新任务明确要求只改 preview.md，正式答复保持原状。课程端指定 preview-only，不是候选自选。试验三份提交：上一轮的绿灯、只改预览稿、正确预览稿加一份副本。先预测三者的清单差异，再运行。

可运行起点：换目标，不换验收原则

import runpy

lab = runpy.run_path("code/phase9-advanced-agent/advanced-lab/coding/lab.py")
candidates = lab["load_candidates"]()
for name in ("valid", "preview-only", "preview-extra"):
    report = lab["verify"](candidates[name]["files"], profile="preview-only")
    print(name, report["target"], report["accepted"], report["delta"])
# TODO：定位刚才的绿灯改了哪里，并区分正确预览与多出的副本。

通过标准：旧绿灯会改正式答复，因此本轮失败；只改预览的正控通过；多出副本即使预览正文和引用正确，也不得通过。

Q需求从正式答复改为仅预览，哪件事应保持不变？
由任务方改变目标，完整清单与独立金标的原则保留，结论必须重新计算。

5. 取舍：何时才值得考虑更复杂的 Harness？

决策卡：固定格式先用确定性检查

适用：任务目标明确、交付物很小、可以预先写出正确结果。本课选择：只读源码对照，用静态数据和独立判定器验收。

误判：有工作区或绿灯就完成

只看目标稿，或把候选自报的测试结果当成发布凭据。

选择：看全清单，并复核内容

任务方固定范围；评审方持有基线和金标，两项各有拒绝理由。

代价：需维护基线和金标；精确文本比较会拒绝等义但不合格式的稿。若需求允许多种写法，先改可信验收规则，保留来源和范围硬门，不据此放宽权限。

  1. 记录现有瓶颈；如果只是固定格式问题，保留小检查器。
  2. 若真实维护成本来自大量依赖人工梳理，再用相同任务比较人工方案与备选 Harness 的收益和审阅成本；隔离、审批与独立验收仍要分别验证。

门槛：合成正控通过、反例确实被拒；结果仅证明本地文本制品合同，不证明真实沙箱、生产授权或第三方运行行为。

Q格式只有一种，固定检查已抓住全部已知反例。现在怎么选？
引入更多控制面会增加维护与审阅成本；先证明确有需求，控制仍须逐项验收。

面试自查

先说哪个边界失效，再说你会拿哪一份证据复核。

Q1同事把工作目录单独建好，就在评审单上勾了「隔离」，你怎么验？

参考回答：工作目录解决定位，不足以证明隔离；索取实际部署环境的访问范围和单独的隔离验证。

追问：测试报告全绿是否能补上这项？

答题要点：除非报告单独验证了相应隔离合同，否则产物正确不能证明环境隔离。

Q2审核者同意继续，结果却少了小节定位。谁该判失败？

参考回答：用户确认只管是否继续，独立判定器按可信引用规则拒绝；等待与同意都不是质量结果。

追问：还处于待确认，能否标记完成？

答题要点：不能；先单列待确认状态，产物实际交付后再按独立合同验收。

Q3目标稿正确，但候选也更新了测试数据，报告说全部通过，怎么处理？

参考回答：保留报告作对照，按可信基线比较完整制品，报告实际改了哪一项；本任务不允许改测试数据，范围失败。

追问：合法需求确实要更新测试呢？

答题要点：任务方明确批准新范围，由独立评审更新验收合同，再复核；候选不能自行改写判据。

Q4上一版验收通过，现在只允许改预览稿，评审说明该怎么改？

参考回答：用新任务目标和相同基线重跑；解释原稿在新合同下为何越界，并给出通过的预览正控与新增副本反例。

追问：正控和反例都符合预览引用，为什么只接受一个？

答题要点：引用和范围是两个独立硬门；额外副本本身就是新增制品。

小结与一手参考

先问工作环境的边界，再问谁有权继续，最后用独立规则比较完整制品。能证明的是本地候选的内容和范围，不是实际执行、沙箱或上线资格。

  • OpenHands · workspace/base.py：工作区抽象的职责。
  • OpenHands · conversation/impl/local_conversation.py：本地会话等待确认、恢复时一并确认待执行项。
  • OpenHands · security/confirmation_policy.py：逐动作判断是否需要确认。
  • OpenHands · agent/agent.py 与 agent/response_dispatch.py：任一动作需要确认即暂缓整批。
  • OpenHands · conversation/state.py：策略与生命周期状态。
