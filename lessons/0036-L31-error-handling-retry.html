错误处理、退避与幂等

生产 Agent 必须假设"调用会失败"——退避 + 抖动 + 幂等，是 demo 与上线的分水岭

💡 为什么这课重要？

前面几课你学会了把 LLM 调起来、流式输出、管理 Context。但那些都是"顺风局"。真实生产里，调用一定会失败：限流(429)、服务端崩(5xx)、超时、网络抖动。一个 Agent 完成一次任务要发几十次 API / 工具调用——任何一次都可能失败。

L10 已经教过你 tenacity 做指数退避重试——那是地基。这一课往上盖两根生产级的承重柱：抖动(jitter)打散重试，避免一群客户端同时重试把服务端二次打垮；幂等键(idempotency key)标识同一次业务操作，配合服务端的幂等契约，才能安全重放有副作用的请求。

学习目标

完成本课后，你将能够：

  • 区分可能值得重试的临时错误（429/5xx/超时）与不可重试的错误（400/401）
  • 理解指数退避为何不够，必须加抖动（full jitter）防"重试风暴"
  • 设置重试预算（最大次数 + 总时间上限），到点 fail fast
  • 用作用域内稳定的操作键 + 请求身份识别重试，验证同库原子提交，并判断外部结果未知时何时该停下来核对
  • 说清楚这套机制为什么是 Agent"能上生产"的门槛

1. LLM API 一定会失败——先学会分类

生产 Agent 的第一条心法：不要假设调用会成功。常见失败有四类：

  • 429 限流（rate limit）：你发太快 / 超了配额，服务端让你"稍后再来"。
  • 5xx 服务端错误：500 / 502 / 503，是对方的问题，通常是临时的。
  • 超时：请求发出去但迟迟没回，可能网络慢、也可能对方在排队。
  • 网络抖动：连接被重置、DNS 抽风等瞬时故障。

但不是所有错误都该重试。关键要分两类——重试错类型只会浪费时间、甚至火上浇油：

【可能值得重试】临时性、换个时间可能就好了
  429 限流 / 5xx 服务端 / 超时 / 网络抖动
     → 确认可安全重放后，再退避重试（见第 5 节）

【不可重试】你自己的请求有问题，重试 100 次还是错
  400 参数错误   → 你的 payload 就是错的，重发没用
  401 鉴权失败   → key 不对，重发只会一直 401
  404 资源不存在 → 目标就是没有
     → 别重试，立即 fail fast 把错误抛给上层

Agent 关联：先判错误类型，再判断重放会不会重复触发副作用。把 401 拿去重试，只会白白拖慢整条链路、还刷爆日志；超时则不说明原操作没执行。

Q 下面哪个错误最不该自动重试？
401 是鉴权失败——不修正凭据，重试只会浪费时间和配额，应立即 fail fast。429（限流）、5xx（如临时服务故障）和超时可能值得退避重试，但要先确认操作可安全重放。错误分类只是第一步。

2. 指数退避：给服务端喘息的空间

失败后立刻重试是最糟的做法——服务端正忙不过来，你还猛捶它。正确姿势是指数退避（exponential backoff）：每失败一次，等待时间翻倍。

第 1 次失败 → 等 1s → 重试
第 2 次失败 → 等 2s → 重试
第 3 次失败 → 等 4s → 重试
第 4 次失败 → 等 8s → 重试
       等待 = base × 2 ** attempt   （指数增长）

越等越久，给对方留出恢复时间。原理你要懂，但生产别自己造轮子——正如 L10 讲过的，tenacity 内置了这一切。下面的片段只演示等待和停止策略；实际使用还要限定可重试的错误和可安全重放的操作。

from tenacity import retry, stop_after_attempt, wait_exponential

@retry(stop=stop_after_attempt(4),
       wait=wait_exponential(multiplier=1, min=1, max=8))  # 约 1→2→4→8s（封顶 8s，实际序列以 tenacity 为准）
def call_llm(prompt):
    return client.chat.completions.create(...)   # 失败自动退避重试

但纯指数退避有个致命缺陷——它在"很多客户端同时失败"时会自己制造灾难。这正是下一节的主角。

3. 抖动（jitter）：防重试风暴 ⚠️ 本课重点

想象一个真实场景：服务端抖了一下，1000 个客户端在同一瞬间全部收到 5xx。它们都用"标准指数退避"，于是会发生什么？

t=0s   服务端抖动，1000 个客户端同时失败
t=1s   → 1000 个客户端【一起】重试   💥 又把服务端打垮
t=3s   → 1000 个客户端【一起】重试   💥 再垮一次
t=7s   → 1000 个客户端【一起】重试   💥 …死循环

因为大家的退避节奏完全同步，重试请求会聚成一波又一波的"脉冲"，反复砸向刚要恢复的服务端。这就是重试风暴 / 惊群效应（thundering herd）——退避不但没救服务端，反而亲手把它按死。

解法：加随机抖动（jitter）。核心思想是把重试时间打散，让 1000 个客户端不再"齐步走"。业界最推荐的是 full jitter——等待时间在 [0, backoff] 区间里随机取：

import random

# ❌ 纯指数退避：所有客户端等待时间【一模一样】→ 同步重试
wait = base * 2 ** attempt

# ✅ full jitter：在 [0, backoff] 里随机 → 重试时间被打散
wait = random.uniform(0, base * 2 ** attempt)
#         ↑ 每个客户端随机落在 0~backoff 之间，波峰被抹平

加了 jitter 后，那 1000 个客户端会均匀地散布在 0~1s、0~2s…里陆续重试，服务端面对的是平缓的涓流而非"脉冲海啸"，得以真正恢复。AWS 的经典模拟证明：full jitter 显著降低服务端负载、缩短整体恢复时间（见本课 primary source）。

🔑 好消息：tenacity 内置抖动，一行开启 
from tenacity import retry, stop_after_attempt, wait_random_exponential

@retry(stop=stop_after_attempt(5),
       wait=wait_random_exponential(min=1, max=30))   # 指数退避 + 随机抖动
def call_llm(prompt):
    return client.chat.completions.create(...)

wait_random_exponential 就是"指数退避 + full jitter"的开箱即用版。别手写——你只需知道背后为什么要这么做。

Agent 关联：生产 Agent 往往是"一群实例并发跑"。一旦上游 LLM 网关抖动，没有 jitter，你的整个 Agent 集群就会自发形成重试风暴，把本可自愈的小故障放大成雪崩。

Q 纯指数退避（不加抖动）在大量客户端同时失败时的问题是？
纯指数退避下，所有客户端的等待时间完全一致，于是在 1s/2s/4s 后一起重试，聚成一波波脉冲反复砸向刚要恢复的服务端——这就是重试风暴 / 惊群效应（thundering herd）。解法是加随机抖动（full jitter），把重试时间打散到 [0, backoff]，让请求变成平缓涓流。

4. 重试预算：别无限重试

退避 + 抖动解决了"怎么重试"，但还有个问题：重试几次才放弃？ 答案绝不是"一直重试"。如果服务端真的挂了，无限重试只会让请求越堆越多，最终连你自己的进程都被拖垮。

要给重试设预算（retry budget）——两条硬上限，任一触顶就fail fast（立即认输、把错误抛给上层）：

【重试预算 = 两条上限】
  ① 最大次数：最多重试 N 次（如 5 次）
  ② 总时间上限：整个重试过程不超过 T 秒（如 30s）

  任一触顶 → 立即抛错，别再堆请求
from tenacity import retry, stop_after_attempt, stop_after_delay, wait_random_exponential

@retry(
    stop=(stop_after_attempt(5) | stop_after_delay(30)),  # 5 次 或 30s，先到先停
    wait=wait_random_exponential(min=1, max=15),
    reraise=True,                                          # 到点抛出真实异常
)
def call_llm(prompt):
    return client.chat.completions.create(...)

fail fast 好过慢慢拖死：与其让用户等 5 分钟最后还是失败，不如及时报错，让上层对可安全重放的调用走 L32 的 fallback（换模型/换供应商）或友好降级。若外部副作用结果未知，不自动换路，按第 5 节先核对。

5. 幂等键：先确认副作用能否安全重放 ⚠️ 本课重点

多查一次天气通常没关系，但想象 Agent 调用工具创建一张虚构工单：服务端已经写入工单，响应却没到。客户端只看到超时，分不清是请求没执行，还是已提交但丢了响应。直接再建一张，可能留下两条记录。

先确定“是不是同一次操作”：发起方在第一次尝试前生成操作键（如 UUID），随任务持久化，重试或进程恢复后仍复用。服务端在可信的作用域（如租户 + 工具动作）内按键关联操作，并保存请求身份（规范化后的业务参数或其指纹）。同作用域、同键、同参数才能重放；同作用域内，同键不同参数应拒绝。两次独立意图即使参数相同，也用不同的键。

副作用可写入同一个数据库：把去重检查、业务写入以及操作记录和结果的写入放在同一个事务；并发访问须由数据库协调，不能让两个请求都读到“未处理”后各自提交。下面用 SQLite 的 BEGIN IMMEDIATE 先取得写事务，复合主键约束作用域内的键。提交前失败，两份写入一起回滚；提交后响应丢失，同一请求重放时返回已保存的工单编号，不再写入。只要记录保留，在这个作用域内，同一操作至多有一次已提交的业务变更，不保证一定成功。

键、锁和唯一约束都不能单独提供这个保证：先执行业务、再单独记完成，可能在两步之间崩溃；反过来先记完成也会留下假成功。锁被占用只说明有人持有它，锁过期（TTL）也不能告诉你动作是否已执行。唯一约束能拒绝重复操作记录，却不能撤销在另一事务或系统里做过的副作用。

外部副作用：按供应商契约重放，或先核对结果

本地事务管不到外部服务。如果对方明确支持幂等，只有在它支持的端点、账号等作用域和保留窗口内，才用相同键和参数按文档重放；还要看它会返回哪些已保存的结果。不能假定换端点、换供应商或超过保留期后仍会去重。

如果没有可信的重放契约（包括键可能已过期），超时后把状态保留为结果未知。用业务引用查询对方的权威状态，或等可信回执：确认已完成就记录原结果，确认原请求未执行且不会再生效才考虑补做，仍不确定就交人工核对。暂时查不到不等于未执行；不要盲目重发、换键或自动换供应商。

Q 同库的工单已经提交，但响应丢了。相同作用域、键和参数的重试为何不会再建一张？
同库事务让业务写入和操作结果一起提交或回滚。只要已提交的记录还在，同键同参数就返回原结果；同键不同参数会被拒绝。锁或唯一约束不能替未参加事务的外部服务做保证。

离线验收：工单已提交，但响应丢了

将下面整段复制到 Python 文件，用 python -I 文件名.py 运行。只用标准库和自动清理的临时 SQLite 文件，不访问网络。每次尝试及状态检查都独立打开、关闭连接，用同一文件模拟服务重启，不在内存里记完成状态。

展开 SQLite 示例与验收断言 
import json
import sqlite3
from contextlib import closing
from pathlib import Path
from tempfile import TemporaryDirectory


def create_ticket(path, scope, key, title, *, fail_at=None):
    request = json.dumps({"title": title}, sort_keys=True, separators=(",", ":"))
    with closing(sqlite3.connect(path, isolation_level=None)) as db, db:
        db.execute("BEGIN IMMEDIATE")  # 先取得写事务，再判断是否重放
        saved = db.execute(
            "SELECT request, ticket_id FROM operations WHERE scope = ? AND op_key = ?",
            (scope, key),
        ).fetchone()
        if saved is not None:
            original, ticket_id = saved
            if original != request:
                raise ValueError("same key, different arguments")
        else:
            ticket_id = db.execute(
                "INSERT INTO tickets (scope, title) VALUES (?, ?)", (scope, title)
            ).lastrowid
            db.execute(
                "INSERT INTO operations (scope, op_key, request, ticket_id) VALUES (?, ?, ?, ?)",
                (scope, key, request, ticket_id),
            )
            if fail_at == "before_commit":
                raise RuntimeError("before commit")  # 两条 INSERT 都已执行，但未提交
    # db 的事务上下文已提交，连接也已关闭；现在才模拟丢响应。
    if fail_at == "after_commit":
        raise TimeoutError("response lost")
    return ticket_id


def snapshot(path):
    with closing(sqlite3.connect(path)) as db:
        return (
            db.execute("SELECT id, scope, title FROM tickets").fetchall(),
            db.execute("SELECT scope, op_key, request, ticket_id FROM operations").fetchall(),
        )


def must_fail(error_type, message, *args, **kwargs):
    try:
        create_ticket(*args, **kwargs)
    except error_type as exc:
        assert str(exc) == message, str(exc)
    else:
        raise AssertionError(f"expected {error_type.__name__}")


if not __debug__:
    raise RuntimeError("run without -O")

with TemporaryDirectory() as directory:
    path = Path(directory) / "tickets.sqlite"
    with closing(sqlite3.connect(path)) as db:
        db.executescript("""
            CREATE TABLE tickets (id INTEGER PRIMARY KEY, scope TEXT NOT NULL, title TEXT NOT NULL);
            CREATE TABLE operations (
                scope TEXT NOT NULL, op_key TEXT NOT NULL, request TEXT NOT NULL,
                ticket_id INTEGER NOT NULL, PRIMARY KEY (scope, op_key)
            );
        """)

    scope, key, title = "demo:create_ticket", "op-42", "Training ticket"
    args = (path, scope, key, title)
    must_fail(RuntimeError, "before commit", *args, fail_at="before_commit")
    assert snapshot(path) == ([], [])

    must_fail(TimeoutError, "response lost", *args, fail_at="after_commit")
    committed = snapshot(path)
    tickets, operations = committed
    assert tickets == [(1, scope, title)]
    assert operations == [(scope, key, '{"title":"Training ticket"}', 1)]
    assert create_ticket(*args) == operations[0][3]
    assert snapshot(path) == committed

    must_fail(ValueError, "same key, different arguments", path, scope, key, "Different title")
    assert snapshot(path) == committed

print("L31 ACCEPTED")

通过标准：提交前注入失败，两张表都为空；提交后模拟丢响应，独立连接仍能读取操作记录和唯一一张工单；重放返回保存的编号，同键不同参数被拒绝且表不变。全部通过才应看到一行 L31 ACCEPTED。本例不验证强杀进程、并发压测或外部服务的幂等契约。

6. 拼起来：这就是"能上生产"的分水岭

把错误分类、重放判断、退避、抖动和预算拼起来：

一次 Agent 工具/API 调用失败时：
  参数或鉴权错误 → 不重试，立即报错
  临时错误（如 429/503/超时）→ 先判断能否安全重放
    ├─ 无副作用，或有可信幂等契约 → 按契约重放（有键则复用）
    │    用指数退避 + full jitter；预算耗尽则停止自动重试
    └─ 外部副作用结果未知且无可信重放契约 → 停止重放，查询或人工核对

退避、抖动和预算决定何时重试、何时停，不能让本来不安全的重试变安全。预算用完时也不能把未知结果当作未执行，再交给 L32 自动换路。

动手想一想：外部工单创建超时，还能重试吗？

场景：假设把离线示例改成调用虚构的外部工单服务。创建请求已发出，但响应超时。分别说出：① 对方在当前端点、账号和保留期内承诺支持幂等重放；② 对方没提供可信的幂等契约，或键可能已过期。两种情况下怎么处理？只做纸面推演，不调用外部服务。

点击查看参考答案
  • ① 可以按契约重放：在预算内，用首次保存的键和相同参数重发到同一作用域，并按对方契约解读返回结果。如果首次已提交且结果保留，应读到原结果；不能假定重试总会成功。
  • ② 不能盲目重放：保留“结果未知”，用业务引用核对外部状态或回执。确认已有工单则记录原编号，确认首个请求没创建工单且不会再生效才考虑补做；无法确认就交人工。自己在本地保存一个键，不能让对方去重。
🎤 面试高频①："如何处理速率限制（429）？"

答：① 指数退避——失败后等待时间翻倍，给服务端喘息；② 加 full jitter——把重试时间随机打散到 [0, backoff]，防止大量客户端同步重试引发重试风暴（thundering herd）；③ 设重试预算——最大次数 + 总时间上限，超了 fail fast；④ 先确认能否安全重放（429/5xx/超时是重试候选，400/401 别重试）。工程上用 tenacity 的 wait_random_exponential，别手写。

🎤 面试高频②："有副作用的工具调用怎么安全重试？"

答：首次尝试前保存操作键，重试时复用；在同一作用域内核对请求参数。同库内把业务变更和操作记录、结果原子提交，重放返回保存的结果，同键不同参数直接拒绝。外部副作用只能按供应商明确的作用域及保留期重放；没有可信契约且结果未知，就核对状态，不盲重试。

🎯 速查卡：错误处理·退避·幂等

【第一步：分类】
  429 限流 / 5xx 服务端 / 超时 / 网络抖动 → 先判断能否安全重放
  400 参数 / 401 鉴权 / 404 → 立即 fail fast

【退避】exponential backoff
  等待 = base × 2**attempt   （1s→2s→4s→8s）给服务端喘息
  别手写 → tenacity: wait_exponential

【抖动】jitter ⚠️ 灵魂
  问题：纯退避 → 千客户端【同步】重试 → 重试风暴 thundering herd
  解法：full jitter → wait = random.uniform(0, base * 2**attempt)
        把重试时间打散，波峰抹平
  tenacity: wait_random_exponential（退避+抖动，一行搞定）

【重试预算】retry budget
  ① 最大次数(N)  ② 总时间上限(T)  任一触顶 → fail fast
  tenacity: stop_after_attempt(N) | stop_after_delay(T)

【幂等键】idempotency key
  同一业务操作 → 同一作用域、复用首次保存的键、核对参数
  同库 → 业务写入与操作记录、结果原子提交；重放返回保存的结果
  外部 → 只在供应商支持的作用域和保留期内按契约重放
  无可信契约且结果未知 → 查状态或交人工；不盲重发或换路

【Agent 分水岭】一次任务几十次调用，任何一次都可能失败
  先判能不能重放，再决定怎么退避、何时停止。

总结

  • 生产 Agent 必须假设调用会失败；临时错误是重试候选，还要判断是否能安全重放
  • 指数退避给服务端喘息（1s→2s→4s→8s），原理懂即可，用 tenacity
  • 抖动(full jitter)是灵魂：纯退避会让客户端同步重试→重试风暴，随机打散才能救场
  • 重试预算（最大次数 + 总时间）到点 fail fast，别把请求堆死
  • 幂等键在首次尝试前保存，在同一作用域内重试复用并核对参数；同库把业务写入和操作记录、结果原子提交
  • 外部副作用只按供应商支持的作用域和保留期重放；没有可信契约且结果未知时先核对，不盲重试
