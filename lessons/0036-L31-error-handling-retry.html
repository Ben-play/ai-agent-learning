错误处理、退避与幂等

调用会失败：先判断能否安全重放，再用退避、抖动和截止时间约束尝试

💡 为什么这课重要？

前面几课你学会了把 LLM 调起来、流式输出、管理 Context。但那些都是"顺风局"。真实生产里，调用一定会失败：限流(429)、服务端崩(5xx)、超时、网络抖动。一个 Agent 完成一次任务要发几十次 API / 工具调用——任何一次都可能失败。

L10 介绍了用 tenacity 做指数退避。这里再做三个决定：用抖动（jitter）打散重试；在截止时间前判断等不等、发不发、单次最多等多久；用幂等键（idempotency key）标识同一操作，只有可信契约支持时才自动重放有副作用的请求。

学习目标

完成本课后，你将能够：

  • 区分可能值得重试的临时错误（429/5xx/超时）与不可重试的错误（400/401）
  • 理解确定性的指数退避为何会同步重试，以及怎样用抖动（full jitter）打散请求
  • 区分尝试次数上限、重试停止策略和调用方截止时间，用剩余时间限制每次尝试
  • 用作用域内稳定的操作键 + 请求身份识别重试，验证同库原子提交，并判断外部结果未知时何时该停下来核对
  • 让同一调用链只有一个重试负责人，并说明离线验证不能证明什么

1. LLM API 一定会失败——先学会分类

生产 Agent 的第一条心法：不要假设调用会成功。常见失败有四类：

  • 429 限流（rate limit）：你发太快 / 超了配额，服务端让你"稍后再来"。
  • 5xx 服务端错误：如 500 / 502 / 503；部分是临时故障，是否值得重试看服务契约。
  • 超时：请求发出去但迟迟没回，可能网络慢、也可能对方在排队。
  • 网络抖动：连接被重置、DNS 抽风等瞬时故障。

但不是所有错误都该重试。关键要分两类——重试错类型只会浪费时间、甚至火上浇油：

【可能值得重试】临时性、换个时间可能就好了
  429 限流 / 5xx 服务端 / 超时 / 网络抖动
     → 确认可安全重放后，再退避重试（见第 5 节）

【不可重试】你自己的请求有问题，重试 100 次还是错
  400 参数错误   → 你的 payload 就是错的，重发没用
  401 鉴权失败   → key 不对，重发只会一直 401
  404 资源不存在 → 目标就是没有
     → 别重试，立即 fail fast 把错误抛给上层

Agent 关联：先判错误类型，再判断重放会不会重复触发副作用。把 401 拿去重试，只会白白拖慢整条链路、还刷爆日志；超时则不说明原操作没执行。

Q 下面哪个错误最不该自动重试？
401 是鉴权失败——不修正凭据，重试只会浪费时间和配额，应立即 fail fast。429（限流）、5xx（如临时服务故障）和超时可能值得退避重试，但要先确认操作可安全重放。错误分类只是第一步。

2. 指数退避：给服务端喘息的空间

上游正忙时，立刻重试会增加负载。若确认能安全重放并且预算允许，指数退避（exponential backoff）会随失败次数拉长等待。下面是未加抖动、未套次数上限的序列：

第 1 次失败 → 等 1s → 重试
第 2 次失败 → 等 2s → 重试
第 3 次失败 → 等 4s → 重试
第 4 次失败 → 等 8s → 重试
       等待 = base × 2 ** attempt   （指数增长）

越等越久，给对方留出恢复时间。L10 介绍的 tenacity 已提供退避策略。下面的片段只演示等待和次数限制；实际使用还要限定可重试的错误和可安全重放的操作。

from tenacity import retry, stop_after_attempt, wait_exponential

@retry(stop=stop_after_attempt(4),  # 共 4 次尝试，含首次；持续失败时只等 1、2、4 秒
       wait=wait_exponential(multiplier=1, min=1, max=8))
def call_llm(prompt):
    return client.chat.completions.create(...)   # 失败自动退避重试

但纯指数退避有个致命缺陷——它在"很多客户端同时失败"时会自己制造灾难。这正是下一节的主角。

3. 抖动（jitter）：防重试风暴 ⚠️ 本课重点

想象一个真实场景：服务端抖了一下，1000 个客户端在同一瞬间全部收到 5xx。它们都用"标准指数退避"，于是会发生什么？

t=0s   服务端抖动，1000 个客户端同时失败
t=1s   → 1000 个客户端【一起】重试   💥 又把服务端打垮
t=3s   → 1000 个客户端【一起】重试   💥 再垮一次
t=7s   → 1000 个客户端【一起】重试   💥 …死循环

因为大家的退避节奏完全同步，重试请求会聚成一波又一波的"脉冲"，反复砸向刚要恢复的服务端。这就是重试风暴 / 惊群效应（thundering herd）——退避不但没救服务端，反而亲手把它按死。

解法：加随机抖动（jitter）。核心思想是把重试时间打散，让 1000 个客户端不再"齐步走"。业界最推荐的是 full jitter——等待时间在 [0, backoff] 区间里随机取：

import random

# attempt 从 0 开始；未抖动的等待上限
backoff = base * 2 ** attempt
# full jitter：在 [0, backoff] 内抽取本轮计划等待
wait = random.uniform(0, backoff)

加了 jitter 后，那 1000 个客户端会均匀地散布在 0~1s、0~2s…里陆续重试，服务端面对的是平缓的涓流而非"脉冲海啸"，得以真正恢复。AWS 的经典模拟证明：full jitter 显著降低服务端负载、缩短整体恢复时间（见本课 primary source）。

🔑 好消息：tenacity 内置抖动，一行开启 
from tenacity import retry, stop_after_attempt, wait_random_exponential

@retry(stop=stop_after_attempt(5),  # 总尝试数含首次
       wait=wait_random_exponential(min=0, max=30))  # 指数退避 + full jitter
def call_llm(prompt):
    return client.chat.completions.create(...)

wait_random_exponential 可复用，但只负责算等待；上面的片段没有设置安全重放条件或截止时间。

Agent 关联：生产 Agent 往往是"一群实例并发跑"。一旦上游 LLM 网关抖动，没有 jitter，你的整个 Agent 集群就会自发形成重试风暴，把本可自愈的小故障放大成雪崩。

Q 纯指数退避（不加抖动）在大量客户端同时失败时的问题是？
纯指数退避下，所有客户端的等待时间完全一致，于是在 1s/2s/4s 后一起重试，聚成一波波脉冲反复砸向刚要恢复的服务端——这就是重试风暴 / 惊群效应（thundering herd）。解法是加随机抖动（full jitter），把重试时间打散到 [0, backoff]，让请求变成平缓涓流。

4. 重试预算：尝试次数、等待排程与截止时间

退避和抖动决定怎么等，不决定该不该再试。Tenacity 的停止策略是在一次失败被判定可重试后决定是否再排一次；下面的已用时间从这轮重试调用开始算：

  • stop_after_attempt(5)：最多 5 次尝试，含首次；若一直失败，最多再重试 4 次。
  • stop_after_delay(30)：只看截至该次失败的已用时间，不把即将发生的等待算进去。若第 29 秒失败、已算出的等待为 2 秒、次数还有余量，它仍允许等到第 31 秒再尝试。
  • stop_before_delay(30)：把本轮计划等待也算进去，已用时间 + 下一次等待 ≥ 30 秒就不排；因此会拒绝上面的 29 + 2 秒，也会拒绝 29 + 1 秒。

若只想限制重试排程，可用 stop_after_attempt(5) | stop_before_delay(30)。两种时间停止策略都不会取消正在执行的调用，也不会限制下一次调用本身的耗时。即使排程时算出能在第 29 秒发起，实际醒来可能已经迟了；首次尝试也不是由这些停止条件拦住的。

调用方截止时间是另一个边界：为整次操作设一个单调时钟上的绝对截止时间，排等待前拒绝会到达或越过截止的等待；每次发起前（包括首次和等待醒来后）重新测剩余时间，剩余时间不为正就不发，其他情况把单次超时设为单次上限与剩余时间的较小值。

这些检查不会强行中断任意同步函数。示例的传输替身按约定在给定时间内返回或报告超时；真实客户端要核对超时是覆盖整次尝试还是只约束某个 I/O 阶段，以及它支持什么取消方式。即便客户端不再等待，也不能断言外部操作已取消或未写入。

决策卡：工单超时后，不把下一次尝试排到截止之外

同一场景：创建一张外部工单，截止为第 30 秒。第 29 秒才发现没收到响应，本轮退避是 2 秒，尝试次数还有余量；以下先假定供应商允许按原键安全重放。

误判：停止策略就是截止时间

只设 stop_after_delay(30)，按第 29 秒的已用时间放行等待，可能到第 31 秒才发第二次请求。

对照：按剩余时间决定等、发和等多久

同一请求不排这 2 秒；若等待能排下，醒来仍先验截止，再把剩余时间传给单次传输。未拿到业务结论就保留原引用以核对。

取舍：宁可少一次重试，也不在预算外发请求。若没有可信重放契约，即使时间和次数都够，也先核对。这里只由调用方重试；接入 SDK 或网关时关闭同一链路的其他自动重试，避免底层次数被放大。

结果诊断：第 29 秒应只有一次传输、没有等待。若还安排了等待，检查是否只看已用时间；若醒来后仍越界发起，查发起前的时钟检查；若单次仍拿到固定超时，查是否取了单次上限与剩余时间的较小值。若收到「结果未知」，去核对原操作，不触发自动换路。

以下脚本只模拟超时，不载入 Tenacity 或 SDK，不用网络或真实睡眠。固定等待代表本轮抖动结果；每次 send 只尝试一次，不模拟远端是否提交。replay_safe 由用例给定；真实外部写入须在每次重放前确认原参数、作用域和保留期仍有效。

发起前就没预算会报 BudgetExhausted；发过写请求但最终没收到结果则报 OutcomeUnknown，带回原操作引用和停止原因，交给第 5 节的核对流程。

展开离线时钟与截止时间验收 
class BudgetExhausted(Exception):
    pass


class OutcomeUnknown(Exception):
    pass


class FakeClock:
    def __init__(self, start=0, *, wakeup_lag=0):
        self.now = start
        self.wakeup_lag = wakeup_lag
        self.waits = []

    def monotonic(self):
        return self.now

    def sleep(self, delay):
        self.waits.append(delay)
        self.now += delay + self.wakeup_lag


class FakeTransport:
    def __init__(self, clock, steps):
        self.clock = clock
        self.steps = iter(steps)
        self.calls = []

    def send(self, reference, *, timeout):
        self.calls.append((reference, self.clock.monotonic(), timeout))
        response_in, result = next(self.steps)
        if response_in >= timeout:
            self.clock.now += timeout
            raise TimeoutError("response not observed")
        self.clock.now += response_in
        if isinstance(result, Exception):
            raise result
        return result


def call_with_budget(send, clock, reference, *, deadline, per_attempt,
                     max_attempts, wait, replay_safe):
    if max_attempts < 1:
        raise BudgetExhausted("attempts")
    last_timeout = None
    for attempt in range(1, max_attempts + 1):
        remaining = deadline - clock.monotonic()  # 首次或醒来后，发起前重测
        if remaining <= 0:
            if last_timeout is not None:
                raise OutcomeUnknown(reference, "deadline") from last_timeout
            raise BudgetExhausted("deadline")  # 尚未发过请求
        try:
            return send(reference, timeout=min(per_attempt, remaining))
        except TimeoutError as error:
            if not replay_safe:
                raise OutcomeUnknown(reference, "not_replay_safe") from error
            if attempt == max_attempts:
                raise OutcomeUnknown(reference, "attempts") from error
            remaining = deadline - clock.monotonic()
            if wait >= remaining:
                raise OutcomeUnknown(reference, "deadline") from error
            last_timeout = error
            clock.sleep(wait)


def expect_error(kind, fn, *args, **kwargs):
    try:
        fn(*args, **kwargs)
    except kind as error:
        return error
    raise AssertionError(f"expected {kind.__name__}")


def run(clock, transport, *, deadline=5, per_attempt=4, wait=2,
        max_attempts=3, replay_safe=True):
    return call_with_budget(transport.send, clock, "op-42", deadline=deadline,
                            per_attempt=per_attempt, max_attempts=max_attempts,
                            wait=wait, replay_safe=replay_safe)


if not __debug__:
    raise RuntimeError("run without -O")

# 截止时间已到：连首次尝试也不能交给传输层。
clock = FakeClock(start=5)
transport = FakeTransport(clock, [])
assert str(expect_error(BudgetExhausted, run, clock, transport)) == "deadline"
assert transport.calls == [] and clock.waits == []

# 离截止还剩 2 秒：传输只拿到 2 秒，不是默认的 4 秒。
clock = FakeClock(start=3)
transport = FakeTransport(clock, [(1, "T-7")])
assert run(clock, transport) == "T-7"
assert transport.calls == [("op-42", 3, 2)] and clock.monotonic() == 4

# 从 t=0 开始，第 29 秒超时；等 1 秒到截止，等 2 秒越过，都不排等待。
for proposed_wait in (1, 2):
    clock = FakeClock()
    transport = FakeTransport(clock, [(35, "T-7")])
    unknown = expect_error(OutcomeUnknown, run, clock, transport,
                           deadline=30, per_attempt=29, wait=proposed_wait)
    assert unknown.args == ("op-42", "deadline")
    assert transport.calls == [("op-42", 0, 29)] and clock.waits == []
    assert clock.monotonic() == 29

# t=3 超时，等 1 秒后还有 1 秒；第二次仍使用同一操作引用。

assert run(clock, transport, wait=1, max_attempts=2) == "T-7"
assert transport.calls == [("op-42", 0, 4), ("op-42", 4, 1)] and clock.waits == [1]

clock = FakeClock(wakeup_lag=2)

assert clock.monotonic() == 6

# 最大尝试数为 1：即使还有时间，也只允许首次调用。
clock = FakeClock()
transport = FakeTransport(clock, [(2, TimeoutError("response lost")), (0, "T-7")])
unknown = expect_error(OutcomeUnknown, run, clock, transport, max_attempts=1)
assert unknown.args == ("op-42", "attempts") and isinstance(unknown.__cause__, TimeoutError)
assert transport.calls == [("op-42", 0, 4)] and clock.waits == []

# 外部写入没有可信重放契约：有预算也不能自动重发，保留查询所需引用。
clock = FakeClock()
transport = FakeTransport(clock, [(2, TimeoutError("response lost")), (0, "T-7")])
unknown = expect_error(OutcomeUnknown, run, clock, transport, replay_safe=False)
assert unknown.args == ("op-42", "not_replay_safe")
assert isinstance(unknown.__cause__, TimeoutError)
assert transport.calls == [("op-42", 0, 4)] and clock.waits == []

5. 幂等键：先确认副作用能否安全重放 ⚠️ 本课重点

多查一次天气通常没关系，但想象 Agent 调用工具创建一张虚构工单：服务端已经写入工单，响应却没到。客户端只看到超时，分不清是请求没执行，还是已提交但丢了响应。直接再建一张，可能留下两条记录。

先确定“是不是同一次操作”：发起方在第一次尝试前生成操作键（如 UUID），随任务持久化，重试或进程恢复后仍复用。服务端在可信的作用域（如租户 + 工具动作）内按键关联操作，并保存请求身份（规范化后的业务参数或其指纹）。同作用域、同键、同参数才能重放；同作用域内，同键不同参数应拒绝。两次独立意图即使参数相同，也用不同的键。

副作用可写入同一个数据库：把去重检查、业务写入以及操作记录和结果的写入放在同一个事务；并发访问须由数据库协调，不能让两个请求都读到“未处理”后各自提交。下面用 SQLite 的 BEGIN IMMEDIATE 先取得写事务，复合主键约束作用域内的键。提交前失败，两份写入一起回滚；提交后响应丢失，同一请求重放时返回已保存的工单编号，不再写入。只要记录保留，在这个作用域内，同一操作至多有一次已提交的业务变更，不保证一定成功。

键、锁和唯一约束都不能单独提供这个保证：先执行业务、再单独记完成，可能在两步之间崩溃；反过来先记完成也会留下假成功。锁被占用只说明有人持有它，锁过期（TTL）也不能告诉你动作是否已执行。唯一约束能拒绝重复操作记录，却不能撤销在另一事务或系统里做过的副作用。

外部副作用：按供应商契约重放，或先核对结果

本地事务管不到外部服务。如果对方明确支持幂等，只有在它支持的端点、账号等作用域和保留窗口内，才用相同键和参数按文档重放；还要看它会返回哪些已保存的结果。不能假定换端点、换供应商或超过保留期后仍会去重。

如果没有可信的重放契约（包括键可能已过期），超时后把状态保留为结果未知。用业务引用查询对方的权威状态，或等可信回执：确认已完成就记录原结果，确认原请求未执行且不会再生效才考虑补做，仍不确定就交人工核对。暂时查不到不等于未执行；不要盲目重发、换键或自动换供应商。

Q 同库的工单已经提交，但响应丢了。相同作用域、键和参数的重试为何不会再建一张？
同库事务让业务写入和操作结果一起提交或回滚。只要已提交的记录还在，同键同参数就返回原结果；同键不同参数会被拒绝。锁或唯一约束不能替未参加事务的外部服务做保证。

def create_ticket(path, scope, key, title, *, fail_at=None):
    request = json.dumps({"title": title}, sort_keys=True, separators=(",", ":"))
    with closing(sqlite3.connect(path, isolation_level=None)) as db, db:
        db.execute("BEGIN IMMEDIATE")  # 先取得写事务，再判断是否重放
        saved = db.execute(
            "SELECT request, ticket_id FROM operations WHERE scope = ? AND op_key = ?",
            (scope, key),
        ).fetchone()
        if saved is not None:
            original, ticket_id = saved
            if original != request:
                raise ValueError("same key, different arguments")
        else:
            ticket_id = db.execute(
                "INSERT INTO tickets (scope, title) VALUES (?, ?)", (scope, title)
            ).lastrowid
            db.execute(
                "INSERT INTO operations (scope, op_key, request, ticket_id) VALUES (?, ?, ?, ?)",
                (scope, key, request, ticket_id),
            )
            if fail_at == "before_commit":
                raise RuntimeError("before commit")  # 两条 INSERT 都已执行，但未提交
    # db 的事务上下文已提交，连接也已关闭；现在才模拟丢响应。
    if fail_at == "after_commit":
        raise TimeoutError("response lost")
    return ticket_id


def snapshot(path):
    with closing(sqlite3.connect(path)) as db:
        return (
            db.execute("SELECT id, scope, title FROM tickets").fetchall(),
            db.execute("SELECT scope, op_key, request, ticket_id FROM operations").fetchall(),
        )

6. 拼起来：用同一份预算做重试决定

整条调用链只有一个重试负责人（L15）。由调用方执行本课策略时，关闭 SDK、传输和网关的其他自动重试，不在外层再套一层。首次及每次尝试前都按同一截止时间限制传输：

一次 Agent 工具/API 调用失败时：
  参数或鉴权错误 → 不重试，立即报错
  临时错误（如 429/503/超时）→ 先判断能否安全重放
    ├─ 无副作用，或有可信幂等契约 → 仅在作用域、有效期和预算内重放
    │    复用原键；退避加抖动；若等待会触及截止，不排下一次
    └─ 外部副作用结果未知且无可信重放契约 → 停止重放，查询或人工核对

退避、抖动和预算不能让不安全的重试变安全。预算用完时可以对安全调用友好降级；不能把未知写入当作未执行，再交给 L32 自动换路。

动手想一想：外部工单创建超时，还能重试吗？

场景：假设把离线示例改成调用虚构的外部工单服务。创建请求已发出，但响应超时。分别说出：① 对方在当前端点、账号和保留期内承诺支持幂等重放；② 对方没提供可信的幂等契约，或键可能已过期。两种情况下怎么处理？只做纸面推演，不调用外部服务。

点击查看参考答案
  • ① 可以按契约重放：在预算和契约有效期内，用首次保存的键和相同参数重发到同一作用域，并按对方契约解读返回结果。如果预算已用完、仍没收到业务结论，则保留原引用核对，不换路重发。
  • ② 不能盲目重放：保留“结果未知”，用业务引用核对外部状态或回执。确认已有工单则记录原编号，确认首个请求没创建工单且不会再生效才考虑补做；无法确认就交人工。自己在本地保存一个键，不能让对方去重。
🎤 面试高频①："如何处理速率限制（429）？"

答：先确认能安全重放，再由唯一重试负责人用指数退避和 full jitter 打散重试；若契约要求 Retry-After，遵守其最短等待。次数用完或等待排不进截止时间就不再试；每次发起前重算单次超时。Tenacity 提供退避策略，但停止策略不替传输层兑现超时。

🎤 面试高频②："有副作用的工具调用怎么安全重试？"

答：首次尝试前保存操作键，重试时复用；在同一作用域内核对请求参数。同库内把业务变更和操作记录、结果原子提交，重放返回保存的结果，同键不同参数直接拒绝。外部副作用只能按供应商明确的作用域及保留期重放；没有可信契约且结果未知，就核对状态，不盲重试。

Q 第 29 秒遇到可重放的失败，次数尚有余量，计划等 2 秒。两种 30 秒停止策略会怎么做？
stop_after_delay 只看已用的 29 秒；stop_before_delay 还计入计划的 2 秒。调用方若要约束实际发起与每次尝试的时长，要在发起前重新测剩余预算，并让传输层兑现适用的超时。

def retry_wait(now, deadline, local_wait, retry_after):
    wait = max(local_wait, retry_after)
    return wait if now + wait < deadline else None

🎯 速查卡：错误处理·退避·幂等

【第一步：分类】
  429 限流 / 5xx 服务端 / 超时 / 网络抖动 → 先判断能否安全重放
  400 参数 / 401 鉴权 / 404 → 立即 fail fast

【退避】exponential backoff
  等待 = base × 2**attempt   （1s→2s→4s→8s）给服务端喘息
  别手写 → tenacity: wait_exponential

【抖动】jitter ⚠️ 灵魂
  问题：纯退避 → 千客户端【同步】重试 → 重试风暴 thundering herd
  解法：full jitter → wait = random.uniform(0, base * 2**attempt)
        把重试时间打散，波峰抹平
  tenacity: wait_random_exponential（退避+抖动，一行搞定）

【重试预算】整条调用链只设一个重试负责人
  stop_after_attempt(N)：最多 N 次尝试，含首次
  stop_after_delay(T)：只看已用时间；stop_before_delay(T)：还计入下一次等待
  两种时间停止策略都不取消执行中的调用
  调用方截止：不排触及截止的等待；发起前重算剩余，无余量则不发
  单次超时 = min(单次上限, 剩余时间)，由传输执行

【幂等键】idempotency key
  同一业务操作 → 同一作用域、复用首次保存的键、核对参数
  同库 → 业务写入与操作记录、结果原子提交；重放返回保存的结果
  外部 → 只在供应商支持的作用域和保留期内按契约重放
  预算耗尽或不能安全重放时，未知写入须核对；不盲重发或换路

【Agent 分水岭】一次任务几十次调用，任何一次都可能失败
  先判能不能重放，再决定怎么退避、何时停止。

总结

  • 生产 Agent 必须假设调用会失败；临时错误是重试候选，还要判断是否能安全重放
  • 指数退避给服务端喘息（1s→2s→4s→8s），原理懂即可，用 tenacity
  • 抖动(full jitter)是灵魂：纯退避会让客户端同步重试→重试风暴，随机打散才能救场
  • 单一重试负责人限制总尝试数（含首次）。停止策略只管排程；调用方在截止前核对等待和发起时机，传输用剩余时间限制单次尝试。
  • 幂等键在首次尝试前保存，在同一作用域内重试复用并核对参数；同库把业务写入和操作记录、结果原子提交
  • 外部副作用只按供应商支持的作用域和保留期重放；不能重放或预算已尽时，保留未知结果和原引用以便核对。
