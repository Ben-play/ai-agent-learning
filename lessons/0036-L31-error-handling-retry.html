错误处理、退避与幂等

生产 Agent 必须假设"调用会失败"——退避 + 抖动 + 幂等，是 demo 与上线的分水岭

💡 为什么这课重要？

前面几课你学会了把 LLM 调起来、流式输出、管理 Context。但那些都是"顺风局"。真实生产里，调用一定会失败：限流(429)、服务端崩(5xx)、超时、网络抖动。一个 Agent 完成一次任务要发几十次 API / 工具调用——任何一次都可能失败。

L10 已经教过你 tenacity 做指数退避重试——那是地基。这一课往上盖两根生产级的承重柱：抖动(jitter)——防止一群客户端同时重试把服务端二次打垮；幂等键(idempotency key)——让"扣款/下单/发消息"这类有副作用的调用重试也安全。没有这两样，你的 Agent 要么被限流拖死、要么重复扣钱。

学习目标

完成本课后，你将能够：

  • 区分可重试（429/5xx/超时）与不可重试（400/401）错误
  • 理解指数退避为何不够，必须加抖动（full jitter）防"重试风暴"
  • 设置重试预算（最大次数 + 总时间上限），到点 fail fast
  • 用幂等键让有副作用的操作"重试只生效一次"
  • 说清楚这套机制为什么是 Agent"能上生产"的门槛

1. LLM API 一定会失败——先学会分类

生产 Agent 的第一条心法：不要假设调用会成功。常见失败有四类：

  • 429 限流（rate limit）：你发太快 / 超了配额，服务端让你"稍后再来"。
  • 5xx 服务端错误：500 / 502 / 503，是对方的问题，通常是临时的。
  • 超时：请求发出去但迟迟没回，可能网络慢、也可能对方在排队。
  • 网络抖动：连接被重置、DNS 抽风等瞬时故障。

但不是所有错误都该重试。关键要分两类——重试错类型只会浪费时间、甚至火上浇油：

【可重试】临时性、换个时间可能就好了
  429 限流 / 5xx 服务端 / 超时 / 网络抖动
     → 退避后重试有意义

【不可重试】你自己的请求有问题，重试 100 次还是错
  400 参数错误   → 你的 payload 就是错的，重发没用
  401 鉴权失败   → key 不对，重发只会一直 401
  404 资源不存在 → 目标就是没有
     → 别重试，立即 fail fast 把错误抛给上层

Agent 关联：Agent 循环里一次工具调用失败，先判类型再决定"退避重试"还是"直接报错"。把 401 拿去重试，只会白白拖慢整条链路、还刷爆日志。

Q 下面哪个错误最不该自动重试？
401 是鉴权失败——你的 key 不对，这是确定性的错误，重试 100 次还是 401，纯属浪费时间和配额。它属于不可重试类，应立即 fail fast。而 429（限流）、5xx（服务端临时故障）、超时都是临时性问题，退避后重试有意义。区分"可重试 vs 不可重试"是错误处理的第一步。

2. 指数退避：给服务端喘息的空间

失败后立刻重试是最糟的做法——服务端正忙不过来，你还猛捶它。正确姿势是指数退避（exponential backoff）：每失败一次，等待时间翻倍。

第 1 次失败 → 等 1s → 重试
第 2 次失败 → 等 2s → 重试
第 3 次失败 → 等 4s → 重试
第 4 次失败 → 等 8s → 重试
       等待 = base × 2 ** attempt   （指数增长）

越等越久，给对方留出恢复时间。原理你要懂，但生产别自己造轮子——正如 L10 讲过的，tenacity 内置了这一切：

from tenacity import retry, stop_after_attempt, wait_exponential

@retry(stop=stop_after_attempt(4),
       wait=wait_exponential(multiplier=1, min=1, max=8))  # 约 1→2→4→8s（封顶 8s，实际序列以 tenacity 为准）
def call_llm(prompt):
    return client.chat.completions.create(...)   # 失败自动退避重试

但纯指数退避有个致命缺陷——它在"很多客户端同时失败"时会自己制造灾难。这正是下一节的主角。

3. 抖动（jitter）：防重试风暴 ⚠️ 本课重点

想象一个真实场景：服务端抖了一下，1000 个客户端在同一瞬间全部收到 5xx。它们都用"标准指数退避"，于是会发生什么？

t=0s   服务端抖动，1000 个客户端同时失败
t=1s   → 1000 个客户端【一起】重试   💥 又把服务端打垮
t=3s   → 1000 个客户端【一起】重试   💥 再垮一次
t=7s   → 1000 个客户端【一起】重试   💥 …死循环

因为大家的退避节奏完全同步，重试请求会聚成一波又一波的"脉冲"，反复砸向刚要恢复的服务端。这就是重试风暴 / 惊群效应（thundering herd）——退避不但没救服务端，反而亲手把它按死。

解法：加随机抖动（jitter）。核心思想是把重试时间打散，让 1000 个客户端不再"齐步走"。业界最推荐的是 full jitter——等待时间在 [0, backoff] 区间里随机取：

import random

# ❌ 纯指数退避：所有客户端等待时间【一模一样】→ 同步重试
wait = base * 2 ** attempt

# ✅ full jitter：在 [0, backoff] 里随机 → 重试时间被打散
wait = random.uniform(0, base * 2 ** attempt)
#         ↑ 每个客户端随机落在 0~backoff 之间，波峰被抹平

加了 jitter 后，那 1000 个客户端会均匀地散布在 0~1s、0~2s…里陆续重试，服务端面对的是平缓的涓流而非"脉冲海啸"，得以真正恢复。AWS 的经典模拟证明：full jitter 显著降低服务端负载、缩短整体恢复时间（见本课 primary source）。

🔑 好消息：tenacity 内置抖动，一行开启 
from tenacity import retry, stop_after_attempt, wait_random_exponential

@retry(stop=stop_after_attempt(5),
       wait=wait_random_exponential(min=1, max=30))   # 指数退避 + 随机抖动
def call_llm(prompt):
    return client.chat.completions.create(...)

wait_random_exponential 就是"指数退避 + full jitter"的开箱即用版。别手写——你只需知道背后为什么要这么做。

Agent 关联：生产 Agent 往往是"一群实例并发跑"。一旦上游 LLM 网关抖动，没有 jitter，你的整个 Agent 集群就会自发形成重试风暴，把本可自愈的小故障放大成雪崩。

Q 纯指数退避（不加抖动）在大量客户端同时失败时的问题是？
纯指数退避下，所有客户端的等待时间完全一致，于是在 1s/2s/4s 后一起重试，聚成一波波脉冲反复砸向刚要恢复的服务端——这就是重试风暴 / 惊群效应（thundering herd）。解法是加随机抖动（full jitter），把重试时间打散到 [0, backoff]，让请求变成平缓涓流。

4. 重试预算：别无限重试

退避 + 抖动解决了"怎么重试"，但还有个问题：重试几次才放弃？ 答案绝不是"一直重试"。如果服务端真的挂了，无限重试只会让请求越堆越多，最终连你自己的进程都被拖垮。

要给重试设预算（retry budget）——两条硬上限，任一触顶就fail fast（立即认输、把错误抛给上层）：

【重试预算 = 两条上限】
  ① 最大次数：最多重试 N 次（如 5 次）
  ② 总时间上限：整个重试过程不超过 T 秒（如 30s）

  任一触顶 → 立即抛错，别再堆请求
from tenacity import retry, stop_after_attempt, stop_after_delay, wait_random_exponential

@retry(
    stop=(stop_after_attempt(5) | stop_after_delay(30)),  # 5 次 或 30s，先到先停
    wait=wait_random_exponential(min=1, max=15),
    reraise=True,                                          # 到点抛出真实异常
)
def call_llm(prompt):
    return client.chat.completions.create(...)

fail fast 好过慢慢拖死：与其让用户等 5 分钟最后还是失败，不如 30 秒内明确报错，让上层去走 L32 的 fallback（换模型/换供应商）或友好降级。

5. 幂等键：让有副作用的重试安全 ⚠️ 本课重点

到这里有个被忽略的致命陷阱。前面的重试对"读"类操作很安全——多查一次天气无所谓。但如果工具调用有副作用呢？

场景：Agent 调用"扣款"工具
  1. 请求发出：扣用户 100 元 ✅ 服务端【已经扣了】
  2. 但响应在回来的路上超时了 ⏱️
  3. 你的重试逻辑："没收到成功？那再扣一次！"
  4. 结果：扣了 200 元 💸💸  ← 真金白银的损失

下单、发消息、扣款——这类操作重试 = 重复执行 = 重复副作用。超时最阴险：你根本不知道"到底扣没扣"，盲目重试就可能重复扣款。

解法：幂等键（idempotency key）。给每次操作分配一个唯一确定的 id，服务端（或你自己）在执行前先查这个键是否处理过：处理过就跳过、直接返回上次结果。这样"重试同一操作"无论发多少次，只会真正生效一次。

# 幂等的核心结构（伪代码）
def do_once(key, action):
    if already_done(key):        # 先查：这个键处理过吗？
        return cached_result(key)  # 处理过 → 跳过，返回上次结果
    result = action()             # 没处理过 → 真正执行
    mark_done(key, result)        # 记下：这个键已完成
    return result

# 无论调几次，同一个 key 只会 action() 一次

already_done / mark_done 靠什么实现？两种业界标准，都利用了"原子性的唯一约束"：

  • Redis SET key NX：只在键不存在时才写入成功（NX = Not eXists）。第一个请求抢到锁执行，重试的请求写入失败 → 知道"已处理"。记得配 TTL（如 24h），避免崩溃留下死锁。
  • 数据库唯一约束：把幂等键设成唯一索引，重复插入直接被数据库拒绝——对"扣款"这类财务操作，这是最权威的一道防线。

成熟的 API 早就这么做了：Stripe 支持 Idempotency-Key 请求头，同一个 key 的重复请求返回缓存的首次结果而非重复扣款（结果缓存 24h）。你的 Agent 工具也应照此设计。

💡 关键细节：key 要在"第一次尝试前"就生成好

幂等键必须客户端生成、并在所有重试中复用同一个（如一个 UUID）。如果每次重试都新生成 key，服务端会以为是"全新操作" → 幂等失效、照样重复扣款。

Agent 关联：Agent 最危险的地方就是它会自主调用有副作用的工具。没有幂等键，一次网络超时 + 一次盲目重试 = 用户被重复扣款、消息被发两遍。幂等是让 Agent"敢碰真实世界"的安全带。

Q 幂等键为什么能让"扣款"这类操作重试也安全？
幂等键给操作一个唯一确定的 id，执行前先查这个键是否处理过（Redis SET NX / DB 唯一约束）：已处理就跳过、返回上次结果。所以同一个 key 无论重试多少次，真正的扣款动作只会生效一次——重复的重试被安全地去重了。注意 key 要客户端生成并在重试间复用同一个。

6. 拼起来：这就是"能上生产"的分水岭

把五块拼成一张图——这正是 L10 的地基之上，生产 Agent 该有的完整错误处理姿态：

一次 Agent 工具/API 调用失败时：
  ┌─ 是不可重试错误(400/401/404)？ ── 是 → 立即 fail fast，抛给上层
  │
  └─ 是可重试错误(429/5xx/超时)？   ── 是 ↓
       ┌── 有副作用(扣款/下单/发消息)？→ 带上幂等键，保证只生效一次
       ├── 指数退避 + full jitter（防重试风暴）
       └── 受重试预算约束（≤N 次 且 ≤T 秒）── 超了 → fail fast → L32 fallback

一个 Agent 完成任务要发几十次调用，任何一次都可能踩中失败。缺了这套机制：没退避 → 捶爆服务端；没抖动 → 集群自造重试风暴；没预算 → 请求堆到进程崩；没幂等 → 重复扣款发双消息。"能跑 demo"和"能上生产"，差的就是这一课。

🧠 动手想一想：超时后"不知道扣没扣"，幂等键怎么救？

场景：你的 Agent 调用扣费工具，请求发出后网络超时——你收不到任何响应，完全不知道服务端到底扣款成功了没有。此时你想重试（万一没扣呢？），但又怕重复扣款（万一扣了呢？）。请说明：引入幂等键后，这次重试为什么就安全了？

💡 点击查看参考答案

关键在于：幂等键在第一次请求前就生成好了（比如一个 UUID op-8f3a...），并且重试时复用同一个 key。于是有两种可能，且都安全：

  • 情况 A：首次其实已扣款成功（只是响应超时丢了）。重试带着同一个 key 到达服务端，服务端一查"这个 key 已处理过" → 不再扣款，直接把上次的成功结果返回给你。✅ 没有重复扣款。
  • 情况 B：首次根本没扣成（请求半路就丢了）。重试带着同一个 key 到达，服务端一查"这个 key 没见过" → 正常执行扣款。✅ 该扣的扣上了。

所以无论真实情况是 A 还是 B，带幂等键的重试都恰好让扣款"生效且仅生效一次"——你不必再纠结"到底扣没扣"，放心重试即可。这就是幂等键把"不确定 + 重试"变安全的原理。（实现上，服务端用 Redis SET NX 或 DB 唯一约束来判断 key 是否处理过。）

🎤 面试高频①："如何处理速率限制（429）？"

答：① 指数退避——失败后等待时间翻倍，给服务端喘息；② 加 full jitter——把重试时间随机打散到 [0, backoff]，防止大量客户端同步重试引发重试风暴（thundering herd）；③ 设重试预算——最大次数 + 总时间上限，超了 fail fast；④ 先区分可重试 / 不可重试（429/5xx/超时才重试，400/401 别重试）。工程上用 tenacity 的 wait_random_exponential，别手写。

🎤 面试高频②："有副作用的工具调用怎么安全重试？"

答：用幂等键（idempotency key）。给每次操作一个客户端生成、重试间复用的唯一 id；执行前先查重（Redis SET NX 或 DB 唯一约束），键已处理就跳过并返回上次结果。这样"重试同一操作只会真正生效一次"，避免超时后盲目重试导致重复扣款/下单。关键坑：key 必须首次请求前生成、重试复用同一个，否则幂等失效。

🎯 速查卡：错误处理·退避·幂等

【第一步：分类】
  可重试  → 429 限流 / 5xx 服务端 / 超时 / 网络抖动
  不可重试 → 400 参数 / 401 鉴权 / 404 → 立即 fail fast

【退避】exponential backoff
  等待 = base × 2**attempt   （1s→2s→4s→8s）给服务端喘息
  别手写 → tenacity: wait_exponential

【抖动】jitter ⚠️ 灵魂
  问题：纯退避 → 千客户端【同步】重试 → 重试风暴 thundering herd
  解法：full jitter → wait = random.uniform(0, base * 2**attempt)
        把重试时间打散，波峰抹平
  tenacity: wait_random_exponential（退避+抖动，一行搞定）

【重试预算】retry budget
  ① 最大次数(N)  ② 总时间上限(T)  任一触顶 → fail fast
  tenacity: stop_after_attempt(N) | stop_after_delay(T)

【幂等键】idempotency key ⚠️ 灵魂
  致命：有副作用(扣款/下单/发消息)重试 → 重复副作用 💸
  解法：唯一 key，执行前查重，已处理就跳过 → 只生效一次
        if not already_done(key): do_action(); mark_done(key)
  实现：Redis SET NX（配 TTL）/ DB 唯一约束
  ★ key 客户端生成 + 重试复用【同一个】，否则失效

【Agent 分水岭】一次任务几十次调用，任何一次都可能失败
  缺退避→捶爆服务端  缺抖动→集群自造风暴
  缺预算→请求堆崩    缺幂等→重复扣款
  = demo 与生产之别

总结

  • 生产 Agent 必须假设调用会失败；先分可重试(429/5xx/超时) vs 不可重试(400/401)
  • 指数退避给服务端喘息（1s→2s→4s→8s），原理懂即可，用 tenacity
  • 抖动(full jitter)是灵魂：纯退避会让客户端同步重试→重试风暴，随机打散才能救场
  • 重试预算（最大次数 + 总时间）到点 fail fast，别把请求堆死
  • 幂等键是灵魂：有副作用的操作靠唯一 key + 执行前查重（SET NX / 唯一约束）做到"只生效一次"，key 要客户端生成、重试复用
  • 退避 + 抖动 + 幂等，是 Agent 从"能跑 demo"迈向"能上生产"的分水岭
