第三阶段 · LLM API 工程实践 25分钟

Context Window 管理

对话越滚越长，窗口迟早撑爆——这是 Agent 能不能"长时间跑"的命脉

💡 为什么这课重要？

L25 你学会了"多轮对话要把历史全塞回 messages"。但这里藏着一个致命问题：历史会无限增长，上下文窗口却是有限的（L21）。Agent 每走一步就往对话里堆一轮 user/assistant、再堆一坨工具返回结果——十几步之后，窗口迟早撑爆。撑爆的下场只有两种：要么直接报错，要么悄悄丢掉早期信息，两者对一个正在执行长任务的 Agent 都是灾难。

更糟的是，就算没撑爆，长上下文本身也有两个税：一是 lost-in-the-middle（L21——放在中间的信息利用率最低，模型容易"看不见"），二是成本随长度线性上涨（L23——每次都把长历史当输入发出去）。所以上下文不能放任它长，必须主动管理。这一课就教你在 API 层怎么管。

学习目标

完成本课后，你将能够：

  • 说清上下文撑爆的两种后果，以及 lost-in-the-middle、成本两个"隐性税"
  • 掌握三大管理策略：滑动窗口 / 摘要记忆 / 压缩精简，知道各自的取舍
  • 用 tiktoken（L18）在发请求前数 token，超阈值就触发策略
  • 写出"计数 → 超阈值 → 摘要旧消息 → 重组 messages"的正确控制流
  • 知道该保什么、该压什么——保 system + 关键信息，压中间冗余

1. 问题：历史无限长，窗口却有限

回忆 L21：LLM 的上下文窗口（context window）是固定容量的——一次能塞进去的 token 数有上限（具体上限以模型而定，几 K 到几百 K 不等）。再回忆 L25：Agent 要"有记忆"，就得每次把全部历史回传。这两件事凑在一起，就是一颗定时炸弹：

  • 历史单调增长：每一轮对话、每一次工具调用的返回，都往 messages 里累加。工具输出尤其"肥"——一次网页抓取、一段日志、一个大 JSON，动辄上千 token。
  • 撑爆 = 报错或丢信息：输入超过窗口上限，要么 API 直接抛错（请求被拒），要么框架帮你"截断"——但截断可能正好切掉了任务开头那句最关键的目标。
  • lost-in-the-middle（L21）：即便没爆，塞得太满时，模型对中间段落的利用率会明显下降——重要信息夹在中间容易被"忽略"。
  • 成本随长度涨（L23）：每次请求都把整段长历史当输入 token 计费，对话越长、单次越贵，长任务累计更是可观。

结论很直接：不能等它爆，要在爆之前主动把上下文"瘦身"。这就引出了下面三大策略。

Q Agent 跑长任务时，为什么上下文迟早会出问题？
根因是两件事的冲突：为了让 Agent 有记忆，每次要把历史全回传（L25）；但上下文窗口容量固定（L21）。历史随每一轮对话和每次工具返回单调增长，迟早超过窗口上限——撑爆就报错或丢信息。此外长上下文还有 lost-in-the-middle 和成本上涨两个隐性税。所以必须主动管理，而不是指望模型或 API 自己清理。

2. 三大策略：滑动窗口 / 摘要记忆 / 压缩

管理上下文的核心思路，都是"用更少的 token 装下够用的信息"。三种主流做法，从粗到精：

策略做法优点代价
滑动窗口
(sliding window)		 只保留最近 N 轮对话，更早的直接丢掉 实现最简单，token 稳定可控 会硬丢早期信息——任务开头的目标可能被丢掉
摘要记忆
(summarization)		 把老对话压成一段摘要塞回上下文，保留要点 比丢弃聪明——要点还在，token 大幅缩减 要多花一次 LLM 调用做摘要；摘要可能丢细节
压缩 / 精简
(compression)		 去掉冗余：重复的工具输出、无关内容，只留有用的 无损或近无损，专杀"肥"工具结果 要判断"什么是冗余"，规则/逻辑更复杂

三者不是三选一，常常组合使用：比如"最近 N 轮原样保留（滑动窗口）+ 更早的压成摘要（摘要记忆）+ 沿途剔除重复工具输出（压缩）"。对 Agent 而言，工具返回是上下文膨胀的头号来源，所以压缩工具结果往往性价比最高。

埋点 · compaction：把一大段历史压成摘要、再用摘要接着往下跑，这个动作在 2026 年的 Agent harness（Claude Code、各类 agent 框架）里叫 compaction，已是标准做法——上下文快满时自动触发一次"压缩重启"，让 Agent 能持续跑很久而不爆。本课先在 API 层掌握它的原理；到 Phase 5 讲 agentic memory 时，我们会把它做成 Agent 的核心机制。

3. 实操思路：先数，超阈值再触发

策略怎么落地？核心是一条发请求前的检查：用 tiktoken（L18）数一下当前 messages 的 token，超过阈值就触发瘦身。阈值一般设成窗口上限的某个比例（如 75%），给模型的回复留出余量。控制流长这样：

import tiktoken

enc = tiktoken.get_encoding("cl100k_base")   # 示例编码器；实际应按你的模型选（L18，如 encoding_for_model）

def count_tokens(messages):
    # 粗略计数：把每条消息内容拼起来数 token
    return sum(len(enc.encode(m.get("content") or "")) for m in messages)

def manage_context(messages, limit, keep_recent=4):
    # 1) 计数：还没超阈值就原样发
    if count_tokens(messages) <= limit:
        return messages

    # 2) 超阈值 → 拆分：system + 最近 keep_recent 轮 要保住，中间的老消息拿去压缩
    system_msgs = [m for m in messages if m["role"] == "system"]
    body        = [m for m in messages if m["role"] != "system"]
    old, recent = body[:-keep_recent], body[-keep_recent:]

    # 3) 摘要旧消息（compaction）：让 LLM 把 old 压成一段要点
    summary = summarize_with_llm(old)        # 另一次 LLM 调用，产出简短摘要

    # 4) 重组 messages：system + 摘要 + 最近几轮 → token 大幅下降
    return system_msgs + [
        {"role": "system", "content": "早前对话摘要：" + summary}
    ] + recent

# 每次发请求前先过一遍
messages = manage_context(messages, limit=6000)   # 阈值 < 窗口上限，留回复余量
resp = client.chat.completions.create(model=..., messages=messages)

四步记牢：① 计数 → ② 超阈值就拆（保 system + 最近几轮）→ ③ 摘要旧消息 → ④ 重组 messages。若走纯滑动窗口，把第 ③ 步省掉、第 ④ 步直接扔掉 old 即可；若走压缩，则在第 ③ 步换成"去重/裁剪工具输出"。这套检查就是 Agent 主循环里每次调 LLM 前都要跑的守卫。

Q 什么时候该触发上下文瘦身？
正确做法是主动、提前：每次发请求之前，用 tiktoken 数当前 messages 的 token，一旦超过阈值（通常设为窗口上限的某个比例，给回复留余量）就触发策略。等 API 报错才处理已经晚了——请求已经失败。也不必每轮都压（没超阈值时压缩纯属浪费一次 LLM 调用和信息）。

4. 保留什么：system + 关键信息优先

瘦身不是"无脑砍最老的"——砍谁、留谁大有讲究。优先级从高到低：

  • system prompt 永远保：它定义了 Agent 的角色、规则、任务目标（L25 讲的"人设"）。丢了它，Agent 直接"忘了自己是谁、在干嘛"。
  • 最近的关键信息优先保：当前正在处理的子任务、最新的工具结果、用户刚提的要求——这些是"现在正用得上"的。
  • 中间的冗余先压：早已用完的中间步骤、重复的工具输出、跑偏后被纠正的弯路——这些压成一句摘要甚至直接删。

这里正好呼应 lost-in-the-middle（L21）：既然模型对"中间"利用率最低，那就把最重要的信息放在开头（system）或结尾（最近消息），把要压缩/丢弃的目标锁定在中间段——一举两得：既省 token，又避开了模型的"视觉盲区"。压缩不只是省钱，还是在帮模型把注意力放对地方。

Q 上下文瘦身时，最该优先保留的是哪部分？
system prompt（定义角色/规则/目标）和最近的关键信息（当前子任务、最新工具结果）优先级最高，要保住；中间的冗余（重复工具输出、跑偏的弯路）先压。这也呼应 lost-in-the-middle（L21）：模型对中间利用率最低，所以把重要信息放开头或结尾、把要压缩的目标锁在中间——省 token 又避开模型盲区。

5. 为什么这是 Agent 的命脉

把镜头拉远：Context Window 管理，直接决定 Agent 能不能"长时间跑"。

  • 一个只聊两三轮的 chatbot，可能永远碰不到窗口上限，管不管无所谓。
  • 但一个要连续执行几十步的 Agent——查资料、调工具、读结果、再决策——上下文是单调膨胀的。没有 context 管理，长任务必崩：不是中途报超限错，就是把开头的目标丢了导致跑偏。

所以你可以把它理解成 Agent 的"呼吸系统"：靠 compaction 一次次把历史压缩重启，Agent 才能在有限窗口里跑出远超窗口容量的任务长度。这一课我们先在 API 层掌握窗口管理的基本功（计数、阈值、三策略、保什么）；到 Phase 5，我们会把它升级成 agentic memory / 结构化笔记——让 Agent 把重要信息主动"记"到外部存储，而不只是在对话里压来压去。先把这一课的地基打牢，Phase 5 才盖得起楼。

🛠 动手练一练：8000 token、窗口上限 8192，你怎么办？（点击展开）

场景：你的 Agent 跑到一半，当前 messages 已累计约 8000 token，而所用模型的窗口上限是 8192。下一步还要发一次请求、并让模型回复约 500 token。请回答：

  1. 直接把这 8000 token 发出去，会发生什么？
  2. 该用哪个（些）策略？怎么重组 messages？

先自己想 30 秒，再看下面的参考答案。

参考答案

1) 会撑爆。 输入 8000 + 要回复 500 ≈ 8500，已超过 8192 上限——请求要么直接报错，要么框架帮你截断（可能切掉开头目标）。而且上下文越长，中间信息越容易被淹没（lost-in-the-middle）。不能原样发。

2) 触发瘦身，优先「摘要记忆 + 保关键」。 按第 3 节的四步走：

  • 计数：确认 8000 已超过阈值（比如阈值设 6000，早就该触发了）。
  • 拆分：system（任务目标）保住；最近 3~4 轮对话/工具结果原样保住；中间的老消息拎出来。
  • 摘要：把中间老消息用一次 LLM 调用压成一段简短摘要（compaction），把里面重复的、跑偏的、已用完的内容压掉。
  • 重组：[system] + [{"role":"system","content":"早前摘要：…"}] + [最近几轮]。这样 token 从 8000 降到比如 2000~3000，既腾出了回复空间，又把重要信息放在了开头和结尾（避开中间盲区）。

如果嫌摘要要多花一次调用，也可退而求其次用纯滑动窗口（只留最近 N 轮 + system）——更快，但会硬丢早期信息，适合早期信息确实不重要的场景。若膨胀主要来自某个巨大的工具输出，则优先压缩/裁剪那条工具结果，往往一步就够。
