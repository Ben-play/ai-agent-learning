A2A 的任务边界

能力卡让你找到候选；主体绑定决定谁能看、谁能取消

为什么这课重要？

客服 support/mei 被问到「导出文件保留多久、同步几点运行」。在 L89 的同进程委托里，宿主自己维护工作边界。如果取证由独立维护的另一套系统完成，发出委托后还要能查状态、取消未完成任务，并决定是否接纳结果；函数调用的返回值不够表达这段生命周期。这里用纯内存的客服取证替身：只有两份合成记录、两个固定任务；不接对端、不运行网络 Agent、不使用凭据，也不写业务数据。

学习目标

  • 区分能力发现、身份可信来源、任务对象授权与结果接纳。
  • 沿待完成、已取消和已完成三种状态对账，核对错主体、串任务和迟到结果均不改变原状态。
  • 说明哪些证据支持引入 A2A，哪些证据只支持保留进程内工作流。

1. 先发现候选，再校验任务归属

Agent-to-Agent（A2A）为独立系统之间的交互提供共同术语和操作。课程固定官方规范 A2A 1.0.0 与 Python SDK 1.3.1 的 README：前者核对规范名称，后者只作固定版本的项目说明。不安装或运行 SDK，也不声明这两个版本与课堂代码兼容、协议一致或能与任何实现互通。

Agent Card 是能力说明，不是授权。规范中的卡片可描述对端技能、接口与安全要求，不能证明你就是任务的拥有者。课堂卡片进一步简化成 AgentCard(peer="classroom-policy-desk", capability="support-evidence")。拿到卡片的运维 ops/mei 与同租户的 support/lin 都不能据此查看或取消客服 support/mei 的任务。Actor(tenant, name) 由可信宿主单独传入；任务存了完整二元组，不从卡片、任务 ID 或结果中重新认领身份。

同一客服工单的本地数据形状（不是协议请求）
形状导出取证样例谁决定
任务记录Task(id, owner, peer, state, evidence)；ID 为 task-export，初态 WORKING、无证据宿主创建一次，锁定主体和预期对端；同一 ID 不重开。
查状态／取消宿主传入当前 Actor("support", "mei") 和 task-export课堂只允许绑定主体；查无此项与不可访问返回同样的 not_found，且不附任务。
结果交接PeerResult(task_id, peer, evidence)；证据为 EXPORT-POLICY v1 §1「导出文件生成后保留 7 天。」按宿主记住的原 ID 查任务；核对结果的 ID、对端标签、工作状态及四项证据字段才接纳。对端标签只是合成关联值，不证明网络身份。
Q 运维 ops/mei 看到了能力卡，也知道导出任务 ID。查看任务时该怎么做？
能力与编号只帮助定位，授权以当前可信主体和已绑定任务为准；不能连存在性或状态也泄露给无权方。

2. 查询、取消和接纳结果各有一道门

规范把两项操作命名为 GetTask 和 CancelTask：前者读取现有任务，后者请求取消，不能保证任务仍可取消。规范枚举的拼写是 TASK_STATE_CANCELED，只有一个 L；课堂 CANCELED 是短名，不是传输字段。get_task、cancel_task 是本地方法，not_found、not_cancelable 是本地诊断码，不是线上绑定的错误格式。课堂只覆盖 WORKING、CANCELED、COMPLETED，不实现规范的完整状态机或传输层。

跟做干跑：先取消，后收到本来正确的导出证据
步本地操作可核对的结果
1发现 support-evidence；运维尝试提交，随后由客服提交运维 not_found；客服建立一条绑定任务，WORKING、无证据。
2运维查询，客服查询前者与不存在的 ID 一样只得 not_found；后者查到原快照。
3客服取消；再注入原任务、原对端的正确证据取消变为 CANCELED；结果接纳报 not_working。再查与取消时的快照完全相同，证据仍为空。

结果接纳先核对关联，再看状态。binding_mismatch 时对照宿主原 ID 与对端标签；evidence_mismatch 时核对文档、版号、定位和原文；两者都不能写入结果。not_working 表示任务不能再接结果，先查原终态，不能重新提交同一 ID 来抹掉历史。若结果先被接受，任务是 COMPLETED；之后取消只报 not_cancelable，不擦去原证据。相同取消请求再来时，本地不新增状态变化，不承诺返回原响应。这里只比较顺序执行的两条时间线，不证明并发竞争、对端工作停止或业务撤销。

决策卡：独立系统有任务生命周期，才考虑 A2A

适用：独立团队确实需要通用的委托、查询与取消合同。不适用：客服只在本进程做有限取证；保留直接函数或 L89 受限工作流。

误判：卡片和任务编号足够

同一导出任务只按编号查询、取消和接收结果，错主体或迟到结果也可能改变交付。

选择：每个动作按它的边界判断

查与取消验当前主体；接纳验原任务、对端、状态和证据。先取消后的证据没有资格改写终态。

  1. 先跑错主体与不存在任务的对照，确认同样拒绝且原状态未动。
  2. 各跑一次「取消先到」与「结果先到」，重查完整快照而非只看返回码。

代价：要维护版本契约、任务相关性、错误与对账；课程只验证本地不变量，真实身份、互通与并发取消需另行验收。

Q 原任务已是 CANCELED，同一对端送来来源也正确的证据。怎么处置？
关联和来源匹配只是必要条件；终态还要挡住接纳。核对任务重查结果与取消快照一致。

独立变式：同步证据先到，再收到取消

新建任务台，同时提交同工单的同步和导出分支，不依赖跟做数据。先让同租户的 support/lin 取消同步；再把仍在工作的导出结果交到同步任务，并试带错对端标签的同步结果。两个任务都不得被错投改变。只有正确同步证据可完成同步任务。最后再由拥有者取消，并重放一次正确结果。

from dataclasses import replace
import sys

if not __debug__:
    raise RuntimeError("run without -O")
sys.dont_write_bytecode = True
sys.path.insert(0, "code/phase10-framework-evolution/evolution-lab/protocols")
from l90_a2a import LIN, MEI, TRANSFER_TASK, WORKED_TASK, Evidence, Reply, State, Task, TaskDesk, classroom_result

desk = TaskDesk()
started = desk.submit(MEI, TRANSFER_TASK)
assert started == Reply("ok", Task("task-sync", MEI, "classroom-policy-desk", State.WORKING))
other = desk.submit(MEI, WORKED_TASK)
assert other == Reply("ok", Task("task-export", MEI, "classroom-policy-desk", State.WORKING))
assert desk.cancel_task(LIN, TRANSFER_TASK) == Reply("not_found")
genuine = classroom_result(TRANSFER_TASK)
for result in (classroom_result(WORKED_TASK), replace(genuine, peer="other-classroom-desk")):
    assert desk.accept_result(TRANSFER_TASK, result) == "binding_mismatch"
    assert desk.get_task(MEI, TRANSFER_TASK) == started
    assert desk.get_task(MEI, WORKED_TASK) == other
wrong_source = replace(genuine, evidence=replace(genuine.evidence, version=2))
assert desk.accept_result(TRANSFER_TASK, wrong_source) == "evidence_mismatch"
assert desk.get_task(MEI, TRANSFER_TASK) == started
assert desk.accept_result(TRANSFER_TASK, genuine) == "accepted"
expected = Evidence("SYNC-POLICY", 1, "§1", "同步任务每天 02:00 运行。")
completed = Reply("ok", Task("task-sync", MEI, "classroom-policy-desk", State.COMPLETED, expected))
assert desk.get_task(MEI, TRANSFER_TASK) == completed
assert desk.cancel_task(MEI, TRANSFER_TASK) == Reply("not_cancelable")
assert desk.accept_result(TRANSFER_TASK, genuine) == "not_working"
assert desk.get_task(MEI, TRANSFER_TASK) == completed
print("L90 TRANSFER PASSED")

面试自查

先说能不能做，再说用哪条证据确认。

Q1 卡片写着支持取证，运维又与客服同名，查询能只按用户名通过吗？

参考回答：不能。查与取消需要当前可信主体及完整任务绑定；名字相同不代表租户相同。

追问：换成同租户的另一位客服呢？

答题要点：本地仍需匹配拥有者；若产品支持共享，需独立授权规则与正负控，不由卡片默认放行。

Q2 客服已收到取消成功，迟到结果的证据又确实正确。可以保留在该任务里吗？

参考回答：不接纳；状态门保护取消快照。重查应无新证据，也不改变终态。

追问：如果结果先被成功接纳，再来取消呢？

答题要点：保留完成和原证据；取消不是撤销，也不能以顺序实验推断对端实际停工。

Q3 同步证据的句子正确，但属于另一任务或另一个版本，先查什么？

参考回答：先查与原任务的关联，再核对文档、版本、定位和原文；正确句子不能补齐关联和来源。

追问：如果结果里的对端名称也正确，能证明是谁发的么？

答题要点：不能；标签检查不替代真实可信对端的认证。

Q4 同进程已经可做固定只读取证，团队想「为了标准」换成 A2A，怎么评估？

参考回答：没有跨独立系统的生命周期与互通需求，继续用函数或有界工作流；协议会增加状态与对账成本。

追问：后来交给独立服务，纯内存用例全绿就够吗？

答题要点：不够；锁版本并验证互通、身份、生命周期和真实取消对账，本课不替代这些证据。

小结与一手参考

用卡片找候选，用当前主体查与取消，用原任务绑定和状态接纳结果。取消保护后续交付，不会抹去已经完成的事实。无跨系统瓶颈就保留原设计。
