生成器与 Streaming 模式

生成器是本地同步的“边算边给”迭代模型，可帮助理解但不等同于真实 SDK 流

💡 为什么这课重要？

本课的生成器（generator）是本地、同步的迭代模型：消费方用 for 或 next() 主动拉取下一个值。真实 SDK 不一定直接返回裸生成器；它可能暴露需要上下文管理的 iterable、async iterator，或带类型的事件对象。

你用 ChatGPT 时那种"内容一点点蹦出来"的体验，靠的是流式（streaming）——服务端算出一部分就推一部分，不用等整段生成完。本课用本地生成器练习这种"边算边给"的消费方式，而不是把生成器等同于网络流。

注意：真实 SDK 交付的文本增量通常已经解码；边界不保证对应词、句或一个用户感知字符。本课先用生成器做最简单的逐字符模拟建立直觉；Python 对 str 的迭代每次产出一个 Unicode code point，并不保证得到一个完整 grapheme cluster。真实 SDK 的边界与生命周期详见第 5 节。

掌握生成器，你才能优雅地处理 LLM 流式响应、边收边解析和惰性处理大数据。只有每个值处理后就丢弃时，额外内存才可保持有界；若累积完整回答，空间复杂度仍是 O(n)。这是 Part C（Agent 工程技能）的第一块拼图。

学习目标

完成本课后，你将能够：

  • 用 yield 写生成器，理解它"惰性、可暂停"的本质
  • 区分生成器表达式和列表推导式，知道何时用哪个
  • 理解迭代器协议（__next__ / StopIteration）
  • 用生成器按 Unicode code point 模拟 LLM 流式响应，并理解它与真实 SDK 的 stream_chunks/text_delta 有何不同
  • 了解 send() 能向生成器"回传"数据

1. yield：让函数"边算边给"

普通函数 return 一次就结束。生成器用 yield 产出一个值后暂停，下次取值再从暂停处继续。

怎么把一个普通函数改造成生成器？其实只改一处：把"建列表 → 循环 append → return 整个列表"换成"循环里直接 yield 每个值"。同一个任务，两种写法并排看：

# ① 普通函数：一次性造好整个列表再返回
def chunk_list(text, n=3):
    result = []
    for i in range(0, len(text), n):
        result.append(text[i:i+n])     # 攒进列表
    return result                      # 最后一次性返回

# ② 生成器：去掉列表，把 append + return 换成 yield
def chunk_gen(text, n=3):
    for i in range(0, len(text), n):
        yield text[i:i+n]              # 产出一块，暂停，等下次取

chunk_list("HelloWorld", 3)   # ['Hel', 'loW', 'orl', 'd']  ← 立刻拿到完整列表
chunk_gen("HelloWorld", 3)    # <generator object>         ← 只拿到一个生成器！

认出生成器就看一点：函数体里有没有 yield。只要有 yield，它就不再是普通函数，而是"生成器函数"——调用它不会立刻执行，只返回一个生成器对象；每次迭代（for / next）才推进到下一个 yield。两者产出的内容一样，但下面这个版本用 for 取值时才逐块算出：

def stream_chunks(text, n=3):
    for i in range(0, len(text), n):
        yield text[i:i+n]          # 产出一块，暂停，等下次取

for chunk in stream_chunks("HelloWorld", 3):
    print(chunk, end="|")          # Hel|loW|orl|d|

关键：stream_chunks(...) 调用时不会立刻执行函数体，只返回一个生成器；每次 for 取值才推进到下一个 yield。这就是"惰性"——用到才算。

🔑 Agent 开发关联：

LLM 的 streaming API 也会逐步交付内容，但具体消费接口由 SDK 决定。若将同步流适配成生成器，上层代码可写成 for chunk in llm_stream(prompt):；真实 SDK 也可能要求 with、async for 或按类型分派事件。边收边显示能改善体验；只有处理后丢弃已消费值时，额外内存才保持有界。

Q 调用一个含 yield 的函数，会发生什么？
含 yield 的函数是生成器函数，调用它只返回一个生成器对象，函数体一行都不先跑。只有当你迭代（for / next）时，才推进到下一个 yield。这种"惰性"正是流式处理的基础。

2. 生成器表达式 vs 列表推导式

# 列表推导式：立刻算出全部，占内存
squares_list = [x*x for x in range(1000000)]     # 一百万个数全在内存里

# 生成器表达式：惰性，用一个算一个，几乎不占内存
squares_gen = (x*x for x in range(1000000))      # 括号，不是方括号

# 生成器是"一次性"的，消费即耗尽
gen = (c.upper() for c in "abc")
print(next(gen))          # A
print("".join(gen))       # BC   ← A 已被取走，只剩 BC

差别就一对括号：[] 立刻生成整个列表，() 生成一个惰性生成器。处理大数据或只需遍历一次时，生成器可避免预先保存全部输入；但只有消费后丢弃各值，额外内存才保持有界，累积完整结果仍需 O(n) 空间。

💡 面试常见问题：

"列表推导式和生成器表达式的区别？"

答：列表推导式立即计算并把所有元素放进内存；生成器表达式惰性求值、逐个产出、几乎不占内存，但只能遍历一次。大数据或流式场景用生成器。

3. 迭代器协议（背后的机制）

for 循环能作用于生成器、列表、文件，是因为它们都遵守迭代器协议。这里要分清两个概念：

  • 可迭代对象（iterable）：能被 iter() 取得迭代器。list、str 是常见的 iterable-only 对象：自身不能直接 next()。
  • 迭代器（iterator）：既实现 __next__，也可迭代且 iter(iterator) is iterator；文件对象和生成器对象通常同时是 iterable 与 iterator。
it = iter([1, 2])       # list 是 iterable，iter() 从它拿到一个 iterator
print(next(it))    # 1
print(next(it))    # 2
next(it)           # StopIteration（for 循环内部捕获它来结束循环）

next([1, 2])       # TypeError: 'list' object is not an iterator —— list 本身不是 iterator！

生成器比较特殊：生成器对象同时是 iterable 和 iterator——它自己实现了 __iter__（返回自身）和 __next__，所以既能被 for 直接消费，也能被 next() 直接取值，不需要再 iter() 一次。这就是它能直接用在 for 里的原因。

4. send()：向生成器回传数据（进阶）

yield 不只能"产出"，还能"接收"。gen.send(x) 把 x 传回给暂停处的 yield 表达式：

def accumulator():
    total = 0
    while True:
        x = yield total       # 产出 total，同时等待 send 传入的值
        if x is not None:
            total += x

acc = accumulator()
next(acc)              # 启动到第一个 yield；也可写 acc.send(None)
print(acc.send(10))    # 10
print(acc.send(5))     # 15

这在需要"双向流"的场景（如可交互的 Agent 步骤流、协程式状态机）有用。日常处理 LLM streaming 通常只用单向 yield，send 了解即可。

Q 生成器表达式 (x for x in data) 相比列表推导式，主要优势是？
生成器表达式惰性求值——用一个算一个，不把整个序列放进内存，处理大数据或流时省内存。代价是它一次性、不能重复遍历、也不能按下标索引。列表推导式则相反。

5. 真实边界：生成器 ≠ 真实 LLM streaming 本身

本课的生成器例子只是本地、同步的 Python 惰性迭代模型，用来练手感。真实 LLM streaming 还包含网络协议与 SDK 生命周期；SDK 可能提供上下文管理的 iterable、async iterator 或 typed events，不能与本地生成器划等号。几个容易踩的坑：

  • text_delta 边界不是语言边界。官方 SDK 的文本字段已经解码为 Python str；一次 text_delta 不保证对应词、句、一个 Unicode code point 或一个用户感知字符，应用应按文本片段累积，而不是自行拼 UTF-8 字节。Python 迭代 str 时按 code point 产出，并不按 grapheme cluster 产出。token 一词保留给用量核算，具体数值以 API 的 usage 为准。
  • 生成器只是本地消费模型之一。真实流通常在一次 HTTP/SSE 长连接上持续到达多个事件，next() 不是每块重发一次请求；异步 SDK 则可能用 async for。
  • break 只停止当前消费。对象以后可能最终回收，但回收时机与资源清理都不是契约；涉及连接或文件时要显式 close/cancel。完整生命周期与计费边界见下方最佳实践卡。

最佳实践：停止消费不等于停止上游，真实流要显式关闭或取消

适用：迭代器背后持有 HTTP/SSE 连接、文件、进程或 SDK 流对象，消费方可能正常结束、提前 break 或抛异常。不适用：不持有外部资源的本地有限生成器，且生命周期完全由当前同步调用控制；这类流自然耗尽即可，不必为它虚构取消协议。

❌ 裸 break：只退出本地循环
stream = CloseOnlyStream(["A", "STOP", "B"])
for chunk in stream:
    if chunk == "STOP":
        break

assert not stream.closed  # close() 没有自动调用

break 改变的是消费方控制流，不会自动调用只有 close() 的资源对象。

✅ closing 适配 close-only 对象
from contextlib import closing

with closing(CloseOnlyStream(["A", "STOP", "B"])) as stream:
    for chunk in stream:
        if chunk == "STOP":
            break

assert stream.closed

若真实 SDK 对象已有原生上下文管理器，优先用原生接口；closing 用于只有 close() 的对象。

为什么更优：显式上下文或 try/finally 把资源所有权与清理责任放在同一边界，提升连接、文件描述符等资源的安全性；同时应记录是否提前停止、何时发起 close/cancel、取消耗时，以及最终可获得的 usage/账单，让取消成本与结果可观察。对已暂停在 yield 的 Python 生成器调用 generator.close() 时，解释器会在暂停点注入 GeneratorExit，随后栈展开并执行 finally；因此课末验收能用 close() 明确触发清理。代价是要维护资源生命周期、停止原因和监控字段，且不同上游的取消语义并不统一；对于无外部资源的本地有限流，自然耗尽即可，对于真实 API 流则可选地迁移到官方 SDK，并优先使用其上下文管理器、close 或取消接口，而不是自造传输层。显式取消只是发出并管理停止意图，不能据此声称服务端必然立即停止生成或停止计费，最终以具体服务的 usage 和账单为准。

自检：contextlib.closing 证明 break 与 close 是两件事
from contextlib import closing


class CloseOnlyStream:
    def __init__(self, chunks):
        self._chunks = iter(chunks)
        self.pulled = []
        self.closed = False

    def __iter__(self):
        return self

    def __next__(self):
        if self.closed:
            raise StopIteration
        chunk = next(self._chunks)
        self.pulled.append(chunk)
        return chunk

    def close(self):
        self.closed = True


bare = CloseOnlyStream(["A", "STOP", "B"])
assert not hasattr(bare, "__enter__")
for chunk in bare:
    if chunk == "STOP":
        break
assert bare.pulled == ["A", "STOP"]
assert not bare.closed
bare.close()

managed = CloseOnlyStream(["A", "STOP", "B"])
with closing(managed) as stream:
    for chunk in stream:
        if chunk == "STOP":
            break
assert managed.pulled == ["A", "STOP"]
assert managed.closed

结果解释：代码静默结束即通过：两种写法都只拉取到停止标记，证明后续 "B" 仍是惰性的；裸 break 后 closed 仍为 False，说明只停了消费；上下文退出后为 True，说明清理确实发生。若第一组已自动关闭，测试对象混淆了“停止迭代”和“释放资源”；若第二组未关闭，则 __exit__ 没有落实生命周期责任。

知识图谱

生成器（本地、纯 Python）
├── yield → 产出即暂停，惰性、可恢复
├── 调用生成器函数 → 只返回生成器，不先执行
├── 生成器表达式 (x for x in ...) → 惰性省内存、一次性
└── send(x) → 向 yield 回传数据；启动用 next(gen) 或 send(None)

迭代器协议
├── iterable-only：list / str，可 iter()，自身不能 next()
├── iterator：可 next() 且 iter(iterator) is iterator
└── 文件对象 / 生成器对象通常同时是 iterable 与 iterator

Streaming 的两层
├── 本课逐 code point 模拟：只教惰性与拉取轨迹，不代表 grapheme cluster
└── SDK text_delta：已解码 str，边界不保证对应词/code point/用户感知字符
    └── token 仅指 usage 核算；长连接、关闭与计费边界 → 见上方最佳实践卡

实战练习

练习：实现一个按 code point 产出的流式模拟器

用生成器逐个输出 Python str 的 Unicode code point（模拟流式效果，不代表真实 SDK 的 stream_chunks/text_delta，也不保证每项是完整 grapheme cluster），并支持在中途根据条件提前停止。先自己写，再看答案。

任务清单

  1. 写生成器 stream_code_points(text)，逐个 code point yield
  2. 写 collect(gen, stop_at=None)：消费生成器、拼接输出；若取到 stop_at code point 就提前停止
  3. 统计实际累积进结果的 code point 数（注意：停止项已被生成器产出并被 for 取走，但因为 break 在 append 之前，它不计入结果和计数）
  4. 体会：因为是惰性的，stop_at 之后的 code point 根本不会被生成器算出来（但停止项自身已经被取出）
💡 点击查看参考答案 
def stream_code_points(text):
    for code_point in text:
        yield code_point              # str 迭代按 code point 产出，不按 grapheme cluster

def collect(gen, stop_at=None):
    parts = []
    code_points = 0
    for code_point in gen:
        if stop_at is not None and code_point == stop_at:
            break                     # 停止项已被 for 取出，只是不再 append
        parts.append(code_point)
        code_points += 1
    return {"text": "".join(parts), "code_points": code_points}


print(collect(stream_code_points("你好，世界！")))
# {'text': '你好，世界！', 'code_points': 6}

print(collect(stream_code_points("答案是42。附注..."), stop_at="。"))
# {'text': '答案是42', 'code_points': 5}
# "答案是42"包含 5 个 code point；停止项"。"被取出但未计入/未 append；
# "。"之后的文本因为惰性没有再往下计算


# 进阶：用生成器表达式做惰性过滤（只在需要时计算）
events = ({"type": "text_delta", "text": c} for c in "abcd")
answer = "".join(e["text"] for e in events if e["type"] == "text_delta")
print(answer)   # abcd

思考题

先自己想，再点开对答案。

Q1如果 stream 背后是真实网络请求（每个 chunk 要等服务端推送），惰性/break 带来的好处和边界是什么？

本地生成器的惰性保证“未拉取就不执行”；真实网络流还要管理上游资源。业务逻辑可以 break，但必须按上方最佳实践卡使用 SDK 原生上下文/取消接口，只有 close-only 对象才用 contextlib.closing。服务端停止与计费语义以具体 SDK 文档和最终 usage/账单为准。

Q2上面 collect 用 parts.append + "".join(parts)，这样内存占用真的接近常量吗？

不是。collect 里的 parts 就是保存所有已产出引用的完整中间列表；"".join(parts) 还要分配最终字符串。因此它与 "".join(list(gen)) 都会同时保留完整列表和最终结果，峰值内存与空间复杂度同为 O(n)（n 为结果长度），并没有因为手动 append 而少一份列表或变成常量级。

生成器真正带来的省内存优势体现在不需要保留完整结果的场景：比如只是逐项打印到终端、逐块写入文件/网络、或者只统计某个特征而不保留原文——这些场景里，每次从生成器拿到一个值就立刻处理并丢弃，同一时刻内存里只有"当前正在处理的这一小块"，额外内存才是近似 O(1)。

如果目的就是拼出完整回答（比如要展示、要存库），那么无论用生成器边收边 append，还是先 list(gen) 再 join，两种写法都显式物化了完整列表，并在连接时生成完整字符串，空间复杂度都是 O(n)。生成器在这里仍提供惰性和提前停止能力，却不会自动降低完整累积的峰值空间。所以判断是否真的省内存，要看消费方有没有及时丢弃已处理的数据，而不是简单地说“用了生成器就是常量内存”。

本课最佳实践验收：用真正生成器证明惰性与清理

这次不复演普通上下文管理：必须写出含 yield 的生成器，用事件轨迹证明调用惰性、按需拉取、提前停止不计算后续，并让正常、关闭与异常三条路径都经过 finally。对暂停在 yield 的生成器调用 close() 会在暂停点注入 GeneratorExit，栈展开时执行 finally；下面的纯标准库验收据此验证显式生命周期。

操作清单

  1. 生成器调用后先检查轨迹为空。
  2. 逐次 next() 核对拉取轨迹。
  3. 提前停止后显式 close()。
  4. 验证正常耗尽与资源关闭。
  5. 验证源异常原样传播且仍清理。
通过标准
  • 函数体含 yield
  • 调用本身不执行
  • 停止后数据未计算
  • 正常耗尽关闭
  • 异常不被吞掉
  • 末尾唯一打印指定验收标记
课末自检（纯标准库，整块复制即可运行）：
def traced_stream(items, events, fail_at=None):
    events.append("open")
    try:
        for index, item in enumerate(items):
            events.append(f"compute:{item}")
            if index == fail_at:
                raise RuntimeError(f"failed:{item}")
            yield item
    finally:
        events.append("close")


# 调用生成器函数只创建对象，不执行函数体。
events = []
early = traced_stream(["A", "STOP", "NEVER"], events)
assert events == []
assert next(early) == "A"
assert events == ["open", "compute:A"]
assert next(early) == "STOP"
assert events == ["open", "compute:A", "compute:STOP"]
early.close()  # 提前停止时显式触发 finally
assert events == ["open", "compute:A", "compute:STOP", "close"]
assert "compute:NEVER" not in events

# 正常耗尽：for 拉到 StopIteration，finally 自动执行。
events = []
normal = traced_stream(["A", "B"], events)
assert list(normal) == ["A", "B"]
assert events == ["open", "compute:A", "compute:B", "close"]

# 异常传播：生成器不吞源异常，finally 仍关闭资源状态。
events = []
failing = traced_stream(["A", "BOOM", "NEVER"], events, fail_at=1)
try:
    list(failing)
except RuntimeError as exc:
    assert str(exc) == "failed:BOOM"
else:
    raise AssertionError("生成器源异常必须继续传播")
assert events == ["open", "compute:A", "compute:BOOM", "close"]
assert "compute:NEVER" not in events

print("L12 ACCEPTED")

结果诊断：只看到一行该验收标记即通过。调用后轨迹非空表示不再惰性；提前关闭后出现 compute:NEVER 表示多算；正常或异常路径缺少 close 表示 finally 未覆盖生命周期；异常未传播则 consumer 吞掉了上游失败。

  • 提前停止不拉取后续数据
  • 源异常保持原对象身份
  • 成功快照是严格 JSON
  • 替换失败保留旧 JSON 且清理临时文件
  • stdout 只有指定检查点标记

参考验收程序（独立完成后展开，纯标准库）：
import json
import os
from contextlib import closing, suppress
from pathlib import Path
from tempfile import NamedTemporaryFile, TemporaryDirectory


def write_json_atomic(path, data, replace=os.replace):
    text = json.dumps(data, ensure_ascii=False, allow_nan=False, sort_keys=True)
    tmp = None
    try:
        with NamedTemporaryFile(
            "w", encoding="utf-8", dir=path.parent,
            prefix=f".{path.name}.", suffix=".tmp", delete=False,
        ) as file:
            tmp = Path(file.name)
            file.write(text)
        replace(tmp, path)
        tmp = None
    except BaseException:
        if tmp is not None:
            with suppress(OSError):
                tmp.unlink()
        raise


def tracked_stream(items, events, failure=None):
    events.append("open")
    try:
        for item in items:
            events.append(f"pull:{item}")
            if failure is not None and item == "BOOM":
                raise failure
            yield item
    finally:
        events.append("close")


def collect_owned(items, events, *, stop_at=None, failure=None):
    parts = []
    stream = tracked_stream(items, events, failure=failure)
    with closing(stream):
        for item in stream:
            if item == stop_at:
                break
            parts.append(item)
    return parts


with TemporaryDirectory() as directory:
    path = Path(directory) / "snapshot.json"
    write_json_atomic(path, {"version": 1, "chunks": ["OLD"]})

    normal_events = []
    chunks = collect_owned(["A", "B"], normal_events)
    assert chunks == ["A", "B"]
    assert normal_events == ["open", "pull:A", "pull:B", "close"]
    write_json_atomic(path, {"version": 2, "chunks": chunks})
    assert json.loads(path.read_text(encoding="utf-8")) == {
        "chunks": ["A", "B"], "version": 2,
    }
    assert "NaN" not in path.read_text(encoding="utf-8")

    early_events = []
    assert collect_owned(
        ["A", "STOP", "NEVER"], early_events, stop_at="STOP",
    ) == ["A"]
    assert early_events == ["open", "pull:A", "pull:STOP", "close"]
    assert "pull:NEVER" not in early_events

    source_error = RuntimeError("source failed")
    source_events = []
    try:
        collect_owned(["A", "BOOM", "NEVER"], source_events,
                      failure=source_error)
    except RuntimeError as exc:
        assert exc is source_error
    else:
        raise AssertionError("source error must propagate")
    assert source_events == ["open", "pull:A", "pull:BOOM", "close"]
    assert "pull:NEVER" not in source_events

    old_text = path.read_text(encoding="utf-8")
    replace_error = OSError("replace failed")

    def fail_replace(source, target):
        raise replace_error

    try:
        write_json_atomic(
            path, {"version": 3, "chunks": ["NEW"]},
            replace=fail_replace,
        )
    except OSError as exc:
        assert exc is replace_error
    else:
        raise AssertionError("replace error must propagate")

    assert path.read_text(encoding="utf-8") == old_text
    assert json.loads(old_text) == {"chunks": ["A", "B"], "version": 2}
    assert list(path.parent.glob(".snapshot.json.*.tmp")) == []

print("P1 CHECKPOINT RESOURCE-LIFECYCLE PASSED")

结果诊断：任一路径缺少 close，说明资源 owner 没覆盖完整控制流；提前停止仍出现 pull:NEVER，说明惰性边界失效；异常身份变化表示错误被替换；旧文本变化、JSON 无法严格解析或残留临时文件，则原子提交与清理责任不完整。

面试常见问题

Q1：生成器和普通函数的区别？

答：生成器用 yield，产出一个值后暂停、保留状态、可恢复；调用它只返回生成器对象，函数体惰性执行。普通函数 return 一次性算完返回。

Q2：列表推导式和生成器表达式怎么选？

答：需要多次遍历、随机访问、或数据不大 → 列表推导式；只遍历一次、数据很大或是流 → 生成器表达式（惰性、省内存）。

Q3：iterable 和 iterator 的区别？

答：iterable 能被 iter() 取得迭代器；list/str 是常见 iterable-only 对象，自身不能直接 next()。iterator 可 next()，且 iter(iterator) is iterator；文件对象与生成器对象通常同时满足两者。

Q4：生成器在 LLM 应用里有什么用，边界是什么？

答：生成器提供本地同步的惰性消费模型。真实 SDK 可能暴露上下文管理的 iterable、async iterator 或 typed events；text_delta 已经解码，但边界不保证对应词、code point、grapheme cluster 或用户感知字符。token 专指 usage 用量核算；提前停止时按上方最佳实践卡显式关闭/取消，不能把本地 break 当作上游契约。

总结

  • yield = 产出即暂停，生成器惰性、可恢复
  • 调用生成器函数只返回生成器，函数体不立即执行
  • 生成器表达式用 ()，惰性省内存但一次性
  • list/str 常为 iterable-only；文件与生成器对象通常同时是 iterable 和 iterator
  • SDK text_delta 已解码，但边界不保证对应词、code point、grapheme cluster 或用户感知字符；token 专指 usage 核算
  • break 只停当前消费；外部资源的关闭/取消按最佳实践卡处理
  • 只有"边处理边丢弃"才是近似常量内存；累积成完整结果（无论 list 还是 append+join）都是 O(n)
  • send() 可向生成器回传数据（双向流，进阶了解）
