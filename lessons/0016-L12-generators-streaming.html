生成器与 Streaming 模式

生成器是"边算边给" — LLM 流式输出在 Python 端的消费接口，本质上就是用生成器包装的迭代

💡 为什么这课重要？

你用 ChatGPT 时那种"内容一点点蹦出来"的体验，靠的就是流式（streaming）——服务端算出一部分就推一部分，不用等整段生成完。在 Python 里，承载这种"边算边给"的正是生成器（generator）。

注意：这里的"一部分"在真实 LLM API 里通常是一个 chunk/delta（可能含一个或多个模型 token，也可能是半个 token），并不等于"一个字符"或"一个模型 token"。本课先用生成器练习最简单的逐字符模拟建立直觉，随后会明确指出它和真实 SDK 流的边界（详见第 5 节）。

掌握生成器，你才能优雅地处理 LLM 流式响应、边收边解析、以及惰性处理大数据而不爆内存。这是 Part C（Agent 工程技能）的第一块拼图。

学习目标

完成本课后，你将能够：

  • 用 yield 写生成器，理解它"惰性、可暂停"的本质
  • 区分生成器表达式和列表推导式，知道何时用哪个
  • 理解迭代器协议（__next__ / StopIteration）
  • 用生成器模拟 LLM 流式响应（逐字符），并理解它与真实 SDK 的 chunk/delta 有何不同
  • 了解 send() 能向生成器"回传"数据

1. yield：让函数"边算边给"

普通函数 return 一次就结束。生成器用 yield 产出一个值后暂停，下次取值再从暂停处继续。

怎么把一个普通函数改造成生成器？其实只改一处：把"建列表 → 循环 append → return 整个列表"换成"循环里直接 yield 每个值"。同一个任务，两种写法并排看：

# ① 普通函数：一次性造好整个列表再返回
def chunk_list(text, n=3):
    result = []
    for i in range(0, len(text), n):
        result.append(text[i:i+n])     # 攒进列表
    return result                      # 最后一次性返回

# ② 生成器：去掉列表，把 append + return 换成 yield
def chunk_gen(text, n=3):
    for i in range(0, len(text), n):
        yield text[i:i+n]              # 产出一块，暂停，等下次取

chunk_list("HelloWorld", 3)   # ['Hel', 'loW', 'orl', 'd']  ← 立刻拿到完整列表
chunk_gen("HelloWorld", 3)    # <generator object>         ← 只拿到一个生成器！

认出生成器就看一点：函数体里有没有 yield。只要有 yield，它就不再是普通函数，而是"生成器函数"——调用它不会立刻执行，只返回一个生成器对象；每次迭代（for / next）才推进到下一个 yield。两者产出的内容一样，但下面这个版本用 for 取值时才逐块算出：

def stream_tokens(text, n=3):
    for i in range(0, len(text), n):
        yield text[i:i+n]          # 产出一块，暂停，等下次取

for chunk in stream_tokens("HelloWorld", 3):
    print(chunk, end="|")          # Hel|loW|orl|d|

关键：stream_tokens(...) 调用时不会立刻执行函数体，只返回一个生成器；每次 for 取值才推进到下一个 yield。这就是"惰性"——用到才算。

🔑 Agent 开发关联：

LLM 的 streaming API 返回的就是这种"一块一块"的流。用生成器包装它，上层代码就能写成 for chunk in llm_stream(prompt):，边收边显示/边处理，用户体验和内存都更好。

Q 调用一个含 yield 的函数，会发生什么？
含 yield 的函数是生成器函数，调用它只返回一个生成器对象，函数体一行都不先跑。只有当你迭代（for / next）时，才推进到下一个 yield。这种"惰性"正是流式处理的基础。

2. 生成器表达式 vs 列表推导式

# 列表推导式：立刻算出全部，占内存
squares_list = [x*x for x in range(1000000)]     # 一百万个数全在内存里

# 生成器表达式：惰性，用一个算一个，几乎不占内存
squares_gen = (x*x for x in range(1000000))      # 括号，不是方括号

# 生成器是"一次性"的，消费即耗尽
gen = (c.upper() for c in "abc")
print(next(gen))          # A
print("".join(gen))       # BC   ← A 已被取走，只剩 BC

差别就一对括号：[] 立刻生成整个列表，() 生成一个惰性生成器。处理大数据、或只需遍历一次时，用生成器省内存。

💡 面试常见问题：

"列表推导式和生成器表达式的区别？"

答：列表推导式立即计算并把所有元素放进内存；生成器表达式惰性求值、逐个产出、几乎不占内存，但只能遍历一次。大数据或流式场景用生成器。

3. 迭代器协议（背后的机制）

for 循环能作用于生成器、列表、文件，是因为它们都遵守迭代器协议。这里要分清两个概念：

  • 可迭代对象（iterable）：实现了 __iter__，能被 iter() 调用产出一个迭代器。列表、字符串、文件都是 iterable，但本身不是迭代器——不能直接 next()。
  • 迭代器（iterator）：实现了 __next__，能被 next() 逐个取值，取完抛 StopIteration。
it = iter([1, 2])       # list 是 iterable，iter() 从它拿到一个 iterator
print(next(it))    # 1
print(next(it))    # 2
next(it)           # StopIteration（for 循环内部捕获它来结束循环）

next([1, 2])       # TypeError: 'list' object is not an iterator —— list 本身不是 iterator！

生成器比较特殊：生成器对象同时是 iterable 和 iterator——它自己实现了 __iter__（返回自身）和 __next__，所以既能被 for 直接消费，也能被 next() 直接取值，不需要再 iter() 一次。这就是它能直接用在 for 里的原因。

4. send()：向生成器回传数据（进阶）

yield 不只能"产出"，还能"接收"。gen.send(x) 把 x 传回给暂停处的 yield 表达式：

def accumulator():
    total = 0
    while True:
        x = yield total       # 产出 total，同时等待 send 传入的值
        if x is not None:
            total += x

acc = accumulator()
next(acc)              # 启动到第一个 yield（必须先 next 一次）
print(acc.send(10))    # 10
print(acc.send(5))     # 15

这在需要"双向流"的场景（如可交互的 Agent 步骤流、协程式状态机）有用。日常处理 LLM streaming 通常只用单向 yield，send 了解即可。

Q 生成器表达式 (x for x in data) 相比列表推导式，主要优势是？
生成器表达式惰性求值——用一个算一个，不把整个序列放进内存，处理大数据或流时省内存。代价是它一次性、不能重复遍历、也不能按下标索引。列表推导式则相反。

5. 真实边界：生成器 ≠ 真实 LLM streaming 本身

本课的生成器例子只是本地、纯 Python 的惰性迭代，用来练手感。真实 LLM streaming 还多了一层网络协议，二者不能划等号，几个容易踩的坑：

  • 字符 ≠ 模型 token ≠ chunk/delta。本课练习逐字符 yield，只是最简单的模拟；真实 SDK 的一次 delta/chunk 可能包含一个模型 token、多个 token，或半个 token（多字节 UTF-8 序列被截断），字符数、token 数、chunk 数三者不能互相替代。账单以 API 返回的 usage 字段（如 usage.input_tokens/output_tokens）为准，不能用字符数估算费用。详见 L09 的 SSE 分层、L15 的 httpx.stream 逐行解析。
  • 生成器只是 Python 端的消费接口，不代表"每 next 一次就发一次新 HTTP 请求"。真实流式 API 通常是一个长连接（一次 HTTP 请求/一个 SSE 连接）持续推送多个事件，Python 侧用 for chunk in response:／生成器只是在消费已经建立好的这个连接里陆续到达的数据，并不会为每个 chunk 单独发起新请求。
  • 本地生成器的 break 不等于"服务端停止计费/停止生成"。普通生成器 break 只是停止了本地这一次 for 迭代，生成器对象会被垃圾回收，但如果背后是网络连接（真实 SSE/SDK 流），必须显式关闭连接（如退出 with httpx.stream(...) as r: 上下文、调用 SDK 提供的取消/close 方法）才能让上游真正停止推流；不同厂商/SDK 的取消语义不同，需要查对应文档确认。即便主动取消，最终是否计费、计多少也要以厂商返回的 usage/账单为准，不能想当然认为"停止读取=不计费"。

知识图谱

生成器（本地、纯 Python）
├── yield → 产出即暂停，惰性、可恢复
├── 调用生成器函数 → 只返回生成器，不先执行
├── 生成器表达式 (x for x in ...) → 惰性省内存、一次性
└── send(x) → 向 yield 回传数据（双向，进阶）

迭代器协议
├── iterable（如 list/文件）：能被 iter() 转成 iterator，本身不能 next()
├── iterator：能被 next() 取值，取尽抛 StopIteration
└── 生成器对象：同时是 iterable 和 iterator（自己实现 __iter__ + __next__）

Streaming 的两层
├── 本课的字符级生成器 —— 教惰性/迭代协议，与真实网络无关
└── 真实 LLM streaming —— SSE/SDK 长连接持续推事件
    ├── 一次 delta/chunk 可能含 0/1/多个 token，字符数 ≠ token 数 ≠ chunk 数
    ├── 计费以 usage 字段为准，不能靠字符/chunk 数估算
    ├── for chunk in stream 只是消费已建立连接的数据，不等于每次 next 发一次新请求
    └── break 只停本地循环；真正停止上游/省费需显式取消/关闭连接，且以最终 usage 为准

实战练习

练习：实现一个逐字符流式模拟器

用生成器逐字符输出一段"回答"（模拟流式效果，不代表真实模型 token），并支持在中途根据条件提前停止。先自己写，再看答案。

任务清单

  1. 写生成器 stream(text)，逐字符 yield
  2. 写 collect(gen, stop_at=None)：消费生成器、拼接输出；若取到 stop_at 字符就提前停止（模拟"遇到停止字符就中断"）
  3. 统计实际累积进结果的字符数（注意：停止字符本身被生成器产出/被 for 取走，但因为 break 在 append 之前，它不计入结果和计数）
  4. 体会：因为是惰性的，stop_at 之后的字符根本不会被生成器算出来（但停止字符自身已经被取出）
💡 点击查看参考答案 
def stream(text):
    for ch in text:
        yield ch                      # 逐字符产出（惰性模拟，非真实模型 token）

def collect(gen, stop_at=None):
    parts = []
    characters = 0
    for ch in gen:
        if stop_at is not None and ch == stop_at:
            break                     # 停止字符已被 for 取出/消费，只是不再 append
        parts.append(ch)
        characters += 1
    return {"text": "".join(parts), "characters": characters}


print(collect(stream("你好，世界！")))
# {'text': '你好，世界！', 'characters': 6}

print(collect(stream("答案是42。附注..."), stop_at="。"))
# {'text': '答案是42', 'characters': 5}
# 逐字符产出："答案是42"是 5 个字符；停止字符"。"被取出但未计入/未 append；
# "。"之后的字符（"附注..."）因为惰性，生成器根本没有再往下算


# 进阶：用生成器表达式做惰性过滤（只在需要时计算）
events = ({"type": "token", "text": c} for c in "abcd")
answer = "".join(e["text"] for e in events if e["type"] == "token")
print(answer)   # abcd

思考题

先自己想，再点开对答案。

Q1如果 stream 背后是真实网络请求（每个 chunk 要等服务端推送），惰性/break 带来的好处和边界是什么？

惰性意味着"用到才算"：只要 collect 里还没消费到某个 chunk，生成器就不会去触发对应的计算/网络等待。但对本地生成器来说，break 只是停止了这一次 for 循环本身，它并不会自动去通知远端服务器"别再算了"。

在纯本地的惰性序列（比如本课的 stream(text)）里，break 之后确实不会再执行后面的循环体，后续元素也不会被计算——这一点是真的。但换成真实 LLM streaming，情况更复杂：response 对象背后有一个已经建立好的 HTTP/SSE 连接，Python 侧的 for chunk in response: 只是在消费这个连接里源源不断到达的数据。你在本地 break 出循环，只是不再读取这个连接，但连接是否关闭、服务端是否真的停止生成、是否停止计费，取决于：底层库/SDK 是否在你退出 with 上下文或调用 close/cancel 时正确关闭了连接，以及厂商后端是不是把"客户端断开"当作停止生成的信号。

结论：想要真正省时省钱，除了在业务逻辑里 break，还必须确保退出流式上下文（如 with httpx.stream(...) as r: ... 结束/调用 SDK 的取消方法），并查阅具体 SDK/厂商文档确认取消语义；即便主动取消，最终计费也以厂商返回的 usage/账单数据为准，不能假设"停止读取=零费用"。

Q2上面 collect 用 parts.append + "".join(parts)，这样内存占用真的接近常量吗？

不是。collect 里的 parts 列表仍然会把整段回答的每个字符都攒起来，最终 "".join(parts) 时内存占用是 O(n)（n 为结果长度），和直接 "".join(list(gen)) 在数量级上没有本质区别——只是省掉了 list(gen) 这一个中间列表对象，峰值内存并没有变成常量级。

生成器真正带来的省内存优势体现在不需要保留完整结果的场景：比如只是逐字符打印到终端、逐块写入文件/网络、或者只统计某个特征而不保留原文——这些场景里，每次从生成器拿到一个值就立刻处理并丢弃，同一时刻内存里只有"当前正在处理的这一小块"，额外内存才是近似 O(1)。

如果目的就是拼出完整回答（比如要展示、要存库），那么无论用生成器边收边 append，还是先 list(gen) 再 join，最终都得有一份完整结果驻留内存，空间复杂度都是 O(n)。生成器省掉的是"中间临时列表"和"提前计算"，不是"最终结果"本身。所以判断是否真的省内存，要看你有没有在消费过程中及时丢弃已处理的数据，而不是简单地说"用了生成器就是常量内存"。

面试常见问题

Q1：生成器和普通函数的区别？

答：生成器用 yield，产出一个值后暂停、保留状态、可恢复；调用它只返回生成器对象，函数体惰性执行。普通函数 return 一次性算完返回。

Q2：列表推导式和生成器表达式怎么选？

答：需要多次遍历、随机访问、或数据不大 → 列表推导式；只遍历一次、数据很大或是流 → 生成器表达式（惰性、省内存）。

Q3：iterable 和 iterator 的区别？

答：iterable 实现 __iter__，能被 iter() 转成迭代器，但本身不能直接 next()（如 list：next([1,2]) 报 TypeError）；iterator 实现 __next__，能被 next() 逐个取值，取尽抛 StopIteration。生成器对象比较特殊，同时满足两者。

Q4：生成器在 LLM 应用里有什么用，边界是什么？

答：生成器是 Python 端消费流式数据的惰性接口，配合真实 SDK/SSE 可以写成 for chunk in stream: 边收边处理，降低首字延迟。但要注意三个边界：① 一个 chunk/delta 不等于一个字符或一个模型 token，计费以 usage 字段为准；② for chunk in stream 消费的是已建立好的一个连接，不是每次 next 发一次新请求；③ 本地 break 只停止本地循环，真正停止上游生成/计费需要显式关闭连接或调用 SDK 取消方法，并以最终账单为准。

总结

  • yield = 产出即暂停，生成器惰性、可恢复
  • 调用生成器函数只返回生成器，函数体不立即执行
  • 生成器表达式用 ()，惰性省内存但一次性
  • iterable（能 iter()）与 iterator（能 next()）不同，生成器对象两者都是
  • 字符 ≠ 模型 token ≠ chunk/delta；账单以 usage 为准，不能靠计数估算
  • 本地 break 只停本地循环；真正停止上游/省费需显式取消连接，且以最终账单为准
  • 只有"边处理边丢弃"才是近似常量内存；累积成完整结果（无论 list 还是 append+join）都是 O(n)
  • send() 可向生成器回传数据（双向流，进阶了解）
