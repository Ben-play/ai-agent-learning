封装 FastAPI、Docker 与持久状态

换掉请求进程，不换掉批准对象和已经提交的事实

为什么这课重要？

客服先起草一份导出保留期答复，同事第二天才审批。更新服务期间，原进程已经退出。若草稿和批准都只放在 Python 字典，控制台可以显示「启动成功」，业务却找不到原工单。反过来，拿到 SQLite 文件也不代表能继续：还要知道它承载哪一种状态、哪个任务和哪份证据。先让旧进程和新进程对接同一份合成业务状态，再考虑把同一宿主挂到 HTTP 与容器上。

学习目标

  • 分开 HTTP 入口、宿主、进程和持久库，分别定位「服务在跑」「依赖就绪」「批准对象还在」。
  • 验证替换进程和依赖故障时的完整绑定、独立回执和零新增写入。
  • 读懂课堂 Dockerfile、专用构建上下文和命名卷；明白本机测试与实际部署的不同门槛。

1. 入口可以换，业务合同不变

FastAPI 是 Python 的 HTTP 应用框架，负责路由和组装响应；Uvicorn 运行这个 ASGI 应用，接收连接并把请求交给它。宿主 是课程代码，实施身份、证据、审批和效果边界。lifespan 在接请求前初始化应用，在停止服务后可清理资源；它不是持久化。「服务已启动」只说明初始化完成，不表示以后每次依赖调用都成功。HTTP 状态码描述这次交互，pending、denied、saved 才是本项目的业务状态。

合成客服任务的五个入口（课堂 JSON 形状）
入口示例输入边界与结果
ask{"topic":"export"}只读授权引文，例如 EXPORT-POLICY v1 §1「导出文件生成后保留 7 天。」；不是草稿或批准。
stage{"job":"export","topic":"export","revision":1}用 Phase 5 原业务接口暂存草稿，返回 pending 和完整绑定；此刻未尝试插入已保存草稿。
inspect{"job":"export"}按宿主主体查看状态和绑定，不返回草稿正文；另一个租户的同名客服查不到。
review{"binding": {...}, "decision":"approve"}固定课堂审核角色写可信决定，绑定租户、主体、任务、动作、修订、摘要；review_recorded 不等于草稿已保存。
recover{"binding": {...}}仅受托角色恢复，重读已记录的决定，检查当前证据与业务状态后才提交或重放。恢复请求不携带新的「批准」。

课堂 HTTP 适配器启动时固定单一合成角色，不接真实认证，不把 JSON 或头部字段当身份，不把测试故障入口暴露为 HTTP。对外只投影状态、绑定、证据、回执和稿件；具体读次数和 INSERT 尝试仅供本地验收。可选说明在部署实验，仅用于隔离机器的回环端口，不能用于共享环境。Phase 7 的当前证据在内存 SQLite 重建；持久库中保存的撤权会先应用。旧草稿的 KB-02 文本是历史释义，宿主校验它与新版证据的固定映射，不把它当逐字引文。

中间进程已写入 review_recorded，随后依赖中断。哪一项可确认草稿是否保存？
批准和草稿提交分别在不同边界；查看独立持久状态才知道业务效果。

2. 从进程替换推导容器要保护什么

镜像 是启动模板，容器 是它的运行实例。删掉实例会丢实例的可写层，命名卷 仍在。这里把 /state 挂到同一个专用卷，卷里两份 SQLite：business.sqlite 存原版 checkpoint 与已保存行，review.sqlite 记录可信决定和课堂撤权。真实环境不要把带写流量的 SQLite 主文件当完整快照：例如 WAL 下已提交数据可能尚在附属文件。

课堂镜像只复制明确列出的课程源码，不把配置或数据混进构建上下文。Dockerfile 使用直接执行的启动参数、一个进程和非 root 用户；容器内监听与宿主地址是两层，手册仅发布到 127.0.0.1。每轮先分配新卷，再让本轮替换实例沿用它；重开上一轮卷不是从干净状态起跑。基础镜像标签可改变，依赖范围也不是锁，课堂示例不提供生产构建物的可复现保证。

本地实际观察：三个顺序子进程、同一个目录（不是 Docker）
阶段宿主结果另开连接的业务证据
初始服务：先问答再暂存读取 7 天原文；导出草稿绑定为第 1 稿一条待批 checkpoint，零审批、零已保存行。
新进程：依赖不可用找回绑定、记录批准；recover 返回 dependency_unavailable（可选 HTTP 映射为 503）保留批准和待批记录，零新增 INSERT 或回执；不需要重录。
再次替换：依赖可用同一绑定重新读取两条当前证据并保存恰好一次草稿 INSERT，一个与原任务、正文相符的业务回执。

父进程关闭旧管道并等待退出以后，才启动下一个进程。PID 可帮助排查观察来自哪个进程，但不能代替退出和绑定证据。本实验只在每个进程处理完请求后切换，不声称验证强杀、并发审批、自动重试或跨库原子性。不同持久编排平台可以提供任务续跑或重试，不能代替本地或外部服务的业务去重凭据。

决策卡：先明确哪个状态必须跨进程保留

适用：有人工等待或业务回执的系统。不适用：无状态只读计算不必为每个请求引入持久工作流。

误判：容器重启后入口恢复，于是替已经审批的任务再起一个草稿。
选择：保留业务目录，关旧开新，用原任务绑定对账；依赖不可用先停。
  1. 在旧实例留下待批或已批任务，独立读回库。
  2. 换实例后比绑定、审批、INSERT 与持久行；再用空目录做能被识别的反例。

代价：额外维护存储路径、状态 schema 和恢复验收；已知只读流程能更简单就保留。诊断：启动成功但任务消失，先查挂载和实际数据库路径，不要重新审批一份替代物。

面试自查

Q1 升级后健康页正常，但原批准找不到，先查什么？

参考回答：查实际挂载及两个库的状态，再比旧绑定；不直接重建任务。

追问：绑定在，批准行不在呢？

答题要点：批准缺失保持等待；检查两份状态是否同一逻辑时间点。

Q2 把 approved=true 放在恢复请求里能简化接口吗？

参考回答：公开请求的主张不是真实决定；恢复应重读受托角色存下的绑定。

追问：正文一样，但草稿修订不同呢？

答题要点：决定跟完整绑定走，摘要相同也不能跨修订放行。

Q3 容器使用命名卷，是不是能开两个写副本提高吞吐？

参考回答：挂载说明文件可见，不证明单写假设、多库一致性或并发锁纪律。

追问：其中一个副本是只读诊断页呢？

答题要点：额外验数据库读快照和对外权限，不把副本当独立备份。

Q4 依赖报 503，能按「一定没写」立即重试吗？

参考回答：不能从客户端码推断业务效果；本练习只能用已知故障点的零 INSERT 与全表证明。

追问：如果实际是提交后连接断了？

答题要点：核原回执并幂等恢复，不盲目新建操作。闭库文件也不是跨机运行证明。
