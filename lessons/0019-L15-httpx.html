用 httpx 发起 HTTP 请求

每一次 LLM 调用、每个联网工具，本质都是一个 HTTP 请求

💡 为什么这课重要？

你调 OpenAI/Anthropic 的 SDK，底层就是在发 HTTP 请求：带上 API Key 的 header、JSON 请求体、处理状态码、读回 JSON。你写的每个"联网工具"（搜索、查天气、调内部 API）也一样。HTTP 是 Agent 的传输层地基。

本课程选择 httpx，因为后续既要演示同步调用，也要用同一套风格进入异步调用与 MockTransport 离线验证。若目标服务已有合适的官方 SDK，优先评估 SDK；只有同步需求的既有 requests 项目不必为追求统一而迁移；需要不同连接模型或更底层控制时也应按约束另行选型。

※ 本课代码需先安装 httpx：uv add httpx（或 pip install httpx）。httpx 也是 OpenAI/Anthropic 官方 SDK 内部使用的客户端。

学习目标

完成本课后，你将能够：

  • 理解 HTTP 请求的组成：方法、URL、headers、body、状态码
  • 用 httpx 发 GET/POST，带 headers 和 JSON body
  • 按状态码分类处理错误（4xx/5xx/超时）
  • 用 AsyncClient 写异步请求
  • 了解 SSE 流式响应怎么读（LLM streaming 的传输层）

1. HTTP 请求的组成

一次请求就是这几样：

  • 方法：GET（取数据）、POST（提交数据）为主
  • URL：请求哪个地址
  • Headers：元信息。OpenAI API Key 常用 Authorization: Bearer <key>；直接调用 Anthropic API 时，API Key 使用 x-api-key: <key>。其他凭据类型及附加 header 必须遵循目标服务当前官方文档；JSON 请求通常还带 Content-Type: application/json
  • Body：请求体，调 LLM 时是一段 JSON（prompt、参数）

响应回来则有：状态码（200 成功 / 4xx 你错了 / 5xx 服务端错了）、响应 headers、响应 body（通常是 JSON）。

2. httpx 基础：GET / POST

import httpx

# 简单 GET
r = httpx.get("https://api.example.com/status", timeout=10)
print(r.status_code)       # 200
print(r.json())            # 自动把响应体解析成 dict

# POST：带鉴权 header + JSON body（示例服务采用 Bearer）
# 若直接调用 Anthropic API，API Key 应按官方文档放在 x-api-key。
resp = httpx.post(
    "https://api.example.com/v1/chat",
    headers={"Authorization": "Bearer example-token"},
    json={"model": "example-model", "messages": [{"role": "user", "content": "你好"}]},
    timeout=30,
)
data = resp.json()

复用连接：要发多个请求时，用 Client() 复用底层连接（更快），并集中配置 base_url / headers / timeout：

with httpx.Client(
    base_url="https://api.example.com",
    headers={"Authorization": "Bearer example-token"},
    timeout=30,
) as client:
    a = client.post("/v1/chat", json={"messages": [...]})
    b = client.post("/v1/chat", json={"messages": [...]})   # 复用连接
# with 结束自动关闭（呼应 L10 的上下文管理器）

同步 timeout 的边界：httpx 的同步 timeout=30（同理，后文的 timeout=remaining）配置的是 connect/read/write/pool 各阶段的超时，不是覆盖整个调用的硬墙钟计时器。例如响应持续在每个 read timeout 到期前送来少量数据，调用总时长仍可能超过 30 秒。同步包装层可以在请求前后用单调时钟做截止时间记账，在发现越界后拒绝结果并停止后续等待/重试，但无法抢占正在进行的同步响应。若需要到点发起取消，应在 L16 使用异步操作与取消机制；取消传播和连接清理仍可能让实际墙钟结束时间晚于截止时刻。

Q 调 LLM 时，API Key 通常放在请求的哪部分？
API Key 通常放在请求 Headers，而不是 URL 或 Body；具体 header 由服务商定义。OpenAI API Key 常用 Authorization: Bearer，直接调用 Anthropic API 的 API Key 使用 x-api-key；其他凭据类型必须核对当前官方文档。放进 URL 容易被日志和浏览器历史记录泄露。

3. 按状态码处理错误

import httpx

try:
    r = httpx.post(url, json=payload, timeout=30)
    r.raise_for_status()             # 4xx/5xx 会抛 HTTPStatusError
    data = r.json()
except httpx.TimeoutException:
    ...                              # 超时：可重试（交给唯一传输策略）
except httpx.HTTPStatusError as e:
    code = e.response.status_code
    retry_after = e.response.headers.get("retry-after")
    if code == 429:
        ...                          # 限流：退避后重试，若有 Retry-After 优先按它等
    elif code == 408:
        ...                          # 请求超时：通常可重试
    elif 500 <= code < 600:
        ...                          # 服务端错误：多数可重试(具体看厂商约定)
    else:
        ...                          # 其它 4xx(如 401/400)：通常别重试，是你的问题
except httpx.RequestError:
    ...                              # 连接层错误(DNS、断网)：网络类，通常可重试
🔑 Agent 开发关联：

429（限流）、408/网络类错误、部分 5xx 通常可重试；400/401 通常不可重试。但这不是绝对规则——具体能不能重试，要看异常类型、这个操作是否幂等、以及厂商响应里的 Retry-After 头或错误码（比如同样是 5xx，有的服务会在错误体里标注"不可重试"；一个会产生副作用的非幂等 POST，即便是 5xx 也要谨慎重试，避免重复下单/重复扣费一类问题）。

另外注意：Anthropic 官方 Python SDK 当前会重试连接错误以及 408、409、429、5xx，默认 max_retries=2，含义是初始请求之后最多再重试 2 次，即总计最多尝试 3 次。这是该 SDK 的上游策略，不是通用 HTTP 规则。若让 SDK 保持默认重试，应用层就不要再无意叠加重试；若必须由应用统一策略，则显式配置 SDK 不重试。两层若各自最多尝试 3 次，最坏会放大为 9 次底层调用。

最佳实践：每条调用链只保留一个重试拥有者

适用：同一次业务调用可能同时经过自带重试的 SDK 与应用/raw-httpx 包装层，而且这条调用链已经决定启用重试。此时只做一个决定：重试由哪一层拥有。外层共享并关闭 Client 可以作为连接管理的装配前提，但不是本卡要比较的决策。

❌ 同一调用：SDK + 应用双重试
gateway = ChatGateway(
    sdk_retries=1,
    raw_retries=1,
)
result = gateway.ask("ping")

业务接口、任务和预期结果都不变，却有两个 owner；配置必须在发请求前拒绝，否则底层调用可能乘法放大。

✅ 同一调用：只由 SDK 重试
gateway = ChatGateway(
    sdk_retries=1,
    raw_retries=0,
)
result = gateway.ask("ping")

仍然调用 ask("ping") 并得到同一结果，唯一变化只是 SDK 成为唯一 owner。

为什么更优：质量上，单一 owner 让失败次数与诊断归属可预测；成本上，避免两层重试把底层调用、延迟和计费乘法放大。可选方案只有两种：官方 SDK 已满足需求时采用 SDK-only；必须自定义策略时关闭 SDK 重试，采用 raw/app-only。两者不能同时开启；既然本调用链要求重试，也不能两者都关闭。共享 Client 只负责连接复用与关闭，和 owner 选择正交。

动手自检（纯标准库，静默通过）：
class Transient(Exception):
    pass

class RetryOwnershipError(ValueError):
    pass

class FakeUpstream:
    def __init__(self):
        self.calls = 0

    def send(self, task):
        self.calls += 1
        if self.calls == 1:
            raise Transient
        return {"task": task, "answer": "pong"}

class FakeSDK:
    def __init__(self, upstream, retries):
        self.upstream, self.retries = upstream, retries

    def complete(self, task):
        for attempt in range(self.retries + 1):
            try:
                return self.upstream.send(task)
            except Transient:
                if attempt == self.retries:
                    raise

class ChatGateway:
    def __init__(self, upstream, *, sdk_owner, raw_owner):
        if sdk_owner == raw_owner:  # both True or both False
            raise RetryOwnershipError("choose exactly one retry owner")
        self.sdk = FakeSDK(upstream, retries=1 if sdk_owner else 0)
        self.raw_retries = 1 if raw_owner else 0

    def ask(self, task):
        for attempt in range(self.raw_retries + 1):
            try:
                return self.sdk.complete(task)
            except Transient:
                if attempt == self.raw_retries:
                    raise

TASK = "ping"
EXPECTED = {"task": TASK, "answer": "pong"}

for owners in ((True, True), (False, False)):
    upstream = FakeUpstream()
    try:
        ChatGateway(upstream, sdk_owner=owners[0], raw_owner=owners[1])
    except RetryOwnershipError:
        pass
    else:
        raise AssertionError("both/none must be rejected")
    assert upstream.calls == 0

for owners in ((True, False), (False, True)):
    upstream = FakeUpstream()
    gateway = ChatGateway(
        upstream, sdk_owner=owners[0], raw_owner=owners[1])
    assert gateway.ask(TASK) == EXPECTED
    assert upstream.calls == 2

通过证据：脚本必须无输出且退出码为 0。双 owner 与无 owner 都会在底层调用前被拒绝；SDK-only 与 raw-only 通过同一个 ask 接口完成同一任务、返回同一业务结果，并且都只有 2 次底层调用，没有乘法放大。

4. AsyncClient：异步请求

httpx 的杀手锏是原生异步——把 Client 换成 AsyncClient，请求前加 await。这是下一课"并发调用多个 LLM"的基础。本课只要求认识 async def / await / async with 这几个结构长什么样，怎么用它们写并发（gather、限流）留给 L16 单独讲。

关键：AsyncClient 要在批次/应用生命周期共享，不要每次请求都新建。正确做法是把 client 作为依赖注入给发请求的函数：

import httpx, asyncio

async def call(client, prompt):                 # client 由外部传入(依赖注入)
    r = await client.post("/v1/chat", json={"prompt": prompt})
    r.raise_for_status()
    return r.json()

async def main():
    # 一个批次/一个应用生命周期只创建一个 client，复用连接池
    async with httpx.AsyncClient(base_url="https://api.example.com", timeout=30) as client:
        result = await call(client, "你好")
        # 同一批次里的其它请求都传入同一个 client，而不是各自 async with 新建一个

asyncio.run(main())

✗ 反例：如果在一个 hot loop（比如批量处理 100 个 prompt）里，每次调用都 async with httpx.AsyncClient() as client 新建一个客户端，就完全失去了连接池复用的意义，还会因频繁建连拖慢速度。client 的生命周期应该和"这一批任务"或"整个应用"对齐，而不是和"这一个请求"对齐。

同步版会"一个请求干等着"；异步版在等网络时能去干别的——所以能同时发很多请求（真正的并发调度、gather、Semaphore 限流留给 L16 详解）。

Q 收到状态码 429，Agent 通常应该怎么做？
429 = Too Many Requests（限流），通常属于临时错误。应先遵循合法的 Retry-After；缺失或畸形时才使用该上游声明的后备等待/退避，并且完整等待必须落在剩余操作预算内。相对地，400/401 通常应修正请求而不是重试；最终仍以上游契约和操作语义为准。

5. SSE 流式响应（了解）

LLM 的流式输出走的是 SSE（Server-Sent Events）：响应不是一次性返回，而是持续推送多行事件。下面是简化版的 OpenAI 风格 SSE——每行 data: {...}，以 data: [DONE] 结束。本课只演示怎么用 httpx.stream/iter_lines 逐行读，不是一个能通吃所有厂商的通用 parser：

import json, httpx

with httpx.stream("POST", url, json={"stream": True}, timeout=None) as r:
    for line in r.iter_lines():
        if line.startswith("data: "):
            chunk = line.removeprefix("data: ")     # 剥掉前缀(呼应 L04)
            if chunk == "[DONE]":
                break
            event = json.loads(chunk)               # 逐块解析(呼应 L09)
            # 取出增量 token 显示...

※ 注意这只是 OpenAI 风格的简化示例。Anthropic 的 SSE 格式不同：每条事件带 event: message_start / content_block_delta / message_stop 这类具名事件类型，终止方式也不是 [DONE]，而是 message_stop 事件。实际项目里，不管调哪家的 API，都优先用官方 SDK 提供的流式接口——它已经处理好了具体协议细节、返回结构化的事件对象，不需要自己手写行解析。

看出来了吗——这正好把前面学的串起来：生成器思维（L12）+ 字符串处理（L04）+ 流式 JSON 解析（L09）+ HTTP 传输（本课）。

知识图谱

HTTP 请求组成
├── 方法(GET/POST) + URL
├── Headers → 按服务文档鉴权(OpenAI API Key 常用 Bearer；Anthropic API Key 用 x-api-key) / Content-Type
├── Body → JSON(prompt+参数)
└── 响应：状态码 + headers + body(JSON)

httpx（pip install httpx）
├── get/post(headers=, json=, timeout=)
├── Client(base_url, headers, timeout) → 复用连接(with 自动关)
├── r.status_code / r.json() / r.raise_for_status()
├── 错误：TimeoutException / HTTPStatusError / RequestError
└── AsyncClient + await → 异步(→ L16 并发)

状态码策略
├── 2xx 成功
├── 429 / 408 / 网络错误 / 部分5xx → 通常可重试
├── 400/401 等其它4xx → 通常不可重试

SSE 流式(OpenAI风格简化示例) → iter_lines + removeprefix("data: ") + json.loads
└── Anthropic 用 event: 具名事件+不同终态 → 优先用官方 SDK 的结构化流式接口

实战练习

练习：让业务模块依赖深传输接口

基于最佳实践卡中的 UpstreamTransport，写一个迷你聊天业务模块。目标不是再实现一次 HTTP 或重试，而是让业务代码只表达操作语义。先自己写，再看答案。

任务清单

  1. Chat 构造时只接收 transport，不接收 Client、parser、classifier、clock 或 send。
  2. ask(prompt) 调用 transport.post_json("chat.complete", "/v1/chat", payload)。
  3. 从返回 JSON 取回答；不在业务模块判断状态码或编写重试循环。
  4. 外层创建一个 Client 和一个 transport，并负责关闭 Client。
💡 点击查看参考答案 
import httpx

class Chat:
    def __init__(self, transport):
        self.transport = transport

    def ask(self, prompt):
        payload = {
            "model": "example-model",
            "messages": [{"role": "user", "content": prompt}],
        }
        data = self.transport.post_json(
            "chat.complete", "/v1/chat", payload)
        return data["choices"][0]["message"]["content"]

with httpx.Client(
    base_url="https://api.example.com",
    headers={"Authorization": "Bearer example-token"},
    timeout=30,
) as client:
    transport = UpstreamTransport(client)
    chat = Chat(transport)
    answer = chat.ask("你好")

这里故意没有 Tenacity：raw-httpx 的重试已由 UpstreamTransport 独占。若改用自带重试的官方 SDK，应整体替换 transport，而不是在 Chat 外再包一层重试。

思考题

Q1为什么 operation 要进入 transport 接口？

【结论】可重试性属于“操作语义 + 上游契约”，不是状态码的固定属性。同一个 409 对预约创建可以是短暂冲突，对目录查询却应立即失败。业务层只提供稳定操作名，transport 在唯一位置分类。

Q2同步与异步并发调用 10 个 prompt 有什么差别？

【结论】同步串行耗时约为 10 次延迟之和；异步并发能重叠网络等待，耗时接近最慢的一次请求。真实场景仍需并发上限与限流；这些留到 L16。

面试常见问题

Q1：这个课程为什么选择 httpx？什么时候不必选它？

答：本课程需要用相近接口同时讲同步 Client、异步 AsyncClient 和离线 MockTransport，因此选择 httpx。真实项目若已有覆盖所需能力的官方 SDK，应先使用 SDK；稳定的同步 requests 项目若没有异步需求，也不必仅为换库而迁移。选型依据是接口需求、生态、迁移成本和目标服务支持，而不是年份排名。

Q2：HTTP 状态码 4xx 和 5xx 的区别？各怎么处理？

答：4xx 是客户端错误（400 参数错、401 鉴权失败、429 限流），5xx 是服务端错误。429、408、部分 5xx 通常临时性、可退避重试；其它 4xx（如 400/401）通常是你自己的问题，重试无用，应修正请求。但这不是绝对规则，具体要看异常类型、请求是否幂等、厂商的 Retry-After/错误码。若用官方 SDK，它常已内置重试，别再自己叠加一层。

Q3：调 LLM 的 API Key 放哪里？为什么？

答：放目标服务规定的请求头，不放 URL、源码或日志。OpenAI API Key 常用 Authorization: Bearer <key>；直接调用 Anthropic API 时，API Key 使用 x-api-key: <key>。其他凭据类型及附加 header 必须核对当前官方文档；真实项目优先使用官方 SDK 的凭据解析，并避免硬编码。

Q4：什么是 SSE？和 LLM streaming 什么关系？

答：SSE（Server-Sent Events）是服务端持续推送多行事件的协议。OpenAI 风格是简化的 data: {...} + [DONE]；Anthropic 用具名的 event: 类型、终态也不同。LLM 流式输出的传输层原理都是逐行读、解析事件——但具体协议细节因厂商而异，实际项目应优先用官方 SDK 的结构化流式接口，而不是自己手写通用 parser。

本课最佳实践验收：共享 Client 与唯一 UpstreamTransport

任务目标

为目录查询和预约创建建立唯一 UpstreamTransport，证明共享 Client、HTTP 分类、重试所有权和预算记账集中在同一边界，并明确同步超时不等于硬取消。

操作清单

  1. 只暴露 JSON GET/POST。
  2. 让 Catalog 和 Reservations 只接收 transport。
  3. 用公开接口覆盖严格数字秒、HTTP-date、显式后备和截止时间记账。
  4. 验证操作上下文决定 409，并保留原始 header。

通过标准

  1. Client 与 transport 身份共享，且只有 transport 重试。
  2. 有效等待不截短；请求前已到截止时间或完整等待会越界时，不 sleep、不重试。
  3. 请求前后都读取单调时钟；若同步请求返回时已经越界，拒绝其成功或普通错误结果，并以 BudgetExceeded 表示“已检测/已记账的越界”，而非已抢占请求。
  4. timeout=remaining 仅约束 httpx 各阶段/连接池等待，不宣称硬墙钟总时限；最终尝试后不 sleep；目录 409 一次，预约 409 可恢复或三次耗尽。
  5. 标准输出严格为 L15 ACCEPTED。

class UpstreamError(Exception):
    def __init__(self, operation, status, retryable, raw):

        self.operation, self.status_code = operation, status
        self.retryable, self.retry_after_raw = retryable, raw
class BudgetExceeded(UpstreamError):
    # Detected after a request returns, or before the next action; not cancellation.

                         error.retryable, error.retry_after_raw)
        self.phase, self.remaining_seconds = phase, remaining
class RetryDelayExceedsBudget(BudgetExceeded):
    def __init__(self, error, required, remaining):
        super().__init__(error, "retry-wait", remaining)
        self.required_delay = required
class UpstreamTransport:
    _DIGITS = re.compile(r"[0-9]+\Z")
    _TRANSIENT = frozenset({408, 429, 502, 503, 504})
    def __init__(self, client, *, attempts=3, budget=30.0, fallback=1.5,
                 monotonic, wall_now, sleep):
        if fallback <= 0: raise ValueError("fallback must be positive")
        self._client, self._attempts, self._budget = client, attempts, budget
        self._fallback = fallback
        self._monotonic, self._wall_now, self._sleep = monotonic, wall_now, sleep
    def get_json(self, operation, path):
        return self._request("GET", operation, path, None)
    def post_json(self, operation, path, payload):
        return self._request("POST", operation, path, payload)
    def _error(self, operation, response):
        status = response.status_code
        retryable = status in self._TRANSIENT or (
            operation == "reservation.create" and status == 409)
        return UpstreamError(operation, status, retryable,
                             response.headers.get("Retry-After"))
    def _delay(self, raw):
        if raw is None: return self._fallback
        if self._DIGITS.fullmatch(raw): return float(raw)
        try: target = parsedate_to_datetime(raw)
        except (TypeError, ValueError, OverflowError): return self._fallback
        if target.tzinfo is None: return self._fallback
        return max(0.0, (target - self._wall_now()).total_seconds())
    def _request(self, method, operation, path, payload):
        deadline = self._monotonic() + self._budget
        last = UpstreamError(operation, None, True, None)
        for attempt in range(1, self._attempts + 1):
            remaining = deadline - self._monotonic()
            if remaining <= 0: raise BudgetExceeded(last, "request", 0.0)
            try:
                response = (self._client.get(path, timeout=remaining)
                    if method == "GET" else self._client.post(
                        path, json=payload, timeout=remaining))
            except httpx.RequestError:
                error = last = UpstreamError(operation, None, True, None)
            else:
                if response.is_success:
                    if self._monotonic() >= deadline:
                        ok = UpstreamError(operation, response.status_code, False,
                            response.headers.get("Retry-After"))
                        raise BudgetExceeded(ok, "request", 0.0)
                    return response.json()
                error = last = self._error(operation, response)
            remaining = max(0.0, deadline - self._monotonic())
            if remaining <= 0:  # 先判预算，再判最终尝试
                raise BudgetExceeded(error, "request", remaining)
            if not error.retryable or attempt == self._attempts: raise error
            delay = self._delay(error.retry_after_raw)
            if delay > remaining:
                raise RetryDelayExceedsBudget(error, delay, remaining)
            self._sleep(delay)
        raise AssertionError("unreachable")
class Clock:
    def __init__(self):
        self.elapsed, self.waits = 0.0, []
        self.origin = datetime(2015, 10, 21, 7, 28, tzinfo=timezone.utc)
    def monotonic(self): return self.elapsed
    def wall_now(self): return self.origin + timedelta(seconds=self.elapsed)
    def sleep(self, seconds): self.waits.append(seconds); self.elapsed += seconds
class Catalog:
    def __init__(self, transport): self.transport = transport
    def lookup(self, sku):
        return self.transport.get_json("catalog.lookup", f"/catalog/{sku}")
class Reservations:
    def __init__(self, transport): self.transport = transport
    def create(self, seat):
        return self.transport.post_json(
            "reservation.create", "/reservations", {"seat": seat})

结果诊断：标准输出必须严格为一行 L15 ACCEPTED。Catalog 与 Reservations 只共享一个 transport；公开接口证明目录 409 只调用一次，预约 409 可恢复或三次耗尽。最强证据是：同一 transport 严格解析并保留原始 header；等待会超过剩余时间时不 sleep、不重试；同步请求返回后单调时钟若已越界，则拒绝该成功/错误结果；最终尝试后不 sleep。这只证明截止时间的检测与记账，不证明硬墙钟总时限或对在途同步响应的抢占；timeout=remaining 仍是 httpx 的阶段/连接池超时。需要取消截止时间时应在 L16 使用异步操作，且清理可能使实际墙钟结束稍晚。

总结

  • HTTP 请求 = 方法 + URL + Headers(鉴权) + Body(JSON)；响应看状态码
  • httpx：get/post(headers=, json=, timeout=)，多请求用 Client 复用连接
  • raise_for_status() + 分类捕获 TimeoutException / HTTPStatusError
  • 429/408/网络/部分5xx 通常可重试，其它4xx（如400/401）通常不重试；具体看异常类型、是否幂等、Retry-After；官方 SDK 常已自动重试，别重复叠加
  • AsyncClient 应在批次/应用生命周期共享、依赖注入给调用函数，不要每请求新建；await 结构是并发调 LLM 的基础（真正并发调度 → L16）
  • SSE 流式（OpenAI风格简化示例）= iter_lines + 剥 data: 前缀 + 解析 JSON（串起 L04/L09/L12）；Anthropic 的 event 类型不同，优先用官方 SDK
