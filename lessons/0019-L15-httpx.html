用 httpx 发起 HTTP 请求

每一次 LLM 调用、每个联网工具，本质都是一个 HTTP 请求

💡 为什么这课重要？

你调 OpenAI/Anthropic 的 SDK，底层就是在发 HTTP 请求：带上 API Key 的 header、JSON 请求体、处理状态码、读回 JSON。你写的每个"联网工具"（搜索、查天气、调内部 API）也一样。HTTP 是 Agent 的传输层地基。

2026 年首选的 Python HTTP 客户端是 httpx——因为它同时支持同步和异步（下一课并发调用要用），API 和老牌的 requests 几乎一样。

※ 本课代码需先安装 httpx：uv add httpx（或 pip install httpx）。httpx 也是 OpenAI/Anthropic 官方 SDK 内部使用的客户端。

学习目标

完成本课后，你将能够：

  • 理解 HTTP 请求的组成：方法、URL、headers、body、状态码
  • 用 httpx 发 GET/POST，带 headers 和 JSON body
  • 按状态码分类处理错误（4xx/5xx/超时）
  • 用 AsyncClient 写异步请求
  • 了解 SSE 流式响应怎么读（LLM streaming 的传输层）

1. HTTP 请求的组成

一次请求就是这几样：

  • 方法：GET（取数据）、POST（提交数据）为主
  • URL：请求哪个地址
  • Headers：元信息，如 Authorization: Bearer <key>（鉴权）、Content-Type: application/json
  • Body：请求体，调 LLM 时是一段 JSON（prompt、参数）

响应回来则有：状态码（200 成功 / 4xx 你错了 / 5xx 服务端错了）、响应 headers、响应 body（通常是 JSON）。

2. httpx 基础：GET / POST

import httpx

# 简单 GET
r = httpx.get("https://api.example.com/status", timeout=10)
print(r.status_code)       # 200
print(r.json())            # 自动把响应体解析成 dict

# POST：带鉴权 header + JSON body（模拟调 LLM）
resp = httpx.post(
    "https://api.example.com/v1/chat",
    headers={"Authorization": "Bearer sk-xxx"},
    json={"model": "claude", "messages": [{"role": "user", "content": "你好"}]},
    timeout=30,
)
data = resp.json()

复用连接：要发多个请求时，用 Client() 复用底层连接（更快），并集中配置 base_url / headers / timeout：

with httpx.Client(
    base_url="https://api.example.com",
    headers={"Authorization": "Bearer sk-xxx"},
    timeout=30,
) as client:
    a = client.post("/v1/chat", json={"messages": [...]})
    b = client.post("/v1/chat", json={"messages": [...]})   # 复用连接
# with 结束自动关闭（呼应 L10 的上下文管理器）
Q 调 LLM 时，API Key 通常放在请求的哪部分？
API Key 通常放在请求头 Authorization: Bearer <key>。放进 URL 会被日志/浏览器历史记录泄露，不安全。Headers 携带鉴权与元信息（Content-Type 等），Body 携带实际数据。

3. 按状态码处理错误

import httpx

try:
    r = httpx.post(url, json=payload, timeout=30)
    r.raise_for_status()             # 4xx/5xx 会抛 HTTPStatusError
    data = r.json()
except httpx.TimeoutException:
    ...                              # 超时：可重试（配合 L10 的 tenacity）
except httpx.HTTPStatusError as e:
    code = e.response.status_code
    retry_after = e.response.headers.get("retry-after")
    if code == 429:
        ...                          # 限流：退避后重试，若有 Retry-After 优先按它等
    elif code == 408:
        ...                          # 请求超时：通常可重试
    elif 500 <= code < 600:
        ...                          # 服务端错误：多数可重试(具体看厂商约定)
    else:
        ...                          # 其它 4xx(如 401/400)：通常别重试，是你的问题
except httpx.RequestError:
    ...                              # 连接层错误(DNS、断网)：网络类，通常可重试
🔑 Agent 开发关联：

429（限流）、408/网络类错误、部分 5xx 通常可重试；400/401 通常不可重试。但这不是绝对规则——具体能不能重试，要看异常类型、这个操作是否幂等、以及厂商响应里的 Retry-After 头或错误码（比如同样是 5xx，有的服务会在错误体里标注"不可重试"；一个会产生副作用的非幂等 POST，即便是 5xx 也要谨慎重试，避免重复下单/重复扣费一类问题）。

另外注意：如果你用的是 OpenAI/Anthropic 官方 SDK，SDK 通常已经内置了指数退避重试（针对 429/5xx/网络错误）。这时不要在自己的代码里再叠加一层 tenacity/自定义重试——两层重试叠加会让真正失败的请求被重试次数远超预期（比如 SDK 重试 3 次、外层又重试 3 次，等效变成 9 次），既浪费配额也可能放大限流。是否需要自己包一层，先确认 SDK 有没有做、做到什么程度。

4. AsyncClient：异步请求

httpx 的杀手锏是原生异步——把 Client 换成 AsyncClient，请求前加 await。这是下一课"并发调用多个 LLM"的基础。本课只要求认识 async def / await / async with 这几个结构长什么样，怎么用它们写并发（gather、限流）留给 L16 单独讲。

关键：AsyncClient 要在批次/应用生命周期共享，不要每次请求都新建。正确做法是把 client 作为依赖注入给发请求的函数：

import httpx, asyncio

async def call(client, prompt):                 # client 由外部传入(依赖注入)
    r = await client.post("/v1/chat", json={"prompt": prompt})
    r.raise_for_status()
    return r.json()

async def main():
    # 一个批次/一个应用生命周期只创建一个 client，复用连接池
    async with httpx.AsyncClient(base_url="https://api.example.com", timeout=30) as client:
        result = await call(client, "你好")
        # 同一批次里的其它请求都传入同一个 client，而不是各自 async with 新建一个

asyncio.run(main())

✗ 反例：如果在一个 hot loop（比如批量处理 100 个 prompt）里，每次调用都 async with httpx.AsyncClient() as client 新建一个客户端，就完全失去了连接池复用的意义，还会因频繁建连拖慢速度。client 的生命周期应该和"这一批任务"或"整个应用"对齐，而不是和"这一个请求"对齐。

同步版会"一个请求干等着"；异步版在等网络时能去干别的——所以能同时发很多请求（真正的并发调度、gather、Semaphore 限流留给 L16 详解）。

Q 收到状态码 429，Agent 通常应该怎么做？
429 = Too Many Requests（限流），是临时性的，正确做法是等一会儿（指数退避）再重试。相对地，4xx 里的 400/401 是你自己请求有问题（参数错/鉴权失败），重试没用，应直接修。

5. SSE 流式响应（了解）

LLM 的流式输出走的是 SSE（Server-Sent Events）：响应不是一次性返回，而是持续推送多行事件。下面是简化版的 OpenAI 风格 SSE——每行 data: {...}，以 data: [DONE] 结束。本课只演示怎么用 httpx.stream/iter_lines 逐行读，不是一个能通吃所有厂商的通用 parser：

import json, httpx

with httpx.stream("POST", url, json={"stream": True}, timeout=None) as r:
    for line in r.iter_lines():
        if line.startswith("data: "):
            chunk = line.removeprefix("data: ")     # 剥掉前缀(呼应 L04)
            if chunk == "[DONE]":
                break
            event = json.loads(chunk)               # 逐块解析(呼应 L09)
            # 取出增量 token 显示...

※ 注意这只是 OpenAI 风格的简化示例。Anthropic 的 SSE 格式不同：每条事件带 event: message_start / content_block_delta / message_stop 这类具名事件类型，终止方式也不是 [DONE]，而是 message_stop 事件。实际项目里，不管调哪家的 API，都优先用官方 SDK 提供的流式接口——它已经处理好了具体协议细节、返回结构化的事件对象，不需要自己手写行解析。

看出来了吗——这正好把前面学的串起来：生成器思维（L12）+ 字符串处理（L04）+ 流式 JSON 解析（L09）+ HTTP 传输（本课）。

import httpx

BASE = "https://api.example.com"
HEADERS = {"Authorization": "Bearer sk-xxx"}

class LLMError(Exception):
    def __init__(self, msg, retryable: bool):
        super().__init__(msg)
        self.retryable = retryable      # 调用方据此决定要不要重试

def _parse(r: httpx.Response) -> str:
    try:
        r.raise_for_status()
    except httpx.HTTPStatusError as e:
        code = e.response.status_code
        # 简化分类：429/408/5xx 通常可重试；生产中还要结合 Retry-After、
        # 具体错误码、以及这次请求是否幂等来决定
        retryable = code in (429, 408) or 500 <= code < 600
        raise LLMError(f"HTTP {code}", retryable) from e
    return r.json()["choices"][0]["message"]["content"]

# client 由外部创建并传入(批次/应用生命周期共享一个，不在这里新建)
def chat(client: httpx.Client, prompt: str) -> str:
    payload = {"model": "claude", "messages": [{"role": "user", "content": prompt}]}
    try:
        r = client.post("/v1/chat", json=payload)
    except httpx.TimeoutException as e:
        raise LLMError("timeout", retryable=True) from e
    return _parse(r)

async def achat(client: httpx.AsyncClient, prompt: str) -> str:
    payload = {"model": "claude", "messages": [{"role": "user", "content": prompt}]}
    r = await client.post("/v1/chat", json=payload)
    return _parse(r)

思考题

先自己想，再点开对答案。

Q1为什么要把 retryable 标记在异常上，而不是在调用处判断状态码？

【结论】因为"这个错该不该重试"是错误本身固有的属性。把它标在异常上，让这份知识随错误一起传播，重试逻辑只需问 exc.retryable，不用在每个调用点重复判断状态码——错误来源与重试策略就此解耦。

如果在调用处判断，每个发请求的地方都要重写一遍"429 或 5xx 才重试、4xx 不重试"的逻辑。散落多处，容易写漏、写岔；将来新增一种可重试错误，得逐个地方改。

把判断收敛到抛错的 _parse 一处（retryable = code in (429, 408) or 500 <= code < 600，生产中还要结合 Retry-After、具体错误码、请求是否幂等），异常带着结论往上冒。tenacity 的重试条件只看 isinstance(e, LLMError) and e.retryable，通用且干净。

好处：新增错误类型只改抛错那一处；重试策略与"哪些错可重试"彻底分离；调用方代码更薄。这就是让语义随对象走、而非散落在流程里的设计思路。

Q2同步 chat 和异步 achat，在"同时调 10 个 prompt"时差别有多大？

【结论】差别接近 10 倍：同步串行大约是 10 × 单个请求延迟（一个接一个等），异步并发（gather）大约只要 1 × 单个请求延迟（10 个网络等待重叠在一起）。

同步 chat 一次只能发一个、等它回来再发下一个。10 个各 1 秒的请求，总耗时≈10 秒——CPU 大部分时间在干等网络。

异步 achat 配 asyncio.gather 可以同时把 10 个请求都发出去，然后一起等。因为瓶颈是 I/O（等网络）而非计算，等待时间可以重叠，总耗时≈最慢的那一个≈1 秒多。

这正是下一课 L16 的主题：I/O 密集场景下 async 靠重叠等待实现高并发。注意真实场景还要用 Semaphore 限流，否则一口气打太多会触发 429 或耗尽本地连接。

面试常见问题

Q1：为什么 2026 年选 httpx 而不是 requests？

答：httpx API 和 requests 几乎一样，但原生支持异步（AsyncClient），还支持 HTTP/2、连接池、超时更完善。Agent 要并发调 LLM，异步是刚需，所以选 httpx。

Q2：HTTP 状态码 4xx 和 5xx 的区别？各怎么处理？

答：4xx 是客户端错误（400 参数错、401 鉴权失败、429 限流），5xx 是服务端错误。429、408、部分 5xx 通常临时性、可退避重试；其它 4xx（如 400/401）通常是你自己的问题，重试无用，应修正请求。但这不是绝对规则，具体要看异常类型、请求是否幂等、厂商的 Retry-After/错误码。若用官方 SDK，它常已内置重试，别再自己叠加一层。

Q3：调 LLM 的 API Key 放哪里？为什么？

答：放请求头 Authorization: Bearer <key>。放 URL 会被日志和历史泄露；放 header 是标准且相对安全的做法（再配合环境变量管理，别硬编码）。

Q4：什么是 SSE？和 LLM streaming 什么关系？

答：SSE（Server-Sent Events）是服务端持续推送多行事件的协议。OpenAI 风格是简化的 data: {...} + [DONE]；Anthropic 用具名的 event: 类型、终态也不同。LLM 流式输出的传输层原理都是逐行读、解析事件——但具体协议细节因厂商而异，实际项目应优先用官方 SDK 的结构化流式接口，而不是自己手写通用 parser。
