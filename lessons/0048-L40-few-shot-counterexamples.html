Zero-shot、Few-shot 与反例

给一个能区分「问工单」和「要起草」的边界示例

为什么这课重要？

「工单草稿是什么？」也有“工单”，但用户没有要求起草。单靠关键词会把解释任务误判为起草。本课用 L39 的结果契约，把容易混淆的边界写清。

学习目标

写出一对正例和近邻反例；用同一批开发用例比较有无示例，不把构造成功当成效果更好。

1. 写出的不是更多规则，而是带标签的例子

Zero-shot 给任务规则但不给已标注的演示；Few-shot 在同样的规则下附上少量输入与预期输出。两者都不修改模型权重。系统规则说明怎么判断，当前用户消息是待判断的输入，演示则展示规则如何用于别的输入。不要把本轮的测试问题混进演示，或让演示替代规则。

造演示时先选一个明确要求起草的正例，再保留「保留期工单草稿」这些词，把动作改成询问。它是起草的近邻反例，但它的标签必须正确：answer。这组对照展示的是「想了解」和「要我写」之间的差别，而不是哪个关键词出现了。这里只判这两类意图；提交请求由应用拒绝，分类结果不授予执行权限。

3. 看错在误起草，还是漏起草

把「应起草」当正类，每道题用人工预期和返回标签在下表记一格。这是混淆矩阵的读法，不是实测结果；两份提示都还没有模型输出。

人工预期返回 draft返回 answer
应起草真正例（TP）：正确识别起草假负例（FN）：漏起草
不应起草假正例（FP）：误起草真负例（TN）：正确识别问答

上面的格式问题若被标成 draft，就记一个 FP；「先帮我拟一份保留期确认工单」若被标成 answer，就记一个 FN。无效标签另记格式失败，不算成正确问答。以后比较时固定模型、设置和开发题，分别统计两类错；若误起草少了但漏起草多了，要按业务代价取舍。规则已足够时可以省掉示例；若意图实在含混，应用可先问清楚，而不是靠示例猜。离线自检核对请求组装与人工标注，不测模型表现。

最佳实践：用近邻反例说明边界，只改变示例

适用与限制：当「工单草稿」这个词反复引起误判时，添加一对词相似、意图不同的演示。若错在应用的授权规则，改示例不能修复权限边界。

错误做法：一起改规则和示例

开发题是「只想看看工单草稿的格式，有示例吗？」（预期 answer）。给候选请求多加一条规则，再把这道题原样塞进演示；即使答对，也不知道是规则、记住例句还是理解边界起了作用。

推荐做法：保留同一题，只换演示条件

同一开发题不出现在演示里。两组规则相同，一组不给示例，一组给「请帮我写一份工单草稿」（draft）和「谁负责填写工单草稿？」（answer）。

取舍：近邻对照突出「请求起草」而不是「出现关键词」；只改示例才能比较这一改动。示例占上下文，也可能让模型偏向某种措辞。若仅规则已能稳定区分，就保留更短的 zero-shot；若要判断收益，还得固定模型与设置，实际比较漏起草和误起草。

  1. 先给不同措辞的开发题标注预期，覆盖应起草和不应起草两侧。
  2. 运行离线请求对照，检查两组输入除 examples 外一致，开发题不在演示里，且每条人工标签与参考答案相符。

结果诊断：L40 ACCEPTED 表示请求按计划组装、开发题与演示没有原句重叠，且逐题标注正确。没有模型输出，不能从这行推断示例降低了误判率。

4. 动手：为同一批问题生成两组请求

先对照同一批开发题的组装与标注，再在下一节独立完成新题。这里的请求只是应用内部的字典，settings（含 temperature）只是本地对照字段，不是 API 参数示范。工单文本均为虚构；代码不调用模型，也不创建或提交工单。

examples = [

# 独立参考：前者询问应包含什么，后者明确委托拟稿。
gold = {"L40-01": "answer", "L40-02": "draft"}


def build(question, demos):
    return dict(rules=rule, input=question, settings={"temperature": 0}, examples=list(demos))


assert proposed.keys() == cases.keys() == gold.keys(), "案例 ID 必须齐全"
assert {item["label"] for item in examples} == {"answer", "draft"}
for case_id, question in cases.items():
    zero, few = build(question, []), build(question, examples)

    assert zero == dict(base, examples=[]) and few == dict(base, examples=examples), case_id
    assert question not in {item["input"] for item in few["examples"]}, case_id
    assert proposed[case_id] == gold[case_id], f"人工标注不符：{case_id}"

def build(question, demos):

def comparable(zero, few, question):
    base = dict(rules=rule, input=question, settings={"temperature": 0})
    return (zero == dict(base, examples=())
            and few == dict(base, examples=examples)
            and question not in {text for text, _label in examples})


def label_errors(candidate):
    assert candidate.keys() == cases.keys() == gold.keys(), "案例 ID 必须齐全"
    return {case_id for case_id in cases if candidate[case_id] != gold[case_id]}


errors = label_errors(proposed)

assert len(examples) == 2 and {label for _, label in examples} == {"answer", "draft"}

面试自查

先合上答案，按「结论 → 理由 → 如何验证」作答，再展开追问。

Q1「保留期工单草稿里通常要写日期吗？」和「请写一份保留期工单草稿，先别提交。」能当一对演示吗？

参考回答：能，前句标 answer，是在询问格式；后句标 draft，「请写」才是在委托拟稿，「先别提交」不改变这个意图。两句共用关键词，能突出用户要做什么；再拿未见过的说法来验证。

追问：用户只说「工单草稿麻烦处理一下」，选哪个标签？

答题要点：先问清是想了解格式还是请你拟稿，不靠关键词硬选。

Q2同事说「先加五条示例更保险」，但只靠规则已答对常见请求。你会马上加吗？

参考回答：不急着加。先用不在演示里的问题测规则版，既看只询问会不会被误判，也看明确委托会不会漏掉。如果两侧都能稳定区分，保留较短的规则版；常见题全对还不能说明边界题也能分清。

追问：如果只有「询问草稿格式」这一类常被误判，第一轮加什么？

答题要点：加一对措辞相近但意图相反的例子，再用没放进演示的同类题对比。

Q3同一批 100 题，20 道应起草。无演示版误起草 8 道、漏起草 2 道；有演示版分别是 3 道、7 道，没有无效标签。业务更怕误起草，你怎么选？

参考回答：若两类错误都在可接受范围内，优先有演示版。两版都答对 90 道，有演示少了 5 个假正例，却多了 5 个假负例。按事先约定的错误代价和门槛取舍，别把开发题结果当成线上比例。

追问：如果这批题最多允许漏起草 5 道，候选还能过吗？

答题要点：不能。少误起草不抵消漏起草超限；无演示版也要另核误起草的门槛。

Q4候选同时改了规则和演示，还把原来错的 3 道开发题贴进演示。现在这 3 道全对，能归功于近邻反例吗？

参考回答：不能。既分不清是规则还是示例起作用，也没测到新的请求。固定规则、模型和运行设置，两组跑同一批未放进演示的开发题，只变有无演示。逐题对照人工预期，分别记误起草、漏起草和无效标签。

追问：本课用固定案例 ID 打分，对调两个人工标签会失败。能据此说有演示的模型更准吗？

答题要点：不能。这个反例只验证评分能识别错标；离线脚本核对的是人工标注和请求组装，没有任何模型输出。要比较模型表现，还得实际运行上面的对照。
