Zero-shot、Few-shot 与反例

给一个能区分「问工单」和「要起草」的边界示例

为什么这课重要？

「工单草稿是什么？」也有“工单”，但用户没有要求起草。单靠关键词会把解释任务误判为起草。本课用 L39 的结果契约，把容易混淆的边界写清。

学习目标

写出一对正例和近邻反例；用同一批开发用例比较有无示例，不把构造成功当成效果更好。

1. 规则不变，只改变是否给示例

Zero-shot 在这次请求中只给任务规则，不提供已标注的输入输出例子；Few-shot 在同样的规则下加少量示例。它们都不是训练模型。这里的「反例」不是给错误标签，而是展示看起来像正例、按规则却应走另一条路径的输入。

输入正确标签分界线
请起草一份说明导出保留期的工单。draft明确请求生成草稿。
导出保留期工单的草稿是什么？answer只是询问，没有请求起草。

系统指令、用户请求、演示不是同一类输入。应用把稳定的任务规则放入目标接口支持的系统或开发者指令；用户消息是这次要判断的请求；示例只是已标注的演示。下方是应用内部的数据形状，不是某家 API 的请求字段。练习只比较问答和起草；提交意图由应用拒绝。模型的 draft 标签不会授予权限，Phase 4 的草稿始终不提交。

最佳实践：先加一条最容易混淆的反例

发现“工单”被误判时，不要随手堆十条正常问句。直接配一条含相同术语但只询问的示例，再用不同措辞检验有无改善。评测用例不复制演示句。

Q 哪条最适合作为起草正例的近邻反例？
这句也提到“工单”，但意图是了解含义，能检验是否过度依赖关键词。

2. 动手：为同一批问题生成两组请求

先写规则、演示对和两条未出现在演示里的开发问题。不运行模型：只检查两组请求除 examples 外一致，并手工标注预期。若日后获准在线对比，两组应固定模型、设置和开发问题，再分别统计误起草、漏起草；不要拿这段离线代码证明示例效果。

展开请求对照与自检
rule = "只有明确请求起草时返回 draft；只询问时返回 answer。不得提交工单。"
examples = [
    {"input": "请写一份保留期工单草稿。", "label": "draft"},
    {"input": "什么是保留期工单草稿？", "label": "answer"},
]
cases = [
    ("工单草稿通常写哪些内容？", "answer"),
    ("先帮我拟一份保留期确认工单。", "draft"),
]

def build(question, examples):
    return {"rules": rule, "input": question, "examples": list(examples)}

for question, expected in cases:
    zero = build(question, [])
    few = build(question, examples)
    base = {"rules": rule, "input": question}
    assert zero == dict(base, examples=[])
    assert few == dict(base, examples=examples)
    assert question not in {item["input"] for item in few["examples"]}
    assert expected in {"answer", "draft"}
assert {item["label"] for item in examples} == {"answer", "draft"}
print("L40 ACCEPTED")

保存后用 python -I 文件名.py 运行。build(question, []) 是零示例请求；传入字典列表是少量示例请求。若两次只改了措辞而没有固定规则，就不能把差异归因给示例。

面试自查

Few-shot 会修改权重吗？

这里的示例随请求发送，不改变模型权重。

为什么不用例子里已经出现的句子评测？

它只能说明会复用该例子，无法检查对新措辞的迁移。

反例应怎么挑？

选与正例表面相似、正确决策不同的真实边界，不是随便找一句反义句。

少量示例一定更好吗？

不一定。示例增加上下文开销，也可能引入偏差；比较误判与用量再决定。
