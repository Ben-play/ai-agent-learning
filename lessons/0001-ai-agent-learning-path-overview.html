AI 面试
Module 2.1 · LLM 本质与核心概念：
· LLM 是什么 — 语言模型本质（概率预测）、Transformer 直觉（不写代码）、注意力机制的作用
· Token 深度理解 — Tokenization 原理、BPE 算法、中文 vs 英文 Token 差异、tiktoken 计数、Token 与成本关系
· 生成参数解密 — Temperature / Top-P 的解码原理与厂商字段边界；部分新 Claude 模型会拒绝这些 sampling 控制的非默认值

Module 2.2 · 模型能力、局限与选型：
· 幻觉问题全解 — 预训练统计错误、评估鼓励猜测与其他工程成因；Self-Consistency/RAG/引用核验的能力边界
· 模型能力边界 — 能做什么 vs 不能做什么、Base Model vs Instruction-Tuned Model
· 推理能力与 Adaptive Thinking — 区分模型能力、adaptive thinking、effort，并按质量/延迟/Token 实测路由
· 看懂 Benchmark — 不只看模型分数，还核对数据污染、Agent scaffold、工具与预算；用开发集调参、隔离测试集验收
· 模型选型实战 — 区分开放权重、托管服务与自托管；合规看地域/合同/保留策略，总成本用真实负载测算，不按“开源/闭源”标签拍板

Module 2.3 · Token 经济学：理解多轮累计成本；按静态前缀占比和命中率评估 Prompt Caching，按业务质量评测 Model Routing；案例降幅不作保证，Batch/压缩/输出控制均按厂商和场景验证

API 面试
Module 3.1 · API 基础：OpenAI 以 Responses 为主线，保留 Chat Completions 兼容基础；Anthropic 使用原生 SDK 与显式 adapter；Google 原生接入保留为后续选做，当前不声称已实现。对照工具调用关联、流式事件、状态与 usage，不把更换 base_url 当作能力等价。在线集成与离线 fixture 证据分别记录。

Module 3.2 · 核心能力（Agent 必备）：
· Function Calling — 工具定义、模型调用工具流程、多工具选择
· Structured Output — Structured Outputs 的 Schema 约束不同于旧 JSON mode；按支持的模型/接口验证拒答、截断和解析失败，Schema 合规不等于事实、授权或业务正确
· 多模态 API — 图片理解（Vision）、音频转录（Whisper）

Module 3.3 · 工程实践与边界：
· Context Window 管理 — 按完整工具交互组重组上下文，计入工具定义、多模态与输出预留；压缩后重新计数，仍超限则降级或退出
· 错误处理与重试策略 — 速率限制（429）、指数退避 + 抖动（full jitter，防重试风暴）、重试预算、幂等键与业务去重（需执行端支持并验证，不能靠加请求头获得保证）
· 模型路由与 Fallback — 主备模型策略、AI Gateway 模式（LiteLLM）
· LLM 可观测性基础 — 调用日志、Token 用量追踪、成本告警；OpenTelemetry GenAI 语义约定（gen_ai.* span，厂商无关标准）+ Langfuse

Module 3.4 · 工具工程与 Function Calling（v7 新增 · P0 实战必修）：
· Tool Schema 设计 — 用 Pydantic / JSON Schema 定义工具、strict mode、参数描述如何影响模型选择
· 完整 Function Calling 循环 — 模型请求工具 → 执行 → 回填结果 → 再推理，多轮 / 并行调用
· 健壮性 — 参数校验失败如何反馈给模型重试、流式响应中增量解析工具调用、工具定义占多少 Token
· 工具注册系统 — 用装饰器做 Tool Registry（衔接 Phase 1）；展示子集不等于执行授权，dispatch 前单独检查允许集合并做运行时参数校验
· 小型 Agent eval（前移至最小工具循环的验收目标）：区分 task / trial / trace / outcome；用小型任务集重复试验，优先检查环境最终状态，保留轨迹诊断，不把固定工具顺序当唯一正确答案

Module 3.5 · 负载驱动的成本工程：先测成功率、每个成功任务的总成本、延迟，再选择前缀缓存、Batch、effort、模型路由或压缩，不背固定优先级。缓存写价、TTL、最小长度与命中边界按模型/API 版本核实；语义缓存另验收用户/租户隔离、数据时效和不可缓存的副作用动作，不承诺降幅。

Prompt Context
规划 · 验收目标
Prompt Engineering：System Prompt、Few-shot、输出契约、模板复用、版本管理与 A/B 测试。理解 CoT 概念，但不要求所有模型“逐步思考”；推理模型优先明确目标/约束，提示策略以任务评测为准。

Context Engineering 基础：管理推理时的全部输入，包括提示、历史、工具和检索证据；理解长上下文的注意力预算与召回退化风险，按任务选择信息，不把“越多越好”当原则。

Skills 小单元：SKILL.md、元数据匹配与渐进披露；流程知识与工具/MCP 操作接口分离，匹配不等于授权，不增加正式课号。Phase 6 再接入实际工具。

验收目标：为贯穿项目建立可版本化的提示/上下文管线和一个可复用业务 Skill，验证应触发与不应触发的输入，记录质量和上下文开销。
Agent Harness
规划 · 验收目标
先选执行方式：普通函数 → 确定性 workflow → 单 Agent，只有动态决策的收益超过成本才增加自主性。Agent Loop 设置最大轮次、预算和退出条件。

Agent Harness：从期望行为反推工具调度、完成标准、上下文预算、执行授权和错误恢复；故障先补回归用例，再决定是否加规则，允许经验证后删改规则。

Context Engineering 进阶：按完整交互组压缩并复算预算；外置有来源的结构化笔记，按需检索和渐进披露。子代理隔离上下文仅作对照，不作为默认架构。

工具设计：Schema、运行时校验、执行权限、错误反馈与测试；先用小工具集建立选择质量/延迟/上下文基线，工具搜索与程序化聚合留作有瓶颈时的进阶。

记忆生命周期：区分短期、工作与长期记忆；每次写入保留依据、来源和时间，支持用户纠正、过期、删除与租户隔离，评测检索质量，不把推测写成永久事实。

持久执行与审批（前移）：数据库检查点 → 暂停审批 → 退出进程 → 重启并恢复同一任务；说明节点可能重放，外部副作用须幂等，检查点不等于 exactly-once。

验收目标：在贯穿项目中手写最小单 Agent Harness，比较函数/workflow 基线；用离线任务验证预算退出、记忆纠正隔离、审批重启及重复执行不重复产生业务副作用。
框架 MCP
规划 · 验收目标
一个框架贯穿深学：为持久图编排目标，主线采用 LangGraph，先学最小状态与工具循环，Phase 10 再深化；Pydantic AI / OpenAI Agents SDK 仅对照类型、事件与授权接缝，不要求再做完整项目。框架选择按任务与证据，不做通用排名。

MCP 基础：Host / Client / Server、Tool / Resource / Prompt 与 stdio / Streamable HTTP。固定规范基线 2026-07-28，另锁定实际验证过的 SDK 版本；新版没有 initialize 握手、协议 session 或 GET 通知流，仍支持 SSE 响应。详见版本化协议与迁移检查表。

授权与 Skills 接入：HTTP 授权是可选能力，采用时按该规范实现发现、PKCE、resource/audience、issuer 与最小 scope；stdio 从环境获取凭证。工具可发现不代表允许执行，Skill 匹配也不授权。

验收目标：将 Phase 5 同一个项目迁入主线框架，复验数据库检查点、审批后进程重启、幂等；MCP 覆盖发现、调用、版本不兼容、JSON/SSE 响应和权限拒绝。Tasks 是官方可选扩展，不是核心必修或恢复机制的替代。
数据 RAG
规划 · 验收目标
数据基础：PostgreSQL / SQLAlchemy、PDF/HTML/Markdown 解析、清洗与分块；Embedding、向量索引和混合检索选一种后端实作，其他仅比较需求与运维取舍。

企业 RAG 先做可靠性：文档/片段携带权限、来源定位与版本；检索阶段执行用户/租户访问控制，引用能回到具体证据；更新和删除须传播至索引、缓存与相关派生数据。检索内容是不可信输入，不得覆盖系统规则或直接授权工具。

分层评测：检索层测权限过滤、召回和证据覆盖；生成层测引用定位、忠实度、答案正确性与无证据时的拒答。确定性检查优先，RAGAS / Judge 仅作经校准的补充。

需求驱动选修：混合检索与 Reranking 建立基线后，再按失败案例选择 HyDE、Agentic RAG 或 GraphRAG，不把更复杂的检索视为默认升级。

验收目标：给贯穿项目加入证据问答；两名权限不同的用户问同一问题时不得检索越权文档，能追溯证据，修订/删除后不再返回旧内容，分别报告检索与生成错误。
工程 生产级
规划 · 验收目标
可观测性（Observability）：选一种追踪工具接入，保留结构化日志、脱敏与告警；按固定版本验证 OpenTelemetry GenAI 语义约定，不把遥测平台数量当学习目标。

评估体系（深化 Phase 3 小型 eval）：区分任务、重复试验、轨迹和最终结果；优先确定性检查环境最终状态，再用与人工标注校准的 Judge 补充。隔离开发/验收集，比较成功率、成功任务成本、延迟与过度代理；工具选择一种实作，公开基准只作外部对照，不替代业务任务集。

高级
规划 · 按需进阶
推理控制：按具体模型/API 核实 thinking / effort 能力和限制，以任务质量、延迟与成本决定推理投入，不依赖固定思维链模板。

大工具集进阶：工具搜索、按需加载、在受限代码执行环境中聚合中间结果。与小工具集基线比较选择质量、上下文量与延迟；程序化调用仍须执行授权、参数校验和资源预算，不照抄旧文章的 beta/API 字段。

框架 协议
规划 · 验收目标
沿主线深化编排：在 Phase 6 的 LangGraph 项目中深化状态、分支、持久化和故障恢复；CrewAI 仅作角色/流程对照。Microsoft Agent Framework 是 Semantic Kernel 与 AutoGen 的共同后继，按语言与版本核实支持状态，不另开一套必修框架项目。

MCP 深化：固定规范与 SDK 版本开发 Server，单独实现业务权限、参数白名单与审计；按采纳的 HTTP 授权规范测试缺令牌、错误 audience/issuer、scope 不足。Tasks 属官方可选扩展，先核实客户端/服务端支持再采用。

多 Agent 决策：默认保留单 Agent；需要边界清晰的委托时才尝试 Orchestrator-Worker 等模式，比较交接丢失、成功率、总成本与端到端延迟。A2A 仅在远程 Agent 互操作需求下学习，不因本地并行就强行引入协议。

源码对照（选一）：从 OpenClaw、Hermes Agent 或 OpenHands 中固定一个源码版本，分析其状态/权限/恢复边界，不以热度证明架构适用性。

验收目标：为贯穿项目产出函数/workflow、单 Agent、多 Agent 的同任务对照；只有收益超过复杂度与交接成本才保留多 Agent，未采用也须能解释证据。

规划 · 验收目标

生产安全加固：越狱攻击检测、间接注入防御、过度代理限制、合规性、审计日志

Agent 迭代方法论（2026 核心循环）：
· 评估驱动开发 — 先定义"好"的标准，再优化 Agent
· 证据驱动迭代 — 故障转成回归用例；规则记录来源、适用范围与复核条件，经回归验证后可新增、纠正、合并或删除
· A/B 测试、数据飞轮、生产事故响应

验收目标：将贯穿项目部署到受控测试环境，演练进程/依赖故障、审批恢复、重复执行、权限拒绝与回滚；满足环境门槛后再决定生产上线，记录一轮评估驱动改进。
