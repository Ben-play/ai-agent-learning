回滚必须接住已存在的审批

换回旧进程，不换回旧数据；先核实已提交的事实，再决定是否返回结果。

为什么这课重要？

灰度停发时，已经受理的任务还在。发布前与灰度期间各留下一张已批准、一张已拒绝但尚未执行的草稿；另有一张还没人评审，一张已提交却没收到回执。恢复发布前的备份会丢掉灰度期间已经落库的事实。

上一课的纯信号样本演示判停规则，但不证明实际交接。本课让仍在运行的 v2 提交草稿、故意丢掉结果；用同一条响应触发本地停发，再验证旧程序能否接手当前两库。

学习目标

  • 按 v1 → v2 → v1 实际更换进程，继续使用同一对业务与审批 SQLite 文件。
  • 按原绑定处理发布前及灰度期间的待审批，区分未批、批准和拒绝。
  • 拿独立查到的原回执对比重放；撤权、坏回执和未知 schema 都不能靠重试解决。

1. 接手前先核对状态和写入者

  1. 停止灰度并交接写入：控制端收到 reply_lost 时不知道是否提交。它把 uncertain_outcome 交给 canary.decide()，判为 STOP_AND_ROLLBACK，不再向该 PID 分发。关管道并等待正常退出，通过预检才在同目录启动 v1。线上还要停分流、处置在途请求；本地不验证切流与并发。
  2. 保留已提交事实：两个版本都认 business.sqlite 和 review.sqlite 的 PRAGMA user_version=1。v2 只增加非必需的 candidate_meta 表，v1 不依赖也不删除它。应用版本号不是状态版本号；版本相同也不替代兼容测试。
  3. 沿用原决定：审批绑定暂存时的租户、主体、任务、动作、修订、摘要。可信评审夹具为 support/mei 落库批准或拒绝；记录决定不等于执行草稿，检查点仍是 pending。v1 不再评审，只按原绑定恢复；批准仍须核对当前来源。
  4. 独立观察：触发丢回复前、v2 退出后和恢复结束后，用 audit() 独立读回所有主体的检查点、审批、保存行、撤权及附加记录，并实读两个 schema 版本。inserts 计草稿 INSERT 尝试，不计审批或检查点更新；read_calls 只计取证，不计 SQLite 查表。
同一份存储上，旧进程必须分清这四种结果
原绑定与事实恢复结果草稿 INSERT 尝试
没有匹配的决定pending，不返回稿件0
匹配批准，来源仍可读saved，返回原稿和回执1
匹配拒绝denied，无稿件、无回执0
已提交但丢回复，原回执与权限有效replayed，只返回已有回执和原稿0

决策卡：切回旧程序，还是停写对账？

可以切回：同一候选已停发并正常退出；预检读到两库均兼容，原绑定、审批和回执相符。不得接手：没有判停、退出失败、版本不匹配，或已保存标记与回执矛盾。保留当前状态，必要时交给值班与数据负责人对账。

用旧快照覆盖当前库

会抹去灰度期间接单和已提交的草稿；随后重试还可能重复产生效果。

保留当前持久记录，替换写入者

在已验证兼容时继续未完任务；对已提交动作核对原回执，不再插入。

代价：要保留可启动的旧构建、兼容状态与对账能力。确实不兼容时，隔离写流量，评估前向修复或另行验证迁移；撤销业务效果需要独立授权与补偿回执，不等同于应用回滚。

  1. 停候选并等待退出，记录当前保存行及两库版本；不从旧备份覆盖。
  2. 确认旧版能接手原绑定；对已提交项比较原回执和实际写入尝试。

诊断：启动被拒绝就不要接单；回执矛盾就停止该任务并对账，不以重试或补写消除警报。

Q 待审任务编号没变，旧程序却不认识当前库的版本。交接时先做什么？
任务编号相同不代表状态布局兼容。先保全当前库与审批证据，再评估修复或迁移，不改版本号强行开机。

2. 跟做：切回旧版，接住两批任务

以下命令和代码块都从可信仓库根目录运行，使用 Python 3.11+。跟做命令：python -B -X utf8 code/phase11-deployment/deployment-lab/rollback.py worked。也可将每个 Python 代码块另存为临时脚本，从仓库根运行 python -I -B -X utf8 文件名.py（不要加 -O）。子进程走本地管道，状态在自动清理的临时目录；不用安装依赖、启动服务或接触真实工单。

v1 为 pre-approve 和 pre-deny 暂存草稿并落库决定；v2 为 canary-approve、canary-deny 做同样的事，另留一条未决定的 sync。在 v2 调用 fixture_lost 之前，独立快照 pre_stop 应看到五条决定（含 lost 的批准）、六条待执行检查点、零条已保存草稿。判停后 v2 不再接单，退出后的预检才确认 lost 已保存。新 v1 沿用原决定恢复任务，并以同一绑定重放 lost 两次。

3. 独立变式：能开机，不代表能放行

运行 python -B -X utf8 code/phase11-deployment/deployment-lab/rollback.py transfer。五个案例分别从全新状态开始，不继承跟做的数据。先写出预期拒绝点，再查返回、实际写入尝试和所有主体的持久行。

错主体与跨租户窥读。
改原绑定的 actor，可信评审恢复仍得 rejected。同名的 operations/mei 不是同一主体：查询没有任务信息，且不能通过评审入口恢复。
旧修订批准。
任务、主题、原文与摘要完全相同，只把修订号从 1 升到 2。用第 1 稿批准绑定恢复得 rejected；用当前绑定仍为 pending，说明相同摘要也不能跨修订借用批准。
已提交后撤权。
先确认原响应可重放，再撤销当前同步来源权限。换回 v1 后不返回回执或稿件，原保存记录仍在；replay_withheld 不是撤销提交。
回执正文损坏。
只在所有写入者退出后的临时副本上改一条已保存回执的正文，不改检查点或审批。旧版返回 inconsistent，原始库不动，副本也不尝试补写。
未知 schema。
在另一份关闭后复制的临时库把业务文件的 PRAGMA user_version 改成 2。真实宿主在接单前拒绝启动，两个文件的摘要和行都不变。这是未知版本实验，不是 v2 真正迁移了业务结构，也不证明任意真实迁移可逆。

面试自查

Q1 灰度期间有了新待审单，值班想把库恢复到发布前备份。如何接手？

参考回答：先停分流和新写入、确认在途请求；验证旧版能读当前库后只换程序，不覆盖当前数据。

追问：旧版读不了时怎么办？

答题要点：停写保全审批和保存记录；评估前向修复或经过验证的迁移。

Q2 发布前批准了第 1 稿，灰度期间已经暂存第 2 稿。旧版能用历史批准保存吗？

参考回答：不能。决定绑定租户、主体、任务、动作、修订和摘要，第 2 稿须等待匹配审批。

追问：怎么证明旧批准没有被挪用？

答题要点：原批准还在，新检查点仍待审；零草稿 INSERT，全表无新增。

Q3 草稿提交成功却丢了回复。旧版重放时证据权限已撤销，如何答复？

参考回答：保留原行，不返回回执或草稿，也不再次写入。已提交不等于当前可披露。

追问：如果回执行正文还和检查点有矛盾呢？

答题要点：停下对账，不能用补写的回执掩盖矛盾。

Q4 旧版拒绝启动改成 schema 2 的离线副本，能据此签生产回滚单吗？

参考回答：不能。它只证明这个宿主对未知版本在接单前拒绝，并且本次未改文件。

追问：还需要什么证据？

答题要点：在获授权的测试环境用实际构建和状态演练在途请求、审批接续与回执对账。
