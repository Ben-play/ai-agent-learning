MCP 服务端的只读权限边界

授权和参数都过关，业务读才可以发生

为什么这课重要？

仍是客服 support/mei 的导出留存与同步时间工单。L90 关心委托任务归谁；这里关心一个固定只读工具能否读某项业务数据。即使工具可见且声明「只读」，读错主体的内容也已经是越界。沿用 L59 和 L75 的宿主边界，在真正读之前检查授权与参数。L90 与本课共享合成记录，但不互相调用；本节只有 Python 内存函数，不启动服务器或套接字、不接 SDK、不发真实令牌，也不实现 OAuth 或任何通用执行接口。

学习目标

  • 区分工具发现、请求的可信授权上下文、参数白名单和对象拥有者。
  • 用读入口的独立观察与最小审计，证明拒绝确实没有读业务内容。
  • 判断何时只需同步读取，何时值得验证双方对 MCP Tasks 扩展的支持。

1. 工具可见，不等于当前调用获准

Model Context Protocol（MCP）让宿主经客户端访问服务端提供的工具或上下文。按 MCP 2026-07-28 的 Tools，tools/list 用于发现、tools/call 用于调用；当前可见列表可以受请求授权影响，但不能替业务入口校验输入和权限。另固定 Python SDK 2.3.0 的 docs/protocol-versions.md，用于核对版本选择和发现差异，不作为本课依赖，不据此假定任一客户端已支持 Tasks。

上下文来自可信宿主，不来自工具参数。下表的 Context 是没有凭据含义的分类标签；这不是令牌结构，构造对象也不代表真实授权。issuer 回答「参考的是不是本课认可的宿主」，audience 回答「是否给这个读边界」，scopes 表示允许哪类动作，actor 对照允许读具体对象的主体。正式 HTTP 授权的受众验证见规范；课堂的相等判断、scope、owner 和参数枚举是业务策略示范，不能用来代替真实的凭据验证。

Q 当前主体和 scope 均正确，但上下文受众是另一个读边界。应该怎么做？
主体、动作许可和目标边界是独立的检查。不能用正确的 scope 替代受众匹配，也不能自行重写来放行。

2. 读之前拒绝，用另一条观测线证明

本地先查缺失和上下文类型，再查签发方、受众与 scope；然后检查参数白名单，以固定拥有者元数据核对主体，最后才调用 ReadObserver.read 读取正文。每次调用使用当下宿主上下文，不沿用之前的许可。观察器在实际读方法的入口独立记一次主题，而不是从边界的 Reply 或审计倒推。元数据查询不算业务正文读取；「零读」在本实验只指未进入这个固定业务读入口。观察器仅为测试保留主题，不是审计日志的一部分。

Tasks 扩展不增加业务能力

MCP Tasks 让已支持的长操作可以返回任务句柄，再查状态或请求取消。只有客户端在请求里声明支持、服务端也宣布支持，且本来已授权的操作确实需要异步时，才考虑采用。扩展只改变受支持操作的交互方式，不提供新的服务端执行原语：任务句柄不是授权，不能放宽 scope、对象或参数边界，取消也不是撤销。一个固定快速读照旧同步；未协商支持就不要返回任务形状。课堂不实现 Tasks，也不模拟真实授权流。

决策卡：让权限判定发生在业务读之前

适用：多个宿主确实要以一致接口使用受保护工具。不适用：一个宿主只需查两条本地规则，保留类型明确的直接函数。

误判：先读导出规则再决定显示

读到正文才检查受众、scope 或拥有者，虽然返回拒绝，业务读已经发生。

选择：先验上下文和参数

同一导出请求错受众时零读；上下文及参数都正确才读一次，并返回准确来源。

  1. 逐项替换上下文或参数，证明读次数没增加。
  2. 保留同一数据正控，核对一次实际读、完整证据和最小审计；再用撤权复访判断是否误用旧许可。

代价：多一层策略、审计约定与版本验收；只有复用和隔离收益明确才引入协议，只有确有长操作且双方支持才加 Tasks。

Q 固定读工具很快，客户端没有声明 Tasks 扩展。调用通过权限校验后如何返回？
快速读没有异步收益；不支持扩展的客户端不能被要求处理任务结果，扩展也不改变现行授权。

面试自查

先判断是否该读，再说如何证明业务边界没被越过。

Q1 导出工具已列出来，客服本次请求受众却不匹配。可以沿用上次许可吗？

参考回答：不可以。发现和历史许可不替代当前请求授权，受众错就拒绝且零读。

追问：受众正确、签发方错误呢？

答题要点：同样不读；受众与签发方应有独立的负控和内部原因。

Q2 日志报「已拒绝」，测试应该算通过吗？

参考回答：不能只看日志；同一次调用要返回无正文，并让业务读入口的观察增量为零。

追问：正控一次后撤权，观察器已经记过一笔，怎么判？

答题要点：对照撤权前后累计数；只能保留正控的一笔，撤权返回仍无正文。

Q3 客服有 policy:read，工具参数又是白名单中的 sync，为什么还要验 owner？

参考回答：scope 允许动作类别，owner 决定这份记录。两者不等价，也不能从参数取身份。

追问：遇到频繁的 owner 拒绝，要把对象内容放进审计吗？

答题要点：不要。先用最小原因诊断；若生产确需关联，应另审最小字段及访问、留存策略。

Q4 客服只读工具偶尔等待人工确认，团队想改用 Tasks。先核对什么？

参考回答：先判断是否真有长等待或断线恢复需要，再验证双方扩展支持、授权和生命周期；扩展只管理原操作。

追问：服务端支持，客户端却未声明呢？

答题要点：不返回任务句柄；保留同步合同或在既有边界内交给人工，不新增执行入口。

小结与一手参考

先检查可信上下文、参数和资源归属，再允许固定读；用读入口观察证明拒绝没有发生正文读取。审计只留诊断所需信息；异步不是扩大权限的理由。

  • MCP 2026-07-28与该版本的 Authorization：区分规范受众要求与课堂业务检查。
  • MCP Python SDK v2.3.0 · Protocol Versions：只作版本文档，不执行 SDK。
  • MCP Tasks 扩展：核对双方协商、句柄和原操作结果。
