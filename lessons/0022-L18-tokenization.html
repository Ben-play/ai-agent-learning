Token 与 Tokenization 深入

模型眼里没有"字"，只有 Token——而 Token 直接等于钱

💡 为什么这课重要？

上一课说 LLM 在"预测下一个 Token"。那 Token 到底是什么？它不是字、不是词、也不完全是字母。搞不清这点，你会在三个地方栽跟头：算错成本、爆掉上下文窗口、误判中英文谁更省钱。

这一课我们用真实的 tiktoken 计数（不是拍脑袋），拆开"Token"这个黑箱，并当场推翻一个流传很广的错误说法——"中文一定比英文费 Token"。学完你能在发请求前就estimate成本、看懂账单。这是所有 Token 经济学（L23）的地基。

学习目标

完成本课后，你将能够：

  • 说清 Token 是子词单元（subword），不是字/词/字母
  • 用直觉解释 BPE（字节对编码）怎么把文本切成 Token
  • 区分 tiktoken 的 OpenAI 编码计数与 Claude 官方 count_tokens 估算
  • 解释"中文更费 Token"取决于分词器，并用数据证明
  • 把 Token 数换算成 API 成本，做预算估算

1. Token 不是字，是"子词"

LLM 不直接读字符，而是先把文本切成 Token——介于"字母"和"单词"之间的子词片段。常见规律（英文）：一个常用词往往是 1 个 Token，生僻词/长词会被拆成几个。

用 OpenAI 的 cl100k_base 分词器实测：

"languages" → 1 个 token: ['languages']
"learning"  → 1 个 token: ['learning']
"语言"       → 2 个 token: ['语', '言']
"学习"       → 3 个 token: ['学', '�', '�']   ← 注意这里！

看到没：英文常用词整个是 1 个 Token；而中文的"学习"被切成了 3 个片段，其中两个还是乱码似的 �——那是字节碎片（下一节解释）。这说明 Token 边界和人类的"字词"直觉完全不一样。经验法则："英文约 4 字符≈1 token、约 0.75 词≈1 token"，但这只是启发式，不是保证（见 The Prompt Index: LLM Tokens 2026）。

Q LLM 里的一个 Token 最准确的描述是？
Token 是子词单元（subword）：常用词可能是 1 个 Token，长词/生僻词/非拉丁文字会被拆成多个片段（甚至字节碎片）。它既不等于单词，也不等于字符——这就是为什么必须用分词器实际计数，不能靠数字数。

2. BPE：Token 是怎么被"合并"出来的

BPE（Byte Pair Encoding，字节对编码）是现代 LLM 常见的分词家族之一；不同厂商会使用不同 tokenizer、词表和训练算法，不能把下面这套合并过程当成所有模型的唯一实现。BPE 的基础思路出奇简单（原是 1994 年的数据压缩算法）：

  1. 从最小单位（字节 / 字符）开始；
  2. 统计语料里相邻出现最频繁的一对，把它合并成一个新符号；
  3. 重复几万次，高频组合（如 ing、tion、常用词）就变成了单个 Token。

切新文本时，BPE 按当初学到的合并规则、同样的顺序"回放"一遍，把文本拼成 Token（出处：Byte Pair Encoding in LLMs）。

关键：byte-level BPE。为保证任何字符都能编码，现代分词器从 256 个字节起步，而不是从字符起步。英文字母本身就是单字节、且高频，所以早早被合并成整词；而一个常用汉字是 3 个 UTF-8 字节（少数生僻字为 4 字节），如果这个字在训练语料里不够高频、没被完整合并，就会回退（byte fallback）成多个字节 Token——这就是上一节 "学习"→['学','�','�'] 里那两个 � 的来历（参考 The Pitfalls of Chinese Tokenization）。

一句话记住 BPE：从字节开始，反复把"最常一起出现的一对"合并成新 Token。语料里越高频的组合，越可能是一个完整 Token；越罕见，越会被拆碎。

3. 计数工具要和模型匹配：tiktoken vs Claude count_tokens

猜 Token 数会算错成本，但计数工具必须和目标模型匹配。tiktoken 是 OpenAI 官方分词器，能在本地、发请求前对匹配的 OpenAI 编码精确计数；拿它估算 Claude / Gemini 只能得到近似值：

pip install tiktoken   # 或 uv pip install tiktoken

import tiktoken

# 按编码名取（cl100k_base=GPT-4 系；o200k_base=GPT-4o/较新系）
enc = tiktoken.get_encoding("o200k_base")

text = "我喜欢学习语言。"
tokens = enc.encode(text)
print(len(tokens))          # → 5
print(tokens)               # 底层是一串整数 id
print([enc.decode([t]) for t in tokens])  # 还原每个 token 的样子

# 也可以按模型名自动选编码：
# enc = tiktoken.encoding_for_model("gpt-4o")

OpenAI 示例见 OpenAI Cookbook: How to count tokens with tiktoken。对 Claude，应把同一份请求结构交给官方计数端点：

import anthropic

client = anthropic.Anthropic()
count = client.messages.count_tokens(
    model="claude-opus-4-8",
    system="你是一个简洁的助手。",
    messages=[{"role": "user", "content": "解释什么是 Token。"}],
)
print(count.input_tokens)

怎么区分：tiktoken 是本地 OpenAI tokenizer；messages.count_tokens 会按你指定的 Claude 模型和完整消息结构估算输入 Token。官方也提醒计数结果仍可能与真正创建消息时的计费量有小幅差异，因此请求前用它做预算，调用后再以 response.usage 对账。不要拿一个厂商的 tokenizer 冒充所有模型的精确账单。

Q 关于用 tiktoken 计数，正确的说法是？
tiktoken 能在本地、发请求前计算 Token，但只有目标模型使用匹配的 OpenAI 编码时才是精确计数；对 Claude / Gemini 只能近似。Claude 应使用官方 messages.count_tokens 估算完整请求，调用后再看 response.usage 对账。

4. "中文更费 Token"？——取决于分词器（用数据说话）

你可能听过"中文比英文费 Token、所以更贵"。这个说法过时且不准确——它严重取决于用哪个分词器。同一句中文，我用两个编码实测：

文本字符数cl100k_base
(GPT-4)		o200k_base
(GPT-4o/较新)
EN: "I love learning languages."2655
中: "我喜欢学习语言。"8115
中: "人工智能正在改变世界。"11126

看这组对比的冲击力：同一句"我喜欢学习语言。"在旧的 cl100k 分词器下要 11 个 Token，换到 o200k（GPT-4o 系）只要 5 个——和那句英文一样多！"中文贵一倍"的说法，主要是旧分词器的产物；新分词器扩充了中文词表、把常见中文组合合并成了单个 Token，差距被大幅抹平。

一项 2026 年的初步研究（arXiv 2604.14210 · Chinese Language Is Not More Efficient Than English in Vibe Coding）也观察到：中文的 Token 成本比会随模型变化，并不存在“换成中文就稳定更省”的通用结论。它研究的是特定编程任务和模型，不能外推成所有语言/模型的定律。正确姿势：别记“中文一定贵/便宜”，用目标模型自己的计数工具实测。

⚠️ 面试高频陷阱："为什么中文消耗更多 Token？" 满分回答不是"因为中文复杂"，而是："取决于分词器——旧的如 cl100k 对中文按字节回退、切得碎；新的如 o200k 扩了中文词表、差距已很小。Token 效率是词表设计问题，不是语言问题。"

5. Token = 钱：成本换算

API 按 Token 收费，且输入和输出分开定价，输出通常是输入的 3~5 倍（Redis: LLM Token Optimization）。基本公式：

成本 = (输入Token数 × 输入单价 + 输出Token数 × 输出单价) / 1,000,000

例：一句 5-token 的中文输入，假设输入价 $3 / 百万 token：
    5 × 3 / 1,000,000 = $0.000015
（单次微不足道，但 Agent 一次任务可能调几十次 LLM、
  每次带上长 system prompt + 历史，累积起来就是真金白银）

三个"钱包警报"：

  • 上下文会累加：多轮对话里，历史每轮都作为输入重发，Token 随轮数线性增长。
  • system prompt 每次都算钱：你那段很长的角色设定，每次请求都计入输入 Token。
  • 爆窗口 = 报错或截断：超过模型上下文窗口上限，请求会失败或丢信息。

怎么系统性降本（Prompt Caching、Model Routing、压缩历史）是 L23 · Token 经济学的主题。这一课你只需会数、会换算。

Q 关于 API 的输入与输出 Token 定价，通常是？
主流 API 输出 Token 通常是输入的 3~5 倍价（生成比读取更耗算力）。所以省钱既要压输入（长 system prompt、累积历史用缓存/压缩），也要控输出（别让模型啰嗦）。算成本时务必输入、输出分开算。

6. 实战：该用哪一种计数方式

🧪 Agent 成本预估练习：OpenAI 与 Claude 请求分别怎么数（先自己判断）

场景：同一段 system prompt 将分别发给一个使用 o200k_base 的 OpenAI 模型和 Claude Opus 4.8。你要在请求前估算输入，并在请求后核对账单。

参考答案：

  • OpenAI 模型：请求前可用匹配编码的 tiktoken 本地计数；完整聊天请求仍需考虑角色、工具等格式开销，调用后查看该厂商 usage。
  • Claude：不要把 o200k 数字当精确值。用 client.messages.count_tokens(model="claude-opus-4-8", ...) 估算完整结构；请求完成后以 response.usage.input_tokens / output_tokens 等字段核对实际用量。
  • 跨厂商横向比较：先使用各自官方计数方式，再乘各自输入/输出单价。用同一个 tokenizer 数所有模型只能做粗略代理，不能冒充账单。
