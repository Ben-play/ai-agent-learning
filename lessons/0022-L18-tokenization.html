Token 与 Tokenization 深入

模型眼里没有"字"，只有 Token——而 Token 直接等于钱

💡 为什么这课重要？

上一课说 LLM 在"预测下一个 Token"。那 Token 到底是什么？它不是字、不是词、也不完全是字母。搞不清这点，你会在三个地方栽跟头：算错成本、爆掉上下文窗口、误判中英文谁更省钱。

这一课我们用真实的 tiktoken 计数（不是拍脑袋），拆开"Token"这个黑箱，并当场推翻一个流传很广的错误说法——"中文一定比英文费 Token"。学完你能在发请求前就estimate成本、看懂账单。这是所有 Token 经济学（L23）的地基。

学习目标

完成本课后，你将能够：

  • 说清 Token 是子词单元（subword），不是字/词/字母
  • 用直觉解释 BPE（字节对编码）怎么把文本切成 Token
  • 区分 tiktoken 的 OpenAI 编码计数与 Claude 官方 count_tokens 估算
  • 解释"中文更费 Token"取决于分词器，并用数据证明
  • 把 Token 数换算成 API 成本，做预算估算

1. Token 不是字，是"子词"

LLM 不直接读字符，而是先把文本切成 Token——介于"字母"和"单词"之间的子词片段。常见规律（英文）：一个常用词往往是 1 个 Token，生僻词/长词会被拆成几个。

用 OpenAI 的 cl100k_base 分词器实测：

"languages" → 1 个 token: ['languages']
"learning"  → 1 个 token: ['learning']
"语言"       → 2 个 token: ['语', '言']
"学习"       → 3 个 token: ['学', '�', '�']   ← 注意这里！

看到没：英文常用词整个是 1 个 Token；而中文的"学习"被切成了 3 个片段，其中两个还是乱码似的 �——那是字节碎片（下一节解释）。这说明 Token 边界和人类的"字词"直觉完全不一样。经验法则："英文约 4 字符≈1 token、约 0.75 词≈1 token"，但这只是启发式，不是保证（见 The Prompt Index: LLM Tokens 2026）。

Q LLM 里的一个 Token 最准确的描述是？
Token 是子词单元（subword）：常用词可能是 1 个 Token，长词/生僻词/非拉丁文字会被拆成多个片段（甚至字节碎片）。它既不等于单词，也不等于字符——这就是为什么必须用分词器实际计数，不能靠数字数。

2. BPE：Token 是怎么被"合并"出来的

BPE（Byte Pair Encoding，字节对编码）是现代 LLM 常见的分词家族之一；不同厂商会使用不同 tokenizer、词表和训练算法，不能把下面这套合并过程当成所有模型的唯一实现。BPE 的基础思路出奇简单（原是 1994 年的数据压缩算法）：

  1. 从最小单位（字节 / 字符）开始；
  2. 统计语料里相邻出现最频繁的一对，把它合并成一个新符号；
  3. 重复几万次，高频组合（如 ing、tion、常用词）就变成了单个 Token。

切新文本时，BPE 按当初学到的合并规则、同样的顺序"回放"一遍，把文本拼成 Token（出处：Byte Pair Encoding in LLMs）。

关键：byte-level BPE。为保证任何字符都能编码，现代分词器从 256 个字节起步，而不是从字符起步。英文字母本身就是单字节、且高频，所以早早被合并成整词；而一个常用汉字是 3 个 UTF-8 字节（少数生僻字为 4 字节），如果这个字在训练语料里不够高频、没被完整合并，就会回退（byte fallback）成多个字节 Token——这就是上一节 "学习"→['学','�','�'] 里那两个 � 的来历（参考 The Pitfalls of Chinese Tokenization）。

一句话记住 BPE：从字节开始，反复把"最常一起出现的一对"合并成新 Token。语料里越高频的组合，越可能是一个完整 Token；越罕见，越会被拆碎。

3. 计数工具要和模型匹配：tiktoken vs Claude count_tokens

猜 Token 数会算错成本，但计数工具必须和目标模型匹配。tiktoken 是 OpenAI 官方分词器，能在本地、发请求前对匹配的 OpenAI 编码精确计数；拿它估算 Claude / Gemini 只能得到近似值：

pip install tiktoken   # 或 uv pip install tiktoken

import tiktoken

# 按编码名取（cl100k_base=GPT-4 系；o200k_base=GPT-4o/较新系）
enc = tiktoken.get_encoding("o200k_base")

text = "我喜欢学习语言。"
tokens = enc.encode(text)
print(len(tokens))          # → 5
print(tokens)               # 底层是一串整数 id
print([enc.decode([t]) for t in tokens])  # 还原每个 token 的样子

# 也可以按模型名自动选编码：
# enc = tiktoken.encoding_for_model("gpt-4o")

OpenAI 示例见 OpenAI Cookbook: How to count tokens with tiktoken。对 Claude，应把同一份请求结构交给官方计数端点：

import anthropic

client = anthropic.Anthropic()
count = client.messages.count_tokens(
    model="claude-opus-4-8",
    system="你是一个简洁的助手。",
    messages=[{"role": "user", "content": "解释什么是 Token。"}],
)
print(count.input_tokens)

怎么区分：tiktoken 是本地 OpenAI tokenizer；messages.count_tokens 会按你指定的 Claude 模型和完整消息结构估算输入 Token。官方也提醒计数结果仍可能与真正创建消息时的计费量有小幅差异，因此请求前用它做预算，调用后再以 response.usage 作为该次调用的权威用量记录。若 provider 把缓存输入拆为独立字段，总输入应组装为 input_tokens + cache_creation_input_tokens + cache_read_input_tokens；不要只读 input_tokens，也不要拿一个厂商的 tokenizer 冒充所有模型的精确账单。

最佳实践：请求前用模型原生估算，请求后用 response usage 对账

适用：同一内容可能发往不同 provider / 模型，需要在发送前做上下文与成本门控，并在返回后记录真实用量。不适用：完全不经过模型的本地字符串处理。本卡只做一个决定：每个 adapter 使用自己的原生计数器估算，并在响应后用同一 provider 的 usage 完成 reconciliation。

❌ 一把跨厂商尺子当账单
estimated = generic_count(request)
ledger.record(provider, estimated)

同一任务、输入与 meter.measure() 接口，却忽略模型 tokenizer 和消息包装差异；预算与账单漂移没有被观测。

✅ adapter 估算 + usage 对账
estimated = adapter.estimate(request)
response = adapter.send(request)
actual = total_input_tokens(response["usage"])
meter.reconcile(estimated, actual)

请求前数字只用于门控；请求后从权威 usage 组装总输入并保存 estimate、actual 与 delta，同时记录 adapter / counter 身份及其收到的精确请求。

为什么更优：把计数放进 provider adapter，并把估算与 usage 成对落账，动作上绑定了目标模型和完整请求；机制上记录 adapter / counter 身份与精确计数输入，并在 provider 拆分缓存计数时用 input_tokens + cache_creation_input_tokens + cache_read_input_tokens 组装实际总输入；结果提高预算正确性、账单可审计性、路由可靠性和漂移可诊断性。真实成本是额外计数调用、计数端点速率限制、遥测存储以及 adapter 维护；estimate 还可能因系统优化与真正消息创建量有小幅差异。极低价值且绝不会接近窗口的流量可用经校准的本地近似；一旦用于拒绝请求、选模型或预测账单，就切换到模型原生估算并以 response usage 对账。不同原生 tokenizer 也可能碰巧得到相同数字，因此“数字不同”不是 adapter 归属的证明；调用身份和精确请求记录才是。Anthropic 官方明确说明 count_tokens 是估算，实际输入用量可能有小幅差异（Claude token counting）。

动手自检（纯标准库、离线、静默通过）：
def total_input_tokens(usage):
    return sum(
        usage.get(field, 0)
        for field in (
            "input_tokens",
            "cache_creation_input_tokens",
            "cache_read_input_tokens",
        )
    )


class FixtureAdapter:
    def __init__(self, name, counter_id, estimate, usage):
        self.name = name
        self.counter_id = counter_id
        self._estimate = estimate
        self._usage = usage
        self.counted_requests = []

    def estimate(self, request):
        self.counted_requests.append(request)
        return self._estimate

    def send(self, request):
        return {"usage": self._usage}


def measure(adapter, request):
    estimated = adapter.estimate(request)
    usage = adapter.send(request)["usage"]
    actual = total_input_tokens(usage)
    return {
        "provider": adapter.name,
        "counter_id": adapter.counter_id,
        "estimated": estimated,
        "actual": actual,
        "delta": actual - estimated,
    }


REQUEST = {"task": "subtitle", "text": "博物馆 closes at six."}
adapters = [
    FixtureAdapter(
        "fictional_a",
        "counter-a-v2",
        estimate=11,
        usage={"input_tokens": 12},
    ),
    FixtureAdapter(
        "fictional_b",
        "counter-b-v5",
        estimate=8,
        usage={
            "input_tokens": 3,
            "cache_creation_input_tokens": 2,
            "cache_read_input_tokens": 3,
        },
    ),
]
records = [measure(adapter, REQUEST) for adapter in adapters]

assert records == [
    {"provider": "fictional_a", "counter_id": "counter-a-v2", "estimated": 11, "actual": 12, "delta": 1},
    {"provider": "fictional_b", "counter_id": "counter-b-v5", "estimated": 8, "actual": 8, "delta": 0},
]
assert [adapter.counter_id for adapter in adapters] == ["counter-a-v2", "counter-b-v5"]
assert all(adapter.counted_requests == [REQUEST] for adapter in adapters)
assert total_input_tokens({"input_tokens": 6}) == 6
assert total_input_tokens({"input_tokens": 1, "cache_creation_input_tokens": 2, "cache_read_input_tokens": 3}) == 6

结果诊断：无输出且退出码为 0 即通过。counter identity 不符或记录的请求不是 REQUEST，说明计数没有归属到正确 adapter / 精确输入；缓存 fixture 的 actual 不是 6，说明漏加 cache creation / read；ledger 没有 actual / delta，表示只做预算没有对账；把 estimate 覆盖为 usage 会丢失漂移证据。两个 provider 计数相同本身不是错误，因为不同 tokenizer 可能碰巧返回相同数字。

边界：原生 token count 是模型请求的预算信号，不是文本“长度”的跨模型统一单位；response usage 才是该次调用的权威用量记录。对拆分缓存字段的 provider，总输入需由 usage 各输入分量组装。

Q 关于用 tiktoken 计数，正确的说法是？
tiktoken 能在本地、发请求前计算 Token，但只有目标模型使用匹配的 OpenAI 编码时才是精确计数；对 Claude / Gemini 只能近似。Claude 应使用官方 messages.count_tokens 估算完整请求，调用后再看 response.usage 对账。

4. "中文更费 Token"？——取决于分词器（用数据说话）

你可能听过"中文比英文费 Token、所以更贵"。这个说法过时且不准确——它严重取决于用哪个分词器。同一句中文，我用两个编码实测：

文本字符数cl100k_base
(GPT-4)		o200k_base
(GPT-4o/较新)
EN: "I love learning languages."2655
中: "我喜欢学习语言。"8115
中: "人工智能正在改变世界。"11126

看这组对比的冲击力：同一句"我喜欢学习语言。"在旧的 cl100k 分词器下要 11 个 Token，换到 o200k（GPT-4o 系）只要 5 个——和那句英文一样多！"中文贵一倍"的说法，主要是旧分词器的产物；新分词器扩充了中文词表、把常见中文组合合并成了单个 Token，差距被大幅抹平。

一项 2026 年的初步研究（arXiv 2604.14210 · Chinese Language Is Not More Efficient Than English in Vibe Coding）也观察到：中文的 Token 成本比会随模型变化，并不存在“换成中文就稳定更省”的通用结论。它研究的是特定编程任务和模型，不能外推成所有语言/模型的定律。正确姿势：别记“中文一定贵/便宜”，用目标模型自己的计数工具实测。

⚠️ 面试高频陷阱："为什么中文消耗更多 Token？" 满分回答不是"因为中文复杂"，而是："取决于分词器——旧的如 cl100k 对中文按字节回退、切得碎；新的如 o200k 扩了中文词表、差距已很小。Token 效率是词表设计问题，不是语言问题。"

5. Token = 钱：成本换算

API 按 Token 收费，且输入和输出分开定价；两者价差随厂商、模型、计费层级和日期变化（Redis: LLM Token Optimization）。基本公式：

成本 = (输入Token数 × 输入单价 + 输出Token数 × 输出单价) / 1,000,000

例：一句 5-token 的中文输入，假设输入价 $3 / 百万 token：
    5 × 3 / 1,000,000 = $0.000015
（单次微不足道，但 Agent 一次任务可能调几十次 LLM、
  每次带上长 system prompt + 历史，累积起来就是真金白银）

三个"钱包警报"：

  • 上下文会累加：多轮对话里，历史每轮都作为输入重发，Token 随轮数线性增长。
  • system prompt 每次都算钱：你那段很长的角色设定，每次请求都计入输入 Token。
  • 爆窗口 = 报错或截断：超过模型上下文窗口上限，请求会失败或丢信息。

怎么系统性降本（Prompt Caching、Model Routing、压缩历史）是 L23 · Token 经济学的主题。这一课你只需会数、会换算。

Q 关于 API 的输入与输出 Token 定价，通常是？
输入与输出使用不同单价，价差必须查目标模型当前价格，不能背固定倍数。所以省钱既要压输入（长 system prompt、累积历史用缓存/压缩），也要根据账单控制无用输出。算成本时务必输入、输出分开算。

6. 实战：该用哪一种计数方式

🧪 Agent 成本预估练习：OpenAI 与 Claude 请求分别怎么数（先自己判断）

场景：同一段 system prompt 将分别发给一个使用 o200k_base 的 OpenAI 模型和 Claude Opus 4.8。你要在请求前估算输入，并在请求后核对账单。

参考答案：

  • OpenAI 模型：请求前可用匹配编码的 tiktoken 本地计数；完整聊天请求仍需考虑角色、工具等格式开销，调用后查看该厂商 usage。
  • Claude：不要把 o200k 数字当精确值。用 client.messages.count_tokens(model="claude-opus-4-8", ...) 估算完整结构；请求完成后以 response.usage 为权威记录。若启用了 prompt caching，总输入要把 input_tokens、cache_creation_input_tokens 与 cache_read_input_tokens 相加；输出 Token 另行保留。
  • 跨厂商横向比较：先使用各自官方计数方式，再乘各自输入/输出单价。用同一个 tokenizer 数所有模型只能做粗略代理，不能冒充账单。

本课最佳实践验收：仓库导入规划器批量预约账本

先独立完成：为仓库导入规划器准备一批带 tool definition 的请求，并让两个虚构 provider 分别使用自己的原生 counter。必须先完成整批计数与预算预约，再发送获准成员；返回后把缓存与非缓存 usage 对账到 provider 账本。

操作清单

  1. 构造收货、库存和退货三项仓库导入请求，每项都携带可审计的 tool definition。
  2. 为两个 provider 注入不同的原生 counter / model 身份，并记录 counter 收到的最终请求。
  3. 在任何 send 发生前完成整批 estimate 与累计预算预约；剩余预算不足的成员标记为拒绝。
  4. 只发送已预约成员，分别用含缓存和不含缓存的 response usage 计算 actual 与 delta。
  5. 按 provider 形成账本，证明相同 estimate 可以来自不同 counter，且 request digest、counter ID、发送次数都可追查。
通过标准
  • 两个 batch plan 完成时发送记录仍为空；第三个成员虽单项小于总预算，也因累计余额不足而未发送。
  • 每个 counter 依次收到该 provider 的三份完整请求；plan 与 ledger 都保留 counter ID 和稳定 request digest。
  • 两个 provider 对首项都估算为 12 不会被当成身份冲突；身份由 counter 与精确请求证明。
  • 已发送项满足 actual = input + cache creation + cache read 与 delta = actual - estimated；拒绝项不进入账本。
  • 程序离线、纯标准库、确定性运行；标准输出只有最终标记。

import hashlib
import json


def stable_digest(request):
    payload = json.dumps(
        request,
        ensure_ascii=False,
        sort_keys=True,
        separators=(",", ":"),
    ).encode("utf-8")
    return hashlib.sha256(payload).hexdigest()


def total_input_tokens(usage):
    return sum(
        usage.get(field, 0)
        for field in (
            "input_tokens",
            "cache_creation_input_tokens",
            "cache_read_input_tokens",
        )
    )


def tool_definition(name):
    return {
        "name": name,
        "description": "Plan one warehouse import without executing it.",
        "input_schema": {
            "type": "object",
            "properties": {
                "source_uri": {"type": "string"},
                "target_table": {"type": "string"},
                "mode": {"type": "string"},
            },
            "required": ["source_uri", "target_table", "mode"],
        },
    }


def build_requests(model):
    jobs = [
        ("receipts", "receipts.csv", "plan_receipts_import"),
        ("inventory", "inventory.json", "plan_inventory_import"),
        ("returns", "returns.ndjson", "plan_returns_import"),
    ]
    return [
        {
            "request_id": request_id,
            "model": model,
            "messages": [
                {
                    "role": "user",
                    "content": f"Plan the import for {source}; do not execute it.",
                }
            ],
            "tools": [tool_definition(tool_name)],
        }
        for request_id, source, tool_name in jobs
    ]


class NativeWarehouseProvider:
    def __init__(self, name, model, counter_id, estimates, usages):
        self.name = name
        self.model = model
        self.counter_id = counter_id
        self.estimates = estimates
        self.usages = usages
        self.counted_requests = []
        self.sent_requests = []

    def count(self, request):
        self.counted_requests.append(request)
        return self.estimates[request["request_id"]]

    def send(self, request):
        self.sent_requests.append(request)
        return {"usage": self.usages[request["request_id"]]}


def reserve_batch(provider, requests, budget):
    estimates = [provider.count(request) for request in requests]
    remaining = budget
    plan = []
    for request, estimated in zip(requests, estimates):
        reserved = estimated <= remaining
        if reserved:
            remaining -= estimated
        plan.append(
            {
                "provider": provider.name,
                "counter_id": provider.counter_id,
                "request_id": request["request_id"],
                "request_digest": stable_digest(request),
                "estimated": estimated,
                "reserved": reserved,
                "request": request,
            }
        )
    return plan


def execute_reserved(provider, plan):
    ledger = []
    for reservation in plan:
        if not reservation["reserved"]:
            continue
        usage = provider.send(reservation["request"])["usage"]
        actual = total_input_tokens(usage)
        ledger.append(
            {
                "provider": provider.name,
                "counter_id": provider.counter_id,
                "request_id": reservation["request_id"],
                "request_digest": reservation["request_digest"],
                "estimated": reservation["estimated"],
                "actual": actual,
                "delta": actual - reservation["estimated"],
            }
        )
    return ledger

阶段实践检查点：请求契约

把 L17 能力映射与 L18 模型原生计数迁移到新的“活动通知”领域：同一通知任务先由 adapter 删除不支持控制，再用该 adapter 的原生估算做发送门控，并在返回后保留 usage 差值。

操作清单

  1. 为活动通知 provider 定义不同控制能力与专属计数器。
  2. 经同一 NotificationAdapter.prepare() 生成请求。
  3. 证明不支持字段不在 payload，counter 收到的正是投影后的最终 payload。
  4. 加入一个超预算项，在 send 前拒绝；对已发送请求用含缓存 / 不含缓存 usage 完成 reconciliation。
通过标准
  • 同一活动、同一 prompt、同一接口下公平比较。
  • 能力映射发生在计数之前；counter identity 与精确计数 payload 都可验证。
  • 未发送项没有 actual / delta 且不增加 send 次数；已发送项保留 estimate、总 actual 与 delta。
  • 标准输出只有检查点标记。

def total_input_tokens(usage):
    return sum(
        usage.get(field, 0)
        for field in (
            "input_tokens",
            "cache_creation_input_tokens",
            "cache_read_input_tokens",
        )
    )


class NotificationAdapter:
    def __init__(self, name, counter_id, capabilities, estimates, usages):
        self.name = name
        self.counter_id = counter_id
        self.capabilities = capabilities
        self.estimates = estimates
        self.usages = usages
        self.counted_payloads = []
        self.sent_payloads = []

    def prepare(self, *, event, prompt, controls):
        supported = {
            key: value
            for key, value in controls.items()
            if self.capabilities.get(key, False)
        }
        return {"event": event, "prompt": prompt, "controls": supported}

    def count(self, payload):
        self.counted_payloads.append(payload)
        return self.estimates[payload["event"]["id"]]

    def send(self, payload):
        self.sent_payloads.append(payload)
        return {"usage": self.usages[payload["event"]["id"]]}


def deliver(adapter, *, event, prompt, controls, limit):
    payload = adapter.prepare(event=event, prompt=prompt, controls=controls)
    estimated = adapter.count(payload)
    if estimated > limit:
        return {"provider": adapter.name, "counter_id": adapter.counter_id, "payload": payload, "estimated": estimated, "sent": False, "actual": None, "delta": None}
    usage = adapter.send(payload)["usage"]
    actual = total_input_tokens(usage)
    return {"provider": adapter.name, "counter_id": adapter.counter_id, "payload": payload, "estimated": estimated, "sent": True, "actual": actual, "delta": actual - estimated}

总结

  • Token 是子词片段，不是字/词/字母；必须用分词器实际数，不能靠数字数
  • BPE 是常见 tokenizer 家族；byte-level BPE 学习高频合并规则，中文可能回退成字节碎片
  • tiktoken 对匹配 OpenAI 编码本地计数；Claude 请求前用 messages.count_tokens，请求后以 response.usage 为权威记录，缓存输入分量需相加
  • "中文更费 Token"取决于分词器——同句中文 cl100k 要 11、o200k 只要 5
  • 成本 = 输入输出分开按目标模型当前单价计算；历史与 system prompt 会累加计费
