流程控制、字符串与 Prompt 构造

把"决策逻辑"和"字符串拼接"练成肌肉记忆 — 因为 Prompt 就是字符串，Agent 的每一步都是分支

💡 为什么这课重要？

Agent 的本质是一个循环里的决策机器：根据 LLM 的输出决定下一步走哪个分支（调用工具？结束？重试？），再把上下文拼成新的 Prompt 喂回去。这一课的两件事——流程控制（怎么做决策）和字符串构造（怎么拼 Prompt）——就是 Agent Loop 的骨架。

尤其是 Prompt：它说到底就是一个字符串。能不能优雅地做变量替换、条件拼接、上下文注入，直接决定你的 Agent 代码是清爽还是一团浆糊。这一课你会亲手写一个 Prompt 模板引擎。

学习目标

完成本课后，你将能够：

  • 熟练使用 if/elif/else 和 for/while 控制 Agent 的决策与循环
  • 用 match-case 优雅地分发 LLM 返回的不同动作（tool_call / text / end）
  • 掌握 f-string 高级用法：表达式、格式化、!r、= 调试、多行
  • 用常用字符串方法清洗和切分 LLM 文本
  • 设计可复用的 Prompt 模板：变量替换 + 条件拼接 + 上下文注入

1. 流程控制：Agent 的决策骨架

条件与循环你大概率写过，这里只挑 Agent 场景里最常见的写法过一遍。

if / elif / else — 根据 LLM 输出分支

finish_reason = "tool_calls"

if finish_reason == "tool_calls":
    action = "执行工具"
elif finish_reason == "stop":
    action = "返回最终答案"
elif finish_reason == "length":
    action = "输出达到生成上限，当前回答可能被截断"
else:
    action = "未知状态，记录日志"

注：finish_reason 及其取值是 OpenAI 风格的简化字段，不同厂商命名和取值都不一样。"length" 只表示输出达到了生成长度上限，不等同于"上下文超限"——上下文窗口超限通常在请求阶段就报错，或由框架提前裁剪，二者不要混为一谈。

for / while — Agent Loop 的两种循环

# for：遍历已知集合（比如多个工具调用）
for call in tool_calls:
    run_tool(call)

# while：Agent 主循环，直到完成或到达步数上限
step = 0
done = False
MAX_STEPS = 10
while not done and step < MAX_STEPS:   # ← 一定要有上限，否则可能无限循环
    response = llm(messages)
    done = response.finish_reason == "stop"
    step += 1

response.finish_reason 同样是 OpenAI 风格的简化字段；真实项目里字段名和取值因厂商而异，通常由 provider adapter 统一归一化后再交给 Agent Loop 处理。

最佳实践：Agent Loop 必须有安全边界

什么时候会遇到：模型持续请求下一步、迟迟不返回终态，或 adapter 交来循环不认识的动作，Agent 就可能不断消耗时间和预算。

本卡只做一个决定：循环只接收 provider adapter 归一化后的动作 {"type": "continue"} 或 {"type": "terminal", "output": ...}，并统一执行步数上限、显式终态和未知动作失败。这个二状态接口是本课为演示控制流而刻意缩小的契约；adapter 必须在进入循环前处理或明确表示重试、拒绝、暂停等更丰富的 provider 状态。若这些状态本身要驱动循环，应改用更丰富的动作协议或现成 harness，而不是强行压成两类；循环不直接读取任何厂商的原始字段。

❌ 无边界：正常任务能跑，异常输入会失控

✅ 有边界：显式处理每个出口
def run_agent(next_action, max_steps=3):
    if (
        isinstance(max_steps, bool)
        or not isinstance(max_steps, int)
        or max_steps <= 0
    ):
        raise ValueError("max_steps must be a positive integer")

    for step in range(1, max_steps + 1):
        action = next_action()
        match action:
            case {"type": "continue"}:
                continue
            case {"type": "terminal", "output": output}:
                return {
                    "status": "completed",
                    "output": output,
                    "steps": step,
                }
            case _:
                action_type = (
                    action.get("type")
                    if isinstance(action, dict)
                    else None
                )
                if not isinstance(action_type, str):
                    action_type = "<missing-or-non-string>"
                raise ValueError(
                    "unknown action: "
                    f"type={action_type!r}, "
                    f"python_type={type(action).__name__}"
                )
    return {
        "status": "max_steps",
        "output": None,
        "steps": max_steps,
    }

成功路径的输入和输出不变，只把终态、耗尽和未知动作变成可测试、可诊断的结果。

为什么更优：显式边界把不确定动作约束成有限状态迁移，使可用性、成本和故障定位都可控。代价是过低的 max_steps 会截断合法长任务，调用方还要处理耗尽状态；若任务天然需要跨进程长时间运行，替代方案是持久化任务队列与可恢复状态机，并为每次模型或工具调用单独设置超时。

动手自检（默认折叠；整块复制即可运行）：
def scripted_actions(*actions):
    """依次返回归一化动作；用完后重复最后一个。"""
    index = 0

    def next_action():
        nonlocal index
        action = actions[min(index, len(actions) - 1)]
        index += 1
        return action

    next_action.read_count = lambda: index
    return next_action

怎么看结果：代码静默结束即通过；返回值中的 status、steps 和 output 提供运行诊断。未知动作异常只报告归一化 type 与 Python 类型，不回显其他字段；非法 max_steps 会在读取动作前失败。

边界：max_steps 只限制循环轮数，无法中断一次永久卡住的外部调用，也不等于预算或墙钟超时；这些约束仍应由 adapter、SDK 配置或任务运行器负责。

break / continue / for-else

for call in tool_calls:
    if call["name"] == "forbidden_tool":
        break          # 命中禁用工具，立刻跳出
    if call["name"] == "noop":
        continue       # 跳过这一个，继续下一个
    run_tool(call)
else:
    # 循环正常结束（没被 break）才会执行
    print("所有工具调用完成")
Q 下面循环结束后，print 会执行吗？ 
for x in [1, 2, 3]:
    if x == 2:
        break
else:
    print("done")
for-else 的 else 只在循环正常结束（没有被 break）时执行。这里 x == 2 触发了 break，所以 else 不执行。这个特性常用于"找到就跳出、没找到才走 else"的搜索场景。

2. match-case：分发 LLM 的动作

match-case 是 Python 3.10+ 的结构化模式匹配。Agent 里特别适合分发 LLM 返回的不同动作类型，比一长串 if/elif 更清晰。

# LLM 返回的动作（简化）
action = {"type": "tool_call", "name": "search", "args": {"q": "python"}}

match action:
    case {"type": "tool_call", "name": name, "args": args}:
        result = run_tool(name, args)        # 解构出 name 和 args
    case {"type": "text", "content": content}:
        result = content
    case {"type": "end"}:
        result = None
    case _:                                   # 兜底，相当于 else
        raise ValueError(f"未知动作: {action}")

关键能力：match 可以一边匹配结构、一边把字段解构出来（上面的 name、args、content）。if/elif 也能先判断类型再手动取字段，只是要多写几行；match-case 的优势是把"结构匹配"和"变量绑定"合并写在同一个声明式分支里，更紧凑、更好扩展。

🔑 Agent 开发关联：

Agent Loop 的核心就是"拿到 LLM 输出 → 判断它想干什么 → 分发执行"。match-case 让这个分发逻辑既好读又好扩展，新增一种动作类型只要加一个 case。

Q match-case 中的 case _: 作用是什么？
_ 是通配模式，匹配任何前面没命中的情况，相当于 if/elif 里的 else。注意它不会绑定变量——只是"匹配但不关心值"。Agent 里常用它兜住未知的动作类型并报错。

3. f-string：拼 Prompt 的主力工具

Prompt 就是字符串，而 f-string 是 Python 拼字符串最好用的方式。Agent 开发里你会写无数个 f-string，把这些高级用法练熟。

基础：嵌入表达式

model = "claude-opus-4-8"
MAX_RESULTS = 10
n = 5
prompt = f"用模型 {model} 搜索，返回 {n} 条结果"
# 表达式也行（不只是变量）
prompt = f"还能再搜 {MAX_RESULTS - n} 条"

格式化：对齐、精度、千分位

cost = 0.0123456
print(f"成本：${cost:.4f}")        # 成本：$0.0123   （保留 4 位小数）

tokens = 1234567
print(f"用量：{tokens:,} tokens")   # 用量：1,234,567 tokens   （千分位）

name = "search"
print(f"{name:>10}")               # "    search"   （右对齐占 10 格）

调试神器：!r 和 =

text = "hi\n"

print(f"{text}")     # 直接展开，看不出有换行
print(f"{text!r}")   # 'hi\n'  ← !r 用 repr()，把转义字符显出来

# = 同时打印"变量名和值"，调试 Agent 状态超好用
step = 3
print(f"{step=}")    # step=3
🔑 Agent 开发关联：

调 LLM 时经常遇到"Prompt 里混进了看不见的换行/空格"导致行为异常。f"{prompt!r}" 能立刻看出隐藏字符；f"{var=}" 则是排查 Agent 状态的最快方式，不用写一堆 print("step:", step)。

多行 Prompt：三引号 + f-string

role = "搜索助手"
tools = "search, calculator"

system_prompt = f"""你是一个 {role}。

可用工具：{tools}
规则：
- 必要时才调用工具
- 用中文回答
"""
Q f"{name!r}" 里的 !r 表示什么？
!r 调用对象的 repr() 而不是 str()，会带引号并显示转义字符（如 \n、\t）。排查 Prompt 里的隐藏字符时极其有用。另两个转换：!s（str，默认）、!a（ascii）。

4. 字符串方法：清洗 LLM 文本

LLM 返回的文本经常需要清洗、切分、判断。这些方法是日常基本功：

raw = "  ```json\n{\"ok\": true}\n```  "

raw.strip()                 # 去掉首尾空白
raw.strip().removeprefix("```json").removesuffix("```")  # 去掉代码块包裹（3.9+）

text = "search, calc , weather"
[t.strip() for t in text.split(",")]   # ['search', 'calc', 'weather']  切分+去空格

"TOOL_CALL".lower()         # "tool_call"   归一化
", ".join(["a", "b", "c"])  # "a, b, c"   用分隔符把列表拼成一个字符串

resp = "Final Answer: 42"
"error" in resp.lower()     # 子串判断（先转小写更稳）
resp.startswith("Final")    # True
resp.split(":", 1)[1].strip()  # "42"   按第一个冒号切一刀
💡 面试常见问题：

"split(',') 和 split(',', 1) 有什么区别？"

答：第二个参数 maxsplit 限制最多切几次。split(":", 1) 只在第一个冒号处切一刀，得到两段——解析 "key: value: 含冒号的内容" 这种字符串时非常关键。

5. Prompt 构造模式（本课核心）

把前面的零件组合起来，就是 Agent 开发里最高频的活：动态构造 Prompt。三种基本模式：

下面的例子已经用到了 def 函数和参数——函数的定义方式、参数设计会在 L05 正式讲，这里先把它们当"现成容器"来看，只关注函数体里的分支、字符串和列表操作。

模式一：变量替换

def build_prompt(question, context):
    return f"""根据下面的资料回答问题。

资料：
{context}

问题：{question}
"""

模式二：条件拼接（按需加入片段）

关键技巧：把 Prompt 拆成完整片段，按条件 append，最后统一 join。工具、资料和严格模式各负责一个片段，避免在多个分支里手工维护空格与换行。下面的最佳实践卡把这个模式直接实现为 render_prompt()，并在同一代码块中做精确测试，不再另写一套近似示例。

模式三：上下文注入（拼对话历史）

history = [
    {"role": "user", "content": "北京天气？"},
    {"role": "assistant", "content": "晴，25°C"},
]

# 把结构化历史渲染成文本上下文
lines = [f"{m['role']}: {m['content']}" for m in history]
context = "\n".join(lines)
prompt = f"对话历史：\n{context}\n\n请继续。"

最佳实践：集中组装 Prompt 的可选片段

什么时候会遇到：Prompt 由工具、资料和规则等可选片段组成；改一个开关时，容易误改其他片段的顺序、空行或内容。

本卡只做一个决定：保持渲染契约不变，把条件片段集中到列表后统一 join。下面两种实现接收完全相同的参数，并为每组参数产生字节完全相同的字符串；差别只在代码结构和维护成本。

❌ 可运行，但边界散落在分支中
def render_prompt_weak(
    role, question, context="", tools=None, strict=False
):
    prompt = f"你是一个{role}。"
    if tools:
        prompt += "\n\n可用工具：" + ", ".join(tools)
    if context:
        prompt += f"\n\n参考资料：\n{context}"
    if strict:
        prompt += "\n\n只能基于资料回答，不要编造。"
    prompt += f"\n\n问题：{question}"
    return prompt

输出正确，但每个分支都要重复维护分隔符。

✅ 同一契约，片段边界集中管理
def render_prompt(
    role, question, context="", tools=None, strict=False
):
    parts = [f"你是一个{role}。"]
    if tools:
        parts.append("可用工具：" + ", ".join(tools))
    if context:
        parts.append(f"参考资料：\n{context}")
    if strict:
        parts.append("只能基于资料回答，不要编造。")
    parts.append(f"问题：{question}")
    return "\n\n".join(parts)

输出不变，每个开关只拥有一个完整片段。

为什么更优：集中组装完整片段并统一写一次分隔符后，新增或移动可选片段不必同步修改多处换行，更容易维持字节完全一致的格式契约，也更便于组合测试和维护。代价是多维护一个列表；若模板需要循环、继承、本地化或多种输出格式，可改用 Jinja 等模板引擎，但简单模板不必提前引入依赖。

组合矩阵自检（默认折叠；整块复制即可运行）：
def render_prompt_weak(
    role, question, context="", tools=None, strict=False

    if tools:
        prompt += "\n\n可用工具：" + ", ".join(tools)
    if context:
        prompt += f"\n\n参考资料：\n{context}"
    if strict:
        prompt += "\n\n只能基于资料回答，不要编造。"
    prompt += f"\n\n问题：{question}"
    return prompt


def render_prompt(
    role, question, context="", tools=None, strict=False
):
    parts = [f"你是一个{role}。"]
    if tools:
        parts.append("可用工具：" + ", ".join(tools))
    if context:
        parts.append(f"参考资料：\n{context}")
    if strict:
        parts.append("只能基于资料回答，不要编造。")
    parts.append(f"问题：{question}")
    return "\n\n".join(parts)

怎么看结果：代码静默结束即通过。八种可选片段组合逐一做精确字符串断言，并用 encode() 证明两种组装结构的输出字节一致；失败时 Python 会显示具体组合和格式差异。

安全边界：这个函数只负责可预测地拼字符串，不会把 context 变成可信指令，也不能防止 prompt injection。外部资料仍是不可信数据；权限控制、工具确认、输入隔离和输出校验要在 Agent 架构的其他层完成。

Q "条件拼接 Prompt" 推荐用哪种写法？
把各片段按条件 append 进列表、最后按本课格式契约用 "\n\n".join(parts)，可读性和可维护性最好——加一个条件片段只要多一个 if ... append。反复用 += 拼字符串或嵌套三元表达式都会让 Prompt 逻辑迅速失控。

流程控制

def render_prompt(role, question, context="", tools=None, strict=False):
    tools = tools or []          # 防可变默认参数陷阱（见 L03）

思考题

先自己想，再点开对答案。

Q1如果 tools 默认写成 tools=[] 会有什么隐患？

会踩可变默认参数陷阱：所有调用共享同一个列表，一次污染、次次遭殃。

默认值 [] 只在函数定义时创建一次，之后每次不传 tools 的调用拿到的都是同一个列表对象。只要函数体内对它做过一次 append（或别处持有它并改动），下一次调用就会看到上一次残留的内容——工具列表会莫名越攒越多。

正解是默认写 tools=None，进函数第一件事 tools = tools or []，让每次调用都拿到一个全新的空列表。这正是本课参考实现里 tools = tools or [] 那行的用意，也呼应 L03 的可变默认参数陷阱。

Q2如果要支持 few-shot 示例（一组 输入→输出 样例），你会怎么扩展这个函数？

加一个 examples 参数（默认 None），把每个样例渲染成一段文本片段，按条件 append 进 parts 列表。

沿用本课「条件拼接」的套路，签名扩成 render_prompt(role, question, ..., examples=None)，其中 examples 是一个 [{"input": ..., "output": ...}, ...] 列表。函数内先 examples = examples or [] 兜住可变默认参数，再判断非空才拼这一段。

拼法就是一个 f-string 循环：lines = [f"输入：{e['input']}\n输出：{e['output']}" for e in examples]，然后 parts.append("示例：\n" + "\n\n".join(lines))。位置放在「问题」之前——先给模型看几个范例，再抛出真正的问题，效果最好。

这样既没破坏原有结构，又完全复用了「片段入列表再 join」的思路：新增一种内容，只是多一个 if ... append。

本课最佳实践验收：离线任务事件轮询器

任务目标

实现一个完全离线且受读取次数约束的作业事件轮询器，证明继续、成功、耗尽和协议违约都有明确、最小化且可测试的结果。

操作清单

  1. 实现 poll_job(read_event, limit)，每次读取一个作业事件。
  2. queued 与 running 表示继续轮询。
  3. succeeded 是终态，返回作业结果和实际轮询次数。
  4. 先验证 limit 是正整数；耗尽时返回诊断，未知事件错误只报告 kind 与 Python 类型。

通过标准

  • 完全离线，不需要模型、密钥或网络
  • 四条核心路径和非法 limit 都有精确断言
  • 成功结果、轮询次数与错误文本均不可含糊
  • 只打印一次唯一标记 L04 ACCEPTED
课末自检（默认折叠；整块复制即可运行）：
def event_reader(*events):
    """依次读取离线事件；事件用完后重复最后一个。"""
    index = 0

    def read_event():
        nonlocal index
        event = events[min(index, len(events) - 1)]
        index += 1
        return event

    read_event.read_count = lambda: index
    return read_event


def poll_job(read_event, limit=4):
    if (
        isinstance(limit, bool)
        or not isinstance(limit, int)
        or limit <= 0
    ):
        raise ValueError("limit must be a positive integer")

    for poll_count in range(1, limit + 1):
        event = read_event()
        match event:
            case {"kind": "queued" | "running"}:
                continue
            case {"kind": "succeeded", "result": result}:
                return {
                    "status": "succeeded",
                    "result": result,
                    "polls": poll_count,
                }
            case _:
                event_kind = (
                    event.get("kind")
                    if isinstance(event, dict)
                    else None
                )
                if not isinstance(event_kind, str):
                    event_kind = "<missing-or-non-string>"
                raise ValueError(
                    "unknown job event: "
                    f"kind={event_kind!r}, "
                    f"python_type={type(event).__name__}"
                )
    return {
        "status": "limit_exhausted",
        "result": None,
        "polls": limit,
    }

怎么看结果：应只看到一行 L04 ACCEPTED。精确断言会检查终态、耗尽、未知事件的最小化诊断，以及非法 limit 发生零次读取；失败时会显示实际值，便于定位分支或边界错误。

边界与替代方案：这里的 limit 控制读取次数，不处理真实等待时间、并发更新或进程重启。生产轮询器还需退避、墙钟超时和持久化检查点；若事件源支持推送，可用 webhook 或消息队列替代轮询，减少空读成本。

排错为什么达到次数上限不直接抛异常？

耗尽是调用方已经声明并可预期的运行结果，未知事件才是协议违约。返回结构化耗尽状态便于上层决定稍后重试或报警；若业务把耗尽定义为不可恢复故障，也可以在边界层把这个状态转换成异常。

面试常见问题

Q1：match-case 和一连串 if/elif 比，优势在哪？

答：match-case 能在匹配的同时解构数据（从 dict/对象里直接取出字段绑定到变量），还能匹配结构和类型，代码更声明式、更好扩展。纯做相等判断时两者差别不大，但分发"带结构的数据"（如 LLM 动作）时 match 明显更清晰。

Q2：f-string 的 !r、= 各是干嘛的？

答：!r 用 repr() 渲染，会显示引号和转义字符，适合排查隐藏字符；{x=} 同时输出变量名和值（x=3），是快速调试利器。两者在排查 Prompt 和 Agent 状态时很常用。

Q3：为什么推荐"片段列表 + join"而不是用 + 拼接长字符串？

答：可读性和可维护性。条件拼接时，每个片段就是一个 if ... append，逻辑一目了然、容易增删；用 += 反复拼接则容易漏空格/换行、难以维护。性能上，大量拼接时 join 也优于循环里反复 +。

Q4：Agent 主循环为什么必须有终止条件？

答：LLM 可能始终不返回"结束"信号，或在工具间反复横跳，没有 MAX_STEPS 或超时就会无限循环、耗尽 Token 和成本。终止条件（步数上限 / 超时 / 显式 stop）是 Agent 最基本的安全设计。

Q5：split(sep, maxsplit) 的 maxsplit 有什么用？

答：限制最多切分次数。解析形如 "key: value 里也有: 冒号" 的字符串时，split(":", 1) 只切第一刀，保证右半部分完整，避免把值里的分隔符也切碎。

总结

  • Agent 是"循环里的决策机器"——流程控制就是它的骨架
  • while 主循环必须有终止条件（MAX_STEPS / 超时 / stop）
  • match-case 分发"带结构的动作"，能匹配+解构，比 if/elif 更清晰
  • f-string 高级用法：格式化、!r 显转义、= 调试、三引号多行
  • Prompt 构造可用变量替换、片段列表 + join 和上下文注入；同一“条件拼接”原则不必重复实现
  • 字符串渲染函数不提供 prompt injection 防护，安全边界还需要权限、隔离与校验
