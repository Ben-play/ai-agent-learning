检查 & 安装 Python

打开终端，按平台运行对应命令：

# Windows PowerShell（优先用 py，Python 官方安装器自带的启动器）
py --version
# 如果 py 不可用，再试
python --version
# macOS / Linux

应该看到类似 Python 3.11.x 或 3.12.x 的输出。

3.10 或更低⬇️ 需要升级
Windows：py/python 均无输出⬇️ 还没装 Python，需要安装（注意 Windows 通常没有 python3 命令，看到 python3 报错不代表没装 Python）

安装/升级 Python：

全平台最稳的路径是官网安装包：从 python.org/downloads 下载安装，Windows 安装时务必勾选 "Add python.exe to PATH"。

pyenv global 3.12

（pyenv 的 shell 初始化细节不在本课展开，跟着安装脚本输出的提示操作即可。）

安装后重新检查版本：

# Windows PowerShell

# macOS / Linux
python3 --version
# 应该输出 Python 3.11.x 或 3.12.x

安装 uv 包管理工具

uv 是 2024-2025 年 Python 生态最重要的工具之一，比 pip 快 10-100 倍。Agent 开发中你会频繁安装依赖，uv 能节省大量时间。

# Mac / Linux
curl -LsSf https://astral.sh/uv/install.sh | sh

# Windows
powershell -c "irm https://astral.sh/uv/install.ps1 | iex"

验证安装：

uv --version
# 应该输出类似 uv 0.x.x

uv 常用命令速查：

命令作用
uv init myproject创建新项目
uv add requests安装依赖
uv add --dev pytest安装开发依赖
uv run python main.py在虚拟环境中运行脚本
uv sync同步所有依赖
uv pip list查看已安装的包

--dev 表示把依赖记录进 dev 依赖组；uv sync / uv run 默认仍会同步 dev 组。生产环境要显式使用 --no-dev 等选项排除。

配置 VS Code

VS Code 是 Agent 开发最主流的编辑器。安装以下扩展：

# 用命令行安装扩展（如果已安装 VS Code CLI）
code --install-extension ms-python.python
code --install-extension ms-python.vscode-pylance
code --install-extension charliermarsh.ruff
code --install-extension ms-python.debugpy

或者在 VS Code 中手动安装：

  1. 打开 VS Code
  2. 按 Cmd+Shift+X（Mac）或 Ctrl+Shift+X（Windows）打开扩展面板
  3. 搜索并安装：
    • Python (ms-python.python) — Python 语言支持
    • Pylance (ms-python.vscode-pylance) — 智能提示和类型检查
    • Ruff (charliermarsh.ruff) — 代码格式化和 lint
    • Python Debugger (ms-python.debugpy) — 调试支持

让 VS Code 与 uv 项目使用同一个解释器：

  1. 先在项目根目录运行一次 uv run python -c "import sys; print(sys.executable)"，让 uv 创建或同步项目的 .venv。
  2. 在 VS Code 打开项目根目录，进入命令面板并运行 Python: Select Interpreter。
  3. 选择项目内的解释器：Windows 为 .venv/Scripts/python.exe，macOS/Linux 为 .venv/bin/python。不要选择全局 Python。
  4. 如果不想依赖编辑器当前选择，则在 VS Code 集成终端或任务中运行 uv run python main.py；任务的工作目录必须是项目根目录。
诊断：“Run Python File” 使用的是 VS Code 当前选择的解释器，并不自动等同于 uv run。若导入结果与终端不同，先比较 VS Code 显示的解释器路径与 uv run python -c "import sys; print(sys.executable)" 的输出；两者都应指向当前项目的 .venv。

4
创建第一个项目 & 虚拟环境

虚拟环境让每个项目的依赖互相隔离，避免版本冲突。这是 Python 开发的基本纪律。

mkdir my-first-agent
cd my-first-agent
uv init
# 此时生成 main.py；.venv 尚未创建
uv run main.py
# 首次 uv run 会创建 .venv 并同步项目环境

uv init 之后你会看到这样的目录结构（还没有 .venv）：

# my-first-agent/
# ├── .python-version    # Python 版本
# ├── pyproject.toml     # 项目配置
# ├── README.md
# └── main.py            # 示例文件

查看 pyproject.toml：

[project]
name = "my-first-agent"
version = "0.1.0"
requires-python = ">=3.11"

运行 uv run main.py 后，会看到输出 Hello from my-first-agent!，同时目录下多出一个 .venv（首次 uv run 才会创建虚拟环境并同步依赖，这一步之前是不存在的）。

最佳实践：从目标 uv 项目执行代码

本检查能证明：当前目录就是预期的 uv 项目根目录，且 uv run 的虚拟环境前缀对应该项目根目录的 .venv。它不证明其他终端、编辑器或部署环境也使用同一解释器。

什么时候会遇到：包明明安装过却无法导入，或 VS Code 与终端运行同一文件却得到不同结果。

❌ 依赖 PATH 猜解释器
# 可能调用全局 Python
python main.py

命令没有证明解释器属于目标项目。

✅ 从明确的 uv 项目运行
uv run python main.py

uv 按当前项目解析并执行；下面的检查再核对项目根目录与解释器路径。

为什么更优：uv run 把执行动作绑定到当前 uv 项目；再比较项目根目录、虚拟环境 sys.prefix 与 .venv 的真实路径，可以发现“站错目录”或“选错环境”。使用 sys.prefix 而非解析 sys.executable，可避免 Unix 上解释器符号链接指向基础 Python 时误报。该证据只针对本次命令，不能推出跨机器结果必然一致。

  1. 在目标项目根目录运行检查。
  2. 确认 pyproject.toml 与 uv.lock 都位于当前目录。
  3. 确认 uv run 的虚拟环境前缀对应当前项目的 .venv。
动手自检：核对项目根目录与 uv 解释器 
test -f pyproject.toml || { printf '%s\n' 'FAIL: 当前目录缺少 pyproject.toml；请 cd 到目标 uv 项目根目录。' >&2; exit 1; }
test -f uv.lock || { printf '%s\n' 'FAIL: 当前目录缺少 uv.lock；这不是已锁定的目标 uv 项目。' >&2; exit 1; }
uv run python -c "from pathlib import Path; import sys; root=Path.cwd().resolve(); prefix=Path(sys.prefix).resolve(); expected=(root/'.venv').resolve(); assert sys.prefix != sys.base_prefix, 'FAIL: uv run 未使用虚拟环境'; assert prefix == expected, f'FAIL: 虚拟环境不是当前项目 .venv: {prefix}'; print('project-root: PASS'); print('project-interpreter: PASS')"

怎么看结果：必须依次看到 project-root: PASS 与 project-interpreter: PASS。若目录缺文件，先切到当前练习创建的 uv 项目根目录；若解释器路径失败，检查当前目录是否为目标项目、删除错误的本地 .venv 后重新运行 uv run。VS Code 是否对齐要另行比较编辑器选择的解释器路径与 uv run python -c "import sys; print(sys.executable)" 的输出；编辑器选择不会控制 uv run。

安装常用依赖

Agent 开发最常用的几个包，先装上：

# 核心依赖
uv add httpx           # 异步 HTTP 客户端（调 LLM API 用）
uv add pydantic        # 数据验证（Agent 工具定义用）
uv add python-dotenv   # 环境变量管理（API key 存储用）

# 开发依赖
uv add --dev pytest    # 测试框架
uv add --dev ruff      # 代码 lint 和格式化
uv add --dev mypy      # 类型检查

验证安装：

uv pip list
# 应该能看到 httpx, pydantic, pytest 等

最佳实践：把已版本化的清单与锁文件作为依赖输入

本检查能证明：pyproject.toml 与 uv.lock 当前被 Git 跟踪，锁文件与清单一致，且 .venv 被忽略并未被跟踪。它只验证当前工作树的输入与状态，不证明其他平台一定产生相同结果。

什么时候会遇到：拉取代码后依赖漂移，或本机环境可用但清单、锁文件没有进入版本历史。

❌ 把本机环境当输入
pip install httpx
# 只保留 .venv/

本机安装状态不能替代可审查的项目文件。

✅ 检查版本化输入
uv lock --check --offline
git ls-files --error-unmatch pyproject.toml uv.lock

验证锁一致性，并确认两个真值文件已被 Git 跟踪。

为什么更优：版本化的 pyproject.toml 与 uv.lock 是团队能够审查、比较和重放的依赖输入；.venv 是本地产物。这里不运行同步，因此不会宣称“什么都不安装”，也不把一次本地检查夸大成跨平台可复现性证明。

  1. 用 uv add 或 uv remove 有意修改依赖。
  2. 审核清单与锁文件的差异，并将两者纳入版本控制。
  3. 忽略且不跟踪 .venv；需要构建环境时再用锁文件同步。
动手自检：检查锁一致性、真值文件与本地环境状态 
set -euo pipefail
uv lock --check --offline
git ls-files --error-unmatch pyproject.toml uv.lock >/dev/null || { printf '%s\n' 'FAIL: pyproject.toml 与 uv.lock 必须都被 Git 跟踪。' >&2; exit 1; }
git check-ignore -q .venv || { printf '%s\n' 'FAIL: .venv 未被 .gitignore 忽略。' >&2; exit 1; }
test -z "$(git ls-files -- .venv)" || { printf '%s\n' 'FAIL: .venv 已被 Git 跟踪；仅添加忽略规则不能取消跟踪。' >&2; exit 1; }
printf '%s\n' 'manifest-lock: PASS' 'venv-git-state: PASS'

怎么看结果：必须看到 manifest-lock: PASS 与 venv-git-state: PASS。uv lock --check --offline 失败表示离线缓存不足或锁文件与清单不一致；不要在验收中隐式联网或改锁，先区分错误并在受控步骤中处理。git ls-files 失败表示真值文件尚未纳入版本控制；.venv 失败则按消息修复忽略或跟踪状态。

6
配置环境变量（API Key）

LLM API 需要 API Key。我们用 .env 文件管理，永远不要把 key 写在代码里。

# Windows PowerShell
New-Item .env -ItemType File
# macOS / Linux
touch .env

也可以直接在 VS Code 资源管理器里右键 → New File，新建一个名为 .env 的文件。

在 .env 中添加（后续课程会用到）：

# .env（不要提交到 Git！）
OPENAI_API_KEY=sk-xxx
ANTHROPIC_API_KEY=sk-ant-xxx

在 .gitignore 中添加：

# .gitignore
.env
__pycache__/
*.pyc
.venv/

最佳实践：本地加载 .env，诊断只输出布尔状态

本检查能证明：当前 .env 与 .venv 被忽略且未被 Git 跟踪，python-dotenv 能从本地 .env 加载占位变量，并且诊断输出只有布尔状态。它不能证明 Git 历史、旧日志或截图中从未出现过密钥。

什么时候会遇到：调试 API 时最容易把 key 写进源码，或把完整值、前缀打印到终端和证据文件。

❌ 输出密钥材料
api_key = os.getenv("OPENAI_API_KEY")
print(api_key[:8])

即使只打印前缀，也会把密钥材料写入日志或截图。

✅ 只输出布尔状态
api_key = os.getenv("OPENAI_API_KEY")
print("key-loaded:", bool(api_key))

只回答“是否加载”，不输出值、长度或前缀。

为什么更优：本地 .env 让开发配置不进入源码，布尔诊断避免在新日志中复制密钥材料。忽略与未跟踪检查只说明当前工作树状态；无法反证历史泄露。任何真实密钥只要曾进入代码、Git 历史、日志或截图，就必须立即在服务端撤销并轮换，删除文本并不能恢复其安全性。

  1. 把 .env 与 .venv 写入忽略规则，并确认两者未被跟踪。
  2. 用 load_dotenv() 本地加载变量；诊断只打印 bool(...)。
  3. 若发生过真实暴露，不要尝试用本检查“证明安全”；直接撤销并轮换。
动手自检：用临时占位值验证本地加载 
set -euo pipefail
tmp_env=$(mktemp .l01-bp.XXXXXX)
trap 'rm -f "$tmp_env"' EXIT
printf '%s\n' 'L01_PLACEHOLDER=local-only-demo' > "$tmp_env"
git check-ignore -q .env || { printf '%s\n' 'FAIL: .env 未被 .gitignore 忽略。' >&2; exit 1; }
git check-ignore -q .venv || { printf '%s\n' 'FAIL: .venv 未被 .gitignore 忽略。' >&2; exit 1; }
test -z "$(git ls-files -- .env .venv)" || { printf '%s\n' 'FAIL: .env 或 .venv 已被 Git 跟踪。' >&2; exit 1; }
uv run python -c "from dotenv import load_dotenv; import os; load_dotenv(dotenv_path='$tmp_env', override=True); loaded=os.getenv('L01_PLACEHOLDER') == 'local-only-demo'; assert loaded, 'FAIL: 临时探针变量未精确加载'; print('secret-loaded:', loaded)"
rm -f "$tmp_env"
trap - EXIT

怎么看结果：唯一的密钥状态应为 secret-loaded: True，它表示加载值与本检查写入的精确占位值一致；错误值或环境中的同名旧值都会让检查停止。输出不得出现占位值本身或任何真实密钥前缀。忽略或未跟踪检查失败时，按精确错误修复。历史泄露或截图无法由这些命令排除，必须轮换。

在 Python 中使用：

from dotenv import load_dotenv
import os

load_dotenv()  # 加载 .env 文件

api_key = os.getenv("OPENAI_API_KEY")
print("Key loaded:", bool(api_key))  # 只输出 True / False

实战任务

任务：搭建完整的 Agent 开发项目

按照以下步骤，从零搭建一个可运行的项目：

  1. 用 uv init agent-hello 创建项目
  2. 安装依赖：uv add httpx pydantic python-dotenv
  3. 创建 .env 文件，只写课程占位变量：L01_PLACEHOLDER=local-demo（不要读取或粘贴真实 key）
  4. 创建 main.py，写入以下代码：
"""我的第一个 Agent 项目骨架"""
from dotenv import load_dotenv
from pydantic import BaseModel
import os

# 明确从当前项目 .env 加载，并覆盖同名继承变量，避免环境噪声误通过
load_dotenv(dotenv_path=".env", override=True)

# 下面的 BaseModel、函数定义、类型注解不是本课考点
# 当前只需要照抄运行，验证环境是否搭好就行
# BaseModel 会在 L14 讲，函数在 L05 讲，类型注解在 L13 讲
class Message(BaseModel):
    """消息模型 - 后续 Agent 的基础数据结构"""
    role: str
    content: str

def main():
    # 验证 .env 是否成功加载
    placeholder = os.getenv("L01_PLACEHOLDER")
    if placeholder != "local-demo":
        raise RuntimeError("未从当前项目 .env 精确读取 L01_PLACEHOLDER")
    print(".env 加载成功:", placeholder == "local-demo")

    # 验证 Pydantic
    msg = Message(role="user", content="Hello, Agent!")
    print(f"✅ Pydantic 工作正常: {msg.model_dump()}")

    # 验证类型提示
    def greet(name: str) -> str:
        return f"你好, {name}! 准备好学 Agent 了吗？"

    print(f"✅ {greet('同学')}")

# __name__ == "__main__" 这行也不是本课考点，L02 会讲，这里照抄能跑就行
if __name__ == "__main__":
    main()
  1. 运行：uv run main.py
  2. 看到 .env 加载成功: True 就算成功；程序只比较课程占位值，不读取或打印真实密钥。（如果抛出 RuntimeError，说明当前项目 .env 没建对或占位值不精确。）
Windows PowerShell 故障提示：如果运行时出现 UnicodeEncodeError，先执行 $env:PYTHONIOENCODING="utf-8"，再运行 uv run main.py。这个设置只影响当前终端会话。

课末自检：运行独立、安全的 Shell 验收 
set -euo pipefail

repo_root=$(git rev-parse --show-toplevel) || { printf '%s\n' 'FAIL: 当前目录不在课程 Git 仓库内。' >&2; exit 1; }
project="$repo_root/code/phase1-python/part-a-basics/agent-hello"
test -d "$project" || { printf '%s\n' "FAIL: 找不到现有项目: $project" >&2; exit 1; }
cd "$project"

evidence=$(mktemp .l01-evidence.XXXXXX)
probe=$(mktemp .l01-secret-probe.XXXXXX)
trap 'rm -f "$evidence" "$probe"' EXIT

demo_prefix='l01-local-demo-'
demo_secret="${demo_prefix}not-a-real-key"
printf 'L01_PLACEHOLDER=%s\n' "$demo_secret" > "$probe"

{
  test -f pyproject.toml || { printf '%s\n' 'FAIL: 项目根目录缺少 pyproject.toml。' >&2; exit 1; }
  test -f uv.lock || { printf '%s\n' 'FAIL: 项目根目录缺少 uv.lock。' >&2; exit 1; }
  printf '%s\n' 'project-root: PASS'

  git ls-files --error-unmatch pyproject.toml uv.lock >/dev/null || { printf '%s\n' 'FAIL: pyproject.toml 与 uv.lock 必须都被 Git 跟踪。' >&2; exit 1; }
  before=$(sha256sum pyproject.toml uv.lock)
  uv lock --check --offline
  printf '%s\n' 'manifest-lock-inputs: PASS'

  git check-ignore -q .env || { printf '%s\n' 'FAIL: .env 未被 .gitignore 忽略。' >&2; exit 1; }
  git check-ignore -q .venv || { printf '%s\n' 'FAIL: .venv 未被 .gitignore 忽略。' >&2; exit 1; }
  test -z "$(git ls-files -- .env .venv)" || { printf '%s\n' 'FAIL: .env 或 .venv 已被 Git 跟踪。' >&2; exit 1; }
  printf '%s\n' 'local-files-git-state: PASS'

  uv run --offline --locked python -c "from pathlib import Path; import sys; root=Path.cwd().resolve(); prefix=Path(sys.prefix).resolve(); expected=(root/'.venv').resolve(); assert sys.version_info >= (3, 11), f'FAIL: 需要 Python 3.11+，实际为 {sys.version.split()[0]}'; assert root == Path(r'$project').resolve(), f'FAIL: 项目根目录不匹配: {root}'; assert sys.prefix != sys.base_prefix, 'FAIL: uv run 未使用虚拟环境'; assert prefix == expected, f'FAIL: 虚拟环境不是项目 .venv: {prefix}'; print('python-version: PASS'); print('project-interpreter: PASS')"
  uv run --offline --locked python -c "from pathlib import Path; import httpx, pydantic, dotenv; venv=(Path.cwd()/'.venv').resolve(); files=[Path(httpx.__file__).resolve(), Path(pydantic.__file__).resolve(), Path(dotenv.__file__).resolve()]; assert all(venv in path.parents and 'site-packages' in path.parts for path in files), f'FAIL: 依赖未全部来自项目 .venv site-packages: {files}'; print('locked-import-provenance: PASS')"
  L01_EXPECTED="$demo_secret" uv run --offline --locked python -c "from dotenv import load_dotenv; import os; load_dotenv(dotenv_path=r'$probe', override=True); loaded=os.getenv('L01_PLACEHOLDER') == os.environ['L01_EXPECTED']; assert loaded, 'FAIL: 临时探针变量未精确加载'; print('secret-loaded:', loaded)"

  after=$(sha256sum pyproject.toml uv.lock)
  test "$before" = "$after" || { printf '%s\n' 'FAIL: 验收期间 pyproject.toml 或 uv.lock 发生变化。' >&2; exit 1; }
  printf '%s\n' 'manifest-lock-unchanged: PASS'
} 2>&1 | tee "$evidence"

if grep -F -e "$demo_secret" -e "$demo_prefix" "$evidence" >/dev/null; then
  printf '%s\n' 'FAIL: 证据中出现了密钥值或密钥前缀。' >&2
  exit 1
else
  grep_status=$?
  if [ "$grep_status" -ne 1 ]; then
    printf 'FAIL: 证据扫描执行失败，grep exit=%s。\n' "$grep_status" >&2
    exit 1
  fi
fi
printf '%s\n' 'L01 ACCEPTED'

安全边界：证据只显示 secret-loaded: True，不会显示占位值、其前缀或真实密钥。最后一行必须且只在全部检查通过后显示 L01 ACCEPTED。该验收无法反证历史 Git、旧日志或截图中没有泄露；若真实密钥曾出现过，必须在服务端撤销并轮换。

精确通过标准

  • project-root: PASS
  • manifest-lock-inputs: PASS
  • local-files-git-state: PASS
  • python-version: PASS
  • project-interpreter: PASS
  • locked-import-provenance: PASS（三个包均来自项目 .venv 的 site-packages）
  • secret-loaded: True（加载值与临时占位值精确相等）
  • manifest-lock-unchanged: PASS
  • 证据扫描未发现占位密钥值或前缀
  • 最后一行恰为 L01 ACCEPTED
排错命令没通过时先检查什么？

按第一条 FAIL 定位。“不在课程 Git 仓库”表示应先在课程仓库内打开 Git Bash；“缺少 pyproject.toml/uv.lock”表示现有项目路径不完整；“必须被 Git 跟踪”表示真值文件未版本化；“.env/.venv 未忽略”与“已被跟踪”是两种不同状态；“解释器不在项目 .venv”表示当前 uv 项目边界或本地 .venv 不正确，与 VS Code 的解释器选择无关；依赖来源失败表示导入包不在当前项目 .venv 的 site-packages；“锁文件发生变化”表示验收期间有其他进程修改了依赖输入，应审查差异后重试；离线检查报告缓存或缺包错误时，先在联网且受控的步骤中按锁文件准备环境，再重新执行验收。临时探针必须与脚本生成的占位值精确相等，否则会立即停止，不会继续输出 L01 ACCEPTED。

阶段实践检查点：开发环境证据闭环

任务目标

为当前 agent-hello 建立可重复的开发环境证据闭环，证明 uv 项目边界、依赖来源、锁文件不变性和占位诊断可在无网络、无真实密钥的条件下共同成立。

操作清单

  • 先独立确认 VS Code 与终端都选择 agent-hello/.venv
  • 独立执行离线锁检查、依赖来源检查和占位变量布尔诊断，不使用真实 API Key
  • 完成后再展开参考验收程序，检查锁文件未变化、临时文件已清理和唯一输出标记

学习任务与验收脚手架分开：你负责完成环境配置和证据核对；折叠区使用少量后续语法自动验收结果，不要求在 L01 自己编写这段测试脚手架。

参考验收程序（独立完成环境任务后展开） 
set -euo pipefail
repo_root=$(git rev-parse --show-toplevel) || { printf '%s\n' 'FAIL: 当前目录不在课程 Git 仓库内。' >&2; exit 1; }
project="$repo_root/code/phase1-python/part-a-basics/agent-hello"
test -d "$project" || { printf 'FAIL: 找不到当前 agent-hello: %s\n' "$project" >&2; exit 1; }
cd "$project"
tmp_dir=$(mktemp -d "${TMPDIR:-/tmp}/p1-environment.XXXXXX")
cleanup() { rm -rf "$tmp_dir"; }
trap cleanup EXIT
probe="$tmp_dir/placeholder.env"
diagnostics="$tmp_dir/diagnostics.json"
printf '%s\n' 'L01_CHECKPOINT_PLACEHOLDER=checkpoint-placeholder-only' > "$probe"
before=$(sha256sum pyproject.toml uv.lock)
uv lock --check --offline >/dev/null
L01_PROBE="$probe" L01_DIAGNOSTICS="$diagnostics" uv run --offline --locked python - <<'PY'
import json
import os
import sys
from pathlib import Path

import dotenv
import httpx
import pydantic
from dotenv import load_dotenv

root = Path.cwd().resolve()
venv = (root / ".venv").resolve()
prefix = Path(sys.prefix).resolve()
assert root.name == "agent-hello", f"FAIL: 当前项目不是 agent-hello: {root}"
assert sys.prefix != sys.base_prefix, "FAIL: uv run 未使用虚拟环境"
assert prefix == venv, f"FAIL: sys.prefix 不是项目 .venv: {prefix}"
for module in (httpx, pydantic, dotenv):
    source = Path(module.__file__).resolve()
    assert venv in source.parents and "site-packages" in source.parts, (
        f"FAIL: {module.__name__} 不来自项目 .venv/site-packages: {source}"
    )
load_dotenv(dotenv_path=Path(os.environ["L01_PROBE"]), override=True)
state = os.environ.get("L01_CHECKPOINT_PLACEHOLDER") == "checkpoint-placeholder-only"
diagnostics = {"placeholder-loaded": state}
assert all(type(value) is bool for value in diagnostics.values())
assert all(diagnostics.values()), "FAIL: 课程占位变量未精确加载"
Path(os.environ["L01_DIAGNOSTICS"]).write_text(
    json.dumps(diagnostics, sort_keys=True, separators=(",", ":")), encoding="utf-8"
)
PY
after=$(sha256sum pyproject.toml uv.lock)
test "$before" = "$after" || { printf '%s\n' 'FAIL: pyproject.toml 或 uv.lock 字节发生变化。' >&2; exit 1; }
test "$(tr -d '\r\n ' < "$diagnostics")" = '{"placeholder-loaded":true}' || { printf '%s\n' 'FAIL: 诊断必须只包含占位变量的布尔状态。' >&2; exit 1; }
printf '%s\n' 'P1 CHECKPOINT ENVIRONMENT PASSED'

通过标准

  • 脚本定位课程仓库中的当前 agent-hello
  • uv 全程使用 --offline，运行使用 --locked
  • sys.prefix 精确等于项目 .venv
  • httpx、pydantic、dotenv 均来自该 .venv/site-packages
  • pyproject.toml 与 uv.lock 前后字节哈希一致
  • 诊断文件只含占位变量的布尔状态，临时目录被清理
  • stdout 精确等于 P1 CHECKPOINT ENVIRONMENT PASSED

怎么看结果：成功时 stdout 只有 P1 CHECKPOINT ENVIRONMENT PASSED。若失败，按 stderr 的第一条 FAIL 或 Python 断言定位：项目路径错误先回到课程仓库；离线锁定失败先在受控联网步骤准备缓存；sys.prefix 或依赖来源失败时重建项目 .venv；哈希失败表示验收期间依赖输入被修改；布尔诊断失败只修复脚本创建的占位探针，不要提供真实密钥。继续参照 Environment 工程最佳实践。
