模型能力边界与 Base vs Instruct

搞懂 LLM 天生做不到什么——因为 Agent 架构，本质就是来补这些短板的

💡 为什么这课重要？

你调的助手 API 背后，是一个经过指令与偏好优化的模型。纯预训练的 base model 主要学习续写分布，没有被专门训练成稳定的对话助手；它可能回答问题，也可能继续补全文本。理解它如何变成今天的“助手”，是第一个必须搞懂的分水岭。

更关键的是它的能力边界：知识会过时、不会精确算术、会一本正经地幻觉、上下文有限还会"迷失在中间"、默认没有记忆……这些不是 bug，是 LLM 的先天局限。而这，正是 Agent 存在的全部意义——用工具、检索、记忆去补 LLM 的先天短板。学完这课，你会明白 Agent 每个组件到底在"救"哪条局限。这也是面试最爱问的一类问题。

学习目标

完成本课后，你将能够：

  • 说清 Base Model 和 Instruction-Tuned Model 的本质差别
  • 区分 SFT 与偏好优化（RLHF / DPO 类方法），知道训练路线并不唯一
  • 解释为什么不能假设指令微调会可靠注入事实知识，以及它与 RAG 的适用边界
  • 列出 LLM 能做的核心任务清单
  • 准确说出 LLM 的 6 大局限（面试常考），并解释每条为什么发生
  • 把每条局限映射到 Agent 用什么能力去补——建立贯穿全课程的主线

1. Base Model vs Instruction-Tuned Model

同一个模型，训练分两大阶段，产出两种"人格"：

Base Model（基座）Instruction-Tuned（指令模型）
怎么来的主要经过预训练：在海量数据上学习预测 Token通常在 base 之上做 SFT（监督式指令微调）+ 偏好/安全优化
行为倾向主要擅长续写 / 补全，也可能展现问答能力，但未专门对齐助手行为更稳定地理解并执行指令、遵循对话与安全规范
你问它问题可能回答，也可能继续补全类似文本通常按助手角色直接回答
典型代表Llama-3-Base、各家 -base 权重GPT / Claude / Gemini 的 chat 版

直觉例子：给 base model 输入"中国的首都是"，它可能补全成"中国的首都是北京，日本的首都是……"——它在模仿文本分布，不是在应答。指令模型才会理解成"你在问我，我该回答'北京'"。差别来自训练方式（见 Toloka: Base LLM vs Instruction-Tuned LLM）。

关键洞察：指令微调通常首先改变“如何回应、如何执行任务”，不能默认它会可靠注入新的事实知识。研究《A Closer Look at the Limitations of Instruction Tuning》在特定模型、数据集与单轮开放问答实验中发现：LoRA 微调主要改变格式与风格；全参数微调虽可能吸收信息，却可能损害事实质量。它不证明所有微调都不能学习知识——领域/任务微调仍可教授技能或模式。

怎么选：需要可更新、可引用的私有/最新事实时，RAG 往往更合适；需要改变行为、格式、领域术语或特定任务能力时，可考虑微调。两者可以组合，不是“只能二选一”。

对 Agent 开发者的意义：你日常调的 API（GPT / Claude / Gemini 的 chat / instruct 版）都是 instruction-tuned 的——正因为它们听得懂指令，你才能用自然语言下达任务、写 system prompt、做 function calling。base model 一般不直接拿来做 Agent。

Q 关于 base 与 instruction-tuned 模型，哪句最准确？
指令训练通常首先改善响应范式、任务执行和偏好对齐；不能把它当成可靠更新事实知识的保证。Base 也可能回答问题，训练路线也不只经典 RLHF。需要最新、私有且可引用的事实时通常优先考虑 RAG，但领域微调和 RAG 可以组合。

2. SFT、RLHF、DPO：别把训练路线混成一步

从 base 走向助手模型，常见但并不唯一的路线是：

  1. SFT（监督式指令微调）：用“指令 → 理想回答”示范教模型按任务作答。
  2. 偏好数据：让人类或其他评审比较多个回答，得到“哪个更好”的信号。
  3. 偏好优化：经典 RLHF 会训练奖励模型，再用强化学习优化；DPO 类方法则可直接用偏好对训练策略，不必走同一套奖励模型 + PPO 流程。

因此“指令模型 = SFT + RLHF”只是常见概括，不是所有厂商的统一配方。训练细节可能还包含安全微调、规则反馈、蒸馏和其他专有方法。

记忆钩子：预训练建立广泛能力与知识基础，SFT教任务响应范式，偏好优化让输出更符合人类/产品目标。三者边界不是绝对的，但不要把 RLHF 当成唯一对齐方法。

3. LLM 能做什么

指令模型的能力面相当宽，绝大多数是语言层面的任务：

  • 语言理解与生成：写文案、对话、续写
  • 总结 / 翻译 / 改写：长文压缩、跨语言、换语气
  • 抽取 / 分类：从文本里抠出结构化字段、打标签、判情感
  • 代码：生成、解释、调试、转写
  • 基于给定上下文的推理与问答：你把资料喂进 prompt，它据此回答（这正是 RAG 生效的基础）
  • 遵循复杂指令：多步骤、带约束、指定输出格式
  • 调用工具（function calling）：输出结构化调用意图，交给外部系统执行——这是 Agent 的技术地基

注意最后两条："遵循复杂指令" + "调用工具"正是让 LLM 从"聊天机器人"升级成"Agent"的两块拼图。而"基于给定上下文问答"则告诉我们——只要把正确的资料放进上下文，模型就能用；问题只在于怎么把正确资料找来放进去（下一节的局限会揭晓答案）。

4. LLM 不能做什么 / 六大局限（面试重点）

这一节是全课的核心。请把这张表背下来——它既是面试高频，也是理解 Agent 架构的钥匙。每条局限，右侧就是 Agent 用什么能力去补：

局限为什么会发生Agent 如何补
知识截止
(knowledge cutoff)		 只知道训练数据截止日之前的事；问最新事件会过时或干脆编造 联网 / 检索工具：搜索、调 API 拉实时数据（RAG）
不会精确计算 本质是概率预测下一个 Token，不是真在"算"；大数运算、精确计数容易错 代码 / 计算器工具：把算式交给 Python / calculator 执行
幻觉
(hallucination)		 会一本正经编造看似合理实则错误的内容；无法根除（见 L19） RAG + 引用校验 + 工具核对：让答案有据可查
上下文窗口有限 超长输入会被截断 / 丢信息；且"迷失在中间"(lost in the middle)——长上下文中间部分利用率低 检索 + 压缩 + 分块：只放相关片段，把关键信息放头尾
没有持久记忆 Messages API 默认无状态：服务端不会自动替应用维护完整业务会话 应用层状态 / 外部记忆：保存并重发必要历史，或按需检索长期偏好（Phase 5）
不知私有 / 实时数据 训练语料里没有你的内部文档、数据库、当下状态 直接上下文 / RAG / 工具：小文件可直接提供，知识库先检索，实时状态调 API

两个高频细节值得展开：

  • "迷失在中间"(lost in the middle)：当相关信息被放在超长上下文的中间位置时，模型的利用率明显低于放在开头或结尾。这意味着"上下文窗口大"不等于"信息就一定被用上"——工程上要把最关键的资料放到头尾。
  • 参数知识有截止与覆盖边界：模型不能仅凭参数可靠知道训练后事件或实时状态；但应用可以在当前请求里提供新资料、调用搜索/API，部分平台也可能提供服务器工具。问“现在最新版本”时应查询当前来源，而不是让模型凭记忆猜。
Q 用户问“今天的天气怎么样”，若请求没有工具或实时上下文，主要缺什么？
当前天气不是仅靠模型参数就能可靠回答的内容。本次请求需要天气 API、搜索工具或用户提供的实时数据，再由模型解释。关键是请求中有没有当前数据源，不是参数量、采样温度或上下文窗口大小。

5. 贯穿主线：Agent 就是来补 LLM 短板的

把第 4 节反过来读，你就理解了 Agent 架构存在的全部意义——它不是给 LLM"加聪明"，而是用外部能力补齐 LLM 的先天短板。一一对应：

LLM 先天短板          →   Agent 补的能力
─────────────────────────────────────────
参数知识过时 / 缺实时数据 →   搜索 / 业务 API / 当前上下文
不会精确算术            →   代码 / 计算器工具
幻觉                    →   外部证据 + 引用 / 工具核验
上下文有限 + 迷失中间    →   检索 + 压缩 + 证据编排
API 默认无状态           →   应用保存并重发 / 外部记忆
未见过私有数据           →   直接文档输入 / RAG / 业务工具

换句话说：LLM 是 Agent 的"大脑"，但大脑没有手、没有笔记本、也不上网。工具是它的手，记忆是它的笔记本，检索是它的联网。之后学到的每一个 Agent 组件——tool use、RAG、memory、planning——你都可以问自己一句："这是在补哪条局限？"这条主线会一直贯穿到课程结束。

Agent 场景练习：下面 4 个用户请求，各触碰了哪条 LLM 局限？Agent 该用什么能力补？先自己想，再展开对照。

  1. "今天 XX 公司的股价多少？"
  2. "帮我算一下 1234 × 5678 等于几。"
  3. "你还记得我上周说过我更喜欢简洁的回答吗？"
  4. "总结一下我刚上传的这份 PDF。"
点击查看参考答案
  • ① 今天的股价 → 局限：知识截止 + 无实时数据。补：联网 / 行情 API 工具拉当前价，再让 LLM 组织语言。
  • ② 1234 × 5678 → 局限：不会精确计算（概率预测，大数易错）。补：代码 / 计算器工具执行算式，返回精确结果。
  • ③ 还记得我的偏好吗 → API 默认无状态，不会自动保留上周会话。应用应保存偏好；短期可重发必要历史，长期可用外部记忆按需检索。
  • ④ 总结刚上传的 PDF → 如果平台支持文档输入且文件能放入上下文，可直接把 PDF 作为本轮输入，不需要模型预训练见过它；若文档库很大、只需局部证据或反复查询，再使用切块 + 检索（RAG）。

这 4 个请求需要的补充能力并不相同：实时股价要工具，计算要确定性执行，跨会话偏好要应用状态，上传 PDF 可能直接作为上下文或在大规模知识库中走 RAG。Agent 的价值是按缺口选择正确外部能力，不是所有问题都统一套 RAG。

Q 让应用跨会话记住用户偏好，主要需要补哪一层？
Messages API 默认不替应用维护跨会话业务状态。应用可保存偏好，在后续请求中直接重发必要内容，或从外部记忆检索后注入上下文。这里补的是应用状态管理，不是模型参数、温度或输出长度。
⭐ 面试高频：“LLM 系统有哪些能力边界？” 不要只背“六条天生缺陷”，要说明边界属于哪一层：参数知识过时/缺实时数据 → 搜索或业务 API；精确计算 → 代码工具；幻觉 → 外部证据与核验；长上下文利用不足 → 检索/压缩/证据编排；API 默认无状态 → 应用保存并重发或外部记忆；私有文件 → 直接文档输入、RAG 或业务工具。Agent 的意义是按缺口接入合适能力。

总结

  • Base 主要学习续写分布；Instruct 通常经过 SFT 与偏好/安全优化，更稳定地执行指令——这是行为倾向，不是绝对能力开关
  • 指令微调通常先改善响应与任务适配，不能假设会可靠更新事实；微调与 RAG 可组合，按行为/技能还是可更新知识来选
  • 偏好优化不只经典 RLHF；DPO 类方法可直接使用偏好对，不需要相同的奖励模型 + PPO 流程
  • 能力边界要按系统看：参数知识、实时数据、计算、幻觉、上下文和 API 状态分别由当前上下文、工具、检索、校验与应用存储补齐
  • 贯穿主线：Agent 架构的意义，正是用工具 / 检索 / 记忆去补 LLM 这些先天短板——之后每个组件都能对号入座
现在你手里有一张“LLM 系统能力边界”清单了。挑一个 Agent 场景，逐条判断缺的是当前数据、确定性工具、证据、上下文编排还是应用状态，再选择对应能力。下一课学习怎么看懂 Benchmark、按需求选对模型：L22。
