用回归用例改进 Harness

先重现失败，再修一个规则；验结果，不锁死合法路径

为什么这课重要？

工单方案没保存，系统却把一次中间结果当成成功。只改提示词让话术更谨慎，无法保证下次依赖失败会走正确终态。把失败变成可重复的任务，才知道修复是否有效。

学习目标

能把一条故障写成输入、预期业务状态和禁止动作，并用同一组案例对比修复前后。

1. 把一条故障写成任务、试验、轨迹和结果

故障报告写着「已经批准，页面说保存成功，重新打开却找不到草稿」。先把它缩到一个输入：空草稿区里保存 draft-01，审批已通过，保存依赖在落库前失败。如果规则把「尝试过」当成「成功」，就会返回 saved，但草稿区仍是空的。这个差异比「页面不对」更容易复现。

  • 任务（task）：给定上述初始状态和故障，要求报告依赖失败且不留下草稿。预期由业务规则决定，不从实现的当前输出抄来。
  • 试验（trial）：从空记录运行一次固定输入。旧版跑一次、新版再从空记录跑一次，是同一任务的两次试验，不共用上次的草稿或事件。
  • 轨迹（trace）：过程中发生了什么：审批通过后进入保存入口，记下 save_attempt，替身随后报告失败。入口有记录，不代表写入已提交。
  • 结果（outcome）：去草稿区查这次留下什么。旧版和修复版在这个故障下都留下零条，区别在返回状态；因此仅查存储也抓不到旧版误报成功的问题。

2. 同一份预期先让旧版失败，再让新版通过

故障替身只控制「保存依赖是否成功」，不替执行器决定要回什么状态。让旧版和新版用同一份独立预期：旧版应因误报保存而判红，新版应因正确报告失败且未落库而判绿。若旧版也绿，先确认确实尝试了保存并触发了故障，再检查断言是否漏比较状态，或把预期写成了和实现一样的分支。

固定试验条件应从系统观察到什么
已批准，保存依赖失败返回 dependency_failed，草稿区为空；旧规则的 saved 不得通过。
已批准，依赖可用返回 saved，恰有一条 draft-01；这条能抓住「全部拒绝」或「从来不写」的假修复。
未批准，依赖可用返回 denied，草稿区为空，且未进保存入口；沿用可用的依赖，只改批准条件，就能单独检查审批闸门。

3. 状态对了仍可能失败：到正确的观察点找原因

如果返回 dependency_failed 却留下一条草稿，说明改对了状态映射，但要查是否在确认依赖成功前写入，或失败时没回滚。若返回 saved 且有一条记录，还要核对记录是原来的 draft-01，不能拿任意一条凑数。反过来，denied 加空草稿区也不能证明闸门有效：保存入口可能已经被调用，只是没提交。直接观察入口是否被触达，才能区别「拦住尝试」与「尝试未生效」。

只固定业务要求的轨迹，比如没有批准就不得进入保存入口，预算耗尽后不能再分派；不要断言整条日志列表。将来先读任务还是先查本地策略，只要仍在许可与预算内，就可以不同。否则测试会因合法重排而报红，却未必能抓到真正的越界。

最佳实践：先证明回归能抓到原故障

适用：程序在异常路径留下了错误结果，且能用固定输入和本地替身重现。不适用：若故障只在真实并发、网络或模型波动中发生，本地替身只能验证已知机制，还要另做集成或重复试验。

❌ 只检查成功复跑

依赖抛错但仍返回 saved；若测试只查正常用例，旧回归也全绿。

✅ 让同一故障打中旧规则

依赖仍抛同一个错误。旧规则必须失败；新规则应返回 dependency_failed、不留下草稿，同时保留正常保存与拒绝行为。

为什么：先排除错误的验收条件或未触发的故障，再判断修改是否有效。维护三条用例比只测成功更费工；若底层依赖已有稳定错误契约，可复用其替身，不必为每次修复复制整套系统。

  1. 从实际报告提取最小输入、预期终态和必要轨迹。
  2. 执行旧规则与修复版对照，只改出错规则。
  3. 复跑正常与禁止路径；准备拿掉无效规则时用同一批用例复核。

怎么看：旧版也过，先确认故障确实触发、断言比较了返回状态：旧版和修复版的业务状态都是零条草稿。修复版误拦正常用例，通常是规则条件过宽。若终态对但越过禁止边界，查实际保存入口，不改预期掩盖问题。

Q 固定样例用于验证「未获审批不得尝试保存」。哪个证据最直接？
副作用可能尝试了却没成功。因此仅见数据库没变化还不够，另查保存入口是否被调用。

4. 动手：保留一个故意错误的旧实现

跟做：找出能抓住误报的断言

起点：两次都从 drafts = []、events = [] 开始。要保存 draft-01，已批准（approved=True），但保存依赖失败（dependency_ok=False）。

只做一步：保持这些输入不变，先写一条断言，让旧版（fixed=False）失败、修复版（fixed=True）通过，再展开对照。

自检：两次都只有一次 save_attempt 和零条草稿；你的断言必须能抓住「没写入却报告成功」。

预测下面哪条用例会抓到旧规则的问题。每次试验都创建新的内存记录；approved 是此练习已给定的判定结果，不是生产授权接口。依赖失败为确定性的本地模拟。

展开对照用例与离线自检
def trial(approved, dependency_ok, *, fixed):
    drafts, events = [], []
    if not approved:
        return "denied", drafts, events
    events.append("save_attempt")
    if not dependency_ok:
        # 旧规则把“尝试保存”误当成“已保存”。
        return ("dependency_failed" if fixed else "saved"), drafts, events
    drafts.append("draft-01")
    return "saved", drafts, events


cases = [
    (True, False, "dependency_failed", [], False),
    (True, True, "saved", ["draft-01"], False),
    (False, True, "denied", [], True),
]


def failures(fixed):
    failed = []
    for approved, dep_ok, expected, drafts, forbid_save in cases:
        status, stored, events = trial(approved, dep_ok, fixed=fixed)
        if status != expected or stored != drafts:
            failed.append(expected)
        elif forbid_save and "save_attempt" in events:
            failed.append(expected)
    return failed


assert failures(False) == ["dependency_failed"]
assert failures(True) == []
print("L53 ACCEPTED")

将代码保存为 Python 文件，用 python -I 文件名.py 运行。只应输出 L53 ACCEPTED。它证明旧规则被反例击中且修复未破坏两个对照；不证明真实依赖恢复或任何线上表现。

本课最佳实践验收：修复重试预算回归

任务：把练习从草稿保存换成只读目录。第一次读取返回暂时不可用；额度为一时，应停止且实际只读一次。额度为二允许再尝试一次并成功；首次即可读取时不要多调。先独立写出这三个结果和调用次数，再展开参考。

展开变式参考与自检（标准库、离线）
def exercise(limit, responses, *, obey_budget):
    calls = []

    def read():
        response = responses[len(calls)]
        calls.append(response)
        return response

    while len(calls) < (limit if obey_budget else 2):
        if read() == "found":
            return "complete", len(calls)
    return "exhausted", len(calls)


cases = [
    (1, ("unavailable", "found"), ("exhausted", 1)),
    (2, ("unavailable", "found"), ("complete", 2)),
    (1, ("found", "found"), ("complete", 1)),
]
assert [i for i, (limit, replies, expected) in enumerate(cases)
        if exercise(limit, replies, obey_budget=False) != expected] == [0]
for limit, replies, expected in cases:
    assert exercise(limit, replies, obey_budget=True) == expected
print("L53 TRANSFER PASSED")

通过标准：只打印 L53 TRANSFER PASSED。额度一却读了两次，要检查分派前的预算；额度二也失败，要检查规则是否把所有暂时故障都直接终止。这个故障替身不是重试、超时和取消的完整实现。

面试自查

先合上答案，按「结论 → 理由 → 如何验证」作答，再展开追问。

Q1已批草稿遇到落库前故障，旧版返回「已保存」但库是空的，怎么写回归判定？

参考回答：从空库用替身固定触发依赖失败，要求返回 dependency_failed 且草稿区为空。save_attempt 是过程轨迹，不是已提交结果；旧版和修复版都可能有一次尝试、零草稿，必须核对返回状态才能抓住误报。

追问：修复版返回失败，却多了原草稿，算通过吗？

答题要点：不算。状态正确不能抵消业务效果错误；应检查是否过早写入或未回滚。

Q2未获审批时返回 denied 且库为空，能证明拦住了保存尝试吗？

参考回答：不能，调用可能已经发生，只是没提交。除返回状态和存储结果，还要在保存入口观测调用次数并断言为零；不必比较完整轨迹，也不必锁定合法的只读步骤顺序。

追问：重构后删了旧日志文本，怎样保留同样的断言？

答题要点：在实际保存入口挂计数器或用替身记录调用，不用日志措辞代替边界证据。

Q3已批且依赖失败的用例通过了，要留哪两条对照防止假修复？

参考回答：每次从空记录起跑。已批且依赖可用应返回 saved 并留下原 draft-01，防止把所有写入关掉；未批但依赖同样可用应返回 denied，保存入口零次、草稿零条，单独验证审批闸门。

追问：为什么不让未批对照的依赖也失败？

答题要点：相对成功对照同时改了两个条件，零草稿可能只是依赖失败。保持依赖可用，只改变审批；再用入口计数验证是闸门拦下的。

Q4旧规则已被「误报成功」用例打红，怎么确认回归也能抓住「越过审批后未落库」？

参考回答：保留独立预期和可用的依赖替身，只在本地练习的修复版里改一处：让未批分支也触达保存入口，但仍返回 denied 且不提交。修复版应全绿，变异版应仅在未批用例的入口次数断言上判红，才说明该断言能抓住这类越界。

追问：如果变异版在初始化就抛错，算证明断言有效吗？

答题要点：不算。先确认试验实际触发目标行为、响应与业务结果仍满足预期，并在预定的入口断言上失败。
