RAG 数据模型与行级访问

同一个资料编号，换了查看者，数据库应该返回什么？

为什么先学数据访问？

夜间值班助理收到「领取台几点停止发放？」。北站和南站都用同一个模板，文档编号甚至都叫 KB-01，但结束时间不同。用户需要的是自己所在站点的答案，而不是词面最像的问题对应的答案。北站还有一张复核表，普通成员知道编号也不代表可以查看。接续 L59：宿主仍负责确认当前在代表谁；这里把「能不能读」落实到候选行，而不是让模型从全库结果中挑出自己认为合适的段落。

学习目标

  • 把租户、成员身份、行受众和用户想查的文档编号分开，画出从宿主到证据的边界。
  • 读懂 PostgreSQL 的默认拒绝、查看角色所需授权及行策略，用同一对象的不同查看者预测实际可见结果。
  • 用本地标准库实验验证正负对照，知道这些结果不能证明 PostgreSQL 或 SQLAlchemy 已接通。

1. 显式分开身份、对象与查询条件

租户规定资料归属范围；成员关系规定某人是否属于这个范围，以及在这里是普通读者还是复核员；行受众规定一个版本是本租户成员都可读，还是只给复核员。生产设计中，文档业务键是「租户＋文档编号」，不可变的资料版以「租户＋文档编号＋版本」入库；当前版由可信发布清单选择，返回行也带版本交给 L61 引用。若开放历史版本，先按访问规则核对该版本，不能假定读取过旧版便能读取新版。成员键是「租户＋用户」；北站的林与南站的林即使是同一个人，也要分开查成员关系，不能把任一站点的角色提升成全局角色。

生产宿主先认证用户，再核对其当前租户及租户成员资格，把结果作为可信上下文传入固定的取数工具；用户能提出要查哪份资料，却不能用自然语言、请求头或工具 JSON 为自己选择租户和角色。若界面提供切换站点，也须先由宿主确认该站点属于当前会话，再构造新的身份。绑定 SQL 参数保护语句结构，不证明参数有权代表谁。历史对话、模型记忆、文档内的指示都不是身份来源；宿主无法建立可信上下文时，终止此次取数，不以默认账号补救。

本课把权限检查放在候选集合形成时。想象合法资料在全库排序第四，前三名都是别的站点：如果先做全库前三，再删不可见行，用户会被告知没有资料，即使库里有正确答案；如果已经把这些行交给模型才过滤，数据早就出了边界。查询、索引、缓存与日志都应遵守这一约束：后续若引入索引，不能只在数据库源表上开策略就认为索引自动受保护；要限制搜索范围、处理权限与缓存失效，并在组装证据和打开引用时重新确认权限。

2. 为什么既需要角色授权，也需要行策略？

PostgreSQL 先要求查看角色能使用 schema 并对目标关系执行 SELECT，然后 RLS 决定哪些行可见。只有表授权、没启用 RLS 时，普通查询并不会凭空理解多租户；只建策略但没授表权限，则会报权限错误，不等同于查到零行。启用 RLS 却没有适用策略时，正常查看角色默认看不到行。本课的 FOR SELECT … USING 只控制读：没有写授权，不把读策略误当插入或更新时检查新行的 WITH CHECK。

迁移角色拥有表；运行时查看角色必须不是对象所有者或能取得所有者权限的成员，也不能是超级用户或有 BYPASSRLS。所有者通常不受 RLS 限制；FORCE ROW LEVEL SECURITY 可让所有者也受策略约束，但不是给运行时用所有者身份的理由，更不会限制超级用户或具备 BYPASSRLS 的角色。这里直接查基础表，不靠视图替代策略；将来经视图读取，要核对视图以谁的权限与策略读底表，以及调用者所需的授权。审核策略叠加也很重要：默认的宽松策略可按「或」组合，新增一条宽松规则未必会缩小可见集合。

预览用 l60_viewer 统一管理只读权限，但各个实际查看身份是独立的固定角色。成员表只让查看者看到 db_role = current_user 的映射；文档策略再使用该映射，要求文档租户一致且角色符合行受众。由于策略用到成员表，查看角色还需要其 SELECT，成员表本身也必须限制行。这里采用「一个已映射的数据库角色对应一个可信租户／用户」是为了让验证直接观察 current_user；并非要求大型系统为每个终端用户创建登录账户。换方案时，仍须回答：由谁设置身份、谁能改它、连接归还后是否留存上一请求的身份？

选读：SQLAlchemy 2.x 如何在一次事务内取数（未执行）

连接由宿主在另一隔离环境中预配；需已有 PostgreSQL schema、SQLAlchemy PostgreSQL 驱动及一个无管理权限的服务凭据，服务角色仅能切换到固定的查看角色（需要相应的 SET 成员资格），不能成为所有者、超级用户或可绕过 RLS 的角色。上段预览以回滚结束，因此不会为下段代码留下任何可连接对象。下段只展示事务内的操作，不创建引擎、数据库或凭据。文档编号可由用户提供；固定角色与当前版由宿主和发布清单选择。行策略回答「这个版本的受众是谁」，发布筛选回答「哪个版现在可用」，两者不是同一件事。

from sqlalchemy import text

ROLE_SQL = {
    ("north", "lin"): ("l60_north_lin", "SET LOCAL ROLE l60_north_lin"),
    ("north", "mei"): ("l60_north_mei", "SET LOCAL ROLE l60_north_mei"),
    ("south", "lin"): ("l60_south_lin", "SET LOCAL ROLE l60_south_lin"),
}


def fetch_document(engine, actor, doc_id, published_versions):
    # actor 与 published_versions 均来自可信宿主，不来自本轮请求。
    assignment = ROLE_SQL.get((actor.tenant, actor.user))
    version = published_versions.get((actor.tenant, doc_id))
    if assignment is None or version is None:
        return []
    role, role_sql = assignment
    with engine.begin() as conn:
        conn.exec_driver_sql(role_sql)
        state = conn.execute(text("""
            SELECT current_user,
                   row_security_active(CAST('l60.document' AS regclass)),
                   row_security_active(CAST('l60.membership' AS regclass))
        """)).one()
        if tuple(state) != (role, True, True):
            raise RuntimeError("unexpected viewer or RLS state")
        rows = conn.execute(text("""
            SELECT tenant, doc_id, version, body FROM l60.document
            WHERE tenant = :tenant AND doc_id = :doc_id AND version = :version
        """), {"tenant": actor.tenant, "doc_id": doc_id, "version": version}).mappings()
        return [dict(row) for row in rows]

SET LOCAL ROLE 和查询必须发生在同一连接的同一真实事务中，不用自动提交。退出事务会提交或回滚，局部角色随之结束；生产集成应让两个不同用户先后借到同一池连接，覆盖成功和异常回滚，确认不会沿用上一人的角色。不能把允许执行任意 SQL 的通道交给模型或终端用户，也不能用连接失败后的高权限重试填补空结果。

最佳实践：候选入口先验身份，查询结果再排序

适用：共享相同编号和关键词，但成员资格或行受众不同的知识库。不适用：只有单一公开语料、无需按用户隔离的索引；此时不必为每段附加虚构角色，但仍要区分公开与未发布资料。

后过滤

先算跨租户全局候选，再删去不可展示的行；既可能占用名额，也扩大候选暴露给后续组件的范围。

限定读取后排序

从受约束的视图或查询范围形成候选，后续只比较仍可用的资料；换用户，必须换授权范围。

权衡：数据库与索引必须了解权限维度，缓存颗粒变细，权限变更也要传播。换来的是正确的候选集合和清楚的审计边界。不要在日志写无权正文来证明少了一行。

  1. 同一编号换身份，再同名换租户；对照检索前的候选租户、编号和获准正文。
  2. 零候选时用已知可读项做正控；把预期的不可见与库或角色配置异常区分。

诊断：同一对象两人都读不到，先查表和 schema 权限及正控；同编号得到异地时间，先查租户键和身份绑定。

前两项在授权域之外排名，增加上限也不能保证合法项留下。最后一项只做了租户过滤，不可读的复核资料仍会占名额；必须在形成候选时同时约束租户和行受众。

面试自查

先说明决定发生在哪一层，再说需要观察什么才能证明。

Q1查询已经用绑定参数，能直接采用请求里的租户编号吗？

参考回答：不能。绑定参数解决语句与数据的分离；代表哪个租户必须由宿主身份和成员关系决定。可由请求提供编号作为查找条件，但服务只会在可信主体的可见行内查它。

追问：用户确实属于两个站点，如何切换？

答题要点：核实新站点的当前成员关系，重建本次的可信上下文，再查询；不能把另一站角色带过来。

Q2怎么证明 PostgreSQL 的「查不到」来自行策略？

参考回答：先确认 current_user、非所有者、无超级用户和绕过属性、当前关系的 RLS 状态，再确认具备 schema 与表的读权限。让普通读者查一条可读行，并对同一受限行比较普通读者的零行与复核员的一行。

追问：若返回权限错误，能当作负例通过吗？

答题要点：不能；权限错误反映对象授权或策略依赖未配齐，不能证明受众谓词按预期筛掉行。

Q3SQLAlchemy 连接池里怎样避免把上个用户身份带给下一个？

参考回答：在同一真实事务内局部设置固定角色、检查有效用户，再查询并在事务内取完结果。事务结束清理局部身份；连接角色本身只允许受控切换。

追问：如何验证异常分支没有遗留身份？

答题要点：让下一次调用复用同一池连接，分别覆盖前一请求成功与回滚，检查当前角色和实际可见行；SQLite 夹具不能替代这项测试。

Q4数据库读权限正确，就能把混合租户的向量索引交给任何人搜索吗？

参考回答：不能。复制到索引后的向量、摘要和原文有新的访问边界。搜索应在获准范围内产生候选，缓存要与权限范围关联，引用回查时仍须重新授权。

追问：用户移出站点后，旧缓存还能用吗？

答题要点：旧权限不是当前权限。设计撤销后的失效或重验；若不能确认当前有效，不把旧候选交给模型。
