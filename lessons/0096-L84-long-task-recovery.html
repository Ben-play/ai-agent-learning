长任务的取消、重放与预算

停掉未来的步骤，保住已经提交的业务事实

什么情况下只是恢复还不够？

客服取到制度，准备一份同步时间草稿，等人批准。L51 已经能恢复原任务，L52 还能处理保存后丢回执。但这次用户在批准之后、真正写入之前取消。如果进程重启就恢复成「从头跑」，预算会被补满，旧批准也会把草稿继续写进去。反过来，保存已提交后再按取消，也不能谎报成「没有保存」。本课把取消点放在下一次业务步骤之前，以同一个本地任务分别检查取消、耗尽、提交和重放。

学习目标

  • 根据持久化状态、剩余预算和审批绑定，判断下一次可否发生业务效果。
  • 用新解释器与独立 SQLite 查询，区分等待、缺证、耗尽、取消、回执丢失和已保存。

1. 预算和取消都是状态，不是提示词

本地任务以固定合成主体 support/mei 创建，任务 ID 是本地夹具名称。SQLite 中有两类记录：task 保存状态、剩余步数、取证原文、已批准绑定、已完成事件和回执；effects 保存实际提交的本地草稿记录（任务 ID、稳定操作 ID、完整证据）。审批采用 L52 的绑定形状：主体、任务、动作、草稿版本及内容摘要。本课的草稿数据就是一条可追溯的合成条目；不扩展成真实表单。SQLite 写锁串行化本例的状态和业务效果，不依赖内存里的「已取消」布尔值。审批来自固定实验宿主，不是让请求或模型声称自己拥有批准。

一次预算单位定义为一次有业务进展的步骤：检索、从证据生成预览、获批后保存，各扣一步。进入每一步前确认还有额度，再在同一事务里扣减并持久化。等待批准、取消、只查回执不扣步数；预算不是可意会的「少用一些」。在新进程读原任务时不接收新的预算，如果已经终态，更不能为同一 ID 再初始化。

同步草稿取证例：各条路线只改一个条件
初始预算和操作重开后的终态与余额业务效果
3 步；检索、预览、批准，再取消cancelled，余 1；后续推进不添事件零 INSERT，零持久行
2 步；检索、预览、批准，尝试推进exhausted，余 0；重启不补额度还没进入保存，零 INSERT
3 步；批准后正常推进saved，余 0；刚好用掉最后一步一次 INSERT，一条持久行
3 步；写入已提交，但子进程没回报退出 19、无 stdout；新进程查询得到 saved 与原回执业务表已有一行；恢复不再 INSERT

缺证是另一种停止：例如从两步预算开始，查不到可读规则仍发生过一次检索，终态 needs_evidence、余 1。零预算时则未检索就 exhausted。两种结果都没草稿，但处置不同：前者补合法资料，后者重新评估任务预算；都不要悄悄重置原试验。

2. 先问效果有没有提交，再解释退出

实验每个命令由可信父进程用固定脚本和参数数组启动，不用 shell。上一个解释器退出后，下一次仅继承同一临时数据库的路径、固定任务和动作，不传正文、审批内容或状态。阶段事件记录在任务事务内；insert_attempts 是这次 worker 实际到达业务 INSERT 前的计数，不是历史累计。若流程在提交后故意不返回，计数也随该响应一起消失，不能从空输出推出零次尝试。此时先从独立只读连接查全表；用同样绑定校验原回执，再让新 worker 读取原结果。持久事件列表没有增加，并且这次的插入次数确为零，才支持「重放没有再写」。这里没有强杀、断电或真实远程不可逆操作。

如果取消被接受时尚未进入保存，后续恢复就不该重新投递。若效果已提交，取消只会保留 saved；要撤销必须设计另一项有独立权限、批准与回执的业务动作。本课没有尝试抢占正在运行的远程调用，所有对照都是顺序调度；真实提供方是否响应取消、并发时谁赢、未确认结果怎么对账，都需要独立验证。前一课的工作区安全与本课的停止状态各守一层，不能互相替代。

决策卡：保存前守住停止点，保存后按回执对账

适用：任务跨请求或进程，且审批后仍可能排队。不适用：无副作用的单次快查询，不必为它建设持久队列。

误判：重启即重试整单

拿不到回执就重新执行，同时从头发额度。

选择：按持久状态续跑

终态先挡下一步，已提交只对账；检查点与业务效果分开观测。

代价：要维护状态、预算口径与历史任务；只有可重现的排队取消或恢复缺口才值得引入。下一步先用确定性 workflow，而不是让模型决定是否重放。

  1. 比较批准后取消、额度刚好不足与最后一步成功。
  2. 制造提交后丢回包，在新进程至少读两次回执，独立读取业务表。

验收：零新增事件不能替代零实际业务行；同一已存草稿只有一份，取消已保存任务不改写历史。

Q 已提交草稿，但调用方未收到回复。新的工作进程应先做什么？
没有回复不等于没有提交。应通过原操作绑定核对效果，而不是猜测。

3. 跟做：恢复不是从头再来

在可信课程仓库根，从进阶实验复制起点。用 Python 3.11+ 执行 python -I -X utf8 文件名.py，不加 -O。每个子进程只运行课程固定的 worker；-I 用于隔离导入环境，不是系统沙箱。

选修阶段检查点：验证是否值得持久化取消

选做约 10 分钟，另计。 两个临时库使用同一个同步草稿、同一批准绑定和 3 步预算；都在批准后请求取消，再由新进程推进。教学基线只在本轮收到停止请求，不写检查点，并明确返回 not_persisted；候选把 cancelled 写入检查点并清除批准。本例不是在声称 Phase 8 遇到了相同问题：Phase 8 是保存与重放参考，不是取消对照中的原方案。

重启后观察同一条已批准、尚未保存的任务
方案检查点与余额业务 INSERT／全表行数
停止未持久化批准仍在，推进后为 saved／0 步1／1

面试自查

先给业务结论，再给能够推翻它的观测。

Q1 任务已等审批一小时，预算只剩最后一步，重启时要补额度吗？

参考回答：不补。状态与剩余步数从持久库读；等待不消费这里的步数。

追问：产品还有从受理起算的截止时间呢？

答题要点：它是另一条规则，使用共享可验证时间基准，不能简单相减不同进程的单调时钟。

Q2 没拿到回执，却在业务库找到记录。要重新发送保存吗？

参考回答：以原操作 ID 和完整效果核对，匹配就读取原回执，不重新写。

追问：外部服务暂时查不到回执呢？

答题要点：区分未提交与无法确认，走对账或人工；本地事务不能许诺外部恰好一次。

Q3 取消后没有新增记录，能说运行中的外部动作也被取消了吗？

参考回答：不能；这是停止后续调度的本地证据。确认外部动作需服务确认及效果对账。

追问：如果对账表明已生效？

答题要点：保留原事实；若业务允许补偿，作为独立动作授权并验证。

Q4 异步队列上线前，团队只用一个进程重开数据库。它漏了什么？

参考回答：连接重开不能发现使用进程内存补状态；另启解释器，只按持久输入恢复。

追问：顺序子进程通过，能证明并发取消也正确吗？

答题要点：不能；要单独验证竞争顺序、真实效果边界与回执一致性。

小结与一手参考

以持久状态决定是否还能推进，每个实际步骤消费预算；终态意味着停止后续动作，不意味着撤销已提交效果。

  • SQLite · Transactions：本地事务与回滚的边界。
  • Python · subprocess.run：参数数组、超时与退出码。
  • AWS Builders’ Library · Idempotent APIs：用操作身份处理不确定结果，不把本地实验证明外推到所有服务。
