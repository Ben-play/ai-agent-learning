1. 版本、节点、稿件修订是三个坐标

状态里的 thread（真实图的 thread_id）定位 training:reviewer:export。授权仍由独立的审批库与当前业务库比对。正文和来源 ID 不放进图状态；业务快照保存原稿，回执标识指向业务行。

同一业务输入，由 Phase 10 v1 应用合同分别推进到三个停点
停止点图中可读事实审批与持久业务事实
待批准pending；下一节点 review，有一个中断无审批，也没有已保存行
已批准未执行reviewed；下一节点 apply_review有匹配批准；宿主停在业务调用之前，无保存行

后两种的图状态值与下一节点相同，不能仅看标签判断是否提交。闭库后，标准库实验将编排快照 contract.json、审批与来源 reviews.sqlite、业务 business.sqlite 一起封存，并逐文件计算 SHA-256；若还有 SQLite 附属文件就不封存。真实演练用自己的 graph.sqlite；业务金标可复用，快照格式和文件不可互换。此处是顺序本地夹具，不等于带并发写流量时跨库一致的备份方案。

另一路：Phase 6 原图实际写的是什么？

独立入口直接用 Phase 6 的 draft_graph.py：run_step(..., "stage") 留下人工中断；原 open_graph 用公开的 interrupt_before=["apply_review"] 停在获批未执行；再推进原图并捕获 Phase 6 的 LostReply，由业务全表读回判断是否确已提交。待批只初始化空的审批表。

旧图的顶层通道是 revision、digest、status 和可选的 op_id，没有 Phase 10 的 schema／binding。候选图保留旧通道、节点和中断顺序；固定宿主身份在内存补齐绑定，不能从 thread_id 推断批准。原审批库没有来源表；当前来源由固定合成宿主另行校验，不把新表当成原始证据。

原图和候选只推进从封存输入复制出的独立副本，不重建旧任务、不写 saver 私表。继续获批步骤时，invoke(None, ...) 仅传目标线程，不带快照里的 checkpoint_id。用公开接口核对最新 ID、一个可区分的旧快照及推进后的父链，旧 ID 只作对照。L56 使用刚读到的 snapshot.config 固定单写者停点；借用这份配置去继续一个可能已推进的线程，就会选错起点。是否保存或重放仍由原稿、全表和持久回执证明。

本课不执行真实 SDK。在已有获准且依赖锁定的 Phase 6 环境，可从 checkpoints/ 用该解释器运行 python -B -X utf8 langgraph_rehearsal.py --native-only；不带参数则另跑 Phase 10 应用图夹具。后者不是 Phase 6 快照。本环境只做静态检查，真实演练仍待验。

2. 给完成态加分支，不搬动旧中断

from pathlib import Path
from tempfile import TemporaryDirectory
import sys

sys.path.insert(0, str(Path("code/phase10-framework-evolution/evolution-lab/checkpoints").resolve()))
import contract
from rehearsal import clone, hashes, seed_bundle

with TemporaryDirectory() as tmp:
    root = Path(tmp)
    source = root / "sealed"
    origin = seed_bundle(contract, source, "pending", "named")["origin"]
    copy = clone(source, root / "working", origin)
    assert hashes(copy, origin) == origin
    for name in ("business.sqlite", "reviews.sqlite"):
        (copy / name).unlink()
    assert contract.inspect(copy) == contract.inspect(source)
    try:
        hashes(copy, origin)
    except AssertionError as error:
        assert "closed bundle entries" in str(error)
    else:
        raise AssertionError("accepted graph file without its ledgers")
    assert hashes(source, origin) == origin
print("L85 TRANSFER PASSED")

面试自查

Q1 线上业务把草稿修订从 2 升到 3。是否也要升级应用 schema？

参考回答：不必，修订标识的是批准绑定的稿件，不是应用状态形状。

追问：正文碰巧没变呢？

答题要点：修订仍是绑定的一部分；不能因摘要一样而替换批准对象。

Q2 同事希望直接重命名待运行的审批节点。上线前要什么证据？

参考回答：先用旧运行路径生成实际暂停记录，复跑原节点与恢复顺序。

追问：可以在旧名外保留适配节点吗？

答题要点：可以对照，但要核对中断顺序和效果；不能只测新建任务。

Q3 恢复日志没有回复，能按「未提交」处理吗？

参考回答：不能；先看业务回执和持久行是否存在且一致。

追问：图和审批都还是已批呢？

答题要点：两份样本正好有相同图状态和批准；业务库才区分。

Q4 能用三个 SHA-256 摘要证明线上备份跨库一致吗？

参考回答：不能，摘要只比对字节；此处靠无并发且闭库后同批封存。

追问：线上不能停写怎么办？

答题要点：先设计一致切点或日志重放策略，再独立演练，不拷贝正在写的库。

小结与一手参考

分开看应用合同与原图存量：先封存三种停点，再对照最新续跑、历史快照和独立业务读回。标准库合同不证明旧图可恢复；真实入口仍需在阶段 6 固定依赖环境验证，未运行不算通过。

  • LangGraph · Interrupts：节点会重新从开头执行，中断顺序要稳定。
  • LangGraph · Graph migrations：图拓扑与运行中线程的约束。
  • SQLite · Write-Ahead Logging：附属文件与数据库状态的关系。
