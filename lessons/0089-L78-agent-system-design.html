在系统设计中说明取舍

先定证据、权限、状态和恢复，再问模型是否需要选下一步

为什么这课重要？

沿用 L76 导出客服：用授权证据回答，必要时转人工，另可保存带证据且已批准的本地草稿，不提交、不外发。高频保留期查询、等人批准的草稿、政策互相冲突的调查都从同一入口进来；给三种任务一套 Agent 循环既增加可变性，也可能把本应由代码控制的恢复与写入交给模型。本课按同一个业务合同选择最简单的控制流，并留下可被复核的决策记录。

学习目标

  • 按授权读取、审批与恢复要求，在函数、workflow 和有界单 Agent 间选择。
  • 用案例记录验证写入归属、停止位置与何时应复议。

1. 一条客服主线，五个组件各守一件事

网关定作用域。故事从宿主提供的合成作用域 support/mei 开始；实际系统先验证身份、租户和请求权限，再分配任务 ID、截止时间和预算。请求文本里的租户名字不能覆盖经过认证的租户。网关记录路由、版本与关联 ID，不持久化原始证据或审批正文到通用日志；读取及草稿落盘各自在自己的边界重核授权。RAG 只供证据。按租户和角色过滤后才检索，精确查验版本与定位，本例常规问答在 support 引 EXPORT-POLICY/v1 §1 得七天，operations 的同键三十天不能用来补空。检索排名不是政策权威；旧培训样张和当前政策冲突时，先按文档版本、人员适用范围和来源负责人核对，不能只挑分数高的。

人工交接有状态。例如 ticket-42 取到保留期，但发现区域附录缺失，答复只给可证实的事实，把缺口、已核实的证据键、版本、失败原因和后续责任人交给本租户客服队列；接手人须重新获准读取。交接不等于批准草稿，也不是把整个上下文搬到公共队列。另一路若证据齐全且用户选择留草稿，宿主保存预览与待批状态，审批须绑定任务、作用域、有效期和预览版本或摘要。禁止因有人接手就把待批改为已批准；取消、审批过期或证据版本变化时，重新核验或终止，不能悄悄换内容再沿用旧批准。

长时任务靠持久状态，不靠对话记忆。以草稿为例：取证 → 预览 → 等待批准 → 核验 → 写草稿 → 回执；等批应释放工作进程，恢复从检查点读当前授权、批准、证据版号和操作键，而不是重放整段会话。若写入后回执丢失，以原操作键核对已提交效果；同键不同预览不能复用。没有安全查询或幂等保证就暂停交人工，不承诺天然「恰好一次」。这条客服链路还有独立的夜间回归作业：按冻结的任务集与配置拆分回放，保存每分片结果及版本；重启后只补未完成分片，不把部分报告发布为整批通过。

评估系统观测这些决策，不接管业务。记录证据精确度、正确保守停止、批准绑定、恢复是否重复写入、交接原因、成功任务成本和端到端延迟；保持开发例与独立验收例分开。上线候选先按 L77 查硬门，再看按任务类型的质量、延迟、成本及人工接手负担。夜间评估任务只是读取合成样本、写独立结果，不使用客服草稿工具；其后台重试、取消和回放也用可查状态。以上是设计说明，不是本课脚本实现的网关、作业系统或权限证明。

2. 按谁决定下一步来选，不按节点数

薄函数适合已知问题到已知读取路径：按授权键定位当前政策，返回值与引文或明确缺口，不保留跨请求状态。确定性 workflow让代码掌管分支、状态与转移：可在节点内调用模型写预览，但模型不选择何时批准、恢复或写入。受限单 Agent用于下一条证据要靠上一条结果决定，且这种灵活性已有独立验证的读路径；例如先看本租户主政策的适用对象，再选择同租户已有授权的附录，而不是一开始总查所有资料。宿主限定来源和工具允许表，限制步数、时间与用量；缺证、不确定或耗尽就交接，不能写草稿、改变角色或延长预算。

这是组件级取舍：即便草稿前的取证以后嵌入受限 Agent，编排、审批、幂等和恢复的所有权仍归宿主。对于稳定案型，先保留固定路径作为对照，再给失败样本做盲测；判断额外一轮读取能否补齐可核验证据、是否提高人工接手量、尾延迟和维护成本。相同证据可由规则查到时，把分支收回 workflow。没有通用的步数、百分比或延迟阈值；约束来自产品、风险、现有负载及团队值班能力。

把同一客服业务拆成可独立复核的架构案例
决策输入独立审阅预期停下以后
policy-lookup：已知键、可授权读，无等待薄函数；最少状态无证据就报告缺口
approved-draft：要保存草稿，必须等待批准并能恢复workflow；显式保存审批与幂等状态从检查点恢复，仅宿主批准后写
conflicting-evidence：上条证据决定下一条；有受限读和独立评估正证受限单 Agent；增加调用和回归维护缺证或超额就交人工，不写
unscoped-reader / unvalidated-branch：上例分别去掉已授权读能力 / 独立评估证据workflow；分别停在交接 / 仅允许规定的固定检索仍未解决就交人工，不写
nightly-eval：固定案例分片，需跨进程续跑workflow；不是自适应取证从检查点补未完成分片，不碰业务草稿

按一次实际选择顺序走：给 conflicting-evidence 的是「允许同租户读、无草稿、无恢复、自适应取证有收益的验收证据」，因此产出 bounded-single-agent / adaptive-evidence-only / handoff-no-write。把其中「受限读取」置为假，即便原评估正证仍在，也要转 workflow / no-scoped-reader / handoff-no-write，停止自动读取。记录同时包含范围版本、案例 ID、写入归属、代价和回访条件。夹具中「通过适应性评估」仅为人工预置的设计输入，不是脚本真的测出了模型收益；字符串非空也不能代替人工审阅代价和证据。

从同一个 ticket-42 回看取舍：如果区域附录归属可查且当前可读，选下一次读取可能免去一次转人工；如果根本没给该租户授权，增加读取步数没有用。若用户只要保留天数，拿到七天和有效引用就结束；若要求保存待审批草稿，交由可恢复流程。把缺证、等待批准和写入结果未知记成不同状态，值班时才知道该补来源、继续等待，还是查原回执。

决策卡：写清控制者和停止后的去向

适用：同一个客服合同要选择控制流，且团队能供给授权读取、交接及评估。不适用：仅凭产品命名、工具多少或演示成功直接增加自主权限。

误判： Agent 会写预览，也可以自己认定获批

混淆生成、授权与持久提交，失去故障恢复和审计的清晰边界。

选择：固定宿主权限，有证据时才让模型选下一次读

取证可以灵活；交接、恢复和副作用按宿主合同执行。

  1. 写下证据范围、交付、禁止动作、批准和故障终态，不先选框架。
  2. 为最简单的可用方案写独立案例标签，再列明当前放弃了什么、重评看什么。
  3. 实测固定路线不足的案例，纳入 L77 的回归，再把记录及负例交给 L79。

诊断：查一次固定政策仍要迭代，找可收回的确定性步骤；恢复后草稿重复，查宿主的操作键和回执而非调提示；自适应不比固定路线多补证据，先降级而非加预算。

Q草稿预览由模型生成，但必须等人批准；工作进程重启也不能重复保存。谁应主导这条路径？
生成节点可以用模型，控制流、批准和写入回执仍是可恢复的宿主责任。

独立变式：调查要加一张草稿，谁拥有写入？

面试自查

Q1保留期问答已有稳定政策键，并能返回精确引用。怎样说服团队先不上 Agent？

参考回答：薄函数可以授权直读、带引用回答或标缺口，状态和成本都更低；先留结果基线。

追问：新增地区差异就必须上 Agent 吗？

答题要点：已知地区映射可配置进固定流程；只有下一次取证确需看前一步，并证明有收益时，才研究受限自适应。

Q2客服接手后发现证据更新，而审批来自旧预览，能否继续保存？

参考回答：不能自动沿用。交接只是换责任人，恢复要重验权限、证据与批准绑定；旧批准不覆盖变更后的预览。

追问：写入可能已发生，但回执没到呢？

答题要点：同键读回已提交效果，核对作用域与参数；无可靠机制则暂停核对，绝不盲目再写。

Q3现有流程经常因冲突证据交人工。会直接赋予单 Agent 全库读取吗？

参考回答：不会。先确认固定流程漏了什么，在同一独立负载上比较受限读取收益；将可读来源、预算与终态写入宿主控制。

追问：证据资格无法核验但回答看起来合理怎么办？

答题要点：停止并按最小交接合同转授权人员，不输出未证实结论或写草稿。

Q4夜间评估一千题跑到一半重启，团队想让模型判断从哪题接着跑。怎么设计？

参考回答：任务版本、分片完成记录和幂等键已知，应用 workflow 续跑并核完每个分片再聚合；模型不定状态。

追问：有什么资格在设计记录上写「可上线」？

答题要点：固定配置下复现完整的独立结果，证明权限、重复写入和恢复硬门，再报告质量、成功成本与延迟；本地决策检查不能替代它。
