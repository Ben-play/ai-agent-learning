把 L17–L23 学的全部串成一个能跑的"模型体检报告"脚本

💡 为什么这课重要？

前面 7 课你分别学了 LLM 的本质与参数（L17）、Token 计数（L18）、幻觉（L19）、推理模型、能力边界、Benchmark 与选型框架（L22）、Token 经济学（L23）。它们现在还是散的知识点。

真实工作里没人问你"什么是 Token"，他们问的是："这个场景该用哪个模型？为什么？贵不贵？靠不靠谱？" 回答这个问题，你要同时动用能力、幻觉、成本三块认知。这一课我们把它们拼成一个工具——"模型体检报告"脚本：用同一批任务跑不同模型，做幻觉测试，算成本，最后输出一张能拍板的对比表。这是 Phase 2 的收官，也是你之后做任何选型的可复用模板。

学习目标

完成本课后，你将能够：

  • 把"选哪个模型"拆成能力 / 幻觉 / 成本三个可测量的维度
  • 用 tiktoken 在发请求前本地估算每个 prompt 的 token 与成本（复用 L18）
  • 写出结构正确的 async 并发调用骨架，用环境变量读 key、设低温复现（复用 L15/L16/L17）
  • 设计"陷阱问题"+ Self-Consistency 做幻觉测试并打分（复用 L19）
  • 把三维汇总成一张综合报告，用决策框架给出选型结论（复用 L22/L23）

1. 项目目标 & 设计

我们要做一个脚本：给它一批任务和一组候选模型，它自动跑完、算完、评完，输出一张体检报告。为什么叫"体检"？因为它像医院的三项检查——每一项对应 Phase 2 学的一块：

维度测什么怎么测呼应
能力对比同一组 prompt，哪个模型答得质量高跑同一批任务、比输出L22 选型框架
幻觉测试问"陷阱问题"，谁在编造Self-Consistency + 人工核对L19 幻觉
成本核算跑这批任务要花多少钱token 计数 × 单价L18 / L23

整体数据流很简单，四步串起来：

一批任务(prompts) + 一组模型(models)
        │
        ├─ Step 1  用 tiktoken 数 token → 估算成本         (本地、真能跑)
        ├─ Step 2  async 并发调各模型 → 收集输出            (骨架、标 key 位置)
        ├─ Step 3  陷阱问题多次采样 → 判定是否幻觉           (Self-Consistency)
        └─ Step 4  汇总 能力/幻觉/成本 → 一张对比报告
                        │
                        └─ 选型结论：这个场景该选谁、为什么
设计原则：一次只测一个变量。 想公平对比模型，就要让除模型外的一切都相同——同样的 prompt、同样的 temperature、同样的评分标准。这跟 L17 的"设低温可复现"是同一个道理：把随机性摁住，差异才归因得清。

2. Step 1 · Token 计数与成本估算（复用 L18）

先算钱。这一段完全在本地跑，不需要任何 API key——因为 tiktoken 是本地库。我们数出每个 prompt 的 token 数，套上单价公式，就能在发请求前估出这批任务大概要花多少钱。

pip install tiktoken        # 或 uv pip install tiktoken

import tiktoken

# 取一个编码器（o200k_base 对应较新的 OpenAI 系模型）
enc = tiktoken.get_encoding("o200k_base")

def count_tokens(text: str) -> int:
    """本地精确计数：发请求前就知道这段有多少 token。"""
    return len(enc.encode(text))

# 单价用「示例」值：真实价格请查各厂商官网，这里只演示算法
# 单位：美元 / 每百万 token（输出通常是输入的 3~5 倍，见 L23）
PRICE = {
    # 模型名: (输入价/百万, 输出价/百万)  —— 均为示例，非真实报价
    "model-a": (3.0, 15.0),
    "model-b": (0.5,  1.5),
}

def estimate_cost(prompt: str, model: str, est_output_tokens: int = 300) -> float:
    """估算单次调用成本：输入按实际数，输出按经验预估。"""
    in_price, out_price = PRICE[model]
    in_tokens = count_tokens(prompt)
    cost = (in_tokens * in_price + est_output_tokens * out_price) / 1_000_000
    return cost

# —— 试跑 ——
prompt = "用一句话解释什么是向量数据库。"
for m in PRICE:
    print(m, "输入token=", count_tokens(prompt),
          "单次≈$", round(estimate_cost(prompt, m), 6))

这段代码直接可运行。输出会长这样（token 数是本地 tiktoken 实算的，金额是示例单价算出来的；不同 tiktoken 版本可能有 ±1 的差异）：

model-a 输入token= 10 单次≈$ 0.00453
model-b 输入token= 10 单次≈$ 0.000455

看到了吗——同一个 prompt，光算法本身就让 model-b 便宜了一个数量级。输出 token 通常比输入贵好几倍（L23），所以 est_output_tokens 这个预估值对总成本影响很大；真实场景里你应该用几次实测的平均输出长度来校准它。

⚠️ 两个提醒（都来自 L18）：①tiktoken 是 OpenAI 的分词器，对 Anthropic/Google 只是近似——跨厂商比成本时它给的是"同一把尺子下的相对值"，够用；②真实账单还含聊天格式的固定开销（role、分隔符），以及多轮历史会累加。所以这里算的是估算，用于横向对比，不是逐分逐厘对齐账单。
Q 为什么 Step 1 的 token 计数不需要 API key 就能跑？
tiktoken 把分词规则打包在本地库里，enc.encode(text) 完全在你机器上算，不发任何网络请求，所以不需要 key。这正是它的价值：发请求前就估好成本。真正要花钱、要 key 的是 Step 2 的模型调用。

3. Step 2 · 调用模型对比（复用 L15 / L16 / L17）

现在要真调模型了。因为不假设你手上有 key，下面的代码写成结构正确、原则上可运行的骨架：真实调用的位置、endpoint、key 都清楚标出，并给一个"没 key 就用 mock"的降级写法，让你现在就能跑通整条流水线。

三个关键设计，每个都呼应前面的课：

  • key 用环境变量读，绝不写死（写死会泄露）——os.environ["..."]；
  • temperature 设低（如 0）——对比要可复现，把随机性摁住，差异才归因得清（L17）；
  • 用 async 并发跑多个模型 × 多个 prompt——I/O 密集就该并发，别一个个串行等（L16）。
pip install httpx        # 传输层，见 L15

import os, asyncio, httpx

# key 从环境变量读，不写死。运行前：export MODEL_API_KEY="sk-..."
API_KEY  = os.environ.get("MODEL_API_KEY")      # 没有就走 mock
API_URL  = "https://api.example.com/v1/chat"    # ← 换成你厂商的真实 endpoint

USE_MOCK = API_KEY is None                       # 没 key → 降级为 mock

async def call_model(client: httpx.AsyncClient, prompt: str, model: str, temperature: float = 0) -> dict:
    """调一次模型。没 key 时返回 mock，方便先跑通流程。"""
    if USE_MOCK:
        await asyncio.sleep(0.1)                  # 模拟网络耗时
        return {"model": model, "prompt": prompt,
                "output": f"[MOCK-{model}] 对「{prompt[:12]}…」的回答",
                "output_tokens": 42}

    # —— 真实调用（有 key 时走这里）——
    payload = {
        "model": model,
        "messages": [{"role": "user", "content": prompt}],
        "temperature": temperature,   # 默认 0（对比可复现，L17）；采样一致性检测时传高值
        "max_tokens": 512,
    }
    headers = {"Authorization": f"Bearer {API_KEY}"}   # ← key 只在这里用
    r = await client.post(API_URL, json=payload, headers=headers, timeout=30)
    r.raise_for_status()
    data = r.json()
    return {"model": model, "prompt": prompt,
            "output": data["choices"][0]["message"]["content"],
            "output_tokens": data["usage"]["completion_tokens"]}

async def run_matrix(prompts: list[str], models: list[str]) -> list[dict]:
    """并发跑 models × prompts 的所有组合 (L16 的 gather 思路)。"""
    sem = asyncio.Semaphore(5)                    # 限流，别打挂对方 / 触发 429
    async with httpx.AsyncClient() as client:     # async with = 异步资源 (L15/L16)
        async def one(p, m):
            async with sem:
                return await call_model(client, p, m)
        tasks = [one(p, m) for m in models for p in prompts]
        return await asyncio.gather(*tasks)       # 同时发起、一起等

# —— 试跑（无 key 也能跑，走 mock）——
prompts = ["解释什么是幻觉。", "写一个 Python 快排。"]
models  = ["model-a", "model-b"]
results = asyncio.run(run_matrix(prompts, models))
for r in results:
    print(r["model"], "|", r["output"][:30], "| out_tok=", r["output_tokens"])

这段的方法名、async 模式、限流、async with 都是结构正确的（对照 L16 的 gather/Semaphore）。有 key 时把 API_URL 换成真实 endpoint 即可；没 key 时它自动走 mock，你现在就能跑通"矩阵调用 → 收集结果"这一步。

为什么 temperature 设 0 而不是默认值？因为对比实验要控制变量。默认温度下同一个 prompt 每次输出都不同，你就分不清"这次差是模型不行，还是这次运气不好"。设 0（或很低）让输出尽量确定，模型间的差异才是真差异。这跟 L17 讲的"低温更可复现、适合确定性任务"完全一致。（注意：低温≠完全确定，但足够公平对比。）
Q 做模型对比时，为什么把 temperature 设得很低？
对比实验要控制变量：默认温度下同一 prompt 每次输出都不同，你分不清差异来自模型还是来自随机采样。设低温（如 0）让输出尽量确定，模型间的差异才归因得清（L17）。温度和省钱、限流都无关。

4. Step 3 · 幻觉测试（复用 L19）

能力测完，测可靠性：谁在一本正经地编造？L19 讲过，幻觉是流畅、自信、但事实错误或无依据的生成。我们要主动去钓它出来。方法是设计一批"陷阱问题"，专挑模型容易编的三类：

  • 问不存在的事：一个查无此人/查无此物的对象（好模型应答"不知道/查无此……"，坏模型会编出细节）；
  • 问最新事件：超出训练截止的事（好模型应承认不确定，坏模型会瞎猜）；
  • 问需要精确计算的：一个必须算对的数（考它是真算还是"看起来对"）。

怎么判定是不是幻觉？用 L19 的 Self-Consistency（自洽性检测）：同一个问题，用较高温度采样多次，看几次答案是否一致。如果模型对某事有真知，多次采样会稳定收敛到同一个答案；如果是在瞎编，多次采样往往互相矛盾——答案越发散，越可能是幻觉。再配合人工核对标注对错。

import asyncio
# 复用 Step 2 的 call_model；这里注意：Self-Consistency 要「较高温度」采样，
# 与 Step 2 的对比（低温）目的不同——一个求确定，一个求发散看一致性。

# 陷阱问题库：每题标注类型，便于分析模型在哪类上更容易翻车
TRAP_QUESTIONS = [
    {"q": "介绍一下学者「张无极」在拓扑量子场论上的代表作。",
     "type": "不存在的对象", "expect": "应表示查无此人/不确定"},
    {"q": "请列出本月刚发布的所有大模型及其参数量。",
     "type": "超训练截止", "expect": "应承认信息可能过时/不确定"},
    {"q": "17389 × 20563 等于多少？只给最终数字。",
     "type": "精确计算", "expect": "应给出可核对的确定数值"},
]

async def self_consistency(client, question: str, model: str, n: int = 5) -> list[str]:
    """同一问题采样 n 次（较高温度），返回 n 个答案看一致性。"""
    async def one():
        # 高温采样才看得出发散：真实调用把 temperature 调高（如 0.8）；mock 恒定返回
        return (await call_model(client, question, model, temperature=0.8))["output"]
    return await asyncio.gather(*[one() for _ in range(n)])

def judge_hallucination(answers: list[str]) -> str:
    """极简判定：答案高度发散 → 疑似幻觉；高度一致 → 可能有真知（仍需人工核对）。"""
    unique = set(a.strip() for a in answers)
    if len(unique) >= max(2, len(answers) - 1):
        return "疑似幻觉(答案发散)"
    if len(unique) == 1:
        return "一致(需人工核对是否为真)"
    return "部分一致(存疑)"

评分表建议这样组织（每个模型 × 每个陷阱问题一格），最后统计每个模型的幻觉率：

模型      | 陷阱题类型     | Self-Consistency | 人工核对 | 判定
----------|----------------|------------------|----------|--------
model-a   | 不存在的对象   | 5/5 一致「查无此人」 | 正确弃权 | ✅ 未幻觉
model-a   | 精确计算       | 3/5 数字不一       | 算错     | ❌ 幻觉
model-b   | 不存在的对象   | 2/5 各编了细节     | 编造     | ❌ 幻觉
...       | ...            | ...              | ...      | ...
→ 幻觉率 = 幻觉格子数 / 总格子数

注意：judge_hallucination 是粗筛——一致不代表就对（可能一致地错），所以"一致"这一档仍要人工核对；但"发散"是很强的幻觉信号。而且这里用 set 精确匹配对格式很敏感（"3.14" 与 "3.14。" 会算作发散），工程里应先归一化再比（去标点/小写/抽关键值）。Self-Consistency 的价值是低成本地把可疑项筛出来，让人工只盯少数格子。

⚠️ 回顾 L19 的核心洞见：幻觉无法根除，因为评估机制在奖励瞎猜（诚实弃权反而扣分）。所以体检的目标不是找到"零幻觉"的模型（不存在），而是量化各模型幻觉率的高低，并看它在你关心的那类问题上表现如何。一个在闲聊上很稳的模型，可能在精确计算上频繁翻车。

5. Step 4 · 生成综合报告

三项检查都做完了，把能力、幻觉、成本汇总成一个结构，输出一张能拍板的表。数据结构很简单——每个模型一条记录：

def build_report(models, quality_scores, halluc_rates, cost_per_1k) -> list[dict]:
    """把三维汇总成一张表。三个入参分别来自 Step2/Step3/Step1。"""
    report = []
    for m in models:
        report.append({
            "模型": m,
            "平均质量": quality_scores[m],   # 0~10，来自能力对比(可人工/LLM-as-judge)
            "幻觉率":   halluc_rates[m],     # % ，来自 Step 3 评分表
            "每千次成本": cost_per_1k[m],    # $ ，来自 Step 1 估算 × 1000
        })
    return report

├───────────┼──────────┼────────┼──────────────┤

这张表把三门课变成了一眼能比的东西。关键是它逼你同时看三列——只看质量会选最贵的，只看成本会选最不靠谱的。真正的决策发生在下一节：怎么综合这三列做选择。

🧪 进阶挑战：用 LLM-as-judge 自动给质量打分（点开看思路）

上表的"平均质量"如果全靠人工评，量大了就评不动。L19 提过 LLM-as-judge：让一个（通常更强的）模型当裁判，按固定 rubric 给每个输出打分。思路草图：

# 让裁判模型按统一标准打分，减少人工
JUDGE_PROMPT = """你是评审。请按以下标准给「回答」打 0~10 分，只输出数字：
- 事实正确性(0~4)  - 完整性(0~3)  - 清晰度(0~3)
问题：{q}
回答：{a}"""

async def llm_judge(client, question, answer, judge_model) -> float:
    p = JUDGE_PROMPT.format(q=question, a=answer)
    out = (await call_model(client, p, judge_model))["output"]
    try:
        return float(out.strip().split()[0])
    except ValueError:
        return 0.0        # 裁判没给出数字，记 0 并人工复核

三个坑要记住：①裁判本身也会幻觉/有偏好，别把它当绝对真理，重要结论仍要抽样人工核对；②别让模型给自己打分（自评偏高），用不同/更强的模型当裁判；③rubric 要固定且明确，否则分数不可比——这跟 L22 说的"benchmark 要看评测方法"是一个道理。（另一个可选进阶：给 Step 1 加上 Prompt Caching 前后成本对比，把长 system prompt 缓存起来看省多少——见 L23。）

6. 选型结论（复用 L22 / L23）

报告有了，怎么从三列数字走到"就用它"？用 L22 的决策框架：先明确场景对三维的敏感度，再据此加权。同一张表，不同场景会选出不同模型——这才是重点。看三个示范推理（沿用上表的示例数字）：

场景最看重示范推理选择
医疗/法律问答 幻觉率 ≫ 成本 编错一条信息代价极高，贵一点无所谓。选幻觉率最低、质量最高的。 model-c
海量内容分类 成本 ≫ 质量 任务简单、调用量巨大，单次成本被放大 100 万倍；分类容错高。选最便宜的。 model-b
通用客服助手 三者平衡 质量要够用、成本要可控、别频繁编造。选三项都居中、没有明显短板的。 model-a

看出来了吗——同一张体检表，选出了三个不同的模型。这正是选型的本质：没有"最好的模型"，只有"最适合这个场景的模型"。

把决策逻辑写成代码也很直接——按场景给三维不同权重，算加权分：

def pick_model(report, w_quality, w_low_halluc, w_low_cost):
    """按场景权重打分选型。权重体现你对三维的敏感度 (L22)。"""
    def score(row):
        # 幻觉率、成本越低越好 → 取反向；质量越高越好
        return (w_quality     * row["平均质量"]
              - w_low_halluc  * row["幻觉率"]
              - w_low_cost    * row["每千次成本"])
    return max(report, key=score)

# 医疗场景：极度看重「低幻觉」，成本权重给低
best = pick_model(report, w_quality=1, w_low_halluc=2.0, w_low_cost=0.1)
# 分类场景：极度看重「低成本」
cheap = pick_model(report, w_quality=0.5, w_low_halluc=0.5, w_low_cost=2.0)
最容易犯的错：只看一个维度。 只看 benchmark 分数 → 可能选了个贵到用不起、还爱编造的模型；只看价格 → 可能选了个便宜但不靠谱、返工成本更高的。L23 提醒过：真正的成本是"总拥有成本"——包括幻觉导致的返工、人工复核。永远把能力 + 幻觉 + 成本放在一起权衡，这就是这份体检报告存在的意义。

🎯 速查卡：Phase 2 一页复习

【L17 本质与参数】LLM = 预测下一个 token 的概率机器
  优化「像人话」≠「事实正确」；temperature 低=确定/可复现, 高=多样
  对比实验设低温控变量；创意任务才调高

【L18 token / 计数】token = 子词片段，不是字/词/字母
  tiktoken 本地精确计数：enc.encode(text) → len 就是 token 数
  中文更费 token? 取决于分词器(o200k 已大幅抹平)；跨厂商只是近似

【L19 幻觉】流畅+自信+事实错/无依据；根源是评估「奖励瞎猜」
  无法根除，只能缓解：RAG / CoT / Self-Consistency / 允许弃权
  检测：多次采样看一致(发散=疑似幻觉) / LLM-as-judge / 要出处

【L20 推理模型】用「思考 token」换准确率，适合难推理/规划
  代价是更慢更贵；简单任务用它 = 杀鸡用牛刀

【L21 能力边界 / Base vs Instruct】Base=续写, Instruct=听指令(对齐后)
  知道模型「不能」做什么，比知道它能做什么更重要

【L22 benchmark / 选型】分数要看评测方法、别只看榜单数字
  选型框架：先定场景对 能力/幻觉/成本/延迟 的敏感度 → 再加权

【L23 token 经济学】输出通常 3~5× 输入；成本=(in×in价+out×out价)/1e6
  降本杠杆：Prompt Caching / Model Routing / 压缩历史
  真正成本 = 总拥有成本(含幻觉返工 + 人工复核)

【本课 体检报告】能力 + 幻觉 + 成本 三维一起看
  Step1 tiktoken 估成本(本地) → Step2 async 并发调模型(低温/env读key)
  → Step3 陷阱问题 + Self-Consistency 测幻觉 → Step4 汇总选型
  结论：没有最好的模型，只有最适合这个场景的模型

总结

  • 选型不是"哪个模型最好"，而是把问题拆成能力 / 幻觉 / 成本三维一起权衡
  • Step 1：tiktoken 本地数 token、套单价估成本——发请求前就算好，不需 key（L18）
  • Step 2：async 并发调各模型，env 读 key、设低温复现，没 key 用 mock 兜底（L15/L16/L17）
  • Step 3：陷阱问题 + Self-Consistency 测幻觉，答案越发散越可疑，粗筛后人工核对（L19）
  • Step 4：汇总成一张表，用决策框架按场景加权——同一张表能选出不同模型（L22/L23）
  • 最大的坑是只看一个维度；真正的成本是含返工与复核的"总拥有成本"
