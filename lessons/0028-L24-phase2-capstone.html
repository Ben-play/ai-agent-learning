💡 为什么这课重要？

前面 7 课你分别学了 LLM 的本质与参数（L17）、Token 计数（L18）、幻觉（L19）、推理模型、能力边界、Benchmark 与选型框架（L22）、Token 经济学（L23）。它们现在还是散的知识点。

真实工作里没人问你"什么是 Token"，他们问的是："这个场景该用哪个模型？为什么？贵不贵？靠不靠谱？" 回答这个问题，你要同时动用能力、幻觉、成本三块认知。这一课我们把它们拼成一个工具——"模型体检报告"脚本：用同一批任务跑不同模型，做幻觉测试，算成本，最后输出一张能拍板的对比表。这是 Phase 2 的收官，也是你之后做任何选型的可复用模板。

学习目标

完成本课后，你将能够：

  • 把"选哪个模型"拆成能力 / 幻觉 / 成本三个可测量的维度
  • 区分 OpenAI tokenizer 估算与 Claude 官方 count_tokens / response usage（复用 L18）
  • 设计中立 Provider Adapter：Claude 使用官方 Anthropic SDK，不把 OpenAI 响应字段伪装成通用协议
  • 设计"陷阱问题"+ Self-Consistency 做幻觉测试并打分（复用 L19）
  • 把三维汇总成一张综合报告，用决策框架给出选型结论（复用 L22/L23）

1. 项目目标 & 设计

我们要做一个脚本：给它一批任务和一组候选模型，它自动跑完、算完、评完，输出一张体检报告。为什么叫"体检"？因为它像医院的三项检查——每一项对应 Phase 2 学的一块：

维度测什么怎么测呼应
能力对比同一组 prompt，哪个模型答得质量高跑同一批任务、比输出L22 选型框架
幻觉测试问"陷阱问题"，谁在编造Self-Consistency + 人工核对L19 幻觉
成本核算跑这批任务要花多少钱token 计数 × 单价L18 / L23

整体数据流很简单，四步串起来：

一批任务(prompts) + 一组模型(models)
        │
        ├─ Step 1  用目标厂商计数方式 → 估算并核对成本
        ├─ Step 2  Provider Adapter → 统一结果结构 → async 并发
        ├─ Step 3  陷阱问题多次采样 → 判定是否幻觉           (Self-Consistency)
        └─ Step 4  汇总 能力/幻觉/成本 → 一张对比报告
                        │
                        └─ 选型结论：这个场景该选谁、为什么
设计原则：记录并控制可控变量。 固定 prompt、系统指令、工具、输出上限、rubric、运行次数和预算；厂商参数不一定相同，不能强求同一 temperature。对非确定系统要重复运行，报告分布与失败案例，而不是把一次结果全归因给模型。

2. Step 1 · Token 计数与成本估算（复用 L18）

先算钱，但不能用一个 tokenizer 假装精确覆盖所有厂商。tiktoken 可在本地对匹配 OpenAI 编码计数；Claude 请求应调用官方 messages.count_tokens 估算完整消息结构，真正调用后再用 response usage 对账。下面本地示例只演示 OpenAI 编码下的估算算法。

pip install tiktoken        # 或 uv pip install tiktoken

import tiktoken

# 取一个编码器（o200k_base 对应较新的 OpenAI 系模型）
enc = tiktoken.get_encoding("o200k_base")

def count_openai_tokens(text: str) -> int:
    """对 o200k_base 编码本地计数；不代表 Claude/Google 账单。"""
    return len(enc.encode(text))

# 单价用「示例」值：真实价格请查各厂商官网，这里只演示算法
# 单位：美元 / 每百万 token（输出通常是输入的 3~5 倍，见 L23）
PRICE = {
    # 模型名: (输入价/百万, 输出价/百万)  —— 均为示例，非真实报价
    "model-a": (3.0, 15.0),
    "model-b": (0.5,  1.5),
}

def estimate_cost(prompt: str, model: str, est_output_tokens: int = 300) -> float:
    """估算单次调用成本：输入按实际数，输出按经验预估。"""
    in_price, out_price = PRICE[model]
    in_tokens = count_openai_tokens(prompt)
    cost = (in_tokens * in_price + est_output_tokens * out_price) / 1_000_000
    return cost

# —— 试跑 ——
prompt = "用一句话解释什么是向量数据库。"
for m in PRICE:
    print(m, "输入token=", count_openai_tokens(prompt),
          "单次≈$", round(estimate_cost(prompt, m), 6))

这段代码直接可运行。输出会长这样（token 数是本地 tiktoken 实算的，金额是示例单价算出来的；不同 tiktoken 版本可能有 ±1 的差异）：

model-a 输入token= 10 单次≈$ 0.00453
model-b 输入token= 10 单次≈$ 0.000455

同一段文本在两个示例价目下成本不同；真正比较厂商时，必须先换成各自的计数方式与单价。Claude 的请求前计数形状如下（会调用免费计数端点，因此需要有效认证，但不产生模型输出费用）：

import anthropic

client = anthropic.Anthropic()
count = client.messages.count_tokens(
    model="claude-opus-4-8",
    messages=[{"role": "user", "content": prompt}],
)
print(count.input_tokens)  # 请求前估算；实际调用后再看 response.usage
⚠️ 三层边界：①匹配 OpenAI 编码时，tiktoken 可离线计数；②Claude count_tokens 按指定模型和完整请求结构估算，但官方仍允许与实际用量有小幅差异；③最终成本以真实响应的 usage、缓存字段和厂商账单为准。
Q 跨厂商估算 Token 时，哪种做法最可靠？
OpenAI 匹配编码可用 tiktoken；Claude 用 messages.count_tokens 估算完整请求，调用后再看 response.usage。跨厂商共用一个 tokenizer 只能粗估，不能冒充精确账单。

3. Step 2 · 调用模型对比（复用 L15 / L16 / L17）

“统一调用模型”不等于“所有厂商共用同一 JSON”。正确做法是给每个 provider 写 adapter，统一的是你自己的返回结构，厂商认证、请求字段和 usage 解析留在各自 adapter 内。

Claude adapter（官方 Anthropic SDK）：

pip install anthropic

from anthropic import AsyncAnthropic

async def call_claude(client: AsyncAnthropic, prompt: str) -> dict:
    response = await client.messages.create(
        model="claude-opus-4-8",
        max_tokens=1_024,
        thinking={"type": "adaptive"},
        output_config={"effort": "medium"},
        messages=[{"role": "user", "content": prompt}],
    )
    text = "".join(block.text for block in response.content if block.type == "text")
    return {
        "provider": "anthropic",
        "model": response.model,
        "prompt": prompt,
        "output": text,
        "input_tokens": response.usage.input_tokens,
        "output_tokens": response.usage.output_tokens,
    }

若接 OpenAI 风格 API，应在另一个 adapter 中使用它自己的官方 SDK，并在那里解析 choices / 对应 usage；不要让中立业务层知道这些厂商字段，也不要把它们当成 Anthropic Messages API 的响应结构。

无 key 的离线 adapter：

import asyncio

async def mock_call(prompt: str, model: str) -> dict:
    await asyncio.sleep(0)
    output = f"[MOCK-{model}] {prompt[:12]}"
    return {
        "provider": "mock", "model": model, "prompt": prompt,
        "output": output,
        "input_tokens": len(prompt),   # 仅为 mock 占位，不是模型 token
        "output_tokens": len(output),
    }

async def run_matrix(prompts, models, call) -> list[dict]:
    sem = asyncio.Semaphore(5)
    async def one(prompt, model):
        async with sem:
            return await call(prompt, model)
    return await asyncio.gather(*[
        one(prompt, model) for model in models for prompt in prompts
    ])

这里的 call 就是 adapter 接口。离线练习传 mock_call；真实 Claude 环境可包装 call_claude。并发器只依赖统一 dict，因此增加 provider 时不需要改评测流程。

公平对比要固定 prompt、系统指令、工具、最大输出、effort/采样策略和重复次数。若某模型不支持另一个模型的参数（当前 Claude Opus 4.8 就不接受 temperature），记录差异并比较各自推荐配置，不能为了“字段一样”发送无效请求。
Q 跨厂商模型评测中，Provider Adapter 应统一什么？
Adapter 隔离认证、请求字段、响应内容块和 usage 差异，向评测流程返回统一的中立结构。统一厂商原始 JSON 会让代码在换 provider 时直接出错。

4. Step 3 · 幻觉测试（复用 L19）

能力测完，再测可靠性。题库必须有可核对的 ground truth 或证据：不存在对象由权威检索确认，实时问题用带时间戳的来源，精确计算交给代码工具。Self-Consistency 只观察输出是否稳定；发散是风险信号，一致仍可能一致地错。

下面的 mock 故意为三个模型安排稳定、部分一致和发散样本，因此无 key 也能真正跑到三条分支：

import asyncio

SCRIPTED = {
    "model-stable": ["查无可靠资料"] * 5,
    "model-mixed": ["查无资料", "查无资料", "论文A", "查无资料", "论文B"],
    "model-unstable": ["论文A", "论文B", "论文C", "论文D", "论文E"],
}

async def mock_sample(question: str, model: str, sample_index: int) -> dict:
    await asyncio.sleep(0)
    output = SCRIPTED[model][sample_index]
    return {"provider": "mock", "model": model, "prompt": question,
            "output": output, "input_tokens": len(question),
            "output_tokens": len(output)}

async def self_consistency(question: str, model: str, n: int = 5) -> list[str]:
    rows = await asyncio.gather(*[
        mock_sample(question, model, i) for i in range(n)
    ])
    return [row["output"] for row in rows]

def normalize_answer(text: str) -> str:
    return "".join(ch.lower() for ch in text.strip() if ch.isalnum())

def judge_consistency(answers: list[str]) -> str:
    unique = {normalize_answer(answer) for answer in answers}
    if len(unique) == 1:
        return "一致（仍需核对真伪）"
    if len(unique) >= max(2, len(answers) - 1):
        return "发散（高风险）"
    return "部分一致（需复核）"

async def demo():
    question = "介绍学者张无极在拓扑量子场论上的代表作。"
    for model in SCRIPTED:
        answers = await self_consistency(question, model)
        print(model, judge_consistency(answers))

asyncio.run(demo())
model-stable 一致（仍需核对真伪）
model-mixed 部分一致（需复核）
model-unstable 发散（高风险）

评分表要把稳定性和事实正确性分成两列：

模型     | 题型       | 一致性筛查       | 真值/证据核对 | 最终标签
---------|------------|------------------|---------------|---------
model-a  | 不存在对象 | 一致             | 正确弃权      | 正确
model-a  | 精确计算   | 部分一致         | 数值错误      | 错误
model-b  | 不存在对象 | 发散             | 多次编造      | 错误

发散率 = 发散样本数 / 总样本数       （稳定性指标）
错误率 = ground truth 判错数 / 总样本数（事实指标）

归一化只能减少“3.14”与“3.14。”这类格式差异，不能把语义不同的回答自动判成同一事实。生产评测应按题型使用解析器、业务数据库、检索证据或人工 rubric，并保留原始回答方便复核。

⚠️ 回顾 L19：预训练统计错误与评估激励是重要机制，但不是所有错误的唯一来源。体检要按题型报告发散率、事实错误率、拒答率和证据覆盖；一个模型可能很稳定，却稳定地给出错误答案。

5. Step 4 · 生成综合报告

把质量、ground-truth 错误率、成本和运行信息汇总。每个指标必须说明样本数和评测方法，不能把一次 toy run 当成模型排名：

def build_report(models, quality, error_rate, cost_per_1k, runs) -> list[dict]:
    return [
        {"model": model,
         "quality": quality[model],
         "error_rate": error_rate[model],
         "cost_per_1k": cost_per_1k[model],
         "runs": runs[model]}
        for model in models
    ]

示例表只演示形态；所有模型名、分数和价格都是虚构值：

模型      | 平均质量(0~10) | 事实错误率 | 每千次成本($) | 运行数
----------|----------------|------------|---------------|-------
model-a   | 8.6            | 12%        | 4.54          | 30
model-b   | 7.4            | 21%        | 0.46          | 30
model-c   | 9.1            |  9%        | 9.80          | 30

这些数值不是任何真实模型的 benchmark 或报价，不能用于生产选型。

这张表把三门课变成了一眼能比的东西。关键是它逼你同时看三列——只看质量会选最贵的，只看成本会选最不靠谱的。真正的决策发生在下一节：怎么综合这三列做选择。

🧪 进阶挑战：用 LLM-as-judge 自动给质量打分（点开看思路）

上表的"平均质量"如果全靠人工评，量大了就评不动。L19 提过 LLM-as-judge：让一个（通常更强的）模型当裁判，按固定 rubric 给每个输出打分。思路草图：

# 让裁判模型按统一标准打分，减少人工
JUDGE_PROMPT = """你是评审。请按以下标准给「回答」打 0~10 分，只输出数字：
- 事实正确性(0~4)  - 完整性(0~3)  - 清晰度(0~3)
问题：{q}
回答：{a}"""

async def llm_judge(question, answer, judge_model, call) -> float | None:
    prompt = JUDGE_PROMPT.format(q=question, a=answer)
    out = (await call(prompt, judge_model))["output"]
    try:
        score = float(out.strip().split()[0])
        return score if 0 <= score <= 10 else None
    except (ValueError, IndexError):
        return None       # 解析失败是“待复核”，不能伪装成 0 分

三个坑要记住：①裁判本身也会幻觉/有偏好，别把它当绝对真理，重要结论仍要抽样人工核对；②别让模型给自己打分（自评偏高），用不同/更强的模型当裁判；③rubric 要固定且明确，否则分数不可比——这跟 L22 说的"benchmark 要看评测方法"是一个道理。（另一个可选进阶：给 Step 1 加上 Prompt Caching 前后成本对比，把长 system prompt 缓存起来看省多少——见 L23。）

6. 选型结论（复用 L22 / L23）

报告有了，怎么从三列数字走到"就用它"？用 L22 的决策框架：先明确场景对三维的敏感度，再据此加权。同一张表，不同场景会选出不同模型——这才是重点。看三个示范推理（沿用上表的示例数字）：

场景最看重示范推理选择
医疗/法律问答 事实可靠性硬门槛 先设事实错误率、引用覆盖和人工升级硬门槛；示例中 model-c 仅进入下一轮验证。 model-c（候选）
海量内容分类 成本 ≫ 质量 先满足类别准确率/召回率门槛；若 model-b 通过，再利用低成本优势。 model-b（达标后）
通用客服助手 三者平衡 先定义满意度、事实错误和升级人工阈值；示例权重下 model-a 可继续 A/B。 model-a（候选）

看出来了吗——同一张体检表，选出了三个不同的模型。这正是选型的本质：没有"最好的模型"，只有"最适合这个场景的模型"。

质量是 0–10、错误率是百分比、成本是美元，不能直接相加。先在候选集合内 min-max 归一化，再加权：

def minmax(value, values, *, lower_is_better=False):
    low, high = min(values), max(values)
    score = 1.0 if high == low else (value - low) / (high - low)
    return 1.0 - score if lower_is_better else score

def pick_model(report, weights):
    qualities = [row["quality"] for row in report]
    errors = [row["error_rate"] for row in report]
    costs = [row["cost_per_1k"] for row in report]
    scores = {}
    for row in report:
        scores[row["model"]] = (
            weights["quality"] * minmax(row["quality"], qualities)
            + weights["reliability"] * minmax(
                row["error_rate"], errors, lower_is_better=True)
            + weights["cost"] * minmax(
                row["cost_per_1k"], costs, lower_is_better=True)
        )
    return max(scores, key=scores.get), scores

best, scores = pick_model(
    report, {"quality": 0.4, "reliability": 0.5, "cost": 0.1}
)

归一化只解决量纲问题：候选集合变化会改变分数，极端值也会扭曲尺度。生产中还应先设置硬门槛（如法律问答错误率不得超过阈值），淘汰不合格候选后再加权。

最容易犯的错：只看一个维度。 只看 benchmark 分数 → 可能选了个贵到用不起、还爱编造的模型；只看价格 → 可能选了个便宜但不靠谱、返工成本更高的。L23 提醒过：真正的成本是"总拥有成本"——包括幻觉导致的返工、人工复核。永远把能力 + 幻觉 + 成本放在一起权衡，这就是这份体检报告存在的意义。

  • Step 3：Self-Consistency 只筛稳定性风险；事实错误率必须通过 ground truth、证据或人工 rubric 判断
  • Step 4：记录样本数和重复运行；不同量纲先归一化，硬门槛通过后再加权
  • 总拥有成本还包括重试、误路由、人工复核和错误影响；toy 表格不能直接用于生产拍板
