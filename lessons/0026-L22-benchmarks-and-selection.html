看懂 Benchmark 与模型选型

厂商都吹自己第一——你得会自己判断，因为"跑分高≠适合你的场景"

💡 为什么这课重要？

你要给 Agent 选一个"大脑"（LLM）。打开任何一家厂商的发布页，全是"SOTA""第一""超越对手"的跑分图。如果你不会读 benchmark，就只能被营销牵着走。而更危险的是反过来——盲目相信榜单：跑分第一的模型，放到你的业务上可能拉胯。

这一课教你两件事：看懂主流 benchmark 各测什么（MMLU / GPQA / SWE-bench / ARC-AGI），以及为什么榜单会失真（数据污染、过拟合、场景不匹配）。最后给你一套能落地的选型决策框架。核心口号先记住："别信榜单，信你自己的评测集；别记版本号，记决策方法。" 选型直接决定 Agent 的能力上限、成本和延迟——这一步选错，后面全是补丁。

学习目标

完成本课后，你将能够：

  • 说清 MMLU / GPQA / SWE-bench / ARC-AGI 各测的是什么能力
  • 理解为什么"跑分高≠适合你"——尤其是数据污染和过拟合榜单
  • 权衡开源 vs 闭源：托管便利 vs 数据主权 / 成本拐点
  • 用一套可落地的决策框架为具体项目选模型
  • 回答面试高频题："你怎么给项目选模型？""跑分高就是最好吗？"

1. 为什么要会读 Benchmark

Benchmark（基准测试）就是一套标准化考卷：给所有模型出同一批题，按得分排名。它的价值在于横向可比——否则你只能听厂商各说各话。

但读 benchmark 有一条铁律贯穿全课：

跑分高  ≠  适合你的场景

  · benchmark 测的是"通用考卷"，不是"你的业务题"
  · 厂商挑对自己有利的榜单展示（幸存者偏差）
  · 分数可能"虚高"（下一节：数据污染）

所以正确的姿势不是"背哪个模型第一"，而是学会自己判断一份跑分说明了什么、没说明什么。对 Agent 开发者，这直接关系到你给 Agent 挑的大脑是真强，还是只会考试。

2. 主流 Benchmark 各测什么

不同 benchmark 测的是完全不同的能力维度。选型时要看"和你任务相关的那个"，而不是笼统的"综合分"。下面这张表是必背的地图（出处：Lumichats: AI Benchmarks Explained 与 Nanonets: GPQA / SWE-bench / Chatbot Arena）：

Benchmark测什么能力形式 / 特点
MMLU广度学术知识覆盖多学科的选择题；测"知道多少"。注意：已高度饱和 + 是数据污染的典型案例——正因如此才有了 MMLU-Pro
MMLU-Pro广度知识（更难）MMLU 升级版：更难、更抗猜（选项更多、更需推理）
GPQA专家级科学推理研究生级物理/化学/生物，Google 都难搜到答案，必须真推理
SWE-bench
(含 Verified)		软件工程 / Agent 编码真实 GitHub issue，能否真修 bug / 写 PR；Agent 硬指标，无背题捷径
ARC-AGI抽象推理 / 举一反三对训练里没见过的新模式的泛化能力
Chatbot Arena
(Elo)		人类偏好人类盲评两两对比→ Elo 排名；但偏爱"长而自信"的回答，可被"讨好"

对 Agent 开发者最关键的是 SWE-bench（尤其 Verified）：它直接测"能不能真的干活修代码"，比"选择题得高分"更贴近 Agent 的真实工作。而 MMLU/GPQA 高，说明模型"知识广、会推理"，但不代表它会用工具、会规划。看 benchmark 先问：它测的维度是我 Agent 需要的那个吗？

Q 你在做一个自动修 bug、提 PR 的编码 Agent，最该重点看哪个 benchmark？
SWE-bench（含 Verified）用真实 GitHub issue 考"能否真正修 bug / 写 PR"，没有背题捷径，是 Agent 编码能力最贴切的硬指标。MMLU 测知识广度、ARC-AGI 测抽象泛化、Chatbot Arena 测人类偏好——都不直接反映"会不会动手改代码"。选型第一问永远是：这个 benchmark 测的维度，是我的 Agent 真正需要的吗？

3. 榜单为什么会失真（重点，资深必问）

这一节是初级和资深的分水岭。"跑分高"和"真的强"之间，隔着三道坑：

① 数据污染 / 泄漏（contamination / data leakage）——最隐蔽、也最要命。如果 benchmark 的题目和答案混进了模型的训练数据，那模型就是"背过答案"，而非真会做——分数虚高。学界有专门的 survey 综述这个问题（A Survey on Data Contamination for LLMs），核心结论一句话：模型"无意中在训练里见过测试题"，会产出不能反映真实能力的成绩。也有会议论文系统研究其影响（OpenReview: Data Contamination）。

② 过拟合榜单（benchmark gaming）——厂商针对性优化去刷分：专门在类似题型上训练、调 prompt、挑对自己有利的评测方式。结果是"应试能力"上去了，通用能力未必。

③ 与你的场景不匹配——benchmark 测的是通用任务（学术题、公开 issue），≠ 你的业务任务（你公司的内部合同、你特定领域的黑话）。榜单第一，到你这儿可能水土不服。

所以业界的判断是：benchmark 有用，但"不足以"单独决定选型。有分析指出实验室跑分和真实部署表现之间存在明显落差，光看静态榜单不可靠，生产上线需要分层评测（自动指标 + LLM 评审 + 人工把关）（Kili: Why Benchmarks Are Not Enough）。

⚠️ 一句话记住失真的三坑：污染（背过答案，分数虚高）、过拟合（针对性刷分）、不匹配（考卷≠你的业务）。看到某模型"某榜第一"，先问：这榜有没有被污染？是不是被专门优化过？它测的任务像不像我的任务？
Q 某模型 benchmark 分数虚高，最隐蔽的原因通常是？
这是数据污染 / 泄漏（data contamination / leakage）：benchmark 的题目或答案无意中进入了训练语料，模型是"背过答案"而非真会做，于是分数虚高、不反映真实能力（见 contamination survey）。参数量、算力、上下文窗口都不是"虚高"的成因。防坑办法：优先用自建的、外部拿不到的小评测集去实测。

4. 开源 vs 闭源：怎么权衡

选型的第二个大决策：用闭源托管 API，还是开源自托管？（下面用"…系"表述，不写死具体版本号——版本天天变，决策逻辑不变。）

维度闭源（GPT / Claude / Gemini 系）开源（Llama / Qwen / DeepSeek 系）
接入简单，调 API 即用，官方托管要自己部署、搭推理服务
能力前沿闭源模型在部分高难维度常暂时领先差距快速收窄，部分场景已够用甚至反超
数据要出境（发到厂商服务器）可自托管，数据不出境
可控性不可微调底座，随厂商更新可微调、可固定版本，完全可控
成本按 token 付费，用多少付多少自己扛 GPU 运维；只有高用量才划算

关键的"成本拐点"概念：自托管有固定的 GPU / 运维成本。低于某个月用量，闭源 API 反而更便宜（你没把机器跑满，固定成本摊不下去）；只有当月调用量足够大、把机器吃满，自托管的单位成本才低于 API。所以"开源省钱"是有条件的——先估用量，再谈划算。（成本的详细算法见下一课 L23 · Token 经济学。）

对 Agent 开发者的落地判断：数据敏感 / 不能出境 / 用量大 / 要微调 → 倾向开源自托管；追求最强能力 / 快速起步 / 用量不大 / 不想养运维 → 倾向闭源 API。

💡 "开源一定更省钱"是新手常见误区。真相：自托管有成本拐点——用量不够大时，闭源 API 更便宜（省下你养 GPU 和运维的钱）。开源的核心优势其实是数据主权 + 可控 + 可微调，"省钱"只在高用量时才成立。

5. 选型决策框架（可落地）

把前面所有东西串成一个能照着走的清单。别再"看哪个榜第一就用哪个"，按这个流程走：

模型选型 · 五步决策流

① 明确任务 ──────► 任务类型？质量要求多高？
                    (问答 / 编码 / 规划 / 抽取…；容错空间多大)

② 看相关 benchmark ► 只看和你任务相关的维度 (如编码看 SWE-bench)
        │            ⚠️ 警惕污染/过拟合 → 榜单只作"初筛参考"
        ▼
③ 自建小评测集 ───► 用你真实业务样本，外部拿不到的题
        │            ← 这才是"信自己的评测集"的落地做法
        ▼
④ 估算成本 & 约束 ► token量 × 单价 (对照 L23)
        │            + 延迟 / 上下文窗口 / 数据合规 / 是否需自托管
        ▼
⑤ 小规模 A/B 实测 ► 用候选模型跑真实流量的一小部分，比数据再定
                    (别凭跑分拍板，凭你自己的实测结果拍板)

整个框架的灵魂是第③步和第⑤步：自建评测集 + 小规模 A/B。厂商的榜单会污染、会过拟合，但你用真实业务样本、亲手跑出来的数据不会骗你。这也是为什么资深工程师从不"背模型排名"——他们背的是这套方法。

核心口号（贴墙上）：「别信榜单，信你自己的评测集；别记版本号，记决策方法。」模型版本三个月一换，但这套框架永远适用。

Q 按本课决策框架，为项目定模型最可靠的"临门一脚"是？
框架的灵魂是自建评测集 + 小规模 A/B 实测：用你真实业务样本（外部拿不到、不会被污染的题）亲手跑候选模型、比数据再拍板。榜单排名会被污染/过拟合、也未必匹配你的场景；"最热门""参数最大"都不等于最适合你。口号：别信榜单，信你自己的评测集。

6. 选型 × Agent：为什么这一步是地基

对 Agent 而言，选模型不是"选个聊天机器人"，而是选整个系统的能力天花板：

  • 能力上限：模型不会规划 / 不会用工具，Agent 再多脚手架也救不回来。
  • 成本：Agent 一次任务常调几十次 LLM，模型单价 × 调用次数 = 真金白银。
  • 延迟：模型慢，Agent 的每一步都慢，多步任务体验直接崩。

还有一个进阶技巧：不同子任务用不同模型——贵的强模型做规划 / 难推理，便宜的小模型做简单步骤 / 格式化。这叫 model routing，是 Agent 降本的核心杠杆之一（详见 L23）。所以"选型"在 Agent 里往往不是选一个模型，而是设计一套模型组合。

🧭 Agent 场景练习（先自己想，再展开对照）：
场景：为公司做一个"内部合同问答 Agent"。数据是内部合同，高度敏感、绝不能出境；预算有限；但月调用量很大（全公司天天用）。你怎么选模型？用本课框架给建议。

参考决策（走五步框架）：

  • 数据合规是硬约束 → 敏感合同不能出境，直接排除闭源托管 API，倾向开源自托管（Llama / Qwen / DeepSeek 系），数据留在自己机房。
  • 用量大 → 成本拐点站在开源这边：月调用量很大能把 GPU 吃满，自托管的单位成本低于按 token 付费；正好也契合"预算有限"。（用量若很小，结论会反过来。）
  • 任务是合同问答（有领域黑话）→ 通用 benchmark 参考价值有限，必须自建评测集：拿真实合同问答样本（外部拿不到）当考卷，才测得准。可考虑在开源底座上微调 / RAG 贴合合同领域。
  • 别忘了其他约束： 上下文窗口要够（合同长）、延迟可接受、以及验证数据确实不出境。
  • 临门一脚： 选 2~3 个开源候选，用自建评测集做小规模 A/B，比准确率 + 成本 + 延迟，再拍板。

一句话结论：倾向开源自托管 + 自建合同评测集 + 认真核算成本拐点——敏感数据 + 高用量 + 有限预算，几乎就是开源自托管的教科书场景。

总结

  • 跑分高 ≠ 适合你——会读 benchmark，是为了不被营销牵着走，也为了不盲信榜单
  • 不同 benchmark 测不同维度：MMLU 广度、GPQA 专家推理、SWE-bench 编码(Agent 硬指标)、ARC-AGI 抽象泛化
  • 榜单会失真：数据污染（背过答案）、过拟合刷分、场景不匹配——benchmark "不足以"单独定选型
  • 开源 vs 闭源：闭源省事常领先但数据出境；开源可控不出境，但只有高用量才越过成本拐点
  • 选型五步：任务 → 相关 benchmark → 自建评测集 → 成本/延迟/合规 → 小规模 A/B
🎤 面试高频："你怎么给一个项目选模型？" 满分回答走框架——明确任务 → 看相关 benchmark（警惕污染）→ 自建评测集实测 → 权衡成本/延迟/合规/上下文窗口 → 小规模 A/B 再定。"benchmark 高就是最好吗？" → 不。可能有数据污染、针对性过拟合，或测的任务根本不匹配你的业务；要以自己的评测集实测为准。
