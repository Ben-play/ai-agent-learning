第二阶段 · AI 知识与模型选型 60分钟

看懂 Benchmark 与模型选型

厂商都吹自己第一——你得会自己判断，因为"跑分高≠适合你的场景"

💡 为什么这课重要？

你要给 Agent 选一个"大脑"（LLM）。打开任何一家厂商的发布页，全是"SOTA""第一""超越对手"的跑分图。如果你不会读 benchmark，就只能被营销牵着走。而更危险的是反过来——盲目相信榜单：跑分第一的模型，放到你的业务上可能拉胯。

这一课教你两件事：看懂主流 benchmark 各测什么（MMLU / GPQA / SWE-bench / ARC-AGI），以及为什么榜单会失真（数据污染、过拟合、场景不匹配）。最后给你一套能落地的选型决策框架。核心口号先记住："别信榜单，信你自己的评测集；别记版本号，记决策方法。" 选型直接决定 Agent 的能力上限、成本和延迟——这一步选错，后面全是补丁。

学习目标

完成本课后，你将能够：

  • 说清 MMLU / GPQA / SWE-bench / ARC-AGI 各测的是什么能力
  • 理解为什么"跑分高≠适合你"——尤其是数据污染和过拟合榜单
  • 区分开放权重、自托管与托管 API，从部署、合规和总成本而非标签做选择
  • 用一套可落地的决策框架为具体项目选模型
  • 回答面试高频题："你怎么给项目选模型？""跑分高就是最好吗？"

1. 为什么要会读 Benchmark

Benchmark（基准测试）就是一套标准化考卷：给所有模型出同一批题，按得分排名。它的价值在于横向可比——否则你只能听厂商各说各话。

但读 benchmark 有一条铁律贯穿全课：

跑分高  ≠  适合你的场景

  · benchmark 测的是"通用考卷"，不是"你的业务题"
  · 厂商挑对自己有利的榜单展示（幸存者偏差）
  · 分数可能"虚高"（下一节：数据污染）

所以正确的姿势不是"背哪个模型第一"，而是学会自己判断一份跑分说明了什么、没说明什么。对 Agent 开发者，这直接关系到你给 Agent 挑的大脑是真强，还是只会考试。

2. 主流 Benchmark 各测什么

不同 benchmark 测的是完全不同的能力维度。选型时要看"和你任务相关的那个"，而不是笼统的"综合分"。下面这张表是必背的地图（出处：Lumichats: AI Benchmarks Explained 与 Nanonets: GPQA / SWE-bench / Chatbot Arena）：

Benchmark测什么能力形式 / 特点
MMLU广度学术知识覆盖多学科的选择题；测"知道多少"。注意：已高度饱和 + 是数据污染的典型案例——正因如此才有了 MMLU-Pro
MMLU-Pro广度知识（更难）MMLU 升级版：更难、更抗猜（选项更多、更需推理）
GPQA专家级科学推理研究生级物理/化学/生物，Google 都难搜到答案，必须真推理
SWE-bench
(含 Verified)		软件工程 / Agent 编码真实 GitHub issue 上生成补丁并通过测试；结果同时受模型、Agent 版本、scaffold、工具与预算影响
ARC-AGI抽象推理 / 举一反三对训练里没见过的新模式的泛化能力
Chatbot Arena
(Elo)		人类偏好人类盲评两两对比→ Elo 排名；但偏爱"长而自信"的回答，可被"讨好"

如果你在做编码 Agent，SWE-bench（尤其 Verified）比学术选择题更贴近“在仓库中生成补丁并通过测试”的目标。但它评的是整个系统：同一个模型搭配不同 Agent 版本、scaffold、工具、上下文和预算，结果可能不同。MMLU/GPQA 高也不代表会使用你的工具或适应你的仓库。看 benchmark 先问：它测的任务、系统配置和资源预算，是否像我的场景？

Q 你在做一个自动修 bug、提 PR 的编码 Agent，最该重点看哪个 benchmark？
SWE-bench（含 Verified）使用真实 GitHub issue 和测试来评估生成补丁的能力，比知识选择题更接近编码 Agent。但公开 issue/补丁存在污染风险，成绩还依赖 Agent scaffold、工具与预算，因此它是相关证据，不是脱离配置的“模型真值”。

3. 榜单为什么会失真（重点，资深必问）

这一节是初级和资深的分水岭。"跑分高"和"真的强"之间，隔着三道坑：

① 数据污染 / 泄漏（contamination / data leakage）——最隐蔽、也最要命。如果 benchmark 的题目和答案混进了模型的训练数据，那模型就是"背过答案"，而非真会做——分数虚高。学界有专门的 survey 综述这个问题（A Survey on Data Contamination for LLMs），核心结论一句话：模型"无意中在训练里见过测试题"，会产出不能反映真实能力的成绩。也有会议论文系统研究其影响（OpenReview: Data Contamination）。

② 过拟合榜单（benchmark gaming）——厂商针对性优化去刷分：专门在类似题型上训练、调 prompt、挑对自己有利的评测方式。结果是"应试能力"上去了，通用能力未必。

③ 与你的场景不匹配——benchmark 测的是通用任务（学术题、公开 issue），不等于你的业务任务（内部合同、领域黑话、特定工具链）。榜单第一，到你这里可能水土不服。

④ Harness / scaffold 与预算不一致——Agent benchmark 测的不只是底座模型。系统提示词、工具、重试次数、上下文管理、推理 effort、时间和 Token 预算都会改变结果。比较榜单时必须核对配置，不能把“Agent A + 模型 X”的成绩直接归因给模型 X。

因此 benchmark 有用，但不足以单独决定选型。生产评测至少要分层：确定性任务用程序指标；开放回答用固定 rubric 的人工/模型评审；高风险样本由人工把关；非确定系统还要重复运行并报告均值、失败案例或方差。

⚠️ 一句话记住四坑：污染、针对性优化、场景不匹配、harness/预算不同。看到“某榜第一”，先问测试是否公开、系统配置是否可比、运行是否重复、任务是否像你的业务。
Q 某模型 benchmark 分数虚高，最隐蔽的原因通常是？
这是数据污染 / 泄漏（data contamination / leakage）：benchmark 的题目或答案无意中进入了训练语料，模型是"背过答案"而非真会做，于是分数虚高、不反映真实能力（见 contamination survey）。参数量、算力、上下文窗口都不是"虚高"的成因。防坑办法：优先用自建的、外部拿不到的小评测集去实测。

4. 开放权重、托管 API 与自托管：三个维度别混在一起

“开源模型 vs 闭源模型”经常把许可证、权重可得性和部署方式混成一件事。很多常被称为“开源”的 LLM 更准确地说是开放权重（open weights）：可以下载权重，但训练数据、训练代码或许可证未必满足完整开源定义；开放权重也可以由云厂商托管，并不等于必须自建 GPU。

维度托管 API开放权重 / 自托管候选
接入厂商维护服务，按 API 使用可自己部署，也可选择第三方托管
能力按具体模型和任务评测，不能只看“闭源”标签同样按模型、量化、推理框架和任务评测
合规看部署地域、合同、数据保留、训练使用、访问控制自托管可增强数据控制，但安全与合规责任转给自己
可控性版本和功能由服务方管理，可通过版本固定能力降低漂移通常可固定权重、量化或微调，但受许可证约束
成本按 Token / 请求付费，少运维GPU、闲置率、峰值容量、能耗、工程与值班都计入总成本

合规不能简化为“托管 = 出境”。同一厂商可能提供不同地域、云平台、保留策略和合同条款；“不能出境”也要先定义适用司法辖区与组织要求。反过来，自托管并不会自动合规——身份权限、日志、补丁、备份和供应链都由你负责。

成本拐点必须测量。估算真实吞吐、上下文长度、峰谷流量、GPU 利用率、延迟目标、运维人力和故障冗余，再与 API 账单比较。高用量可能有利于自托管，但量化模型、批处理 API、预留容量或低利用率都可能改变结论。

💡 满分判断不是“敏感数据就开源、高用量就自托管”，而是：先列不可违反的合规/部署约束，再在可行候选里比较任务质量、总拥有成本和运维风险。

5. 选型决策框架（可落地）

把前面所有东西串成一个能照着走的清单。别再"看哪个榜第一就用哪个"，按这个流程走：

模型选型 · 五步决策流

① 明确任务 ──────► 任务类型？质量要求多高？
                    (问答 / 编码 / 规划 / 抽取…；容错空间多大)

② 看相关 benchmark ► 只看和你任务相关的维度 (如编码看 SWE-bench)
        │            ⚠️ 警惕污染/过拟合 → 榜单只作"初筛参考"
        ▼
③ 自建小评测集 ───► 用你真实业务样本，外部拿不到的题
        │            ← 这才是"信自己的评测集"的落地做法
        ▼
④ 估算成本 & 约束 ► token量 × 单价 (对照 L23)
        │            + 延迟 / 上下文窗口 / 数据合规 / 是否需自托管
        ▼
⑤ 小规模 A/B 实测 ► 用候选模型跑真实流量的一小部分，比数据再定
                    (别凭跑分拍板，凭你自己的实测结果拍板)

整个框架的灵魂是自建评测集 + 小规模 A/B，但自建集也会被你自己过拟合。最低限度要做到：

  • 开发集 / 测试集分开：用开发集调 prompt、阈值和路由；最终测试集保持隔离，不边看答案边修改。
  • 固定版本与预算：记录模型 ID、系统提示词、工具、scaffold、effort、Token/时间上限。
  • 固定 rubric：先写清正确性、完整性、引用、格式怎样计分；高风险项单独设硬门槛。
  • 重复运行：非确定任务至少多跑几次，报告均值与失败案例，别把一次好运当能力。

真实业务样本更相关，但只有遵守这些规则，结果才比公开榜单更可信。

核心口号（贴墙上）：「别信榜单，信你自己的评测集；别记版本号，记决策方法。」模型版本与榜单会持续变化，但这套决策框架可以复用。

最佳实践：公开榜单只初筛，固定开发集调优，隔离留出集拍板

适用：公开 benchmark 能缩小候选范围，但业务质量必须由私有样本决定，且 prompt、阈值或路由还需要调优。不适用：一次性低风险试验只需粗略可行性判断时，可先做小型 smoke test，但不能把它写成生产结论。本卡只决定候选模型的业务验收顺序，不同时决定部署地域或成本架构。

❌ 同一接口，公开分最高者直接胜出
def select_model(public_scores, dev_scores, holdout_scores):
    return max(public_scores, key=public_scores.get)

开发集与隔离留出集虽已提供，却完全没参与决策；结果只是复述公开排名。

✅ 同一接口，初筛→开发→留出
def select_model(public_scores, dev_scores, holdout_scores):
    candidates = screen(public_scores, floor=0.80)
    tuned = tune_on_dev(candidates, dev_scores)
    return decide_on_holdout(tuned, holdout_scores)

榜单只排除明显不相关候选；调参只看固定开发集，最终胜者只由未参与调优的业务留出集决定。

为什么更优：先用公开证据低成本筛选，再把配置调优限制在开发集，最后由隔离留出集估计泛化表现，因此选择更相关、可复现，也减少看答案调参造成的乐观偏差。真实成本是准备标注、维护隔离、重复运行与人工复核；若留出样本过少或业务分布变化，就补充新样本并重新验收；若只有低风险探索预算，可先用公开榜单 + 少量 smoke test，但一旦要上线或比较接近候选，就切换到开发/留出分离。

边界：公开榜单是外部初筛证据；开发集允许反复查看并调 prompt/阈值；隔离留出集在配置冻结后才用于最终决定，不能回流参与本轮调优。

动手自检（纯标准库；离线、确定性、通过时静默）
from inspect import signature


def screen(public_scores, *, floor):
    return [name for name, score in public_scores.items() if score >= floor]


def tune_on_dev(candidates, dev_scores):
    return {
        name: max(dev_scores[name], key=dev_scores[name].get)
        for name in candidates
    }


def decide_on_holdout(tuned, holdout_scores):
    return max(
        tuned,
        key=lambda name: holdout_scores[(name, tuned[name])],
    )


def select_model(public_scores, dev_scores, holdout_scores):
    candidates = screen(public_scores, floor=0.80)
    tuned = tune_on_dev(candidates, dev_scores)
    return decide_on_holdout(tuned, holdout_scores)


public = {"atlas": 0.92, "birch": 0.84, "cedar": 0.70}
dev = {
    "atlas": {"brief": 0.73, "evidence": 0.78},
    "birch": {"brief": 0.82, "evidence": 0.86},
}
holdout = {
    ("atlas", "evidence"): 0.71,
    ("birch", "evidence"): 0.89,
}

assert max(public, key=public.get) == "atlas"
assert screen(public, floor=0.80) == ["atlas", "birch"]
assert tune_on_dev(["atlas", "birch"], dev) == {
    "atlas": "evidence", "birch": "evidence"
}
assert list(signature(tune_on_dev).parameters) == ["candidates", "dev_scores"]
assert select_model(public, dev, holdout) == "birch"
assert holdout[("birch", "evidence")] > holdout[("atlas", "evidence")]

失败诊断：胜者仍是 atlas 表示公开榜单越权拍板；tune_on_dev 出现 holdout 参数表示留出集泄漏进调优；cedar 进入调优表示初筛门槛无效；开发配置不是 evidence 表示调优逻辑错误；留出排名不能反转公开排名则 fixture 没有证明私有评测能改变决定。

Q 按本课决策框架，为项目定模型最可靠的"临门一脚"是？
用真实业务样本建立开发集 + 隔离测试集，固定模型版本、scaffold、工具、预算和 rubric，并对非确定任务重复运行。这样才能减少调参泄漏和一次好运的影响；榜单、热度和参数量只能帮助初筛。

6. 选型 × Agent：为什么这一步是地基

对 Agent 而言，选模型不是"选个聊天机器人"，而是选整个系统的能力天花板：

  • 能力上限：模型不会规划 / 不会用工具，Agent 再多脚手架也救不回来。
  • 成本：Agent 一次任务常调几十次 LLM，模型单价 × 调用次数 = 真金白银。
  • 延迟：模型慢，Agent 的每一步都慢，多步任务体验直接崩。

还有一个进阶技巧：不同子任务用不同模型——贵的强模型做规划 / 难推理，便宜的小模型做简单步骤 / 格式化。这叫 model routing，是 Agent 降本的核心杠杆之一（详见 L23）。所以"选型"在 Agent 里往往不是选一个模型，而是设计一套模型组合。

🧭 Agent 场景练习（先自己想，再展开对照）：
场景：为公司做一个"内部合同问答 Agent"。数据是内部合同，高度敏感、绝不能出境；预算有限；但月调用量很大（全公司天天用）。你怎么选模型？用本课框架给建议。

参考决策（走五步框架）：

  • 先把“不能出境”写成可验证约束：适用地域、允许的云/机房、数据保留与日志要求、哪些字段必须脱敏。不要先用“闭源/开源”标签替代合规审查。
  • 建立可行部署候选：若合同明确禁止外部托管，就比较内部自托管方案；若允许合规地域或私有云托管，也可纳入满足合同与保留要求的 API / 托管开放权重方案。
  • 合同问答必须自建评测集：划分开发集与隔离测试集，固定引用准确率、漏答率、幻觉率和拒答策略。RAG 通常用于提供合同证据，是否微调取决于领域行为/格式需求。
  • 成本用真实负载测：对 2~3 个可行候选压测吞吐、P95 延迟、GPU 利用率、API Token、运维人力与冗余；月调用量大只是自托管可能占优的信号，不是结论。
  • 小规模 A/B 再拍板：只有同时满足合规硬门槛，才比较质量、总拥有成本与运维风险。

一句话结论：先满足可审计的合规硬约束，再用隔离评测集与真实负载比较可行部署。自托管可能胜出，但必须由证据得出，而不是由“敏感 + 高用量”标签自动推出。

🎯 速查卡：读榜与选型

【铁律】跑分高 ≠ 适合你的场景

【benchmark 地图 · 各测什么】
  MMLU / MMLU-Pro …… 广度学术知识 (Pro=更难更抗猜)
  GPQA ……………… 专家级科学推理 (Google 都搜不到答案)
  SWE-bench(Verified) 真实 GitHub issue + 测试；成绩依赖模型+scaffold+工具+预算
  ARC-AGI ………… 抽象推理 / 举一反三 (没见过的新模式)
  Chatbot Arena … 人类盲评偏好 Elo (偏爱"长而自信")

【榜单为什么失真 · 四坑】
  ① 数据污染  ② 针对性优化  ③ 场景不匹配
  ④ harness/scaffold/工具/预算不同
  → benchmark 是系统在特定配置下的证据，不是模型真值

【开放权重 / 托管 / 自托管】
  开放权重描述权重可得性，不自动等于完整开源或自托管
  托管合规看地域/合同/保留/访问；自托管责任转给自己
  成本拐点必须测 GPU 利用率、峰值、能耗、运维与冗余

【选型五步】
  ①明确任务 → ②相关 benchmark 初筛 → ③开发集调参+隔离测试集
  → ④固定版本/scaffold/预算/rubric → ⑤重复运行 + 小规模 A/B

【口号】别信榜单信你自己的评测集；别记版本记决策方法
【Agent】选型=能力上限+成本+延迟；贵模型做规划,便宜模型做简单步骤

本课最佳实践验收：保修工单的私有评测

先独立为保修工单候选模型设计公开初筛、固定开发集与隔离留出集；参考 fixture 会故意让私有留出结果反转公开排名。

操作清单

  1. 按公开分数门槛初筛候选。
  2. 在留出对象尚不存在时，只用开发集选择 prompt。
  3. 冻结配置后才创建隔离留出集并决定胜者。
  4. 记录调优读取的数据来源与留出评估次数。
  5. 只打印最终验收标记。
通过标准
  • 公开排名第一是 atlas。
  • 未过门槛的 cedar 不参与调优。
  • 开发集为候选冻结配置。
  • 留出集最终选择 birch，明确反转公开排名。
  • 标准输出只有验收标记。

    return [model for model, score in scores.items() if score >= minimum]

阶段实践检查点：私有评测驱动的执行策略

在新的理赔分流域，把 L21 能力约束、L20 评测驱动的最低 effort 与本课开发/留出隔离组合起来：先剔除能力不合格候选，再用开发集选择最低达标 effort，冻结后才让留出集拍板。

操作清单

  1. 先剔除不能满足实时保单查询或精确金额计算的候选。
  2. 对每个可行候选，只在开发集上筛选质量与延迟门。
  3. 从达标 trials 中选择最低 effort，并保留质量、延迟与输出 Token 证据。
  4. 冻结配置后才创建留出集，且只评估一次。
通过标准
  • 缺少工具能力的公开高分候选被剔除。
  • 高质量但超延迟的 effort 不入选；达标时不盲选最高档。
  • 冻结配置包含所选 trial 的质量、延迟和输出 Token。
  • 调优时留出对象尚不存在；隔离留出能反转剩余候选公开排名。
  • 标准输出只有检查点标记。

参考验收程序（独立完成后展开，纯标准库）
from dataclasses import dataclass


ORDER = ("low", "medium", "high")


@dataclass(frozen=True)
class Candidate:
    name: str
    public_score: float
    augmentation: str


@dataclass(frozen=True)
class Trial:
    effort: str
    quality: float
    latency_ms: int
    output_tokens: int


def capability_filter(candidates):
    return [candidate for candidate in candidates if candidate.augmentation == "tool"]


def tune_effort(candidates, development, reads, *, min_quality, max_latency_ms):
    reads.append("development")
    chosen = {}
    for candidate in candidates:
        eligible = [
            trial for trial in development[candidate.name]
            if trial.quality >= min_quality and trial.latency_ms <= max_latency_ms
        ]
        if not eligible:
            raise ValueError(f"no effort trial passes for {candidate.name}")
        chosen[candidate.name] = min(
            eligible,
            key=lambda trial: ORDER.index(trial.effort),
        )
    return chosen


def decide(configurations, holdout, evaluations):
    evaluations.append("holdout")
    return max(
        configurations,
        key=lambda name: holdout[(name, configurations[name].effort)],
    )


candidates = [
    Candidate("fast-public-leader", 0.96, "none"),
    Candidate("atlas", 0.91, "tool"),
    Candidate("birch", 0.85, "tool"),
]
development = {
    "atlas": (
        Trial("low", 0.84, 300, 110),
        Trial("medium", 0.91, 620, 220),
        Trial("high", 0.96, 910, 410),
    ),
    "birch": (
        Trial("low", 0.86, 260, 100),
        Trial("medium", 0.92, 580, 205),
        Trial("high", 0.95, 760, 370),
    ),
}
reads = []
evaluations = []

feasible = capability_filter(candidates)
configurations = tune_effort(
    feasible,
    development,
    reads,
    min_quality=0.90,
    max_latency_ms=800,
)
frozen = tuple(sorted(configurations.items()))
assert reads == ["development"]
assert "holdout" not in globals()

holdout = {
    ("atlas", "medium"): 0.75,
    ("birch", "medium"): 0.91,
}
winner = decide(dict(frozen), holdout, evaluations)

assert [candidate.name for candidate in feasible] == ["atlas", "birch"]
assert configurations["atlas"] == Trial("medium", 0.91, 620, 220)
assert configurations["birch"] == Trial("medium", 0.92, 580, 205)
assert all(trial.effort != "high" for trial in configurations.values())
assert all(trial.output_tokens > 0 for trial in configurations.values())
assert evaluations == ["holdout"]
assert max(feasible, key=lambda item: item.public_score).name == "atlas"
assert winner == "birch"

print("P2 CHECKPOINT PRIVATE-EVALUATION PASSED")

结果诊断：fast-public-leader 未被剔除表示能力硬约束失效；低 effort 未达质量仍入选或 high 超延迟仍入选，表示 effort 门失效；选中最高档而 medium 已达标表示没有选择最低可行投入；配置未保留 output_tokens 表示投入证据丢失；调优前已有 holdout、冻结后评估多次或最终仍选公开领先者，表示留出隔离/决定权失效。

总结

  • 跑分高 ≠ 适合你——会读 benchmark，是为了不被营销牵着走，也为了不盲信榜单
  • 不同 benchmark 测不同维度；SWE-bench 更贴近仓库修复，但成绩属于模型 + Agent scaffold + 工具 + 预算的组合
