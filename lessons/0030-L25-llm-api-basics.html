主流 LLM API 上手

OpenAI / Anthropic / Google 三家，一套心智模型全搞定

💡 为什么这课重要？

Phase 2 你搞懂了 LLM 是什么、怎么选、怎么算钱。现在开始真正把它调起来。Agent 的每一次"思考"，本质都是一次 LLM API 调用——这是你后面所有工程能力的原点。

好消息：虽然有三大厂商（OpenAI / Anthropic / Google），但它们的请求心智模型几乎一样——都是「发一串 messages，收一条回复」。学会一家，另外两家半小时就能上手。这一课我们用真实 SDK 的正确写法（已核对 openai 2.x / anthropic 0.x），并教你一个让代码"一次写好、随处可换"的关键技巧。

学习目标

完成本课后，你将能够：

  • 用 messages 数组（system / user / assistant 角色）表达一次对话
  • 用 openai / anthropic 两个官方 SDK 各发一次请求
  • 从环境变量读 API Key（绝不硬编码）
  • 用 OpenAI 兼容模式（base_url）一套代码切换不同厂商
  • 知道 OpenAI 的 Chat Completions vs Responses API 之别

1. 统一心智模型：messages 进，message 出

无论哪家，一次基础调用都是这个形状：你发一个消息列表，模型回一条新消息。消息有角色：

[
  {"role": "system",    "content": "你是一个简洁的助手。"},   # 设定行为（可选）
  {"role": "user",      "content": "用一句话解释向量数据库。"}, # 用户说的话
  # 模型会回一条 {"role": "assistant", "content": "..."}
]
  • system：设定模型的角色 / 规则（整段对话的"人设"，见 L04 Prompt 构造）。
  • user：用户的输入。
  • assistant：模型的历史回复——多轮对话时，你要把之前的往返都放回列表里，模型才有记忆（它本身无状态，见 L21）。

记住这个形状，你就掌握了 90% 的 API 调用。剩下的都是参数细节。

Q 多轮对话里，模型怎么"记得"前面聊过什么？
LLM 本身无状态（L21）——它不记得任何跨请求的东西。多轮对话要"有记忆"，靠的是你每次把之前的 user/assistant 往返都塞回 messages 列表再发出去。这也是为什么对话越长、输入 Token 越多、越费钱（L18/L23）。

2. OpenAI：Chat Completions

最经典、最通用的接口。Key 从环境变量读（SDK 默认会找 OPENAI_API_KEY）：

pip install openai        # 或 uv pip install openai
# 运行前：export OPENAI_API_KEY="sk-..."（Windows: setx）

from openai import OpenAI

client = OpenAI()   # 自动读环境变量 OPENAI_API_KEY，别把 key 写进代码

resp = client.chat.completions.create(
    model="gpt-5.5",                # 具体型号以官网为准，别写死在生产逻辑里
    messages=[
        {"role": "system", "content": "你是一个简洁的助手。"},
        {"role": "user",   "content": "用一句话解释向量数据库。"},
    ],
    temperature=0.3,                # 见 L17：要稳就调低
)

print(resp.choices[0].message.content)   # ← 回复文本在这里
print(resp.usage)                        # ← Token 用量（算成本用，L23）

两个你每次都会用到的字段：resp.choices[0].message.content（回复正文）和 resp.usage（prompt_tokens / completion_tokens，直接对应 L23 的成本公式）。

OpenAI 的两个接口：老牌的 chat.completions（全行业通用、兼容性最好）和较新的 responses（Responses API，OpenAI 现在主推、对推理模型体验更好）。本课教 chat.completions——因为它是跨厂商的"普通话"，学会它最迁移友好；Responses API 作为 OpenAI 的新方向了解即可（官方迁移指南）。

3. Anthropic：Messages API

Claude 用 client.messages.create。形状几乎一样，但有两个关键差异：

pip install anthropic
# 运行前：export ANTHROPIC_API_KEY="sk-ant-..."

from anthropic import Anthropic

client = Anthropic()   # 自动读 ANTHROPIC_API_KEY

resp = client.messages.create(
    model="claude-sonnet-4-6",       # 型号以官网为准
    max_tokens=1024,                 # ← 差异①：Anthropic 必填 max_tokens
    system="你是一个简洁的助手。",     # ← 差异②：system 是顶层参数，不放 messages 里
    messages=[
        {"role": "user", "content": "用一句话解释向量数据库。"},
    ],
)

print(resp.content[0].text)          # ← 回复在 content[0].text（不是 choices）
print(resp.usage)                    # input_tokens / output_tokens

记住这两个坑：① max_tokens 必填（OpenAI 选填）；② system 是独立顶层参数，不像 OpenAI 塞进 messages。回复也从 content[0].text 取，不是 choices。

Q 从 OpenAI 换到 Anthropic，下面哪个差异是真的？
Anthropic 的两个关键差异：system 提示是独立的顶层参数（不放进 messages），且 max_tokens 必填。返回结构也不同——Claude 从 content[0].text 取回复，OpenAI 从 choices[0].message.content。角色（user/assistant）两家都用，消息也照发。

4. 关键技巧：OpenAI 兼容模式，一套代码切三家

每家一套 SDK 太累。业界的通用解法：大多数厂商 / 网关都提供「OpenAI 兼容」端点——你继续用 openai 这一个 SDK，只改 base_url 和 key，就能打到别家模型。

from openai import OpenAI

# 还是 openai SDK，只是把 base_url 指向别的厂商 / 网关
client = OpenAI(
    api_key="...",                              # 对应厂商的 key
    base_url="https://api.anthropic.com/v1/",   # ← 换成目标厂商的兼容端点
)

# 之后 client.chat.completions.create(...) 照常用，业务代码基本不动

这就是 L32 的 AI Gateway（LiteLLM）能"一个接口统一 100+ 模型"的底层原理——统一成 OpenAI 的调用格式。你现在只需记住：换厂商 ≈ 换 base_url + key，业务代码几乎不动。Anthropic 官方也提供 OpenAI SDK 兼容层（OpenAI SDK compatibility）。

⚠️ 兼容模式很方便，但不是 100% 等价——各家独有的高级特性（如 Claude 的 Extended Thinking、某些参数）在兼容层下可能用不了。快速多模型对比、简单调用→ 兼容模式；要吃满某家的独门能力→ 用它自己的原生 SDK。

5. 铁律：Key 永远走环境变量

你可能注意到上面所有例子都没有把 key 写进代码。这是不可退让的工程纪律：

  • 绝不硬编码 key 到源码里——一旦 push 到 GitHub 就是泄露，会被爬虫秒扫、盗刷。
  • 用环境变量：os.environ["OPENAI_API_KEY"]，或让 SDK 自动读（它默认就找这个变量）。
  • 本地开发用 .env 文件（L01 学过），并把 .env 加进 .gitignore。
import os
from openai import OpenAI

# 显式读（找不到就早失败，比默默出错好）
api_key = os.environ["OPENAI_API_KEY"]   # 没设会抛 KeyError，一眼看出问题
client = OpenAI(api_key=api_key)

这不是小题大做——本课程自己的仓库就因为要 push GitHub，专门把带 key 的配置做了 gitignore + 环境变量注入。key 泄露是 AI 工程最常见、最贵的事故之一。

Q API Key 应该怎么放进代码？
Key 永远从环境变量读（或 SDK 自动读），绝不硬编码进源码。硬编码 + push 到 GitHub = 秒级泄露被盗刷。本地用 .env + .gitignore。这是 AI 工程最基本也最容易翻车的安全纪律。

🎯 速查卡：三家 API

【统一心智模型】发 messages 列表 → 收一条 assistant 消息
  role: system(人设) / user(输入) / assistant(历史回复)
  ★ 模型无状态：多轮要把历史全塞回 messages

【OpenAI · Chat Completions】
  client = OpenAI()                        # 读 OPENAI_API_KEY
  r = client.chat.completions.create(model=..., messages=[...])
  回复: r.choices[0].message.content   用量: r.usage

【Anthropic · Messages】
  client = Anthropic()                     # 读 ANTHROPIC_API_KEY
  r = client.messages.create(model=..., max_tokens=必填,

  回复: r.content[0].text

【差异速记】
  max_tokens: OpenAI 选填 / Anthropic 必填

  • 一次调用 = 发 messages 列表（system/user/assistant），收一条回复
