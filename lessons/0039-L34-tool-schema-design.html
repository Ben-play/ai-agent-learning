Tool Schema 设计

工具定义就是模型的"说明书"——写好 Tool Schema 是 Agent 基本功

💡 为什么这课重要？

L27 你学了 Function Calling 的原理：模型不直接执行工具，而是输出一个"想调哪个工具、参数填什么"的结构化请求。但模型凭什么知道有哪些工具、每个工具干嘛、参数怎么填？——全靠你给的工具定义（Tool Schema）。

这就是本课的灵魂：Schema 的质量直接决定模型用不用得对。模型看不到你的函数实现，它只能看到 name / description / 参数 schema 这几行字来做决策。描述写得烂，模型就选错工具、填错参数——再强的模型也救不回来。Tool Schema 设计是"提示工程"在工具层的延伸，也是 Agent 能力的天花板。这一课把你在 L14 Pydantic 学的 model_json_schema() 真正用到刀刃上。

学习目标

完成本课后，你将能够：

  • 说清"工具定义 = 模型的说明书"：模型只凭 name/description/参数 schema 做决策
  • 用 Pydantic 定义参数、model_json_schema() 一键导出工具 schema
  • 写出好的 description——让模型知道"何时用、参数填什么"
  • 用 enum / Literal 约束取值、用 strict mode 保证格式严格符合 schema
  • 控制工具数量与描述长度，省 input token

1. 工具定义 = 模型的"说明书"

先建立最核心的心智模型。你写的工具是这样一个函数：

def get_order_status(order_id: str) -> dict:
    # ...真实实现：查数据库、调物流 API...
    return {...}

但模型看不到这段实现。传给模型的、模型唯一能读到的，只有一份"工具定义"——一段 JSON：

{
  "type": "function",
  "name": "get_order_status",        # ← 模型据此决定"调不调"
  "description": "查询用户订单的当前物流状态。", # ← 模型据此决定"什么时候调"
  "parameters": {                    # ← 模型据此决定"参数填什么"
    "type": "object",
    "properties": {
      "order_id": {"type": "string", "description": "订单号，如 'ORD-2026-0007'"}
    },
    "required": ["order_id"]
  }
}

所以一句话：模型是靠"读说明书"来决定用不用、怎么用这个工具的。说明书写得清楚，模型就用得对；写得含糊，模型就选错工具、填错参数、甚至该调不调。这不是模型笨——是你没把话说清楚。

Q 模型靠什么决定"要不要调某个工具、参数怎么填"？
模型看不到函数实现，也不会预先运行工具。它唯一的依据是你传入的工具定义（name + description + 参数 schema）。这几行字就是模型的全部信息——所以描述质量直接决定模型选得对不对、填得准不准。这正是本课的灵魂。

2. 用 Pydantic / JSON Schema 定义参数

手写 parameters 那坨 JSON 又累又容易错。业界标准做法：用 Pydantic 定义参数，再 model_json_schema() 一键导出（呼应 L14——LangChain、OpenAI SDK、Pydantic AI 内部都这么做）。

from pydantic import BaseModel, Field

class GetOrderStatus(BaseModel):
    """查询用户订单的当前物流状态。"""     # ← docstring 会进 schema 的顶层 description
    order_id: str = Field(
        ...,                              # ... 表示必填（见 L14）
        description="订单号，用户提供的完整编号，如 'ORD-2026-0007'",
    )

# 一键导出为工具参数 schema
GetOrderStatus.model_json_schema()
# {
#   'type': 'object',
#   'properties': {
#     'order_id': {'type': 'string',
#                  'description': "订单号，用户提供的完整编号，如 'ORD-2026-0007'"}
#   },
#   'required': ['order_id'],
#   'description': '查询用户订单的当前物流状态。'
# }

关键点：每个字段都用 Field(description=...) 写清含义。这个 description 会进 JSON Schema，成为模型理解"这个参数填什么"的唯一依据。把它拼进工具定义：

tool = {
    "type": "function",
    "name": "get_order_status",
    "description": GetOrderStatus.__doc__,               # 顶层：这个工具干嘛
    "parameters": GetOrderStatus.model_json_schema(),    # 参数：每个字段干嘛
}
🔑 Agent 开发关联：

Pydantic 不只帮你导出 schema，还在工具执行前把模型返回的参数（一坨不可控的 JSON）校验一遍——类型不对、缺必填字段立刻抛错，而不是让脏参数流进你的函数（呼应 L14"跨信任边界就用 Pydantic"）。导出 schema + 校验入参，一个模型两头用。

3. description 如何影响模型选择（本课重点）

这是全课最该背下来的一节。description 直接决定模型选得对不对，有三个层面：

① 工具的 description 要说清"这个工具什么时候用"。别只写工具是什么，要写它的用途和边界——尤其当你有多个相似工具时，模型全靠 description 区分该选哪个。

② 每个参数的 description 要说清"填什么、什么格式"。给出格式、单位、示例。看这组"坏 vs 好"对比：

❌ 坏描述（模型只能瞎猜）
  query: "string"

✅ 好描述（模型知道填什么、什么格式、给了例子）
  query: "用户的搜索关键词，自然语言，如 '2026 最佳轻薄笔记本'"

坏描述里 "string" 是废话——模型早知道它是字符串，它不知道的是"该塞用户原话还是提炼过的关键词"。好描述把这些全讲明白了。

③ 用 enum / Literal 约束取值（呼应 L14 的 Literal）。取值有限就别让模型自由发挥，直接列出合法值：

from typing import Literal
from pydantic import BaseModel, Field

class QueryOrders(BaseModel):
    """按状态筛选并列出用户的订单。"""
    status: Literal["pending", "shipped", "delivered", "cancelled"] = Field(
        ..., description="要筛选的订单状态"
    )
# 导出的 schema 里 status 会带 "enum": ["pending","shipped","delivered","cancelled"]
# → 模型只会从这 4 个里选，不会瞎编 "in_transit" 这种你代码里没有的值

Literal 导出成 JSON Schema 的 enum，模型只能在你给的选项里挑——从源头杜绝"编一个不存在的枚举值"。

Q 下面哪个参数 description 写得更好？
好的参数 description 要告诉模型它不知道的东西：该填什么内容、什么格式，最好给个例子。"是个字符串""必填""传给搜索函数"这些要么是废话、要么模型从 schema 已经知道了。只有"用户搜索词 + 示例"真正帮模型判断该塞什么进去——这直接提升调用准确率。

4. strict mode：让参数严格符合 schema

就算 description 完美，模型偶尔还是会漏字段、填错类型、多塞个你没定义的参数。strict mode（约束解码）从机制上根治这点——开启后，模型的输出被约束到只能生成符合 schema 的参数，而不是"尽力而为"。

tool = {
    "type": "function",
    "name": "get_order_status",
    "description": "查询用户订单的当前物流状态。",
    "strict": True,                              # ← 开启严格模式
    "parameters": {
        "type": "object",
        "properties": {"order_id": {"type": "string", "description": "订单号"}},
        "required": ["order_id"],
        "additionalProperties": False,           # strict 要求：禁止多余字段
    },
}

OpenAI 官方原话：strict 让 function call "reliably adhere to the function schema, instead of being best effort"，并建议始终开启。注意它的两条要求：所有对象要 additionalProperties: false、properties 里的字段都要列进 required（可选字段用"允许 null"来表达）。

同源机制：strict mode "works by leveraging our structured outputs feature"——它和你在 L28 Structured Outputs 学的约束解码是同一套底层技术。L28 用它保证"输出的 JSON 符合 schema"，这里用它保证"工具参数符合 schema"。一个机制，两处开花。来源：OpenAI · Function calling（strict mode）。

5. Token 成本：工具定义本身要花钱

容易被忽略的一点：工具定义会拼进每一次请求的 input，占 input token（呼应 L23 / L14）。每一轮对话，你注册的所有工具的 name + description + 参数 schema 都要发一遍。

  • 工具越多越贵：塞 40 个工具，这 40 份定义每轮都占 token，成本和延迟一起涨。
  • 描述越长越贵：description 要"讲清楚"但也要"精炼"，不是越啰嗦越好。
  • 工具太多还会降准确率：选项一多，模型更容易选错——省 token 和提准确率在这里是同一件事。

实战原则：只给当前任务相关的工具。别一股脑把系统里几十个工具全塞进去；按场景动态挑选一小撮，既省钱又选得准。

Q 关于工具定义的 token 成本，哪个说法对？
你注册的所有工具定义（name + description + 参数 schema）都会拼进每一轮请求的 input，无论是否被调用，都占 input token（L23）。所以工具越多、描述越长越贵，还会因选项过多降低选择准确率。对策：只给当前任务相关的一小撮工具，描述精炼。

6. 设计原则清单

把前面几节压缩成一份可直接照做的清单：

原则怎么做
名字动词化get_order_status / search_docs——动词开头，一看就知道"做什么"
description 讲清用途和边界写"什么时候用"，不只写"是什么"；多工具靠它区分
参数最少化只留必要参数；能有默认值的给默认值，减少模型要填的空
用 enum 约束取值有限就用 Literal/enum，杜绝模型编不存在的值
开 strict mode约束解码保证参数严格符合 schema
错误信息友好参数非法时返回模型读得懂的报错，让它能据此重试（埋点 L36）

最后一条尤其重要：工具报错不该是给人看的堆栈，而该是给模型看的、能指导它下一步怎么改的一句话（如"order_id 格式应为 ORD-年份-序号"）。这为 L36 的"工具健壮性 + 让模型自我纠错"铺路。

7. Agent 关联：工具设计是能力的天花板

把这一课放回 Agent 的大图里：Agent = 模型 + 一堆工具 + 循环（L35 讲循环）。而模型能做多少事，上限就卡在工具设计上：

  • 工具描述差 → 模型选错、填错 → 再强的模型也用不好你的工具。
  • 工具描述好 → 模型稳、准 → 一个中等模型也能把活干漂亮。

所以本课的定位是：Tool Schema 设计是"提示工程"在工具层的延伸。你花在打磨 description、约束取值、精简参数上的每一分功夫，都会直接变成 Agent 的可靠性。这是 P0 级的 Agent 基本功——不是可选的优化，是能不能跑通的前提。

实战练习

练习：设计"查订单状态"工具的 Schema

给你一个工具需求：查询订单状态。用 Pydantic 写出参数 schema，重点练好的 description 和 Literal 约束。要求：

  1. 参数 order_id：必填，写清格式并给示例
  2. 参数 detail_level：可选，只能是 "summary" 或 "full"，默认 "summary"（用 Literal 约束）
  3. 工具的顶层 description 要说清"什么时候用它"
  4. 调 model_json_schema() 导出，拼成完整工具定义

先自己写，再看答案。

💡 点击查看参考答案 
from typing import Literal
from pydantic import BaseModel, Field

class GetOrderStatus(BaseModel):
    """当用户询问某个订单的物流/发货状态时调用，返回该订单的当前状态。
    需要用户提供订单号；查询多个订单请多次调用。"""   # ← 讲清"何时用 + 边界"

    order_id: str = Field(
        ...,
        description="订单号，用户提供的完整编号，格式为 'ORD-年份-序号'，如 'ORD-2026-0007'",
    )
    detail_level: Literal["summary", "full"] | None = Field(
        None,
        description="返回详细程度（可选）：summary=只给当前状态；full=含完整物流轨迹；不填默认按 summary 处理",
    )

# 导出参数 schema（detail_level 会带 enum: ["summary","full"]）
params = GetOrderStatus.model_json_schema()

# 拼成完整工具定义
tool = {
    "type": "function",
    "name": "get_order_status",          # 动词化命名
    "description": GetOrderStatus.__doc__,
    "strict": True,                       # 严格模式保证格式
    "parameters": params,
}

# —— 校验演示：模型返回的参数进来先过一遍 Pydantic ——
GetOrderStatus(order_id="ORD-2026-0007")              # ✅ detail_level 默认 summary
GetOrderStatus(order_id="X", detail_level="verbose")  # ❌ ValidationError：不是合法枚举值

为什么这样写好？

  • 顶层 description 讲了何时用（用户问订单状态）和边界（多订单要多次调），模型不会误用。
  • order_id 给了格式 + 示例，模型不会填个乱七八糟的值。
  • detail_level 用 Literal 锁死取值，模型编不出 "verbose"；设成"允许 null"（| None）表达"可选"，这才是 strict 模式下表达可选字段的正确姿势（strict 要求所有字段都在 required 里，用 null 表达"不填"）。
  • 顺手拿同一个模型校验入参——脏参数在进函数前就被 Pydantic 拦下。
