第三阶段 · LLM API 工程实践 45分钟

Structured Outputs（约束解码）

正常完成且未拒答、未截断时保证符合受支持的 Schema 子集；事实与业务另验

💡 为什么这课重要？

Agent 的每一步都要把 LLM 的输出交给下游代码——存进数据库、拿去调 API、传给下一个节点。这些下游只吃结构化数据：字段名要对、类型要对、必填的不能少。可 LLM 生来输出的是自由文本，你写句"请返回 JSON"求它配合，它随时可能不听。

从纯 prompt 到 JSON mode，再到 Structured Outputs，保证逐步变强。仅对目标模型和接口支持的 JSON Schema 子集，在响应正常完成、没有拒答也没有截断时，Structured Outputs 才保证输出符合 Schema。本课接着用 L14 的 Pydantic 定义结构，再把格式、事实和业务许可分开验证。

学习目标

完成本课后，你将能够：

  • 分清 纯 prompt / JSON mode / Structured Outputs 三个层次各保证什么
  • 一句话说清 Structured Outputs ≠ JSON mode（这是面试送分/送命题）
  • 解释约束解码（constrained decoding）如何约束每一步可选的 token
  • 用 Pydantic 模型 + OpenAI parse 拿回一个已验证的对象
  • 知道兜底：不支持时退回"校验 + 重试"，并处理 refusal
保证之外：结构正确不代表事实正确、业务已授权或外部动作成功。JSON mode 也可能因输出耗尽而产生未完成内容。参见官方边界和第 5 节。

1. 问题：下游代码只吃可靠的结构化数据

设想 Agent 要从一段用户消息里抽出订单信息，交给 create_order(...)：

# 你只是"请求"模型返回 JSON —— 靠 prompt
resp = client.chat.completions.create(
    model="gpt-5.5",
    messages=[{"role": "user",
               "content": '把这句抽成 JSON：{"item": ..., "qty": ...}。原句：来两杯拿铁'}],
)
raw = resp.choices[0].message.content
data = json.loads(raw)          # ← 这一行随时可能炸
create_order(item=data["item"], qty=data["qty"])

这段代码脆在哪？模型完全可能：① 在 JSON 外面裹一句"好的，这是结果："——json.loads 直接抛异常；② 把 qty 写成 "两" 而不是 2——类型错；③ 干脆漏掉 item 字段——KeyError。

对 Agent 而言，输出格式不是"锦上添花"，而是能不能把这一步的结果接到下一步的硬前提。"请返回 JSON" 这种 prompt 层面的请求，在生产里不可靠——因为它没有任何机制拦住上面三种翻车。我们需要更强的保证。

Q Agent 为什么必须要"结构化"的 LLM 输出？
关键是下游：Agent 每一步的输出都要喂给代码（存库、调 API、传给下一节点），而代码只吃字段名对、类型对、必填齐的结构化数据。纯文本或"格式随缘"的 JSON 会让 json.loads / 字段访问随时炸。省 Token、便宜都不是重点——结构化输出有时反而多花 Token。

2. 三个层次：这是面试的分水岭

对正常完成、没有拒答且未截断的输出，分清三个强度递增的手段各保证什么：

方法保证什么可靠性
纯 prompt
（"请输出 JSON"）		 什么都不保证——只是请求模型配合 最弱 · 可能不听、裹废话、字段/类型全错
JSON mode 只保证输出是合法 JSON（能被 json.loads 解析）；不保证符合你的具体 schema 中 · 字段可能缺、类型可能错、可能多出字段
Structured Outputs
（strict mode / 约束解码）		 最强：对支持的 JSON Schema 子集，正常、未拒答且未截断的输出必须符合 Schema 强 · 约束字段、类型、必填、枚举等受支持规则

这三行请刻进脑子。面试官问"怎么保证 LLM 输出格式"，本质就是在考你分不分得清这三层。

🔑 一句话记牢：Structured Outputs ≠ JSON mode

JSON mode 约束 JSON 语法；Structured Outputs 还约束受支持的结构。前者给你的可能是 {"数量": "两杯", "note": "多加糖"}：能解码，却不符合下游要求的 item 和整数 qty。

Q 在正常完成、未拒答且未截断，并使用受支持的 Schema 子集时，Strict Structured Outputs 比 JSON mode 多保证什么？
在这些前提下，JSON mode 约束 JSON 语法，但字段仍可能缺失或类型错误；Structured Outputs 还保证符合指定的受支持 Schema。遇到拒答、截断或失败应另走分支，格式也不代替事实和业务校验。

3. 约束解码原理：为什么是"保证"而不是"求配合"

Structured Outputs 强在哪？强在它不靠"求模型听话"，而是从采样机制上动手。这个机制叫约束解码（constrained decoding，也叫 constrained sampling）。

回忆一下模型怎么生成文本（L21）：每生成一个 token，模型先给整个词表打分（logits），再从中采样出下一个。约束解码在这一步插了一手：

【普通生成】词表所有 token 都能被选中
   logits ──softmax──▶ 采样 ──▶ 任意 token（可能破坏结构）

【约束解码】先算出"此刻哪些 token 合法"，把非法 token 概率归零
   JSON Schema ──转成──▶ 语法(CFG) ──▶ 每一步的"合法 token 集合"

   logits[非法 token] = -∞      # 概率被压到 0，绝无可能被采样
   logits ──softmax──▶ 采样 ──▶ 只可能是"让结构依然合法"的 token

原理拆开看：把你的 JSON Schema 编译成一套语法（上下文无关文法 CFG），据此在生成的每一步算出"接下来只有哪些 token 能让输出仍然符合 schema"。所有不合法的 token，其 logits 被设为 -∞——softmax 之后概率是 0，根本不可能被采样出来。

这约束的是受支持语法中的生成路径，并不保证能走到终点：输出耗尽可以只留下合法前缀，拒答也不走这份 Schema。这和在 prompt 里仅仅请求一种格式不同。

🔑 Agent 开发关联：

工具参数、状态机更新、路由决策都依赖稳定的结构。约束解码减少了正常返回但格式错误的分支；是否执行工具、更新状态，仍由宿主校验并决定。

Q 对正常完成、未拒答且未截断的输出，约束解码怎样落实受支持的 Schema 规则？
约束解码把受支持的 Schema 转成生成规则，每一步都让破坏规则的 token 概率为零。它不依赖提示词语气，也不是生成后重写；拒答或输出耗尽仍不算正常完成的结构化答案。

4. 实操：配合 Pydantic，拿回已验证的对象

用 L14 的 Pydantic 模型定义结构。Chat Completions 的 Python SDK parse 会生成 strict Schema，并尝试在返回给应用之前解析。以下两块按顺序运行是可选联网对照；沿用 OPENAI_MODEL、凭证和预算约定，先确认模型和接口支持这份 Schema。

import os
from openai import ContentFilterFinishReasonError, LengthFinishReasonError, OpenAI
from pydantic import BaseModel, ValidationError

client = OpenAI()


def parse_chat(prompt, Model):
    try:
        completion = client.chat.completions.parse(
            model=os.environ["OPENAI_MODEL"],
            messages=[{"role": "user", "content": prompt}],
            response_format=Model,
        )
    except LengthFinishReasonError as exc:
        raise ValueError("Chat 输出截断") from exc
    except ContentFilterFinishReasonError as exc:
        raise ValueError("Chat 输出被内容过滤") from exc
    except ValidationError as exc:
        raise ValueError("Chat 返回无法通过 Pydantic 解析或校验") from exc

    choice = completion.choices[0]
    if choice.message.refusal:
        raise ValueError("模型拒答")
    if choice.finish_reason != "stop" or choice.message.parsed is None:
        raise ValueError("未得到可消费的完整结构化答案")
    return choice.message.parsed
class Order(BaseModel):
    item: str
    qty: int


order = parse_chat("从这句抽取订单：来两杯拿铁", Order)
if order.qty < 1:
    raise ValueError("数量不符合业务规则")
# 下单还需独立授权和幂等控制；这里只输出候选数据。
print(order.model_dump())

length 和 content_filter 可在调用 parse 时分别触发 SDK 异常；它们不是返回消息里的 refusal。只有 parse 成功返回，才能查 finish_reason、message.refusal 和 message.parsed。网络和 API 错误在此继续抛出，不当格式错误处理。qty 的最小值由本地业务规则判断，不假定所有模型都支持范围关键字。

※ 底层等价于给 chat.completions.create 传 response_format={"type": "json_schema", "json_schema": {..., "strict": True}} 且 additionalProperties: false；parse 只是帮你把这些 + Pydantic 解析都包好了。工具调用（Function Calling）里同理，在 tool 定义上加 strict: true。具体方法名 / 参数一律以官方文档为准。

🔑 Agent 开发关联：

在支持的接口上开启 strict 能约束工具输入的结构，但 Schema 不是执行权限，也不会自动执行 Python validator。仍应在 L36 的 dispatch 中做运行时校验、授权和业务检查；不要把“合法参数”误当成“允许执行”。

5. 兜底与坑：不是万能，要有 Plan B

Structured Outputs 很强，但工程上必须知道它的边界，并准备退路：

  • ① 不是所有模型 / 所有情况都支持。老模型、某些接口、或走 L25 的兼容层时可能没这能力。退路：验证 + 重试——照常让模型输出，拿 Pydantic 校验；ValidationError 了就把报错信息塞回 messages 让模型重试（"你上次 qty 不是整数，请修正"）。这就把 L14 的校验变成了自愈循环。
  • ② refusal（拒答）单独处理。Chat 在 parse 成功返回后查 message.refusal；Responses 查每个消息 Item 的内容块（第 6.1 节）。拒答不进入格式修正重试。
  • ③ schema 太复杂可能不支持。Structured Outputs 只覆盖 JSON Schema 的一个子集，过深的嵌套、某些高级关键字可能被拒。先查目标模型和接口，再选尽量扁平的结构。
  • ④ 截断、过滤和业务失败另行处理。Chat SDK 可能在返回对象前抛异常；Responses 则先看终态。仅对可恢复的格式错误做有界修正。格式通过不保证事实正确，入库和下单仍需授权与幂等。
from pydantic import ValidationError

# 用于不支持结构约束的接口。call_llm 由应用提供，仅返回通过终态/拒答检查的文本。
def ask_with_retry(prompt, Model, max_try=3):
    for _ in range(max_try):
        raw = call_llm(prompt)        # 普通调用，不保证格式
        try:
            return Model.model_validate_json(raw)   # Pydantic 校验
        except ValidationError as e:
            # 只回填位置和错误类型，不把可能含敏感值的完整异常原样发回。
            issues = [(error["loc"], error["type"]) for error in e.errors()]
            prompt += f"\n上次输出不合法：{issues}，请按 schema 修正"
    raise RuntimeError("重试仍无法得到合法结构")
🔑 Agent 开发关联（呼应 L19）：

L19 教过：对冲 LLM 的不确定性，靠结构化 + 校验。这里是它的落地——能约束就约束（Structured Outputs），不能约束就校验 + 重试（Pydantic）。Agent 的可靠性从来不是"信任模型",而是"在机制上不给它出错的机会,出了错也能自愈"。

💡 练习：从用户评论抽取结构化情感数据（点击查看参考答案）

场景：你的 Agent 要把一段用户评论抽成 {sentiment, score, keywords}。用 Pydantic 定义结构：sentiment 三选一，score 是数字，keywords 是字符串列表；另外在本地检查分数是否在 0 到 1 之间。沿用第 4 节的 SDK 异常和拒答分支，先自己写，再看答案。

参考答案

from typing import Literal
from pydantic import BaseModel


class Review(BaseModel):
    sentiment: Literal["positive", "negative", "neutral"]
    score: float
    keywords: list[str]


# 接在第 4 节 parse_chat 的定义后；异常和拒答处理沿用。
review = parse_chat("抽取情感：最近更新后的界面让我找不到需要的功能。", Review)
if not 0 <= review.score <= 1:
    raise ValueError("score 必须在 0 到 1 之间")
print(review.model_dump())

思考：若换成一个不支持 Structured Outputs 的模型，你会怎么改？（提示：用第 5 节的 model_validate_json + 带错重试兜底。）

🎤 面试高频：「如何保证 LLM 输出格式？」区分纯 prompt、仅约束语法的 JSON mode，以及约束受支持 Schema 子集的 Structured Outputs。结构保证以正常完成、未拒答且未截断为前提；接口不支持时，可做本地校验并对可恢复的格式问题有界重试。
变式追问：同一个合法候选在名额从 2 降到 1 后还能用吗？结构没变，业务结果变了；按当前余量复验，不能靠重试 JSON 解决。

6.1 Responses 对照与离线失败分支

L25 的 Responses 主线使用 text.format，不是 Chat 的 response_format。先确认响应状态、检查所有消息 Item 中的拒答，再将 output_text 解码并校验结构。无效 JSON 和合法 JSON 但结构错误是两类问题。

import json


class SchemaMismatch(ValueError):
    pass


def checked_answer(response, *, decode=json.loads):
    if response.status != "completed":
        raise ValueError(f"not completed: {response.status}")
    if any(part.type == "refusal" for item in response.output
           if item.type == "message" for part in item.content):
        raise ValueError("refused")
    data = decode(response.output_text)  # JSONDecodeError 表示文本不是合法 JSON
    if not isinstance(data, dict) or set(data) != {"summary"} or not isinstance(data["summary"], str):
        raise SchemaMismatch("summary must be the only field and must be a string")
    return data

误判：能解码就能下单

同一候选写着 {"item":"拿铁","qty":0}。它是合法 JSON，也符合两字段结构，却不是合法订单。

对照：结构通过后还要验数量

同一候选先过终态和拒答门槛，再解码、校验结构。随后在业务层拦住零数量；不提交订单。

取舍：多一个业务关口，但能区分解码失败、结构错误与业务不允许，避免无效修正或误操作；不能只靠模型输出保证授权。

  1. 跑本节的解码自检，观察非法 JSON、类型错误和零次解码。
  2. 做课末变式，在有效结构上只改变业务余量。

结果诊断：后置拒答触发解码说明终态守门过晚；名额不足仍放行则是业务规则缺失，不是 Schema 太宽就一定能解决。

本课最佳实践验收：正常解码的预约仍可能超额

已通过终态和拒答检查的文本仍需分类。活动还有两个名额；Schema 只要求对象仅含整数 seats。复制起点，实现 classify(raw, remaining)，区分 invalid_json、invalid_schema、outside_capacity 和 candidate。人数须在 1 到剩余名额之间；两席仅在还有两席时可接受，三席虽是整数也要拦住。只分类，不实际预约，不用前面的代码。

remaining = 2
raw_cases = ['{"seats":', '{"seats":"2"}', '{"seats":true}', '{"seats":3}', '{"seats":2}']

def classify(raw, remaining):
    try:
        data = json.loads(raw)
    except json.JSONDecodeError:
        return "invalid_json"
    if not isinstance(data, dict) or set(data) != {"seats"} or type(data["seats"]) is not int:
        return "invalid_schema"
    if not 1 <= data["seats"] <= remaining:
        return "outside_capacity"
    return "candidate"


observed = [classify(raw, remaining) for raw in raw_cases]
assert observed == ["invalid_json", "invalid_schema", "invalid_schema", "outside_capacity", "candidate"], observed
assert classify('{"seats":2}', remaining=1) == "outside_capacity"
print("L28 TRANSFER PASSED")

总结

  • Agent 每步输出都要喂下游代码，格式对 = 硬前提，"请返回 JSON" 靠 prompt 不可靠
  • 纯 prompt 只能请求格式；JSON mode 约束语法；Structured Outputs 通过约束解码保证受支持的结构，前提是响应正常完成且不拒答、不截断。
  • Chat SDK 可能先抛解析相关异常；Responses 则先检查终态和全部消息块，再自行解码并验证。
  • 结构正确不等于事实正确、业务可用或有权执行；不支持 strict 时做本地校验，只对可恢复的格式错误有界重试。
