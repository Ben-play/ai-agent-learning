第三阶段 · LLM API 工程实践 30分钟

Structured Outputs（约束解码）

让 LLM 的输出保证符合你给的 schema，而不是"希望它格式对"

💡 为什么这课重要？

Agent 的每一步都要把 LLM 的输出交给下游代码——存进数据库、拿去调 API、传给下一个节点。这些下游只吃结构化数据：字段名要对、类型要对、必填的不能少。可 LLM 生来输出的是自由文本，你写句"请返回 JSON"求它配合，它随时可能不听。

这一课教你把"求它配合"升级成"机制上保证"。核心是一个 2026 面试高频区分题：纯 prompt、JSON mode、Structured Outputs 是三个不同强度的层次——尤其 Structured Outputs ≠ JSON mode，这句话答错当场扣分。搞懂它，你就掌握了 Agent 可靠性的一根支柱。本课延续 L14 的 Pydantic——你已经会用它定义 schema，这里让那份 schema 真正"锁死"模型的输出。

学习目标

完成本课后，你将能够：

  • 分清 纯 prompt / JSON mode / Structured Outputs 三个层次各保证什么
  • 一句话说清 Structured Outputs ≠ JSON mode（这是面试送分/送命题）
  • 解释约束解码（constrained decoding）在 token 层面怎么做到"不可能违反 schema"
  • 用 Pydantic 模型 + OpenAI parse 拿回一个已验证的对象
  • 知道兜底：不支持时退回"校验 + 重试"，并处理 refusal

1. 问题：下游代码只吃可靠的结构化数据

设想 Agent 要从一段用户消息里抽出订单信息，交给 create_order(...)：

# 你只是"请求"模型返回 JSON —— 靠 prompt
resp = client.chat.completions.create(
    model="gpt-5.5",
    messages=[{"role": "user",
               "content": '把这句抽成 JSON：{"item": ..., "qty": ...}。原句：来两杯拿铁'}],
)
raw = resp.choices[0].message.content
data = json.loads(raw)          # ← 这一行随时可能炸
create_order(item=data["item"], qty=data["qty"])

这段代码脆在哪？模型完全可能：① 在 JSON 外面裹一句"好的，这是结果："——json.loads 直接抛异常；② 把 qty 写成 "两" 而不是 2——类型错；③ 干脆漏掉 item 字段——KeyError。

对 Agent 而言，输出格式不是"锦上添花"，而是能不能把这一步的结果接到下一步的硬前提。"请返回 JSON" 这种 prompt 层面的请求，在生产里不可靠——因为它没有任何机制拦住上面三种翻车。我们需要更强的保证。

Q Agent 为什么必须要"结构化"的 LLM 输出？
关键是下游：Agent 每一步的输出都要喂给代码（存库、调 API、传给下一节点），而代码只吃字段名对、类型对、必填齐的结构化数据。纯文本或"格式随缘"的 JSON 会让 json.loads / 字段访问随时炸。省 Token、便宜都不是重点——结构化输出有时反而多花 Token。

2. 三个层次：这是面试的分水岭

把 LLM 输出格式化，业界有三个强度递增的手段。务必分清它们各自保证什么：

方法保证什么可靠性
纯 prompt
（"请输出 JSON"）		 什么都不保证——只是请求模型配合 最弱 · 可能不听、裹废话、字段/类型全错
JSON mode 只保证输出是合法 JSON（能被 json.loads 解析）；不保证符合你的具体 schema 中 · 字段可能缺、类型可能错、可能多出字段
Structured Outputs
（strict mode / 约束解码）		 最强：在 token 生成层面保证输出严格符合你给的 JSON Schema 强 · 字段、类型、必填、枚举全部锁死

这三行请刻进脑子。面试官问"怎么保证 LLM 输出格式"，本质就是在考你分不分得清这三层。

🔑 一句话记牢：Structured Outputs ≠ JSON mode

JSON mode 只保证"是合法 JSON"，Structured Outputs 保证"符合你的 schema"。JSON mode 给你的可能是 {"数量": "两杯", "note": "多加糖"}——它是合法 JSON，但字段名、类型、结构全不对你的胃口，下游照样炸。OpenAI 官方原话："only Structured Outputs ensure schema adherence"（只有 Structured Outputs 保证符合 schema）。把这两个概念混为一谈，是这块最常见的错答。

Q JSON mode 和 Structured Outputs 的核心区别是？
JSON mode 只保证输出是合法 JSON（能解析），但不保证符合你的具体 schema——字段可能缺、类型可能错、可能多字段。Structured Outputs 额外保证严格符合你给的 JSON Schema。二者不是别名、也不是同一件事：官方明确"only Structured Outputs ensure schema adherence"。速度/成本不是区分点。

3. 约束解码原理：为什么是"保证"而不是"求配合"

Structured Outputs 强在哪？强在它不靠"求模型听话"，而是从采样机制上动手。这个机制叫约束解码（constrained decoding，也叫 constrained sampling）。

回忆一下模型怎么生成文本（L21）：每生成一个 token，模型先给整个词表打分（logits），再从中采样出下一个。约束解码在这一步插了一手：

【普通生成】词表所有 token 都能被选中
   logits ──softmax──▶ 采样 ──▶ 任意 token（可能破坏结构）

【约束解码】先算出"此刻哪些 token 合法"，把非法 token 概率归零
   JSON Schema ──转成──▶ 语法(CFG) ──▶ 每一步的"合法 token 集合"

   logits[非法 token] = -∞      # 概率被压到 0，绝无可能被采样
   logits ──softmax──▶ 采样 ──▶ 只可能是"让结构依然合法"的 token

原理拆开看：把你的 JSON Schema 编译成一套语法（上下文无关文法 CFG），据此在生成的每一步算出"接下来只有哪些 token 能让输出仍然符合 schema"。所有不合法的 token，其 logits 被设为 -∞——softmax 之后概率是 0，根本不可能被采样出来。

所以结论是机制级的：模型"不可能"生成不符合 schema 的输出——不是因为它乖，而是因为非法的路径在采样时被物理封死了。这和 prompt"请你务必按格式来"有本质区别：后者是请求，前者是约束。

🔑 Agent 开发关联：

"保证"这两个字对 Agent 是刚需。工具调用的参数、状态机的更新、路由的决策——这些输出一旦格式错，整条链就断。约束解码把"格式对不对"从一个概率问题（大概率对）变成确定性问题（一定对），这是 Agent 能稳定跑长链路的底层保障。

Q 约束解码为什么能"保证"符合 schema？
约束解码把 JSON Schema 编译成语法，在每一步生成时把"不符合 schema 的 token"的 logits 设为 -∞，softmax 后概率为 0，永远采样不到。所以模型不可能产出违反 schema 的输出。这是采样机制上的保证，既不靠 prompt 严厉，也不是"生成后再修"，更不是换个大模型就行。

4. 实操：配合 Pydantic，拿回已验证的对象

好消息：你不用手写 JSON Schema。L14 学的 Pydantic 模型可以直接当 schema 传给 API——OpenAI SDK 会自动导出 model_json_schema()、开启 strict、并把返回解析成 Pydantic 对象还给你。三步走：

from pydantic import BaseModel, Field
from openai import OpenAI

# ① 用 Pydantic 定义 schema（呼应 L14）—— 就是你想要的结构
class Order(BaseModel):
    item: str = Field(..., description="商品名")
    qty:  int = Field(..., ge=1, description="数量，至少 1")

client = OpenAI()   # key 走环境变量（L25），没 key 可 mock

# ② 传给 API：response_format 直接吃 Pydantic 模型
#    方法名 parse 以官方文档为准
completion = client.chat.completions.parse(
    model="gpt-5.5",
    messages=[{"role": "user", "content": "来两杯拿铁"}],
    response_format=Order,          # ← strict 约束解码在此开启
)

# ③ 拿回的是已验证的 Order 对象，不是字符串！
order = completion.choices[0].message.parsed
create_order(item=order.item, qty=order.qty)   # 放心直接用：类型/字段都已保证

和第 1 节的脆代码对比：那里是 json.loads(raw) 加一堆祈祷；这里 completion.choices[0].message.parsed 直接是结构正确的对象，order.qty 铁定是 int ≥ 1。约束解码保证结构、Pydantic 保证类型与业务约束，两层叠加。

※ 底层等价于给 chat.completions.create 传 response_format={"type": "json_schema", "json_schema": {..., "strict": True}} 且 additionalProperties: false；parse 只是帮你把这些 + Pydantic 解析都包好了。工具调用（Function Calling）里同理，在 tool 定义上加 strict: true。具体方法名 / 参数一律以官方文档为准。

🔑 Agent 开发关联：

这正是 L27 Function Calling 里"工具参数为什么可靠"的答案——真实框架在工具定义里开 strict，让模型填的参数保证符合工具的 Pydantic schema，你的工具函数才敢直接用这些参数。Structured Outputs 不只是"输出个 JSON"，它是整个工具调用链的可靠性地基。

5. 兜底与坑：不是万能，要有 Plan B

Structured Outputs 很强，但工程上必须知道它的边界，并准备退路：

  • ① 不是所有模型 / 所有情况都支持。老模型、某些接口、或走 L25 的兼容层时可能没这能力。退路：验证 + 重试——照常让模型输出，拿 Pydantic 校验；ValidationError 了就把报错信息塞回 messages 让模型重试（"你上次 qty 不是整数，请修正"）。这就把 L14 的校验变成了自愈循环。
  • ② refusal（拒答）要单独处理。模型可能因安全原因拒绝，此时它不会吐你要的 schema。strict 模式下会有独立的 refusal 字段——先判空 refusal，再取 parsed，否则你会拿着 None 去访问字段而崩溃。
  • ③ schema 太复杂可能不支持。Structured Outputs 只覆盖 JSON Schema 的一个子集（出于性能/技术原因），过深的嵌套、某些高级关键字可能被拒。对策：schema 尽量扁平、字段克制。
# 兜底两件事：先看 refusal，再走"校验+重试"
msg = completion.choices[0].message
if msg.refusal:                       # ← 坑②：安全拒答，没有 parsed
    handle_refusal(msg.refusal)
else:
    order = msg.parsed                # 正常路径

# 若模型 / 接口不支持 Structured Outputs → 坑① 的通用退路
def ask_with_retry(prompt, Model, max_try=3):
    for _ in range(max_try):
        raw = call_llm(prompt)        # 普通调用，不保证格式
        try:
            return Model.model_validate_json(raw)   # Pydantic 校验
        except ValidationError as e:
            prompt += f"\n上次输出不合法：{e}，请严格按 schema 重发"  # 带错重试
    raise RuntimeError("重试仍无法得到合法结构")
🔑 Agent 开发关联（呼应 L19）：

L19 教过：对冲 LLM 的不确定性，靠结构化 + 校验。这里是它的落地——能约束就约束（Structured Outputs），不能约束就校验 + 重试（Pydantic）。Agent 的可靠性从来不是"信任模型",而是"在机制上不给它出错的机会,出了错也能自愈"。

6. 动手练一练

💡 练习：从用户评论抽取结构化情感数据（点击查看参考答案）

场景：你的 Agent 要把一段用户评论抽成固定结构 {sentiment, score, keywords}，交给下游做统计入库。要求：sentiment 只能是 positive/negative/neutral 三选一；score 是 0~1 的浮点；keywords 是字符串列表。请用 Pydantic 定义 schema，并说明 Structured Outputs 如何保证这份输出能被下游直接用。先自己写，再看答案。

参考答案

from typing import Literal
from pydantic import BaseModel, Field
from openai import OpenAI

class Review(BaseModel):
    sentiment: Literal["positive", "negative", "neutral"] = Field(
        ..., description="整体情感倾向")
    score: float = Field(..., ge=0, le=1, description="情感强度 0~1")
    keywords: list[str] = Field(..., description="评论中的关键短语")

client = OpenAI()
completion = client.chat.completions.parse(
    model="gpt-5.5",
    messages=[
        {"role": "system", "content": "你是情感分析器，抽取结构化情感数据。"},
        {"role": "user",   "content": "用了三年，最近这次更新界面太难用了，找功能像寻宝。"},
    ],
    response_format=Review,          # 约束解码：strict 开启
)

r = completion.choices[0].message.parsed
# r.sentiment 一定 ∈ {positive,negative,neutral}；r.score 一定是 0~1 的 float
db.insert(sentiment=r.sentiment, score=r.score, keywords=r.keywords)  # 直接入库

Structured Outputs 如何"保证可直接用"？

  • 字段齐全：三个字段都是必填（...），约束解码不会漏生成任一字段。
  • 类型正确：score 生成时只允许合法的数字 token，不可能给你 "高" 这种字符串。
  • 枚举锁死：Literal[...] 让 sentiment 只可能是这三个值之一，下游 if r.sentiment == "positive" 永不落空。
  • 下游零防御：因为结构在生成时就被锁死，db.insert(...) 不用再写一堆 try/except 和字段存在性判断。

思考：若换成一个不支持 Structured Outputs 的模型，你会怎么改？（提示：用第 5 节的 model_validate_json + 带错重试兜底。）

🎤 面试高频：「如何保证 LLM 输出格式？」满分答按强度分三层：Structured Outputs（约束解码，token 级保证符合 schema）> JSON mode（只保证是合法 JSON）> prompt 请求（最弱，可能不听）；并主动补一句 Structured Outputs ≠ JSON mode——前者保证符合你的 schema，后者只保证是合法 JSON。最后加兜底：模型/接口不支持时，用 Pydantic 校验 + 带错重试，并处理 refusal。这样层次、区分、兜底都齐，直接满分。

总结

  • Agent 每步输出都要喂下游代码，格式对 = 硬前提，"请返回 JSON" 靠 prompt 不可靠
  • 三个层次：纯 prompt（不保证）< JSON mode（只保证合法 JSON）< Structured Outputs（保证符合 schema）
  • 核心区分：Structured Outputs ≠ JSON mode——前者保证符合你的 schema，后者只保证是合法 JSON
  • 原理是约束解码：把非法 token 概率归零，模型"不可能"违反 schema——是机制保证，不是求配合
  • 实操：把 Pydantic 模型当 schema 传给 parse，拿回已验证的对象直接用
  • 兜底：不支持时校验 + 带错重试；strict 下先处理 refusal；schema 尽量扁平
有 key 的话，把第 4 节那段 parse 跑一次，再故意把 Order 改出个 Literal 字段，看模型是不是"只可能"给你允许的值——你会对"约束"两个字有实感。没 key 也行，用第 5 节的 model_validate_json + 重试先把兜底链路跑通。记住这根准绳：能约束就约束，不能约束就校验加重试。下一课：让模型开始"看图听声"——多模态 API。
