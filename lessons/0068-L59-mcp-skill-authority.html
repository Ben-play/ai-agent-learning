第六阶段 · LangGraph 与 MCP55分钟

MCP、Skill 与业务授权边界

能读证据、能看见工具，不等于能保存眼前这份草稿

为什么这课重要？

用户只问「导出文件保留多久」，助手已用 L58 的只读工具拿到 KB-01。这时工作手册（Skill）可以提醒助手引用原文、按模板整理草稿，并在保存前请求确认；它不能把「请答疑」扩展为「允许保存」。同样，工具目录展示了接口名和参数，也只是说明怎样调用它。真正该问的是：这份凭据能访问哪个服务？宿主代表谁？草稿属于谁？用户批准的是不是现在这份、这个版本、这个动作？四个问题不能用一个「看起来允许」代答。

学习目标

  • 把传输凭据的 audience／scope 与宿主的身份、资源所有权、快照审批分别验证。
  • 区分 HTTP 401／403 与工具级业务拒绝；用入口计数及业务记录证明未执行，再用同路径正控排除「保存函数根本没接上」。

1. 先过传输门，再核对宿主手里的业务上下文

Agent Skill 可以把说明放进 SKILL.md，再按需附模板或参考资料；它解决的是「怎么做、什么时候加载」。即便宿主支持实验性的 allowed-tools 字段，它也描述 Skill 可用的工具，不能替资源服务器授予 scope，或替用户同意保存某张工单。工具配置和业务授权应分别检查。

继续使用 2026-07-28 的 POST /mcp。验收时，测试夹具传入不可变的 HostContext，包含当前租户及操作者、暂存草稿和可选的人工批准。这个对象在创建回环服务时从宿主代码传入，不从 HTTP 头、正文、模型输出或 Skill 文本构造。实验同时用 Authorization: Bearer <合成标签> 在服务端查询一张静态表：标签不含可解析声明，表项只有目标受众和 scope，不映射操作者。真实系统则必须可信地绑定当前请求与业务主体，不能照搬「每个实验实例只注入一个人」的办法。

可信输入或参考资料判断的问题不能代替什么
可信凭据验证器（本地合成查表）标签是否有效、目标受众是否是本资源、此次是否含 evidence:read 或 draft:save？有写 scope 不等于拥有任何一张单，也不代表用户确认了本次内容。
宿主的可信身份与暂存对象当前租户和操作者是否与草稿所有者相同，编号是否就是那份草稿？只传一个知道的编号、在 clientInfo 里写人名，均不是身份凭证。
宿主的意图快照与人工决定本次提交的编号、版本、正文是否等于暂存快照？批准是否绑定这份完整快照、所有者与这个动作？同编号的旧版、同正文的预览批准、请求自带的 approved 都不能放行。
Skill、工具目录、证据原文如何选工具、填参数、组织答复？这些内容描述步骤或提供事实，不能授予权限、证明身份或批准执行。

走一遍合成工单 case-72：team-a/u1 暂存第 2 版 Training draft。只读凭据可以取出 KB-01，同一凭据请求保存会被挡在 scope 门外。换为读写凭据后，当前请求依然要匹配所有者和暂存快照。换租户、改正文、拿旧版批准都不会写入。只有该所有者发出符合第 2 版快照的保存请求，且宿主已有绑定 save_training_draft 的批准，才进入登记函数。登记只在内存增加一条训练草稿，不提交工单、不发消息，也不能调用其他动作。

2. 用真实的入口次数验证「没执行」

先从通过路径往回拆：用同一位操作者、同一份草稿与同一份批准，只更换凭据，看 HTTP 层；再用受众和 scope 均正确的凭据，只变宿主上下文或请求草稿，看业务层。否则，一个缺 scope 的用例哪怕也改了草稿版本，最多只能证明 scope 门挡住调用，测不到版本校验。每条负例都要判读返回结果，并独立看 save_entries、saved 是否不变；这与 L54 把返回状态、边界次数、现存记录分开的思路一样。

从空账本开始：唯一变化收到的证据（省略传输框架）保存入口 / 实际记录
无凭据／目标受众错误401；有值但不通过时，WWW-Authenticate: Bearer error="invalid_token"0 / 0
受众正确，但只含读取 scope403；Bearer error="insufficient_scope", scope="draft:save"0 / 0
凭据足够，但宿主用户不是所有者200；result.isError: true，structuredContent.status: "not_available"0 / 0
编号对、版本或正文变了；或没有对应批准200；isError: true，分别为 intent_changed 或 approval_required；无 scope 挑战0 / 0
凭据、所有者、草稿、批准都匹配200；isError: false，{"status":"saved","draft_id":"case-72","revision":2}1 / 1，原草稿

HTTP 200 只表明成功交付了工具响应。业务拒绝用 isError: true 是这个实验的接口设计，不是在说每个系统都必须这样编码。业务拒绝不应触发自动加 scope；应提示用户核对目标、变更或确认状态。只测响应，挡不住「先执行、后拒绝」；只测最终行数，又可能漏掉入口被触发但没有留下记录的情况。因此计数放在实际保存函数的第一步，不数 HTTP 到达、清单查询、预览与审批检查。在写成功之后再跑一条缺 scope 的负例，原有一条必须保留，入口不能涨到两次。

3. 区分本地夹具、生产授权与长任务状态

本地故意不接真实 OAuth：练习需要可重复控制每一项输入，不需要访问身份服务、浏览器登录或取得实际访问令牌。课程用明文回环 HTTP 和不具备任何真实权限的固定标签；没有授权服务器，不验证真实令牌的签发、有效期或刷新，也没有 TLS 或真实身份认证的验收。实验的 WWW-Authenticate 只示范状态与区分原因，不提供真实的 resource_metadata 发现地址。回环和来源校验是传输限制，不是用户认证。

若实际采纳 MCP 的 OAuth 授权规范，MCP 服务端是资源服务器，不是凭空签发授权的角色。要实现受保护资源元数据及授权服务器发现，选择受信任的发行方与注册方式，验证适用流程中的 PKCE、回调与 iss，用 HTTPS 保护生产通信；localhost 回调的例外不等于能把真实 Bearer 放在普通 HTTP 上。按规范在授权与换取令牌时声明目标 resource，服务端验证令牌确为本资源发行且有效、限制 scope、安全存放并脱敏日志，不把入站令牌透传给上游。最后还得独立建立当前请求到宿主身份的可信绑定，并把业务所有权、参数与审批绑定验证放到效果入口之前；OAuth 同意不是这张训练草稿的保存批准。

长任务也有三个不同层次：L58 的 POST-SSE 是一条响应怎样交付；2026-07-28 把 Tasks 从核心移到官方可选扩展 io.modelcontextprotocol/tasks，由双方声明能力后使用，按任务句柄查询 tasks/get，需要时通过 tasks/update 提交输入；应用检查点则由宿主管理，要记录流程位置、原意图、当前审批绑定和业务回执。任务句柄不是权限；任务状态完成不自动证明本地草稿已保存，也不能替代续跑时检查当前权限、重新核对快照与效果。此实验没有实现 Tasks 或持久化；重启后恢复与安全重放仍由 L51、L52 的实验来证明。

最佳实践：拒绝发生在效果入口之前，批准绑定准确的业务意图

适用：同一个助手既能读证据又能保存内部草稿。边界：本练习只记本地合成草稿，固定的宿主夹具不能替代生产身份服务、持久审批或幂等记录。

错误：有写 scope 就准许保存

仅因凭据支持写入，不核对当前人、所有者、版本与批准。即使接口最后回答拒绝，也可能已经动过业务对象。

正确：逐门核对，分别记录实测

凭据只回答能不能请求这类能力，宿主仍按所有者、意图和动作绑定的审批决策；每个负例入口不变，匹配后才新增一条。

原因与代价：把权限保存在可信的边界而非提示词中，Skill 改写不会意外升权；代价是维护身份、快照与审批状态，以及研发只观察、不泄漏凭据的测试入口。变化后要复核，不以重复确认掩盖无权访问。

  1. 分别固定草稿换凭据、固定凭据换宿主或批准，不用一条多处错误的请求冒充多条验收。
  2. 正常保存一次后再测负例，观察入口增量及原记录有没有改变。

诊断：出现 200 先看 isError；入口涨但记录没变，也不算安全拒绝；连正控也为零，先查保存路径是否真的接通。

Q 读写凭据有效，当前人拥有第 2 版草稿，但宿主只批准了第 1 版；应如何处理？
scope 不能替代业务审批；批准必须绑定当前快照和保存动作，且在实际入口前完成核对。

4. 动手：同一个调用，分别拿掉一项条件

跟做：为每次请求写出预期

起点：team-a/u1 已暂存 case-72 第 2 版，宿主持有该版的保存批准，内存账本为空。按「HTTP 状态 / 工具状态 / 入口次数 / 记录数」填表，每次只改变一个验证条件。

  1. 先不带合成凭据，再带目标受众不匹配的夹具。
  2. 改用只读夹具；先验证它不能保存，再验证它能读出七天原文。
  3. 换为读写夹具，只改正文并试一次；随后恢复原正文保存。最后换回只读夹具再次尝试保存，确认原记录没被改动。

通过标准：前三个保存负例是 401、401、403；改正文得到 200 和工具拒绝，仍零写入。正控进入一次并留下原草稿，随后 403 的入口增量为零。

面试自查

先合上答案，按「结论 → 理由 → 如何验证」作答，再展开追问。

Q1用户看见工具，Skill 也建议保存，是不是已经获准？

参考回答：不是。清单交代工具接口，Skill 交代流程，两者都不持有宿主身份、对象所有权或批准决定。即使用相同的工具描述和请求参数，只换宿主操作者或取消批准就应被拒绝，且保存入口为零。正确所有者和批准才有一条真实内存记录。

追问：请求里的 clientInfo 写成宿主用户名，或参数携带 approved: true，有帮助吗？

答题要点：没有。前者是客户端自报，后者不是可信决定，且本工具白名单不接受该字段。审批只能来自宿主可信通道并绑定原意图。

Q2受众不对、scope 不够、草稿属于别人，客户端应该怎样分别处理？

参考回答：错受众的 401：核对目标资源与凭据，不沿用错受众的凭据。缺 scope 的 403：只按明确的最小权限挑战决定是否重新授权。所有权错误的 200：读 isError 与业务状态，告知当前对象不可操作，不重试保存。逐个改变一个条件，并核对拒绝路径的入口次数与记录。

追问：所有权拒绝后再扩大授权 scope，会补齐条件吗？

答题要点：不会。scope 只限定凭据可请求的操作类别；扩大 scope 不改变归属或人工决定。不应自动升权重试。

Q3为什么不能把合成 Bearer 查表作为上线方案？

参考回答：实验只控制受众和 scope 的组合，未验证签发方、发现、当前令牌有效性、真实主体绑定、生产 TLS、凭据安全存放或刷新。真实接入先固定规范与受信任提供方，再独立测无效／过期、错受众、缺 scope 和主体隔离，不以回环成功作证。

追问：如果证据以后从上游服务来，能把客户端的原 Bearer 转发过去吗？

答题要点：不能透传。入站令牌只给目标 MCP 资源；如需上游访问，使用独立且面向上游的授权，最小权限并保持业务审计。

Q4Tasks 显示完成，可以删掉应用检查点与审批证据吗？

参考回答：不可以。Tasks 只描述可选扩展中的远端任务交互，不能代表宿主流程进度或原操作的真实存储效果。若流程暂停后重启，仍要用应用记录找回操作与批准绑定，核对此时权限和业务回执，才能决定是登记旧结果、拒绝，还是请求人工复核。

追问：原任务没结果，或换了任务句柄才重试，是否能确认原操作没有执行？

答题要点：不能。没有结果不是没有效果。要向权威业务记录核对原操作；无法确定就保留未知，不因句柄变化补写。
