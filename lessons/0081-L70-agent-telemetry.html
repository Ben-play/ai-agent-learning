第八阶段 · Agent 工程45分钟

贯通任务、试验与轨迹

把同一轮的检索、模型、模拟工具、审批与终态接到本地接收端

为什么把轨迹交给接收端核对？

同一项交班任务第一次没有产出，第二次却成功了。如果按任务号拼日志，第一次的检索可能被接到第二次的草稿上。看似找到了原因，其实是把两轮拼成了一轮。先固定任务的目标与版本，再用试验号标明每轮实际运行。同一轮内部用一个追踪标识把各阶段关联起来；同一任务重跑时，不要复用上轮的试验号或追踪标识。线上请求内的重试则可以作为同一轨迹下的不同子跨度，并不必然等于重新做了一次离线试验。

任务回答「测什么」，试验回答「哪一次运行」，轨迹回答「这一次的调用如何连接」。课程在每条跨度上重复放应用自己的 phase8.task_id 和 phase8.trial_id，模型等规范字段仍用 gen_ai.*。trace_id 在同一轨迹内相同；span_id 区分单个操作；parent_span_id 表达父子关系，根没有父跨度。不要用操作名代替跨度号：两次模型调用完全可能同名。真实异步流程要显式传递上下文，或按语义用链接关联新轨迹；共享任务号既不能证明父子关系，也不能授权读取轨迹。

先在接收端查根、父子关系和关联字段，再看一轮中缺哪一步。模型失败后没有预览和审批是预期短路；模型成功但没有终态记录则需要另查投递、采样或状态写入。轨迹所见不等于业务事实：检索有记录不能证明证据可用，模拟工具有记录不等于真的执行，审批标记也不能替代实际授权。业务验收还要核对独立的证据与环境终态。

学习目标

  • 用任务号、试验号、追踪标识和父子关系从接收端重建单次运行，不把两轮的跨度串在一起。
  • 核对秒与毫秒、真实零与未知用量、错误码与业务状态，解释失败后的预期短路。
  • 把本地接收和交接摘要与 SDK、OTLP 传输及业务结果区分开。

1. 把语义约定、埋点库和自定义字段分别锁住

截至 2026-11-25，OpenTelemetry 原站将 GenAI 文档迁往独立仓库；课程核对该仓库的最新发布并固定在 v0.1.0。其中推理、检索、工具等约定仍处于 Development，不能把标签里的字段当作未来不变。示例另固定 Python SDK 的 opentelemetry-sdk==1.42.1；它是可选的埋点库版本，不是 GenAI 语义版本，不会自动生成正确的 GenAI 字段。必做实验没有安装 SDK，只实现明确列出的字段子集。升级时先在接收端对照旧版与新版的字段、类型、单位和省略规则，再切读端；不要靠同名报表猜测两版相容。

取检索的 retrieval、推理的 chat lesson-model、工具的 execute_tool draft_preview 为跨度名；它们分别有对应的 gen_ai.operation.name。推理还记录已知模型 gen_ai.request.model 和提供方 gen_ai.provider.name，合成场景使用固定自定义值 synthetic_fixture。进程内模拟推理可用 INTERNAL；真实远程推理一般用 CLIENT。审批和终态的名字是课内约定，业务状态用 phase8.state，不拼进状态描述。成功默认保留 UNSET，合成模型失败写 ERROR 与有限枚举的 error.type；UNSET 不等于「业务成功」，例如等待审批时也可为它。

固定时钟内部走整数毫秒。接收行的 start_offset_ms 是相对本轮起点的偏移，而 duration_s 是以秒表示的课内投影列，250 毫秒应收到 0.25 秒。两列都不是 OTLP 的跨度时间字段；本版本里推理时长的规范指标 gen_ai.client.inference.duration 用秒（s），实验只核对跨度投影，不发指标。墙钟适合标日历时间，不宜直接用于计算进程内的耗时。扇出并行时，子调用的时长之和也不能代替根跨度的经过时间。

模型给出可靠用量时，用整数分别记录 gen_ai.usage.input_tokens 和 gen_ai.usage.output_tokens；真的报告零就保留零，没收到可靠用量就省略对应跨度属性，不猜测，报表另记未知数。失败也可能产生已知用量，缺响应不能当作免费。不要套用旧版的单一 token 指标名：本标签将 gen_ai.client.inference.usage.* 用作已知正数计数器，并将每次操作用量放到 gen_ai.client.inference.operation.input_tokens / output_tokens 直方图，单位都是 {token}。规范对已支持的逐操作直方图规定无响应或响应无用量时记零作为占位；这不等于跨度属性已知为零，也不能把该分布当账单。若埋点根本无法有效获得用量，不应靠猜测发指标。

2. 阅读实际接收的交班试验

以下行来自 run_trial() 的接收端实读：task-70、trial-1，完整追踪标识 000000000000000000000000000002bd。表里只显示跨度标识的末两位。此处编号由合成样例指定；真实运行由埋点库生成并传播追踪上下文，不拿业务主键充当追踪标识。实验先由产生端构造白名单投影，再调用同进程 LocalReceiver.receive() 收入一批跨度。之后由另一个调用通过角色检查读回副本，并以读到的内容验收。仅打印 JSON 不会走这条链路；此处没有 SDK 导出器、Collector 或 OTLP 传输。OTLP 即使用 HTTP JSON，也须遵循它自己的 Protobuf 消息与映射，不能把下表的字典当它的载荷发送。

交接时可用 summarize_trace(receiver, trace_id, role="trace_reader") 取本地合成摘要：保留关联号、末尾状态、跨度名与时长；分别标出摘要版本、课程投影版本和参考的 GenAI 语义版本。它读的是已接收的副本，不表示 SDK 或 OTLP 已接通；没有可读轨迹时不会生成成功摘要。

决策卡：先对齐同一轮，再验证字段与单位

适用：同一任务重复试验、变更埋点版本，或日志无法定位在哪一步停止。边界：本地通过只证明选定的字段投影和接收，不替代真实管道验收。

误判：看到相同任务号就算关联

把多轮混用，只检查终点文字和输出行数；用量未知也补成零。

选择：按轮关联，从接收端验收

检查根与父引用，用独立预期对照单位、错误码和业务终态。

代价：字段迁移要维护正、负两类样本；换来可复现的诊断，也减少隐私内容和指标基数。

  1. 冻结语义文档、库版本、应用字段表；为每个时间字段写单位，为未知值写省略规则。
  2. 分别跑一轮成功、一次失败后重跑，读取实际收到的行；对照跨度链、秒值、缺失属性与终态。
  3. 线上变更另查采样、传输、失败反馈和最终查询结果；本地不替它们作证。

诊断：父标识串错先修上下文；值大千倍查毫秒转换；未知被填零查投影；轨迹有终态但实际资源不符，查业务提交而不是改图表。

Q 同一任务第一次模型失败、第二次成功，怎样判断预览属于哪一轮？
任务号用于跨轮比较；父子结构和追踪标识才标出这一轮的跨度。
Q 一次模型调用 250 毫秒，供应方没给用量，该跨度如何投影？
单位要转换；未知与真实零不可互换，逐操作直方图的占位规则也不能拿来填跨度。

面试自查

Q1 回归试验两次跑同一任务，后来者能不能沿用轨迹？

参考回答：任务号相同，试验和追踪标识分开。否则失败处可能接到另一轮的成功上。

追问：同一个请求里模型又试了一次呢？

答题要点：可以留在同一轨迹中，用两个跨度区分；总调用成功不意味着第一次尝试没失败。

Q2 输出 token 没回来，为什么图上却有个零？

参考回答：先弄清是跨度属性、逐操作直方图的占位，还是报表填值；不要把零当作供应方计费事实。

追问：同时还有输入用量怎么办？

答题要点：两个属性独立保留，输入已知就记，输出未知就省略，并在聚合中保留未知分母。

Q3 本地已经读出七行，可以宣称生产 OTLP 已打通吗？

参考回答：不能。本地只验证投影、接收和读取；使用真 SDK 的内存导出器也不等同于网络传输。

追问：网络验收还需要什么？

答题要点：验证协议载荷、目标与采样、失败反馈、后端收到并能查到同一批，并重查保密边界。

Q4 业务没结束，根跨度却是 UNSET，是不是漏报错误？

参考回答：先看业务状态和时间线；等待审批不等于运行错误，UNSET 不是成功标志。

追问：如果模型明确失败、流程中止呢？

答题要点：在失败操作标 ERROR 和低基数错误类型，业务终态另写 failed，确认无后续执行。
