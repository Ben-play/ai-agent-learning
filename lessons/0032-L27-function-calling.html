Function Calling 原理

让 LLM 从"只会说"变成"能行动"——但它其实一行代码都不执行

💡 为什么这课重要？

到目前为止，你的 LLM 只能吐字：你问它天气，它只能编一句"我无法查询实时天气"。Function Calling（函数调用 / 工具调用）就是打破这堵墙的机制——它让模型能说出"我要用哪个工具、传什么参数"，从此 Agent 才有了"手"。

但这里藏着一个面试高频、新手必错的坑：模型自己并不执行任何代码。它只是输出一段"我想调用 X 工具、参数是 Y"的结构化意图（JSON），真正跑代码、把结果送回去的是你的应用。搞懂这个"谁做什么"的边界，你就拿到了整个 Agent 循环的钥匙。本课把原理讲透，多轮/并行的循环细节留给 L35。

学习目标

完成本课后，你将能够：

  • 用一句话说清 Function Calling 的本质：模型只输出调用意图，不自己执行
  • 画出 Function Calling 的完整 5 步流程（发工具 → 模型选 → 你执行 → 回填 → 继续）
  • 写出一个符合 OpenAI 规范的 工具定义（name / description / parameters JSON Schema）
  • 从 resp.choices[0].message.tool_calls 里正确取出工具名和参数，并 json.loads 参数
  • 理解模型可以一次返回多个工具调用（并行工具调用）
  • 说清 Function Calling 为什么是 Agent "行动能力"的核心

1. 什么是 Function Calling：模型出"意图"，不出"动作"

Function Calling 常被翻译成"函数调用"或"工具调用"，一听好像是模型自己去调了个函数。这是最大的误解。真实情况是：

❌ 错误心智：模型收到问题 → 模型自己运行 get_weather() → 返回结果
✔ 正确心智：模型收到问题 → 模型输出一段 JSON 说"我想调 get_weather，参数 {city:'北京'}"
             → 你的代码读到这个意图 → 你的代码去跑 get_weather("北京")
             → 你把结果塞回去 → 模型基于结果继续回答

换句话说，模型能做的只有"说话"——只不过这次它说的不是自然语言，而是一段结构化的、机器可解析的调用意图。它不会、也没有能力去访问网络、读数据库、发邮件。所有真正"改变世界"的动作，都是你的应用代码执行的。

为什么这个区分对 Agent 至关重要？因为 Agent 的定义就是"能感知并采取行动"。LLM 本身只能说不能做；Function Calling 正是把"模型的语言意图"翻译成"程序可执行动作"的那道桥。没有它，LLM 永远停在聊天框里。

Q Function Calling 时，工具函数到底是谁执行的？
模型不执行任何代码——它只输出一段"我想调用哪个工具、传什么参数"的结构化 JSON 意图。真正去运行函数、访问数据库或网络的，是你的应用代码；跑完还要由你把结果回填给模型。记住这个"谁做什么"的边界，是理解整个 Agent 循环的前提。

2. 完整流程：五步走通一次工具调用

一次完整的 Function Calling 是你和模型之间的一来一回，共五步。先建立整体画面，多轮循环与并行的细节我们留到 L35：

          你的应用                         模型（LLM API）
             │                                  │
   ① 带上"工具定义"发起请求  ───────────────▶  读到有哪些工具可用
     (messages + tools=[...])                   │
             │                                  │ 判断：这题需要用工具吗？
             │                                  │ 需要 → 不直接答，而是……
             │        ②  返回 tool_calls   ◀───  输出"我要调 get_weather,
             │           (工具名 + 参数)          参数 {city:'北京'}"
             │                                  │
   ③ 你的代码真正执行该工具                        │
     result = get_weather("北京")                │
             │                                  │
   ④ 把结果作为 role:"tool" 消息  ─────────────▶  读到工具返回的真实数据
     追加进 messages 再发一次                      │
             │                                  │ ⑤ 基于结果继续
             │           最终自然语言回答   ◀───   "北京现在 25°C，晴。"
             ▼                                  │

关键点：第 ② 步模型不会给你最终答案，它只是"举手"说要用工具；第 ③ 步的执行完全是你的责任；第 ④ 步的回填是模型"看见"真实数据的唯一途径。这一来一回构成了 Agent Loop 最小的一个单元——Agent 的每一步"行动"，几乎都是这五步的重复。

Q 模型返回 tool_calls 后，下一步该做什么？
收到 tool_calls 意味着模型"举手要用工具"，而不是给出了最终回答。你要：①执行对应的工具函数，②把返回值作为 role:"tool" 消息追加进 messages，再发一次请求，模型才能基于真实结果继续。跳过回填，模型就永远看不到工具的输出。

3. 工具定义长什么样：description 决定成败

要让模型知道"有哪些工具可用"，你得在请求里传一个 tools 参数。每个工具是一个 type:"function" 的对象，核心三件套：name（叫什么）、description（干什么用）、parameters（要哪些参数，用 JSON Schema 描述）：

tools = [
    {
        "type": "function",
        "function": {
            "name": "get_weather",
            # ↓ description 是模型"读说明书"的地方——写清楚"何时该用它"
            "description": "查询指定城市的当前天气。当用户询问天气、气温、是否下雨时使用。",
            "parameters": {                      # ← 这就是 JSON Schema
                "type": "object",
                "properties": {
                    "city": {
                        "type": "string",
                        "description": "城市名，如 '北京'、'上海'",  # 参数描述也很关键
                    },
                    "unit": {
                        "type": "string",
                        "enum": ["celsius", "fahrenheit"],  # 枚举帮模型选对值
                        "description": "温度单位，默认摄氏",
                    },
                },
                "required": ["city"],            # 哪些参数必填
            },
        },
    }
]

# 发请求时把 tools 一起带上
resp = client.chat.completions.create(
    model="gpt-5.5",                             # 具体型号以官网为准
    messages=[{"role": "user", "content": "北京今天天气怎么样？"}],
    tools=tools,                                 # ← 关键：告诉模型有哪些工具
)

划重点：description 和每个参数的描述，直接决定模型选不选这个工具、选得对不对、参数填得准不准。模型没有别的线索——它就是靠读这段"说明书"来决策的。描述含糊，模型就乱选或不选；描述清晰（写明"何时用、参数啥含义"），命中率立刻上一个台阶。工具 Schema 的设计本身是一门手艺，我们在 L34 Tool Schema 设计专门展开。参数 Schema 怎么用 Python 优雅地生成，见 L14 Pydantic。

把 description 当成写给模型的 API 文档：不是给人看的注释，而是模型做决策的唯一依据。多写一句"什么时候该用 / 不该用"，往往比换个更大的模型还管用。这是最便宜的 Agent 提效手段。

4. 模型怎么把工具调用还给你

当模型决定用工具时，它不会把答案放进平时的 message.content（这时 content 常常是 None），而是放进一个专门的字段 tool_calls：

import json

resp = client.chat.completions.create(model="gpt-5.5", messages=..., tools=tools)
msg = resp.choices[0].message

# ① 判断模型是否要求调用工具
if msg.tool_calls:
    messages.append(msg)                   # ★ 必须先把「模型这条工具请求」加回历史，
                                           #   否则下一次请求会 400（tool 结果必须紧跟对应的 tool_calls 消息）
    for call in msg.tool_calls:
        name = call.function.name          # 工具名，如 "get_weather"
        # ② arguments 是【JSON 字符串】，不是 dict！必须先解析
        args = json.loads(call.function.arguments)   # → {"city": "北京"}

        # ③ 你的代码按名字分发、真正执行
        if name == "get_weather":
            result = get_weather(**args)   # 这一步才真的去查天气

        # ④ 回填：把结果作为 role:"tool" 消息追加（要带上 call.id）
        messages.append({
            "role": "tool",
            "tool_call_id": call.id,       # 对应哪一次调用
            "content": json.dumps(result), # 工具返回值（字符串）
        })
    # 再发一次请求，模型就能基于结果继续（详见 L35）

三个每次都会踩的点：① 回复在 tool_calls 里，不在 content；② 回填 tool 结果前，必须先把模型那条 tool_calls 消息 append 回 messages（否则下一次请求报错——tool 消息必须紧跟它对应的 tool_calls 消息）；③ call.function.arguments 是一段 JSON 字符串，不是 Python dict——必须 json.loads() 之后才能当参数用。字段名（tool_calls / function.name / function.arguments）都是 OpenAI 官方的真实结构，可对照官方文档核对：OpenAI · Function calling guide。

Q call.function.arguments 拿到手是什么类型，怎么用？
arguments 是模型生成的一段 JSON 字符串（如 '{"city":"北京"}'），不是 dict。要用 json.loads(call.function.arguments) 解析成字典后再传给函数（get_weather(**args)）。同理，工具名在 call.function.name，且模型的这轮回复在 tool_calls 里而非 content。

5. 多工具选择与并行调用

真实 Agent 手里往往有一整套工具（查天气、查数据库、发邮件、算数……）。Function Calling 在这里有两层能力：

  • 多选一 / 选合适的：你把多个工具一起放进 tools，模型会根据 description 自己判断该用哪一个（或一个都不用，直接文字作答）。这也是为什么第 3 节反复强调描述质量。
  • 并行工具调用：模型可以在一次回复里返回多个 tool_calls——比如"帮我对比北京和上海的天气"，它可能一口气要求调用两次 get_weather。所以第 4 节的代码用 for call in msg.tool_calls 循环遍历，而不是只取第一个。你可以并发执行这些调用、分别回填，再让模型汇总。
# 一次返回多个 tool_calls 的形状（简化）
msg.tool_calls == [
    call(id="c1", function=(name="get_weather", arguments='{"city":"北京"}')),
    call(id="c2", function=(name="get_weather", arguments='{"city":"上海"}')),
]
# → 你遍历执行两次，各自用 tool_call_id 回填，模型再对比作答

这里只建立概念：模型能一次要多个工具、也能在多工具间挑选。把它编织进"发→选→执行→回填→再发"的多轮循环，正是 Agent 真正干活的样子——完整机制我们在 L35 完整 FC 循环里手把手实现。

6. 回到 Agent：Function Calling 就是 Agent 的"手"

把前面几节串起来，你会发现一个朴素但关键的结论：

LLM 本身        = 一张"只会说话的嘴"（无状态、不能行动，见 L21/L25）
+ Function Calling = 给它装上一双"手"（能表达"我要做什么"）
+ 你的执行代码     = 手真正落到实处（跑工具、改世界）
= Agent            = 能感知、能决策、能行动的系统

观察任何一个 Agent Loop，你会发现它的几乎每一步都是一次 Function Calling：模型看当前状态 → 决定调哪个工具（输出意图）→ 应用执行 → 结果回填 → 模型再决定下一步……如此往复，直到任务完成。所以说，Function Calling 不是一个可选的 API 花样，而是"LLM 能行动"这件事的底层开关。没有它，你手里就只有一个聊天机器人，永远迈不进 Agent 的门。

本课把"原理与单次调用"讲透了。真正把它跑成一个会自己多轮推进、并行调用、直到收敛的 Agent，是 L35 的主题。

练习：为"查数据库"设计一个工具定义，并说明模型会怎么返回调用

目标：定义一个能"按用户 ID 查订单"的工具，并预测模型收到"帮我查下用户 42 的订单"时会返回什么。

① 工具定义（tools 里的一项）：

{
    "type": "function",
    "function": {
        "name": "query_orders",
        # 描述写清"何时用" —— 决定模型选不选它
        "description": "按用户 ID 查询该用户的历史订单。当用户询问某人的订单、购买记录时使用。",
        "parameters": {
            "type": "object",
            "properties": {
                "user_id": {
                    "type": "integer",
                    "description": "要查询的用户的数字 ID",
                },
                "limit": {
                    "type": "integer",
                    "description": "最多返回多少条，默认 10",
                },
            },
            "required": ["user_id"],
        },
    },
}

② 模型会怎么返回（resp.choices[0].message.tool_calls）：

tool_calls == [
    call(
        id="call_abc123",
        function=(
            name="query_orders",
            arguments='{"user_id": 42}',   # ← 注意：是 JSON 字符串！
        ),
    )
]

# 你的代码这样接住它：
args = json.loads(tool_calls[0].function.arguments)  # → {"user_id": 42}
rows = query_orders(**args)                           # 你的代码真正查库
messages.append({                                     # 回填结果
    "role": "tool",
    "tool_call_id": tool_calls[0].id,
    "content": json.dumps(rows),
})

要点自检：模型只给出了"要调 query_orders、user_id=42"的意图；arguments 是字符串要 json.loads；真正的查库和回填都由你的代码完成。如果模型没填 limit，说明它按你写的"默认 10"理解了——这正是参数描述在起作用。

可运行性说明：上面代码的方法名（chat.completions.create）、字段名（tool_calls / function.name / function.arguments）都是 OpenAI SDK 的真实结构，json.loads(arguments) 是必需的。完整跑通需要 pip install openai 和 OPENAI_API_KEY（见 L25）；没有 key 时，你可以把 tool_calls 手动 mock 成上面的形状，先把"解析 → 执行 → 回填"这段应用侧逻辑跑通。

🎯 速查卡：Function Calling

【一句话本质】
  模型只输出"我想调 X 工具、参数 Y"的结构化 JSON 意图
  ★ 模型不执行任何代码；执行 + 回填 = 你的应用代码
  ★ 这是 Agent"能行动"的核心开关

【完整 5 步】
  ① 带 tools=[...] 发请求（工具的 name/description/parameters）
  ② 模型返回 tool_calls（工具名 + 参数），content 常为 None
  ③ 你的代码执行工具： result = fn(**args)
  ④ 回填： messages += {role:"tool", tool_call_id, content}
  ⑤ 再发一次 → 模型基于结果继续（多轮循环见 L35）

【工具定义三件套】
  name         工具名
  description  何时用它 —— 决定模型选不选、选得对不对（L34）
  parameters   JSON Schema（type/properties/required/enum）

【怎么取调用】
  msg = resp.choices[0].message
  for call in msg.tool_calls:           # 可能有多个（并行）
      name = call.function.name
      args = json.loads(call.function.arguments)  # ★ 是字符串，要解析！

【多工具 / 并行】
  多工具：模型按 description 自己选合适的（或都不用）
  并行：一次回复可含多个 tool_calls → 用 for 遍历执行

【铁律】arguments 是 JSON 字符串，永远 json.loads 后再传参

  • Function Calling 让 LLM 能"用工具"，但模型只输出调用意图（结构化 JSON），不执行任何代码
