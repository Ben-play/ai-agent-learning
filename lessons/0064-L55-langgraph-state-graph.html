为什么这课重要？

从 L54 接手时，项目已经能查证据、在额度内改写一次，并在缺证据时停止。图的价值是把「接下来去哪」显式化，不是替应用决定什么可以执行。先迁移只读路径；审批写入留到 L56，不把两种问题一起引进来。

学习目标

把输入、节点更新、条件分支和业务结果连起来；用同一组输入比较手写版和 LangGraph 版；能解释为什么一个返回值正确的实现仍可能不合格。

验证状态：下面的状态与调用次数取自 Phase 5 的已验证契约，也是迁移的判定标准；LangGraph 候选版尚待安装依赖后实跑。

1. 先为边标名字，再为节点写代码

在一个执行周期中，状态是下一步会用到的数据，不是完整聊天记录。用 TypedDict 写出字段：正在查的 question、是否允许已知改写、总预算、已经分派的次数、当前状态和可发布的答复与来源。TypedDict 不会在运行时替应用验证输入；入口仍要检查任务类型、非空问题和额度。只读流程不需要把数据库连接或凭证塞进可序列化状态。若未来要放并行节点，才有必要设计多个更新怎样合并；这个串行练习先按字段替换即可。

节点完成有限的一步并返回本步更新，不直接修改传入字典。gate 只决定能否再分派，read 才调用 Phase 4 且推进计数；一个节点可以只返回 {"status": "exhausted"} 等更新，不必复制整份状态。边消化更新后的状态：START 固定进 gate；只有仍为 pending 才到 read，读取后同样只有待处理才回 gate。其他分支都到 END。compile() 让图可以执行，不会替这套业务条件发现少了一道守卫。

START → gate ── pending ──→ read
           │                 │
           │ terminal        ├── pending ──→ gate
           ↓                 ↓ terminal
          END               END

例如，登记好两个节点之后，下面这段把「还能执行」映射成读节点，否则终止。路由函数不做读取；读取只在节点体发生。

builder.add_edge(START, "gate")
builder.add_conditional_edges(
    "gate", lambda state: state["status"] == "pending",
    {True: "read", False: END},
)

2. 带着一个输入走完条件边

输入「导出文件有效期？」。Phase 4 的合成问题表不收录这句，第一次分派拿到 needs_evidence 而不是答案。只有当前问句恰是已知别名且启用改写时，才把下一次查询改成「导出文件保留多久？」。这不是模型判断，也不是通用同义改写。表中分派只数进入 Phase 4 问答边界；第一次缺证据甚至可能没调用内部适配器，不能把这个数当作模型调用数。

只改变的条件路径合同结果
禁用改写，额度 2放行 → 读别名 → 停止failed，1 次分派，无答复
启用改写，额度 2放行 → 读别名 → 再检查 → 读已知问句complete，2 次，KB-01、KB-02
启用改写，额度降为 1放行 → 读别名 → 闸门拒绝exhausted，1 次，无答复

「最后一步把额度用完」不总等于耗尽：若第一步就查询到有据答案，可在 read 返回 complete，直接结束，不再回闸门。与「还缺一个不允许发出的调用」区分开。把读取入口计数作为第二份证据：若终态是 exhausted 却已经读了两次，先查边是否绕过了闸门，而不是改报表。

3. 迁移先比较业务，再比较框架成本

迁移暂时保留同一个问句和同一个证据函数，只把手写 while 换成两节点的图。每个实现用独立初始状态，核对业务状态、答复、来源和分派边界。比较的轨迹只包括有业务约束的动作；内部若增设一个纯整形节点，不占分派额度，就不用因图不同而改门槛。相反，框架的递归上限防止图继续转，不是每个业务资源的总预算，不能用它替代调用前额度检查。

最佳实践：保护外部调用的边界，不锁定内部节点顺序

适用：有稳定基线、多个可复用步骤或下一课的跨进程待办。不适用：若一个确定函数足够，直接函数少一层依赖与调试成本。

误判：返回耗尽就算通过

额度 1，图先读两次，再把返回改成耗尽；账面状态对，行为已经越界。

对照：先拦分派，再验结果

同一输入与额度，待办回到闸门后直接结束，读取入口只收到一次请求。

取舍：一条守卫边让失败可解释、可观测，但图并不自动省钱或提高证据质量。确需验并发、延迟或真实模型时另做试验。

  2. 把候选的返回值与真实分派计数并列；两边一致才算保住这条合同。

终态正确但次数不对，修执行边界而非计数文案；来源错先对比实际送进读取的问句与返回结果。

本课最佳实践验收：设备校准目录

把「读证据」换成仪表校准记录：先查台账，再查校准条目。给校准图加一条额度检查，限制每次执行最多读一次或两次。对照一个故意错的版本：它在发现超出预算之后返回正确终态，却已经执行了第二次读取。

独立起点：一条分支条件

通过标准：预算 1 时有台账记录、无详情调用；预算 2 时正好两次，并为返回值相同但偷偷多读的反例写一条断言。

展开变式参考与自检
from typing import TypedDict
from langgraph.graph import END, START, StateGraph
from langsmith import tracing_context


class State(TypedDict, total=False):
    budget: int
    status: str
    source: str


def trial(budget, check_first):
    reads = []

    def index(state):
        reads.append("index")
        return {"source": "CAL-03"}

    def route(state):
        return "detail" if not check_first or state["budget"] > 1 else "stop"

    def detail(state):
        reads.append(state["source"])
        return {"status": "complete" if state["budget"] > 1 else "exhausted"}

    graph = StateGraph(State)
    graph.add_node("index", index)
    graph.add_node("detail", detail)
    graph.add_node("stop", lambda _: {"status": "exhausted"})
    graph.add_edge(START, "index")
    graph.add_conditional_edges("index", route, {"detail": "detail", "stop": "stop"})
    graph.add_edge("detail", END)
    graph.add_edge("stop", END)
    with tracing_context(enabled=False):
        result = graph.compile().invoke({"budget": budget})
    return result["status"], reads


expected = ("exhausted", ["index"])
assert trial(1, True) == expected
assert trial(2, True) == ("complete", ["index", "CAL-03"])
bad = trial(1, False)
assert bad[0] == expected[0] and bad[1] == ["index", "CAL-03"]
assert bad != expected  # 状态相同，观察到的动作不同。
print("L55 TRANSFER PASSED")

独立验收：应只打印 L55 TRANSFER PASSED。反例若也通过，检查是否只断言状态；正例两种预算都不读详情，则是闸门一刀切。练习只涵盖串行合成场景。

面试自查

先按「结论 → 理由 → 如何验证」作答，再展开追问。

Q1把政策正文、SQLite 连接和预算都塞进状态，因为节点都会用。你保留哪些？

参考回答：预算和必要的证据数据随任务推进；连接是运行期依赖，不是任务事实。传入前验证状态类型和缺失字段，不认为 TypedDict 会拒绝坏输入。用一次无效任务确认读入口没触发。

追问：什么时候存来源 ID 而不存全文？

答题要点：能按权限和版本可靠回查时可存 ID 和版本；要复核当时看到的证据，不能只凭指向现行正文的 ID。

Q2最终答对、来源也对，但预算 1 时调用了两次再返回。可以先上线再优化吗？

参考回答：不行。调用次数是该路径的业务上限，不是只影响速度的建议。分别对额度 1 或 2 记录实际分派次数；只允许第二个场景尝试第二次读取。

追问：递归上限设成 1 能替代吗？

答题要点：不能。它约束图执行，不等于资源分派负载；一个节点也可能发多次请求。

Q3旧版手写流程和状态图返回一致，后者多了一个纯整形节点。该不该报回归？

参考回答：不因拓扑不同就报。核对答案、来源、额度、禁止动作。整形步骤若不改变任何合同字段且不消耗受限资源，仍可通过；是否值得换框架另看维护成本。

追问：整形时把 KB-01 引文起算点从生成换成下载呢？

答题要点：这是内容回归，即使节点数量、终态、来源 ID 都不变也不能放行。

Q4只测一次成功就宣布迁移完毕，最少还要补哪两条不同的停止证据？

参考回答：第一次无支持且不可改写应 failed；第一次无支持、可以改写但预算为 1 应 exhausted。两条都没有答案且只分派一次，但原因不同，防止把失败一律当耗尽或偷偷重试。

追问：实际入口记录为 1 次，但适配器计数是 0，哪个错了？

答题要点：不必有错。前者数宿主分派，后者数内部适配；项目可以在适配器之前就发现证据不足。
