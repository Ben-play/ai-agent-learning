多模态 API

让模型不止会读文本，还能"看图"、"听音"——以及背后那笔容易被忽略的账

💡 为什么这课重要？

真实 Agent 面对的输入不只是纯文本——用户可能发来一张报错截图、一份扫描的发票、一段语音。本课用获准使用、不含敏感信息的样例，演示怎么让 Agent 看图、读 PDF、听录音。

L25 的 Responses input 也能放图片或文件：把一条消息的 content 写成数组，文字与附件并列；录好的音频则先走转录接口。本课看怎样构造请求、验收返回和核对用量。

学习目标

完成本课后，你将能够：

  • 说清什么是多模态，以及它在 Agent 里的典型用途（看截图、读文档、语音输入）
  • 用 Responses 的 input_image 传图（URL、base64 data URL 或文件 ID），认出 Chat Completions 的兼容写法
  • 用 input_file 读一份 PDF，分清单文档输入与按权限检索多文档
  • 用 audio.transcriptions 把录好的音频转成文字，区分批量转录和实时语音
  • 按模型、图像细节档位和实际用量评估成本（呼应 L18/L23）

1. 什么是多模态

「模态（modality）」就是信息的种类：文本、图片、音频、视频……多模态模型能处理不止一种模态，但不代表什么都能接。支持视觉的模型可以把一张图和问题一起读；语音则可以先交给转录模型，再把文字交给 Agent。

对 Agent 来说，这直接打开了几类以前做不了的活：

  • 截图理解：用户丢来一张报错/界面截图，Agent 看懂了才能帮忙排障。
  • 文档 / 表格 OCR：读扫描件、发票、合同，把图里的字段抽成结构化数据（衔接 L28）。
  • 看图答题：对着一张图表/照片提问，让模型基于图像内容作答。
  • 语音输入：用户说话 → 转成文字 → 再喂给 Agent 的文本流程。

换句话说：多模态是让 Agent 从"只能读你打的字"，升级到"能看你给的东西"。这是视觉 Agent、文档处理 Agent 的地基（第 6 节详述）。

Q 下面哪个最适合用"多模态"能力来做？
看懂报错截图需要处理图片，这是典型的 Vision（视觉）场景。拼文本、开启流式输出或存 Key，本身都不会让模型获得新的输入能力。

2. Vision：用 Responses 看图、读 PDF

在 Responses 的 input 里，用户消息的 content 是一个数组：问题用 input_text，图片用 input_image，两块并排放。看图和读 PDF 都用下面的消费函数：先查正常终态和拒答，再读 output_text。

def accepted_text(response):
    if response.status != "completed":
        raise ValueError(f"not completed: {response.status}")
    if any(part.type == "refusal" for item in response.output
           if item.type == "message" for part in item.content):
        raise ValueError("refused")
    text = response.output_text
    if not text:
        raise ValueError("no text output")
    return text

下面的联网示例是可选的，会计费；将它接在函数后，照 L25 配置 SDK、凭证和 OPENAI_MODEL，先查模型是否支持视觉输入。L29_IMAGE_URL 填服务端可访问的、获准使用的非敏感样图链接。

import os
from openai import OpenAI

client = OpenAI()
resp = client.responses.create(
    model=os.environ["OPENAI_MODEL"],
    input=[{"role": "user", "content": [
        {"type": "input_text", "text": "这张图里有什么？"},
        {"type": "input_image", "image_url": os.environ["L29_IMAGE_URL"],
         "detail": "auto"},
    ]}],
)
print(accepted_text(resp))

传图有三种写法，选一种就行：

  • URL：image_url 直接是链接字符串，不再套一层 url；模型服务端要能访问这张图。
  • base64 内联：同一个 image_url 字段也收 data:image/png;base64,...。不用把图放到公网，但图片仍会发给服务端，请求体也会变大。
  • 文件 ID：若已用 Files API（purpose="vision"）上传样图，用 {"type":"input_image","file_id": image_file.id,"detail":"auto"}，其中 image_file 是上传结果，不再填 image_url。
兼容写法 · Chat Completions：用 messages，其中 content 的文字块是 {"type":"text","text": question}，图片块是 {"type":"image_url","image_url":{"url": url}}（url 也可为 data URL）。不要把这个嵌套结构搬进 Responses。
✍️ 小练习：把本地 PNG 编成 data URL —— 先自己构造 input_image，再展开对照

用获准使用的非敏感 PNG 样例（例如自制的虚构收据）；这段只在本地构造图片块，不发送请求。

import base64

with open("fixture-receipt.png", "rb") as f:
    b64 = base64.b64encode(f.read()).decode("ascii")
data_url = f"data:image/png;base64,{b64}"
image_part = {"type": "input_image", "image_url": data_url, "detail": "auto"}

要做可选的联网测试，就用 image_part 替换上例的图片块；input_text 不用改。不要用真实收据或用户截图。

Q 在 Responses 里，内联的 base64 data URL 应该放在哪里？
input_text 和 input_image 在 content 里并列。Responses 的 image_url 直接收 URL 或 data URL；引用已上传的图片才改用 file_id。

一份 PDF：用 input_file

给支持 PDF 输入的视觉模型传 PDF 时，服务会把提取出的文本和每页的图像一起放进模型上下文。扫描件、图表和版式都有机会被看见；页图也会增加输入用量。沿用上例的导入、client 初始化和 accepted_text（不用先发看图请求），上传获准使用的非敏感测试 PDF，再把文件 ID 传给 Responses：

with open("fixture-manual.pdf", "rb") as f:
    pdf_file = client.files.create(file=f, purpose="user_data")

resp = client.responses.create(
    model=os.environ["OPENAI_MODEL"],
    input=[{"role": "user", "content": [
        {"type": "input_text", "text": "按页列出操作步骤；找不到就说明。"},
        {"type": "input_file", "file_id": pdf_file.id},
    ]}],
)
print(accepted_text(resp))

读一份已选定的文档，不等于在知识库里找答案。如果要从多份文档组成的知识库找答案，用 RAG（检索增强生成）：检索时按当前用户权限过滤，只把有权查看、与问题相关的片段交给模型，并保留出处。直接上传文件不会替你做跨文档检索或权限检查；上传前也要确认文件保留和清理要求。

3. 批量音频转录：语音 → 文字

手上已有一段录音时，用批量转录把音频文件变成文字。这是独立端点：成功时读转录结果的 text，API 错误按该端点处理，不套用 Responses 的 status 或拒答块检查。下面是可选联网示例：准备一段获准使用、不含敏感信息的测试音频，按 Speech-to-Text 指南设置支持 JSON 返回格式的 OPENAI_TRANSCRIPTION_MODEL，不沿用视觉模型。

import os
from openai import OpenAI

client = OpenAI()
with open("fixture-audio.mp3", "rb") as audio_file:
    result = client.audio.transcriptions.create(
        model=os.environ["OPENAI_TRANSCRIPTION_MODEL"],
        file=audio_file,
        response_format="json",
    )

print(result.text)

result.text 就是普通文本，可以作为 Responses 的文本输入。一种常见的语音 Agent 流程是转录 → 文本推理 → 可选的语音合成（TTS）。如果要边说边出字幕，选读实时转录指南；如果要低延迟的语音进、语音出对话，选读语音 Agent 指南里的 speech-to-speech 路线。这两种实时场景不在本课练习范围内。

4. 成本注意（本课重点）：图片不是免费附件

OpenAI 会把图片输入折算成 Token；怎么折算、每单位多少钱，要看模型。有的模型按缩放后的尺寸切块（tile / patch），所选的 detail 也可能影响用量。相同的一张图，换模型或换档位，不能照搬原来的估算。

  • 细节按任务选：只想知道图上大概有什么，可以试试模型支持的 detail:"low"；要读小字或核对图表细节，就先验证识别效果。常见的 low / high / auto 含义和支持情况以模型文档为准。
  • 请求体大小不等于 Token 量：用 URL 或文件 ID 引用同一张图，或只压缩文件字节，不代表模型少处理了图像内容，也不保证更便宜。

延续 L18 和 L23 的习惯：请求前按文档估算，请求后看实际用量。Responses 的 usage.input_tokens 是整次请求的输入用量（也包括问题文字），不是单独的图片账单。结合输出用量和模型定价算账；音频转录另查所选模型的计费规则。

实战 · 先做小样对比：固定模型和问题，用同一张非敏感样图比较两种受支持的细节档位，或比较原图和缩小版。一起记录 usage 和识别效果，再决定是否批量使用；别把一次观察当作保证，也别忘了 PDF 的页图。
Q 想估算图片输入的成本，哪种做法靠谱？
尺寸和细节档位如何影响用量，取决于模型的处理规则。先查规则和单价，再对照实际用量和识别效果，不用文件大小或固定折扣来猜。

5. 三条工程注意

把上面串成落地时的检查清单：

  • ① 尺寸够用就好：大图可以试着缩小，再对照用量和识别效果。别只看压缩后省了多少字节，也别为了省用量把小字缩糊了。
  • ② 查模型和接口能力：能读文本不代表能看图，能看图也不代表能接实时音频。用之前查模型页和接口文档，确认支持的模态、格式和限制。
  • ③ 分清输入和输出：看图、读 PDF、转录音频在本课都输出文字。生成图片、合成语音是不同的任务，要另查对应接口和模型能力。

决策卡：先选媒体入口，再验返回结果

适用：巡检工单附一份已选定的 PDF 和一段录音，要分别提取文本。不适用：从整个文档库找答案要做权限检索；实时语音也不走批量转录。

误判：附件和输出都套一个形状

同一工单的 PDF 当图片传，或把录音也交给视觉请求；一收到字就入库，可能把未完成的描述记为事实。

对照：端点各自处理，合流只拿已接收的文字

同一 PDF 用 input_file，完成且未拒答才读正文；同一段录音单独转录，成功后读 result.text。

取舍：多维护一处分发，换来明确的输入和返回契约。PDF 页图会占用上下文；转录另计费用，识别准确性也要单独评估。

  1. 用下面的验收核对四种附件块及正常返回。
  2. 保留附件，改成截断或后置拒答，确认不能读取或交付正文。

结果诊断：L29 ACCEPTED 只证明本地契约；请求形状错先查块类型，失败响应还交付文字先查终态门槛。

离线小验收：检查请求形状和正文接收门槛

先自己拼出一条文字加附件的消息，再用下面的纯 Python 断言对照。把第 2 节的 accepted_text 代码块和此块放进同一个文件，用 python -I 文件名.py 运行。链接、文件 ID、data URL 和返回对象都是虚构替身；不读文件，不联网，也不验证 SDK 或识别效果。

from types import SimpleNamespace as Record


def user_input(question, kind, value):
    if kind == "pdf_id":
        attachment = {"type": "input_file", "file_id": value}
    elif kind == "image_id":
        attachment = {"type": "input_image", "file_id": value, "detail": "auto"}
    elif kind in ("url", "data_url"):
        attachment = {"type": "input_image", "image_url": value, "detail": "auto"}
    else:
        raise ValueError("未知附件来源")
    return [{"role": "user", "content": [
        {"type": "input_text", "text": question}, attachment,
    ]}]


url = "https://example.invalid/fixture.png"
data_url = "data:image/png;base64,AA=="  # 仅测形状，不是有效图片
image_id = "file-image-fixture"
pdf_id = "file-pdf-fixture"
cases = [
    ("url", url, {"type": "input_image", "image_url": url, "detail": "auto"}),
    ("data_url", data_url, {"type": "input_image", "image_url": data_url, "detail": "auto"}),
    ("image_id", image_id, {"type": "input_image", "file_id": image_id, "detail": "auto"}),
    ("pdf_id", pdf_id, {"type": "input_file", "file_id": pdf_id}),
]
for kind, value, expected in cases:
    assert user_input("说明附件内容。", kind, value) == [{"role": "user", "content": [
        {"type": "input_text", "text": "说明附件内容。"}, expected,
    ]}]

# 图片和 PDF 使用同一种 Responses 输出形状。
for text in ("图里是一张桌子。", "第 1 页：按下启动键。"):
    message = Record(type="message", content=[Record(type="output_text", text=text)])
    assert accepted_text(Record(status="completed", output=[Record(type="reasoning"), message],
                                output_text=text)) == text

    later_refusal = Record(type="message", content=[Record(type="refusal", refusal="未提供答案")])
    for status, output, expected in [
        ("completed", [message, later_refusal], "refused"),
        ("incomplete", [message], "not completed: incomplete"),
        ("failed", [], "not completed: failed"),
    ]:
        # 不提供 output_text：拒绝分支若提前读取，会抛 AttributeError，不能假装通过。
        try:
            accepted_text(Record(status=status, output=output))
        except ValueError as exc:
            assert str(exc) == expected, exc
        else:
            raise AssertionError(f"不应交付正文: {expected}")
try:
    accepted_text(Record(status="completed", output=[], output_text=""))
except ValueError as exc:
    assert str(exc) == "no text output", exc
else:
    raise AssertionError("正常终态也不应交付空正文")
print("L29 ACCEPTED")

标准输出应只有一行 L29 ACCEPTED。输入断言失败时检查块类型、image_url 嵌套及文件 ID 的位置；若拒答或未完成时报 AttributeError，检查是否在守门前就读取了 output_text。

6. 和 Agent 的关系：这是"视觉 Agent"的地基

多模态不是花活，它撑起了两类越来越重要的 Agent：

  • 能"看屏幕"的 Agent（Computer-Use / 视觉 Agent）：让 Agent 自己操作电脑——点按钮、填表单——的前提，是它得先"看懂"当前屏幕截图上有什么、按钮在哪。Vision 就是这类 Agent 的眼睛。
  • 文档处理 Agent：用 Vision 读扫描件或 PDF 页图，再配合 L28 的结构化输出抽取字段。如果用户问的是整个知识库，先按权限检索证据，再把相关内容交给模型。

一句话：文本让 Agent 会"想"，多模态让 Agent 会"看"和"听"——面对真实世界的输入，这一步不可少。

本课最佳实践验收：展品记录只收通过检查的文字

展品录入系统同时拿到标签照片、说明 PDF 和口述录音的返回。用第 2 节的 accepted_text，接上起点，实现 collect_notes(rows)：分别返回「编号 → 已接收文字」和「编号 → Responses 拦截原因」。照片和已成功的转录各收一条；只拦未完成的 PDF 并记录原因。全程用本地替身，不上传附件或入库。

from types import SimpleNamespace as Record

label = "展品编号 A17"
label_item = Record(type="message", content=[Record(type="output_text", text=label)])
page = "第 1 页：展品名称"
page_item = Record(type="message", content=[Record(type="output_text", text=page)])
rows = [
    ("photo", "image", Record(status="completed", output=[label_item], output_text=label)),
    ("leaflet", "pdf", Record(status="incomplete", output=[page_item], output_text=page)),
    ("narration", "audio", Record(text="讲解录音已转成文字。")),
]
# TODO: collect_notes(rows)，图像/PDF 走 accepted_text，转录成功只读 text。
展开独立参考与断言（接在起点后运行）
def collect_notes(rows):
    notes, blocked = {}, {}
    for item_id, kind, reply in rows:
        if kind == "audio":
            notes[item_id] = reply.text
        elif kind in {"image", "pdf"}:
            try:
                notes[item_id] = accepted_text(reply)
            except ValueError as exc:
                blocked[item_id] = str(exc)
        else:
            raise ValueError("unknown attachment kind")
    return notes, blocked


notes, blocked = collect_notes(rows)
assert notes == {"photo": "展品编号 A17", "narration": "讲解录音已转成文字。"}, notes
assert blocked == {"leaflet": "not completed: incomplete"}, blocked
print("L29 TRANSFER PASSED")

依次复制第 2 节 accepted_text、起点、参考，执行 python -I 文件名.py；唯一输出应为 L29 TRANSFER PASSED。PDF 半页进入记录说明漏验终态；音频报缺少 status 则说明把转录当成了 Responses。

🎯 速查卡：多模态 API

【Responses · 看图】input 里的用户消息：content = [文字块, 图片块]
  {"type":"input_text", "text": question}
  {"type":"input_image", "image_url": url, "detail":"auto"}
  url 可为链接或 data:image/png;base64,...；已上传图片用 file_id 替换 image_url。
  兼容写法（Chat Completions）：messages → text / image_url → image_url.url。

【Responses · 读 PDF】文字块 + {"type":"input_file", "file_id": pdf_id}
  PDF 的提取文本和页图一起进上下文；跨知识库提问用按权限检索的 RAG。
  看图/读 PDF：completed 且遍历消息确认无 refusal 后，才读 output_text。

【批量音频转录】audio.transcriptions.create(model=..., file=audio_file,
  response_format="json") → result.text → 文本流程；实时语音另选路线。

【成本 ★重点】按模型、尺寸与 detail 估算，再核对实际 usage 和定价。
  压缩字节不等于减少 Token；对比用量，也要对比效果。

【工程注意】用获准的非敏感样例；查模型与接口能力；分清输入与输出。

总结

  • 看图：用 Responses 的 input_text 加 input_image。image_url 直接放链接或 data URL；也可改用 file_id。Chat Completions 的嵌套写法只作兼容对照。
  • 读文档：一份 PDF 用 input_file；跨文档问答先做权限检索。看图和读 PDF 都先确认正常完成且无拒答，再读正文。
  • 听录音：用 audio.transcriptions.create 转成文字，再走文本流程；实时字幕和语音到语音另选路线。
  • 算成本：查模型、图片尺寸和 detail 的计量规则，再用实际 usage 验证；别拿压缩后的字节数当账单。
先做离线小验收。如果具备模型访问权、预算和获准使用的非敏感样图，再选做第 4 节的用量对比。下一课 L30：文字、图片和 PDF 页图都要放进有限的 Context Window，我们讲怎么管它。
