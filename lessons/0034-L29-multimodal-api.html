多模态 API

让模型不止会读文本，还能"看图"、"听音"——以及背后那笔容易被忽略的账

💡 为什么这课重要？

到目前为止，你发给模型的都是纯文本。但真实 Agent 面对的世界不是纯文本——用户会甩来一张报错截图、一份扫描的发票、一段语音输入。想让 Agent 处理这些，就得学会「多模态」：把图片、音频也塞进请求里。

好消息是：调用形状你已经会了。多模态不是一套全新 API，而是在 L25 那个 messages 结构上，把 content 从"一段文本"扩成"一个数组"，数组里既能放文本、也能放图片。真正的新知识只有两点：①怎么把图片/音频放进去（结构）；②它们凭什么比文本贵（成本）。第二点是实战最常踩的坑，我们会重点讲。

学习目标

完成本课后，你将能够：

  • 说清什么是多模态，以及它在 Agent 里的典型用途（看截图、读文档、语音输入）
  • 用 content 数组把图片放进 messages（公网 URL 与 base64 内联两种方式）
  • 用 audio.transcriptions 把语音转成文字
  • 理解图片会按分辨率折算成大量 Token——多模态输入也是要算钱的（呼应 L18/L23）
  • 掌握三条工程注意：压缩省 Token、查能力矩阵、分清输入与输出模态

1. 什么是多模态

「模态（modality）」就是信息的种类：文本、图片、音频、视频……多模态模型指一个模型能同时理解不止一种。以前的 LLM 只"读文本"，现在的主流模型很多能直接"看"图片、"听"音频——你把一张图连同问题一起发过去，它就能描述、分析、回答。

对 Agent 来说，这直接打开了几类以前做不了的活：

  • 截图理解：用户丢来一张报错/界面截图，Agent 看懂了才能帮忙排障。
  • 文档 / 表格 OCR：读扫描件、发票、合同，把图里的字段抽成结构化数据（衔接 L28）。
  • 看图答题：对着一张图表/照片提问，让模型基于图像内容作答。
  • 语音输入：用户说话 → 转成文字 → 再喂给 Agent 的文本流程。

换句话说：多模态是让 Agent 从"只能读你打的字"，升级到"能看你给的东西"。这是视觉 Agent、文档处理 Agent 的地基（第 6 节详述）。

Q 下面哪个最适合用"多模态"能力来做？
多模态的核心是让模型处理文本以外的模态——图片、音频等。"看懂报错截图"正是典型的 Vision（视觉）场景。拼文本、流式输出、存 Key 都仍是纯文本/工程问题，跟模态无关。

2. Vision：把图片放进 messages

关键变化只有一个：content 不再是一个字符串，而是一个数组，里面每一项是一个"块"——可以是文本块，也可以是图片块。以 OpenAI Chat Completions 为例，图片块的 type 是 "image_url"：

from openai import OpenAI
client = OpenAI()

resp = client.chat.completions.create(
    model="...",                         # 需支持视觉的型号，以官网能力矩阵为准
    messages=[{"role": "user", "content": [
        {"type": "text", "text": "这张图里有什么?"},
        {"type": "image_url",
         "image_url": {"url": "https://.../img.png"}},   # 或 data:image/png;base64,...
    ]}],
)
print(resp.choices[0].message.content)

注意 content 是个列表，文本和图片是列表里并列的两项。模型会把两者一起理解——它"看着这张图"来回答"这张图里有什么"。

两种传图方式，按场景选：

  • 公网 URL：image_url.url 直接放一个可访问的链接。适合图片已经在网上/对象存储、模型服务端能拉到的情况——请求体小。
  • base64 内联：把本地图片读出来编码成 base64，拼成 data:image/png;base64,.... 这种 data URL，同样放进 image_url.url。适合图片在本地、不方便暴露公网链接的情况——但请求体会变大。

另外 OpenAI 的图片块支持一个 detail 参数（如 low / high / auto）：low 会把图降到低分辨率处理、更省 Token，high 更精细但更贵——这正好引出第 4 节的成本话题。（OpenAI Images & Vision 指南）

⚠️ 图片块的结构是厂商特定的（不像文本，L25 里只有 system/max_tokens 那点差异）。上面是 OpenAI 形状；Anthropic 用 {"type":"image","source":{"type":"base64","media_type":...,"data":...}}（或 type:"url"），也没有 detail 参数。概念一致（图片放进 content 数组），但字段名要照目标厂商文档写。
✍️ 小练习：传一张本地图片（base64）问它内容 —— 先自己写 messages 结构，再展开对照

提示：本地文件要先读成字节、base64 编码、再拼成 data: URL 放进 image_url.url。

import base64
from openai import OpenAI
client = OpenAI()

# 1) 读本地文件 → base64 → 拼成 data URL
with open("receipt.png", "rb") as f:
    b64 = base64.b64encode(f.read()).decode()
data_url = f"data:image/png;base64,{b64}"

# 2) 图片作为 content 数组里的一项传进去
resp = client.chat.completions.create(
    model="...",                          # 支持视觉的型号，以官网为准
    messages=[{"role": "user", "content": [
        {"type": "text",  "text": "这张图里写了什么?"},
        {"type": "image_url", "image_url": {"url": data_url}},
    ]}],
)
print(resp.choices[0].message.content)

核心要点：本地图 = 读字节 → base64 → data:image/...;base64,... → 塞进 image_url.url；文本和图片是 content 列表里并列的两项。

Q 在 OpenAI Chat Completions 里，图片是怎么放进请求的？
图片是把 content 从字符串扩成数组后，作为其中一项（type:"image_url"）和文本块并列传入的——URL 或 base64 data URL 都放在 image_url.url 里。它不是单独上传、也不能塞进 system 文本里当字符串。

3. 音频转录：语音 → 文字

处理"语音输入"最常见的做法是转录（transcription）：把音频转成文字，再喂给你已有的文本 Agent 流程。OpenAI 用 client.audio.transcriptions.create，把打开的音频文件作为 file 传进去（Whisper 类模型）：

from openai import OpenAI
client = OpenAI()

with open("audio.mp3", "rb") as audio_file:      # 二进制读
    result = client.audio.transcriptions.create(
        model="...",                             # 转录模型，以官网为准
        file=audio_file,
    )

print(result.text)                               # ← 转出来的文字

拿到 result.text 后，它就是普通文本——接下来完全走你熟悉的 chat.completions 那套。"语音 Agent"常见形态就是：转录 → 文本推理 →（可选）再转回语音。（OpenAI Speech-to-Text 指南）

4. 成本注意（本课重点）：图片是"吞 Token 的大户"

这是多模态实战最容易踩的坑，务必记牢：图片不是"免费附件"，它会被折算成大量 Token 计费。官方明确说明——图片输入按 Token 计量、和文本一样计费（"metered and charged in token units similar to text inputs"）。

它怎么折算？各家/各型号规则不同，但共同点是：按图片的分辨率/尺寸切成若干块（tile / patch），块越多、Token 越多。所以——

  • 高分辨率图尤其贵：一张大图折算出的 Token，可能顶得上好几百字甚至更多文本。你以为"只发了一张图"，账单上却是一大笔输入 Token。
  • 用 detail:"low" 能显著省：模型改用低分辨率版本处理，Token 大幅下降——不需要看清细节时优先用。

这正是 L18「一切输入都要 tokenize」和 L23「Token 就是钱」的自然延伸：多模态输入也是 Token，也进成本公式。发一张高清图前，请先估算它折算成多少 Token——别把成本估算只用在文本上。

⚠️ 具体每张图折算多少 Token、tile 怎么算，随型号变化，务必以官方文档/定价页为准，不要背死数字。你要记住的是规律（分辨率越高越贵）和习惯（发图前先估）。

面试 / 实战 · 多模态的隐藏成本：很多人把图片当"附件"，觉得不占 Token——大错。图片会按分辨率折算成大量 Token，高分辨率更贵，一张大图可能比一整段文字还烧钱。工程上：①发请求前先估算图片的 Token 量（呼应 L23 的成本意识）；②不需要细节就降分辨率 / 用 detail:"low"；③批量看图的场景，成本会线性叠加，务必先算账。能主动说出"多模态输入也是 Token、要算成本"，是区分新手和熟手的一道题。
Q 关于图片输入的成本，下面哪句是对的？
图片输入会按分辨率/尺寸折算成 Token、和文本一样计费，分辨率越高、折算的 Token 越多、越贵。它不是免费附件、也不是固定一口价。所以发高清图前要估算 Token；不需细节时降分辨率或用 detail:"low" 省钱。

5. 三条工程注意

把上面串成落地时的检查清单：

  • ① 大图先压缩 / 降分辨率：上传前把图缩到"够用就好"的尺寸，能直接砍掉一大截 Token（也更快）。这是省钱最立竿见影的一招，接上一节的成本逻辑。
  • ② 不是所有模型都支持所有模态：有的模型能看图不能听音、有的纯文本；同一家不同型号能力也不同。用之前查官网的"能力矩阵 / 模型页"确认，别假设"这模型应该也能看图"。
  • ③ 分清"多模态输入"和"多模态输出"：本课讲的是把图/音输入给模型让它理解。而生成图片、合成语音（TTS）是另一类 API（如图像生成、语音合成接口），调用方式不一样，别和"看图/转录"混为一谈。

6. 和 Agent 的关系：这是"视觉 Agent"的地基

多模态不是花活，它撑起了两类越来越重要的 Agent：

  • 能"看屏幕"的 Agent（Computer-Use / 视觉 Agent）：让 Agent 自己操作电脑——点按钮、填表单——的前提，是它得先"看懂"当前屏幕截图上有什么、按钮在哪。Vision 就是这类 Agent 的眼睛。
  • 文档处理 Agent：处理扫描件、发票、合同这类图片形式的文档，靠 Vision 把图里的内容读出来，再（配合 L28 的结构化输出）抽成字段。没有 Vision，这些"纸质/扫描"输入 Agent 根本碰不了。

一句话：文本让 Agent 会"想"，多模态让 Agent 会"看"和"听"——面对真实世界的输入，这一步不可少。

总结

  • 多模态 = 模型不止读文本，还能"看"图、"听"音；Agent 用它做截图理解、文档 OCR、看图答题、语音输入
  • 传图 = 把 content 扩成数组，图片作为一项（type:"image_url"）；两种方式：公网 URL / base64 内联 data URL
  • 音频 = audio.transcriptions.create(file=...) 转成文字，再走文本流程
  • 成本（重点）：图片按分辨率折算成大量 Token、高分辨率更贵——发请求前先估算（呼应 L18/L23）
  • 工程：大图先压缩、查模型能力矩阵、分清输入模态与"生成图/音"这类输出 API
  • Agent 意义：Vision 是视觉 / Computer-Use / 文档处理 Agent 的地基
有支持视觉的模型的话，把第 2 节那段跑一次：先发一张小图、再发一张高清大图，对比 usage 里的输入 Token——你会对"图片有多吃 Token"有直接的痛感，这比任何文字都记得牢。下一课 L30：这些 Token（文本 + 图片）都要挤进有限的 Context Window，我们讲怎么管它。有疑问随时问我。
