第四阶段 · Prompt 与 Context 工程45分钟

把请求写成可判定任务

先定答复、缺证据与草稿的通过条件，再写 Prompt

为什么这课重要？

「做一个客服 Agent」不是可验收的任务。收到「导出文件保留多久？」时，助手即使说得很流畅，也可能答错，或在用户没要求时起草一张工单。L38 验的是调用链，本课验的是对用户交付了什么。

学习目标

能写出一份含输入、预期结果和禁止副作用的任务契约；能用三个固定案例判断是否通过。

1. 先写任务契约，再写 Prompt

任务契约不是告诉模型「尽量准确」，而是约定给定什么、什么结果算通过。一个用例固定用户请求和当轮可用的证据，也写明期望的业务状态、答复或草稿必须包含或留空的内容，以及禁止发生的动作。把这个用例执行一次，叫一次试验；多次试验的输入相同，结果未必相同。

落笔时先问三个问题：结论是否有证据、走的是哪条业务路径、应用实际做了什么？前两项要看返回值和原文，最后一项要看执行记录或外部状态。HTTP 成功只表示请求在接口层成功处理；JSON Schema 合规只表示数据满足声明的约束。一个结构合法的 answered 结果照样可以引错政策，或在应用已经误建工单后返回。

2. 固定同一条证据，走三种路径

把本轮资料冻结为一条虚构政策：KB-01「导出文件生成后保留 7 天。」先不改变资料，只换用户请求。这个版本的 KB-01 支持「从生成起保留 7 天」，不支持「过期后能恢复」或「过期后不能恢复」。证据是否够用，要针对这次要下的结论判断。

用户请求业务状态应观察到的输出
「导出文件保留多久？」answered回答从生成起保留 7 天，引用 KB-01；无草稿。
「过期后能恢复吗？」needs_evidence提示缺少恢复政策；结论、引用和草稿均为空。
「请为保留期起草一份确认工单。」drafted返回有引用、待人工确认的草稿；不声称已提交。

例如「可保存一周，从文件生成时算起」和原文意思相同，不必逐字相等；「下载后还有一周」却换了起算点。三条路径都禁止真实的创建、更新或发送：第三条多的是一段待确认的文本，不是多了一次写操作。

3. 通过状态不等于通过任务

如果第一条返回 answered、引用 KB-01，却写成「保留 30 天」，状态和字段检查可以都通过，失败的是事实断言。反过来，第二条按契约缺证据是正确结果；如果线上本应有恢复政策，却也走到这一条，就检查政策是否入库、检索是否命中、证据是否真的装入本轮，而不是让模型猜一个答案。

「零动作」也要独立检查。比如在隔离环境预置两张工单，执行起草请求后，确认两张的内容和状态均未变、没有新增记录，并且本次试验的写操作轨迹为空。只数最后还剩几张，可能漏掉更新或创建后又删除；助手说「没有提交」也不是操作证据。若系统只交付草稿，优先不给这条路径接写工单的能力。下方离线断言只判返回形状，不能替代证据复核或写操作验收。

最佳实践：先约定什么才算成功，再写 Prompt

适用与限制：同一个助手可能回答、请求补充证据或起草工单时，为每条路径写可观察的通过条件。若任务允许多种好答案，不把字面一致当成通用的正确标准。

错误做法：只看状态

用户问「过期后能否恢复？」；只有保留期证据。返回 needs_evidence，但正文还说「大概能恢复」。只核对状态会误判通过。

推荐做法：状态和内容一起验

同一问题、同一证据。needs_evidence 才是预期结果，且答案、引用、草稿都为空；若还声称能恢复，就拒绝该结果。

取舍：把状态和禁止出现的字段一起断言，能抓到「表面拒答、实际猜测」。这些规则需要随业务维护，但不必逐字锁定正常答复：结构用 schema 或断言检查，证据是否支持结论则用事实规则或人工复核。若还承诺不创建工单，要另查动作记录或工单状态。

  1. 写下同一输入的预期状态、必须出现和必须为空的字段。
  2. 运行原离线契约自检，找出哪条断言拦住了挂着拒答状态的猜测。

结果诊断：L39 ACCEPTED 表示正常样例通过、违规样例被拒；若还放行猜测，检查是否只验了状态。原自检不证明回答的事实正确，也没有观测外部工单状态。

Q 证据只讲保留多久，用户问过期后能否恢复。该返回什么？
到期与能否恢复是两个问题。没有支持恢复结论的材料就请求补充，不能把不相关事实当作答复依据。

def matches_contract(result, expected):
    if result["status"] != expected:
        return False
    if expected == "needs_evidence":
        return result["answer"] is None and not result["citations"] and result["draft"] is None
    if expected == "answered":
        return bool(result["answer"] and result["citations"]) and result["draft"] is None
    if expected == "drafted":
        draft = result["draft"]
        return bool(draft and draft["title"].startswith("需人工确认：")
                    and draft["body"] and result["citations"])
    return False


refs = [{"source_id": "KB-01", "quote": "导出文件生成后保留 7 天。"}]
answer = dict(status="answered", answer="保留 7 天。", citations=refs, draft=None)
missing = dict(status="needs_evidence", answer=None, citations=[], draft=None)
draft = dict(status="drafted", answer="保留 7 天。", citations=refs,
             draft=dict(title="需人工确认：导出保留期", body="请确认保留期。"))
assert matches_contract(answer, "answered")
assert matches_contract(missing, "needs_evidence")
assert matches_contract(draft, "drafted")
assert not matches_contract(dict(missing, answer="大概能恢复。"), "needs_evidence")
assert not matches_contract(dict(draft, draft=dict(title="已提交", body="已登记")), "drafted")
print("L39 ACCEPTED")

Q 如果正式系统要求确认工单确实没有提交，哪项证据合适？
真实副作用应以可相信的外部状态或执行记录为证，不以模型话术或 HTTP 成功代替。

本课最佳实践验收：会议室能留物过夜吗？

同一问题先只给开放时间，再给「不可留物过夜」的规定。为两次分别写状态、引用和禁止出现的字段。正确答复不必照抄原文，但结论必须由相关证据支持。

展开独立参考：检查答复与拒答边界
policy = {"source_id": "ROOM-02", "quote": "会议室内不得留物过夜。"}


def accepted(result, expected):
    if result["status"] != expected or result["draft"] is not None:
        return False
    if expected == "needs_evidence":
        return result["answer"] is None and result["citations"] == []
    if expected == "answered":
        # 本例只允许一个明确结论；真实文案可接受同义表述。
        return result["answer"] == "不能留物过夜。" and result["citations"] == [policy]
    return False


# 固定返回样例：第一次只给开放时间，第二次有留物规定。
missing = dict(status="needs_evidence", answer=None, citations=[], draft=None)
answered = dict(status="answered", answer="不能留物过夜。", citations=[policy], draft=None)
assert accepted(missing, "needs_evidence"), "开放时间不回答留物问题"
assert accepted(answered, "answered"), "答复应有正确结论和引用"
assert not accepted(dict(missing, answer="应该可以留到明天。"), "needs_evidence"), "假拒答漏检"
print("L39 TRANSFER PASSED")

面试自查

先合上答案，按「结论 → 理由 → 如何验证」作答，再展开追问。

Q1接口返回 200，字段符合 Schema，还引了 KB-01，却说「下载后保留一周」。算通过吗？

参考回答：不通过。KB-01 说的是从生成时算起，答复却改成了从下载时算起。即使保留天数没说错，也要用原文核对起算点；接口成功、字段合法、引用有值，都不能证明结论正确。

追问：改成「生成后可保存一周」，但没照抄原文，能通过事实检查吗？

答题要点：能。一周等于 7 天，起算点也没变；对答复验事实，不要求逐字相同。

Q2同样问能否恢复文件：用例 A 只给保留期，用例 B 配了明确的恢复政策。两次都返回 needs_evidence，怎么判？

参考回答：A 的状态符合预期，还要验答案、引文和草稿都为空；B 不符合预期，因为用例有足够证据，应给带引用的答复。误把两个相同状态都算通过，就漏掉了 B 没有交付答案的问题。

追问：B 失败后，怎样区分材料没送到和材料到了却没用上？

答题要点：先查实际装入本轮的证据；缺条款再追查检索和装配，条款完整则查证据判断。

Q3唯一条款是「至少提前 24 小时取消可全退」。用户问「提前 12 小时能退一半吗？如果能，帮我起草申请。」你会验什么？

参考回答：应返回 needs_evidence，提示缺少半额退款规定，答案、引用和草稿为空，也不执行退款或提交。全退的条件不是半退的规则，不能据此同意或否定半退，也不能把有条件的起草当作无条件委托。

追问：如果补了明确允许提前 12 小时退一半的条款呢？

答题要点：条件成立才返回带对应引文、标明待确认的草稿；仍不能真的提交。

Q4起草用例返回「待确认」，工单前后都是两张，但 12 号的优先级从高变成了低。该改测试还是改实现？

参考回答：本次验收应判失败，并补上逐条对照内容和状态的检查。数量没变不代表没修改；用这份前后记录复现问题，再查写入轨迹定位哪一步碰了 12 号工单，把写入从起草路径移除。

追问：如果优先级后来又改回去了，前后快照还能抓住吗？

答题要点：不能；还要查本次试验覆盖写入入口的操作轨迹，快照相同只说明最终状态相同。
