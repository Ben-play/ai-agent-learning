第九阶段 · 高级 Agent 能力 · 选修40分钟

按任务选择推理投入

简单题不升级，复杂题不漏证，没有证据就停

为什么这课重要？

客服既要答「导出文件保留多久」，也要核对留存和同步两条政策。加大推理投入可能对第二题有用，却不会凭空补出备份政策，更不能替代租户隔离。沿用 L79 的交接原则：没有质量瓶颈就不引入高级能力；有瓶颈才用同一批题对照，这节选修不阻塞后续必修。

学习目标

  • 区分厂商的 effort 字段、thinking 模式、单次输出上限和宿主的任务级预算。
  • 用独立的事实、引文和拒答标签比较三个策略，并区分「便宜」「可选」「尾部更快」。
  • 分别诊断掉证、错证、不支持的配置和账本错误；答对也不能掩盖漏账。

1. 先核对接口与型号，再谈 low 或 high

一手文档对照｜2026-11-25；仅列本文示例所用直连 API 与型号
接口与型号投入与模式硬输出上限与终态
Claude Messages
claude-sonnet-4-6		output_config.effort 支持 low/medium/high/max，不支持 xhigh；effort 默认 high。默认不启用 thinking；可显式选 thinking.type: adaptive，让模型按题决定是否及如何深入。effort 也影响正文和工具调用，不只是 thinking。max_tokens 给单次输出设硬上限，包含 thinking；若 stop_reason 为 max_tokens，不要把截断当交付。
OpenAI Responses
gpt-5-2025-08-07		reasoning.effort 支持 minimal/low/medium/high，不是 none；不传 Claude 的 thinking。同名档位不代表两家使用相同 Token 数。max_output_tokens 同时覆盖推理与可见输出；触顶可返回 status: incomplete 和 incomplete_details.reason: max_output_tokens，甚至无可见答复。推理用量看 usage.output_tokens_details.reasoning_tokens。

Sonnet 4.6 仍接受手动旧模式 thinking: {type: "enabled", budget_tokens: 1024}，但已弃用；这个数是推理目标，不是严格上限。普通非交错手动模式要求至少 1024 且小于 max_tokens；旧交错模式有例外。本实验不实现该例外。不要把 budget_tokens 留在 adaptive 里，也不要把 adaptive 当 effort 值。别的型号可能拒绝旧模式，或不允许关闭 thinking。OpenAI Chat Completions 另用顶层 reasoning_effort 和 max_completion_tokens，不能把 Responses 选项直接搬过去。

别拿软信号当保险丝。 effort 不规定固定 Token 或时间，不保障质量。API 的硬上限只管一次输出，不管整个工作流的检索、重复请求、排队和工具。宿主另设总费用、截止时间或调用次数，执行前检查剩余量，用完就明确停。线上还要用保守预留和实测用量对账；到期时停止安排新动作不等于撤销已经开始的调用。

Q 合法的高投入请求耗尽输出空间，没有可用正文。怎样记账？
空正文、明确拒答、无调用不是一种状态。不能用较高 effort 抵销截断或账单。

2. 固定同一批 Phase 7 查证题

phase9-effort/v1 固定题序、主题和可信身份 mei，从 Phase 7 合成资料的内存 SQLite 按租户、文档、版号和定位读取。先比可信来源与交接包，再由模拟器从已收引文抽取值；独立金标手写原句，不从交接包和模拟答复复制。改标签、资料或题目后应给负载另起版本，并重跑三臂。

3. 质量先过门，再看成本和尾部

实际执行模拟取证才记 6 uc / 15 ms；调用低档模型替身加 18 uc / 45 ms，高档加 42 uc / 105 ms，截断也要计这笔。取证前因预算不足停下，零事件、零费用、零耗时；缺证拒答不生成，但已取证就要计账。

compare() 用独立冻结的数值核对取证与调用，再把两者相加核对每个终态的费用、耗时和宿主上限。整批任务（含拒答和失败）都留在统计中，按记录的事件累计成本和 p95，不直接信任报告总数。账本错误单列为 ledger_errors，有关答案不计合格交付，整臂不入围。零交付时没有均摊值。按需费用可手算为 24 + 24 + 48 + 6 = 102 uc，除以三件交付是 34 uc/件。

同一批题的合成回放结果；uc 为虚构计费单位，ms 不是实测模型耗时
策略过门／交付费用（总额／每件，uc）p95（ms）
固定低否／2/478／3960
固定高是／3/4150／50120
按需是／3/4102／34120

仅在过硬门的方案间先比每件交付成本、再看 p95。固定低虽快但漏了同步，不能排第一；按需省了常规题的开销，但最慢的双事实题不变。四件任务的最近秩 p95 取升序第 4 项，只是这批的最大值，不是 SLO，也不是实际费率。

决策卡：何时值得加推理投入？

适用：资料齐全且能区分查证成本与推理瓶颈的混合负载。停止条件：缺授权证据、配置不兼容或任务预算不足时，拒答或报未完成，不默认升级或换型号。

误判：更多推理必然更可靠

证据不是靠思考产生，正确措辞也不是正确交付轨迹。

选择：按可测任务差异调整

固定语料与金标，确认复杂题确有收益；成本和尾部都要报。

  1. 为锁定的型号与接口核对支持表、停止原因和用量口径。
  2. 分别判质量、来源、分发资格和账本；截断和拒答保留实际发生的开销。
  3. 在入围方案间选更便宜的一个，并确认尾部满足预先设定的目标。

取舍：按需需要维护分类和异常退路，分类错会导致漏证或白花费用。若固定低已过门，优先保留简单方案；若尾部不可接受，先找到真正慢的阶段。

Q 按需方案的账本总额更低，但删掉了复杂题的同步原句。怎么比较？
取证、交接、答复各自可失效。升级不能恢复从交接包消失的来源。

from dataclasses import replace
import runpy

if not __debug__:
    raise RuntimeError("run without -O")
lab = runpy.run_path("code/phase9-advanced-agent/advanced-lab/effort/main.py")
rows = lab["replay"]("selective")
_, other, good, _ = rows
a, b = good.call.packet
mutations = ((a,), (other.call.packet[0], b), (a, replace(b, quote="同步任务每天 03:00 运行。")))
task = lab["TASKS"][2]
bad_mode = replace(lab["CLAUDE"], thinking="between_tools")
with lab["open_demo"]() as db:
    for packet in mutations:
        bad = lab["run_task"](db, task, "selective", packet=packet)
        assert (bad.status, bad.claims, bad.call) == ("evidence_mismatch", (), None)
    refused = lab["run_task"](db, task, "selective", target=bad_mode)
    assert refused.status == "unsupported_config" and refused.call is None

for packet in mutations:
    fake = replace(good, call=replace(good.call, packet=packet))
    report = lab["compare"]((*rows[:2], fake, rows[-1]))
    assert not report.eligible and report.quality_errors == report.dispatch_errors == report.ledger_errors == ()
    assert report.evidence_errors == ("cross-check",)
bad_options = {**good.call.options, "thinking": {"type": "between_tools"}}
fake = replace(good, call=replace(good.call, options=bad_options))
report = lab["compare"]((*rows[:2], fake, rows[-1]))
assert not report.eligible and report.quality_errors == report.evidence_errors == report.ledger_errors == ()
assert report.dispatch_errors == ("cross-check",)

missing = rows[-1]
for batch, task_id, delivered in (

    assert report.ledger_errors == (task_id,)
    assert report.quality_errors == report.evidence_errors == report.dispatch_errors == ()

面试自查

先说要保护的边界，再换一个条件，看结论是否仍成立。

Q1 常规题压到低档后没漏事实，是否把所有题都调低？

参考回答：不能从常规题推断复杂题。分层检查多来源任务与缺证拒答，再比较同批账本。

追问（改条件）：复杂题的所有证据先压成了一条，应该按「一条」路由吗？

答题要点：输入条数改变不等于事实核对变简单；确认两项事实仍可分别追溯，再用独立样本重测复杂度规则。

Q2 三档都拒答备份题，要不要提高 effort 重试？

参考回答：缺授权证据时不重试生成。检查资料是否存在或有无授权，不把高档当数据源。

追问（改条件）：后来已发布并授予备份政策读取权，还算正确拒答吗？

答题要点：重建版本化证据与金标，准许新版本回答；不要拿旧拒答标签判断新资料。

Q3 把 Claude 的配置迁到 OpenAI Responses，为什么不能原样照搬？

参考回答：字段、可用档位与模式依接口和型号；宿主验证后才分发。

追问（改条件）：如果选的是 OpenAI Chat Completions 呢？

答题要点：重新查顶层字段与限制，用实际目标接口的配置与终态验收，而不是只换模型字符串。

Q4 按需更省，但 p95 不动，能承诺更快吗？

参考回答：不能。尾部仍是高档复杂题；现有数字是四个合成时长的最近秩，不是线上承诺。

追问（改条件）：上线样本的尾部主要是等待检索，不再是推理，优先改什么？

答题要点：先分解端到端时长，验证检索瓶颈；改推理档位不一定改善等待。

小结与一手参考

先验资料与配置，按任务选择投入，再用独立质量门和账本做决定。缺证、无权或超预算，应该停，而不是升级。

  • Claude API · Effort、逐型号 thinking 支持表与手动模式与预算规则：核对档位、默认值和不兼容组合。
  • OpenAI · Reasoning guide、GPT-5 型号页与Chat Completions 参数：核对快照、推理用量与终态字段。
