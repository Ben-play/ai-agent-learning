限制过度代理与工具权限

建议、分发、写入尝试、落库与回执，各有自己的证据

为什么这课重要？

客服页面集成了「查询制度」和「保存培训草稿」。检索可读、稿件可展示、甚至工具已被发现，都不能推出「这次应该保存」。如果验收只看最终文字，越权动作可能与正确回答同时发生；如果只统计保存行数，又看不出模型是否反复提出任务不需要的建议。本课把这两条指标分开，用真实的临时 SQLite 和普通合成建议验收宿主的决定。

  • 为只读和起草任务划能力边界，用可信主体、scope、当前快照和批准作为不同检查。
  • 用拒绝例与实际提交正控核对零分发、零写入尝试、零业务记录，不用建议计数代替副作用证据。

1. 把哪几样东西交给谁？

数据来源与形状用途
事实与样张标记从 Phase 7 读取的 SYNC-POLICY v1 §1 和普通样张标签，如「培训样张」都进入建议构造，改变标签会改变可见预览；标签不属于证据原文或权限字段。
建议构造预览并携带 (action, binding)只有动作和稿件绑定进入分发判定；建议不能授予主体、scope 或批准。
任务档位与 scope宿主从任务和访问上下文决定是否开放草稿；evidence:read 与 draft:save 分开本课用集合模拟已验证的 scope；不解析令牌，也不把有 scope 当作已获业务批准。
所有者、当前稿件和批准宿主记录主体（租户、用户名）、任务、动作、版本和内容摘要当前快照和批准都必须匹配；同名异租户或换稿件后，历史批准都不能复用。

风险要按任务来看：只读问题没有任何保存需要，应该从可见目录去掉保存工具，并在分发入口再拒绝。起草任务可以合理地提出保存，因此一次因缺批准而被挡住的建议不是同一种「多余建议」。不同指标需要不同分母：多余建议可按任务统计，用反例决定是否收紧工具目录；禁止效果必须按条为零，不因总任务量大而被稀释。

本课主实验只走 Phase 8 同进程分发与 Phase 5 的 SQLite，不做 HTTP，也不将文本送给模型。需要验证 L59 的 MCP 分支时，另跑下方的 Phase 6 回环检查。两条检查不共用授权上下文、回执或效果记录，都没有真实 OAuth。生产还需检查受众、有效期、撤权、身份绑定和服务端业务约束；长时间等待后按执行时状态再校验。

2. 为什么一个「没有写」不够？

每条用例先暂存一份同步时间草稿。只读档直接把保存视为任务以外；起草档但只有读 scope，则报告 scope_required；scope 齐全却没有对当前版本的批准，则是 approval_required。这不是布尔变量「失败」的三个名字：它们分别指向计划约束、接入权限和等待人工，下一步处置不同。换成普通的「交班样张」后，建议预览应变，但这些判定以及获准保存的稿件均不变。

用 proposals → dispatches → writes → rows 读一次结果：建议在宿主被记录；通过全部门才进入回调；真正的业务 INSERT 前有独立观察点。事务结束后，saved_drafts() 用只读连接查该库的全部业务行，不按预期所有者过滤，以免漏掉误写到别处的行。正控查精确所有者、稿件标题、正文、来源以及回执与持久行的对应；负例查零写入、零提交、没有保存回执。待审检查点本身不算业务写入。分发 1、写入 0 可能只是下游拒绝；写入 1、行 0 可能是回滚；行 1、调用方没有回执则要按 L52 对账。

决策卡：目录收窄，效果入口仍校验

适用：同一助手承担只读与草稿任务。边界：本课只保存本地培训草稿，不执行外部操作。

误判：发现就可调用

所有任务用同一工具目录，依靠模型说明或最终文字判断是否安全。

选择：逐门给出证据

宿主限制动作，独立验 scope、所有者和批准，并在效果入口存证。

代价：要维护任务档位与批准快照；换来可解释的拒绝、可重验的正控和更小的执行面。

  1. 先固定建议和草稿，逐次改任务、scope 或批准。
  2. 再固定 scope 和旧批准，改当前稿件或主体；观察每一层计数是否保持为零。

验收门槛：禁止路径分发、实际写入尝试、持久行均为零；批准正控三项为 1。全部为零的实验不是充分证据，它可能根本没接上效果入口。

Q 起草任务需要保存，scope 充足，现稿已换版；宿主持有旧版批准。应如何处理？
旧批准只对应旧快照。不要自动更新已批准的对象，也不自动保存旧版本；展示要确认的当前内容。

面试自查

先说失效边界，再选能证明它的观察点。

Q1答复正确，却每十次就多一次保存建议。业务表没变化，需不需要改？

参考回答：要分报多余建议与业务副作用。只读任务下缩减工具目录，保留分发拒绝，独立计数验证。

追问：换成真正需要保存、只是缺人工批准呢？

答题要点：正常待审不能被计成同一类多余建议；仍必须零分发和零写入。

Q2工具能被列出来但用读 scope 调用时受阻，如何定位？

参考回答：发现工具不发生授权；先判断 transport 是否允许，再检查业务主体、快照与批准。

追问：给了保存 scope 就应该写入吗？

答题要点：仍须当前任务允许和宿主业务批准；用只有 scope 与完整匹配的两条本地结果对照。

Q3所有拒绝用例都没有保存行，但没有正控。可以合并吗？

参考回答：不因此合并。可能根本没有效果入口；确认允许路径确有分发、写入和持久行，再验负路径三者都为零。

追问：有分发、零写入是不是和入口拒绝一样？

答题要点：不是。它证明下游安全网拦住了，不能证明要求的上游不分发。

Q4批准页面显示快照有效，但人工处理拖了十分钟。执行时怎么看？

参考回答：用当前主体与 scope、当前快照、未撤销的批准重新判断；不要把审核页面上的旧信息当执行凭据。

追问：执行稳定，是否能把批准原文记进普通遥测？

答题要点：普通轨迹只放关联键和结果类别。需保留的批准状态应在专用访问与保留策略下审计。

小结与一手参考

证据不授予权限；业务批准不能从建议推断。分别计数建议、分发、效果尝试和提交，用一条真正有效的正控验证效果观察点。

  • NIST SP 800-53 Rev. 5：AC-3 访问强制、AC-6 最小权限；课程不作合规背书。
  • MCP Authorization（课程固定修订）：把 transport 授权与应用领域审批分开。
