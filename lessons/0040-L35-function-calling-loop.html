完整 Function Calling 循环

把单步工具调用跑成一个 while 循环——这就是 Agent Loop 的骨架

💡 为什么这课重要？

L27 讲透了 Function Calling 的原理：模型只输出"我要调哪个工具、传什么参数"的意图，执行和回填由你完成。但那只是一来一回的单步。真实任务往往不是一步能完成的——模型可能先调工具 A、看结果、再调工具 B、……最后才给答案。

这一课把单步展开成一个循环：只要模型还在请求工具，就执行 + 回填，直到它给出最终文本答案。这个 while 循环不是某个花哨的技巧，它就是 Agent Loop 最核心的骨架——感知 → 行动 → 观察 → 再感知。Phase 4/6 里所有 Agent 架构，本质都建在这几行代码之上。写对它，你就握住了整个 Agent 的心脏。

学习目标

完成本课后，你将能够：

  • 说清为什么单步不够，为什么需要一个 while 循环反复"执行 + 回填"
  • 写出一个结构正确的完整 FC 循环（真实字段名、tool_call_id、json.loads/dumps）
  • 记住三个关键动作：把模型的 tool_calls 消息 append 回去、每个结果带对应 tool_call_id、循环到没有 tool_calls
  • 区分并行工具调用（一个回合多个工具）与多轮调用（多个回合串行）
  • 用最大轮数上限防止模型无限调工具（死循环）
  • 指出这个 while 循环就是 Agent Loop 的骨架

1. 回顾一步 → 展开成循环

L27 里那"一来一回"是这样的：你带 tools 发请求 → 模型返回 tool_calls → 你执行 → 回填 → 再发一次。问题是："再发一次"之后呢？ 模型看到工具结果，可能又要调下一个工具，而不是直接给答案。

用户："帮我查下北京天气，然后根据天气推荐今天穿什么。"

第 1 回合：模型说 → "先调 get_weather(city='北京')"   （还不能推荐，它还不知道天气）
   ↓ 你执行 + 回填："北京 3°C，大风"
第 2 回合：模型说 → 基于结果，给出最终文本 "今天冷且大风，建议羽绒服 + 围巾。"（不再要工具）

一步显然不够——第 1 回合模型只拿到了信息，还没做完事。它需要"看一眼结果再决定下一步"。把这个"看→决定→（可能再调）"的过程重复执行，直到模型不再要工具、给出最终答案，就是一个循环。

所以我们需要一个 while 循环，规则只有一条：只要模型这一回合还在请求工具（返回了 tool_calls），就执行它们、把结果回填、再发一次；一旦模型不要工具了（tool_calls 为空、直接给了文本），就结束循环、输出答案。 这正是把 L27 的单步"卷"起来。

Q 为什么单次"发→执行→回填"不够，要做成循环？
回填之后，模型看到工具结果，可能又要调下一个工具（比如先查天气、再据此推荐穿搭），而不是直接给答案。单步只覆盖"一来一回"；要走完一个多步任务，就得把"执行 + 回填"放进 while 循环反复做，直到模型不再要工具、给出最终文本。这个循环就是 Agent Loop 的雏形。

2. 完整循环代码（核心）

下面是整个循环的骨架。字段名（choices[0].message / tool_calls / function.name / function.arguments / tool_call_id）都是 OpenAI SDK 的真实结构，可对照官方文档逐一核对：

import json

messages = [{"role": "user", "content": "查北京天气，再据此推荐穿搭"}]

while True:
    resp = client.chat.completions.create(
        model=MODEL, messages=messages, tools=TOOLS,   # 型号以官网为准
    )
    msg = resp.choices[0].message

    if not msg.tool_calls:            # 模型不再要工具 → 这就是最终答案
        print(msg.content)
        break

    messages.append(msg)             # ① 把模型这条"工具请求"消息加回历史
    for tc in msg.tool_calls:        # ② 逐个执行工具（可能不止一个）
        args = json.loads(tc.function.arguments)          # arguments 是 JSON 串！
        result = dispatch(tc.function.name, args)         # 你的工具分发
        messages.append({            # ③ 把结果作为 tool 消息回填
            "role": "tool",
            "tool_call_id": tc.id,   # ★ 对应哪一次调用
            "content": json.dumps(result),
        })
    # 回到循环顶：模型基于刚回填的工具结果，决定下一步（再调 or 给答案）

这段代码短，但有三个关键点，漏一个循环就崩：

  • ① 模型的 tool_calls 消息要 append 回去（messages.append(msg)）。很多人只回填了工具结果，却忘了先把模型那条"我要调工具"的 assistant 消息放回历史——那样 tool 消息就"无主"了，API 会报错（每个 tool 消息必须能对上前面某个 tool_call）。
  • ② 每个 tool 结果要带对应的 tool_call_id。一个回合可能有多个工具调用，模型靠 tool_call_id 把"哪条结果对应哪次请求"配起来。用 tc.id 原样回填，别自己编。
  • ③ 循环条件是"直到没有 tool_calls"。if not msg.tool_calls: break 就是出口——模型不再举手要工具、直接给文本时收敛。

把这三点刻进肌肉记忆，你就能凭手写出整个 Agent 的执行内核。字段与回填格式的权威来源：OpenAI · Function calling guide。

Q 回填工具结果前，为什么要先 messages.append(msg)？
每个 role:"tool" 消息都要对应前面某个 tool_call（靠 tool_call_id 配对）。如果不先把模型那条带 tool_calls 的 assistant 消息 append 回历史，回填的 tool 消息就"无主"，API 会直接报错。顺序是固定的：先放模型的工具请求消息，再逐个放对应的 tool 结果。

3. 并行工具调用：一个回合，多个工具

模型在一个回合里可以一次返回多个 tool_calls——比如"帮我对比北京和上海的天气"，它可能一口气要求调两次 get_weather。这就是并行工具调用。第 2 节的 for tc in msg.tool_calls 循环已经处理了它：遍历全部调用、逐个执行、各自带 tool_call_id 回填。

# 模型一个回合返回多个 tool_calls（简化形状）
msg.tool_calls == [
    tc(id="c1", function=(name="get_weather", arguments='{"city":"北京"}')),
    tc(id="c2", function=(name="get_weather", arguments='{"city":"上海"}')),
]
# → for 循环执行两次，各自用 c1 / c2 的 id 回填，模型下一回合再汇总对比

易错点：别只取第一个。 msg.tool_calls[0] 只处理了一半，另一个工具的结果没回填，模型就会"缺一条腿"——要么报错（有 tool_call 没对应的 tool 结果），要么答得残缺。永远 for 遍历全部。

因为这几个调用互不依赖（查北京不需要先知道上海），它们可以并发执行提速——呼应 L16 的 asyncio.gather：把两次 get_weather 同时发出去，总耗时约等于最慢那个，而不是两个相加。对 Agent 来说这很实在：一个回合要调 5 个 API，串行等 5 秒，并发可能 1 秒。

4. 多轮 vs 并行：别把两个概念搅在一起

"并行"和"多轮"听起来像，其实是两个正交的维度，面试常被追问，务必分清：

并行工具调用（一个回合，横向铺开）
   模型这一回合同时要 A、B、C  →  你全部执行、各自回填  →  下一回合汇总
   前提：A/B/C 互不依赖（查北京 / 查上海，谁先都行）→ 可并发提速（L16）

多轮工具调用（多个回合，纵向串行）
   回合1：调 A（查天气）      → 回填
   回合2：看了 A 的结果，才决定调 B（据天气推荐）→ 回填
   回合3：给最终答案
   前提：B 依赖 A 的结果（不查到天气，没法推荐穿搭）→ 只能一轮一轮来

一句话记：并行是"一个回合里宽"，多轮是"跨回合深"。 两者可以叠加——某一回合并行调 3 个工具，看完结果这一回合再串到下一回合调更多。而承载这一切的容器，正是第 2 节那个 while 循环：循环负责"多轮"（一圈就是一个回合），循环体里的 for 负责"并行"（一圈内的多个工具）。

Q "并行工具调用"和"多轮工具调用"的区别是？
并行：模型在同一个回合返回多个 tool_calls（它们互不依赖，可并发执行）——由循环体内的 for 处理。多轮：跨多个回合串行，后一个工具依赖前一个的结果（先查天气才能推荐穿搭）——由外层 while 循环处理。一个是"横向铺开"，一个是"纵向推进"，可以叠加。

5. 防死循环：给循环装个"闸"

while True 有个隐患：万一模型"想不明白"，一直反复要工具、永不给最终答案怎么办？ 那循环就停不下来——烧钱、卡死、甚至打爆下游 API。生产代码必须给它装个闸：设一个最大轮数上限。

MAX_TURNS = 8            # 上限：最多循环 8 回合

for turn in range(MAX_TURNS):        # 用 for 天然带上限，比 while True 更稳
    resp = client.chat.completions.create(model=MODEL, messages=messages, tools=TOOLS)
    msg = resp.choices[0].message
    if not msg.tool_calls:
        print(msg.content); break
    messages.append(msg)
    for tc in msg.tool_calls:
        args = json.loads(tc.function.arguments)
        messages.append({
            "role": "tool", "tool_call_id": tc.id,
            "content": json.dumps(dispatch(tc.function.name, args)),
        })
else:                                 # for-else：没 break（跑满上限也没收敛）
    print("达到最大轮数，未能完成——需要人工介入或返回兜底回答")

把 while True 换成 for turn in range(MAX_TURNS)，就天然有了硬上限；配合 for-else，跑满还没收敛时能给出兜底处理（返回错误、降级答复、或转人工），而不是无声地卡住或无限烧钱。

这正是 L31 的预算思想在 Agent 循环里的落地：Token 有预算、延迟有预算，"步数"同样要有预算。任何会自主循环的系统，都必须有一个"最多做多少"的闸——这是 Agent 从"能跑"到"敢上生产"的分水岭。

6. 回到 Agent：这个 while 循环就是 Agent Loop 的骨架

现在把第 2 节那段代码换个视角看——它不只是"FC 循环"，它就是 Agent Loop 本身。Agent 的经典四拍——感知 → 行动 → 观察 → 再感知——每一拍都对得上循环里的一行：

感知（Perceive） = 模型看当前 messages，输出下一步意图
                    msg = resp.choices[0].message  →  msg.tool_calls
行动（Act）       = 你的代码真正执行工具
                    dispatch(tc.function.name, args)
观察（Observe）   = 把工具结果回填进 messages
                    messages.append({"role":"tool", ...})
再感知（Loop）     = 回到循环顶，模型基于新观察决定下一步
                    while / for turn in range(MAX_TURNS)

出口：模型不再要工具（给出最终文本）→ 任务收敛

换句话说，你刚写的这几行，已经是一个能自主多步推进、并行调工具、直到收敛的最小 Agent。Phase 4 讲的 ReAct、Plan-and-Execute，Phase 6 讲的多智能体协作，剥到最里层，核心都是这个"感知-行动-观察"的循环——只是在感知里加了规划、在观察里加了记忆、在出口处加了反思。

所以这一课是整个 Agent 部分的地基。 L27 给了你"手"（单次调用），这一课把手接上了神经和肌肉（循环）。下一课 L36 会让这个循环更健壮——工具报错怎么办、几十个工具怎么优雅注册与分发，把这个骨架养成能扛生产的躯干。

动手练习

先在脑子里把循环跑一遍，再展开对照——能"手动模拟"循环，才算真懂它。

练习：给"查天气 → 据天气推荐穿搭"的场景，说明这个 while 循环会跑几个回合、每回合发生什么

场景：用户说"查一下北京今天的天气，然后根据天气告诉我该穿什么。" 工具只有一个 get_weather(city)。请说明第 2 节的循环会跑几圈、每圈里 msg.tool_calls 是什么、messages 怎么变化。

循环会跑 2 个回合（外层循环 2 圈）：

【回合 1】发出 messages=[user]
  模型判断：要推荐穿搭，得先知道天气 → 返回 tool_calls
  msg.tool_calls == [ tc(id="c1", name="get_weather", arguments='{"city":"北京"}') ]
  → not msg.tool_calls 为 False，不 break
  → ① messages.append(msg)               # 放回模型的工具请求
  → ② 执行 get_weather("北京") == {"temp": 3, "wind": "大风"}
  → ③ messages.append({role:"tool", tool_call_id:"c1",
                        content:'{"temp":3,"wind":"大风"}'})
  此时 messages == [user, assistant(带tool_calls), tool(c1的结果)]
  → 回到循环顶

【回合 2】带着上面 3 条 messages 再发一次
  模型看到"3°C、大风" → 已经够了，不再要工具，直接给文本
  msg.tool_calls == None（或空）
  → not msg.tool_calls 为 True → print(msg.content); break
  输出："北京今天 3°C 还有大风，建议羽绒服 + 围巾，注意保暖。"

要点自检：① 这是多轮（不是并行）——因为"推荐穿搭"依赖先查到的天气，两个动作必须串行、跨两个回合。② 第 1 回合模型只拿信息、不给答案；第 2 回合才收敛。③ 每圈都严格执行"append 模型消息 → 执行 → 带 tool_call_id 回填"三步。如果工具改成"同时查北京和上海"，则会变成一个回合里两个 tool_calls（并行），由 for 处理，循环仍只需约 2 圈。

可运行性说明：上面代码的方法名（chat.completions.create）、字段名（tool_calls / function.name / function.arguments / tool_call_id）都是 OpenAI SDK 的真实结构，json.loads(arguments) 与回填时的 json.dumps(result) 都是必需的。完整跑通需要 pip install openai 和 OPENAI_API_KEY（见 L25）；没有 key 时，你可以把每一回合的 resp 手动 mock 成上面的形状，先把"循环 + 执行 + 回填"这段应用侧逻辑跑通。

🎯 速查卡：完整 FC 循环

【一句话本质】
  把 L27 的单步"发→执行→回填"卷进一个 while 循环，
  直到模型不再要工具、给出最终文本 → 这就是 Agent Loop 骨架

【循环骨架】
  while True:
      msg = client.chat.completions.create(...).choices[0].message
      if not msg.tool_calls:            # 出口：模型给了最终答案
          print(msg.content); break
      messages.append(msg)              # ① 模型的工具请求消息，先放回历史
      for tc in msg.tool_calls:         # ② 遍历全部（并行也在这处理）
          args = json.loads(tc.function.arguments)   # arguments 是 JSON 串
          result = dispatch(tc.function.name, args)  # 你执行
          messages.append({             # ③ 结果回填，带 tool_call_id
              "role":"tool", "tool_call_id": tc.id,
              "content": json.dumps(result)})

【三个必记关键点】
  ① 模型的 tool_calls 消息要 append 回去（否则 tool 消息无主、报错）
  ② 每个 tool 结果带对应 tool_call_id（tc.id 原样回填）
  ③ 循环到没有 tool_calls 为止（if not msg.tool_calls: break）

【并行 vs 多轮】
  并行 = 一个回合多个 tool_calls（互不依赖）→ 循环体内 for，可并发(L16)
  多轮 = 跨回合串行（B 依赖 A 的结果）      → 外层 while，一圈一回合
  可叠加：某回合并行 3 个，看完再串到下一回合

【防死循环】
  for turn in range(MAX_TURNS)  代替  while True
  配 for-else 兜底：跑满未收敛 → 报错/降级/转人工（预算思想 L31）

【Agent Loop 对应】
  感知=模型输出意图 / 行动=执行工具 / 观察=回填结果 / 再感知=回到循环顶

总结

  • 单步不够——模型看完结果可能再要工具，所以要把"执行 + 回填"卷进一个 while 循环，直到它给出最终文本
  • 循环三个关键点：① 模型的 tool_calls 消息要 append 回去；② 每个结果带对应 tool_call_id；③ 循环到没有 tool_calls 为止
  • 并行=一个回合多个工具（循环体内 for，可并发提速 L16）；多轮=跨回合串行（外层 while，后者依赖前者结果）
  • 生产必设最大轮数上限防死循环（for range(MAX_TURNS) + for-else 兜底，呼应 L31 预算思想）
  • 这个 while 循环就是 Agent Loop 的骨架：感知 → 行动 → 观察 → 再感知，Phase 4/6 的架构都建在它之上
面试高频 · "并行工具调用怎么处理？"：一个回合里模型可能返回多个 tool_calls，要全部执行、各自带 tool_call_id 回填（用 for 遍历，别只取第一个）；因它们互不依赖，可并发（asyncio.gather）提速。而整个 FC 循环是一个 while 循环，跑到模型不再要工具为止，并且要设最大轮数上限防死循环。能把"并行（一回合内 for）vs 多轮（跨回合 while）"和"防死循环"一起说清，就答到点子上了。下一课我们把这个骨架养壮：工具健壮性 + 注册。有疑问随时问我。
