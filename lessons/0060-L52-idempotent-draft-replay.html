副作用已提交但响应丢失

Harness 用原操作 ID 重放本地草稿保存，不多写一份

为什么这课重要？

工单草稿已经保存，Harness 却在标记完成前失去了调用结果。恢复时，检查点仍显示「待保存」：如果把它当成「肯定没写」，Agent 就可能再建一份草稿。L31 已讲如何判断重试是否安全；这课把那条契约用在续跑的任务上，不再讲退避策略。

学习目标

  • 恢复时从检查点取回稳定的操作 ID，而不是为每次尝试生成新 ID。
  • 用本地故障点验证草稿与回执同库提交，丢响应后重放返回原编号，草稿仍只有一份。
  • 外部结果未知时，区分「有可信回执」「确认未生效且不会再生效」和「仍需核对」。

1. 检查点找回操作，回执说明效果

任务 ID 用来找回流程；操作 ID 标识其中一次具体业务意图。同一个任务以后可以有另一次独立操作，但同一次保存不管重跑几次，都用第一次写入检查点的 op_id 和原草稿内容。示例的 op-demo-52 是固定测试数据；工程中应在首次调用前生成并持久化，不能在恢复分支里重新生成。

本例假定保存步骤已获准，只演练单租户、单动作的本地写入；不以检查点替代 L51 的审批验证。检查点在收到结果后才另行标记完成，刻意留下「草稿已存，任务未完成」的窗口。SQLite 的同一个事务把草稿和操作回执一起提交；回执保存原操作 ID、原内容和原草稿编号。重放从回执读编号，同键不同内容报冲突，不覆盖原草稿。只要记录保留，反复执行同一保存步骤最多产生一次已提交的本地草稿；这既不保证一定成功，也不是对外部效果的保证。

Q 本地草稿已提交，响应丢失，检查点仍待保存。怎样拿到真实的草稿编号？
检查点没有证明未执行，草稿文本也不是编号。用原操作键找到同事务提交的回执，核对内容后取回原编号，不再写入。

2. 按时间线找故障：到底停在了哪一步？

先按正常顺序走一遍：① 检查点保存 op-demo-52 和原草稿，状态 ready_to_save；② 同一 SQLite 事务写入草稿行与回执行，回执行把原操作 ID、正文和编号绑在一起；③ 事务成功提交，独立连接能同时查到两行；④ 调用方拿到编号，另行把检查点改成 done。第 ③ 步是本地效果的分界线，第 ④ 步只是流程确认，两步之间有故障窗口。

断点能确认的事实恢复后的下一步
事务未提交，且已确认回滚本课的 after_draft_insert 已执行一条 INSERT，但事务回滚；独立连接查到草稿、回执都是 0 行。获准后沿用原操作 ID、原草稿重新保存；不是把旧任务换成新任务。
已提交，响应没有到达after_commit_before_reply 发生后，两张表各 1 行，但检查点仍待保存。没收到编号不代表没有效果。同键同内容查到回执就返回原编号，推进检查点；同键不同内容报冲突，不覆盖原草稿。
外部依赖超时，缺可信结果只知道没收到响应；本地库的状态不告诉我们对端是否受理或提交。保留未知并核对原请求，不按本地「待保存」直接重发。

因此，调这类故障先分别看检查点、业务行、回执，不要只看日志里的异常类型。两行都在却重复写，查操作 ID 是否在恢复时被重新生成；只有其中一行，查是否拆成了两个事务。切勿把所有发生在 COMMIT 附近的异常都归为「已经回滚」：表中第一行的前提是已确认回滚。本课用定点异常和新连接验证这些分支，不模拟断电或磁盘故障。

3. 外部结果未知：先核对，不猜测

本地回执只能证明本地效果。外部调用若超时，先保留「结果未知」，用原操作 ID 或业务引用在原作用域内查询权威状态或核对可信回执。例如内部库已留货，不代表承运商已确认预约；即使 HTTP 请求放在 SQLite 事务代码块内，回滚也撤不回外部动作。本课用固定查询结果演练保守分支，不调用服务：

  • 确认已生效：记下原结果，不再发写入请求。
  • 确认未生效，且原请求不会迟到生效：交给业务复核是否补做；本例只返回建议，不自动写入。
  • 查不到或仍不能确定：保留未知，停止自动动作并交人工核对，不换键、不换路。普通「未找到」不是最终确认。

如果供应商明确保证安全重放，可按其文档在约定作用域和保留期内用原键、原参数重放。自己保存一个键、检查点或本地回执，都不能让外部系统自动去重。

自检：两次都用新连接查表，草稿和回执应始终各一行；恢复返回回执中的原草稿编号。

import sqlite3
from contextlib import closing
from pathlib import Path
from tempfile import TemporaryDirectory


class SimulatedCrash(RuntimeError):
    pass


def save_draft(path, op_id, body, crash_at=None):
    with closing(sqlite3.connect(path, isolation_level=None)) as db, db:
        db.execute("BEGIN IMMEDIATE")  # 先开启写事务，再检查回执。
        saved = db.execute("SELECT body, draft_id FROM receipts WHERE op_id=?",
                           (op_id,)).fetchone()
        if saved is not None:
            original_body, draft_id = saved
            if body != original_body:
                raise ValueError("same operation ID, different draft")
        else:
            draft_id = db.execute("INSERT INTO drafts (body) VALUES (?)", (body,)).lastrowid
            if crash_at == "after_draft_insert":
                raise SimulatedCrash(crash_at)  # 异常离开事务，未提交的草稿回滚。
            db.execute("INSERT INTO receipts VALUES (?, ?, ?)", (op_id, body, draft_id))
    if crash_at == "after_commit_before_reply":
        raise SimulatedCrash(crash_at)  # 两行已提交，但调用方拿不到编号。
    return draft_id


def resume(path, task_id, crash_at=None):
    with closing(sqlite3.connect(path)) as db:
        op_id, body, state = db.execute(
            "SELECT op_id, body, state FROM checkpoints WHERE task_id=?", (task_id,),
        ).fetchone()
        if state == "done":
            return db.execute("SELECT draft_id FROM receipts WHERE op_id=?",
                              (op_id,)).fetchone()[0]
    draft_id = save_draft(path, op_id, body, crash_at)
    with closing(sqlite3.connect(path)) as db, db:
        db.execute("UPDATE checkpoints SET state='done' WHERE task_id=?", (task_id,))
    return draft_id


def snapshot(path):
    with closing(sqlite3.connect(path)) as db:
        return (
            db.execute("SELECT op_id, body, state FROM checkpoints").fetchone(),
            db.execute("SELECT id, body FROM drafts").fetchall(),
            db.execute("SELECT op_id, body, draft_id FROM receipts").fetchall(),
        )


def simulate_loss(path, task_id, point):
    try:
        resume(path, task_id, crash_at=point)
    except SimulatedCrash as exc:
        assert str(exc) == point
    else:
        raise AssertionError(f"missing simulated crash: {point}")


def reconcile_external(op_id, observations):
    # observations 只含测试提供的查询结果；不联网、不执行补写。
    status, receipt = observations.get(op_id, ("unknown", None))
    if status == "committed" and receipt is not None:
        return "record_existing", receipt
    if status == "final_no_effect":  # 权威来源确认原请求不会再生效。
        return "review_retry", None
    return "needs_manual_review", None

最佳实践：先查原操作的效果证据，再决定是否重放

适用：恢复时检查点仍待保存，调用方没拿到结果；本地草稿与回执可由同一 SQLite 事务提交。边界：回执只证明该库的效果；外部超时不是回滚证明。没有供应商的明确安全重放契约，证据不明就停止，不盲重试。

错误：把丢响应当作未执行

同一草稿在提交后丢了编号，Harness 看到待保存便换键重写，本地可能多出一份；再用同样逻辑处理外部「未找到」，也可能在原请求迟到时造成重复效果。

正确：沿原操作标识核对提交证据

同样丢编号，本地从原键回执取回原编号，计数仍为一；同键改内容则报冲突。外部仍是「未找到」时保持未知，不发第二次请求，由人工核对。

原因与代价：检查点进度、提交和响应是三个事件，响应缺失不能推断提交结果。同库事务让草稿和回执一起出现或一起回滚；需承担操作标识持久化、参数绑定、回执存储与保留期成本。外部若支持明确的幂等契约，可在约定时限内按原作用域、键和参数重放；未知且无这种保证时，宁可暂停。参见 SQLite 的原子提交说明和 AWS 关于迟到请求与同键不同意图的说明。

  1. 运行原重放验收。先分别预测提交前、提交后丢响应、恢复后的检查点状态、草稿和回执行数。
  2. 在临时副本中将 after_commit_before_reply 的抛错挪入事务，再运行；复原后核对同键异内容和外部「未找到」的负例。

结果诊断：完整版本只输出 L52 ACCEPTED。挪动故障点会使提交后应各有一行的断言失败，说明测成了回滚而非丢响应；重放后有第二份草稿则查操作键和回执匹配；外部查不到仍建议补做则查是否把查询滞后误当成最终未生效。

本课最佳实践验收：库内留货与承运商预约不是同一笔提交

任务：仓库已经提交本地留货，承运商取件预约却超时。先为「普通未找到」「确认生效但缺回执」「查到的是另一单」「同一单的有效回执」「最终确认未生效」分别写出处理决定和发出预约请求的次数。不可用库内留货回执替代取件回执。

这里没有网络。固定夹具表现「查询结果暂时不可见，但第一次请求随后生效」；只有权威方能断言旧请求已终结且不会迟到生效。这个承运商夹具不承诺安全重放，所以任何分支都不自动再发；确认无效果的分支只供人工复核。

import sqlite3
from contextlib import closing
from dataclasses import dataclass
from pathlib import Path
from tempfile import TemporaryDirectory


@dataclass(frozen=True)
class CarrierEvidence:
    reference: str
    status: str
    receipt: str | None = None


class CarrierFixture:
    def __init__(self):
        self.requests = []
        self.pickups = {}
        self.evidence = {}

    def request_with_lost_response(self, reference):
        self.requests.append(reference)
        raise TimeoutError("pickup response missing")

    def observe(self, reference):
        return self.evidence.get(reference)


def start_pickup(carrier, reference):
    try:
        carrier.request_with_lost_response(reference)
    except TimeoutError:
        return "unknown"
    raise AssertionError("missing simulated timeout")


def reconcile(carrier, reference):
    evidence = carrier.observe(reference)
    if evidence is None or evidence.reference != reference:
        return "needs_manual_review", None
    if evidence.status == "committed" and evidence.receipt:
        return "record_existing", evidence.receipt
    if evidence.status == "final_no_effect" and evidence.receipt is None:
        return "review_retry", None  # 决策建议，不发预约请求。
    return "needs_manual_review", None

        pending = store.stage(actor, "export", 2, lab["QUESTION"])
        denied = store.stage(actor, "declined", 1, lab["QUESTION"])
    assert pending.status == "pending" and pending.op_id is None
    assert pending.draft != old.draft and effects(path) == []

    with open_store(path) as store:
        assert store.checkpoint(actor, "export") == pending
        for caller, binding, decision in (
            (actor, pending.binding, None),  # 模拟宿主还没有收到人工决定。
            (other, pending.binding, Review.APPROVE),
            (actor, old.binding, Review.APPROVE),
            (actor, replace(pending.binding, action="submit"), Review.APPROVE),
        ):
            assert store.resume(caller, "export", binding, decision).status == "rejected"
            assert store.checkpoint(actor, "export") == pending and effects(path) == []
        assert store.resume(actor, "declined", denied.binding, Review.DENY).status == "denied"
        assert effects(path) == []
        assert store.resume(actor, "declined", denied.binding, Review.APPROVE).status == "denied"
        assert effects(path) == []
        try:
            store.resume(actor, "export", pending.binding, Review.APPROVE, lose_reply=True)
        except LostReply:
            pass
        else:
            raise AssertionError("expected reply loss after commit")

    rows = effects(path)
    assert len(rows) == 1 and rows[0][1:4] == (actor.tenant, actor.name, "export")
    assert json.loads(rows[0][4]) == [pending.draft.title, pending.draft.body,
                                    list(pending.draft.source_ids)]
    with open_store(path) as store:
        committed = store.checkpoint(actor, "export")
        assert committed == replace(pending, status="saved", op_id=rows[0][0])
        assert committed.op_id
        replay = store.resume(actor, "export", pending.binding, Review.APPROVE)
        assert (replay.status, replay.op_id, replay.draft) == (
            "replayed", committed.op_id, pending.draft,
        )
        assert effects(path) == rows

    # 仅破坏临时夹具的引用：实际保存行仍在，但检查点指向一个不存在的结果。
    with closing(sqlite3.connect(path)) as db, db:
        db.execute("UPDATE checkpoints SET op_id=? WHERE tenant=? AND actor=? AND job=?",
                   ("missing-result", actor.tenant, actor.name, "export"))
    with open_store(path) as store:
        result = store.resume(actor, "export", pending.binding, Review.APPROVE)
        assert (result.status, result.op_id, result.draft) == ("inconsistent", None, None)
        assert effects(path) == rows

结果诊断：换连接后找不到原版本，先查路径和检查点提交；负例有行，查当前决定和绑定是否在写入前校验；模拟丢响应后零行，查故障点是否放在提交前；重放换了操作 ID 或多出行，查是否复用了原操作与结果。对账不一致后行数或内容变了，查是否把缺失证据误判为可以补写。

文字知识图

  • 任务 ID → 原检查点 → 原操作 ID 与原草稿。
  • 本地提交前失败 → 两表都无记录；提交后丢响应 → 草稿与回执均在，续跑取回原编号。
  • 同键换内容 → 冲突，不改原写入；外部结果未知 → 核对权威状态，仍无定论就交人工。

面试自查

先合上答案，按「结论 → 理由 → 如何验证」作答，再展开追问。

Q1同一任务第一次保存丢了响应，第二次续跑该沿用哪个 ID？

参考回答：用任务 ID 找检查点，沿用首次保存前落盘的操作 ID 和原正文。一个任务可有多个操作，每次尝试的编号也可不同，但都不能代替标识本次业务意图的操作 ID。核对两次使用同一个操作 ID，重放取回原编号且草稿仍只有一行。

追问：第二次仍用原操作 ID，却传了改过的正文，怎么办？

答题要点：报冲突，原草稿和回执都不变。确实要保存新版时，走另一个业务操作并重新满足审批规则。

Q2草稿插入后确认回滚，与提交后丢响应，检查点都待保存，如何区分？

参考回答：从新连接查草稿和回执。两者同事务提交，确认回滚时应各零行，仍获准时可按原操作保存；提交后丢响应时应各一行，应读原回执而不重写。分别在两处注入故障，核对两表、检查点与恢复返回的编号。

追问：新连接查到草稿，却没有对应回执，能按「未保存」处理吗？

答题要点：不能。这不符合两者原子提交的预期；先停止补写，检查事务边界和查询键是否一致，再查明原操作的效果。

Q3仓库已留货，但承运商预约超时且暂时查不到，如何处理？

参考回答：保留「预约结果未知」，在原作用域按原引用核对权威状态，不自动重发。留货回执只证明本地效果，预约查询可能滞后。用夹具模拟先未找到、后迟到生效，断言请求数始终为一，最终登记原预约回执。

追问：查询返回「已提交」和回执，但引用是另一单，能结束对账吗？

答题要点：不能。证据必须绑定原请求；错单回执与缺回执一样，不能确认效果，应保持未知并交人工核对。

Q4假设对端只承诺 24 小时内安全重放，23 小时与 25 小时的未知请求能否同样处理？

参考回答：不能。按对端约定的起算点确认仍在窗口内，且当前策略仍允许时，才可用原作用域、原键和原参数重放；到期后同键可能被当作新请求，应暂停写入并核对。用固定时钟与对端替身检查窗口两侧：前者只允许按原请求重放，后者不得发写入。

追问：超过窗口后，什么证据才足以把「未知」转为「可复核是否补做」？

答题要点：权威来源确认原请求最终未生效、也不会迟到生效；仅未找到不够。即使拿到该确认，本课也只给复核建议，不自动补写。
