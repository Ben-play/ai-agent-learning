类、对象与 @dataclass

@dataclass 是 Agent 数据模型的起点 — Message、ToolCall、AgentState 都从这里来

💡 为什么这课重要？

Agent 系统里到处是"数据模型"：一条消息、一次工具调用、整个 Agent 的状态。用普通 dict 存这些数据，字段拼错了也不报错；用 @dataclass，字段清晰、自带比较和打印，代码立刻规整。

而且到 L14 你会用 Pydantic 做带校验的模型——@dataclass 是它的"前身"。搞清楚"什么时候用 dataclass、什么时候上 Pydantic"是高频面试题。

学习目标

完成本课后，你将能够：

  • 写一个类，区分实例属性、类属性、self
  • 区分实例方法 / @classmethod / @staticmethod
  • 用 @dataclass 快速定义数据模型
  • 用 field(default_factory=...) 安全地给可变默认值
  • 用 frozen=True 定义不可变模型，并说清 dataclass vs Pydantic

1. 类的基础：属性与方法

类是"把数据和操作它的函数打包在一起"的模板——它本身不是数据，只是造数据的图纸。前面学的函数是零散的动作，而一个 Agent 既有状态（名字、配置、对话历史）又有行为（回复、调工具）——用类正好把两者收在一处。

写 class Agent: 只是定义模板；真正产生一个能用的对象要靠实例化——调用类本身，像函数一样传参：Agent("bot")。这一步会先造出一块空白的实例，再自动调用 __init__，把传进来的参数写成这个实例自己的属性。a = Agent("bot") 之后，a 就是指向这个具体实例的变量；同一个类可以实例化出无数个互不影响的对象。__init__ 里第一个参数 self，指的就是"正在被创建、正在被初始化的那个实例"——之后每次通过 a.xxx 调用方法，Python 都会把 a 自动传进去，绑定成方法内的 self。

认清一个类的"三件套"：类属性（定义在类体里，默认所有实例共享读取）、实例属性（每个实例独有，通常在 __init__ 里用 self.xxx = ... 设置）、方法（类里定义的函数，按用途分三种，不是"第一个参数永远是 self"）。

class Agent:
    default_model = "claude"          # 类属性：定义在类体里

    def __init__(self, name):
        self.name = name              # 实例属性：每个实例独有

    def greet(self):                  # 实例方法：约定第一个参数是 self
        return f"{self.name}@{self.default_model}"

    @classmethod
    def make_default(cls):            # 类方法：拿到类本身(cls)，常用作"工厂"
        return cls("default")

    @staticmethod
    def is_valid(name):               # 静态方法：不接收隐式的 self/cls
        return bool(name)

a = Agent("bot")              # 实例化：调用类 → 创建实例 → 自动执行 __init__
print(a.greet())              # bot@claude
print(Agent.make_default().name)   # default
print(Agent.is_valid(""))    # False
  • 实例化：Agent("bot") 这一步——调用类本身，产出一个新实例，并自动触发 __init__ 初始化字段
  • self：实例方法里指向"当前这个实例"；只是约定俗成的命名，不是语法关键字
  • 实例方法：惯例上第一个参数是 self，Python 调用 a.greet() 时自动把 a 传进去
  • @classmethod：第一个参数是类本身 cls，常用来写"另一种构造方式"（工厂方法）
  • @staticmethod：不接收隐式的 self/cls，只是逻辑上归属这个类的普通函数
⚠️ 类属性遮蔽与共享陷阱：

访问 a.default_model 时，Python 先找实例自己有没有这个属性，没有才去类上找——所以类属性其实是"默认从类上读取"。写 a.default_model = "gpt" 并不会修改类属性，只是给 a 这个实例新建了一个同名的实例属性，把类属性遮蔽掉了；其他实例和类本身都不受影响。

真正危险的是可变类属性：如果类属性是 list/dict 这类可变对象，比如 history = []，那么所有没有遮蔽它的实例都在共享同一个对象——一个实例 a.history.append(x) 会让 b.history 也看到这条记录。这才是"共享状态陷阱"，和 L03 讲的可变默认参数是同一类坑。

Q @classmethod 的第一个参数是什么？
类方法的第一个参数是类本身 cls，所以能用 cls(...) 创建实例——这让它很适合写工厂方法（如 from_dict、make_default）。实例方法用 self，静态方法两者都不要。

2. @dataclass：一行省掉一堆样板

手写数据类要写 __init__、__eq__、__repr__…很啰嗦。@dataclass 自动帮你生成：

from dataclasses import dataclass, field

@dataclass
class Message:
    role: str
    content: str
    meta: dict = field(default_factory=dict)   # ⚠️ 可变默认值必须用 default_factory

m1 = Message("user", "你好")
m2 = Message("user", "你好")
print(m1)          # Message(role='user', content='你好', meta={})  ← 自动 __repr__
print(m1 == m2)    # True  ← 自动 __eq__（按字段比较）
🔑 Agent 开发关联：

field(default_factory=dict) 正是 L03/L05 讲的可变默认参数陷阱在 dataclass 里的正解——绝不能写 meta: dict = {}，dataclass 会当场抛 ValueError 阻止你这样写（就是为了帮你避开"所有实例共享同一个 dict"这个坑）。这个坑面试常考。

3. frozen 不可变模型

加 frozen=True，实例的字段就不能被重新绑定——适合表示"一旦产生就不该变"的数据，比如一次工具调用记录：

@dataclass(frozen=True)
class ToolCall:
    name: str
    args: dict

tc = ToolCall("search", {"q": "python"})
tc.name = "calc"          # ❌ FrozenInstanceError：字段不能重新赋值
tc.args["q"] = "changed"  # ✅ 能成功！args 指向的 dict 本身还是可变的
print(tc.args["q"])       # changed
⚠️ frozen 只是"浅层不可变"：

frozen=True 阻止的是字段重新绑定（tc.name = ... 这种赋值），并不会递归冻结字段内部的对象。如果字段本身是 list/dict 这类可变容器，容器内部的内容照样可以修改——上面例子里 tc.args 这个 dict 就被原地改了，tc 本身"没变"，但它引用的数据变了。

连带的后果：ToolCall 带了 dict 字段，试图 hash(tc) 会直接抛 TypeError（dict 本身不可 hash），并不会因为加了 frozen=True 就自动可 hash。frozen 也不等于自动线程安全——它只保证字段不会被重新赋值，多线程同时修改内部可变字段依然不安全。

如果确实需要一个可 hash、能进 set/当 dict key 的 ToolCall，字段本身也要换成不可变类型，比如把 args: dict 换成 args_json: str（先序列化）：

@dataclass(frozen=True)
class ToolCallKey:
    name: str
    args_json: str      # 不可变字段 → 整个实例才真正可 hash

print(hash(ToolCallKey("search", '{"q": "python"}')))  # 正常输出一个整数
Q dataclass 里给 list/dict 默认值，正确写法是？
可变默认值必须写 field(default_factory=list)，让每个实例各拿一个新列表。直接 = [] 会触发可变默认值共享的陷阱（dataclass 实际上会直接报错阻止你这么写）。这是 dataclass 版的"可变默认参数陷阱"。

4. dataclass vs Pydantic（面试高频）

@dataclassPydantic BaseModel
来源标准库，零依赖第三方库
数据校验不校验（类型注解只是提示）自动校验 + 类型转换
用途内部纯数据容器外部输入/输出、Tool Schema
JSON Schema不支持一键导出（喂给 LLM）

选择原则：内部传数据用 dataclass（轻、快）；一旦数据来自外部（用户、LLM、API）需要校验，或要生成工具 Schema，就用 Pydantic（L14 深入）。

知识图谱

类基础
├── 实例属性(self.x) vs 类属性(默认从类读取，实例可遮蔽)
├── 实例方法(self)
├── @classmethod(cls) → 工厂方法
└── @staticmethod → 归属类的工具函数

@dataclass
├── 自动 __init__ / __eq__ / __repr__
├── field(default_factory=...) → 可变默认值正解
└── frozen=True → 禁止字段重绑定（浅层），非深度不可变/非自动可 hash

dataclass vs Pydantic
├── dataclass：内部数据、不校验、零依赖
└── Pydantic：外部输入、自动校验、导 JSON Schema（→ L14）

实战练习

练习：用 @dataclass 定义 Agent 数据模型

为 Agent 定义三个核心数据模型，并思考它们和 Pydantic 的差异。先自己写，再看答案。

任务清单

  1. Message：role、content，可选 meta（dict，默认空）
  2. ToolCall：name、args（dict）——设为 frozen（调用记录不可变）
  3. AgentState：messages（Message 列表，默认空）、step（int，默认 0）、done（bool，默认 False）
  4. 给 AgentState 加一个方法 add(msg) 追加消息并让 step + 1
💡 点击查看参考答案 
from dataclasses import dataclass, field

@dataclass
class Message:
    role: str
    content: str
    meta: dict = field(default_factory=dict)

@dataclass(frozen=True)
class ToolCall:
    name: str
    args: dict

@dataclass
class AgentState:
    messages: list = field(default_factory=list)
    step: int = 0
    done: bool = False

    def add(self, msg: Message):
        self.messages.append(msg)
        self.step += 1


state = AgentState()
state.add(Message("user", "北京天气？"))
state.add(Message("assistant", "晴，25°C"))
print(state.step)              # 2
print(len(state.messages))     # 2
print(ToolCall("search", {"q": "天气"}))   # ToolCall(name='search', args={'q': '天气'})

思考题

先自己想，再点开对答案。

Q1如果 Message.content 传进来的是数字 123，dataclass 会报错吗？

不会报错。Message(role="user", content=123) 会照常创建，content 里就老老实实存着整数 123。

关键在于：dataclass 里的 content: str 只是类型注解，不是校验。Python 的注解在运行时不强制，@dataclass 也只拿它来生成 __init__/__repr__ 等样板，完全不检查你传进来的值是不是真的 str。所以传 123、None、一个列表，都能塞进去，直到后面某处把它当字符串用（比如 .strip()）才可能意外炸掉。

这正是「数据一旦来自外部（用户、LLM、API）就该用 Pydantic」的理由：换成 Pydantic BaseModel，content: str 会在构造时自动校验并尝试类型转换，类型不对直接抛错，把脏数据挡在门口。dataclass 负责「内部可信数据的容器」，校验的活交给 Pydantic（L14 深入）。

Q2为什么 ToolCall 适合 frozen，而 AgentState 不适合？frozen 的 AgentState 会发生什么？

因为 ToolCall 是「一旦发生就不该再变」的历史记录，而 AgentState 天生要随对话不断被修改。

ToolCall 记录的是「某一刻用某参数调了某工具」这一既成事实，把它设成 frozen=True 有两重好处：语义上宣告「这是不可篡改的日志」；防止代码不小心把 tc.name 这类字段整个重新赋值。但要注意，ToolCall 现在带 args: dict 字段——frozen 只挡得住字段重绑定，挡不住 tc.args["q"] = ... 这种内部修改，hash(tc) 也依然会因为 dict 不可 hash 而报错。真正「记录事实且可 hash」需要把可变字段换成不可变类型（如上面的 ToolCallKey）。

AgentState 恰恰相反——它的 add() 方法要 messages.append(msg)、要 step += 1，本质就是一个随 Agent Loop 逐轮累积、持续变化的状态对象。若把 AgentState 设为 frozen=True：self.step += 1 是对字段 step 重新赋值，会直接抛 FrozenInstanceError，方法跑不通；但 self.messages.append(msg) 只是修改 messages 这个 list 内部的内容、没有重新绑定字段本身，即使 frozen 也可能执行成功——这正说明 frozen 只挡字段重绑定，不是真正的深度不可变。想要 AgentState 整体真正不可变，需要连 messages 也换成不可变类型（如 tuple）并且每次「修改」都返回一个新实例。不可变适合「记录事实」，可变适合「承载过程」——这就是二者的分野。

面试常见问题

Q1：@dataclass 帮你自动生成了哪些方法？

答：主要是 __init__、__repr__、__eq__（按字段比较）；加 frozen=True 会阻止字段重新绑定（浅层不可变），但不会递归冻结内部对象——若字段本身是 dict/list，实例本身仍可能不可 hash，也仍需注意内部可变。省掉大量样板代码。

Q2：dataclass 和 Pydantic 有什么区别？怎么选？

答：dataclass 是标准库、不做校验，适合内部纯数据；Pydantic 自动校验并转换类型、能导出 JSON Schema，适合外部输入/输出和工具 Schema。数据来自外部或需要 Schema 就用 Pydantic。

Q3：dataclass 里怎么正确给列表/字典默认值？

答：用 field(default_factory=list)。直接写 = [] 会因可变默认值共享而被 dataclass 直接报错。

Q4：@classmethod 和 @staticmethod 区别？

答：classmethod 接收类 cls，能用来构造实例（工厂方法）；staticmethod 不接收 self/cls，只是逻辑上归属该类的普通函数。

总结

  • 实例属性归各实例；类属性默认从类上读取，实例可用同名属性遮蔽（可变类属性才是共享陷阱）
  • 实例方法惯例第一个参数是 self；@classmethod 拿 cls（写工厂方法），@staticmethod 归属类的工具函数
  • @dataclass 自动生成 __init__/__eq__/__repr__，写数据模型神器
  • 可变默认值用 field(default_factory=...)，别写 = []
  • frozen=True → 禁止字段重新绑定（浅层不可变），非深度不可变、非自动可 hash、非自动线程安全
  • 内部数据用 dataclass，外部输入/Schema 用 Pydantic（→ L14）
