工具健壮性与注册系统

让工具层在真实世界稳定行动 —— 参数校验、流式拼接、Token 预算，再用装饰器把工具变得可扩展

💡 为什么这课重要？

上一课（L35）你把 Function Calling 拼成了完整循环。但那还是"理想天气"下的循环——真实世界里，模型填的参数会出错、流式响应把工具调用切成碎片、工具一多 Token 就爆、手动维护工具列表根本不可扩展。这一课就是把循环从"能跑"升级到"扛得住生产"。

本课分两半：前半是工具健壮性（校验失败怎么办、流式怎么拼、Token 怎么省），后半是工具注册系统——用一个 @tool 装饰器自动注册 + 分发。这里会正式闭合 Phase 1 L11 埋下的"手写 @tool 装饰器"那条线：当时你学会了从函数签名生成 Schema，现在把它接进真实的 Agent 工具层。学完这课，你就看得懂 LangChain / Pydantic AI 的 @tool 在幕后到底怎么实现的。

学习目标

完成本课后，你将能够：

  • 把工具参数校验失败当成可回填的信号——用 Pydantic 校验，报错塞回让模型自我修正重试
  • 在流式响应中把分片到达的 arguments 增量拼成完整 JSON 再解析
  • 理解每个工具 Schema 的 Token 开销，据此决定"注册哪些工具、description 写多细"
  • 用装饰器实现一个工具注册表（Registry）：自动提取 Schema + 登记 + 名字到函数的分发
  • 说清"健壮的工具层"和"可扩展的注册系统"如何一起支撑 Agent

1. 健壮性①：参数校验失败，回填给模型重试

模型决定调用工具时，参数是它"猜"着填的——类型可能填错（qty 填成字符串）、字段可能缺失、值可能越界（page=-1）。哪怕开了 Structured Outputs（L28）约束结构，业务约束（"数量必须 ≥ 1"）仍可能被违反。

新手会直接把参数丢进函数，一崩整个 Agent 就死了。正确姿势：用 L14 的 Pydantic 校验，校验失败不要抛到顶层，而是把错误信息当成 tool 结果回填给模型——模型看到"你上次填错了什么"，会自己改正重试。这就是 L31 错误处理思想在工具层的落地，也和 L28 的"校验 + 重试自愈循环"是同一招。

from pydantic import BaseModel, Field, ValidationError

# 用 Pydantic 描述这个工具的参数契约（L14）
class SearchArgs(BaseModel):
    query: str
    max_results: int = Field(ge=1, le=50)     # 业务约束：1~50

def run_tool(name, raw_args: dict) -> dict:
    """执行一个工具调用；返回值会作为 tool 消息回填给模型。"""
    try:
        args = SearchArgs(**raw_args)          # ← 校验模型填的参数
    except ValidationError as e:
        # 关键：不 raise！把错误当成 tool 结果返回
        return {"ok": False, "error": e.errors()}   # ← 模型会看到并据此改正
    result = do_search(args.query, args.max_results)   # 校验通过才真正执行
    return {"ok": True, "data": result}

# 在 L35 的循环里，这条 tool 消息塞回 messages：
# {"role": "tool", "tool_call_id": call.id, "content": json.dumps(ret)}
# 模型下一轮读到 error，自己修好参数再调一次 —— 自我修正闭环

要点：① 校验（Pydantic）和执行（业务逻辑）分开——校验没过绝不碰真实副作用；② 错误信息要具体（Pydantic 的 e.errors() 会说清哪个字段、为什么），模型才知道怎么改；③ 错误走的是正常的 tool 返回通道，不是异常通道。

🔑 Agent 开发关联：

这一步是 Agent"在真实世界稳定行动"的核心。人类用错工具会看报错重来，Agent 也一样——把校验错误变成模型能读懂的反馈，它就获得了自我修正能力，而不是一遇脏参数就整轮崩溃。可靠 Agent 的信条：不信任模型的输出，但给它出错后自愈的机会。

Q 模型给工具填了非法参数（比如 max_results=-1），最稳的处理是？
用 Pydantic 校验参数，失败时不要 raise 崩掉，而是把具体错误信息作为 tool 结果回填进 messages，让模型看到自己错在哪、据此改正重试（自我修正闭环，呼应 L28/L31）。抛异常会让整轮 Agent 死掉；悄悄改默认值会掩盖问题、产生模型没预期的行为；直接跳过则丢了这步动作。

2. 健壮性②：流式响应里，增量拼接工具调用

当你用流式（L26）接收响应时，工具调用不是一次到齐的——模型把工具的 arguments（一段 JSON 字符串）切成很多 chunk 逐片吐出来。你不能拿到一片就 json.loads（那是残缺的 JSON，必然解析失败），得把所有 delta 片段按工具索引累加、拼成完整字符串，等这一轮结束再一次性 parse。

import json

# arguments 是分片到达的，用 dict 按 index 累加各工具的片段
buffers = {}     # index -> {"name": str, "args": str(累加中的 JSON 片段)}

for chunk in stream:
    delta = chunk.choices[0].delta
    for tc in (delta.tool_calls or []):
        buf = buffers.setdefault(tc.index, {"name": "", "args": ""})
        if tc.function.name:
            buf["name"] = tc.function.name          # 名字通常首片就给
        if tc.function.arguments:
            buf["args"] += tc.function.arguments    # ← 关键：把片段拼起来，别急着 parse

# 流结束后，缓冲区里才是完整 JSON，这时才解析
for idx, buf in buffers.items():
    args = json.loads(buf["args"])                  # 现在才是合法 JSON
    run_tool(buf["name"], args)                     # 交给第 1 节的校验+执行

心智模型：流式下的工具调用 = 一堆需要"按 index 归位再拼接"的碎片。名字一般首片就完整，而 arguments 是逐字符流过来的，所以用 += 累加、只在流结束后 parse 一次。多个并行工具调用则靠 tc.index 区分，各拼各的。（具体字段名以官方 SDK 文档为准。）

为什么 Agent 需要流式还要拼工具调用？流式让用户"边想边看"（体验好，L26），但工具调用必须等参数完整才能执行——半个 JSON 无法校验、无法调用函数。所以流式 Agent 的标准套路是：文本 delta 实时显示给用户，工具调用的 arguments 在后台默默累加，凑齐了再进第 1 节的校验+执行流程。

3. 健壮性③：工具定义的 Token 开销

容易被忽略的成本：你注册的每一个工具，它的 Schema（名字 + description + 参数结构）都要作为 input token 发给模型——而且每一轮都要发（L18 讲过一切都是 token；L34 讲过 Schema 设计）。工具越多，两个问题同时恶化：

  • 越贵：20 个工具的 Schema 可能就上千 token，每轮循环都重复计费（成本细节见下一课 L37）。
  • 越容易选错：给模型摆 30 把工具，它更可能挑错那一把、或纠结。工具集越聚焦，模型决策越准。

两条实操策略：

  • 只注册当前任务相关的工具——不要把全公司 50 个工具一股脑塞进去。按场景/子任务动态挑选一个小工具集（这也是为什么第 4 节的注册表要能"按需取子集"）。
  • description 精简但够用——写清"什么时候用它"，删掉废话。一句准确的描述胜过一段模糊的长文；token 省了，模型选得还更准。
Q 关于工具定义（Schema）的 Token 开销，下面哪句对？
每个工具的 Schema 都是 input token，每一轮都要重发（L18）。工具越多：越贵（重复计费，L37）且模型越容易选错那一把。对策是只注册当前任务相关的工具 + description 精简够用——不是写得越长越好，冗长反而费 token 又干扰决策。

4. 工具注册系统：用装饰器自动注册（闭合 L11 的线）

前三节都假设"工具已经登记好了"。但手动维护一个工具列表根本不可扩展——每加一个工具，你得手写 Schema、手动加进 tools=[...]、还得在 dispatch 里加一条 if name == ...。三处同步，迟早漏。

解法就是 L11 教的那套：用装饰器做自动注册。@tool 装饰一个函数时，一次做三件事：① 从类型注解 / docstring 提取 Schema；② 把它登记进注册表；③ 建立"名字 → 函数"的映射供分发。你只管专心写函数，Schema 生成、工具清单、分发全自动。

import functools, inspect, json

REGISTRY = {}          # 工具名 -> {"schema": {...}, "fn": callable}

# Python 类型名 → JSON Schema 类型名（str≠string 会生成非法 schema！）
_JSON_TYPE = {"str": "string", "int": "integer", "float": "number", "bool": "boolean"}

def tool(fn):
    """把普通函数注册成工具：自动抽 Schema + 登记 + 建分发映射。"""
    sig = inspect.signature(fn)                       # 读签名（呼应 L11/L05）
    props, required = {}, []
    for pname, p in sig.parameters.items():
        props[pname] = {"type": _JSON_TYPE.get(getattr(p.annotation, "__name__", ""), "string")}
        if p.default is inspect.Parameter.empty:      # 没默认值 = 必填
            required.append(pname)
    REGISTRY[fn.__name__] = {                          # ← ② 登记进注册表
        "schema": {                                    # ← ① 自动生成的 Schema
            "name": fn.__name__,
            "description": (fn.__doc__ or "").strip(), # docstring 就是 description
            "parameters": {"type": "object",
                           "properties": props,
                           "required": required},
        },
        "fn": fn,                                       # ← ③ 名字→函数，供 dispatch
    }
    @functools.wraps(fn)                                # 保住元信息（L11 强调过）
    def wrapper(*args, **kwargs):
        return fn(*args, **kwargs)
    return wrapper

# ---- 现在加工具，只需一个装饰器，别处零改动 ----
@tool
def web_search(query: str, max_results: int = 5) -> dict:
    "搜索网页并返回若干条结果。需要外部信息时使用。"
    return {"query": query, "n": max_results}

@tool
def get_weather(city: str) -> dict:
    "查询某城市的当前天气。"
    return {"city": city, "temp": 22}

# 自动生成"喂给 LLM 的工具清单"（第 3 节说的：可按需只取子集）
def tools_param(names=None):
    items = REGISTRY.values() if names is None \
            else (REGISTRY[n] for n in names)
    return [{"type": "function", "function": t["schema"]} for t in items]

print(json.dumps(tools_param(["web_search"]), ensure_ascii=False))
# 只把 web_search 的 schema 发出去 —— 呼应第 3 节"只注册相关工具"省 token

对比 L11：当时的 @tool 只做到"生成 Schema 存进 REGISTRY"；这一版把真实函数也一起存进去（"fn"），于是注册表既能产出工具清单、又能拿来分发。Phase 1 埋的"手写 @tool"这条线，到这里正式闭合成一个能用的 Agent 工具层。

🔑 这就是框架的底层原理：

LangChain 的 @tool、Pydantic AI 的工具注册，幕后做的正是这三件事：装饰器读函数签名 + 类型注解 + docstring → 自动生成 Schema → 登记 + 提供分发。区别只是它们用 Pydantic 把参数 Schema 做得更严谨（带校验、可导出标准 JSON Schema，正好接上第 1 节）。看懂了这一版，你就看懂了它们。

5. 分发（dispatch）：把工具名映射到真实函数

模型返回的工具调用里只有名字（字符串）和参数——它并不知道你的 Python 函数在哪。分发就是注册表的另一半价值：拿名字去 REGISTRY 查出真实函数并调用。这正是 L35 循环里"收到工具调用 → 执行 → 回填"那一步的实现。

def dispatch(name: str, args: dict) -> dict:
    entry = REGISTRY.get(name)
    if entry is None:                       # 模型幻觉出一个不存在的工具
        return {"ok": False, "error": f"未知工具: {name}"}   # ← 也回填让它改
    # 这里可以接第 1 节：先用 Pydantic 校验 args 再执行
    result = entry["fn"](**args)            # 名字 → 函数 → 调用
    return {"ok": True, "data": result}

# 在 L35 的循环中：
# for call in resp.tool_calls:
#     ret = dispatch(call.function.name, json.loads(call.function.arguments))
#     messages.append({"role": "tool", "tool_call_id": call.id,
#                      "content": json.dumps(ret, ensure_ascii=False)})

注意最后一环也呼应第 1 节：连"模型调了个不存在的工具"都不该崩——查不到就返回一条错误回填，模型自己换一个。注册（第 4 节）负责"工具进得来"，分发（本节）负责"调用出得去"，两者合起来才是完整的工具层。

Q 工具注册系统里，"分发（dispatch）"这一步做的是什么？
模型只返回工具名 + 参数。分发就是拿这个名字去注册表里查出对应的真实函数并调用它（名字 → 函数 → 执行），这是 L35 循环里"执行工具"那一步的实现。从签名生成 Schema 是"注册"（第 4 节）干的事；判断是否继续循环是循环控制（L35）的事——都不是分发。

6. 收束：健壮工具层 + 注册系统 = 可扩展的 Agent

把这一课两半拼起来看，它们各解决 Agent 的一个层面：

  • 健壮的工具层（第 1–3 节）→ Agent 能在真实世界稳定行动。参数校验回填让它自我修正、流式拼接让它在真实响应下不碎、Token 预算让它既省钱又选得准。工具是 Agent 伸向世界的手，手稳，行动才可靠。
  • 注册系统（第 4–5 节）→ 工具可扩展、可维护。加工具只需一个 @tool，Schema、清单、分发全自动；从"手动同步三处"变成"一处声明"。Agent 的能力边界能随业务持续扩张，而不是加一个工具改三个地方。

而这正是框架的底层原理——LangChain 的 @tool、各家 Agent SDK 的工具系统，本质就是"健壮性处理 + 装饰器注册 + 分发"这三件事的工程化封装。学完这课，你不再是"会调框架的人"，而是看得懂框架为什么这么设计、必要时能自己造一个的人。这就是从"用轮子"到"懂轮子"的跨越。

🛠 动手练习：写一个 @tool 装饰器骨架

不看第 4 节的完整实现，自己写一个 @tool 装饰器骨架，说清它如何自动收集函数名 + 参数 Schema 并登记进 registry。先自己写，再看答案。

任务清单

  1. 用 inspect.signature(fn) 读出参数名、类型注解、有无默认值
  2. 把每个参数转成 Schema 字段（类型名；没默认值的进 required）
  3. 用 fn.__name__ 作工具名、fn.__doc__ 作 description
  4. 把 {schema, fn} 登记进全局 REGISTRY（fn 要一起存，方便分发）
  5. 用 functools.wraps，保证被装饰函数照常可调用
💡 点击查看参考答案 
import functools, inspect

REGISTRY = {}   # 工具名 -> {"schema": {...}, "fn": callable}
_JSON_TYPE = {"str": "string", "int": "integer", "float": "number", "bool": "boolean"}

def tool(fn):
    sig = inspect.signature(fn)
    props, required = {}, []
    for name, p in sig.parameters.items():
        props[name] = {"type": _JSON_TYPE.get(getattr(p.annotation, "__name__", ""), "string")}
        if p.default is inspect.Parameter.empty:   # 无默认值 = 必填
            required.append(name)

    REGISTRY[fn.__name__] = {                       # ← 登记：名字为键
        "schema": {
            "name": fn.__name__,                    # 函数名 = 工具名
            "description": (fn.__doc__ or "").strip(),   # docstring = 描述
            "parameters": {
                "type": "object",
                "properties": props,                # ← 自动收集的参数 Schema
                "required": required,
            },
        },
        "fn": fn,                                    # ← 存函数本体，供 dispatch
    }

    @functools.wraps(fn)                             # 保住 __name__/__doc__
    def wrapper(*args, **kwargs):
        return fn(*args, **kwargs)
    return wrapper


@tool
def add(a: int, b: int) -> int:
    "把两个整数相加。"
    return a + b

print(REGISTRY["add"]["schema"])
# {'name': 'add', 'description': '把两个整数相加。',
#  'parameters': {'type': 'object',
#    'properties': {'a': {'type': 'int'}, 'b': {'type': 'int'}},
#    'required': ['a', 'b']}}
print(add(2, 3))            # 5 —— 装饰后照常调用
print(add.__name__)         # add —— wraps 生效

总结

  • 参数校验失败别崩：Pydantic 校验（L14），错误作为 tool 结果回填让模型自我修正重试（呼应 L28/L31）
  • 流式下工具调用要拼：arguments 分片到达，按 index 累加、流结束后一次性 parse（L26）
  • 工具 Schema 占 token 且每轮都发：只注册相关工具 + description 精简，省钱又选得准（L18/L34/L37）
  • 注册系统 = 装饰器自动注册：@tool 抽 Schema + 登记 + 存函数，闭合 Phase 1 L11 那条线
  • 分发：拿模型给的名字去注册表查真实函数并调用（呼应 L35 循环）
  • 健壮工具层 → Agent 稳定行动；注册系统 → 工具可扩展 —— 这就是框架的底层原理
💼 面试高频：「工具参数校验失败怎么办？」 标准答法——别让它崩：用 Pydantic 校验模型填的参数，校验失败不 raise，而是把错误信息作为 tool 结果回填给模型，让它据此改正重试（自我修正，呼应 L28/L31）；再配合 Tool Registry（装饰器自动注册 + 分发）让工具集可扩展、可维护。一句话点透：可靠 Agent 不是信任模型，而是在机制上给它自愈的机会、并让工具层能持续长大。 下一课我们把 token 成本这条线收尾——L37 成本工程。有疑问随时问我。
