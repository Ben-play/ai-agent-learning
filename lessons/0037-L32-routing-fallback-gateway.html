路由、Fallback 与 AI Gateway

先筛能力和数据边界，再比较成本；没有合格备选时明确降级

💡 为什么这课重要？

同一个客服 Agent 收到两个都很短的任务：「改写公开 FAQ」与「查询我的内部订单」。后者需要工具和获批的数据路径。用长度挑最便宜的模型，可能连协议都不支持，或把不该外发的数据送错地方。L31 先解决单条路上的重试；这课判断还有没有另一条合格的路。

学习目标

  • 区分路由（选首发）、重试（原路再试）和 Fallback（安全时换合格备选）。
  • 先按能力、数据范围和故障依赖筛选，再比较质量、成本与时间。
  • 用调用轨迹验收切换、不可用和待核对，判断何时才需要网关。

1. 先筛合格路线，再比价格

任务携带所需能力（如 tools）、数据分类、允许的端点以及当前阶段能否安全重放；端点列经过验证的能力、范围、费用和已知依赖。允许列表由宿主从可信策略得到，不由模型扩大。下表两条内部路线已通过质量验收；这里用本地试次验证分派，不测模型质量。

Q 内部订单短查询需要工具，最低价端点只支持公开文本。怎么选首发？
只能在符合能力、数据策略和质量门槛的端点之间比较价格。发送后才检查数据范围已经太迟。

2. 跟做：有限尝试后才换路

复制下面核心块和折叠自检到同一文件。route 接收负责单路线重试与时限的适配器；max_routes 只限制端点次数，不是模型总尝试数。replay_safe 表示换路时可以重建请求，并且不会重做结果未知的操作。

from dataclasses import dataclass

@dataclass(frozen=True)
class Endpoint:
    name: str
    capabilities: frozenset[str]
    scopes: frozenset[str]
    cost: int
    dependency: str

@dataclass(frozen=True)
class Task:
    needs: frozenset[str]
    scope: str
    allowed: frozenset[str]
    replay_safe: bool

def route(task, endpoints, send, *, max_routes=2):
    if type(max_routes) is not int or max_routes < 1:
        raise ValueError("need a positive endpoint budget")
    eligible = sorted(
        (e for e in endpoints if e.name in task.allowed
         and task.scope in e.scopes and task.needs <= e.capabilities),
        key=lambda e: (e.cost, e.name),
    )
    attempts, failed_dependencies = [], set()
    for endpoint in eligible:
        if len(attempts) == max_routes:
            break
        if endpoint.dependency in failed_dependencies:
            continue
        attempts.append(endpoint.name)
        status = send(endpoint)  # 适配器管理本路线重试与整个任务的剩余时间
        if status in {"ok", "refused", "fatal", "deadline"}:
            return status, attempts
        if status == "unknown_write":
            return "reconcile", attempts
        if status != "transient_exhausted":
            raise ValueError(f"unexpected adapter status: {status}")
        if not task.replay_safe:
            return "unavailable", attempts
        failed_dependencies.add(endpoint.dependency)
    return "unavailable", attempts

这是本地替身，send 不请求外部。例中保守跳过共享已知失败依赖的端点。只有临时错误且当前阶段可安全重放才看下一路；拒答不换厂绕过，任务截止不加新尝试。已提交但回复丢失时走 reconcile，按原业务引用查回执。无合格路线返回 unavailable，可交人工或用不依赖模型的只读流程。

tools, internal = frozenset({"tools"}), frozenset({"internal"})
endpoints = (Endpoint("economy", frozenset(), frozenset({"public"}), 1, "shared"),

for primary, expected, calls in (

    ("refused", "refused", ["site-a"]),
    ("fatal", "fatal", ["site-a"]),
    ("deadline", "deadline", ["site-a"]),
    ("unknown_write", "reconcile", ["site-a"]),

    def send(endpoint):
        visited.append(endpoint.name)

Q 工单提交后响应超时，结果未知；备用模型支持工具。怎么处理？
是否切推理端点与业务是否可重放是两个问题。对未知写入先核对，不从超时推断未写入。

3. 何时才把策略放进网关

AI Gateway 是在客户端与上游之间集中管理路由、额度、账本或追踪的组件，不是必选协议。一个服务、一条路线时，薄适配器加明确的不可用或人工路径通常足够；多个服务重复维护同一规则且能统一验收时，再将共享策略移入网关。

LiteLLM Proxy、OpenRouter 等有兼容入口或路由选项，Portkey 也有治理工具。兼容请求形状不保证 Responses Items、Chat 工具或 Messages 内容块可以无损互换。即使自托管，请求也可能发往外部模型，遥测或缓存也可能出域；逐跳核对上游、数据保留、租户隔离和追踪配置。

网关本身也带来延迟、故障域和运维。不要让应用、SDK 与网关重复拥有无关的重试预算。业务授权、人工批准和写入幂等仍由可信宿主定，不交给模型网关代判。

决策卡：没有合格备选，比错误切换好

适用：有工具契约一致、符合数据政策且可重放的备用模型。不适用：只有共享故障依赖的备用，或已发生未确认的外部写入。

超时就换

订单任务超时就切便宜文本端点，甚至重做整条写操作。

先划定可重放边界

同是超时，纯推理在预算内换合法端点；未知写入只查原回执。

取舍：拒绝不合格备用会降低可用性，但不突破数据或写入约束；备选方案是只读、人工排队或返回不可用。

  1. 发送短但需要工具的内部任务，核对选择与实际分派。
  2. 分别注入临时故障和未知提交，确认后者不分派备用。

出现未经授权的端点，先查过滤是否在 send 之前；备用同样失效则先核共享配额和依赖。

Q 自托管网关已就绪，能由此确认订单内容没有出域吗？
自托管只决定网关所在位置。要验证数据边界，需检查每一跳允许的范围与实际流向。

总结与面试自查

先筛能力、数据和重放条件；成本只在合格路线间比较。网关是可选的共享治理层，业务权限和未知副作用仍由宿主处理。

客服订单模型持续 429，备用支持工具，能切吗？

先查任务剩余预算、备用数据权限、工具协议和共享限额，再判当前步骤可否安全重放。不合格时转人工或返回不可用。

追问：工单已送出，网关只报超时？要点：保留原操作绑定、查原回执，不让备用重做工单；以实际分派轨迹证明。
