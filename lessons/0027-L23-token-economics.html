Token 经济学与降本杠杆

同一个 Agent，账单可以差 3~5 倍——差在你会不会用两根杠杆

💡 为什么这课重要？

L18 教了你怎么数 Token、算成本。这一课回答下一个问题：怎么把这笔成本压下去。

这不是可选项。Agent 和单次 chat 有本质区别——一次任务里 LLM 被反复调用，每次都拖着长 system prompt 和越滚越长的历史。同一个功能，不会优化的人月账单可能是会优化的人的 3~5 倍。好消息是：最大的两根杠杆——Prompt Caching（提示缓存）和 Model Routing（模型路由），官方文档和真实案例都能落到 50%~90% 的降幅（其余如压缩历史、控输出、批处理是补充）。学完你能给一个 Agent制定 token 预算、并把成本砍一半以上。这是从"能跑"到"生产级"的必修课。

学习目标

完成本课后，你将能够：

  • 说清 Agent 场景里成本从哪来、为什么被放大
  • 用 Prompt Caching 把重复的静态前缀降到约 0.1× 价格（省约 90%）
  • 设计「静态前缀 + 动态后缀」的缓存友好结构
  • 用 Model Routing 让便宜模型兜底、贵模型只接难活
  • 给一个 Agent制定 token 预算并估算月成本

1. 快速回顾：成本公式（细节看 L18）

一句话把 L18 的结论捡回来。API 按 Token 收费，输入和输出分开定价，输出通常是输入的 3~5 倍：

成本 = (输入Token数 × 输入单价 + 输出Token数 × 输出单价) / 1,000,000

例：输入 2200 token、输出 300 token，输入 $3/M、输出 $12/M
    (2200×3 + 300×12) / 1e6 = $0.0102  ← 单次

单次不起眼，但 Agent 一天调 10 万次，就是 ~$1000/天。

这课不重复整节 L18，只做一件事：把公式里的每一项往下压。想复习"怎么数 Token、中英文谁更省"，回 L18。

2. 隐藏成本：Agent 的钱到底花在哪

为什么强调 Agent 的 token 消耗远大于单次 chat？因为有四个"放大器"，每一个都让输入 Token膨胀（Redis: LLM Token Optimization）：

放大器为什么费钱
① 多轮历史每轮重发API 是无状态的，每轮都要把全部历史当输入重新送一遍，输入量随轮数线性增长
② 长 system prompt那段角色设定 + 工具说明 + 少样本示例，每一次请求都完整计费，一个字不少
③ 工具调用循环一次任务 = 多次往返 LLM（想→调工具→读结果→再想）。每次往返都带上完整上下文
④ 检索长文档RAG / 长文档塞进上下文，动辄几千 token，且往往反复出现在多轮里

看出规律没有：费钱的几乎都是"重复的、静态的输入"——长 system prompt 每次都在、检索的文档反复出现、历史一遍遍重发。这正好是下一节第一根杠杆的靶心。

直觉校准：一个带 2000-token system prompt 的客服 Agent，如果每天 10 万次请求，光那段一字不改的 system prompt 每天就烧掉约 $600（按 $3/M 算）——而它的内容每次都一模一样。这就是缓存的用武之地。

3. 杠杆一：Prompt Caching（第一降本杠杆）

原理：把静态的、重复的前缀（长 system prompt、固定的少样本示例、反复出现的文档）缓存起来。后续请求只要前缀逐字节命中缓存，这部分就大幅降价——你不再为"每次都一样的内容"付全价。

各家的数量级（以官方文档为准，这里用"约"）：

厂商缓存读（命中）缓存写（首次）TTL
Anthropic约 0.1× 输入价
（省约 90%）		约 1.25×
（首次略贵）		默认约 5 分钟；另有 1 小时选项（写约 2×）
OpenAI命中约省 50%~90%（视模型代次，较新模型可达 ~90%）自动，无额外写入费自动前缀缓存

数据出处：Anthropic: Prompt Caching、OpenAI: Prompt Caching。Anthropic 首次写入略贵（约 1.25×），所以缓存的经济学是：同一前缀被读得越多越划算——一次性任务别缓存，反复命中的 Agent 场景才是甜点。

关键设计原则：把 prompt 拆成「静态前缀（可缓存）+ 动态后缀（每次变）」，静态部分放最前面。因为缓存是前缀匹配——前缀里任何一个字节变了，后面全部失效。所以千万别把时间戳、用户 ID、随机数塞进 system prompt 开头：

【缓存键设计：静态前缀 + 动态后缀】

┌─ 静态前缀（放前面，打缓存标记）──────────────┐
│  · 角色设定 / 行为准则          ← 一字不改      │  ← 命中缓存
│  · 工具定义（按名字排序，别乱序）              │     约 0.1×
│  · 固定的少样本示例 / 长文档                    │
└──────────────────────────────────────────────┘
┌─ 动态后缀（放后面，不缓存）────────────────────┐
│  · 本轮用户问题                                │  ← 全价
│  · 当前时间戳 / 请求 ID / 检索到的新片段        │     但很短
└──────────────────────────────────────────────┘

⚠️ 反例：system prompt 开头写 "当前时间：{now}"
   → 前缀每次都变 → 缓存永远不命中 → 白交钱

真实案例把这条原则落地后，报道的降幅在 59%~70%（ProjectDiscovery: How We Cut LLM Cost with Prompt Caching）。对 Agent 来说，长 system prompt + 固定工具集天然就是巨大的静态前缀，缓存几乎是"免费的午餐"。

验证缓存是否真的命中：看 API 返回的 usage——若 cache_read 类字段一直是 0，说明有"静默失效因子"（多半是前缀里混进了时间戳 / 随机 ID / 没排序的 JSON）。缓存不命中不报错，只是悄悄多收钱，所以必须主动核对。
Q 想让 Prompt Caching 真正省钱，prompt 该怎么组织？
缓存是前缀匹配：前缀里任何一个字节变了，后面全部失效。所以要把静态、每次都一样的内容（角色设定、固定工具、少样本示例）放最前面并打缓存标记，把动态内容（用户问题、时间戳、检索片段）放后面。反例——在开头写"当前时间：{now}"或每次换措辞——会让前缀每次都变，缓存永远不命中，白交钱。

4. 杠杆二：Model Routing（模型路由）

原理：不是所有请求都值得用最贵的模型。让便宜、快的小模型兜底处理简单请求，把贵、强的大模型只留给难请求。按难度分类、动态路由。

请求进来 → 判断难度
   ├─ 简单（分类 / 提取 / 闲聊 / 格式化） → 便宜快模型 兜底
   ├─ 中等（一般问答 / 总结）             → 中档模型
   └─ 困难（多步推理 / 复杂 Agent 规划）   → 顶级模型 只接这类

思路：先用便宜模型试；不确定 / 判为难，再升级到贵模型。

为什么有效：小模型的单价往往是大模型的几分之一到几十分之一，而生产流量里大部分请求其实很简单。把这部分从大模型挪走，账单立刻塌方——真实报道的降幅在 40%~85%（TrueFoundry: LLM Routing — Cost/Quality-Aware Model Selection）。

工程落地：用一个 gateway（如 LiteLLM，见课程 RESOURCES）统一路由，业务代码不用管背后是哪个模型，换模型 / 调路由策略只改配置。这直接连回两条已学的原则：

  • 👉 L20：推理模型（思考更多）更贵更慢——别对"翻译一句话""判断正负面"这种简单活开推理，纯属烧钱。
  • 👉 L22：选型不是"永远选最强"，而是按任务难度匹配。路由就是把"选型"从一次性决策变成每请求的动态决策。
Q Model Routing 降本的核心思路是？
路由的关键是按难度分流：生产流量里大部分请求很简单，用便宜快的小模型兜底，只把真正困难的请求升级到贵模型。因为小模型单价常是大模型的几分之一，这一分流就能砍掉 40%~85% 成本。它和"选型"（L22）一脉相承，只是把选择从一次性变成每请求的动态决策。

5. 其他杠杆（简述）

两根主杠杆之外，还有几个"顺手就能拧"的旋钮：

杠杆怎么省
压缩历史 / 对话（compaction）多轮太长时，只保留摘要而非全文回传，砍掉①号放大器。深入见 Phase 5（Agent 上下文工程）
控制输出长度输出是输入的 3~5 倍价，最贵。设 max_tokens、在 prompt 里明确"简洁作答 / 只返回 JSON"，别让模型啰嗦
批处理（Batch API）非实时任务（离线分类、批量总结）走批处理，通常约省 50%，代价是延迟（结果稍后返回）

这些是补充，不是替代。先上缓存和路由（收益最大、几乎无副作用），再按场景补这几个。

6. 给 Agent 制定 Token 预算

"降本"落地前先要"知本"。给一个 Agent 制定预算的四步思路：

① 估算单次任务 token 量
     = system prompt + 历史 + 检索文档 + 输出
     （别忘 Agent 一次任务可能往返 LLM 多次，要乘往返数）
② 乘调用频次
     × 每天 / 每月请求数
③ 对照单价，得出未优化月成本（这是"上限"）
④ 用缓存 + 路由压下来
     静态前缀 → 缓存（约 0.1× / 约 0.5×）
     简单请求 → 路由到便宜模型
     → 得出优化后成本，与上限对比看省了多少

为什么先算再优化：不算预算，你既不知道钱花在哪一项（是历史太长？还是 system prompt 太肥？），也无法判断优化值不值。把它当成 Agent 上线前的"体检"。

Q 关于 Anthropic 的 Prompt Caching，下面哪个说法对？
Anthropic 缓存读约 0.1× 输入价（省约 90%，不是全免），首次写入反而略贵（约 1.25×）。缓存对静态、重复的前缀最有效——动态后缀每次都变、无法命中。所以设计上要把静态部分放前面、打缓存标记，让它被反复命中。具体倍数以官方文档为准。

7. 成本估算练习：把两根杠杆算给你看

动手最能建立体感。给你一个具体场景，先自己算，再展开对答案。

【场景】客服 Agent
  · system prompt：2000 token，固定不变
  · 每次用户问题：约 200 token
  · 每次回答：约 300 token
  · 每天请求数：10 万次
  · 单价：输入 $3/M，输出 $12/M

问：
  ① 不加缓存，日成本是多少？
  ② Prompt Caching 能省下哪部分？大致省多少？
点我看算法与答案

① 不加缓存的日成本

每次输入 = system 2000 + 问题 200 = 2200 token
每次输出 = 300 token

日输入成本 = 100,000 × 2200 × $3 / 1e6 = $660
日输出成本 = 100,000 ×  300 × $12 / 1e6 = $360
─────────────────────────────────────────────
日总成本  = $660 + $360 = $1020 / 天

② Prompt Caching 能省哪部分

那 2000 token 的 system prompt 是静态前缀，每次一字不改——正是缓存的靶心。问题（200）和输出（300）每次都变，不动。

静态前缀原价 = 100,000 × 2000 × $3 / 1e6      = $600 / 天
命中缓存后   = $600 × 0.1（约 0.1×）           = $60  / 天
                                    省下 ≈ $540 / 天

加缓存后日总成本：
  缓存前缀 $60 + 动态输入 $60 + 输出 $360 = $480 / 天

────────────────────────────────────────────────
$1020 → $480，账单砍掉约 53%
其中光"静态前缀"这一项就从 $600 降到 $60（省约 90%）

体会两点：(a) 缓存只作用于静态前缀，动态部分（问题+输出共 $420）它管不着——所以要尽量把内容往静态前缀里归；(b) system prompt 越大、请求越频繁，缓存收益越夸张。这里再叠一层路由（把简单问答分给便宜模型），$480 还能继续往下走。

💼 面试高频："如何优化 LLM 成本？" 满分答法按性价比排序：① Prompt Caching——缓存静态前缀，命中省约 90%（Anthropic）/约 50%~90%（OpenAI，视模型代次）；② Model Routing——便宜模型兜底、贵模型只接难请求；③ 压缩历史（只留摘要）；④ 控输出（max_tokens + 要求简洁）；⑤ 批处理（非实时约省 50%）。一句话点题原则："原生缓存优先"——先把静态前缀缓存吃干净，再谈其他。

总结

  • 成本 = 输入输出分开算，输出通常 3~5× 输入；Agent 因多轮/长 prompt/工具循环，token 消耗远超单次 chat
  • 费钱的几乎都是重复的静态输入——这正是两根杠杆的靶心
  • 杠杆一 Prompt Caching：缓存静态前缀，Anthropic 读约 0.1×（省约 90%）、OpenAI 约省 50%~90%（视模型代次）；设计成「静态前缀 + 动态后缀」，静态放前面
  • 杠杆二 Model Routing：便宜模型兜底、贵模型只接难请求，报道降 40~85%；连回 L20/L22
  • 先制定 token 预算（估单次×频次×单价 = 上限），再用缓存+路由压下来；从 Phase 3 起养成"原生缓存优先 + 路由"的习惯
