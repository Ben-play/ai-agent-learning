Token 经济学与降本杠杆

先测钱花在哪，再用缓存、路由、批处理和输出控制逐项验证收益

💡 为什么这课重要？

L18 教了你怎么数 Token、算成本。这一课回答下一个问题：怎么把这笔成本压下去。

Agent 一次任务可能反复调用 LLM，每轮又携带 system prompt、工具定义和增长的历史，因此成本会被放大。Prompt Caching 与 Model Routing 往往是高收益候选，但节省比例取决于静态前缀占比、命中率、任务分布和路由质量；第三方案例只能说明“可能做到”，不能保证你的系统也省一半。学完你会建立预算、测量成本构成，再按证据选择优化手段。

学习目标

完成本课后，你将能够：

  • 说清 Agent 场景里成本从哪来、为什么被放大
  • 按 Anthropic 当前官方边界，用 Prompt Caching 把命中的重复静态前缀按约 0.1× 基础输入价计费（约省 90%）
  • 设计「静态前缀 + 动态后缀」的缓存友好结构
  • 用 Model Routing 让便宜模型兜底、贵模型只接难活
  • 给一个 Agent制定 token 预算并估算月成本

1. 快速回顾：成本公式（细节看 L18）

一句话把 L18 的结论捡回来。API 按 Token 收费，输入和输出分开定价；输入/输出价差取决于厂商、模型、计费层级和日期，下面的 $3/M 与 $12/M 只是一组教学示例，不能外推成通用的 3~5 倍规律：

成本 = (输入Token数 × 输入单价 + 输出Token数 × 输出单价) / 1,000,000

例：输入 2200 token、输出 300 token，输入 $3/M、输出 $12/M
    (2200×3 + 300×12) / 1e6 = $0.0102  ← 单次

单次不起眼，但 Agent 一天调 10 万次，就是 ~$1000/天。

这课不重复整节 L18，只做一件事：把公式里的每一项往下压。想复习"怎么数 Token、中英文谁更省"，回 L18。

最佳实践：先拆完整美元成本，再选择一根降本杠杆

适用：一次任务同时含未缓存输入、缓存写入、缓存读取、输出、重试与升级调用，需要知道哪一项真正主导账单。不适用：还没有可代表生产的 usage、价格表或调用概率时，只能做带日期/来源的情景估算，不能宣称已找到主因。本卡只决定第一根优化杠杆。

❌ 按 Token 最大项直接优化
largest = max(tokens, key=tokens.get)
lever = LEVER_BY_COMPONENT[largest]

忽略不同价格倍数与概率；Token 最多不一定美元最多。

✅ 同一 usage，逐项换算美元
costs = component_costs(usage, rates)
largest = max(costs, key=costs.get)
lever = LEVER_BY_COMPONENT[largest]

先把缓存写/读、输出和期望重试/升级成本放进同一货币量纲，再选杠杆。

为什么更优：逐项执行 Token×适用费率×发生概率，把异质 usage 转成可比美元，因此优化会命中真实账单主因，而不是体量最大的 Token 桶，提升成本效率与决策可解释性。代价是维护带生效日期的价格表、记录重试/升级概率并持续对账；若缺少真实 usage，先采样 tracing；若输出美元最大就收紧输出/rubric，若缓存写入最大且复用不足就取消或缩短缓存，若升级最大则先修路由质量。

边界：未缓存输入按基础输入价；缓存写/读按目标厂商当前倍数；输出按输出价；重试/升级是额外调用的期望成本，不能藏在“平均一次请求”里。生产计算必须使用带来源与生效日期的当前价格；下面 fixture 的费率只为证明算法，不代表任何真实模型报价。

动手自检（纯标准库；离线、确定性、通过时静默）
def component_costs(usage, rates):
    return {
        name: usage[name] * rates[name] / 1_000_000
        for name in usage
    }


usage = {
    "uncached_input": 9_000,
    "cache_write": 1_000,
    "cache_read": 5_000,
    "output": 800,
    "retry": 200,
    "escalation": 100,
}
rates = {
    "uncached_input": 2.0,
    "cache_write": 2.5,
    "cache_read": 0.2,
    "output": 40.0,
    "retry": 2.0,
    "escalation": 30.0,
}

costs = component_costs(usage, rates)
assert max(usage, key=usage.get) == "uncached_input"
assert max(costs, key=costs.get) == "output"
assert round(costs["uncached_input"], 6) == 0.018
assert round(costs["output"], 6) == 0.032
assert sum(costs.values()) > costs["output"]
assert set(costs) == set(usage) == set(rates)

失败诊断：最大 Token 项与最大美元项相同则 fixture 没证明价格构成的重要性；未缓存输入不是 0.018 或输出不是 0.032 表示百万 Token 换算错误；遗漏 retry/escalation 表示期望额外调用成本仍被隐藏；直接依据 Token 选杠杆表示尚未完成成本组成分析。

2. 隐藏成本：Agent 的钱到底花在哪

为什么强调 Agent 的 token 消耗远大于单次 chat？因为有四个"放大器"，每一个都让输入 Token膨胀（Redis: LLM Token Optimization）：

放大器为什么费钱
① 多轮历史每轮重发第 n 轮请求携带的历史长度常随轮数近似线性增长；若每轮都重发完整历史，前 n 轮累计输入量常近似二次增长
② 长 system prompt那段角色设定 + 工具说明 + 少样本示例，每一次请求都完整计费，一个字不少
③ 工具调用循环一次任务 = 多次往返 LLM（想→调工具→读结果→再想）。每次往返都带上完整上下文
④ 检索长文档RAG / 长文档塞进上下文，动辄几千 token，且往往反复出现在多轮里

看出规律没有：费钱的几乎都是"重复的、静态的输入"——长 system prompt 每次都在、检索的文档反复出现、历史一遍遍重发。这正好是下一节第一根杠杆的靶心。

直觉校准：一个带 2000-token system prompt 的客服 Agent，如果每天 10 万次请求，光那段一字不改的 system prompt 每天就烧掉约 $600（按 $3/M 算）——而它的内容每次都一模一样。这就是缓存的用武之地。

3. Prompt Caching：静态前缀占比高时的强杠杆

原理：把静态的、重复的前缀（长 system prompt、固定的少样本示例、反复出现的文档）缓存起来。后续请求只要前缀逐字节命中缓存，这部分就大幅降价——你不再为"每次都一样的内容"付全价。

下表是按本课引用的官方文档整理的边界快照；价格与支持范围会变化，实施时必须重新核对目标模型与平台：

厂商缓存读（命中）缓存写（首次）TTL
Anthropic约 0.1× 输入价
（省约 90%）		约 1.25×
（首次略贵）		默认约 5 分钟；另有 1 小时选项（写约 2×）
OpenAI缓存折扣、写入计费与保留时间按模型/产品变化；本课不固定数值，实施时查下方 OpenAI 当前官方文档

数据出处：Anthropic: Prompt Caching、OpenAI: Prompt Caching。按相对输入价粗算：5 分钟缓存一次写入 1.25×，之后一次读取 0.1×，两次使用合计 1.35×，低于两次全价 2×；1 小时缓存写 2×，通常要到第三次使用（2×+0.1×+0.1×）才低于三次全价。实际收益还取决于命中时机、并发和静态前缀占比。

还有一个常被漏掉的门槛：可缓存前缀必须达到目标模型的最小 Token 数，且该阈值随模型/平台变化；太短时不会报错，只是不会建立缓存。因此不要背一个固定阈值，接入时查当前模型文档并看 usage 验证。

关键设计原则：把 prompt 拆成「静态前缀（可缓存）+ 动态后缀（每次变）」，静态部分放最前面。因为缓存是前缀匹配——前缀里任何一个字节变了，后面全部失效。所以千万别把时间戳、用户 ID、随机数塞进 system prompt 开头：

【缓存键设计：静态前缀 + 动态后缀】

┌─ 静态前缀（放前面，打缓存标记）──────────────┐
│  · 角色设定 / 行为准则          ← 一字不改      │  ← 命中缓存
│  · 工具定义（按名字排序，别乱序）              │     约 0.1×
│  · 固定的少样本示例 / 长文档                    │
└──────────────────────────────────────────────┘
┌─ 动态后缀（放后面，不缓存）────────────────────┐
│  · 本轮用户问题                                │  ← 全价
│  · 当前时间戳 / 请求 ID / 检索到的新片段        │     但很短
└──────────────────────────────────────────────┘

⚠️ 反例：system prompt 开头写 "当前时间：{now}"
   → 前缀每次都变 → 缓存永远不命中 → 白交钱

ProjectDiscovery 的案例报告了 59%~70% 的降幅（案例原文），但这是其请求结构和命中率下的结果，不是普遍保证。长 system prompt + 固定工具集通常是良好候选；若前缀太短、频繁变化、并发请求来不及读取刚写入的缓存，收益会显著下降。

最佳实践：规范化稳定前缀，把动态请求严格追加在后

适用：工具定义、系统规则或固定示例足够长且会在 TTL 内重复使用。不适用：前缀低于目标模型/平台的最小缓存长度，或首段内容每次都不同且没有可复用前缀时，不应为零命中支付写入溢价。本卡只决定缓存前缀边界与字节稳定性。

❌ 动态字段混进前缀
prefix = {
    "request_id": request_id,
    "tools": tools,
    "system": system,
}

业务接口相同，但每个请求 ID 都改变摘要，后续前缀无法完全一致。

✅ 固定序列化 + 动态后缀
prefix = stable_prefix(tools, system)
suffix = {"request_id": request_id, "question": question}

工具按名排序、JSON 固定序列化；请求 ID 和问题位于边界之后。

为什么更优：先规范化工具顺序与序列化，再对稳定部分设置边界，缓存机制才能对 100% 相同的前缀复用，结果是更高命中率、更低重复输入成本与可诊断摘要。代价是冻结顺序、维护版本与接受首次写入溢价；5 分钟写入按基础输入价 1.25×、1 小时写入 2×、读取 0.1×，所以复用不足时切回不缓存或较短 TTL；工具定义确实变化时必须让摘要变化并重新写入，不能为命中伪造旧工具集。

官方边界：支持默认 5 分钟与显式 1 小时 TTL；命中要求缓存断点前的 prompt 前缀完全一致；最小可缓存长度依模型且有平台差异，过短会静默不缓存。用 usage.input_tokens、cache_creation_input_tokens、cache_read_input_tokens 分别核对未缓存、写入和读取 Token，三者之和才是总输入。

动手自检（纯标准库；离线摘要模拟、确定性、通过时静默）
import hashlib
import json


def stable_prefix(tools, system):
    normalized = {
        "tools": sorted(tools, key=lambda tool: tool["name"]),
        "system": system,
    }
    return json.dumps(
        normalized,
        ensure_ascii=False,
        sort_keys=True,
        separators=(",", ":"),
    )


def digest(text):
    return hashlib.sha256(text.encode("utf-8")).hexdigest()


def request(tools, system, *, request_id, question):
    prefix = stable_prefix(tools, system)
    dynamic_suffix = json.dumps(
        {"request_id": request_id, "question": question},
        ensure_ascii=False,
        sort_keys=True,
    )
    return digest(prefix), prefix + dynamic_suffix


tools = [
    {"name": "search", "description": "查当前公告"},
    {"name": "calculate", "description": "执行精确计算"},
]
first_digest, first_request = request(
    tools, "遵循市政服务规则", request_id="r-1", question="今天开放吗？"
)
second_digest, second_request = request(
    list(reversed(tools)),
    "遵循市政服务规则",
    request_id="r-2",
    question="现在排队多久？",
)
changed_tools = [*tools, {"name": "status", "description": "读取申请状态"}]
third_digest, _ = request(
    changed_tools,
    "遵循市政服务规则",
    request_id="r-3",
    question="我的申请在哪一步？",
)

assert first_digest == second_digest
assert first_request != second_request
assert third_digest != first_digest
assert len(first_digest) == 64

失败诊断：动态请求改变前缀摘要表示边界放错；仅交换工具顺序就改变摘要表示没有规范化；工具定义新增后摘要不变表示缓存会错误复用陈旧接口；重复请求 usage 的读取字段始终为 0 时，应再检查最小长度、TTL、完全一致性与并发写入时机。

验证 Anthropic 缓存是否命中：看 usage.cache_read_input_tokens；首次写入看 cache_creation_input_tokens，input_tokens 是未缓存的剩余部分。若重复请求的读取字段一直为 0，检查前缀长度、时间戳 / 随机 ID、工具顺序和并发时机。
Q 想让 Prompt Caching 真正省钱，prompt 该怎么组织？
缓存是前缀匹配：前缀里任何一个字节变了，后面全部失效。所以要把静态、每次都一样的内容（角色设定、固定工具、少样本示例）放最前面并打缓存标记，把动态内容（用户问题、时间戳、检索片段）放后面。反例——在开头写"当前时间：{now}"或每次换措辞——会让前缀每次都变，缓存永远不命中，白交钱。

4. 杠杆二：Model Routing（模型路由）

原理：不是所有请求都值得用最贵的模型。让便宜、快的小模型兜底处理简单请求，把贵、强的大模型只留给难请求。按难度分类、动态路由。

请求进来 → 判断难度
   ├─ 简单（分类 / 提取 / 闲聊 / 格式化） → 便宜快模型 兜底
   ├─ 中等（一般问答 / 总结）             → 中档模型
   └─ 困难（多步推理 / 复杂 Agent 规划）   → 顶级模型 只接这类

思路：先用便宜模型试；不确定 / 判为难，再升级到贵模型。

为什么可能有效：不同模型单价差异大，若流量中确有一批简单请求，且路由器能在不显著损害质量的前提下识别它们，就能降低平均成本。TrueFoundry 的文章汇总了 40%~85% 的案例区间（案例原文）；这不是保证，误路由、二次升级和路由器自身调用也会产生质量与成本。

工程落地：用 provider-neutral adapter / gateway 隔离厂商请求与响应（例如可评估 LiteLLM，见课程 RESOURCES），业务层只依赖统一任务结果；具体网关仍要按你锁定的版本、支持矩阵和评测验证，不能假设换配置就自动获得公平或无损路由。这直接连回两条已学的原则：

  • 👉 L20：推理模型（思考更多）更贵更慢——别对"翻译一句话""判断正负面"这种简单活开推理，纯属烧钱。
  • 👉 L22：选型不是"永远选最强"，而是按任务难度匹配。路由就是把"选型"从一次性决策变成每请求的动态决策。

最佳实践：在质量门槛内选择期望成本最低的路由策略

适用：候选策略已有私有评测通过率、首轮成本、升级概率和升级成本。不适用：只有“请求长/短”或公开榜单，没有业务质量证据时，不应上线自动路由。本卡只决定每类请求采用哪条已评测策略。

❌ 按文本长度猜难度
strategy = "cheap_only" if len(request) < 80 else "strong_only"

短而困难的请求会被误路由；也没有计入便宜模型失败后的二次调用。

✅ 质量先过门，成本含升级概率
qualified = [s for s in strategies if s.pass_rate >= gate]
strategy = min(qualified, key=expected_cost)

同一任务接口下，只比较达标策略；级联期望成本包含首轮和概率加权的升级调用。

为什么更优：先用私有评测执行质量硬门，再按 first_cost + escalation_probability × escalation_cost 排序，机制上阻止廉价但不合格的策略胜出，同时把二次调用纳入账单，因此兼顾可靠性、成本可预测性与可解释性。代价是维护按任务分层的评测和持续校准升级率；若短而困难类在低成本策略上不过门，就切换为直接强模型；若级联达标且升级率低则保留级联；若没有任何策略达标，升级为人工/拒绝上线，而不是降低门槛。

边界：质量门先淘汰不合格策略；升级概率来自同分布私有评测，不是拍脑袋；期望成本比较策略平均美元成本，不保证每个请求都恰好花该金额。

动手自检（纯标准库；离线、确定性、通过时静默）
from dataclasses import dataclass


@dataclass(frozen=True)
class Strategy:
    name: str
    pass_rate: float
    first_cost: float
    escalation_probability: float = 0.0
    escalation_cost: float = 0.0


def expected_cost(strategy):
    return (
        strategy.first_cost
        + strategy.escalation_probability * strategy.escalation_cost
    )


def choose(strategies, *, quality_gate):
    qualified = [s for s in strategies if s.pass_rate >= quality_gate]
    if not qualified:
        raise RuntimeError("no strategy passes the quality gate")
    return min(qualified, key=expected_cost)


short_but_hard = [
    Strategy("cheap-only", 0.62, 0.001),
    Strategy("cheap-then-strong", 0.93, 0.001, 0.35, 0.020),
    Strategy("strong-only", 0.97, 0.020),
]

winner = choose(short_but_hard, quality_gate=0.90)
assert winner.name == "cheap-then-strong"
assert round(expected_cost(winner), 6) == 0.008
assert expected_cost(winner) < expected_cost(short_but_hard[2])
assert len("修复并证明这个竞态") < 80  # 短不等于简单

try:
    choose([Strategy("cheap-only", 0.62, 0.001)], quality_gate=0.90)
except RuntimeError:
    pass
else:
    raise AssertionError("no-qualified strategy must not be selected")

失败诊断：cheap-only 胜出表示质量门未先执行；strong-only 胜出表示期望成本或升级概率计算错误；短请求被自动标为简单表示路由特征替代了私有评测；无达标策略仍返回候选表示系统会为省钱牺牲硬质量要求。

Q Model Routing 降本的核心思路是？
路由的关键是用业务评测识别哪些任务可以交给低成本候选，并持续监控误路由、升级率和失败成本。第三方 40%~85% 只是案例区间；如果路由器判断不准或经常二次调用，节省会缩水甚至反转。

5. 其他杠杆（简述）

两根主杠杆之外，还有几个"顺手就能拧"的旋钮：

杠杆怎么省
压缩历史 / 对话（compaction）多轮太长时，只保留摘要而非全文回传，砍掉①号放大器。深入见 Phase 5（Agent 上下文工程）
控制输出长度输出单价与输入单价的关系取决于具体厂商/模型/日期；当 usage 证明输出美元占大头时，再用 max_tokens、明确 rubric 或结构化格式减少无用输出，避免低上限截断答案
批处理（厂商能力）Anthropic 官方 Message Batches 以标准价格的 50% 异步处理 Messages 请求，适合不要求即时响应的离线评测/分析等工作；多数批次在 1 小时内完成，但不是同步交互替代品。其他厂商的折扣、限制和时限需查其当前官方文档

优化顺序取决于测量结果：静态前缀占比高且会重复命中时先测缓存；请求难度分层明显时再评估路由；离线任务可比较 Batch；若输出本身占大头，先控制输出可能更直接。没有一项对所有系统都“几乎无副作用”。

6. 给 Agent 制定 Token 预算

"降本"落地前先要"知本"。给一个 Agent 制定预算的四步思路：

① 估算单次任务 token 量
     = system prompt + 历史 + 检索文档 + 输出
     （别忘 Agent 一次任务可能往返 LLM 多次，要乘往返数）
② 乘调用频次
     × 每天 / 每月请求数
③ 对照单价，得出未优化月成本（这是"上限"）
④ 用缓存 + 路由压下来
     静态前缀 → 按目标厂商/模型测缓存命中与盈亏平衡
     简单请求 → 仅在质量评测通过后路由到便宜模型
     → 得出优化后成本，与上限对比看省了多少

为什么先算再优化：不算预算，你既不知道钱花在哪一项（是历史太长？还是 system prompt 太肥？），也无法判断优化值不值。把它当成 Agent 上线前的"体检"。

Q 关于 Anthropic 的 Prompt Caching，下面哪个说法对？
Anthropic 缓存读取约 0.1× 输入价，5 分钟首次写约 1.25×，并非免费。前缀还要达到目标模型的最小缓存长度且保持一致；最终通过 cache_read_input_tokens / cache_creation_input_tokens 验证，而不是只看配置。

7. 成本估算练习：把两根杠杆算给你看

动手最能建立体感。给你一个具体场景，先自己算，再展开对答案。

【场景】客服 Agent
  · system prompt：2000 token，固定不变
  · 每次用户问题：约 200 token
  · 每次回答：约 300 token
  · 每天请求数：10 万次
  · 单价：输入 $3/M，输出 $12/M

问：
  ① 不加缓存，日成本是多少？
  ② Prompt Caching 能省下哪部分？大致省多少？
点我看算法与答案

① 不加缓存的日成本

每次输入 = system 2000 + 问题 200 = 2200 token
每次输出 = 300 token

日输入成本 = 100,000 × 2200 × $3 / 1e6 = $660
日输出成本 = 100,000 ×  300 × $12 / 1e6 = $360
─────────────────────────────────────────────
日总成本  = $660 + $360 = $1020 / 天

② Prompt Caching 能省哪部分

那 2000 token 的 system prompt 是静态前缀，每次一字不改——正是缓存的靶心。问题（200）和输出（300）每次都变，不动。

静态前缀原价 = 100,000 × 2000 × $3 / 1e6      = $600 / 天
命中缓存后   = $600 × 0.1（约 0.1×）           = $60  / 天
                                    省下 ≈ $540 / 天

加缓存后日总成本：
  缓存前缀稳态近似 $60 + 动态输入 $60 + 输出 $360 = $480 / 天

────────────────────────────────────────────────
$1020 → 约 $480，稳态账单下降约 53%
其中静态前缀的缓存读取从全价降到约 0.1×

这是稳态近似：严格计算还应把每个缓存周期的首次写入按 1.25×（或 1 小时写入 2×）计入；在 10 万次请求中一次写入影响很小，但低频场景不能忽略。缓存只作用于命中的静态前缀，动态问题与输出仍按常规定价。是否再加路由，要看质量评测和升级率。

💼 面试高频：“如何优化 LLM 成本？” 先用 usage / tracing 拆出 system、历史、工具结果、输出和重试分别占多少，再匹配手段：重复静态前缀测缓存；任务难度分层明显时测路由；长历史做压缩；输出过长收紧格式；支持批处理且不要求实时的任务比较 Batch。每项都要同时报告节省、质量、延迟和失败率。

🎯 速查卡：Token 经济学与降本

【成本公式】(in×in价 + out×out价) / 1e6；输入/输出价差以目标厂商与模型当前价格为准（细节→L18）

【钱从哪来·Agent 放大器】几乎都是"重复的静态输入"
  ① 历史每轮重发  ② 长 system prompt 每次都算
  ③ 工具循环多次往返  ④ 检索长文档反复出现

【Prompt Caching】适合重复、足够长、字节稳定的前缀
  Anthropic：5m写约1.25× / 1h写约2× / 读约0.1×
  粗略回本：5m约第2次使用；1h约第3次使用
  最小前缀随模型变；查 cache_creation_input_tokens / cache_read_input_tokens

【Model Routing】按业务评测分流，监控误路由、升级率和失败成本
  第三方 40~85% 仅案例，不是保证；路由器本身也有成本

【其他】历史压缩 / 控输出 / 厂商 Batch（Anthropic：异步、非即时工作负载按标准价50%）

【预算】单次量 × 频次 × 单价只是起点；还要加重试、路由、缓存写入
【原则】先测成本构成，再选杠杆；同时验证质量、延迟和失败率

本课最佳实践验收：夜间内容处理的工作负载计划

任务目标

为夜间内容批次形成工作负载级成本、缓存和分片路由计划，证明流量、稳定前缀、私有质量门与完整期望成本共同决定策略。

操作清单

  1. 把多个 trace 的成本分量乘以调用频次，汇总工作负载级美元组成。
  2. 按稳定前缀 digest 分组；只为有复用的组规划一次写入与后续读取，单次组不缓存。
  3. 为普通清洗和事实审查分别使用各自的私有通过率与流量占比选择路线。
  4. 输出分组缓存计划、按切片路由表和流量加权总期望成本。

通过标准

  • 高频升级切片能改变工作负载级最大美元项。
  • 相同稳定前缀的不同动态请求进入同组，工具版本变化进入新组。
  • 零复用组明确不缓存，不为一次使用支付缓存写入。
  • 普通切片可直达低成本候选，事实审查切片必须走达标级联。
  • 任一切片无达标路线时整体明确失败；标准输出只有验收标记。

先独立完成：不要再复制三个卡片的单样本断言。本题要利用卡片产物形成工作负载级计划：频次会改变成本主因，digest 用于分组，私有评测决定每个切片可用哪些路线。

课末参考验收（纯标准库；离线、确定性）
from dataclasses import dataclass
import hashlib
import json


COMPONENTS = (
    "uncached_input",
    "cache_write",
    "cache_read",
    "output",
    "retry",
    "escalation",
)


@dataclass(frozen=True)
class Trace:
    name: str
    calls: int
    unit_costs: dict[str, float]


@dataclass(frozen=True)
class Request:
    request_id: str
    tools: tuple[tuple[str, int], ...]
    system: str
    question: str


@dataclass(frozen=True)
class Route:
    name: str
    pass_rate: float
    first_cost: float
    escalation_probability: float = 0.0
    escalation_cost: float = 0.0


def workload_costs(traces: tuple[Trace, ...]) -> dict[str, float]:
    return {
        component: sum(
            trace.calls * trace.unit_costs[component]
            for trace in traces
        )
        for component in COMPONENTS
    }


def prefix_digest(request: Request) -> str:
    stable = json.dumps(
        {
            "system": request.system,
            "tools": sorted(request.tools),
        },
        ensure_ascii=False,
        sort_keys=True,
        separators=(",", ":"),
    )
    return hashlib.sha256(stable.encode()).hexdigest()


def cache_plan(requests: tuple[Request, ...]) -> dict[str, tuple[str, int, int]]:
    grouped: dict[str, list[Request]] = {}
    for request in requests:
        grouped.setdefault(prefix_digest(request), []).append(request)
    return {
        digest: (
            "cache" if len(group) > 1 else "skip",
            1 if len(group) > 1 else 0,
            len(group) - 1 if len(group) > 1 else 0,
        )
        for digest, group in grouped.items()
    }


def expected_cost(route: Route) -> float:
    return route.first_cost + route.escalation_probability * route.escalation_cost


def choose_route(routes: tuple[Route, ...], gate: float) -> Route:
    qualified = [route for route in routes if route.pass_rate >= gate]
    if not qualified:
        raise RuntimeError("no route passes this task slice")
    return min(qualified, key=expected_cost)


traces = (
    Trace("cleanup", 1_000, {
        "uncached_input": 0.0010,
        "cache_write": 0.0002,
        "cache_read": 0.0001,
        "output": 0.0015,
        "retry": 0.0001,
        "escalation": 0.0000,
    }),
    Trace("fact-review", 400, {
        "uncached_input": 0.0015,
        "cache_write": 0.0003,
        "cache_read": 0.0001,
        "output": 0.0030,
        "retry": 0.0002,
        "escalation": 0.0100,
    }),
)
composition = workload_costs(traces)
assert composition == {
    "uncached_input": 1.6,
    "cache_write": 0.32,
    "cache_read": 0.14,
    "output": 2.7,
    "retry": 0.18,
    "escalation": 4.0,
}
assert max(composition, key=composition.get) == "escalation"

requests = (
    Request("r-1", (("normalize", 1),), "cleanup-v1", "修正标点"),
    Request("r-2", (("normalize", 1),), "cleanup-v1", "统一空格"),
    Request("r-3", (("normalize", 2),), "cleanup-v1", "处理新版格式"),
)
plan = cache_plan(requests)
shared = prefix_digest(requests[0])
versioned = prefix_digest(requests[2])
assert shared == prefix_digest(requests[1])
assert shared != versioned
assert plan[shared] == ("cache", 1, 1)
assert plan[versioned] == ("skip", 0, 0)
assert requests[0].question != requests[1].question

routes = {
    "routine-cleanup": (
        0.85,
        0.70,
        (
            Route("cheap-direct", 0.93, 0.0010),
            Route("cheap-then-strong", 0.98, 0.0010, 0.10, 0.0200),
        ),
    ),
    "fact-review": (
        0.15,
        0.92,
        (
            Route("cheap-direct", 0.62, 0.0010),
            Route("cheap-then-strong", 0.95, 0.0010, 0.25, 0.0200),
            Route("strong-direct", 0.99, 0.0200),
        ),
    ),
}
route_table = {
    task: choose_route(options, gate)
    for task, (_, gate, options) in routes.items()
}
assert route_table["routine-cleanup"].name == "cheap-direct"
assert route_table["fact-review"].name == "cheap-then-strong"
weighted_expected_cost = sum(
    routes[task][0] * expected_cost(route)
    for task, route in route_table.items()
)
assert round(weighted_expected_cost, 6) == 0.00175

try:
    choose_route((Route("unsafe", 0.40, 0.0001),), gate=0.90)
except RuntimeError:

else:
    raise AssertionError("a slice with no qualified route must fail")

结果诊断：没有乘调用频次会把成本主因错误留在单次请求；同前缀动态请求未分组表示把后缀混入缓存键；工具版本变化仍命中旧组表示稳定前缀过期；单次组被缓存表示忽略写入回本；事实审查落到不达标直达路线或总成本未按流量加权，表示路由政策没有使用切片评测。

阶段实践检查点：成本感知的翻译路由

任务目标

为法律术语翻译建立成本感知路由，证明原生 Token 计数和私有质量门不可被长度或公开排名替代，达标策略按完整期望成本排序。

操作清单

  1. 通过注入的目标模型计数函数获取输入 Token，不使用通用字符近似。
  2. 为短但法律术语密集的请求保留 high effort/升级可能。
  3. 用私有留出通过率执行质量门。
  4. 把缓存读写、输出和升级概率纳入策略期望成本。

通过标准

  • 计数器恰好收到完整提示一次。
  • 短但困难样本不会因长度进入 cheap-only。
  • 未过私有质量门的策略不能入选。
  • 达标候选按完整期望成本排序。
  • 标准输出只有检查点标记。

from dataclasses import dataclass


@dataclass(frozen=True)
class TranslationStrategy:
    name: str
    effort: str
    input_rate: float
    cache_write_cost: float
    cache_read_cost: float
    output_cost: float
    retry_cost: float
    escalation_probability: float
    escalation_cost: float


def expected_cost(strategy, input_tokens):
    counted_input_cost = input_tokens * strategy.input_rate / 1_000_000
    return (
        counted_input_cost
        + strategy.cache_write_cost
        + strategy.cache_read_cost
        + strategy.output_cost
        + strategy.retry_cost
        + strategy.escalation_probability * strategy.escalation_cost
    )


def route(prompt, counter, strategies, private_pass_rates, gate):
    input_tokens = counter(prompt)
    qualified = [
        strategy for strategy in strategies
        if private_pass_rates[strategy.name] >= gate
    ]
    if not qualified:
        raise RuntimeError("no translation strategy passes holdout")
    winner = min(qualified, key=lambda strategy: expected_cost(strategy, input_tokens))
    return winner, input_tokens


calls = []

def native_counter(prompt):
    calls.append(prompt)
    return 137


prompt = "Translate: notwithstanding the foregoing"
assert len(prompt) < 80

strategies = [
    TranslationStrategy("cheap-only", "low", 2.0, 0, 0, 0.001, 0.0001, 0, 0),
    TranslationStrategy("cached-escalation", "high", 2.0, 0.001, 0.0002, 0.003, 0.0005, 0.20, 0.020),
    TranslationStrategy("strong-only", "high", 6.0, 0, 0, 0.010, 0.0005, 0, 0),
]
private_pass_rates = {
    "cheap-only": 0.70,
    "cached-escalation": 0.94,
    "strong-only": 0.98,
}
winner, counted_tokens = route(
    prompt, native_counter, strategies, private_pass_rates, 0.90
)
assert calls == [prompt]
assert counted_tokens == 137
assert private_pass_rates["cheap-only"] < 0.90
assert winner.name == "cached-escalation"
assert winner.effort == "high"
expected = expected_cost(winner, counted_tokens)
assert round(expected, 6) == 0.008974
assert expected == (
    137 * 2.0 / 1_000_000
    + 0.001
    + 0.0002
    + 0.003
    + 0.0005
    + 0.20 * 0.020
)

print("P2 CHECKPOINT COST-AWARE-ROUTING PASSED")

结果诊断：计数器未收到实际短难 prompt、调用不止一次或计数未进入 input 美元项，表示原生计数与路由断开；cheap-only 因文本短而入选表示长度绕过私有质量门；精确期望成本不等于 counted input + cache write/read + output + retry + 概率升级，表示至少一项遗漏；结果不是 cached-escalation 表示达标策略排序错误。
