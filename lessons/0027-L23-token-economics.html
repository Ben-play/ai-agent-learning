Token 经济学与降本杠杆

先测钱花在哪，再用缓存、路由、批处理和输出控制逐项验证收益

💡 为什么这课重要？

L18 教了你怎么数 Token、算成本。这一课回答下一个问题：怎么把这笔成本压下去。

Agent 一次任务可能反复调用 LLM，每轮又携带 system prompt、工具定义和增长的历史，因此成本会被放大。Prompt Caching 与 Model Routing 往往是高收益候选，但节省比例取决于静态前缀占比、命中率、任务分布和路由质量；第三方案例只能说明“可能做到”，不能保证你的系统也省一半。学完你会建立预算、测量成本构成，再按证据选择优化手段。

学习目标

完成本课后，你将能够：

  • 说清 Agent 场景里成本从哪来、为什么被放大
  • 用 Prompt Caching 把重复的静态前缀降到约 0.1× 价格（省约 90%）
  • 设计「静态前缀 + 动态后缀」的缓存友好结构
  • 用 Model Routing 让便宜模型兜底、贵模型只接难活
  • 给一个 Agent制定 token 预算并估算月成本

1. 快速回顾：成本公式（细节看 L18）

一句话把 L18 的结论捡回来。API 按 Token 收费，输入和输出分开定价，输出通常是输入的 3~5 倍：

成本 = (输入Token数 × 输入单价 + 输出Token数 × 输出单价) / 1,000,000

例：输入 2200 token、输出 300 token，输入 $3/M、输出 $12/M
    (2200×3 + 300×12) / 1e6 = $0.0102  ← 单次

单次不起眼，但 Agent 一天调 10 万次，就是 ~$1000/天。

这课不重复整节 L18，只做一件事：把公式里的每一项往下压。想复习"怎么数 Token、中英文谁更省"，回 L18。

2. 隐藏成本：Agent 的钱到底花在哪

为什么强调 Agent 的 token 消耗远大于单次 chat？因为有四个"放大器"，每一个都让输入 Token膨胀（Redis: LLM Token Optimization）：

放大器为什么费钱
① 多轮历史每轮重发第 n 轮请求携带的历史长度常随轮数近似线性增长；若每轮都重发完整历史，前 n 轮累计输入量常近似二次增长
② 长 system prompt那段角色设定 + 工具说明 + 少样本示例，每一次请求都完整计费，一个字不少
③ 工具调用循环一次任务 = 多次往返 LLM（想→调工具→读结果→再想）。每次往返都带上完整上下文
④ 检索长文档RAG / 长文档塞进上下文，动辄几千 token，且往往反复出现在多轮里

看出规律没有：费钱的几乎都是"重复的、静态的输入"——长 system prompt 每次都在、检索的文档反复出现、历史一遍遍重发。这正好是下一节第一根杠杆的靶心。

直觉校准：一个带 2000-token system prompt 的客服 Agent，如果每天 10 万次请求，光那段一字不改的 system prompt 每天就烧掉约 $600（按 $3/M 算）——而它的内容每次都一模一样。这就是缓存的用武之地。

3. Prompt Caching：静态前缀占比高时的强杠杆

原理：把静态的、重复的前缀（长 system prompt、固定的少样本示例、反复出现的文档）缓存起来。后续请求只要前缀逐字节命中缓存，这部分就大幅降价——你不再为"每次都一样的内容"付全价。

各家的数量级（以官方文档为准，这里用"约"）：

厂商缓存读（命中）缓存写（首次）TTL
Anthropic约 0.1× 输入价
（省约 90%）		约 1.25×
（首次略贵）		默认约 5 分钟；另有 1 小时选项（写约 2×）
OpenAI命中约省 50%~90%（视模型代次，较新模型可达 ~90%）自动，无额外写入费自动前缀缓存

数据出处：Anthropic: Prompt Caching、OpenAI: Prompt Caching。按相对输入价粗算：5 分钟缓存一次写入 1.25×，之后一次读取 0.1×，两次使用合计 1.35×，低于两次全价 2×；1 小时缓存写 2×，通常要到第三次使用（2×+0.1×+0.1×）才低于三次全价。实际收益还取决于命中时机、并发和静态前缀占比。

还有一个常被漏掉的门槛：可缓存前缀必须达到目标模型的最小 Token 数，且该阈值随模型/平台变化；太短时不会报错，只是不会建立缓存。因此不要背一个固定阈值，接入时查当前模型文档并看 usage 验证。

关键设计原则：把 prompt 拆成「静态前缀（可缓存）+ 动态后缀（每次变）」，静态部分放最前面。因为缓存是前缀匹配——前缀里任何一个字节变了，后面全部失效。所以千万别把时间戳、用户 ID、随机数塞进 system prompt 开头：

【缓存键设计：静态前缀 + 动态后缀】

┌─ 静态前缀（放前面，打缓存标记）──────────────┐
│  · 角色设定 / 行为准则          ← 一字不改      │  ← 命中缓存
│  · 工具定义（按名字排序，别乱序）              │     约 0.1×
│  · 固定的少样本示例 / 长文档                    │
└──────────────────────────────────────────────┘
┌─ 动态后缀（放后面，不缓存）────────────────────┐
│  · 本轮用户问题                                │  ← 全价
│  · 当前时间戳 / 请求 ID / 检索到的新片段        │     但很短
└──────────────────────────────────────────────┘

⚠️ 反例：system prompt 开头写 "当前时间：{now}"
   → 前缀每次都变 → 缓存永远不命中 → 白交钱

ProjectDiscovery 的案例报告了 59%~70% 的降幅（案例原文），但这是其请求结构和命中率下的结果，不是普遍保证。长 system prompt + 固定工具集通常是良好候选；若前缀太短、频繁变化、并发请求来不及读取刚写入的缓存，收益会显著下降。

验证 Anthropic 缓存是否命中：看 usage.cache_read_input_tokens；首次写入看 cache_creation_input_tokens，input_tokens 是未缓存的剩余部分。若重复请求的读取字段一直为 0，检查前缀长度、时间戳 / 随机 ID、工具顺序和并发时机。
Q 想让 Prompt Caching 真正省钱，prompt 该怎么组织？
缓存是前缀匹配：前缀里任何一个字节变了，后面全部失效。所以要把静态、每次都一样的内容（角色设定、固定工具、少样本示例）放最前面并打缓存标记，把动态内容（用户问题、时间戳、检索片段）放后面。反例——在开头写"当前时间：{now}"或每次换措辞——会让前缀每次都变，缓存永远不命中，白交钱。

4. 杠杆二：Model Routing（模型路由）

原理：不是所有请求都值得用最贵的模型。让便宜、快的小模型兜底处理简单请求，把贵、强的大模型只留给难请求。按难度分类、动态路由。

请求进来 → 判断难度
   ├─ 简单（分类 / 提取 / 闲聊 / 格式化） → 便宜快模型 兜底
   ├─ 中等（一般问答 / 总结）             → 中档模型
   └─ 困难（多步推理 / 复杂 Agent 规划）   → 顶级模型 只接这类

思路：先用便宜模型试；不确定 / 判为难，再升级到贵模型。

为什么可能有效：不同模型单价差异大，若流量中确有一批简单请求，且路由器能在不显著损害质量的前提下识别它们，就能降低平均成本。TrueFoundry 的文章汇总了 40%~85% 的案例区间（案例原文）；这不是保证，误路由、二次升级和路由器自身调用也会产生质量与成本。

工程落地：用一个 gateway（如 LiteLLM，见课程 RESOURCES）统一路由，业务代码不用管背后是哪个模型，换模型 / 调路由策略只改配置。这直接连回两条已学的原则：

  • 👉 L20：推理模型（思考更多）更贵更慢——别对"翻译一句话""判断正负面"这种简单活开推理，纯属烧钱。
  • 👉 L22：选型不是"永远选最强"，而是按任务难度匹配。路由就是把"选型"从一次性决策变成每请求的动态决策。
Q Model Routing 降本的核心思路是？
路由的关键是用业务评测识别哪些任务可以交给低成本候选，并持续监控误路由、升级率和失败成本。第三方 40%~85% 只是案例区间；如果路由器判断不准或经常二次调用，节省会缩水甚至反转。

5. 其他杠杆（简述）

两根主杠杆之外，还有几个"顺手就能拧"的旋钮：

杠杆怎么省
压缩历史 / 对话（compaction）多轮太长时，只保留摘要而非全文回传，砍掉①号放大器。深入见 Phase 5（Agent 上下文工程）
控制输出长度输出是输入的 3~5 倍价，最贵。设 max_tokens、在 prompt 里明确"简洁作答 / 只返回 JSON"，别让模型啰嗦
批处理（厂商能力）例如 Anthropic Message Batches 对非实时请求提供 50% 价格折扣；其他厂商的折扣、限制和完成时限不同，接入前查当前官方定价

优化顺序取决于测量结果：静态前缀占比高且会重复命中时先测缓存；请求难度分层明显时再评估路由；离线任务可比较 Batch；若输出本身占大头，先控制输出可能更直接。没有一项对所有系统都“几乎无副作用”。

6. 给 Agent 制定 Token 预算

"降本"落地前先要"知本"。给一个 Agent 制定预算的四步思路：

① 估算单次任务 token 量
     = system prompt + 历史 + 检索文档 + 输出
     （别忘 Agent 一次任务可能往返 LLM 多次，要乘往返数）
② 乘调用频次
     × 每天 / 每月请求数
③ 对照单价，得出未优化月成本（这是"上限"）
④ 用缓存 + 路由压下来
     静态前缀 → 按目标厂商/模型测缓存命中与盈亏平衡
     简单请求 → 仅在质量评测通过后路由到便宜模型
     → 得出优化后成本，与上限对比看省了多少

为什么先算再优化：不算预算，你既不知道钱花在哪一项（是历史太长？还是 system prompt 太肥？），也无法判断优化值不值。把它当成 Agent 上线前的"体检"。

Q 关于 Anthropic 的 Prompt Caching，下面哪个说法对？
Anthropic 缓存读取约 0.1× 输入价，5 分钟首次写约 1.25×，并非免费。前缀还要达到目标模型的最小缓存长度且保持一致；最终通过 cache_read_input_tokens / cache_creation_input_tokens 验证，而不是只看配置。

7. 成本估算练习：把两根杠杆算给你看

动手最能建立体感。给你一个具体场景，先自己算，再展开对答案。

【场景】客服 Agent
  · system prompt：2000 token，固定不变
  · 每次用户问题：约 200 token
  · 每次回答：约 300 token
  · 每天请求数：10 万次
  · 单价：输入 $3/M，输出 $12/M

问：
  ① 不加缓存，日成本是多少？
  ② Prompt Caching 能省下哪部分？大致省多少？
点我看算法与答案

① 不加缓存的日成本

每次输入 = system 2000 + 问题 200 = 2200 token
每次输出 = 300 token

日输入成本 = 100,000 × 2200 × $3 / 1e6 = $660
日输出成本 = 100,000 ×  300 × $12 / 1e6 = $360
─────────────────────────────────────────────
日总成本  = $660 + $360 = $1020 / 天

② Prompt Caching 能省哪部分

那 2000 token 的 system prompt 是静态前缀，每次一字不改——正是缓存的靶心。问题（200）和输出（300）每次都变，不动。

静态前缀原价 = 100,000 × 2000 × $3 / 1e6      = $600 / 天
命中缓存后   = $600 × 0.1（约 0.1×）           = $60  / 天
                                    省下 ≈ $540 / 天

加缓存后日总成本：
  缓存前缀稳态近似 $60 + 动态输入 $60 + 输出 $360 = $480 / 天

────────────────────────────────────────────────
$1020 → 约 $480，稳态账单下降约 53%
其中静态前缀的缓存读取从全价降到约 0.1×

这是稳态近似：严格计算还应把每个缓存周期的首次写入按 1.25×（或 1 小时写入 2×）计入；在 10 万次请求中一次写入影响很小，但低频场景不能忽略。缓存只作用于命中的静态前缀，动态问题与输出仍按常规定价。是否再加路由，要看质量评测和升级率。

💼 面试高频：“如何优化 LLM 成本？” 先用 usage / tracing 拆出 system、历史、工具结果、输出和重试分别占多少，再匹配手段：重复静态前缀测缓存；任务难度分层明显时测路由；长历史做压缩；输出过长收紧格式；支持批处理且不要求实时的任务比较 Batch。每项都要同时报告节省、质量、延迟和失败率。

🎯 速查卡：Token 经济学与降本

【成本公式】(in×in价 + out×out价) / 1e6；输出通常 3~5× 输入（细节→L18）

【钱从哪来·Agent 放大器】几乎都是"重复的静态输入"
  ① 历史每轮重发  ② 长 system prompt 每次都算
  ③ 工具循环多次往返  ④ 检索长文档反复出现

【Prompt Caching】适合重复、足够长、字节稳定的前缀
  Anthropic：5m写约1.25× / 1h写约2× / 读约0.1×
  粗略回本：5m约第2次使用；1h约第3次使用
  最小前缀随模型变；查 cache_creation_input_tokens / cache_read_input_tokens

【Model Routing】按业务评测分流，监控误路由、升级率和失败成本
  第三方 40~85% 仅案例，不是保证；路由器本身也有成本

【其他】历史压缩 / 控输出 / 厂商 Batch（如 Anthropic 非实时折扣50%）

【预算】单次量 × 频次 × 单价只是起点；还要加重试、路由、缓存写入
【原则】先测成本构成，再选杠杆；同时验证质量、延迟和失败率

总结

  • 成本 = 输入输出分开算，输出通常 3~5× 输入；Agent 因多轮/长 prompt/工具循环，token 消耗远超单次 chat
  • 费钱的几乎都是重复的静态输入——这正是两根杠杆的靶心
  • Prompt Caching：适合足够长、重复且字节稳定的前缀；Anthropic 5m 写约 1.25×、1h 写约 2×、读约 0.1×，必须看 usage 验证命中
  • Model Routing：按业务评测分流并监控误路由/升级率；第三方节省区间只作案例
  • 先制定包含重试、缓存写入和路由调用的预算，再按成本构成选择缓存、路由、压缩、输出控制或 Batch，并同时验证质量与延迟
