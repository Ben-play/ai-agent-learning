Skills 按需加载与权限边界

只在需要时打开做事说明，不把说明书当成执行许可

为什么这课重要？

客服助手大多数时候只回答政策。如果每次都塞进起草和审阅流程，会增加无关上下文，也更难排查为什么误触发。这里把「怎么起草」单独保存，明确要求起草时才取用。

学习目标

写出可触发也可排除的 Skill 描述；区分元数据、正文和可选资料的加载时机，以及加载与授权。

1. Skill 文件如何创建，何时读取

以 Agent Skills 参考为底稿：在目录 ticket-draft/ 创建文件 SKILL.md。两个 --- 之间是 YAML 元数据，后面是 Markdown 正文。最小文件需要 name 和 description；name 与目录名一致。

---
name: ticket-draft
description: 仅在用户明确要求起草支持工单时加载。不用于政策问答或提交工单。
---
根据本次验证过的引用起草标题和正文，标记为待人工确认。不要创建、更新或发送真实工单。
何时读什么用途
发现名称、描述等轻量元数据判断是否值得加载。
匹配后SKILL.md 正文读取起草步骤与边界。
确有需要可选模板、参考资料只读需要的内容，不整目录塞进上下文。

这是规范的加载模式，真实宿主实现及授权要分别验证。Skill 是做事知识；工具 是操作接口；应用授权才能决定是否允许实际调用。实验字段 allowed-tools 不能当作跨宿主的授权保证。起始项目的 skill 字段只标记选择了起草流程，不会发现或加载真实的 SKILL.md。

最佳实践：正触发和反触发成对验收

一条检查“明确要求时读取”，另一条检查“相似问句时不读取”。只看最终文字很难证明第二条，记录实际加载次数。

Q 只问「工单草稿是什么」，第一次发现 Skill 时应该怎么做？
描述用于判定是否匹配，了解含义不是起草请求。即使匹配，也不会因此得到操作权限。

2. 动手：用本地计数测「有没有加载」

先自己写一份上面的 ticket-draft/SKILL.md，检查名称、正反触发条件和禁止动作，不安装到真实宿主。再预测只询问、明确起草、要求提交三条路径各加载几次。代码用可信应用已判定的 intent 演示，不做自然语言分类；load=load_body 是把本地加载函数交给选择器，不是马上调用它。

展开加载器替身与离线自检
metadata = {"name": "ticket-draft", "description": "仅明确要求起草时使用"}
loaded = []


def load_body(name):
    loaded.append(name)
    return "生成待人工确认的草稿。"


def select_instructions(intent, *, load):
    if intent != "draft":
        return None
    return load(metadata["name"])


assert select_instructions("answer", load=load_body) is None
assert loaded == []
assert select_instructions("draft", load=load_body) == "生成待人工确认的草稿。"
assert loaded == ["ticket-draft"]
assert select_instructions("send", load=load_body) is None
assert loaded == ["ticket-draft"]
print("L43 ACCEPTED")

用 python -I 文件名.py 运行，唯一通过标记为 L43 ACCEPTED。这是加载决策的检查，不是实际的权限测试；没有任何可提交的工具存在。

面试自查

Skill 与工具最大的区别是什么？

Skill 提供流程知识；工具提供具体操作。二者也不能自行替代授权。

为什么描述要写“不用于什么”？

能区分术语相似的任务，减少错误匹配。

目录里所有资料要立即读吗？

不需要。先判定是否加载正文，完成任务确实需要时再加载附加材料。

为什么不直接测最后回答？

回答可能碰巧正确，无法证明正文没有提前加载；要观察加载本身。

小结与一手参考

先读元数据 → 匹配才读正文 → 需要才读资料。授权由应用另判。隔天写出一个描述相近但不该加载的反例。
