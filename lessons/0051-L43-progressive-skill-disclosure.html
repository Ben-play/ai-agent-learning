Skills 按需加载与权限边界

只在需要时打开做事说明，不把说明书当成执行许可

为什么这课重要？

客服助手大多数时候只回答政策。如果每次都塞进起草和审阅流程，会增加无关上下文，也更难排查为什么误触发。这里把「怎么起草」单独保存，明确要求起草时才取用。

学习目标

写出可触发也可排除的 Skill 描述；区分元数据、正文和可选资料的加载时机，以及加载与授权。

1. Skill 文件如何创建，何时读取

Skill 是一份可复用的办事说明。依据 Agent Skills 规范和本课的格式速查，先建目录 ticket-draft/，在里面写 SKILL.md。两个 --- 之间是 YAML 元数据，必填的 name 与目录同名，description 写明做什么和何时用。先写清输出是草稿，再列出容易混淆的「问政策」和「提交」；这比只写「处理工单」更能帮助宿主匹配任务。

---
name: ticket-draft
description: 仅在用户明确要求起草支持工单时加载。不用于政策问答或提交工单。
---
根据本次验证过的引用起草标题和正文，标记为待人工确认。不要创建、更新或发送真实工单。
何时读什么用途
发现名称、描述等轻量元数据判断是否值得加载。
匹配后SKILL.md 正文读取起草步骤与边界。
确有需要可选模板、参考资料只读需要的内容，不整目录塞进上下文。

正文写成匹配后能照着做的步骤：使用本次校验过的引文，生成标题和正文，明确只交稿。只要这些步骤能完成任务，就不用附文件。假如某种工单另有格式，可把模板放在 assets/，把详细规则放在 references/，在正文用相对路径说明各文件何时需要。普通起草不因此读完整目录，附加资料也不能把未获准的材料变成证据。

2. 同一业务的三种意图，何时才读正文

「导出文件保留多久？」只走证据问答：本轮目标是回报天数，没有起草理由，Skill 至多参与元数据匹配。「请根据保留期政策起草支持工单」明确要求草稿，才读正文，用已校验的引文生成一份待确认文本；若普通格式已经够用，不读附加模板。「请直接提交工单」不属于起草，Phase 4 应拒绝，不读正文，也不把拒绝悄悄改成一次起草。只说「帮我处理工单」而目的不清，先问是查政策还是要草稿。

渐进披露的收益来自并非每轮都要做同一套步骤：问答不带起草说明，普通草稿不带特殊表单；也可独立修改表单而不改问答提示。代价是多了一道匹配决策，描述写宽会误加载，写窄会漏掉合理的起草请求。如果规则短而且每轮都要用，留在主流程反而更简单。这里观察的是正文读取次数，不是实测 Token、延迟或成本。

3. 用加载记录定位问题，不用它推导授权

下面的本地选择器接收应用已确认的标签，不理解上面的自然语言。按顺序给它 answer、draft、send，预期累计正文读取数是 0、1、1；最后一个 1 是前例留下的读取，不是提交请求又读了一次。若问答让计数增加，先查是否判定前就调用了加载器；若明确起草却没有记录，先查输入标签和选择分支。项目本身的 skill="ticket-draft" 也只标记选择了内存草稿模板，不代表从磁盘读过 SKILL.md。

在真实宿主中，发现 Skill 是知道有哪些办事说明，发现工具是知道有哪些可提议的操作；两者都不表示这个用户能对这条记录执行操作。执行点应由应用按身份、资源范围、参数和审批独立判定；就算能看到某个提交工具，也不能把起草匹配当许可。规范里的 allowed-tools 是实验字段，支持随实现而异。核对宿主时，要分别留发现、正文读取和执行许可的记录，不能用本地计数替代。

最佳实践：按明确意图加载，另验操作权限

适用与限制：问答和起草共用词汇、起草说明却不是每轮都需要时，用正反例检查正文加载点。本地替身只观测加载选择，不模拟宿主授权。

错误做法：命中词就预读

收到「工单草稿是什么？」时，因为出现「工单」就读正文。即使最终只解释概念，看似正确的回答也掩盖了那次多余的读取。

推荐做法：只为明确任务读取

同一问句由应用判定为解释，只用元数据做匹配，正文零读取。换成明确起草才读取；正文不能把「起草」升级成「提交」。

取舍：把加载放在意图判断之后，可以减少上下文和非必要读取，但需要维护触发描述和反例。若规则极短且每次都需要，可留在主流程；意图不清时先澄清。真实宿主要分别验加载记录、工具权限与审批，不能从加载成功推出授权。

  1. 用一个明确起草请求和一个只询问的近邻例界定触发，再加入禁止提交的意图。
  2. 运行原加载器自检，逐案检查记录，而不只看最后的文字。

结果诊断：L43 ACCEPTED 表示只有明确起草令替身读取一次。若询问或提交增加计数，先修加载门槛；此结果与真实宿主是否能执行某个工具无关。

Q 只问「工单草稿是什么」，第一次发现 Skill 时应该怎么做？
描述用于判定是否匹配，了解含义不是起草请求。即使匹配，也不会因此得到操作权限。

4. 动手：用本地计数测「有没有加载」

先自己写一份上面的 ticket-draft/SKILL.md，检查名称、正反触发条件和禁止动作，不安装到真实宿主。再预测只询问、明确起草、要求提交三条路径各加载几次。代码用可信应用已判定的 intent 演示，不做自然语言分类；load=load_body 是把本地加载函数交给选择器，不是马上调用它。

阶段检查点：用证据答续借问题，只在请求时起草提醒

串起 L42 的证据边界和 L43 的加载门槛。先把预算设为只够装主规则，记录实际发送内容、引用及加载次数。预测预算少一个字节、缺相关证据、只引补充条款时，流程在哪里停止；再给够两条的预算，看看补充条款能否回答续借次数。

本例先用固定响应器回传引文，再由应用在显式起草且引文有效时调用本地加载器生成草稿。字节上限只针对这一轮证据请求，不计后续本地模板；真实宿主须按目标接口核算发送的所有内容，另外验证 Skill 加载行为和实际工具权限。本例不分类自然语言、不装载真实 Skill，也不提交任何东西。

展开独立参考：串起证据预算、引用和加载探针
import json

question = "图书可以续借几次？"
primary = {"source_id": "LIB-01", "quote": "未到期的借阅可续借一次。"}
extra = {"source_id": "LIB-02", "quote": "续借可在服务台办理。"}
requests, reads = [], []


def encode(text, rows):
    return json.dumps(dict(question=text, evidence=rows), ensure_ascii=False,
                      separators=(",", ":")).encode("utf-8")


def fixture(payload, *, citation=None):
    requests.append(payload)
    return json.loads(payload)["evidence"][0] if citation is None else citation


def load_body(name):
    reads.append(name)
    return "待确认的续借提醒："


def run(text, intent, limit, *, respond=fixture):
    if intent not in {"answer", "draft_reminder"}:
        return "invalid_request", None, None
    if text != question:
        return "needs_evidence", None, None
    payload = encode(text, [primary])
    if len(payload) > limit:
        return "budget_exceeded", None, None
    full = encode(text, [primary, extra])
    if len(full) <= limit:
        payload = full
    citation = respond(payload)
    if citation not in json.loads(payload)["evidence"]:
        return "invalid_response", None, None
    if citation != primary:  # 只有主条款能支持「续借几次」的结论。
        return "invalid_response", None, None
    if intent == "draft_reminder":
        draft = load_body("renewal-reminder") + citation["quote"]
        return "drafted", citation, draft
    return "answered", citation, None


limit = len(encode(question, [primary]))
assert run(question, "answer", limit) == ("answered", primary, None), "有效引文未通过"
assert len(requests[0]) == limit and json.loads(requests[0])["evidence"] == [primary], "装配与预算不符"
assert reads == [], "问答不应读起草正文"
assert run(question, "draft_reminder", limit - 1) == ("budget_exceeded", None, None)
assert run("丢失的书能用新书抵还吗？", "draft_reminder", limit) == ("needs_evidence", None, None)
assert run(question, "send_reminder", limit) == ("invalid_request", None, None)
assert len(requests) == 1 and reads == [], "预算、证据或意图未通过时不应调用或读取"
assert run(question, "draft_reminder", limit, respond=lambda p: fixture(p, citation=extra)) == (
    "invalid_response", None, None)
assert len(requests) == 2 and reads == [], "已知但未发送的引文不能触发起草"
full_limit = len(encode(question, [primary, extra]))
assert run(question, "draft_reminder", full_limit, respond=lambda p: fixture(p, citation=extra)) == (
    "invalid_response", None, None), "即使已发送，补充条款也无法说明续借次数"
assert len(requests) == 3 and json.loads(requests[-1])["evidence"] == [primary, extra] and reads == []
assert run(question, "draft_reminder", limit) == ("drafted", primary, "待确认的续借提醒：" + primary["quote"])
assert len(requests) == 4 and reads == ["renewal-reminder"], "明确起草且有有效证据才读一次"
print("P4 CONTEXT AND SKILL PASSED")

整块复制后用 python -I 文件名.py 运行，只应打印 P4 CONTEXT AND SKILL PASSED。缺证据或预算不足却有请求，先查输入守卫；发出后引用被拒却读了正文，检查引文校验和加载的先后；只问问题也读正文，查显式意图门槛。这些记录不证明真实权限。

面试自查

先合上答案，按「结论 → 理由 → 如何验证」作答，再展开追问。

Q1「保留期工单草稿要写哪些信息？」和「请按保留期政策写一份工单草稿」都提到草稿。在证据检查通过的前提下，哪条才该读 Skill 正文？

参考回答：只给第二条读正文。第一条在询问该填什么，用名称和描述判断不匹配即可；第二条才把拟稿交给助手。对这对近邻输入，要核对实际读取记录，而不只是看回答像不像草稿。

追问：「帮我处理这张工单」既没说查什么，也没说拟稿，怎么办？

答题要点：先澄清意图，不预读正文；不能把不明确的请求自动当成拟稿。

Q2「每轮只用本轮获准的证据」和「特殊格式草稿要附三栏表」都放在起草 Skill 里，好吗？

参考回答：不好。问答也要遵守证据使用规则，应留在主流程，由应用把关；三栏表只服务特殊拟稿，可由正文按需指向模板。验证普通问答不读正文也遵守证据限制，普通草稿不读特殊模板。

追问：如果三栏格式只有一句话，而且每份草稿都要用呢？

答题要点：把它直接写进拟稿正文，省掉一次额外读取；仍不必让问答加载拟稿正文。

Q3100 个请求均有足够证据：90 个问政策，8 个要普通草稿，2 个要专用格式草稿。不考虑缓存，改成按需加载有什么取舍？

参考回答：建议按需读。按每轮分别记录，正确匹配时只读正文 10 次、专用模板 2 次，问答不混入拟稿说明。代价是多了意图和模板选择，可能漏载；抽查各类读取记录，不能把读取次数当成延迟或费用。

追问：专用格式请求读了正文，却没读模板，先排哪一步？

答题要点：先核对正文里的模板条件与应用的格式判断；已有正文读取，不必先改 Skill 的匹配描述。

Q4本地替身从空记录依次收到 answer → draft → answer → send，正文累计读取数是 0、1、2、2。问答文字都对，哪里出错？

参考回答：第三轮问答误读了正文，预期累计数是 0、1、1、1。逐轮比对意图和新增读取记录，查加载器是不是在判断意图前就被调用，或是否误入起草分支。最后一个计数没增加，不能说提交请求又读了一次。

追问：修到计数符合预期，能证明真实宿主的提交权限正确吗？

答题要点：不能。替身只测已确认标签下的读取，不测真实授权；在宿主的执行点另验身份、资源范围、参数和审批。

小结与一手参考

先读元数据 → 匹配才读正文 → 需要才读资料。授权由应用另判。隔天写出一个描述相近但不该加载的反例。
