LLM 本质与生成参数

LLM 只是在"猜下一个词"——但怎么猜，你能调

💡 为什么这课重要？

你接下来所有的 Agent 代码，本质都是在调一个"下一个 Token 预测器"。不理解它怎么预测、凭什么有时候胡说、有时候很稳，你就只能靠玄学调参。

这一课把 LLM 的工作原理讲到“够用就好”的程度（不写 Transformer 代码），然后拆开三个常见的解码概念——temperature、top_p、重复惩罚。先理解它们如何改变候选 Token，再看具体厂商是否真的开放这些请求字段：概念通用，不代表每个 API 都有同名旋钮。这是 Phase 2 的开篇，也是面试必问的第一组概念。

学习目标

完成本课后，你将能够：

  • 用一句话说清 LLM 的本质：基于概率的下一个 Token 预测
  • 直觉理解"注意力"在做什么（不涉及数学）
  • 讲清 temperature 如何缩放概率分布、top_p 如何裁剪候选集
  • 区分 frequency_penalty 与 presence_penalty，并知道它们不是所有厂商都有
  • 先查目标模型支持哪些字段，再为抽取 / 创作 / 代码任务选择控制方式
  • 说清一个反直觉事实：temperature=0 也不保证完全可复现

1. LLM 的本质：一台下一个 Token 预测机

抛开所有神秘感，一个大语言模型做的事只有一件：给定前面的一串 Token，预测下一个 Token 的概率分布。

比如输入 "今天天气真"，模型会输出一张概率表：

好   → 0.62
不错 → 0.19
热   → 0.08
糟   → 0.04
...（词表里每个 Token 都有一个概率）

然后按某种策略从这张表里挑一个，把它接到输入后面，再重复这个过程——一个 Token 一个 Token 地"续写"。这就是"生成"。怎么挑，就是本课后半段的生成参数在控制的事。

关键推论：LLM 没有"事实数据库"，它只是在预测"看起来最该接下去的词"。这正是幻觉（L19）的根源——统计上合理 ≠ 事实正确。

Q LLM 生成文本的本质是什么？
LLM 的核心是基于概率的下一个 Token 预测：给定上文，输出整个词表的概率分布，再按采样策略挑一个接上去。它不检索数据库、也不保证真值——"统计上合理"不等于"事实正确"，这就是幻觉的根源。

2. 注意力：模型怎么知道"该看哪几个词"

预测下一个 Token 时，上文里不是每个词都同样重要。注意力机制（Attention）让模型在预测时，动态地给上文中的每个 Token 分配"关注权重"——相关的词权重高，无关的词权重低。

一个直觉例子：

"小明把书放在桌子上，然后他坐下来读 ___"

要预测这个空，模型需要"注意"到前面的 书（读什么）和 小明/他（谁在读），而不是 桌子。注意力就是让"他"这个词能回头连接到"小明"、让"读"连接到"书"的机制。

Transformer 架构（2017 年论文《Attention Is All You Need》）就是把注意力堆叠很多层。你不需要会推导它——只需记住：注意力 = 模型在每一步动态决定"上文里哪些 Token 现在最相关"。想建立可视化直觉，3Blue1Brown 的 Transformer 视频是最好的入门。

面试常问"注意力是什么"。合格回答不是背公式，而是：一种让模型在预测每个 Token 时，按相关性给上文各 Token 加权的机制，从而捕捉长距离依赖（如代词指代）。

3. Temperature：给概率分布"加热"或"降温"

回到第 1 节那张概率表。Temperature（温度）在采样前对这张表做缩放：

  • 低温（→0）：让高概率 Token 更突出、低概率的被压得更低。分布变"尖"，模型几乎总挑最可能的那个 → 稳定、保守、可预测。
  • 高温（→1 甚至更高）：把差距拉平，低概率 Token 也有机会被选中。分布变"平"，输出更多样、有创造力、也更容易跑偏。

直觉记法：温度高 = 脑洞大，温度低 = 循规蹈矩。数学上，temperature 通常是在 softmax 前对 logits 除以 T——T 越小，分布越集中；部分实现把 T=0 特判为贪心 / argmax（详见 Hugging Face: Decoding Strategies）。

先分清“解码概念”和“API 字段”。Temperature / top-p 是理解采样的基础，但并非每个模型都开放这些字段。例如当前 Claude Opus 4.8 / 4.7 与 Claude Sonnet 5 不接受 temperature、top_p、top_k；使用这些模型时，应通过清晰提示词约束输出，并在需要推理深度控制时使用 output_config.effort（L20 再展开）。所以表里的数值只适用于确实支持该采样参数的 API，接入前先查模型文档。
任务建议 temperature为什么
抽取信息 / 分类 / 函数调用0 ~ 0.3要确定、可复现，不要惊喜
问答 / 摘要 / 改写0.3 ~ 0.7准确为主，略有灵活
创意写作 / 头脑风暴0.7 ~ 1.0+要多样性和新鲜感
Q 要让 Agent 抽取字段结果稳定，temperature 应该？
抽取 / 分类 / 函数调用要的是确定和可复现，应把 temperature 调到 0~0.3。温度越低，分布越尖、越倾向选最高概率 Token，输出越稳定。高温带来的多样性在这类任务里只会添乱。

4. Top-P：只从"最可能的一小撮"里采样

Top-P（核采样 / nucleus sampling）换一个思路裁剪候选：把 Token 按概率从高到低累加，只保留累计概率达到 P 的那一小撮，其余全部丢弃，再在这撮里采样。

top_p = 0.9 的含义：
按概率排序累加，取到累计 90% 为止的那批 Token，
剩下 10% 概率的"长尾低概率词"直接排除。

它的好处是自适应：模型很确定时（一个 Token 就占 95%），候选集自动变小；模型不确定时（概率分散），候选集自动变大。这比固定取前 K 个（top-k）更聪明——出处见 Hugging Face: How to generate text。

temperature vs top_p 怎么配？如果目标 API 同时支持两者，通常只重点调一个、另一个留默认，便于归因；同时把两个都往极端调，行为会很难预测。常见做法是固定 top_p=1 只调 temperature，或反之。若目标模型不接受这些字段，就不要硬塞参数，应改用该厂商支持的控制方式。

⚠️ 陷阱题："temperature 和 top_p 有什么区别？" — temperature 是缩放整个分布的形状（改变每个 Token 被选中的相对概率）；top_p 是裁剪候选集（先砍掉长尾，再采样）。一个改"概率"，一个改"能选谁"。

5. 两个惩罚项：治重复啰嗦

一些 API（例如部分 OpenAI 风格接口）提供重复惩罚字段，通过调低已出现 Token 的 logit 来抑制车轱辘话（参考 Prompt Engineering Guide: LLM Settings）：

  • frequency_penalty（频率惩罚）：按 Token 出现的次数成比例惩罚——出现越多，越难再出现。治"同一个词反复刷屏"。
  • presence_penalty（存在惩罚）：只要 Token 出现过一次就施加固定惩罚，与次数无关。鼓励模型换新话题、引入新词。

在提供这两个字段的接口里，常见范围是 -2.0 ~ 2.0、默认 0。区别一句话：frequency 看“出现几次”（按量），presence 看“有没有出现”（按 0/1）。但它们不是通用 LLM 参数；目标模型没有这些字段时，应通过提示词、输出约束或厂商提供的其他机制控制重复，不能照搬请求体。

Q frequency_penalty 与 presence_penalty 的核心区别是？
两者都惩罚已出现的 Token，区别在缩放方式：frequency_penalty 按出现次数成比例（越频繁越重罚），presence_penalty 只看出现过没有（0/1 固定罚）。前者治刷屏式重复，后者鼓励引入新内容。

6. 反直觉真相：temperature=0 ≠ 完全可复现

很多人以为"temperature 设 0，模型就每次输出一模一样"。不对。 temperature=0 让模型总是挑最高概率的 Token（贪心解码），逻辑上确实该确定——但实践中仍可能有细微差异。原因：

  • 浮点数不满足结合律：(a+b)+c ≠ a+(b+c)。GPU 上并行归约的加法顺序会变，导致 logits 有极小抖动，偶尔翻转"谁是第一名"。
  • 批处理 / 硬件差异：同一请求在不同 batch 大小、不同 GPU、不同推理引擎版本下，数值路径不同。

这不是玄学，是被 Thinking Machines Lab 和 vLLM 维护者系统分析过的工程现实。面试加分点：在支持采样控制的 API 上，低温 / 贪心解码配合固定 seed（若厂商提供）只能提高一致性，不能保证逐字节相同。Seed 也是厂商能力：部分 OpenAI 接口提供，Anthropic Messages API 当前没有对应请求字段；当前 Claude 模型若不接受 temperature，也不能照搬“temperature=0”方案。

这条对 Agent 工程很实际：不要把关键逻辑建立在"LLM 输出逐字节稳定"的假设上。要稳，就用结构化输出 + 校验（后面 Pydantic 那套），而不是指望采样完全确定。

7. 实战：先问“支持什么”，再谈怎么调

🧪 Agent 场景练习：为抽取、创作和代码任务选择控制方式（先自己判断）

题目：Provider A 支持 temperature / top_p；当前 Claude Opus 4.8 不支持这些采样字段，但支持清晰提示词与 output_config.effort。分别为“发票字段抽取”“广告创意”“复杂代码审查”选择控制方式。

参考答案：

  • 发票抽取：Provider A 可用低 temperature 并配结构化输出；Claude Opus 4.8 不传采样参数，改用严格输出格式、明确字段规则和运行时校验。稳定性主要靠结构化约束，不靠“温度必然可复现”。
  • 广告创意：Provider A 可提高 temperature 或调 top-p（只重点调一个）；Claude 则在提示词里明确“给出多种差异明显的方向”，而不是发送不支持的字段。
  • 复杂代码审查：重点不是提高随机性。两类 provider 都应先明确审查标准；Claude 可在 L20 学到用较高 effort 增加分析深度，再通过测试验证结论。

判断顺序：任务需要什么行为 → 目标模型支持什么接口 → 选择对应控制手段。不要先背一组参数，再强塞给所有模型。

总结

  • LLM 的本质是基于概率的下一个 Token 预测，生成就是"预测→采样→接上"的循环
  • 注意力让模型按相关性给上文各 Token 加权，捕捉长距离依赖
  • temperature 缩放分布形状，top_p 裁剪候选集；它们是通用解码概念，但不是每个 API 都开放的字段
  • frequency_penalty 按次数罚、presence_penalty 按有无罚；同样要先确认目标厂商支持
  • 控制输出的顺序是：明确任务行为 → 查模型能力 → 选采样参数、提示约束或结构化校验
  • 即便 API 支持 temperature=0 / seed，也不能保证逐字节复现；当前 Claude 模型还可能不接受这些采样字段
