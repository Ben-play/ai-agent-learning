LLM 本质与生成参数

LLM 只是在"猜下一个词"——但怎么猜，你能调

💡 为什么这课重要？

你接下来所有的 Agent 代码，本质都是在调一个"下一个 Token 预测器"。不理解它怎么预测、凭什么有时候胡说、有时候很稳，你就只能靠玄学调参。

这一课把 LLM 的工作原理讲到“够用就好”的程度（不写 Transformer 代码），然后拆开三个常见的解码概念——temperature、top_p、重复惩罚。先理解它们如何改变候选 Token，再看具体厂商是否真的开放这些请求字段：概念通用，不代表每个 API 都有同名旋钮。这是 Phase 2 的开篇，也是面试必问的第一组概念。

学习目标

完成本课后，你将能够：

  • 用一句话说清 LLM 的本质：基于概率的下一个 Token 预测
  • 直觉理解"注意力"在做什么（不涉及数学）
  • 讲清 temperature 如何缩放概率分布、top_p 如何裁剪候选集
  • 区分 frequency_penalty 与 presence_penalty，并知道它们不是所有厂商都有
  • 先查目标模型支持哪些字段，再为抽取 / 创作 / 代码任务选择控制方式
  • 说清一个反直觉事实：temperature=0 也不保证完全可复现

1. LLM 的本质：一台下一个 Token 预测机

抛开所有神秘感，一个大语言模型做的事只有一件：给定前面的一串 Token，预测下一个 Token 的概率分布。

比如输入 "今天天气真"，模型会输出一张概率表：

好   → 0.62
不错 → 0.19
热   → 0.08
糟   → 0.04
...（词表里每个 Token 都有一个概率）

然后按某种策略从这张表里挑一个，把它接到输入后面，再重复这个过程——一个 Token 一个 Token 地"续写"。这就是"生成"。怎么挑，就是本课后半段的生成参数在控制的事。

关键推论：LLM 没有"事实数据库"，它只是在预测"看起来最该接下去的词"。这正是幻觉（L19）的根源——统计上合理 ≠ 事实正确。

Q LLM 生成文本的本质是什么？
LLM 的核心是基于概率的下一个 Token 预测：给定上文，输出整个词表的概率分布，再按采样策略挑一个接上去。它不检索数据库、也不保证真值——"统计上合理"不等于"事实正确"，这就是幻觉的根源。

2. 注意力：模型怎么知道"该看哪几个词"

预测下一个 Token 时，上文里不是每个词都同样重要。注意力机制（Attention）让模型在预测时，动态地给上文中的每个 Token 分配"关注权重"——相关的词权重高，无关的词权重低。

一个直觉例子：

"小明把书放在桌子上，然后他坐下来读 ___"

要预测这个空，模型需要"注意"到前面的 书（读什么）和 小明/他（谁在读），而不是 桌子。注意力就是让"他"这个词能回头连接到"小明"、让"读"连接到"书"的机制。

Transformer 架构（2017 年论文《Attention Is All You Need》）就是把注意力堆叠很多层。你不需要会推导它——只需记住：注意力 = 模型在每一步动态决定"上文里哪些 Token 现在最相关"。想建立可视化直觉，3Blue1Brown 的 Transformer 视频是最好的入门。

面试常问"注意力是什么"。合格回答不是背公式，而是：一种让模型在预测每个 Token 时，按相关性给上文各 Token 加权的机制，从而捕捉长距离依赖（如代词指代）。

3. Temperature：给概率分布"加热"或"降温"

回到第 1 节那张概率表。Temperature（温度）在采样前对这张表做缩放：

  • 低温（→0）：让高概率 Token 更突出、低概率的被压得更低。分布变"尖"，模型几乎总挑最可能的那个 → 稳定、保守、可预测。
  • 高温（→1 甚至更高）：把差距拉平，低概率 Token 也有机会被选中。分布变"平"，输出更多样、有创造力、也更容易跑偏。

直觉记法：温度高 = 脑洞大，温度低 = 循规蹈矩。数学上，temperature 通常是在 softmax 前对 logits 除以 T——T 越小，分布越集中；部分实现把 T=0 特判为贪心 / argmax（详见 Hugging Face: Decoding Strategies）。

先分清“解码概念”和“API 字段”。Temperature / top-p 是理解采样的基础，但并非每个模型都开放这些字段。例如当前 Claude Fable 5 / Mythos 5、Claude Opus 4.8 / 4.7 与 Claude Sonnet 5 会拒绝 temperature、top_p、top_k 的非默认值；这不等于字段名在所有情况下都被类别性拒绝。可移植做法是：能力档案未声明支持时就不发送这些字段，改用清晰提示词约束输出，并在需要推理深度控制时使用 output_config.effort（L20 再展开）。所以表里的数值只适用于确实支持该采样参数的 API，接入前先查模型文档。
任务建议 temperature为什么
抽取信息 / 分类 / 函数调用0 ~ 0.3要确定、可复现，不要惊喜
问答 / 摘要 / 改写0.3 ~ 0.7准确为主，略有灵活
创意写作 / 头脑风暴0.7 ~ 1.0+要多样性和新鲜感

最佳实践：先建立能力档案，再生成厂商请求字段

适用：同一任务会路由到多个模型或 provider，请求构造器可能发送 sampling / thinking / effort 控制。不适用：只调用一个固定后端，且请求字段已由其官方 SDK 类型和测试完全锁定；仍应在升级模型时重查。本卡只做一个决定：先读取模型能力档案，再决定发送哪些控制字段。

❌ 按厂商名猜字段
request = {
    "model": model,
    "temperature": 0.2,
    "top_p": 0.9,
    "effort": "high",
}

同一任务、输入与 build_request() 接口，却把一组控制无条件塞给所有 adapter；不支持字段可能报错，静默忽略则更难诊断。

✅ 按能力映射投影请求
profile = PROFILES[provider]
request = build_request(
    profile, model=model, prompt=prompt,
    controls=controls,
)

adapter 只投影能力档案允许的字段；fixture 可机械证明不支持字段没有越过边界。

为什么更优：先维护能力档案，再由 adapter 投影请求，动作上把“任务意图”与“厂商字段”分开；机制上让字段支持范围成为可测试数据；结果是兼容性、可移植性、可审计性和错误可诊断性提高。真实成本是要维护档案、升级 fixture，并在模型发布后重验；档案陈旧也会错误删字段。若只接一个后端，可直接使用其强类型请求对象；当第二个 provider 出现或模型支持范围分叉时，切换到显式能力档案。当前官方文档的边界是：Fable 5 / Mythos 5、Opus 4.8 / 4.7 与 Sonnet 5 拒绝 sampling 控制的非默认值，不应夸大成字段在所有情况下都类别性拒绝（Anthropic · Adaptive thinking）。

动手自检（纯标准库、离线、静默通过）：
PROFILES = {
    "fictional_a": {
        "temperature": True,
        "top_p": True,
        "effort": False,
    },
    "fictional_b": {
        "temperature": False,
        "top_p": False,
        "effort": True,
    },
}


def build_request(profile, *, model, prompt, controls):
    request = {"model": model, "prompt": prompt}
    for field, value in controls.items():
        if profile.get(field, False):
            request[field] = value
    return request


TASK = "classify"
PROMPT = "Classify: museum copy needs review"
CONTROLS = {"temperature": 0.2, "top_p": 0.9, "effort": "high"}

fixtures = {
    name: build_request(
        profile,
        model=f"{name}-model",
        prompt=PROMPT,
        controls=CONTROLS,
    )
    for name, profile in PROFILES.items()
}

assert fixtures["fictional_a"] == {
    "model": "fictional_a-model",
    "prompt": PROMPT,
    "temperature": 0.2,
    "top_p": 0.9,
}
assert fixtures["fictional_b"] == {
    "model": "fictional_b-model",
    "prompt": PROMPT,
    "effort": "high",
}
assert all(request["prompt"] == PROMPT for request in fixtures.values())
assert "effort" not in fixtures["fictional_a"]
assert "temperature" not in fixtures["fictional_b"]
assert "top_p" not in fixtures["fictional_b"]

结果诊断：无输出且退出码为 0 即通过。若 fictional_b 含 temperature/top_p，说明 adapter 没有删除不支持字段；若两个请求的 prompt 不同，比较已不再是同任务 / 同输入 / 同接口；若档案字段名与生成字段不一致，断言会直接暴露映射漂移。

边界：能力档案描述“这个模型 / 端点接受什么”，不证明某个控制会提高业务质量；效果仍要交给评测。

Q 要让 Agent 抽取字段稳定，第一步应该？
第一步是确认目标模型接受哪些控制。支持 sampling 参数时，可从低 temperature 开始评测，并配结构化输出与运行时校验；模型拒绝这些字段的非默认值时，就不要发送，改用该模型支持的提示约束、结构化输出、校验或 effort。低温提高一致性，也不保证事实正确或逐字节复现。

4. Top-P：只从"最可能的一小撮"里采样

Top-P（核采样 / nucleus sampling）换一个思路裁剪候选：把 Token 按概率从高到低累加，只保留累计概率达到 P 的那一小撮，其余全部丢弃，再在这撮里采样。

top_p = 0.9 的含义：
按概率排序累加，取到累计 90% 为止的那批 Token，
剩下 10% 概率的"长尾低概率词"直接排除。

它的好处是自适应：模型很确定时（一个 Token 就占 95%），候选集自动变小；模型不确定时（概率分散），候选集自动变大。这比固定取前 K 个（top-k）更聪明——出处见 Hugging Face: How to generate text。

temperature vs top_p 怎么配？如果目标 API 同时支持两者，通常只重点调一个、另一个留默认，便于归因；同时把两个都往极端调，行为会很难预测。常见做法是固定 top_p=1 只调 temperature，或反之。若能力档案没有声明支持，就不要硬塞参数；对会拒绝非默认 sampling 值的新 Claude 模型，portable adapter 应直接省略这些字段，改用该厂商支持的控制方式。

⚠️ 陷阱题："temperature 和 top_p 有什么区别？" — temperature 是缩放整个分布的形状（改变每个 Token 被选中的相对概率）；top_p 是裁剪候选集（先砍掉长尾，再采样）。一个改"概率"，一个改"能选谁"。

5. 两个惩罚项：治重复啰嗦

一些 API（例如部分 OpenAI 风格接口）提供重复惩罚字段，通过调低已出现 Token 的 logit 来抑制车轱辘话（参考 Prompt Engineering Guide: LLM Settings）：

  • frequency_penalty（频率惩罚）：按 Token 出现的次数成比例惩罚——出现越多，越难再出现。治"同一个词反复刷屏"。
  • presence_penalty（存在惩罚）：只要 Token 出现过一次就施加固定惩罚，与次数无关。鼓励模型换新话题、引入新词。

在提供这两个字段的接口里，常见范围是 -2.0 ~ 2.0、默认 0。区别一句话：frequency 看“出现几次”（按量），presence 看“有没有出现”（按 0/1）。但它们不是通用 LLM 参数；目标模型没有这些字段时，应通过提示词、输出约束或厂商提供的其他机制控制重复，不能照搬请求体。

Q frequency_penalty 与 presence_penalty 的核心区别是？
两者都惩罚已出现的 Token，区别在缩放方式：frequency_penalty 按出现次数成比例（越频繁越重罚），presence_penalty 只看出现过没有（0/1 固定罚）。前者治刷屏式重复，后者鼓励引入新内容。

6. 反直觉真相：temperature=0 ≠ 完全可复现

很多人以为"temperature 设 0，模型就每次输出一模一样"。不对。 temperature=0 让模型总是挑最高概率的 Token（贪心解码），逻辑上确实该确定——但实践中仍可能有细微差异。原因：

  • 浮点数不满足结合律：(a+b)+c ≠ a+(b+c)。GPU 上并行归约的加法顺序会变，导致 logits 有极小抖动，偶尔翻转"谁是第一名"。
  • 批处理 / 硬件差异：同一请求在不同 batch 大小、不同 GPU、不同推理引擎版本下，数值路径不同。

这不是玄学，是被 Thinking Machines Lab 和 vLLM 维护者系统分析过的工程现实。面试加分点：在支持采样控制的 API 上，低温 / 贪心解码配合固定 seed（若厂商提供）只能提高一致性，不能保证逐字节相同。Seed 也是厂商能力：部分 OpenAI 接口提供，Anthropic Messages API 当前没有对应请求字段；当前 Claude 模型若不接受 temperature，也不能照搬“temperature=0”方案。

这条对 Agent 工程很实际：不要把关键逻辑建立在"LLM 输出逐字节稳定"的假设上。要稳，就用结构化输出 + 校验（后面 Pydantic 那套），而不是指望采样完全确定。

最佳实践：把可复现性定义成可审计运行契约，而不是逐字节相同

适用：需要比较回归、重放事故或解释某次模型输出，且模型服务仍可能非确定。不适用：结果由纯确定性函数产生并已有内容哈希保证。本卡只做一个决定：冻结模型、prompt、tools、controls、fixture 与 evaluator，并为这份 run spec 生成指纹；不要求输出字节完全相同。

❌ 以文本完全相同为复现
first = run(task)
second = run(task)
assert first == second

同一任务、输入与 run(spec) 接口，却把非确定生成误当成确定函数；一次措辞变化就造成伪回归。

✅ 固定运行规格与评估门
fingerprint = run_spec_fingerprint(spec)
result = run(spec)
assert evaluate(result, fixture) == "pass"

规格指纹回答“运行条件是否相同”，evaluator 回答“质量契约是否仍满足”。

为什么更优：冻结完整 run spec 并稳定序列化，动作上记录真正影响生成的输入；机制上用指纹识别配置漂移，再用 evaluator 评估语义质量；结果是回归判断更正确、重放更可审计、故障更易诊断。真实成本是保存 fixture、工具 schema 与 evaluator 版本，且指纹只能证明规格一致，不能证明服务端实现或输出一致；evaluator 也可能漏检。若下游协议要求逐字节稳定，应把该步骤换成模板、规则引擎或其他确定性组件；当业务只关心结构 / 含义时，使用规格指纹 + 质量门。

动手自检（纯标准库、离线、静默通过）：
import hashlib
import json


def fingerprint(spec):
    payload = json.dumps(
        spec,
        ensure_ascii=False,
        sort_keys=True,
        separators=(",", ":"),
    ).encode("utf-8")
    return hashlib.sha256(payload).hexdigest()


def evaluator(output, fixture):
    return (
        output["category"] == fixture["category"]
        and set(fixture["required_terms"]) <= set(output["terms"])
    )


SPEC = {
    "model": "fictional-model-v3",
    "prompt": {"version": "museum-label-v2", "text": "Classify copy."},
    "tools": [{"name": "lookup_catalog", "schema_version": 1}],
    "controls": {"effort": "low"},
    "fixture": {"id": "case-17", "text": "Bronze vessel, verified."},
    "evaluator": {"version": "label-gate-v1"},
}
FIXTURE = {"category": "verified", "required_terms": ["bronze"]}

same_spec_different_order = dict(reversed(list(SPEC.items())))
assert fingerprint(SPEC) == fingerprint(same_spec_different_order)

changed_values = {
    "model": "fictional-model-v4",
    "prompt": {"version": "museum-label-v3", "text": "Classify copy."},
    "tools": [{"name": "lookup_catalog", "schema_version": 2}],
    "controls": {"effort": "medium"},
    "fixture": {"id": "case-18", "text": "Bronze vessel, verified."},
    "evaluator": {"version": "label-gate-v2"},
}
for field in SPEC:
    omitted = {key: value for key, value in SPEC.items() if key != field}
    changed = {**SPEC, field: changed_values[field]}
    assert fingerprint(SPEC) != fingerprint(omitted), field
    assert fingerprint(SPEC) != fingerprint(changed), field

outputs = [
    {"text": "Verified bronze object.", "category": "verified", "terms": ["bronze"]},
    {"text": "Bronze object; catalog evidence is verified.", "category": "verified", "terms": ["bronze", "catalog"]},
]
assert outputs[0]["text"] != outputs[1]["text"]
assert all(evaluator(output, FIXTURE) for output in outputs)

结果诊断：无输出且退出码为 0 即通过。相同规格因键顺序得到不同指纹，说明序列化不稳定；模型、prompt、tools、controls、fixture 或 evaluator 改变却不改指纹，说明 run spec 未覆盖审计边界；两份合格措辞被判失败，说明仍在要求字节复现而非质量复现。

边界：run-spec 指纹是配置身份证，不是输出真值证明，也不等于 provider 服务端版本可被完全冻结。

7. 实战：先问“支持什么”，再谈怎么调

🧪 Agent 场景练习：为抽取、创作和代码任务选择控制方式（先自己判断）

题目：Provider A 支持 temperature / top_p；当前 Claude Opus 4.8 会拒绝这些采样字段的非默认值，因此 portable adapter 不发送它们，而使用清晰提示词与 output_config.effort。分别为“发票字段抽取”“广告创意”“复杂代码审查”选择控制方式。

参考答案：

  • 发票抽取：Provider A 可用低 temperature 并配结构化输出；Claude Opus 4.8 不传采样参数，改用严格输出格式、明确字段规则和运行时校验。稳定性主要靠结构化约束，不靠“温度必然可复现”。
  • 广告创意：Provider A 可提高 temperature 或调 top-p（只重点调一个）；Claude 则在提示词里明确“给出多种差异明显的方向”，而不是发送不支持的字段。
  • 复杂代码审查：重点不是提高随机性。两类 provider 都应先明确审查标准；Claude 可在 L20 学到用较高 effort 增加分析深度，再通过测试验证结论。

判断顺序：任务需要什么行为 → 目标模型支持什么接口 → 选择对应控制手段。不要先背一组参数，再强塞给所有模型。

🎯 速查卡：生成参数

【本质】LLM = 下一个 Token 概率预测器；生成 = 反复"预测→采样→接上"

【temperature 温度】缩放分布形状
  ├── →0  分布变尖，几乎总选最可能 → 稳定/抽取/函数调用
  └── →1+ 分布变平，长尾也可能中选 → 创意/多样

【top_p 核采样】裁剪候选集
  └── 按概率累加取到 P%，砍掉长尾再采样；自适应候选大小
  ★ temperature 与 top_p 只重点调一个，另一个留默认

【frequency_penalty】按“出现次数”罚 → 治刷屏重复
【presence_penalty】 按“出现有无”罚 → 鼓励换新话题
  └── 都是厂商可选字段，不是每个模型都有

【先看接口再调参】概念通用 ≠ 字段通用
  ├── 支持 sampling 参数的 API：按任务调 temperature / top_p
  └── 当前新 Claude：不传未获能力档案支持的采样字段
      用提示词、结构化输出、校验；推理深度见 L20 effort

【反直觉】即使支持 temperature=0，也不保证 100% 可复现
  └── 浮点非结合 + 硬件/批次差异；seed 也由厂商决定
      要稳 → 结构化输出 + 校验，别赌采样确定

本课最佳实践验收：科学摘要分诊双 Provider A/B 实验清单

先独立完成：为科学摘要分诊发布一份双 provider A/B 实验清单。每个实验臂都要把统一控制意图编译为该 provider 的原生请求结构，并让每条观察记录携带对应的 manifest ID；这里验收的是可追溯实验，而不是逐字复现输出。

操作清单

  1. 为两个全新虚构 provider 声明不同能力映射，并编译各自的原生控制字段。
  2. 把 endpoint、prompt、tools、controls、abstract batch、rubric 六类受控条件写入每个实验臂的 manifest。
  3. 生成稳定 manifest ID，并把 A/B 输出逐条关联到各自 ID。
  4. 证明 manifest 键顺序打乱不改 ID，而六类受控条件中任一类变化都会生成新 ID。
  5. 在评分前拒绝 manifest ID 不匹配的观察；再用科学摘要分诊 rubric 接受两份字节不同但质量等价的输出。
通过标准
  • Nova 臂只出现 sampling 原生控制，Cedar 臂只出现 reasoning effort；未支持的控制没有越界。
  • 两个 manifest 都完整覆盖六类受控条件；重排键保持 ID，逐类替换条件均改变 ID。
  • 每条观察都能按 provider 连接到正确 manifest；伪造 ID 的观察在 rubric 调用前被拒绝。
  • 两份观察的规范 JSON 字节不同，但都满足目标摘要、分诊结论、证据片段与风险标记 rubric。
  • 程序离线、纯标准库、确定性运行；标准输出只有最终标记。

import hashlib
import json

CONTROLLED_CATEGORIES = (
    "endpoint",
    "prompt",
    "tools",
    "controls",
    "abstract_batch",
    "rubric",
)
PROVIDER_SPECS = {
    "nova_bio": {
        "model": "nova-triage-3",
        "control_map": {
            "temperature": ("sampling", "temperature"),
            "top_p": ("sampling", "top_p"),
        },
    },
    "cedar_compute": {
        "model": "cedar-review-6",
        "control_map": {
            "effort": ("reasoning", "effort"),
        },
    },
}


def stable_bytes(value):
    return json.dumps(
        value,
        ensure_ascii=False,
        sort_keys=True,
        separators=(",", ":"),
    ).encode("utf-8")


def compile_native_controls(provider, intended):
    native = {}
    for intent_name, path in PROVIDER_SPECS[provider]["control_map"].items():
        if intent_name in intended:
            section, field = path
            native.setdefault(section, {})[field] = intended[intent_name]
    return native


def make_manifest(provider, *, prompt, tools, intended, abstract_batch, rubric):
    spec = PROVIDER_SPECS[provider]
    return {
        "endpoint": {"provider": provider, "model": spec["model"]},
        "prompt": prompt,
        "tools": tools,
        "controls": compile_native_controls(provider, intended),
        "abstract_batch": abstract_batch,
        "rubric": rubric,
    }


def manifest_id(manifest):
    return "manifest-" + hashlib.sha256(stable_bytes(manifest)).hexdigest()[:16]


score_log = []


def score_observation(observation, manifest):
    expected_id = manifest_id(manifest)
    if observation["manifest_id"] != expected_id:
        raise ValueError("manifest ID mismatch")
    score_log.append((expected_id, observation["abstract_id"]))
    rubric = manifest["rubric"]
    return (
        observation["abstract_id"] == rubric["target_abstract_id"]
        and observation["decision"] in rubric["allowed_decisions"]
        and set(rubric["required_evidence"]) <= set(observation["evidence"])
        and not (set(rubric["forbidden_flags"]) & set(observation["flags"]))
    )


PROMPT = {
    "version": "abstract-triage-v2",
    "text": "Prioritize abstracts with randomized human outcome evidence.",
}
TOOLS = [{"name": "extract_study_signals", "schema_version": 3}]
INTENDED_CONTROLS = {"temperature": 0.2, "top_p": 0.85, "effort": "medium"}
ABSTRACT_BATCH = [
    {
        "abstract_id": "ABS-41",
        "text": "Randomized trial; human participants; outcomes measured at 30 days.",
    }
]
RUBRIC = {
    "version": "triage-rubric-v1",
    "target_abstract_id": "ABS-41",
    "allowed_decisions": ["priority_review"],
    "required_evidence": ["randomized", "30-day"],
    "forbidden_flags": ["animal-only", "no-outcome"],
}

manifests = {
    provider: make_manifest(
        provider,
        prompt=PROMPT,
        tools=TOOLS,
        intended=INTENDED_CONTROLS,
        abstract_batch=ABSTRACT_BATCH,
        rubric=RUBRIC,
    )
    for provider in PROVIDER_SPECS
}
manifest_ids = {provider: manifest_id(manifest) for provider, manifest in manifests.items()}

assert manifests["nova_bio"]["controls"] == {
    "sampling": {"temperature": 0.2, "top_p": 0.85}
}
assert manifests["cedar_compute"]["controls"] == {
    "reasoning": {"effort": "medium"}
}
assert all(set(manifest) == set(CONTROLLED_CATEGORIES) for manifest in manifests.values())
assert manifest_ids["nova_bio"] != manifest_ids["cedar_compute"]

for provider, manifest in manifests.items():
    shuffled = dict(reversed(list(manifest.items())))
    assert manifest_id(shuffled) == manifest_ids[provider]

changed_values = {
    "endpoint": {"provider": "nova_bio", "model": "nova-triage-4"},
    "prompt": {**PROMPT, "version": "abstract-triage-v3"},
    "tools": [{"name": "extract_study_signals", "schema_version": 4}],
    "controls": {"sampling": {"temperature": 0.1, "top_p": 0.85}},
    "abstract_batch": [{**ABSTRACT_BATCH[0], "abstract_id": "ABS-42"}],
    "rubric": {**RUBRIC, "version": "triage-rubric-v2"},
}
assert set(changed_values) == set(CONTROLLED_CATEGORIES)
base_manifest = manifests["nova_bio"]
for category in CONTROLLED_CATEGORIES:
    changed = {**base_manifest, category: changed_values[category]}
    assert manifest_id(changed) != manifest_ids["nova_bio"], category

observations = [
    {
        "provider": "nova_bio",
        "manifest_id": manifest_ids["nova_bio"],
        "abstract_id": "ABS-41",
        "decision": "priority_review",
        "evidence": ["randomized", "30-day"],
        "flags": [],
        "summary": "Randomized human trial with a 30-day endpoint.",
    },
    {
        "provider": "cedar_compute",
        "manifest_id": manifest_ids["cedar_compute"],
        "abstract_id": "ABS-41",
        "decision": "priority_review",
        "evidence": ["30-day", "randomized"],
        "flags": [],
        "summary": "Human outcomes are reported after random assignment.",
    },
]
assert stable_bytes(observations[0]) != stable_bytes(observations[1])
assert all(
    observation["manifest_id"] == manifest_ids[observation["provider"]]
    for observation in observations
)
assert all(
    score_observation(observation, manifests[observation["provider"]])
    for observation in observations
)

mismatched = {**observations[0], "manifest_id": manifest_ids["cedar_compute"]}
score_calls_before_rejection = len(score_log)
try:
    score_observation(mismatched, manifests["nova_bio"])
    raise AssertionError("mismatched observation reached scoring")
except ValueError as error:
    assert str(error) == "manifest ID mismatch"
assert len(score_log) == score_calls_before_rejection

结果诊断：任一请求同时出现 sampling 与 reasoning 控制，说明能力编译越界；manifest 缺少六类条件、重排后 ID 改变或某类条件变化后 ID 不变，说明实验身份不可审计；观察携带错误 ID 却进入 score_log，说明连接校验放在评分之后；两份字节不同但证据等价的观察不能同时通过，说明 rubric 又退化成了文本复现检查。

总结

  • LLM 的本质是基于概率的下一个 Token 预测，生成就是"预测→采样→接上"的循环
  • 注意力让模型按相关性给上文各 Token 加权，捕捉长距离依赖
  • temperature 缩放分布形状，top_p 裁剪候选集；它们是通用解码概念，但不是每个 API 都开放的字段
  • frequency_penalty 按次数罚、presence_penalty 按有无罚；同样要先确认目标厂商支持
  • 控制输出的顺序是：明确任务行为 → 查模型能力 → 选采样参数、提示约束或结构化校验
  • 即便 API 支持 temperature=0 / seed，也不能保证逐字节复现；部分新 Claude 模型会拒绝 sampling 字段的非默认值
