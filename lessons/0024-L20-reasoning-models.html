推理能力与 Adaptive Thinking

让模型按任务决定是否深入推理，再用 effort 调节质量、延迟与成本

💡 为什么这课重要？

你现在知道 LLM 在预测下一个 Token。面对复杂任务，当前模型可以在最终回答前投入额外计算与推理，但工程上要分清三件事：模型是否擅长推理、请求是否启用 adaptive thinking、以及用 effort 调节投入程度。它们相关，却不是同一个概念。

作为 Agent 开发者，这直接影响质量、延迟与账单。简单任务可能不需要深度推理；复杂任务也不能只凭“推理模型”标签就保证正确。这一课教你按场景实测，并使用当前 Claude 的 Adaptive Thinking + effort，而不是把已经退出新模型主线的固定 budget_tokens 当成通用旋钮。它是后面 L23 · Model Routing 的直接前置。

学习目标

完成本课后，你将能够：

  • 区分推理能力、Adaptive Thinking 与 effort，不再把它们混成一个“推理模型开关”
  • 用当前 Claude API 开启 thinking={"type":"adaptive"}，并在 output_config 中设置 effort
  • 知道 budget_tokens 只属于旧模型兼容路径，新模型不能照搬
  • 按任务质量、延迟、成本与实测结果决定推理投入，并连回 Model Routing
  • 解释 thinking 的展示、计费与 max_tokens 边界，以及为什么更高 effort 不保证总是更好

1. 先拆开三个容易混淆的概念

“推理模型”常被当成一个万能标签，但写 API 时至少要拆成三层：

概念它回答什么问题工程含义
推理能力这个模型是否擅长多步分析、规划和自检？是模型能力，需要用你的评测集验证
Adaptive Thinking本次请求是否允许模型按任务决定要不要深入思考？当前 Claude 的 thinking 模式
effort希望模型在质量、延迟和 Token 之间偏向哪一侧？请求级控制，放在 output_config

可以继续用“草稿纸”建立直觉：复杂问题往往受益于额外推理，但 API 返回的是thinking block 的省略或摘要，不是模型的原始私密思维链。模型也可能判断简单问题无需 thinking，或者在高 effort 下想得过多。

请求 ──▶ 模型判断任务难度 ──┬─ 直接回答
                            └─ 进行额外 thinking ──▶ 最终回答

thinking 是否发生：由模型和任务共同决定
投入程度：受 effort 影响，但更高不等于每次都更准

所以工程结论不是“推理模型永远更聪明”，而是：困难任务可能值得更高推理投入；简单任务应测量它是否只增加延迟和成本。

Q 关于“推理能力、Adaptive Thinking、effort”，哪项最准确？
推理能力属于模型能力，Adaptive Thinking决定请求是否允许模型按需思考，effort调节质量、延迟和 Token 取舍。三者相关但不等同；模型可跳过简单题的 thinking，更高 effort 也必须用实测验证收益。

2. 当前 Claude API：Adaptive Thinking + effort

当前 Claude 新代码使用官方 Anthropic SDK，把 thinking 设为 adaptive，再把 effort 放进 output_config。下面示例使用当前 Opus 模型；它会拒绝 L17 sampling 参数的非默认值，因此 portable 请求直接省略 temperature / top-p：

import anthropic

client = anthropic.Anthropic()
response = client.messages.create(
    model="claude-opus-4-8",
    max_tokens=16_000,
    thinking={"type": "adaptive", "display": "summarized"},
    output_config={"effort": "high"},
    messages=[
        {"role": "user", "content": "分析这个多约束排期问题，并给出可验证方案。"}
    ],
)

for block in response.content:
    if block.type == "thinking":
        print("思考摘要：", block.thinking)
    elif block.type == "text":
        print("最终回答：", block.text)

如何区分四个字段：

  • thinking={"type":"adaptive"}：允许模型按任务决定是否思考以及思考多少。
  • output_config.effort：对整体 Token 投入的软性行为指导，不是严格预算。API 档位全集是 low / medium / high / xhigh / max，但支持范围随模型而定：例如 xhigh 只在 Fable 5 / Mythos 5、Opus 4.8 / 4.7 与 Sonnet 5 可用；high 是 API 默认。更高可能提高难题质量，也可能增加延迟、Token 或过度思考。
  • display="summarized"：在默认 omitted 的新模型上，必须显式设置它才能收到可读思考摘要；omitted 会省略可读 thinking 文本，并可改善流式响应的首个正文 Token 延迟，但不会关闭思考，也不会减少已生成 thinking 的计费。
  • max_tokens：本次响应的硬输出上限，thinking 和最终文本都要留出空间；撞上它会以 max_tokens 停止。

默认值与旧写法边界：adaptive 的默认行为按模型不同：Fable 5 / Mythos 5 始终开启；Sonnet 5 默认开启；Opus 4.8 / 4.7 与 Opus / Sonnet 4.6 必须显式设置 thinking={"type":"adaptive"} 才会开启。thinking={"type":"enabled","budget_tokens":...} 是手动思考预算：Claude Opus 4.8 / 4.7、Claude Sonnet 5、Claude Fable 5 / Mythos 5 会拒绝它；Opus / Sonnet 4.6 仍接受但已弃用。已退役的 Mythos Preview 曾接受手动模式，但不能用于新请求；迁移时改用 Mythos 5，并以当前官方迁移文档为准。初学者的新代码不要再从固定预算起步，应使用 adaptive thinking + effort。

官方资料：Anthropic · Adaptive Thinking 与 Anthropic · Effort。

一句话记住当前写法：adaptive 决定“按需想不想”，effort 调节“愿意投入多少”，display 只控制“给不给你看摘要”，max_tokens 才是硬上限。

最佳实践：选择满足工作负载质量门的最低 effort

适用：目标模型支持多个 effort 档位，且工作负载有固定质量测试、延迟和 Token / 成本记录。不适用：目标模型不支持 effort，或任务尚无可判定质量门；先补评测。本卡只做一个决定：从固定 trials 中选择通过质量门的最低 effort，而不是默认追求最高档。

❌ 永远选最高 effort
choice = "max"
result = run(task, effort=choice)

同一任务、输入与 choose_effort() 接口，却忽略较低档是否已过门，也没有把 latency / token cost 纳入决策。

✅ 固定试验后选最低过门档
choice = choose_effort(
    trials,
    min_quality=0.90,
    max_latency_ms=900,
)

先过滤质量与延迟门，再按 effort 顺序选择最低档；没有档位过门就明确失败，不静默降质。

为什么更优：在固定 workload 上记录每档质量、延迟与输出 Token，动作上把“感觉更聪明”换成可比较试验；机制上以质量门优先、再选最低可行 effort；结果提高成本效率、延迟可预测性、路由可审计性，并减少无收益 overthinking。真实成本是要维护代表性 eval、定期重跑，并承担离线 trial 与线上流量分布不一致的风险；effort 本身只是软指导，不是 token 硬上限。若所有档都不过门，应升级模型、改善工具 / prompt 或转人工；若任务价值极高且延迟不敏感，可把质量门提高并允许更高档。官方 API 值为 low/medium/high/xhigh/max，模型支持不同，默认 high；必须先查目标模型（Anthropic · Effort）。

动手自检（纯标准库、离线、静默通过）：
ORDER = ["low", "medium", "high", "xhigh", "max"]


def choose_effort(trials, *, min_quality, max_latency_ms):
    eligible = [
        trial for trial in trials
        if trial["quality"] >= min_quality
        and trial["latency_ms"] <= max_latency_ms
    ]
    if not eligible:
        raise ValueError("no effort level meets the workload gate")
    return min(eligible, key=lambda trial: ORDER.index(trial["effort"]))


TRIALS = [
    {"effort": "high", "quality": 0.95, "latency_ms": 820, "output_tokens": 330},
    {"effort": "low", "quality": 0.93, "latency_ms": 1200, "output_tokens": 140},
    {"effort": "xhigh", "quality": 0.96, "latency_ms": 1250, "output_tokens": 510},
    {"effort": "medium", "quality": 0.92, "latency_ms": 520, "output_tokens": 210},
]

quality_gate = 0.90
latency_gate = 900
choice = choose_effort(
    TRIALS,
    min_quality=quality_gate,
    max_latency_ms=latency_gate,
)
eligible = [
    trial for trial in TRIALS
    if trial["quality"] >= quality_gate
    and trial["latency_ms"] <= latency_gate
]
assert eligible[0]["effort"] == "high"  # 输入故意无序，不能直接取 eligible[0]
assert choice == {
    "effort": "medium",
    "quality": 0.92,
    "latency_ms": 520,
    "output_tokens": 210,
}
assert ORDER.index(choice["effort"]) == min(
    ORDER.index(trial["effort"]) for trial in eligible
)
assert choice["latency_ms"] <= latency_gate
assert choice["output_tokens"] == 210
assert TRIALS[1]["quality"] >= quality_gate
assert TRIALS[1]["latency_ms"] > latency_gate  # 删除延迟门会错误选 low

try:
    choose_effort(TRIALS, min_quality=0.99, max_latency_ms=400)
except ValueError as error:
    assert str(error) == "no effort level meets the workload gate"
else:
    raise AssertionError("an unmet quality gate must not silently choose a level")

结果诊断：无输出且退出码为 0 即通过。选择 high / xhigh 表示没有取最低过门档；选择 low 表示质量门未生效；选择 xhigh 且忽略 900ms 表示延迟门失效；无档过门却返回结果表示系统在静默降质。

边界：最低 effort 指 API 档位顺序中的最低可行值，不代表最低美元价格；模型单价、重试率与失败成本仍需在完整路由评测中计算。

3. 何时提高推理投入：先分类，再实测

不要只看模型名称。先按任务复杂度做初筛，再用自己的评测集比较质量、延迟和成本：

  • 任务简单、规则明确、速度优先 → 从较低推理投入开始。例如抽取、分类、格式转换；可选轻量模型或较低 effort。
  • 任务困难、多步、多约束、错误代价高 → 测试更强模型或更高 effort。例如复杂调试、规划和需要交叉核对的分析。
任务类型起始策略还要验证什么
发票字段抽取轻量模型 / 低 effort结构化输出准确率与延迟
邮件分类轻量模型 / 低 effort边界样本与类别混淆
JSON 格式转换低推理投入Schema 校验是否全部通过
多步数学题较高 effort + 计算工具不能只信推理文本，要核对结果
复杂代码调试强模型 / 较高 effort真实测试是否复现并通过
多约束规划较高推理投入是否遗漏约束、方案是否可执行
长合同风险分析强模型 + 检索/引用证据覆盖、漏检率与人工复核

Agent 视角：规划常比格式化工具结果更需要推理，但这只是起始假设。成熟系统会为不同步骤设置候选模型 / effort，用业务评测决定路由，而不是写死“规划一定用某类模型”。

Q 下面哪种任务最值得先测试较高推理投入？
隐蔽 bug 调试需要追踪多个假设、理解上下文并用测试核验，通常值得测试强模型或较高 effort。其余任务规则更明确，可从较低推理投入开始，但最终仍应以自建评测的质量、延迟与成本决定。

4. 成本 / 延迟权衡

额外 thinking 会消耗输出 Token 和生成时间。在 Fable 5 / Mythos 5、Sonnet 5、Opus 4.8 / 4.7 等新模型上，display 默认是 omitted；要收到可读摘要必须显式设为 summarized。省略 thinking 文本可改善流式响应的首个正文 Token 延迟，但不会减少已生成 thinking 的计费。你看到摘要、空 thinking 文本或只看到最终回答，都不代表后台没有产生可计费用量；应以响应的 usage 和账单为准。

较低推理投入：输入 ──▶ 回答             ← 通常更快、更省
较高推理投入：输入 ──▶ thinking ──▶ 回答 ← 可能更准，也可能更慢/更贵

显示摘要或省略 thinking 文本，只影响可见内容，不自动降低计费

路由要避免两个方向的错误：

  • 简单任务投入过高：可能只增加延迟和成本，甚至出现 overthinking。
  • 困难任务投入不足：可能漏约束、返工或触发错误工具，最终总成本反而更高。

因此 Model Routing 不是“便宜模型永远做 A、贵模型永远做 B”，而是根据任务特征选择候选，再用质量、延迟、Token 和失败成本实测。系统化方法见 L23。

Q 关于 Claude thinking 的展示与成本，正确的是？
display 控制是否返回可读思考摘要，不是计费开关。完整生成的 thinking 仍可能计入用量；更高 effort 也只是改变投入倾向，必须用实际 usage、延迟和任务质量评估收益。

5. 提示词差异：别替它安排思考步骤

对支持 Adaptive Thinking 的当前模型，提示词重点不是要求它暴露或模仿一条固定思维链，而是把目标、输入、约束和验收标准讲清楚。

  • 先给可验证目标：“找出导致失败的根因，并给出能让测试通过的最小修改”。
  • 再给硬约束：允许改哪些文件、哪些行为不能改变、输出需要哪些证据。
  • 必要时提供过程脚手架：如果你的评测证明分阶段输出能提高结果，可以要求“先列假设，再用测试排除”；不要仅因它被叫作推理模型就删除所有步骤，也不要机械堆叠“think step by step”。
较弱的写法：
  “请深入思考，一步一步想，务必认真。”

可验证的写法：
  “定位这三个失败测试的共同根因。
   约束：只改 parser.py；不得改变公开函数签名。
   完成标准：三个测试通过，并解释哪个输入触发了原缺陷。”

核心变化：从“命令模型怎么想”转向“明确它要完成什么、不能破坏什么、如何证明完成”。这对不同模型都适用。

⚠️ 常见误区：把“请深入思考”当成质量保证。真正有用的是可验证目标 + 明确约束 + 外部检查；是否增加过程脚手架，应通过你的评测验证，而不是按“标准/推理”标签一刀切。

6. Agent 里怎么混合使用

把前五节合起来，得到的是一个分步骤测量并路由的框架，而不是“Agent 必须混用两个标签模型”的教条：

  • 规划 / 复杂决策：通常值得把强模型或较高 effort 纳入候选，因为漏约束的失败成本高。
  • 格式化 / 简单分类：通常可从轻量模型或较低 effort 开始，因为规则明确、调用频繁。
  • 工具调用：难度取决于语义。填固定参数可能很简单，选择工具、解释失败或处理冲突结果可能仍需较强推理。

对每一步记录成功率、延迟、Token 和重试次数，才能决定是否值得分流。怎么工程化这套按任务特征路由并核算收益，是 L23 · Model Routing 的主题。

面试高频：「推理能力与 Adaptive Thinking 怎么用？」
回答要分层：模型本身有不同的推理能力；当前 Claude 可用 thinking={"type":"adaptive"} 允许按需思考，用 output_config.effort 调节投入。thinking 会影响 Token 与延迟，display 只控制摘要可见性。简单任务从较低投入开始，困难任务测试强模型 / 较高 effort，最终以业务评测和外部验证决定路由。

Agent 场景练习：下面几个任务，该从怎样的模型 / effort 候选开始？还要测什么才能拍板？先自己判断，再展开对照。

① 从一张发票里抽取"金额"字段 —— 点开看答案

从轻量模型 / 低 effort 开始。用结构化输出和字段校验测准确率；如果复杂票据漏字段，再升级候选。不能只凭“单步”就跳过真实样本。

② 解一道多步数学题并给出验证过程 —— 点开看答案

把强模型 / 较高 effort 纳入候选，并调用计算工具验证。最终看正确率、延迟和工具核验结果；思考文本本身不是答案正确的证明。

③ 总结一份 50 页合同的风险点 —— 点开看答案

强模型 / 较高 effort + 检索和引用核验。长文档风险分析不仅需要推理，还要保证证据覆盖；测漏检率、引用准确率和人工复核成本。

④ 把用户输入分类成「投诉 / 咨询 / 表扬」 —— 点开看答案

从轻量模型 / 低 effort 开始。重点测边界样本的混淆率、吞吐和成本；若类别含义复杂或错误代价高，再升级候选。

⑤ 在预算、工期、人力三重约束下排一个可行的项目计划 —— 点开看答案

把强模型 / 较高 effort 纳入候选。用约束满足率和计划可执行性评测，而不是只看回答是否写得详细；高 effort 若只是更啰嗦而没减少漏约束，就不值得。

🎯 速查卡：推理能力与 Adaptive Thinking

  Adaptive Thinking = 本次请求允许模型按需思考

  困难多步 → 测强模型 / 较高 effort，并用工具核验

本课最佳实践验收：发票处理多阶段执行策略

任务目标

把无序业务 trials 转换为分阶段执行策略，证明每个阶段按自身质量与延迟门选择最低达标 effort，无可用档位时明确转人工。

操作清单

  1. 定义多个发票阶段各自的质量门、延迟门与 supported efforts。
  2. 为每个支持档位准备质量、延迟、输出 Token 固定 trial，并故意打乱顺序。
  3. 按阶段过滤门槛，再按 API effort 顺序选择最低过门档。
  4. 把阶段、档位、门槛和所选 trial 的 output_tokens 写进策略表。
  5. 对无档过门阶段返回显式 escalation row，不静默选最高档。

通过标准

  • 表头抽取与行项目核对使用不同门槛和 effort 子集。
  • trial 输入顺序不能决定选择结果；多个档过门时取最低可行档。
  • 每个 use row 保留所选 trial 的 output_tokens。
  • 异常复核阶段无档过门时包含原因、人工路由与全部 trial Token 证据。
  • 程序离线、纯标准库、确定性运行；标准输出只有最终标记。
课末近迁移参考程序（独立完成后展开，纯标准库）：
from dataclasses import dataclass

ORDER = ["low", "medium", "high", "xhigh", "max"]


@dataclass(frozen=True)
class Stage:
    stage_id: str
    min_quality: float
    max_latency_ms: int
    supported_efforts: tuple[str, ...]


@dataclass(frozen=True)
class Trial:
    stage_id: str
    effort: str
    quality: float
    latency_ms: int
    output_tokens: int


def build_execution_policy(stages, trials):
    table = []
    for stage in stages:
        if not set(stage.supported_efforts) <= set(ORDER):
            raise ValueError(f"unknown effort in stage {stage.stage_id}")

        stage_trials = [trial for trial in trials if trial.stage_id == stage.stage_id]
        by_effort = {trial.effort: trial for trial in stage_trials}
        if len(by_effort) != len(stage_trials):
            raise ValueError(f"duplicate effort trial in stage {stage.stage_id}")
        if set(by_effort) != set(stage.supported_efforts):
            raise ValueError(f"trial coverage mismatch in stage {stage.stage_id}")

        passing = [
            by_effort[effort] for effort in stage.supported_efforts
            if by_effort[effort].quality >= stage.min_quality
            and by_effort[effort].latency_ms <= stage.max_latency_ms
        ]
        base = {
            "stage_id": stage.stage_id,
            "quality_gate": stage.min_quality,
            "latency_gate_ms": stage.max_latency_ms,
            "supported_efforts": stage.supported_efforts,
        }
        if not passing:
            evidence = tuple(
                {
                    "effort": effort,
                    "quality": by_effort[effort].quality,
                    "latency_ms": by_effort[effort].latency_ms,
                    "output_tokens": by_effort[effort].output_tokens,
                }
                for effort in sorted(stage.supported_efforts, key=ORDER.index)
            )
            table.append({
                **base,
                "decision": "escalate",
                "escalation": {
                    "route": "manual-invoice-review",
                    "reason": "no-supported-effort-meets-stage-gate",
                },
                "trial_evidence": evidence,
            })
            continue

        chosen = min(passing, key=lambda trial: ORDER.index(trial.effort))
        table.append({
            **base,
            "decision": "use",
            "effort": chosen.effort,
            "quality": chosen.quality,
            "latency_ms": chosen.latency_ms,
            "output_tokens": chosen.output_tokens,
        })
    return table


STAGES = [
    Stage("header-intake", 0.950, 350, ("low", "medium")),
    Stage("line-item-match", 0.965, 850, ("medium", "high", "xhigh")),
    Stage("exception-review", 0.985, 1200, ("high", "xhigh", "max")),
]
TRIALS = [
    Trial("line-item-match", "high", 0.985, 720, 430),
    Trial("header-intake", "medium", 0.978, 330, 185),
    Trial("exception-review", "max", 0.992, 1500, 760),
    Trial("header-intake", "low", 0.955, 250, 96),
    Trial("line-item-match", "xhigh", 0.993, 980, 610),
    Trial("exception-review", "high", 0.972, 690, 360),
    Trial("line-item-match", "medium", 0.968, 620, 270),
    Trial("exception-review", "xhigh", 0.983, 930, 520),
]

policy = build_execution_policy(STAGES, TRIALS)
rows = {row["stage_id"]: row for row in policy}
assert [trial.effort for trial in TRIALS if trial.stage_id == "header-intake"] == [
    "medium", "low"
]
assert rows["header-intake"]["decision"] == "use"
assert rows["header-intake"]["effort"] == "low"
assert rows["header-intake"]["output_tokens"] == 96
assert rows["line-item-match"]["effort"] == "medium"
assert rows["line-item-match"]["quality_gate"] == 0.965
assert rows["line-item-match"]["latency_gate_ms"] == 850
assert rows["line-item-match"]["output_tokens"] == 270
assert rows["exception-review"]["decision"] == "escalate"
assert rows["exception-review"]["escalation"] == {
    "route": "manual-invoice-review",
    "reason": "no-supported-effort-meets-stage-gate",
}
assert [item["output_tokens"] for item in rows["exception-review"]["trial_evidence"]] == [
    360, 520, 760
]
assert len(policy) == len(STAGES)

总结

  • 要分清推理能力、Adaptive Thinking 与 effort：模型能力、思考模式和投入控制是三层
  • 当前 Claude 新代码使用 thinking={"type":"adaptive"} + output_config.effort；固定 budget_tokens 只属旧模型兼容知识
  • display 只控制思考摘要是否可见，不代表免计费；max_tokens 才是硬输出上限
  • 简单任务从轻量模型 / 低 effort 开始，困难任务测试强模型 / 较高 effort，并用外部工具核验
  • 提示词应明确目标、约束和验收证据；Agent 路由最终依据成功率、延迟、Token 与失败成本
