推理模型与 Extended Thinking

让模型"先在草稿纸上演算"再作答——你在用 Token 预算换推理深度

💡 为什么这课重要？

你现在知道 LLM 在"预测下一个 Token"。但有一类模型不再脱口而出——它们在给你答案之前，会先自己想一大段：列步骤、试错、自我检查，再吐出最终结论。这就是推理模型（reasoning models），以及 Claude 的 Extended Thinking 机制。

作为 Agent 开发者，这直接决定你两件生死攸关的事：准确率和账单。对简单任务上推理模型是 overkill——烧钱又拖慢；对高难多步任务用标准模型，准确率不够、Agent 会翻车。这一课教你什么时候用哪个，以及 Extended Thinking 里那个关键旋钮——thinking budget（思考预算）——到底在换什么。它是后面 L23 · Model Routing 的直接前置。

学习目标

完成本课后，你将能够：

  • 说清标准模型 vs 推理模型的根本区别：是否先生成一长串内部思考
  • 解释 Extended Thinking 怎么开启，以及 budget_tokens（思考预算）在换什么
  • 用一条决策规则判断某个任务该上标准还是推理模型
  • 说清推理模型更慢更贵的原因（reasoning token 也计费），并连回 Model Routing
  • 知道推理模型的提示词该怎么写（往往更简，不用手写 step-by-step）

1. 标准模型 vs 推理模型

两类模型的差别，用一个类比就懂：

  • 标准 LLM：像被点名就脱口而出——收到问题，直接开始生成答案 Token。
  • 推理模型：像先在草稿纸上演算——收到问题后，先生成一长串内部"思考"（long chain-of-thought，即 reasoning tokens / thinking tokens），在里面拆解步骤、尝试、自我纠错，然后才给出最终答案。

那串"思考"通常对用户隐藏或折叠（你看到的是简洁答案，草稿在幕后）。关键在于：这串思考要消耗额外 Token，也就是额外的时间和钱。换来的是——面对难题时，"先打草稿"往往比"脱口而出"答得更准。

标准模型：  问题 ──────────────────▶ 答案
                    (直接生成)

推理模型：  问题 ──▶ [一长串内部思考/草稿] ──▶ 答案
                    ↑ reasoning tokens
                    ↑ 通常对用户隐藏、且照常计费

注意：推理模型不是"更聪明的另一种架构"那么简单——它本质是让模型把算力多花在生成中间推理上，用更多 Token 去逼近正确答案。这也是为什么它更慢更贵（见第 4 节）。

Q 推理模型和标准 LLM 最根本的区别是？
推理模型在给出最终答案之前，会先生成一长串内部"思考"（long chain-of-thought / reasoning tokens），在其中拆步骤、试错、自查，再作答。这串思考通常对用户隐藏，但照常消耗 Token——所以它更慢更贵，而不是更便宜。它靠"把算力多花在中间推理上"来提升难题准确率。

2. Extended Thinking 是怎么工作的

以 Anthropic Claude 的 Extended Thinking 为例，看推理模型在 API 层面怎么开启。核心是给请求加一个 thinking 参数，并设一个 budget_tokens（思考预算）——告诉模型"这次你最多可以用这么多 Token 来打草稿"：

# 概念示意（以官方文档为准，字段/上限可能随版本变化）
resp = client.messages.create(
    model="<一个支持 extended thinking 的 Claude 模型>",
    max_tokens=8000,
    thinking={
        "type": "enabled",
        "budget_tokens": 4000   # ← 思考预算：给内部推理的 token 额度
    },
    messages=[{"role": "user", "content": "……你的难题……"}],
)
# 模型会先用这个预算做内部推理，再产出最终回答

要理解的核心概念就是 thinking budget（思考预算）：

  • 预算越大 → 能想得越深：模型有更多 Token 去展开步骤、尝试多条路径、自我检查，通常对难题更有利。
  • 预算越大 → 越慢、越贵：这些思考 Token 要花时间生成，而且照常计费。
  • 所以你实际上是在做一笔交易——用 Token 预算换推理深度。

细节以官方文档为准：Anthropic · Extended Thinking。注意：budget_tokens 有上限、且随模型/版本变化——不要硬记某个具体最大值，以官方文档为准。

一句话记住 Extended Thinking：开一个 thinking 开关 + 给一个 budget_tokens 预算，模型就会先"打草稿"再作答。预算是旋钮：调大＝想得更深但更慢更贵，调小＝更快更省但可能不够深。这就是"用 Token 换推理深度"。

3. 何时用哪个：一条决策规则

别凭感觉选。OpenAI 官方的 reasoning best practices 给了一条很干净的规则，可直接照抄：

  • 速度 + 成本优先，任务简单且定义明确 → 用标准模型。（抽字段、分类、改写、格式转换、简单问答……）
  • 准确 + 可靠优先，任务困难 / 多步推理 → 用推理模型。（数学、复杂编码、多约束决策、长文档分析……）

落到具体任务上：

任务类型推荐模型理由
从发票抽取金额字段标准模型定义明确、单步、要快要便宜
邮件/文本分类打标签标准模型模式清晰，无需多步推演
把 JSON 改写成另一种格式标准模型机械转换，脱口而出即可
解多步数学题并验证推理模型需要逐步推演 + 自我检查
调试一段有隐蔽 bug 的复杂代码推理模型需追踪多个约束、试多种假设
在多个约束下做规划/取舍决策推理模型多约束权衡，标准模型易漏条件
分析 50 页合同、找出风险点推理模型长文档、需综合多处、结论要可靠

Agent 视角：一个 Agent 的一次任务里，这两类调用往往同时存在——高层的规划（planning）该用推理模型，而每一步工具调用的解析/填参用标准模型更划算（下节细说）。

Q 下面哪种任务最适合用推理模型？
决策规则：困难 / 多步推理 → 推理模型；简单且定义明确 → 标准模型。多步数学题需要逐步推演加自我检查，正是推理模型的强项。抽字段、打标签、格式改写都是单步、定义明确的任务，用标准模型更快更省——上推理模型属于 overkill。（来源：OpenAI reasoning best practices）

4. 成本 / 延迟权衡

推理模型为什么更慢更贵？因为它要生成大量 reasoning token——而这些思考 Token 即便对你隐藏，也照常计入账单、照常占用生成时间。你为"更准的答案"付出的代价，就是更多 Token × 更长延迟。

标准模型：   输入 ──▶ [答案]              ← 输出 token 少，快、便宜
推理模型：   输入 ──▶ [长草稿] + [答案]   ← 草稿也是 output token，慢、贵

→ 结论：推理模型的"隐藏思考"不是免费的，它是你账单的一部分

对路由 / 成本的两条启示（正好是两个反向错误）：

  • 别对简单任务用推理模型——overkill，白白烧钱又拖慢响应；它还不免疫幻觉，简单题上甚至可能"想太多"(overthink) 反而降准确率。
  • 别对高难任务用标准模型——准确率不够，Agent 会在关键步骤翻车，返工反而更贵。

系统性地"按任务难度把请求分派给不同模型"——便宜快的模型接简单活、贵而强的模型接硬骨头——这件事叫 Model Routing，是 L23 · 成本与 Model Routing 的核心主题。这一课你只需牢牢记住：推理深度是要花钱买的，按需采购。

Q 关于推理模型的成本，正确的说法是？
推理模型的那串内部思考（reasoning token）即便对用户隐藏，也照常计费、照常占用生成时间，所以它更慢也更贵。思考预算越大意味着能想得越深，但也更慢更贵，不是更便宜。这正是要做 Model Routing 的原因：让贵的推理模型只接真正需要它的硬任务。

5. 提示词差异：别替它安排思考步骤

一个反直觉的点：给推理模型写提示词，策略和标准模型不一样。

  • 对标准模型，你常靠 "let's think step by step" 这类 Chain-of-Thought 提示去逼它多想一步。
  • 对推理模型，它自己就会想——你通常不需要手写 step-by-step。过度堆叠 CoT 指令反而可能干扰它本就在做的内部推理。

正确姿势：给最简指令，把目标和约束说清楚就好，把"怎么推"交给模型自己。

对标准模型（需要引导思考）：
  "请一步一步思考（think step by step），先列出……再……最后……"

对推理模型（说清目标+约束即可）：
  "求解这道题。约束：只能用整数；答案需给出验证过程。"
  ← 不必再喊"一步步想"，它自己会打草稿

换句话说：标准模型你要"教它怎么想"，推理模型你只要"告诉它想什么"。提示的重心从"引导推理过程"转向"清晰定义任务与约束"。

⚠️ 常见误区：把老一套"让我们一步步思考"的长 CoT 模板原封不动套到推理模型上。对推理模型，这往往是多余甚至有害的——指令越简、目标与约束越清晰越好，别去替它安排思考步骤。

6. Agent 里怎么混合使用

把前五节合起来看，你会得到一个 Agent 开发的实战结论：不要全程用同一种模型，要混合。

  • 规划（planning）步骤：Agent 要拆解目标、决定先做什么后做什么、权衡多个约束——这是典型的多步推理，常受益于推理模型，值得为准确率多花钱。
  • 工具调用的每一小步：解析工具返回、填一个参数、格式化一段输出——这些大多是简单、定义明确的动作，用标准模型更划算，快且便宜。

于是一个成熟 Agent 的模型使用往往是混合的：硬骨头（规划、复杂决策）交给推理模型，杂活（大量小步工具调用）交给标准模型。怎么把这套"按难度分派"工程化、算清省了多少钱，就是 L23 · Model Routing 要讲的。

面试高频：「推理模型是什么？何时用？」
满分回答：推理模型在作答前先生成一长串内部思考（long chain-of-thought / reasoning tokens），再给最终答案，用 thinking budget（思考预算）换推理深度。何时用：简单、定义明确的任务用标准模型（更快更省），复杂、多步推理的任务（数学、复杂编码、多约束决策、长文档分析）才上推理模型；因为 reasoning token 也计费，对简单任务上推理模型是烧钱的 overkill。

Agent 场景练习：下面几个任务，各该用标准模型还是推理模型？先自己判断，再展开对照。

① 从一张发票里抽取"金额"字段 —— 点开看答案

标准模型。单步、定义明确、要快要便宜，是抽字段的典型场景。上推理模型属于 overkill，白烧钱又变慢。

② 解一道多步数学题并给出验证过程 —— 点开看答案

推理模型。需要逐步推演加自我检查，正是推理模型的强项；标准模型容易在中间步骤出错。提示上只需说清"求解 + 给验证"，不必手写 step-by-step。

③ 总结一份 50 页合同的风险点 —— 点开看答案

推理模型。长文档、需要综合多处条款、结论必须可靠——准确优先，值得为推理深度付费。

④ 把用户输入分类成「投诉 / 咨询 / 表扬」 —— 点开看答案

标准模型。模式清晰的单步分类，快且便宜。这类高频小任务正是 Agent 里该省钱的地方。

⑤ 在预算、工期、人力三重约束下排一个可行的项目计划 —— 点开看答案

推理模型。多约束权衡 + 多步规划，标准模型容易漏掉某个约束。这正对应 Agent 的 planning 步骤该用推理模型。

【两类模型】
  标准模型   ：问题 ─▶ 答案            （脱口而出，快、便宜）
  推理模型   ：问题 ─▶ [长草稿] ─▶ 答案 （先打草稿，慢、贵、更准）
  那串草稿 = reasoning tokens，通常对用户隐藏，但照常计费

【Extended Thinking（以 Claude 为例）】
  开 thinking 开关 + 设 budget_tokens（思考预算）
  预算大 ─▶ 想得深，但更慢更贵   ← 用 token 换推理深度
  budget_tokens 有上限、随版本变 → 以官方文档为准

【选哪个（决策规则）】
  简单 + 定义明确 + 要快要省      → 标准模型
  困难 / 多步 / 多约束 / 长文档   → 推理模型
  例：抽字段/分类/改写=标准；数学/复杂编码/合同风险=推理

【成本】
  reasoning token 也计费 → 推理模型更慢更贵
  别对简单任务上推理(烧钱) / 别对硬任务用标准(不准)
  按难度分派 = Model Routing（见 L23）

【提示词】
  标准模型：可能要写 "step by step" 引导思考
  推理模型：通常不用；指令越简越好，说清目标+约束即可

【Agent 混合用】
  规划/复杂决策 → 推理模型
  大量小步工具调用 → 标准模型

  • 标准模型脱口而出，推理模型先打草稿——后者在作答前生成一长串隐藏的 reasoning token
  • Extended Thinking 靠 thinking 开关 + budget_tokens 开启，本质是用 Token 预算换推理深度（上限以官方文档为准）
