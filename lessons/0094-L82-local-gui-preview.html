本地 GUI 预览与取消

有稳定接口就不绕道；必须走界面时，让取消经得起迟到的回调

为什么这课重要？

客服只想看一眼导出保留期草稿及依据。如果业务已经提供稳定、有授权的预览接口，绕到界面不仅多一次等待，还把稳定合同变成对按钮和页面布局的依赖。某个旧系统只能在自己的界面上显示预览，这才值得评估一条受限的 GUI 路径。本课用同一条合成政策做对照，不构造真正的浏览器助手。

学习目标

  • 用同一草稿与来源比较接口直读和旧界面预览，说明何时不引入 GUI。
  • 区分待处理、已显示和已取消，验证迟到回调不会发布已取消或已过期的结果。
  • 区分 Node 控制器验收与本机浏览器交互验收，记录各自未覆盖什么。

1. 同一个任务，只比较两条预览路径

固定夹具 l82-export-preview/v1 引用 Phase 7 合成政策 EXPORT-POLICY v1 §1 的原文。stable-interface 模拟同一应用内部有稳定读取接口，直接拿到正文和来源，不进入旧界面队列；这里没有 HTTP 或真实业务 API。legacy-gui 模拟缺少这个接口，在同一个本地 HTML 中发起预览并等待回调。两条路径对比的是交付合同和等待环节，不是测 UI 与 API 的实际吞吐。

{
  "route": "legacy-gui",
  "attempt": 1,
  "status": "previewed",
  "preview": {
    "text": "导出文件生成后保留 7 天。",
    "source": "EXPORT-POLICY/v1 §1（合成）"
  }
}

attempt 是同一控制器内递增的尝试编号，不是凭据；preview 是正文与来源组成的一个结果，待处理或取消时一并为空。「已预览」只说明这对内容已显示，不是批准、保存或送达。页面没有真实站点、登录、提交、外发、数据提取或网络调用，也不接受地址、任意选择器或截图目标。它只读本课写死的合成数据。

固定 worked 对照：队列和公开快照记录了什么
路径动作顺序可复核的结果
稳定接口 #1读取接口预览直接 previewed；排队 0 次；显示 7 天和同一来源
旧界面 #1请求预览 → 交付回调先 pending 且无内容；接受当前回调后 previewed，正文与来源和接口相同
旧界面 #2请求预览 → 取消 → 交付回调交付返回 false，前后均为 cancelled；正文、来源都不出现

2. 取消与回调分开验证，不靠抢时间

发起后从 idle 进入 pending；旧界面等当前回调才到成功终态 previewed，或在待处理时到取消终态 cancelled。取消并不撤回排队的回调：演练保留它，点击「交付最早的回调」实际执行，让拒绝可见。控制器只有在当前仍为 pending 且编号匹配时才接受完成。只判断待处理不够：取消 #1 后若已发起 #2，旧回调到来时 #2 恰好仍待处理。已完成的预览不能再用取消撤回；真正的业务写入、撤销与补偿不在本课范围。

本地页与 Node 都引用 gui/controller.js。用手动队列固定回调顺序，免用睡眠或碰运气；页面只把状态、预览和来源渲染到自己的固定区域。「已忽略」是交付记录变化，不是取消状态或预览内容变化。Node 可判定状态机，不能证明浏览器加载了脚本或按钮接线正确。

决策卡：接口优先，界面预览有条件

适用：同一只读交付确实缺少稳定、已授权的应用接口，能圈定固定界面和可核验的来源。不适用：界面漂移、来源不明或只剩高副作用操作；停止并转人工，不扩大能力。

误判：能看到界面，就用它代替接口

给原本直接可读的任务增加队列、误判和 UI 回归负担；还可能把「看到」误作「已保存」。

选择：同一交付，先拿接口基线

只有缺接口时再验证固定预览；正文和来源须同显，取消与完成须互斥，旧回调须拒绝。

代价与复议：即使只预览，也要维护界面绑定、来源合同与本机回归。如果稳定接口补齐，或界面变更使来源无法验证，重新选路，不增加浏览权限。

  1. 固定结果合同；对照有接口时不排队且结果完整。
  2. 分别验证正常完成、取消后回调和重试时旧回调，保留状态与来源。
  3. 分别记录 Node 与本机浏览器结果；浏览器不能运行就标未验证。
Q旧界面取消 #1 后发起 #2，#1 回调先到。接纳回调前应核对什么？
#2 正在 pending 并不能授权 #1 的回调；编号绑定回调与本次预览。两份正文相同也无法证明归属。
Q有授权的稳定接口已能返回同一份正文和来源。该怎么选？
稳定接口已满足同一交付合同。再加 GUI 会带来等待与绑定维护，当前没有补齐任何缺口。

3. 跟做：看见预览，再亲手交付迟到回调

高级 Agent 实验说明。课程网站不发布 GUI 夹具及源码。用可信课程检出，在本机 Chrome 或 Edge 的临时干净配置中打开 code/phase9-advanced-agent/advanced-lab/gui/preview.html 的 file: 地址。不要访问真实站点，也不因环境限制而关闭浏览器安全措施。若本机策略不允许，记录「浏览器未跑」，仍可独立跑 Node。

  1. 点「读取接口预览」：直接看到 previewed · #1、正文与来源；旧界面队列仍为 0。
  2. 点「请求预览」：右栏 pending · #1，正文和来源为空；点「交付最早的回调」才显示同样的正文与来源。
  3. 再次请求，然后先取消，再交付。交付标记「已忽略」，状态仍是 cancelled · #2，两项内容都为空。只看见取消状态、没交付回调，不能证明它会被忽略。

本机浏览器也可在新标签页打开末尾带 #browser-smoke 的同一个 file: 地址。页面加载时会触发固定按钮并核对状态、正文与来源，还验证旧回调先于新回调的重试。通过时页面显示 L82 BROWSER SMOKE PASSED。这验证浏览器接线与 DOM 输出，不等于人工视觉、键盘或真实站点验收。

从可信仓库根用已有 Node 18+ 和 Python 3.11+。可直接运行 node code/phase9-advanced-agent/advanced-lab/gui/run.cjs worked。将下方 Python 块分别保存或在仓库根执行，用 python -I -X utf8 文件名.py，不加 -O。独立单测入口：

独立变式：重试已在等待，第一次回调才到

不要只重放上一个取消案。取消 #1 后，不交付回调，立刻发起 #2；两条回调都在队列中。先写下每一步的预期快照，再交付 #1 并核对 #2 仍等待且预览为空。之后交付 #2 才允许显示；Node 再交付一次 #2 回调并尝试取消已完成的结果，两次都要被拒绝。

面试自查

Q1客服系统已有授权预览接口，团队展示了一条漂亮的界面路线，该上线吗？

参考回答：先验证接口是否完整交付正文与来源；若已满足合同，保留直读，避免无收益的等待和界面维护。

追问：接口只有正文，缺来源呢？

答题要点：先补接口或寻找可靠且已授权的来源；不能凭看起来相同的正文认定来源，也不默认开通 GUI。

Q2客服取消待处理预览，旧系统仍回了完整草稿，要显示吗？

参考回答：不要。取消是控制器终态，后来的回调只能被忽略，不能发布正文和来源。

追问：取消能证明上游完全停止了吗？

答题要点：不能。这里只验证本地不接纳结果；上游是否可中止，以及已发生的副作用能否补偿，是另一份合同。

Q3两次尝试生成同样的文字，旧回调先到时直接显示，风险在哪里？

参考回答：文字相同不能证明结果属于当前尝试。若状态与编号未绑定，旧回调可错误结束新任务；下次两份来源不同时更难发现。

追问：怎样稳定复验？

答题要点：先取消 #1、启动 #2，再按旧先新后交付；核对 #2 的待处理快照、空结果及正确终态，不靠延迟碰撞。

Q4Node 全绿，本机浏览器却被策略阻止，验收记录怎么写？

参考回答：明确写控制器已测、浏览器交互未跑；按钮接线、脚本本地加载和 DOM 输出仍需本机补验。

追问：本地浏览器冒烟也过了，能推断真实站点可用吗？

答题要点：不能，证据只覆盖固定文件和确定性按钮序列，不覆盖真实站点、授权、布局变化或业务提交。

小结与一手参考

先比稳定接口 → 缺接口才试固定预览 → 用状态与编号核对回调 → 正文、来源和终态一并验收。把控制器结果与浏览器结果分别记录。

  • WHATWG HTML · Event loops：浏览器异步任务的背景；本实验为可复验手动排序，不模拟浏览器调度。
  • WHATWG DOM · Aborting ongoing activities：中止需异步操作配合；本实验展示的是宿主拒收结果，不承诺中止上游。
  • Node.js · Test runner：用内置测试工具独立复验控制器。
