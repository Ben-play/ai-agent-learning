Phase 3 综合实战：多模型 Agent 客户端

把 L25–L37 学的全部串成一个"能上生产的 LLM 调用层"

💡 为什么这课重要？

Phase 3 的十几课，每一课都在解决一个单点问题：怎么发请求（L25）、怎么流式（L26）、怎么让模型调工具（L35）、怎么保证输出格式（L28）、怎么在失败时重试和切换（L31/L32）、怎么观测和降本（L33/L37）。它们现在还是一堆零件。

真实生产里，这些能力不是可选项，而是叠在同一次调用上的：一个 Agent 请求要能流式返回、能跑完整的工具循环、能在主模型挂掉时退避重试再切备用、能把最终答案约束成结构化 JSON、还要顺手把 token 和成本记下来。这一课我们把它们拼成一个客户端——一个 generate() 就把上面全部包住。它不是玩具，而是你从 Phase 4 起搭真正 Agent 架构时，反复复用的那一层调用底座。

⚠️ 老规矩：不假设你有 API key。下面代码结构正确、可 mock 跑通，key 从环境变量读（清楚标注位置）。所有成本数字都标了「示例」——它们演示的是形态，不是真实报价。

学习目标

完成本课后，你将能够：

  • 说清一个"生产级 LLM 调用层"要有哪几块能力，以及每块对应哪一课
  • 用 OpenAI 兼容 base_url 封装一个能切厂商的统一 client，key 从 env 读（L25/L32）
  • 包一层指数退避 + full jitter 重试，主模型失败自动切备用（L31/L32）
  • 嵌入一个完整的 Function Calling 循环，工具从 @tool registry 分发（L35/L36）
  • 用 Structured Outputs 或流式打字机组合出最终答案（L28/L26）
  • 从 usage 累加 token 与成本、超阈值告警、用缓存降本（L33/L37）

1. 项目目标 & 架构

我们要造的东西叫 AgentClient：对外只暴露一个 generate(messages, tools=...)，对内把 Phase 3 的能力层层包住。它的能力清单（每一项都对应一课）：

能力做什么来自哪一课
流式输出最终答案逐字蹦出，不干等L26
完整 FC 循环模型请求工具 → 执行 → 回填 → 继续L35

错误重试指数退避 + full jitter，扛住 429/5xxL31

原生缓存把稳定前缀缓存起来降本L37
成本追踪从 usage 累加 token/成本、超阈告警L33

下面我们从内往外一层层 build：先有能切厂商的 client（④），再包重试+Fallback（②③），再嵌 FC 循环（⑤），再拼最终答案（⑥），最后套上成本追踪（①）。

为什么是"一层层包"而不是"一个大函数"？ 每一层职责单一、能独立测试、能单独换实现——这正是 L32 讲的 AI Gateway 思路：把跨模型的通用能力（重试、Fallback、观测、缓存）从业务里抽出来，沉到一个统一的调用层。你现在是在手写一个迷你 Gateway。

2. Step 1 · 统一客户端（L25 / L32）

最内层：一个能切厂商的 client。L25 的关键技巧是——大多数厂商/网关都提供 OpenAI 兼容端点，所以你只用 openai 这一个 SDK，改 base_url + key 就能打到别家模型。L32 把它工程化：用一个供应商表登记每家的 base_url 和 env 变量名，按名字取 client。

import os
from openai import OpenAI

# 供应商表：每家登记「兼容端点 + key 从哪个环境变量读」
# ★ key 绝不写进代码，只写「变量名」，运行时从 env 取（L25 铁律）
PROVIDERS = {
    "primary":  {"base_url": "https://api.openai.com/v1",
                 "key_env": "OPENAI_API_KEY",   "model": "gpt-5.5"},
    "backup":   {"base_url": "https://api.anthropic.com/v1/",  # Anthropic 的 OpenAI 兼容端点（有限兼容：独门特性如 Extended Thinking 用不了；生产更稳的做法是走 LiteLLM 等网关，见 L32）
                 "key_env": "ANTHROPIC_API_KEY", "model": "claude-sonnet-4-6"},
}

def make_client(name: str) -> OpenAI:
    """按供应商名取一个 OpenAI 兼容 client。换厂商 ≈ 换 base_url + key。"""
    cfg = PROVIDERS[name]
    api_key = os.environ.get(cfg["key_env"])     # 没设 → None，交给上层决定 mock
    return OpenAI(api_key=api_key, base_url=cfg["base_url"])

def raw_call(name: str, messages: list, **kw):
    """最底层的一次真实调用：形状就是 L25 的 chat.completions.create。"""
    client = make_client(name)
    return client.chat.completions.create(
        model=PROVIDERS[name]["model"],
        messages=messages,
        **kw,                     # tools / temperature / stream / response_format 都从这透传
    )

注意这一层只负责"发一次请求"，不管重试、不管切换、不管工具循环。方法名 chat.completions.create、参数 model / messages 都是 L25 里的真实写法。上层要什么额外参数（tools、stream、response_format）都从 **kw 透传进来。

⚠️ 兼容模式很方便但不是 100% 等价（L25 提过）：各家独门特性（如 Claude 的 Extended Thinking）在兼容层下可能用不了。做多模型切换 / Fallback时它够用；要吃满某家能力就得用原生 SDK。这也是为什么 PROVIDERS 表里每家单独登记 model——同一个逻辑名，底下是不同厂商的具体型号。

3. Step 2 · 带重试 + Fallback 的调用（L31 / L32）

往外包一层。真实网络里，429（限流）和 5xx（服务端抖动）是常态而非异常。L31 的答案是指数退避 + full jitter：第 n 次重试等待 random(0, base·2ⁿ)，用抖动打散并发重试、避免"惊群"同时砸回去。L32 的答案是 Fallback：一个模型/厂商反复失败，就换一家接着试。

两者叠起来：对每个供应商先退避重试几次，全挂了再切下一个供应商。下面是结构正确的伪代码（标注了可 mock 的位置）：

import os, time, random

USE_MOCK = os.environ.get("OPENAI_API_KEY") is None   # 没 key → 整条链路走 mock

RETRYABLE = (429, 500, 502, 503, 504)   # 只重试「暂时性」错误；400/401 立刻抛(L31)

def call_with_retry(name, messages, max_retries=4, base=0.5, **kw):
    """对单个供应商：指数退避 + full jitter 重试 (L31)。"""
    for attempt in range(max_retries):
        try:
            if USE_MOCK:                       # —— mock：先跑通流程，不需要 key ——
                return _mock_response(messages, **kw)
            return raw_call(name, messages, **kw)   # —— 真实调用 (Step 1) ——
        except Exception as e:
            code = getattr(e, "status_code", None)
            if code not in RETRYABLE or attempt == max_retries - 1:
                raise                          # 不可重试 / 重试用尽 → 抛给 Fallback 层
            # full jitter：等待 random(0, base * 2**attempt)，打散并发重试(L31)
            time.sleep(random.uniform(0, base * (2 ** attempt)))

def call_with_fallback(messages, order=("primary", "backup"), **kw):
    """跨供应商 Fallback：主模型退避重试全挂了，切备用 (L32)。"""
    last_err = None
    for name in order:
        try:
            return call_with_retry(name, messages, **kw), name   # 返回响应 + 实际用了谁
        except Exception as e:
            last_err = e                       # 记下来，换下一家继续
    raise RuntimeError(f"所有供应商都失败了: {last_err}")

这一层是纯控制流：它不知道消息里有没有工具、答案是不是结构化的——它只保证"尽最大努力拿到一个响应回来"。call_with_fallback 顺手返回"实际用了哪个供应商"，方便上层观测（哪家在扛流量、哪家老失败）。_mock_response 是个占位函数，让你没 key 也能把整条链路跑通——它的样子在 Step 3 一并给出。

为什么 400/401 不重试？ L31 的核心区分：暂时性错误（429/5xx，等一下会好）才重试；确定性错误（400 请求错、401 key 错）重试一万次也没用，只会白烧钱和时间——要立刻抛出让人来修。把 RETRYABLE 写成一个明确的白名单，就是把这条纪律固化进代码。

4. Step 3 · Function Calling 循环（L35 / L36）

现在嵌入 Agent 的心脏：完整的 FC 循环。L35 讲过，一次工具调用不是一问一答，而是一个 while 循环：模型说"我要调工具" → 你执行 → 把结果回填进 messages → 再问模型 → …… 直到模型不再要工具、给出最终答案。工具本身从一个 @tool registry 来（L36）——注册即可用，循环里按名字 dispatch。

先看 registry（L36 的核心思想：装饰器登记 + 统一分发）：

import json

REGISTRY = {}      # 工具名 -> (函数, JSON schema)，一处登记、循环里查

def tool(schema):
    """@tool 装饰器：把一个函数注册成模型可调用的工具 (L36)。"""
    def deco(fn):
        REGISTRY[schema["function"]["name"]] = (fn, schema)
        return fn
    return deco

@tool({"type": "function", "function": {
    "name": "get_weather",
    "description": "查询某城市当前天气",
    "parameters": {"type": "object",
        "properties": {"city": {"type": "string", "description": "城市名"}},
        "required": ["city"]}}})
def get_weather(city: str) -> str:
    return f"{city} 现在 22°C 晴"      # 真实实现会去调天气 API

def tool_specs():
    """把所有已注册工具的 schema 汇成 tools= 参数 (L34 的 schema 设计)。"""
    return [schema for _, schema in REGISTRY.values()]

再看循环本身——这是把前面所有层用起来的地方（调用走 call_with_fallback，天然带上了重试和 Fallback）：

def run_tool_loop(messages, max_turns=6):
    """完整 FC 循环 (L35)：工具请求 → dispatch → 回填 → 继续。"""
    for _ in range(max_turns):
        resp, _used = call_with_fallback(messages, tools=tool_specs())
        msg = resp.choices[0].message           # L25 的回复取法

        if not msg.tool_calls:                  # 模型不要工具了 → 这就是最终答案
            messages.append(msg)                # 把最终这轮也 append 进历史，供收尾复用
            return msg

        messages.append(msg)                    # 先把「模型的工具请求」回填进历史
        for call in msg.tool_calls:             # 可能一次请求多个工具，逐个执行
            fn, _ = REGISTRY[call.function.name]           # 按名字 dispatch (L36)
            args = json.loads(call.function.arguments)     # 参数是 JSON 字符串，要 loads
            result = fn(**args)                            # 真正执行工具
            messages.append({                    # 结果回填，用 tool_call_id 对上号
                "role": "tool",
                "tool_call_id": call.id,
                "content": json.dumps(result, ensure_ascii=False),
            })
    raise RuntimeError("工具循环超过最大轮数，可能陷入死循环")

三个 L35 的关键点，都是真实字段名：① 从 msg.tool_calls 读模型的工具请求；② 每个工具结果用 role:"tool" + tool_call_id 回填，tool_call_id 必须和请求对上否则模型接不上；③ 参数是 JSON 字符串，要 json.loads，结果回填时 json.dumps。还有个安全阀：max_turns 上限，防止模型和工具互相纠缠陷入死循环（真实 Agent 常见事故）。

顺带补上 Step 2 欠的 mock——它要能模拟这个循环（第一次假装要调工具，第二次给最终答案），这样没 key 也能验证整条链路：

class _M:                       # 极简的 mock 响应对象，模仿 SDK 的返回结构
    def __init__(self, **kw): self.__dict__.update(kw)

def _mock_response(messages, **kw):
    """没 key 时的降级响应：模拟「一次工具调用 + 一次最终答案」。"""
    called = any(m.get("role") == "tool" for m in messages)
    if kw.get("tools") and not called:          # 第一轮：假装模型要调 get_weather
        tc = _M(id="call_1", function=_M(name="get_weather",
                                         arguments='{"city": "北京"}'))
        message = _M(tool_calls=[tc], content=None)
    else:                                        # 第二轮：给最终答案，无 tool_calls
        message = _M(tool_calls=None, content="[MOCK] 北京现在 22°C 晴。")
    usage = _M(prompt_tokens=120, completion_tokens=30)   # 假的 usage，供成本层累加
    return _M(choices=[_M(message=message)], usage=usage)
Q FC 循环里，工具执行完的结果要怎么交回给模型？
工具结果必须作为一条 {"role": "tool", "tool_call_id": ..., "content": ...} 消息回填进 messages，且 tool_call_id 要和模型那次 tool_calls 请求里的 id 严格对上号（L35）——模型靠这个 id 把"我问的工具"和"你给的结果"配对。塞进普通 user 消息、或走别的接口，模型都接不上。LLM 无状态，服务端不会替你存循环状态。

5. Step 4 · 结构化输出 + 流式（L28 / L26）

循环跑完，模型给出最终答案。这时有两种"收尾方式"，按场景二选一（或组合）：

  • 要机器消费 → Structured Outputs（L28）：最终答案要被下游代码解析（存库、传给下一个服务），就用约束解码保证它一定是合法 JSON、一定符合 schema。做法是在最后一次调用（工具循环结束、要最终答案那次）带上 response_format。
  • 要给人看 → 流式打字机（L26）：最终答案是给用户读的，就 stream=True，逐 chunk 把 delta.content 打出来，像 ChatGPT 一样即时。

怎么组合进我们的 generate()？关键洞察：结构化 vs 流式，只作用在"最终那次调用"上，不影响中间的工具循环。工具循环里的调用照常（要拿 tool_calls），只有确认无工具、要出最终答案时，才按 output 参数切换收尾方式：

# 结构化收尾：给最后一次调用挂上 response_format (L28)
FINAL_SCHEMA = {"type": "json_schema", "json_schema": {
    "name": "answer",
    "schema": {"type": "object",
        "properties": {"summary": {"type": "string"},
                       "confidence": {"type": "number"}},
        "required": ["summary", "confidence"],
        "additionalProperties": False},
    "strict": True}}

def finalize(messages, output="text"):
    """收尾：结构化 or 流式，二选一。中间的工具循环不受影响。"""
    if output == "json":                         # 机器消费：约束成固定 schema (L28)
        resp, _ = call_with_fallback(messages, response_format=FINAL_SCHEMA)
        return json.loads(resp.choices[0].message.content)   # 保证能 loads 成功

    if output == "stream":                       # 给人看：逐字打字机 (L26)
        stream, _ = call_with_fallback(messages, stream=True)
        chunks = []
        for ch in stream:                        # 遍历 chunk，累加 delta.content
            piece = ch.choices[0].delta.content or ""
            chunks.append(piece)
            print(piece, end="", flush=True)     # flush=True 才即时(L26)
        return "".join(chunks)

    return call_with_fallback(messages)[0].choices[0].message.content

这就是"组合"的含义：同一个客户端，同一条重试/Fallback 链路，尾部按需切换成结构化或流式。L28 提醒过——结构化输出和流式可以并存（一边流一边保证最终是合法 JSON），但也各有代价（结构化首次编译 schema 略慢、流式要自己拼 chunk），按"给人还是给机器"来选最省心。

Q 在这个客户端里，Structured Outputs 应该加在哪一步？
结构化输出（L28）只作用在最终答案上——工具循环中间的调用需要模型返回 tool_calls（那是模型在"要工具"，不是最终结果），若也强制成业务 schema 会打断循环。所以正确做法是：循环内照常调，确认无工具、要出最终答案的那一次才挂 response_format。这跟"流式只作用在最终收尾"是同一个道理。

6. Step 5 · 成本追踪 + 可观测（L33 / L37）

最外层：成本追踪。L33 的核心是——生产系统要能回答"它现在花了多少钱、慢不慢、谁在失败"。每次调用的 usage 字段（prompt_tokens / completion_tokens）就是账单原料（L37）。我们做个累加器：每次调用记 token、按单价折算成本、超阈值告警。

# 单价用「示例」值：真实价格请查各厂商官网，这里只演示算法
# 单位：美元 / 每百万 token（输出通常是输入的 3~5 倍，见 L37）
PRICE = {   # 模型名: (输入价/百万, 输出价/百万) —— 均为示例，非真实报价
    "gpt-5.5":            (5.0, 25.0),
    "claude-sonnet-4-6":  (3.0, 15.0),
}

class CostTracker:
    """从 usage 累加 token 与成本，超阈值告警 (L33/L37)。"""
    def __init__(self, alert_usd=1.0):
        self.calls = 0; self.in_tok = 0; self.out_tok = 0
        self.cost = 0.0; self.alert_usd = alert_usd

    def record(self, model: str, usage) -> None:
        in_p, out_p = PRICE[model]
        self.calls += 1
        self.in_tok  += usage.prompt_tokens          # L25 的 usage 字段
        self.out_tok += usage.completion_tokens
        self.cost += (usage.prompt_tokens * in_p
                      + usage.completion_tokens * out_p) / 1_000_000
        if self.cost > self.alert_usd:               # 超阈值 → 告警(L33)
            print(f"⚠️ 成本告警：累计已达 ${self.cost:.4f}（阈值 ${self.alert_usd}）")

    def report(self) -> dict:
        return {"调用数": self.calls, "总输入token": self.in_tok,
                "总输出token": self.out_tok, "总成本USD": round(self.cost, 6)}

把它挂到最外层——generate() 每完成一次底层调用，就 tracker.record(...) 一下。跑几轮（含一次工具往返）后，report() 长这样（下面所有数字都是"示例"，token 数按 mock 的 usage 算、金额按示例单价算）：

┌───────────────┬──────────┐
│ 指标          │ 值(示例) │
├───────────────┼──────────┤
│ 调用数        │    3     │   ← 2 次工具往返 + 1 次最终答案
│ 总输入 token  │   360    │
│ 总输出 token  │    90    │
│ 总成本 (USD)  │ 0.00405  │   ← 按示例单价折算，非真实报价
└───────────────┴──────────┘

成本能看见了，就能动手降它。L37 最省力的杠杆是原生 Prompt Caching：把稳定不变的前缀（长 system prompt、工具 schema、少样本示例）标记缓存，重复请求时这部分只按约 0.1× 单价计费。它对我们的客户端尤其划算——因为工具循环里 system + tool schema 每一轮都重发，缓存一次、循环内全程复用，省的就是这块反复重发的钱。

成本追踪不只是记账，更是"控制回路"。 L33 的意义在于：先看得见（每次 record），才谈得上控制（超阈告警、按供应商归因谁贵）。真实生产里你会把这些数据发到 OTel / 监控面板，而不是 print；但心智模型一样——从 usage 采集 → 折算成本 → 触发告警/优化。缓存降本的效果，也正是靠这个追踪器量化出来的（缓存前后跑一遍，对比总成本）。
🧪 进阶挑战：给这个客户端接上 OTel 分布式追踪（点开看思路）

print 告警在生产里不够用——你需要把每次调用变成一条结构化 span，串成一次完整请求的调用链（哪层重试了、切了哪个供应商、工具循环跑了几轮、各花多少 token）。L33 讲的 OpenTelemetry GenAI 语义约定正是干这个的：给每次 LLM 调用打上标准化属性（gen_ai.request.model、gen_ai.usage.input_tokens …）。思路草图：

from opentelemetry import trace
tracer = trace.get_tracer("agent-client")

def raw_call_traced(name, messages, **kw):
    # 每次底层调用包一个 span，属性走 OTel GenAI 语义约定 (L33)
    with tracer.start_as_current_span("chat.completions") as span:
        span.set_attribute("gen_ai.system", name)                 # 用了哪个供应商
        span.set_attribute("gen_ai.request.model", PROVIDERS[name]["model"])
        resp = raw_call(name, messages, **kw)                     # Step 1 的真实调用
        u = resp.usage
        span.set_attribute("gen_ai.usage.input_tokens",  u.prompt_tokens)
        span.set_attribute("gen_ai.usage.output_tokens", u.completion_tokens)
        return resp

三个要点：① span 要嵌套——外层 generate 一个大 span，里面每次底层调用一个子 span，重试和 Fallback 就在链路上一目了然；② 用 L33 的标准属性名（gen_ai.*），这样任何支持 OTel 的后端（Jaeger / Grafana / Datadog）都认；③ 别把完整 prompt/响应正文塞进 span 属性（可能含敏感数据、也撑爆存储），只记元数据（模型、token、耗时、是否失败）。接上之后，CostTracker 的累加逻辑可以直接从 span 数据聚合，账本和链路合二为一。

7. 收尾：你造出了一个"生产级 LLM 调用层"

把五步拼起来，AgentClient.generate() 现在是这个样子——一次调用穿过全部七层能力：

class AgentClient:
    def __init__(self):
        self.cost = CostTracker(alert_usd=1.0)     # ① 成本追踪 (L33/L37)

    def generate(self, messages, output="text"):
        """一个方法，包住 Phase 3 全部能力。"""
        # ⑤ FC 循环(L35) 内部走 ②重试(L31) + ③Fallback(L32) + ④统一client(L25)
        final_msg = run_tool_loop(messages)   # 工具全跑完，final_msg 是模型的最终回答
        # ⑥ 收尾：text 直接用循环拿到的答案（不重复调用）；
        #        json/stream 才需要对已完成的对话再跑一次，换成结构化 / 流式形态(L28/L26)
        if output == "text":
            return final_msg.content
        return finalize(messages, output=output)

# —— 没 key 也能跑（走 mock），验证整条链路 ——
client = AgentClient()
answer = client.generate(
    [{"role": "user", "content": "北京今天天气怎么样？"}],
    output="text")
print(answer)                    # [MOCK] 北京现在 22°C 晴。
print(client.cost.report())      # {'调用数': ..., '总成本USD': ...}（示例值）

这层东西的价值在于：业务代码从此只跟 generate() 打交道。上层写 Agent 时，不用再操心"这次要不要重试、主模型挂了切哪个、token 记没记"——那些都被这一层吃掉了。这正是 Phase 4 起我们要做的事：在这个稳固的调用底座之上，搭真正的 Agent 架构（规划、记忆、多工具编排、多智能体协作）。你现在拥有的，是所有那些高级架构最终都要落到的那一次次可靠的 LLM 调用。

总结

  • 生产级 LLM 调用层 = 把 Phase 3 的能力叠在同一次调用上，而不是散着用
  • 架构是洋葱式：成本追踪 ⊃ 重试 ⊃ Fallback ⊃ 统一 client ⊃ FC 循环 ⊃（结构化 | 流式）
  • Step 1：OpenAI 兼容 base_url + 供应商表，一套 SDK 切厂商，key 走 env（L25/L32）
  • Step 2：指数退避 + full jitter 重试，主模型全挂再切备用；400/401 立刻抛（L31/L32）
  • Step 3：完整 FC 循环，工具从 @tool registry dispatch，结果用 tool_call_id 回填，设 max_turns（L35/L36）
  • Step 4：收尾按场景切换——机器消费用 Structured Outputs、给人看用流式，只作用在最终那次调用（L28/L26）
  • Step 5：从 usage 累加 token/成本、超阈告警、用原生缓存降本（L33/L37）
  • 成品是 generate() 一个方法——业务代码从此只跟它打交道
